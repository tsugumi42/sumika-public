### 具体参数、禁止的偷懒写法、已知的坑、验收

`channel_gaps` 是毫秒闭区间，状态 open（等待扫描）、blocked（未证实覆盖、停止自动）、filled（已证明完整）、abandoned（旧版停止自动）；running 只属于任务。ADR-278：open 与迁移恢复且 last_try_ms=0 的 blocked 才参与自动扫描；扫过一次仍不能证明即 blocked，不再定时重查。budget 尚未扫到仍保持 open。blocked 纳入 RemainingOpen 以表达尚未完整，不表示会自动重试。新尾段不与已扫描 blocked 合并，不复活旧洞；私聊、空号群和缓存均照此处理。

R01 → `TestAlignmentExistingCoverageContract`、`TestBackfillUnprovenCoverage`：扫描衔接与完整覆盖分开；202 条缓存端点、未知首页中段、手动右锚点零新增、新私聊空页均不得无证据消洞。HistoryPage.Continuous 只能由有明确连续性保证的协议提供；Latest、本地末条、锚点重合和越过起点单独都不够。当前 SnowLuma 不提供 Continuous。

ADR-278 第 2 条新增群序号证明：历史消息的 `message_seq` 来自本机协议端 2.4.0 `convertGroupMessage` 的 `event.msgSeq`（只读 `index.mjs:23102–23126`）；`real_id` 仍只是 `message_id` 别名。适配器仅给群历史填 `Inbound.MessageSeq`，无有效正 int64 时记 0，消息仍可补录。群取回的不同消息须各有不同有效序号，去重后 `max-min=条数-1`，跨页同消息的时间和序号一致；已提交消息的首尾时间包住缺口才可 filled，不将缓存首页时间扩展到现在。私聊序号是发送方局部值，不参与此证明。参考 Telegram `PtsWaiter::check` 的计数相等才推进、LuckyLilliaBot 的空号不能猜漏信数量；不借其并发或持续追洞。

字段形状 × 入口：群数字 / 数字串为有效正 int64 时，historyPageInbound 处理、自动 / 手动 conversation 共用证明；缺 / 空 / null / 0 / 负 / 小数 / 溢出 / 对象 / 布尔均失去证明但保留消息。QQ 私聊统一忽略 message_seq；本地私聊、本地群聊无此入口。仓库 testdata 只读核对为编造对拍样本，没有真实历史录帧；本次不声称真机完整性实测。回归为 TestHistoryGroupSequenceBoundary、TestBackfillGroupSequenceCoverage。

## 一、后台接口、状态与四种场合

### 技术路线

桌面读取与动作分为可选的 `api.GapReader`、`api.BackfillActions` 和 `api.GapAcknowledgements`，由 app 的桌面适配层注入；不把写动作加入基础 Reader。沿用 Result / Snapshot / Subscription：先订阅后读初值，版本仅订阅内递增，发布值不再修改，Close 等到查询 / 发布退出。UI 后台只传快照，不持有界面元素跨线程。

以下为计划契约，具体 Go 声明在实施时落入 `internal/api`：

| 方法 | 入参 / 返回 | 合同 |
|---|---|---|
| `ReadGaps(ctx, GapQuery)` | `Result[List[GapView]]` | Query 带 ConversationKey、Character、FromMS / ToMS、Cursor、Limit。时间范围只用于读；返回相交的 open / blocked / abandoned，按 from_ms、id 排；空消息会话允许无时间窗，按游标分页。会话、观察筛选、能力判断复用当前消息读取边界 |
| `WatchGaps(ctx, GapQuery)` | `Subscription[List[GapView]]` | 同一查询窗口有变化就重查；合并后的旧 ID 从快照移除；和消息订阅使用同一会话变更源，不能只靠新增 seq |
| `ReadAlignmentGaps(ctx, Cursor, Limit)` | `Result[List[GapView]]` | 第 1 / 5 步增加的当前账号登记缺口分页，供状态页和 ctl；私聊限定当前 self，范围外群保留可读但不可重试，游标绑定账号。不会在 ConversationKey 为空时把 ReadGaps 放宽成全账号 |
| `WatchAlignment(ctx)` | `Subscription[AlignmentView]` | 当前活动账号的最近尝试、正在运行的任务、全账号缺口 / 媒体分项汇总；没有做过返回“尚未对齐”，不造当前时间 |
| `RequestGapBackfill(ctx, GapRef)` | `BackfillJob` | Ref 为 ConversationKey、ID、FromMS / ToMS；后台重新读行并核对区间，只补这一条。filled 复用已证实的原任务；没有原任务时只返回处理结束，不合成 CompleteCoverage=true。ID 消失 / 合并改范围返回 stale-gap 并要求刷新 |
| `RequestAlignment(ctx)` | `BackfillJob` | 与自动轮次同一工作队列；检查当前账号全部合规会话和媒体，不扩大范围、不重启接收 |
| `WatchBackfill(ctx, JobID)` | `Subscription[BackfillJob]` | 初始给当前任务，终局保留到后续替换；请求上下文只约束接收请求，关闭订阅 / 切会话不取消后台任务 |
| `SetGapAcknowledged(ctx, GapRef, bool)` | `GapView` | 当前准入范围内 blocked 的独立提醒确认；true 保留首次确认时间，false 撤销。重读原区间，不算填平、不推进水位、不挡手动补录；界面以后接 |

GapView 包含 GapRef、reason、state、tries、lastTryMS、createdMS、updatedMS、AcknowledgedMS、原始条数 1、当前 JobID、CanRetry 和 RetryAfterMS。AcknowledgedMS 非零用于停止主动提醒，记录仍可查询。运行状态只在 BackfillJob（queued / running / completed / failed / canceled），不写进 channel_gaps。

BackfillJob 包含 ID、Scope（account / gap）、Trigger（connected / reconnect / retry / manual）、起止时间、当前会话、已查页数、已新入库条数、去重条数、已检查 / 待检查会话数、短原因。历史总条数未知，不给百分比。“completed”仅表示本轮处理结束；同时返回完整覆盖与否，不能等同于没有缺口。

AlignmentView 把消息轮次和媒体阶段分开：LastAttempt、CurrentJob、RemainingOpen、RemainingAbandoned、Media（queued / running / downloaded / expired / failed / awaitingManual / skipped）。各计数带统计范围和 AsOfMS；后台状态汇总限定当前账号合规会话，聊天视图保留自己的 Character 过滤，二者不混称同一范围。

仅为最近对齐新增一张平台聊天库表 `channel_alignment_latest`，迁移编号按实施时最新编号顺延。键 `(account, slot)`，slot 为 active / last，至多两行；保存 JobID、scope、目标缺口 ID（账号任务为空）、trigger、state、started_ms、ended_ms、新提交 / 去重条数、消息阶段结果、媒体阶段结果及固定短原因，不保存消息正文、URL、令牌或名字。终局在事务内替换 last 并删除 active；重启发现 active 记 canceled / interrupted，不能冒充完成；archive 只读它并把遗留 active 显示为“上次未完成”。最近一次若只补某缺口，明确标“单段补录”；上次失败不能写成上次成功。缺口余数每次现查，不把旧轮次里的余数冒充当前值；不新增无限增长的任务历史。

### 具体参数

| 项 | 值 |
|---|---|
| 查询 | 默认 100 个缺口、上限 200；使用 `(from_ms,id)` 不透明游标；5 秒查询时限，与 Reader 一致 |
| 并发 | 当前活动账号最多 1 个历史工作任务；相同 GapRef 重复点击返回同一任务；全量任务重复请求合并 |
| 排队 | 自动 / 全量任务运行时，单段请求排在当前会话完成后；待处理单段最多 16 个，满则 `busy`，不占入库队列等待 |

| 持久化 | 任务开始、消息阶段结束、媒体阶段结束、终局写快照；页数和字节进度只在内存，不每帧写库 |

## 二、聊天记录里的缺口分隔

### 技术路线

消息仍以 `(created_at, seq)` 正序排列、按 EventRef 去重；宿主在展示行模型中插入独立 GapRow，key 为平台 / 会话 / gap ID。真实消息的 key 不因缺口增删变化。缺口不写 events、不占未读、不参与复制聊天原文、搜索原文、模型上下文、观察或记忆。它中断两边的气泡分组与头像连接，避免画成连续对话。

缺口行放在 from_ms 的时间边界：该时刻的日期标记之后、第一条 created_at ≥ from_ms 的真实消息之前；跨多天只放一行，文案写全起止日期，不制造不存在的每日消息。缺口覆盖了仍有的消息时，显示“这段记录不完整”，保留真实消息，不说整段一条都没有。区间在本地最新消息之后时放末尾；窗口只加载了相交部分时，在该加载窗口边缘放同一个 GapRow，前页加载后按 ID 移动，不能叠第二条。没有真实消息的会话仍能显示缺口。

用 MewTypeUI `chat.ServiceMessage` 画居中服务文字；日期仍用 DateMarker。下面用已存在的 `settings.Button`（无图标、Light 样式）放“补录这一段”，位于同一 GapRow 的动作区，复用其禁用、键盘和涟漪行为；不在 ServiceOptions 塞不存在的子组件。颜色、字体、边距来自 Service / Settings 主题，不手写另一套胶囊。

### 具体参数与文案

| 条件 | 服务消息与动作 |
|---|---|
| open、空档没有现存消息 | “这里缺了 11 月 3 日 10:20 到 10:45 的消息”；下一行“可以重试”，按钮“补录这一段” |
| 与现存消息交错 / unverified-head | “11 月 3 日 10:20 到 10:45 的记录尚未确认完整”；不宣称缺了已知条数 |
| blocked / unverified-history | “这段记录尚未确认完整 · 已停止自动重查”；可手动补录或确认停止提醒；确认后仍可在缺口列表查询和撤销 |
| 排队 / 运行 | “等待补录” / “正在补录 · 已查 2 页，补回 37 条”；同目标按钮禁用，不显示虚假百分比 |
| abandoned | “暂时补不回来了 · 已停止自动重试”，接人话原因；有能力时仍给“补录这一段”，不把它等同平台已永久删除 |
| filled | 消息提交与连续覆盖结算后移除缺口行；媒体未完成仍在各媒体原位置显示状态 |
| 未连 / 只读 / 范围外 | 保留分隔和原因；按钮禁用，写“连接并开始接收后可补录” / “不在当前补录范围”等实际原因 |

| reason | 人话原因 |
|---|---|
| page-cap | “这次能取到的历史页数有限，前面仍没接上”（私聊可补充“当前协议端私聊只能取最近一页”） |
| unverified-head / unverified-history | “还不能确认平台返回的记录完整” |
| no-anchor | “平台没有返回能与本地衔接的记录” |
| stalled / broken-page | “平台返回的历史没有继续往前” / “平台历史的分页没有接上” |
| call-failed | “向平台取历史失败，可重试”；具体脱敏短原因放详情 |
| budget | “本轮查询额度用完，等待下一轮”；不称过期，不消耗取不到的重试次数 |
| unsupported | “当前协议端不支持补录历史” |
| outage / 未知 | “断开期间的记录尚未核对” / “记录尚未确认完整”；详情保留 reason 代码 |

展示合并只针对同会话、同状态、同 reason、同确认状态、相邻或重叠且之间没有真实消息的区间；相邻为至多 1 ms。存储仅合并待扫描 open / 未扫描 blocked，已扫描或确认的 blocked 保留原 ID 和范围；filled / abandoned 不参与合并。展示保留每个子 GapRef，原始缺口数不随折叠减少；连续 3 行以上可折叠，展开按页 100 个列出，动作仍逐段，不扩大范围。

折叠只覆盖当前已读取的一批；跨分页时写“本页 N 处，还有更多”，下一页延续列表，不把本页数量冒充完整区间总数。总缺口数由后台汇总另给，不能用 HasMore 推算。

默认字号下主体最多两行概括，细原因折叠；窗口变窄 / 字号放大允许自然增高，不能截掉起止时间或按钮。按钮命中区至少 24×24 DIP（沿用设计自查的最低检查），键盘 Tab 可达、Enter / Space 激活。100% / 125% / 150% 缩放和明暗主题按 token 验证。

### 禁止的偷懒写法与已知的坑

禁止按长时间无人说话自动画缺口；只有已持久登记的未知区间才画。禁止把 `abandoned`、404、查不到旧锚点统一翻译成“已过期”。from / to 原始值是毫秒 UTC，展示转本地时区；同日可省重复日期，跨日 / 跨年写全，只有边界不明的旧提示不能编一个 00:00。缺口是覆盖不确定性，不能用时间差 / message_seq 差估出缺失条数。

## 三、手动补录这一段与滚动锚点

### 技术路线

点击 → RequestGapBackfill → 协调器任务队列 → 重读缺口和准入 → 复用 conversation 的历史取页 / 覆盖判断 → 仅提交 `[from_ms,to_ms]` 的合法消息 → Ticket 完成 → 结算该缺口 → 消息及缺口订阅刷新。

自动和手动共用 conversation。群优先选本地右边界或之后的合法消息作分页锚点；锚点只证明扫描位置，不证明完整。没有右锚点时从首页取；QQ 私聊仅无锚点首页。范围外消息只用于扫描，不为单段任务写进其他时段。

填平接受 ADR-278 的群无空号序号证明（或协议显式 Continuous 完整保证），须覆盖目标两端且目标消息已提交；手动零新增不合成完整覆盖。无证明时 open / blocked 为 blocked，abandoned 保持原状；自动 tries / last_try_ms 不变。缺页锚点不拦手动向更旧消息继续，仍限五页；手动不推进两类位置、不新建范围外缺口、不填邻段。短页、空页不作完整保证。

消息插入前保存当前第一个可见真实消息 EventRef 和它相对视口顶的 DIP 偏移；批量合并、GapRow 移除、图片占位测高后按同一消息恢复。当前屏只有缺口 / 占位时取后继真实消息，没后继取前驱，均无则保持空视口。用户在任务中滚动，以提交前最新视口重新取锚点，不能用点击时的旧锚点把用户拉回。切会话不取消后台任务，结果只更新对应会话缓存；返回时用该会话的锚点。

### 具体参数

沿用每页 100、群最多 5 页、SnowLuma 私聊 1 页、全账号一轮 120 次协议查询、同一时刻 1 个、查询至少间隔 2 秒、单次 45 秒。单段任务最多群 5 / 私聊 1 次历史请求，接在协调器预算内，不开绕过 get_msg 的独立限速器，不因连点重置 120 次预算。每个 Gap ID 的手动尝试间隔至少 10 分钟；首次手动可不等自动重试冷却，连续手动则以持久手动尝试时间判断，合并行继承最大时间，重启不清零。此时间以新增 `last_manual_ms` 列存 channel_gaps，失败也记录；与自动 last_try_ms / tries 分开。

任务接受后在 100 ms 反馈目标内显示排队 / 正在补（第六节量测），显示页数和新提交条数；重复平台消息只计去重，不计“补回”。完成提示区分“这段已补齐”“补回 N 条，仍有缺口”“已结束，媒体仍在下载”。取消宿主 / 断线时沿用 stop 等旧任务和已开始 Ticket 收尾的顺序；不为本功能增加一套 UI 取消协议。

### 禁止的偷懒写法与已知的坑

不直接调适配器 HistoryPage 绕过协调器；不按文字 / 时间猜去重；不将新插入的 seq 当作展示时间；不清空整段已加载历史再回到底部；不把历史补入当 live Reveal / 发送飞行动画。持久保存 ui.Handle 和状态，不能保存跨帧 Element。断线时可能已补回一部分，canceled 仍须给真实已提交计数。

## 四、连上平台自动对齐与媒体

### 技术路线

继续使用 `sink.Status` 的连接事件。连接已核对当前账号、适配器 Ready 后才启动网络恢复；重复 connected 合并，断线先取消并等待旧任务。现有历史协调器等待 Ready 最多 60 秒、稳定 30 秒；没有 open 且距上轮不足 10 分钟会延后，延后不提前推进水位；持续在线每分钟检查到期缺口。同一个连接协调器确认 Ready 后先开启共享预算，再立即请求媒体 / 转发 Resweep，不等历史的 30 秒防抖；账号自动轮次不再重复补扫，手动账号轮次仍可请求补扫，工人 Start 不另扫。

新增“对齐轮次”只把这些已有步骤关联起来：连接就绪 → 记录消息任务和媒体扫描代次 → 补录入库的新媒体同轮登记 → 消息阶段结束 → 扫描完成且本轮自动下载任务均终局 / 等手动 → 汇总。允许下载与历史拉取并行，协议查询仍串行共享预算；下载延期重试就显示“媒体等待重试”，不靠固定超时宣称完成。同段去重只算一次；重复连接不产生第二批下载。轮次归属用任务 ID 和本轮媒体目标集，不等待不相关的用户大文件任务，也不漏等本轮刚补入的媒体。

未来 NapCat、LuckyLilliaBot 等由适配器声明 History 能力及来源 / 锚点合同，接同一生命周期入口。只有动作名字相同不等于能力相同；当前实现仍是 SnowLuma，NapCat 未经契约与真机验证不得标“已支持”。未知能力返回 unsupported，保留缺口，不假装空历史。

## 五、托盘、后台状态、设置与 sumika-ctl

### 技术路线

三个界面和 ctl 读取同一 AlignmentView；入口动作都委托 BackfillActions。托盘一行摘要“最近对齐 10:45 · 补回 37 条 · 剩 2 处”，另有“立即对齐聊天和媒体”“查看补录缺口”。后台状态页展示消息阶段、媒体阶段和缺口分页列表；设置的“平台账号”区域显示同一摘要和动作，不再建立独立进度模型。设置用 MewTypeUI SectionTitle / Button / DividerContent，长原因展开；托盘只给摘要，不塞聊天正文或长错误。

最近一次时间用 ended_ms；正在运行另显示 started_ms、排队 / 当前步骤。失败 / 中断和只补单段的范围写明。补回条数是本轮真实新提交事件；剩余缺口 = open + blocked + abandoned 原始记录数，RemainingOpen 合计 open / blocked，另列已停自动和排除当前范围。计数不是缺失消息条数。媒体分开列，不与消息数相加。

### 具体参数与 ctl 契约

继续用当前用户命名管道、v1 JSON 一行一个请求 / 回复，原 64 KiB 请求限制和 I/O 时限不变；仅扩展命令与 data 类型。命令写法：

```
sumika-ctl backfill status [--json]
sumika-ctl backfill gaps [--cursor <游标>] [-n 100] [--json]
sumika-ctl backfill retry <缺口句柄> [--json]
sumika-ctl backfill run [--json]
```

线上 cmd 为 backfill，args 的首项分别为 status / gaps / retry / run。gaps 的 n 取 1..200，默认 100；新增可选 cursor 字段，仅 gaps 接受。其余子命令带 n / cursor / wait 等不相干参数一律 invalid。这里不加长连接 / --wait：retry / run 当场回 accepted、JobID、scope、state；通过 status 读进度。accepted 只代表任务接收，不能打印“已补齐”。

gaps 输出 data 为 items、nextCursor、hasMore、asOfMS、范围；每项为 gapHandle、maskedConversation、fromMS / toMS、state、reason、canRetry、retryAfterMS、jobID。不输出消息正文、原始 URL、完整号码或本地文件路径。缺口句柄使用现有 HMAC 句柄设施，域分离输入 `gap + 平台 + 当前账号 + 会话 + ID + from_ms + to_ms`，仍取 8 个小写十六进制字符；后台在当前读取范围的行中解析，冲突回 invalid，不能选择第一条；合并改变范围后旧句柄失效。不接受裸数据库 ID、任意时间 / SQL / 路径作为补录命令。

status 的 data 与界面统计语义一致，含 LastAttempt / CurrentJob、remainingOpen / remainingAbandoned / excluded、媒体分项和能力原因；ctlproto 自己定义传输 DTO，客户端仍只依赖 ctlproto，不 import api / app。自由文本走现有脱敏和 ctlproto.Clean，JSON 及文本输出都清终端控制字符；日志只写固定命令、结果码和任务 ID。

错误码继续使用 invalid / denied / readonly / demo / failed / timeout / version；新能力的 busy / cooldown / unavailable / stale-gap 用 failed 的 data.reasonCode 说明，非法句柄用 invalid；退出码保持 0 / 1 / 2 / 3 / 4。archive 的 status / gaps 可读，retry / run 为 readonly；演示只给编造状态，写动作 demo；未连接 failed / unavailable，不暗中 receive start。

ADR-227 边界继续有效：ctl 没有 speak、加白名单、改准入、启用关闭的下载、执行 / 自动打开文件、发送消息的参数。retry 只恢复现有准入内副本，允许 Agent 使用；大文件及第二档文件的单独“开始下载”不放进本轮 backfill 命令，按原消息的显式下载入口处理，不能藏成 force / all 参数。

### 禁止的偷懒写法与已知的坑

不能托盘显示完成而状态页仍读旧统计；不能拿最后连接时间当对齐时间；读取失败保留旧值并标 stale / 错误，不把剩余数清零。HMAC 句柄冲突 / 过期不得转为全量 run；合并造成按钮失效只要求刷新。宿主 op 锁只用于取状态和接受任务，不持锁等数分钟历史拉取，避免 stop / quit 卡住。

## 六、已知边界与量测验收

### 技术路线与具体参数

实现阶段使用临时库、编造姓名号码、假 WebSocket / HTTP，实际调用生产 App.Run、协调器、Intake、desktopread、管道客户端和 MewTypeUI Tester。普通测试不连真实 Sumika 或 SnowLuma，不读取真实 data。真机验收单独排主人在场，不能用离线结果关闭原收图 M14 或 issue #26 的运行事故核查。

规模夹具冻结：10 个角色、10 个 QQ 会话、1 万 / 10 万 / 30 万条消息分档、1000 个缺口（含混状态与跨页）、1000 个媒体段，30 天历史；另测空会话和同秒连续消息。界面跑主屏 2560×1440、125%（逻辑 2048×1030），再跑最小允许窗口，聊天窄列 320 DIP 与大字。虚拟列表只构造视口及现有 overscan 范围；报告总元素数、可见行数、构建的缺口行数，不允许一次构造 1000 个折叠详情。

沿用[性能标准](notes/标准-性能与效率-2026-11-03.md)的项目暂定线：反馈 P95≤100 ms / P99≤200 ms；200 消息及必要状态的读取 P95≤50 ms；60 Hz 活动帧 P95≤10 ms，实际错过呈现周期≤1%；本次剧本应用造成 >100 ms 停顿 0；十倍夹具主程序 PrivateUsage 峰值≤512 MiB。MYGO_FRAME_STATS 只证明应用帧耗时，实际呈现需相应呈现记录，未量就记未验。测量前固定到达速度、媒体大小和版本，每档三遍，数字从输出取，保留每遍及最大值。假服务不证明真实平台恢复速度。

本节“反馈”的后台验收边界按第三节原文“任务接受后在 100 ms 反馈目标内显示排队 / 正在补”：`TestCtlBackfillCommandsOverPipe` 的 200 次样本从进程内新连真实命名管道前开始，包含连接及 SID 核对、服务端解析 / 校验、完整宿主接受任务、回包和调用方解析，守住 P95≤100 ms / P99≤200 ms。第九节旧记录“仍完整计入 200 次独立客户端启动至回复”记录了旧的混合测法，本次据上述规范条款更正计时口径；Windows 新建客户端进程和退出的调度开销另行诊断。实际 CLI 的 retry / run / status 仍经独立进程验参数、输出、退出码与真实补录终局。任务接受和任务完成分别验收，反馈预算不等待历史拉取。

资源记录包括墙钟、历史请求数 / 共享限速、实际新事件与重复数、消息提交延迟、下载吞吐、进程 CPU 秒 / 单核百分比、工作集 / 私有提交 / Go 堆、协程、文件路径类别 / 数量 / 字节、WAL 峰值及空闲 checkpoint 残留。新增对齐快照固定至多两行 / 账号；媒体内容寻址去重；成功 / 失败 / 取消后无无主临时文件，既有文件不覆盖。不要为了达标缩小历史窗口、丢字段、减少参与会话或取消脱敏。

核查来源：Go `snowluma/query.go` 的 HistoryPage / historyPageInbound、`history_test.go` 的 historyFrame、`replay_test.go`；本机 SnowLuma `<SnowLuma 目录>/release.json` 为 2.4.0，仅只读 `index.mjs` 程序代码；[OneBot v11 消息事件](https://github.com/botuniverse/onebot-11/blob/master/event/message.md)、[通知事件](https://github.com/botuniverse/onebot-11/blob/master/event/notice.md)、SnowLuma [群历史动作](https://snowluma.github.io/zh/docs/api/extended/get_group_msg_history)及[私聊历史动作](https://snowluma.github.io/zh/docs/api/extended/get_friend_msg_history)。OneBot 标准未定义 message_seq / real_seq 连续保证；SnowLuma 动作文档明确消息内部字段不固定，没有区间连续性合同。

### ctl 快反馈计时边界修正（2026-11-05）

原测试把 200 次独立 go test 客户端进程的启动、管道往返和退出放在同一个“反馈”分位数中。空闲和加压分段证明，主要超线来自新进程启动及其调度，后台接受任务仍在毫秒级。只筛客户端正式源码、乃至改为 go build，均不能把受压进程调度时间当作稳定的后台处理指标。

口径依据是第三节规范条款“任务接受后在 100 ms 反馈目标内显示排队 / 正在补”；第六节沿用性能标准里的快速交互线，标准笔记引用的 Microsoft 指南将快速操作与启动分别列为不同类型。第九节原“仍完整计入 200 次独立客户端启动至回复”是历史量测记录，不是另定 CLI 冷 / 热启动的 100 ms 门槛。本次按任务文件允许的后台反馈分支澄清：200 次新连接在进程内走真实命名管道，保留连接 / SID 核对及完整服务端路径；再单独启动真实客户端 retry，与上述接受结果核对同一个 JobID，随后 run / status、JSON / 中文计数、真实入库、archive 拒绝和零出站照旧验收。P95≤100 ms / P99≤200 ms 未改。

参考了本机 OpenAI Codex 的 `codex-rs/.config/nextest.toml:73–88`（Windows 子进程启动受并发负载影响，须与请求处理分开观察）、`codex-rs/app-server/tests/common/test_app_server.rs:1963–1966`（向真实 RPC 路径注入延迟验证往返），以及 Go `os/exec.Cmd.Wait` 的文档（还等待进程退出及输出复制）。借测量边界和受控延迟做法，复用现有 askPipe、独立客户端和宿主夹具，不另建 mock 服务。
