## 零、先说人话

1. 要做三样东西。**渠道中间件**：收、存、认人、决定她接不接、发出去的整套规矩，放在 `native/internal/channel`。**QQ 适配器**：只懂 OneBot 协议，把它翻译成统一格式，放在 `native/internal/onebot`。**QQ 平台插件**：戳回去、`#sl` 协议命令、收发自检、掉线提醒的 QQ 部分，放在 `native/internal/channel/qq`。复读跨平台，放在中间件里，不算 QQ 插件。
2. 中间件不认识 OneBot 的字段名（`post_type`、`sub_type`、`at.qq`）。它只看统一的事件：会话、人、段、通知、回执。
3. 有三件事不照 Bun 搬。第一，发送回执分三种（确认、明确失败、结果未知），不能拿 `void` 当成功（盘点 4.4 第 1、2 条）。第二，**她说的话要等回合定了以后，才裁决、改写、写库**：拦下的、试运行的、被打断的，都不进库，也不进她的下一轮历史；写库和发送计划在发送之前一起完成（Bun 是发完才写映射，中间崩溃就认不回回声）。第三，发出去的字在写库之前定型一次，库里的、历史里的、发出去的是同一句（ADR-114 说的三处对不上）。
4. 拦截链（复读、戳回去）排在观察之后、闸门之前。拦截插件处理掉的那一批不交给内核，但它存库、计数都照常。
5. 对内核要六样事（第九节第 1、3、4、5、6、7 条；第 3、4、6 条内核线 2026-10-26 已做）：渠道来的回合，句子不由内核直接写库（第 1 条）；场合提示词段的名字（第 3 条）；`Steer`、`Stop`、`Interrupt` 按会话找实例（第 4 条）；句子随回合定了交出（`Settled.Said`，第 5 条，ADR-184）；每个 `Respond` 都发"回合定了"（第 6 条）；"对面是谁"由中间件给一句话（第 7 条）。历史读取跳过试运行的事件（第 2 条）代码里已经有，内核线不用改，只补测试。其余的现有接口够用。
6. 分 12 步（第 0 到 11 步）。第 0 步到第 4 步全部用假协议端和契约测试，不碰 SnowLuma。真连 QQ 从第 6 步起，而且 Bun 和 Go 不能同时对同一个号发送（规格-QQ渠道 九点五）。第 6 步起 Go 写自己的库，不写 Bun 正在用的库（第十五节）。

统一段在 `types` 里的样子（草图，字段只写已知消费者要用的）：

```go
// internal/channel/types
type Seg struct {
    Kind   string // text | at | reply | image | emoji | face | superface | voice | video | file | forward | card | other
    Text   string // text
    Target string // at：号，"all" 是全体；reply：被引用的平台消息号
    Hash   string // image、emoji：文件内容的 sha256，不是临时链接；空串表示"还没算出来"，不参与比较（第十二节）
```

段种类在入站和出站两边的名字不同：入站的段用 `reply`（被引用的平台消息号），出站的 Part 用 `quote`（引用回复），是同一个东西。戳一戳不是段：入站是 `Notice{kind: poke}`，出站 Part 的 kind 是 `poke`。Inbound、Notice、Status、Part、Outbox 的字段在 `types` 包里定（实现时写进代码），本规格只定名字和用途。

纯文本、段类型的其余细节（`skipped`、`hidden` 之类的字段）在迁移时按第三节的 `Seg` 落到 `Raw` 或丢掉，丢的字段要列在迁移测试的清单里。

## 四、身份、场合和听众

**会话**（一个会话 = 一串连着的消息，词汇表）：

| 取舍 | Koishi | AstrBot | NoneBot2 | MaiBot | 我们选 | 为什么 |
|---|---|---|---|---|---|---|

**场合 = 渠道 × 形式**（ADR-140，词汇表）。渠道是 `console`（本地）或某个平台（现在只有 `qq`），形式是 `private` 或 `group`（ADR-144：场合的值名不写死平台）。代码里不靠会话字符串的前缀判断（`console.ts:224` 现在这样做，清单⑤），全部用 `Conversation` 的字段。`util/chain.ts:42`、`expression.ts:31-32` 取的是人 id 的前缀，不是会话的，见第十四节"人的前缀认定"。

|---|---|---|---|---|---|
| Channel | `console` | `console` | `qq` | `qq` | 适配器名 |
| Conversation | 本地会话串 | 本地群会话串 | 私聊会话串 | 群会话串 | 第四节上面 |
| Scene | `private` | `group` | `private` | `group` | 形式 |
| PersonIDs | 空（主人本人） | 这一批里的说话人 | 对方的 `qq:<号>` | 这一批里的说话人，只取这批（`router.ts:111`） | 记忆的"这个人"只在和他私聊时给（ADR-139） |

| OwnerAsked | `true` | 触发这一轮的那条是主人发的时 `true` | 发言人是主人时 `true` | 触发这一轮的那条是主人发的时 `true` | ADR-174 第 1、2 条 |

本地群聊现在没有入口（词汇表第一节）：这一列是为了让四种场合都写到（ADR-140 第 4 条），入口不在本规格里做。我定的（2026-10-26，规格起草时），见第十九节 B1。

几条判定是我的判定（不是主人定的，编号见第十九节 B11），写明理由：

- **QQ 群里"触发这一轮的那条"**：闸门放行时，取批里被叫到的那几条（@、引用、叫名字；叫名字只认别名表，判法见第十九节 B4；别名表没填之前不算叫到她，`Addressed` 只认 @ 和引用，主人 2026-10-26 定，A5，ADR-187 第 3 条）；被叫到的有几条时，**都是主人发的**才算 `OwnerAsked` 为真，有一条是群友发的就是假（和规格-记忆-v2 13.2.1 一致；ADR-186 第 2 条：混批不算主人在问，默认收紧；2026-10-26 记忆线指出两份规格原来在"几个人同时叫她"时算法不一样）。没有被叫到、是闸门看热闹放行的，取批里最后一条。理由：闸门的放行原因就是这几条。
- **私聊里 `OwnerAsked` 等于 `PrivateOK`**：ADR-174 没有单独说私聊，主人在私聊里问，本来就是主人在场，两个值一致，不另开口子（B11）。
- **`Scope`（权限档）不由中间件定义**：由记忆包的可见集合函数算出指纹，中间件只调用、只传（8.1 的"档 = 当轮可见集合的指纹"）。这一点不再讨论。
- **`Addressed`**：对话链（规格-群聊闸门 第二节）算出的"叫到她"，在观察步骤里算，早于拦截链，拦截插件要看它（第七节，复读在被叫到时不接）。由中间件算好放进 `Input.Addressed`（和 `ContextIn.Addressed`，都是值字段），插件只能读，改不了。AstrBot 的 `is_wake` 能被任何插件的过滤器置位（拆解 AstrBot 第十二节 12.3），这一点不照它。

## 五、平台适配器：接口和能力声明

**接口草图**（`native/internal/channel/types`，草图，细节实现时定，但方法数量不增加）：

```go
type Adapter interface {
    Name() string                                                       // "qq"
    Caps() Caps                                                         // 启动时读一次，之后不变
    Run(ctx context.Context, sink Sink) error                           // 连上并收；只把事实交给 sink，不做策略
    Send(ctx context.Context, account string, p Part) (Receipt, error)  // 发一段；必须返回三种回执之一。只由出口（第十节）调用
    Poke(ctx context.Context, account string, c Conversation, target string) (Receipt, error) // 只有 Caps.Poke 为真才会被调用；只由出口调用
}

type Caps struct {
    Image   bool // 能发图（复读要发同一张图）
    Poke    bool // 能戳人（戳回去）
    Echo    bool // 自己发的消息会被协议端回报（SnowLuma 的 reportSelfMessage，否则靠补录）
    MaxText int  // 一段最多多少字（QQ 的硬切线，拆条用）
}

type Sink interface {
    Inbound(ctx context.Context, in Inbound) error // 消息、自己的消息回报
    Notice(ctx context.Context, n Notice) error    // 戳一戳、撤回、表情回应、被踢、其他通知
    Status(ctx context.Context, s Status) error    // 连上、断开、重连、被踢、心跳（元事件归这里，不进 events）
}

type Receipt struct {
    PartID     string
    Status     string // confirmed | failed | unknown：三种之一，没有别的
    PlatformID string // 平台消息号，确认时才有
    Via        string // reply（回包）| echo（回声）
    Err        string // failed 时的原因（截短）
    At         time.Time
}
```

`Describe` 不放在接口里：现在没有已知的消费者（原生界面规格里没有会话列表；盘点第七节说它来自会话列表，但那一条还没写规格）。等会话列表的规格写的时候再加，并在那一步写明消费者。

**能力声明的取舍**：

| 取舍 | Koishi | AstrBot | NoneBot2 | MaiBot | 我们选 | 为什么 |
|---|---|---|---|---|---|---|
| 怎么知道平台能做什么 | "方法存在即能力"，基类上的方法恒为真（S `bot.ts:55-57`，`message.create`、`upload.create`、`login.get` 恒在列表里）；`supports` 只认 Methods 的键，写方法名恒为假（S `bot.ts:225-227`） | 没读到能力声明的统一接口（`platform/platform_metadata.py` 只看了文件名）；注册时带 `support_streaming_message`（AB `aiocqhttp_platform_adapter.py:30-34`） | 方法在类上，`Bot.__getattr__` 把任何名字变成 `call_api`，拼错了运行时才报（A `internal/adapter/bot.py:47-52`） | 没有能力声明：网关 `ready` 报到后登记账号和路由（MB `supervisor.py:1680-1733`），发得出与否由适配器回执决定（MB `platform_io/drivers/plugin_driver.py:163-185`） | 启动时声明一次的 `Caps`，只有 4 项，每一项都有已知的消费者 | 只为已知消费者设计（上级 AGENTS 防过度工程）：`Image` 给复读，`Poke` 给戳回去，`Echo` 给发送认领，`MaxText` 给拆条。`Quote`、`React`、`Recall`、`Forward`、`Resolve` 现在没人用，不加；用到时再加。（2026-10-27：`Quote`、`Forward`、`React` 有消费者了：ADR-192、193 链接解析的"展开"要引用原消息、用合并转发、开始处理时点表情回应，做它时加。）`HistoryPage` 第 8 步才加（第十五节） |
| 不支持时怎么办 | 抛 TypeError 或 `not implemented`（S `bot.ts:257-261`） | 没读到 | 同上，运行时才报 | 没有单独的"不支持"：适配器回 `success: false` 记 FAILED（MB `plugin_driver.py:163-185`）；名单拒绝记 DROPPED（MB `platform_io/manager.py:555-572`），和 FAILED 分开 | 调用不支持的动作，返回 `ErrUnsupported`，这是明确的失败，不是成功 | 盘点 4.4 第 2 条：没有认领的动作不能当成功 |

**适配器的边界**：只翻译、只执行动作、只报告事实。它不判断身份（谁是主人、谁是角色，那是中间件按账号配置算的），不判闸门，不写库，不打日志里的令牌。这和 Koishi、MaiBot 的适配器一样：Koishi 的 OneBot 适配器只把解码后的事件交给 `dispatchSession`（O `src/utils.ts:165-176`），不做策略；MaiBot 的 `message_process` 只做反序列化和路由键（MB `chat/message_receive/bot.py:719-745`），策略在 `receive_message`（:754）。

Go 桌面接收转发增加可选 types.ForwardReader（2026-11-02）：只读查询一层，返回 ForwardTree/ForwardMessageNode（与出站纯文字 ForwardNode 分开）。snowluma 负责翻译外部节点，宿主 forwardfetch 管递归预算、存树和排媒体；入库、plain/line 仍只写转发占位，不给角色展开。


## 六、进来的路径

一条消息从适配器到中间件，按这个顺序走。每一步在哪里、为什么这样。先看各家怎么做：

| 取舍 | Koishi | AstrBot | NoneBot2 | MaiBot | 我们选 | 为什么 |
|---|---|---|---|---|---|---|
| 去重 | 没有按消息号去重，只忽略自己发的（K `middleware.ts:235`） | aiocqhttp 和流水线没有按消息号去重（`platform/`、`pipeline/` 里搜 `dedup`、`duplicate`、`seen`）；lark、line、mattermost 适配器各自有（AB `platform/sources/lark/lark_adapter.py:529`、`line/line_adapter.py:489`、`mattermost/mattermost_adapter.py:64-66`） | 没有（A `v11/adapter.py` 里没有去重） | Platform IO 有去重：键是 `dedupe_key`、`external_message_id` 或 `session_message.message_id`（前面加 `driver_id:`），窗口 300 秒、最多 1 万条（MB `platform_io/manager.py:488-492`、`:644-671`，`dedupe.py:40`），窗口外的重复会再收一次；旧链入站没有去重，`echo_message_process` 只把本地 id 换成平台 id（MB `chat/message_receive/bot.py:687-717`） | 键 `(渠道, 会话, 平台消息号)`；号为空或 0 不去重；第二次到达只补观察 | 两个号看同一条消息是正常情况（ADR-007）；去重要去掉的是第二份事件，不是第二份观察。空号去重会把不同的消息当成同一条（清单⑯）。键在库里（唯一约束），没有时间窗口；MaiBot 的 300 秒窗口正是窗口外会重复的原因 |
| 顺序 | 每条消息各跑一条链，没有按频道排队（K 的推断，依赖 cordis 的 emit，没核实） | 每个事件一个 `asyncio.create_task`，没有会话排队（AB `event_bus.py:56-73`） | 每个事件一个任务，没有排队（A `v11/adapter.py:240、279、369`） | 每个聊天流有自己的防抖批次（MB `chat/debounce/controller.py:30`） | 按（渠道、会话）一条队列，包住入库、观察、拦截、闸门判定；内核回合不在队列里（第八节） | 水位要按顺序推进（清单⑬）；别的会话不互相等；回合可能几十秒，不能卡住新消息入库 |
| 存库 | 只记频道和用户行，事件不在这里存（K `middleware.ts:201-205`） | 流水线不存入站消息；群消息历史是内置插件 `persist_group_message`（AB `builtin_stars/astrbot/main.py:138-182`，默认关，`config/default.py:240`） | 不存，Bot 层只做预处理（A `v11/bot.py:202-210`） | 入库在心流处理器里，先于运行时注册（MB `chat/heart_flow/heartflow_message_processor.py:54-62`、`:60`），门控拦下的也入库；出站发送成功后才入库（MB `services/send_service.py:918-919`，旧链 `uni_message_sender.py:316-319`） | 入站：事件、映射、观察一个事务；出站：回合定了以后，裁决、写库（第十节） | 收到和发出都要有记录，而且要和映射在同一次提交里（盘点第五节）。出站在发送前写，崩溃后才知道"可能发了" |
| 引用补全 | 同步取，最长 60 秒（O `src/utils.ts:102-109`） | 引用段带 `chain`，由平台填（AB `message/components.py:590-600`） | 同步 `get_msg`，最长 30 秒（A `v11/bot.py:22-61`、`:35-37`） | `ReplyComponent` 只存 id（MB `common/data_models/message_component_data_model.py:266`） | 入库只存 id，内容后补，不挡入库 | 同步补取会让引用消息晚于后到的普通消息进入（拆解 Koishi 第九节第 2 条）；清单⑧ |

下面的步骤就是按这张表定的：

1. **适配器解码**。OneBot 的 JSON 翻译成 `Inbound` 或 `Notice`。元事件（心跳、生命周期）归连接状态（`Status`），不进 `events`：OneBot 心跳周期性到达，整天会在 events 里积大量噪声（NoneBot 对心跳不记日志，拆解-渠道层-NoneBot2 第 2 节，`v11/event.py:552-553`）。认不出的通知进 `other`，不丢（规格-QQ渠道第三节）。**单帧解析失败只记一条日志，丢掉这一帧，连接不关**（NoneBot 的坏帧会关掉整条连接，A `v11/adapter.py:274-295`，是反例）。
2. **按账号分派**（正向 WS）。每个配置的账号一条连接（规格-QQ渠道第二节，`qq.accounts[].url`）。连上后用 `get_login_info` 取得的号和配置核对（OneBot v11 标准接口；SnowLuma 是否实现未核实，第二十节）；对不上就断开，并提醒一次（规格-QQ渠道第六节，`mismatch`）；不在配置里的号不接入。NoneBot 和 Koishi 的做法是反向 WS 的 `X-Self-ID` 分派（见第十一节），正向 WS 下没有这个头，不适用；理由相同：账号在配置里，不悄悄接新号。
3. **去重**。键是 `(渠道, 会话, 平台消息号)`，和 Bun 的 `qq_msgs` 主键一样（`qq.ts:430`）。平台消息号为空或 0 时**不去重**：这条按单条入库，记一行日志。号以原始数字串保存（解码用 `json.Number` 或保留原文），超过 2^53 的号往返不变。同一个键第二次到达：不再存新事件，只给这个账号补一条观察记录（"两个号都看到了"，规格-QQ渠道第三节）。去重的依据不是内容，因为同一条消息在两个号上的内容可能不同（语音转写、图片链接）。
4. **按会话排队**。同一个渠道的同一个会话，只有一条队列，实时消息和补录消息进同一条队列（水位才能按顺序推进，清单⑬）。队列包住的是：入库、观察、拦截链、闸门判定。**内核回合不在队列里**。回合进行中到的新批次：闸门不放行的，只入库和观察；放行的，分两种：批里有被叫到的（`Addressed`），就先 `Stop` 当前回合，再 `Respond` 新批（ADR-020：回复还没发出就来了更重要的消息，abort 后重新生成）；没有被叫到、OwnerAsked 为假、档和运行中的回合相同的，走 `Steer`（插话，8.1 的 A4）；其余的（OwnerAsked 为真，或档不同）走 `Stop` 再 `Respond`：插话只收文字，不带听众和档（`hub.go:241-253`），插话进上下文时用的是运行中那一轮的听众（`hub.go:502-504`），主人在群里没叫她的话会按群聊听众处理，她想不起主人的私事。这是规格起草时的路由错误，2026-10-26 复核改，验收见第十六节 B。`Steer` 返回 false（这一轮不在跑）就改走 `Respond`。`Steer`、`Stop` 按会话的版本内核线已做（`SteerIn`、`StopIn`，，第九节第 4 条）；`SteerIn` 要先把这批存进库、再交 seq。`Stop` 只在"回合还没定、还没有段在发"时用，发送阶段的段不因此中止（第十节 10.6）。不同会话之间互不等待。Bun 用一个全局队列（`qq.ts:100`，`PQueue` 并发 1），慢任务会堵住所有会话；我们按会话排，这一点和 NoneBot 的"每条事件一个任务、无排队"不同，也不照 Koishi 的频道串行。
5. **一个事务写三样**：`events`（事件本身）、`qq_msgs`（平台消息号映射）、`observations`（哪个账号看到了）。Bun 里前两样分在两次写入（`qq.ts:422` 的 `appendEvent`，`qq.ts:430` 的映射），中间崩了，补录会再存一份（盘点 五节）。事务的范围要在 `store` 里扩到三张表。`events` 的 `seq` 是**到达序**，只用于水位和读取；平台时间另存一列（`time`，精度是整秒，同一秒的多条按平台消息号定序）。**入库时还要存一份排好的行头**（`segments.line`，Bun 就这样存），不然实例重建时群友的话没有名字；这归第 1 步的入库代码，第 3 步做完时发现没做，已补（2026-10-27，`Intake.lineOf`，调第 3 步的 `FormatLine`；`Config.Line` 给名字和引用的查询钩子，`@你` 按收到它的角色的号算，和 Bun 一样）。
6. **媒体后置**。图片下载、算哈希、认格式只在入库之后做，入库不等它（MaiBot 也这样：`message.process(enable_heavy_media_analysis=False)`，MB `bot.py:817`）。图片哈希算出以后，才能判断复读。
7. **引用补全后置**。入库时引用只存平台消息号。被引用的内容如果库里有，直接连上；没有，异步去取，取到了更新那条事件的引用字段，取不到就写"引用的消息没取到"。不挡入库（NoneBot 的反例，第三节）。`resolveContent` 就是 ADR-141 的 `PlatformLookup`（平台服务名等于渠道名）在 Go 里的写法，不另起一套；第 10 步才加。
8. **通知给记忆和其他订阅者**。中间件发一条"她看到了新事件"的通知，带会话、角色、序号、标签（`backfill`、`stranger`、`fromSelf`、`selftest`，沿用 ADR-141 的 `message/stored(event, info)`，平台无关，渠道由事件字段带，不加平台前缀）。**中间件不因为标签而丢掉事件**，过滤在消费者那一边（ADR-092 的记忆不吃补录，ADR-101 的学说法吃补录，两边口径不同，给标签让各自过滤，盘点 第八节第 4 条）。8.1 第 333 行原来写的"补录的、自检的、陌生人的不发"已被 ADR-187 第 1 条改为照发、带标签（主人 2026-10-26 定，第十九节 A3），规格-Go后台 8.1 第 332、333 行已同步。

2026-10-27：渠道入库和出口写库后可接入 `NotifySeen`；只记录档不通知，重复入库不再通知。本地主窗口由内核通知，本地群聊目前没有渠道装配；渠道装配时须向流水线和出口都传入内核。试运行档写进库的那一行（origin 为 `automation:dry-run`）她下一轮看不到，出口不为它发通知。

之后才是第七节的拦截链，再是第八节的闸门，再是回合（第九节），回合定了以后是第十节。

**补录和实时的交错**：补录的页先取回来，每一条都进第 4 步的队列。补录的消息只入库、只观察：不进拦截链（复读和戳回去不对补录的消息做事），不触发回复，不计"这小时热闹"，不算 `Addressed`，不进闸门，不进内核（第八节）。补录的消息打上 `backfill` 标签。历史显示的顺序按平台时间（同秒按平台消息号），而 `seq` 是到达序，两者不同：补录的洞用结构化的未补区间记（第十五节第 8 步），不靠排序补。

## 七、拦截链：处理掉就停

**语义**：拦截插件有一个优先级数字（小的先）、一个场合集合、一个 `Intercept(batch) Verdict` 函数。`Verdict` 只有两种：**接了**（带理由，写日志）或**没接**。插件返回"接了"，链就停，这一批不交给内核；闸门仍然照常收到这一批，但只做计数和更新退避，不做放行判断（需求第一节、第二节）。不管插件有没有运行过、有没有报错。

| 取舍 | Koishi | AstrBot | NoneBot2 | MaiBot | 我们选 | 为什么 |
|---|---|---|---|---|---|---|
| 什么时候停 | 不调 `next` 就停（K `middleware.ts:245-264`，测试 `basic 3`） | 阶段设了 `stop_event()`，调度器在阶段后检查（AB `pipeline/scheduler.py`，`stop_event` 检查在 `_process_stages`） | 运行过就 block，报错、`finish` 也一样（N `message.py:477-478`、`462-466`） | 命令链返回不继续就停（MB `bot.py:878-884`） | 插件明确返回"接了"才停 | NoneBot 的"运行过就停"在插件报错时也会停，等于把错误当成接了；我们要的是"接了"这个明确的事实 |
| 顺序 | 后注册的 prepend 先跑（K `middleware.ts:133-138`） | 阶段顺序固定（AB `stage_order.py:3-13`）；插件优先级是**数字大的先跑**（AB `star/star_handler.py:26`，内置保留插件用 `maxsize - 1` 排最前，`builtin_stars/astrbot/main.py:41`），和下面的"小的先"相反 | 数字升序，同一个数字的并发跑（N `message.py:571-601`） | 固定的命令顺序 | 数字升序，同一个数字按注册顺序**串行** | 复读和戳回去的优先级是初值（戳 10，复读 20，需求第四节）；串行的结果可以复现，"先到先赢"才有意义；并发会让两个插件同时决定，谁赢取决于调度 |
| 出错怎么办 | 写日志，回复一句 `SessionError` 文字（K `middleware.ts:257-263`） | 过滤器抛异常：回复错误文字并 stop（AB `pipeline/waking_check/stage.py:185-195`）；处理函数抛异常：发 `OnPluginErrorEvent`，唤醒时回复错误文字，然后 stop（AB `pipeline/process_stage/method/star_request.py:91-123`）。两处都不是"当没接" | 记日志，仍然 block（N `message.py:462-466`） | 没有通用的插件拦截链；`receive_message` 的异常只打印，不冒泡（MB `chat/message_receive/bot.py:900-902`，见第六节坏数据一行） | 出错、超时都当"没接"，记日志，交给下一个插件，最后交给闸门 | 拦截插件坏了，不能让她哑巴。与闸门不同：闸门出错是不放行（第八节）；拦截插件是放行到正常路径。AstrBot 的做法（插件异常停掉整个事件，并把错误文字发到聊天，AB `star_request.py:91-123`）我们不照：错误进日志和右侧栏，不进聊天 |

| 日志 | 无统一 | 没有拦截日志；过滤器和处理函数的错误走 `OnPluginErrorEvent`（AB `star_request.py:108-115`） | 无 | 没读到拦截日志；出站被名单拒的回执是 DROPPED（MB `platform_io/manager.py:555-572`） | 每次进链记一行：插件名、会话、结果（接了 + 理由，或没接 + 原因）；被别人抢先的记"被 X 抢先" | 需求第五节，方便主人在右侧栏看到"她为什么没说话" |

**停止和"接了"的语义**（AstrBot 的反例）：AstrBot 的 `stop_event()` 是粘性标志，`set_result`、`clear_result` 都不清它（AB `platform/astr_message_event.py:399-413`）；`should_call_llm(True)` 实际是禁止默认模型，名字和效果相反（`:423-428`）。我们的"接了"是拦截插件的返回值，别的操作改不了它。**内核不需要为拦截链加任何东西**：拦截链在渠道中间件里，不进 `turn.Registry`；`plugin.go` 现在只有 `OnContext`、`OnSettled` 两种钩子，够用（第九节）。

**场合**：AstrBot 的内置 `astrbot` 插件用 ALL 过滤器，让群消息全部唤醒，之后的限流计数和图片本地化都覆盖群里每一条（AB `builtin_stars/astrbot/main.py:41-42`，拆解 AstrBot 第一节第 3 条）。我们的拦截插件只在声明的场合和开关下跑（见下面"拦截链和场合、档位、开关的关系"），不让"监听全部"的插件变成"叫到她"（第十七节）。

**拦截链和场合、档位、开关的关系**：

- 每个插件有场合集合（需求第一节的表：复读在本地群聊和 QQ 群跑，戳一戳在 QQ 私聊和 QQ 群跑）。
- 每个群有开关，默认全关（规格-群聊插件 第一节，需求第五节）；私聊里戳回去默认开（只限她本来就接的私聊），每个私聊能单独关（ADR-189，第十九节 A4）。
- **只记录档**（规格-群聊闸门 10.1）：拦截链不跑。她不进来看，插件也不动。
- **试运行档**：拦截链照跑；插件"要发出去的东西"在回合定了以后，由出口写成 `origin = automation:dry-run` 的事件，不发到平台（第十节 10.7）。
- **说话档**：真发。

**拦截链和闸门的先后**：拦截链在前，闸门在后（第八节说明为什么）。复读"接了"以后，这一批不交给内核，但闸门照常计数（这小时热闹不热闹）、更新她刚说过话的退避（需求第二节）。

**戳一戳是通知**：拦截只消费这一条通知；同一批里的消息照常进观察和闸门（不因为有人戳了她，同一批里 @她 的提问就被整批拦下）。

### 8.1 对照 MaiBot：怎么判开口（读码，拆解 MaiBot 第四节）

MaiBot 的顺序（`maisaka/turn_trigger/scheduler.py:64-105`）：防抖没收齐一批 → wait 中 → 频率为 0 静默消费 → @ 或提及强制进规划器 → 空闲退避 → 动态门控 → 规划器 LLM 自选 reply、wait、stop，或者不调工具。我们的顺序：入库 → 观察（计数、`Addressed`、通知）→ 拦截链 → 闸门（只记录 / 试运行 / 说话，保险丝，通道门，"她刚说过话"的退避，对话链，动态门槛）→ 内核 → 她自己看完上下文决定说不说。

|---|---|---|---|
| 入库之前的拦截 | 过滤词命中即返回，不入库、不进上下文（MB `chat/message_receive/bot.py:838-851`）；`chat.receive.before_process` 也在入库前、可以中止（`:797-803`） | 拦截链和闸门都在入库之后；拦下的批次照常入库、计数（第一节第 4 条） | 不照。我们要计"这小时热闹"，也要右侧栏看得到被拦的东西 |

**顺序**（固定）：入库 → 观察 → 拦截链 → 闸门 → 内核。

| 步 | 做什么 | 为什么在这个位置 |
|---|---|---|
| 入库 | 第六节第 3 到 5 步 | 所有后续步骤都要读库 |
| 观察 | 计数（这小时热闹不热闹）、对话链（谁接谁，规格-群聊闸门第二节，算 `Addressed`）、发"她看到了"的通知（补录的、自检的、陌生人的也发，带标签，消费者各自过滤，主人 2026-10-26 定，A3，ADR-187 第 1 条）。**补录只做到这一步，且不计热闹、不算 `Addressed`**（第六节） | 要在拦截之前做：复读被拦下以后，闸门仍然要知道群里刚热闹过（需求第二节，"闸门计数照常算"） |
| 拦截链 | 第七节 | 拦截插件要读 `Addressed`（复读被叫到时不接），所以必须在观察之后 |
| 闸门 | 规格-群聊闸门第三、四节的算式和门槛；档位判断（只记录 / 试运行 / 说话）；保险丝；通道门；她刚说过话的退避。拦截链接了的批次：闸门只计数、更新退避，不判断（需求第一节） | 闸门决定"这批值不值得想一想"，它不改内容，只决定进不进内核 |

**计数的口径**（这一条改过，以下是定稿）：

- **计数单位是一条回复**：就是第十节 10.1 里的"一句"（一步说完的整段字），不是拆开以后的气泡（规格-群聊闸门 10.1 第 176 行只说"按回复算"，没有定义"一步"；一步算一句，主人 2026-10-26 定，见第十九节 A7，ADR-187 第 5 条）。回执是段的，汇总到回复上计数。
- **频率**（"这小时说了几次"）：算"真发出去的"和"结果未知的"回复；标了"没发出去"的不算；同一回复里还没轮到发的段不算（规格-群聊闸门 10.1 第 173 行）。**试运行的也算**（第 165 行，`试运行说的算进"这小时已经说了几次"`）。
- **退避**（"她刚说过话"）：按在途段算，待发、发送中、确认、结果未知都算她说过话，不必等回执全部到齐（清单⑬，回合 1 的段在途 10 秒时，回合 2 的闸门要看到"刚说过话"）。明确失败（用完重试）、守卫拦下、已中止不算。
- **复读**：计退避，也计开口（需求第二节表）。**戳回去**：不计退避，也不计开口（需求第二节表；它是通知，不是她说的话）。

**保险丝**（规格-群聊闸门 10.1 第 172 行，ADR-099）：一个群按最近 60 分钟滑着算；条数上限是 `round(4 + 16 × 频率)`；主动的到上限先不接，被叫到的到两倍才不接；这一轮不看、不调模型，记"保险丝"。试运行想说的也算。字数上限（一条最多 200 字）在回合定了以后、改写之后、拆条之前检查（第十节 10.1 第 3 步）。

**通道门**（第十四节原来写的"通道是否通的检查"，现在是中间件的通用门）：计数只算明确失败（用完重试的那一段记一次）；已中止、守卫拦下、结果未知都不算。连续 3 段明确失败（初值，见第十九节 B12）→ 这个渠道暂停：闸门直接不放行（记原因，右侧栏显示）。恢复：适配器报连接恢复（Status 为连上）时清零、允许放行；或主人在界面上点恢复。`get_status` 是否可用见第二十节第 4 条，核实以前不用它。被踢、断线的提醒照规格-QQ渠道第六节的做法，不算在这个计数里。

**档位**：每个群一个档（只记录、试运行、说话），由第四节的听众和群设置决定，写在 `gate_modes`，和 Bun 一样。切到"说话"时，注入测试（规格-群聊闸门 10.2 的注入测试；`speakCheck` 的定义和用法见规格-群聊闸门第 209、221 行）**只提示不拦**（ADR-135）：切换照常，没过的结果写一条日志和界面提示，这一轮照常开口。中间件不重跑它，闸门读它的结果。

**多个角色同群**（规格-群聊闸门第六节，ADR-061 的"大部分按推荐"）：每个角色各有自己的闸门。同一批几个角色都放行时，只让一个进内核，选择规则照规格-群聊闸门第六节（第 122 行）：被叫到的优先，其次可能性最高的，分数很接近时随机一个；其余的记"闸门放行，但让给了谁"。排在后面的不丢，是排队看（第 123 行）：第一个人说完以后，第二个人开跑前**用最新的批重跑闸门**，再决定接不接（不用旧批回话）。第二个人的停顿比第一个人长一些（第 124 行），同一件事最多两个人说、第二个人的概率打五折（第 125 行）。第一个被打断（stopped）时，第二个的闸门照常判定（它不依赖第一个说没说出口），放行就开跑。中间件负责"只让一个进"，内核负责"排队看"（用 `Respond` 的顺序，第二个在第一个 `Settled` 之后再开始）。

**向内核线要的，有五样**（这是内核线的事，本规格只写要什么。第 1、3 条是为渠道回合改的；第 4 到 6 条是 8.1 定了（第 5 条经 ADR-184 修正）、代码还没有或不够用的；第 2 条代码里已经有，只补测试。2026-10-26 对着 `internal/turn`、`internal/history` 核实过）：

1. **渠道来的回合，句子不由内核直接写库**。`Audience.Channel`（`Input` 没有 Channel 字段；loop.go:444 的注释写的"由 Input 带"与代码不符）不是 `console` 时，内核在每一步收尾（`endStep`）的时候**不 `AppendEvent`**，这一回合的句子留到"回合定了"时随 `Settled.Said` 交出（第 5 条；ADR-184 第 3 条）。主窗口（`console`）照旧写库，对拍 45 份不变。原因：拦下的、试运行的、被打断的句子不能进库和历史；库和历史只由中间件写，写的是改写以后的字（ADR-114，三处一致）。现在 `endStep`（`native/internal/turn/loop.go:430`，写库在 446 行）是先写的（写死 `console`），所以这里要改。 **内核线的做法**（内核线 2026-10-26 已做，，合进 main 的是；规格-Go后台 8.3 有完整说明）：渠道回合（`Audience.Channel` 不是 `console`）她说的内核不写库，`model_runs`、`steps` 照记。中间件写完库以后同步调 `Hub.Commit(角色, 会话, 回合id, []Committed{Step, Seq, Text})`：它排进这个会话的回合队列，做完才返回；接着用的实例里这一回合那一段照库重写（以库为准，，合进 main 的是）：这一回合用过的事件（那一批、插话）加上交回的几行，照 seq 排、照 history 的 `toMessage` 写法；回合开头的参考信息留在原位，插话时追加的那块挪到那几句插话里最早那条前面，她每一步的思考跟着那一步；工具调用、没交回的步（拦下、试运行）不留；seq 记成"跑完的回合用过的"（别的档也追得到）。交回的每一行都要满足：在库里、在这个会话、是她说出口的那一行（`origin = character`，试运行的不算）、`Text` 和库里那一行逐字相同、seq 比这一回合的那一批和插话都大（回合定了以后才写的）、一步一行、两步不能共用一行。不满足上面任一条，或者回合 id 不对、步不存在、没有 seq、同一步交回两次，都报错，什么都不改：中间件记一行日志，再调 `RestartIn`，下一批从库里重建实例（刚写进库的那几行一定读得到，代价是这个会话的缓存断一次）。结局不是 done 的，内核当场拿掉那几句，不调 `Commit`（调了报错）；done 的没调 `Commit`（或交回报错），这个会话下一轮开始时内核照库重写这一回合，她这一回合说的不算进来，日志记"回合 X 定了以后没交回写库的结果（Commit），照库重写了这一回合"。渠道的 `StopIn` 不记主窗口那句"上一轮被主人手动停止了"（渠道打断重回时它会把没发出去的半句塞回历史）。一轮最后一步全是乱码时只拿掉末尾那条，前面说过的照留，所以 `Said` 和实例里的步对得上。**插话和她的话谁在前，以库为准**（我定的，2026-10-26）：回合中途插进来的话先存库（seq 小），她这一回合的句子回合定了才写库（seq 大），库里是"插话在前、她的话在后"；她的话本来就是回合定了才发出去，群里看到的也是这个顺序。所以 `Commit` 以后，实例里这一回合说出口的那几条（群友那一批、中途的插话、她每一步的话）要和"从库里重建"的一样：顺序照 seq，插话照 history 的 `toMessage` 写法（不留"你回话的中途……"那个前缀），她的话就是库里那一行；接着用的实例、重建的实例、别的档追上的，三者去掉参考信息和思考以后逐条相等。本来就不进库的两样不算：这一回合的参考信息块（ADR-022 只追加，接着用的实例里留着；回合开头那块留在原位，插话时追加的那块跟着插话挪到它前面）、她的思考（接着用的实例带回给模型，重建以后没有）。渠道回合没有工具，回合中间的工具调用照"和重建一样"拿掉（内核线 2026-10-26 细化）。理由：ADR-184 要的是库、历史、发送三处一致，顺序也算；代价是这个会话最后一回合那几条的缓存断一次。备选：接受两种顺序不一样、写明（a）；把插话之前那一步的句子先单独写库（b，要在回合定了之前裁决，和 ADR-184 第 1 条相反，不采）。已被[规格-提示词前缀稳定](规格-提示词前缀稳定.md)第三节改为（2026-11-13）：那一批在回合里就照库逐条追加，不再先拼成一条、交回时才拆开。上面“她每一步的思考跟着那一步”已被同一份规格第五节改为：交回以后不带思考，和重建出来的一样。

   **实例内存要和事件库对齐**：渠道回合里，内核实例的内存中还留着她这一回合说的话（Clean 之后、中间件改写之前的字，hub.go:610）。8.3 第 1 项的实例复用会按 seq 从 events 追上中间件写进去的那一行（改写后的字），同一句就会以两种字出现在请求体里。所以回合定了以后，内核按回合 id 把实例里这一回合她说的话，换成中间件写进 events 的那一行（带 seq，改写后的字）；拦下、试运行、打断的，从实例里拿掉。对齐的办法：替换（向内核线提的建议，见第十九节 B9；ADR-184 第 3 条已写"内核实例里这一回合的原文换成库里那一行"，下面的交接办法仍待内核线确认）。交接：中间件在写库事务提交后、屏障放开之前，同步调内核的一个方法，把（回合 id、seq、改写后的字）交给实例，调用方同时把 seq 登进实例的 `seen`（hub.go:640-641）；不走 OnSettled，它是异步的。`Msg`（loop.go:29）要加回合 id 字段，现在没有。要改的地方：loop.go:29-47、hub.go:420-437、hub.go:640-641。
2. **历史读取跳过 `origin = automation:dry-run` 和 `automation:self-skip` 的事件：代码里已经有，内核线不用改**。`history/history.go:71`（`MessageWindow` 的 SQL）、`:130–132`（`notSaid`）、`:167`（`For`）、`:185`（`After`）都排除了它们；调用处是 `turn.go:285`。试运行的话只给界面看，不进她的上下文（规格-群聊闸门 10.1 第 167 行）。要补的是测试：渠道的试运行事件和 self-skip 事件不进 `For` 和 `After` 的结果（第十六节 B 的回合的裁决项）。
3. **场合提示词段**：`Input` 上一个字符串列表（例如 `scene-group`、`platform-qq`，ADR-175）。消费者是内核拼提示词。第 3 步就加（默认值），内容第 5 步前定。 **内核线已做**：`Input.Scenes []string`，非空时按先后逐段拼 `prompts/<名字>.md`，换掉本地私聊的场合段和风格预设，读不到就报错（这一轮的 `Settled` 是 error）；空的照旧。**风格预设不放进 `Scenes`**（我定的，2026-10-26）：`Scenes` 读的是出厂的 `prompts/`，风格预设是主人的（ADR-175），放在数据目录。向内核线提的建议，内核线 2026-10-26 已同意（和 ADR-184 那几条一起做）：另给 `Input.Style`（预设 id），内核照主窗口的读法去取，空 = 默认的全年龄向（不在 ADR-184 那一批里，等主人另排）；用哪个由中间件按平台 × 形式 × 会话选，照 Bun 的 `resolveChoice`（`daemon/util/prompts.ts:32-47`；Bun 拼的顺序是场合段、风格、平台段）。
4. **`Steer`、`Stop`、`Interrupt` 按（角色，会话）找实例**。现在三个都写死 `"console:"+characterID`（`hub.go:242`、`:259`、`:281`，依次是 Steer、Stop、Interrupt），渠道会话的回合找不到实例：`Steer` 返回 false，`Stop` 返回 false，渠道批次的"打断再回复"和"插话"都做不了。改法（向内核线提的建议，见第十九节 B6）：给这几个加一个会话参数，key 用（角色，会话），不带档，和 `h.active` 现在的 key 一致。`Restart`（`hub.go:290`）、`ApprovalResolved`（`hub.go:302`）也写死同一个前缀，渠道线用不到（渠道没有"开始新话题"，也没有审批），内核线改时一并改或注明不改。主窗口的调用方改传 `console:<角色>`，行为不变。 **内核线已做**：`SteerIn(角色, 会话, 文字, seqs)`、`StopIn`、`InterruptIn`、`RestartIn`，原来的入口成了主窗口的包装。`SteerIn` 要 `seqs`：渠道的插话先存进库，再把 seq 交给内核（可以多条），不带 seq 返回 false；送到时内核只登记、不写库（审查查出来的：之前内核会把渠道插话再写一条"主窗口里主人说的"）。渠道插话的前缀内核暂定为"（你回话的中途，这里又来了新消息，不是工具的输出）"（`steer.go` 的 `steerPrefixChannel`），第 5 步定场合内容时一起定。
5. **句子随"回合定了"交出（`Settled.Said`）**（后端 Agent 那条线 2026-10-26 提的，不是主人的原话，主人定的是 A2 选 (a)；写在 ADR-184 第 2 条；原来 8.1 单独的"这一句说完了"事件先不做，本地界面要边说边看时再单独加）。代码里没有：`Settled` 现在没有 `Said`，`internal/turn` 只有 `OnContext`、`OnSettled` 两种钩子（`plugin.go:3-8`）。要的是：每个 `Respond` 的"回合定了"（第 6 条）带上这一回合每一步有字的一句（`Said`：步号、这一步 Clean 之后的字），连同听众（`Audience`）、场合。"句"的定义照第八节：一步说完的整段字。不再要求单独的事件挂在 `endStep`。原因：`OnSettled` 和单独的"这一句说完了"通知是两条各自异步的队列，内核保证不了每句都先于"回合定了"送到，晚到的句子会被中间件的缓冲漏掉；随"回合定了"一起交出就没有先后问题。中间件拿 `Said` 里的字（Clean 之后的），改写在它那一边做（第十节 10.1 第 2 步）。 **内核线的做法**（内核线 2026-10-26 已做，，合进 main 的是；规格-Go后台 8.3 有完整说明）：`Settled.Said []Said{Step, Text}`，`Step` 从 0 数，和这一回合第几次请求对得上；`Text` 是 Clean 之后的字；没字的步不算；提前出错的为空。`Settled` 同时带上这一轮的 `Audience`、`Scenes`。

**中间件要照做的（不是内核的事）**：`OnSettled` 的订阅回调有 30 秒时限（`plugin.go:62`，notify 的默认值）。超时只记日志，同一个订阅者接着送下一条，前一条的回调还在跑（`plugin.go:286-305`），顺序就乱了。所以中间件的回调只把回合放进自己按（渠道、会话）排的队列就返回，裁决在那个队列里做，屏障也在那里（第十节 10.1）。裁决超过 30 秒不影响顺序，因为回调早就返回了。

8.1 的"回合定了"（`OnSettled`，结局 done、stopped、error）内核已经有，但有第 6 条的毛病。渠道线靠它开始第十节的裁决和写库；`Respond` 返回的 `Outcome` 要另外收，早期出错时它是唯一的结束信号。

### 10.1 顺序

**回合定了以后**才开始。句子取自"回合定了"（`OnSettled`）带的 `Settled.Said`（每步有字的一句，带步号和 Clean 之后的字，连同听众、场合；代码里还没有，第九节第 5 条，ADR-184 第 2 条），不再从单独的"这一句说完了"事件收进缓冲；下文说的"这一回合的缓冲"就是 `Said`（按回合 id，不写库）。结局是 done 时，按步号的顺序做下面七步，每一句单独处理；第 7 步的写库是一个事务。有意和 Bun 不同：Bun 是前一条没发出去后面也不发（`router.ts`），这里一句被拦下不影响同回合后面的句子（主会话定的，2026-10-27）。

1. **标记过滤**：内核的 `Clean`（`turn.go:362`，`hub.go:610`）已经做过了：剥句尾乱码、清"】【"，循环最多 16 轮（`cleanRounds`，`turn.go:48`）。中间件这里不重做，只写成"再跑一次同一个函数，结果不变"（幂等，第十六节 B）。
2. **改写**：去句尾句号、剥乱码、按场合和平台定型（ADR-110、ADR-114）。改写是幂等的（第十六节 B；测试的输入用 Clean 之后的字）。**这一步的结果就是"发出去的字"，之后三处都用它**：库里的事件、历史、发送。
3. **字数保险丝**：改写以后超过 200 字（规格-群聊闸门 10.1 第 172 行）→ 拦下，记"保险丝"。在拆条之前算，按整句字数，不按段。
4. **守卫**：`CheckOutbound(text, audience)`（规格-记忆-v2 13.2.8，ADR-181 暂定的做法：代码比原话，再嵌入相似度，像的才问小模型）。守卫查的是第 2 步之后的字，不是原文。守卫的接口是 `channel.Guard`（`CheckOutbound(text, audience)`，签名同规格-记忆-v2 13.2.8），可选再实现 `GuardRoute()` 报刚才走的路（normal / embed-down / model-down），中间件靠它在路变了的时候通知；守卫返回别的错误（库出错、整体超时、panic）照旧拦下，reason 记守卫没判成（主会话定的，2026-10-27）。累计判断的做法：把本回合前面放行的句子用换行接在本句前面一起交给守卫（2026-10-27）。查出来就整句拦下：计划的 kind 记为"拦下"，**不存原文**（它可能含私事，不进库、不进日志；只记命中的记忆编号和次数），不发，不重试（它不是失败，重试只会得到同样的结果）。**守卫出错或超时**：原来写的"也拦下，reason 记'守卫没判成'，不计开口（8.1 的'门'：出错不放行，规格-Go后台第 328 行）"已被 ADR-186 第 4 条改为：嵌入挂了或超时，退回只比原文，没比中的照常发；确认用的小模型挂了或超时，按相似度单独判，超过门槛的拦下；切到退路时提醒主人一次、恢复时再提醒一次，主窗口看得到现在走的是哪条路（规格-记忆-v2 13.2.8 的「出错」条）。嵌入那一半是主人 2026-10-26 定的（主人："暂时先这个吧，老是卡住人家说话不好，让它可以在后台感知自己运行有问题主动走别的路径主动提醒我就ok"）；小模型那一半和"提醒一次、恢复再提醒"的做法是我按主人的意思推的，不是原话（ADR-186 第 4 条）。时限用 13.2.8 的起步值：嵌入 2 秒、模型确认 8 秒、整体 10 秒（同一条）。复读的字过比原话、相似度两段，免掉小模型确认那段（主人 2026-10-26 定，第十九节 A9，ADR-187 第 7 条；需求第三节说"不过模型侧的审核"，嵌入相似度不算模型侧，这是我的解读，主人按推荐定了；相似度门槛量过再定，ADR-181）；戳回去没有字，这一步不查它（主人 2026-10-26 定，见 A8，ADR-187 第 6 条）。
5. **出站记数（只记数，不拦）**：客服腔、"作为 AI"、分点列举这类，记一笔（哪个会话、哪条、命中哪类），界面能看到次数。量一段时间再定拦不拦（ADR-110 第 2 条、ADR-114，盘点 第三节第 53 条）。
6. **拆条**：纯函数，按 ADR-163 和规格-发送前拆条第二节的规则算出 `parts`（第 10.2 节）。随机数由这句话的哈希定（照规格-发送前拆条第二节，同一句话每次结果一样）。拆出来的结果存进计划的段，之后不再重算。
7. **写库（一个事务）**：`events`（她的这句，`origin = character`；试运行的是 `origin = automation:dry-run`；拦下的不写 events）、`outbound_plans`（kind：发、试运行、拦下、已打断、出错；拦下、已打断、出错的计划没有段）、`outbound_parts`（状态"待发"）。这一步之后，计划已经落库，才有第一次 `Send`。出口先 `SendHeld`（落库、返回 `PlanID`、`EventSeq`），`Hub.Commit` 返回以后才 `Start` 发送；发送检查没过返回 `ErrSendCheck`，记成拦下的计划（2026-10-27，第 3 步已做）。 事务提交以后，同步调 `Hub.Commit` 把这一回合交回内核的句子（发的那几步，带 seq 和改写以后的字）交给内核，返回了才开始发、才放下一批（第九节第 1 条）。

回合定了的结局是 done 的，写完库以后，kind 为"发"的计划进入发送（第 10.4 节）。试运行写完即止，不发。拦下的没有段，计划就是记录。

**插件发的（复读、戳回去）不经回合缓冲，也不做第 1、2、3、5、6 步**：复读接了的那一刻，文字直接进出口：第 4 步（守卫，小模型段豁免，见第十节 10.5）、第 7 步（写库，origin 为 `automation:repeater`）；复读按原段重发，不拆条，不做字数保险丝。戳回去没有文字，只做第 7 步和发送检查（第十二节）。插件发的同样进同一会话的出站队列（第 10.5 节），和回合的段排队，不插队。 插件发的写进库以后不调 `Commit`（不是回合说的）；下一批 `Respond` 时把这几条的 seq 放进这一批的 `Seqs`、文字由中间件拼进 `Text`，她的实例才知道自己复读过、戳过。拼的写法和从库里重建实例时一样："（这条是系统替你自动发的（repeater），不是你说的）内容"（`native/internal/history/history.go:216-217`，origin 以 `automation:` 开头的都这样写），接着用的实例和重建以后的实例才是同一种写法（内核线 2026-10-26 建议）。复读以后很久没有下一批，她的实例在那之前不知道自己复读过，这是这个做法本来就有的，接受。

**结局不是 done**（stopped、error）：缓冲的句子全部丢掉，不写库、不发。只写一条计划：stopped 的 kind 为"已打断"，error 的 kind 为"出错"（都没有原文，右侧栏显示"她这一轮没说出口"；出错的另带一行原因）。这和 Bun 的口径一致：说到一半被打断的回复不发，路由标"没发出去"（agent-and-console.md:33，subsystems/qq.md:117）。

**屏障**：同一个会话，上一回合的"回合定了"处理（裁决、写库、`Hub.Commit` 返回）没完成前，新放行的批次挂起：不 `Steer`，也不 `Respond`。这一层由中间件自己的队列做：它是 `Respond` 的调用方，等自己的裁决完成再发下一批。内核的 `OnSettled` 是异步的，不保证处理完了才返回（第九节第 6 条）。这样新回合的历史一定含上一回合已经发出去的句子（第十六节 B）。屏障不设超时（裁决的时限已经在第 4 步里有：守卫的整体时限 10 秒（规格-记忆-v2 13.2.8），超时就拦下，所以整体有上界）；早期出错也要结束这个屏障（第九节第 6 条），结局是 error 的回合不能卡住后面的批次；卡住时记日志，界面显示"等待上一句裁决"。

**为什么写库在发送之前**：Bun 是发完以后才写映射（`qq.ts:777-783`），中间崩了，回声到了认不回来，会被存成"不是她说的"（`qq.ts:301-308`）。先写计划、再发，崩了以后剩下的是"发送中"，启动时标成"结果未知"（第 10.6 节），不会丢，也不会重发。

### 10.2 拆条和节奏

- **拆条**：ADR-163 的规则，两条都要写全：整段只有一条、不到 30 字的一句话，不拆；30 字以上的照规则拆；模型自己用空行分成几条的，每条 20 字以上照规则拆，不到 20 字的仍按 0.7 的概率（ADR-163 第 2 条，ADR-129）。规则的参数在规格-发送前拆条第二节，这里不重复。
- **随机数**：由这句话的哈希定，同一句每次结果一样（规格-发送前拆条第二节）。拆出来的结果存进计划的段，库和发出去的拆法因此一致。
- **拆条和截短按字符（rune）边界切**：emoji（四字节）不切开；CRLF 和 LF 同样处理；分块处理和整段处理结果一致（第十六节 B）。
- **平台上限**：`Caps.MaxText` 给拆条用。QQ 的硬切线按现值（Bun `qq/split.ts`）。
- **节奏**：Bun 的现值是每字 40 毫秒、最多 2500 毫秒、重试间隔 1000 毫秒（`qq.ts:750`，`qq.ts:762`）。节奏在计划里定死：每一段记一个 `pause_ms`。**停顿从上一段的最终状态（确认、失败、结果未知）开始算，不是从发起开始算**（Koishi 的 `sendQueued` 按发起时刻计时，K `session.ts:218-219`，是反例）。
- **为什么不用"发出去以后再等"**：因为"发出去"和"结果确定"是两回事（第 10.4 节），停顿要等结果确定才开始，否则下一段可能和上一段的结果未知同时在路上。

### 10.3 发送计划

计划和段都是结构列，不存 JSON（盘点第四节第 3 条，`qq.ts:853`、`router.ts:171` 的正则读取是要去掉的做法）。

| 表 | 列 | 说明 |
|---|---|---|
| `outbound_plans` | `id`、`character_id`、`conversation`、`event_seq`（拦下的为空）、`account`（发送用的号）、`origin`、`kind`（发 / 试运行 / 拦下 / 已打断 / 出错）、`reason`（守卫拦下、守卫没判成、保险丝、被打断、出错；只有非"发"的计划写）、`state`、`created_at`、`done_at` | 一次回复一条计划。`state` 只在终态写一次，测试断言它等于段状态的汇总（第十六节 B）；留它的理由是界面和统计要快查，拦下、已打断、出错的计划没有段，仍要有状态 |
| `outbound_parts` | `plan_id`、`idx`、`kind`（text / image / emoji / quote / poke）、`text`（kind 为 text 时）、`ref`（图片哈希、表情 id 或引用的平台消息号）、`pause_ms`、`state`、`attempts`、`platform_id`、`via`、`err`、`sent_at` | 一段一行；`(plan_id, idx)` 是主键。拦下的计划没有段，不存原文 |

### 10.4 状态机

段的状态：

| 状态 | 进入条件 | 下一个状态 |
|---|---|---|
| 待发 | 计划写库 | 发送中（前一段到达终态后，或计划开始发送时第一段）；已中止（关闭、切档、重启、本计划前面有段失败） |
| 发送中 | 调了 `Send`，状态已落库 | 确认（回执 confirmed）；明确失败（回执 failed）；结果未知（回执 unknown，或超时没回） |
| 确认 | 回执 confirmed | 终态 |
| 明确失败 | 回执 failed | 重试（尝试次数小于 3，间隔 1 秒，回到发送中）；尝试次数到了 3，段失败（终态） |
| 结果未知 | 回执 unknown；超时没回 | 认领（回声，见下）；超过 5 分钟仍未知，段终态。**不重试** |
| 已中止 | 关闭时还没发、切档、重启、本计划前面的段失败（用完重试或结果未知） | 终态 |

**回声认领（总规则）**：回声可以在任何未终态的段上认领，包括"发送中"（回包还没到）、"明确失败、等待重试"、"结果未知"。认领以后段直接变为"确认"（`Via = echo`），之后到的回包结果和待执行的重试一律作废（取消重试计时器）。"已中止"的段收到回声，只记观察，不改状态。认领的窗口是 5 分钟（`UNSURE_ECHO_MS`，`qq.ts:80`），从这一段第一次调 `Send` 起算。认领键是 `(账号, 会话, 文字)`，每个回声只认领一段，每段只认一次（先到先认；带图、转发段对得上多段时先按优先级挑，见规格-链接发送改版 A1“回声认领扩到带图的段”）。主人手发的同文字：认领只靠文字和窗口，协议端没有别的可比的键时区分不开，这是**残余风险**，写明在这里；若真机帧里有能区分的字段（比如 `sub_type` 或设备），第 6 步前以真机帧为准（第二十节）。

计划的状态（kind 为"发"的计划）：全部段确认 → 完成；有段明确失败且用完重试，前面的都确认 → 部分（后面的标已中止）；任何段结果未知 → 结果未知（主窗口写"不知道发出去没有"，不是失败，也不是完成）；kind 为拦下、试运行、已打断、出错的，状态就是 kind 本身（守卫没判成之类的原因写在 reason 列，不改状态）。

**"明确失败"和"结果未知"在界面和统计上必须分开**（清单第⑩类，Bun 把它们合在一个 `partial` 里，`qq.ts:791-795`）。

### 10.5 发送的几条硬规则

- **只有一个出口**：`Outbox.Send(characterID, origin, conversation, parts []Part)` 是唯一能让适配器发消息的入口，适配器的 `Send` 和 `Poke` 只由它调用。账号由出口按 `characterID` 查配置里的绑定（ADR-007）得出，写进计划的 `account` 列；群里两个号两个角色时，`origin = character` 说的是哪个号，就由这一条定。`parts` 的种类是 text、image、emoji、quote、poke（复读按原段重发，需求第三节；戳回去是 poke）。
- **挡法**：插件只拿 `Outbox` 的接口，不拿适配器。Go 的 `internal` 规则只挡 `native/` 树外的代码（推断：读 Go 规范，未在本机实测），挡不住 `native/internal/channel/qq` 直接 import `native/internal/onebot`（同一棵树下）。所以靠两样：插件的构造函数只收 `Outbox`；架构测试只准装配（`internal/app`）和入口依赖适配器（适配器实际在 `native/internal/channel/snowluma`；第十六节 B，2026-10-31 改），红了就是有包绕了出口。
- **来源**：出口的来源只有三种，调用方只填前两种，第三种由出口决定：`character`（回合说的）、`automation:<插件名>`（插件发的，例如 `automation:repeater`、`automation:poke`）、`automation:dry-run`（试运行档：由 Outbox 按会话当前档位决定，不是调用方填；规格-群聊闸门 10.1）。入站里自己号的消息另有两类，它们只出现在入站回声的分类里，不是出口的来源：`human`（真人登录她的号手动发的，现在的 notMine）、`external`（以前别的程序用这个号说的）（规格-插件 第四节）。
- **守卫**：所有出口的文字都过守卫（8.1、盘点 3.6、第 10.1 节第 4 步）。复读的字过比原话、相似度两段，免掉小模型确认那段（需求第三节说"不过模型侧的审核，但过发送检查"；把嵌入相似度算在"不是模型侧"这边是我的解读，主人 2026-10-26 按推荐定了，第十九节 A9，ADR-187 第 7 条；相似度门槛量过再定，ADR-181）。戳回去没有字，不过文字守卫，只过发送检查（风控间隔、渠道断开时不发，需求第三节；主人 2026-10-26 定，第十九节 A8，ADR-187 第 6 条）。
- **同一会话的出站串行**：一条队列；段与段之间不插入别的计划的段；戳回去不占停顿。
- **不许发送失败后自己补发**：只有"明确失败"且尝试次数没到 3 次才重发。
- **不许在关闭以后写库**（第 10.6 节）。

### 10.6 关闭、打断、重启、切档

- **关闭渠道**：先停止收新事件（已经入库的不动）；队列里还没发的段全部标成"已中止"；正在"发送中"的段等它的回执，最多等 5 秒，等不到的标成"结果未知"。之后关库。
- **关闭以后收到的回执**：什么也不写（Bun `qq.ts:846`、`qq.ts:859` 已经这样做，要保留）。
- **打断**（ADR-020 的口径：回合被新消息打断。什么时候中间件调 `Stop`，见第六节第 4 步：被叫到的新批次，以及 OwnerAsked 为真或档不同的新批次，才 `Stop`）：
  - 回合还没定（stopped）：缓冲的句子丢掉，不写库、不发，只写一条"已打断"计划（没有原文）。这一点和 Bun 现行的口径一致（说到一半被打断的不发）。
  - 回合已经定了、段在发送：这个阶段**不因为新消息中止**。排着的段照发（同一会话的出站是串行的，第 10.5 节）；只有关闭、切档、重启才会中止它们。
- **切档**（群从"说话"切到"只记录"或"试运行"，或者群的开关关掉）：还没发的段标成"已中止"（没发出去）；发送中的段让它完成，并记结果。验收：停顿中切档，后面的段不调用 `Send`。
- **重启**：启动时，所有"发送中"的段标成"结果未知"，**不重发**（进程可能已经在协议端发出去了）；所有"待发"的段标成"已中止"，**不续发**（它们是几分钟前的话，可能已经过时）。计划状态相应写。之后的回声认领照常。这一条直接对应清单④⑩。

### 10.7 试运行

- 试运行的回合：缓冲的句子照第 10.1 节的第 1 到 6 步做（改写、守卫、拆条都照做，效果和正式一样），第 7 步写 `events`（`origin = automation:dry-run`）和计划（kind 为"试运行"），不调 `Send`。
- 算进"这小时说了几次"（规格-群聊闸门 10.1 第 165 行，见第八节"计数的口径"）；不进记忆和学说法（`automation:*` 本来就不进，规格-插件 第四节）；不进她的下一轮历史（第九节第 2 条，历史读取跳过这种事件，规格-群聊闸门 10.1 第 167 行"她没真的说过"）。
- 界面画"她会说：……（试运行，没发出去）"（规格-群聊闸门 10.1 第 164 行）。

## 十二、复读和戳一戳的具体规则

**复读**（规格-群聊插件第二节 + ADR-171 第 3 条 + 需求第六节）：

- 只看同一个群里两个**不同的人**接连发的同一句。她自己的消息不算人数。
- 同一句的判断：文字去掉首尾空白、连续空白合成一个，再比；同音也算一样（拼音只差前后鼻音，加主人确认过的同音写法，规格-群聊插件第二节的 `meme-table.json` 那 10 组）；平翘舌和 l/n 不放宽。图片按内容哈希，表情包按哈希，不按临时链接。**哈希为空的图片（迁移来的旧段、还没算出来的）不参与比较，视为不可比，记一行日志**（清单⑯，空哈希不能判成相等）。@、引用、语音、文件、卡片不复读。
- **只跟最近的**：复读要发生在这一批的最后几条里。
- **同一轮只跟一次**：指纹变了才算新一轮。
- **冷却**：同一个群跟过以后等 3 分钟（默认，可调）。没有每小时上限（主人 2026-10-14 定过）。
- **概率**：默认 100%，可调，每次掷都记日志（掷的数、命中没有）。
- **被叫到的批次不接**（B10）：这一批里有 @ 她、引用她、叫她名字，复读不接（第四节的 `Addressed`）。**这一条是我的建议，ADR-171 没有这一条**（见第十九节 B10）：复读是"跟着群友一起搞"（ADR-171 的理由），被叫到就该回答，不该跟着复读。
- **接了**：这一批不交给内核（第七节）；闸门照常计数，并计她说过话的退避（需求第二节）；她跟着发的那句照常存库（`origin = automation:repeater`，第十节的守卫按上面的规则过：代码比原话和相似度两段，小模型段豁免），并计她的"开口"（第八节）。
- **复读的内容**：文字、同一张图、同一个表情包，按原段重发（需求第三节）；`parts` 原样进出口。
- **优先级初值**：复读 20（需求第四节）。

**戳一戳**（规格-群聊插件二点五 + 需求第三节）：

- 只回戳她的人。她自己戳出去的回声不算。
- 同一个人 60 秒内只戳回一次。
- 同一个群每分钟最多戳回 3 次。
- 对方是机器人（名单 `data/dev/voice-trials/bots.txt` 那类，和按行为认出的模板号）不戳回。
- 默认全关，主人可以按群各自打开（需求第三节"设置里按群开关"）；私聊默认开（只限她本来就接的私聊），每个私聊能单独关（ADR-189，第十九节 A4）。
- 戳回去走出口的 `poke` 段（`Caps.Poke` 为真才发；不是文字发送）。**不过文字守卫**（没有字；8.1 第 332 行原来写的"都过同一道门"，"门"指文字守卫，没有字的戳回去只过发送检查，主人 2026-10-26 定，见第十九节 A8，ADR-187 第 6 条，规格-Go后台 8.1 第 332 行已同步），**过发送检查**（风控间隔、渠道断开时不发，需求第三节）。**不计开口，不计退避**（需求第二节表）。
- 每次都记一行：谁戳的、回没回、没回是因为哪一道限流。
- 这些数字都是初值，可调。优先级初值戳一戳 10（需求第四节）。

**两家怎么做戳一戳（对照）**：AstrBot 把它转成消息段 `Poke`，群里默认不唤醒，私聊唤醒但文本为空、不调模型（AB `pipeline/process_stage/method/agent_sub_stages/internal.py:193-200`，拆解 AstrBot 第一节第 9 条）。MaiBot 把它当成 `is_notify` 的文本消息，写进 `message_cache`，计入待处理数，参与提及检测，文本带昵称会强制进规划器（拆解 MaiBot 第六节第 6 条）。我们的通知不计闸门、不计提及（第三节），戳回去由渠道层的 QQ 插件显式决定（ADR-171 第 3 条），不靠唤醒规则碰运气。

## 十三、QQ 适配器（OneBot v11）

- **连接**：**正向 WS 为主**：SnowLuma 在 `127.0.0.1:3001` 开了 WS 服务，Sumika 去连它（ADR-027 "连 SnowLuma 默认的正向 WebSocket 服务"，规格-QQ渠道 九点五）。**Go 和 Bun 一样作为普通客户端，共用 SnowLuma 现有的 `ws-default`，不改它的配置**（主人 2026-10-26 定，ADR-185；第 6 步先只收不发，连得上就算核实过它能再接一个客户端，第二十节第 3 条）。SnowLuma 的配置里这个键叫 `wsServers`（`<SnowLuma 目录>/config/onebot_<号>.json:17`（只看键名，号码不抄进来），即 SnowLuma 作为服务端；规格-QQ渠道第 175 行只写了 `127.0.0.1:3001`，没有键名）。反向 WS 不做：代码里没有，要它就得改 SnowLuma 的配置，需要主人点头（AGENTS 安全边界）。令牌用 `Authorization: Bearer`，不写进日志（规格-QQ渠道第八节）。
- **握手前的事件**：**不丢**。NoneBot 在 `lifecycle connect` 之前收到的事件直接丢弃（A `v11/adapter.py:355-360`），是反例。我们照常解码、照常交给中间件，靠第六节第 3 步的去重兜底。
- **心跳**：协议端周期性发心跳（OneBot v11 的 `meta_event`，带间隔字段；SnowLuma 是否带未核实）。超过 3 个心跳间隔没收到，或连接断了，判为掉线（规格-QQ渠道第六节）。提醒的 30 秒是另一个数字，见第十四节"掉线提醒"一行。心跳间隔用协议端给的值，不写死。
- **重连**：我们是客户端，由我们重连：1 秒起，翻倍，最多 60 秒（规格-QQ渠道第六节；Bun `daemon/onebot/client.ts:23、186-187`）。AstrBot 的适配器异常后只记日志、不重启（AB `platform/manager.py:259-285`，拆解 AstrBot 第一节第 10 条），这一点不照：我们断了就重连。**重连前先关掉旧连接**：半开的旧连接不等它超时。
- **动作调用**：按 echo 配回包，超时 10 秒（Bun `client.ts:23`），超时的错误带 `maybeDone` 标记（`client.ts:31、77`），中间件据此把段记成"结果未知"而不是"明确失败"。NoneBot 的 `NetworkError` 只有一句文字（A `v11/exception.py:26-31`），分不清"没发出去"和"已经执行"，这一点不借。
- **回包只看 `retcode` 等于 0 才算成功**：Koishi 是这样（O `src/types.ts:575`）。非 0 不一定是失败：协议端可能对"已接受、异步执行"的动作返回别的码。所以非 0 且不能判定失败的，记为"结果未知"，不重试；异步码的具体值以 SnowLuma、NapCat 的真实回包为准（第 6 步前录样本核对，第二十节）。
- **段翻译**：OneBot 段数组 → `Seg`，见第三节（含旧段到新 Kind 的映射）。CQ 码字符串只在认 OneBot 的旧数据时出现，入库前转成段。
- **通知翻译**：群撤回、私聊撤回 → `Notice{kind: recall}`；戳一戳（`notice.notify`、`sub_type poke`）→ `Notice{kind: poke, actor, target, conv}`，`target` 是她的号时才是"戳她"；表情回应 → `Notice{kind: reaction}`；被踢（`bot_offline`，规格-QQ渠道第六节，SnowLuma 未核实）→ `Notice{kind: kicked}` 同时发 `Status`；其他 → `Notice{kind: other, raw}`，不丢（Koishi 的做法是丢，O `utils.ts:303`，我们不照）。
- **元事件**：心跳、生命周期 → `Status`，不进 `events`（第六节第 1 步）。
- **自己发的消息**：`message_sent`，或者 SnowLuma 的 `reportSelfMessage` 打开后的回报，都进 `Inbound{kind: self}`，由中间件按第十节的认领规则处理。
- **号码 0**（ADR-221，2026-10-31）：协议端换不出号码时填 0。发言人、私聊对方、通知的做事的人、撤回的操作人（0 不覆盖原来的做事的人）和被戳的人读到 0 一类的写法都当成没有（`snowluma.go` 的 `qqID`）；外层 `user_id` 是 0 不回退 `sender.user_id`，发言人是空的消息中间件不收；私聊通知做事的人是空时，准入按会话对方认陌生人（`app/channel.go` 的 `admitNotice`）。at 段、群号、消息号不走这条。
- **协议端之间的差别**（SnowLuma 和 NapCat）：表情包的标记（`sub_type`）、转发的接口名（`send_forward_msg` 和 `send_group_forward_msg`）（规格-QQ渠道第九节）、历史分页的锚点写法（盘点第三节第 27 条）都在适配器里分开处理，中间件看不到。
- **测试**：假协议端（按 OneBot v11 回包）。录下来的真实帧只放在 `data/dev/` 下，测试里只用编的号和群名（第十六节）。

**B. 契约测试**（独立于 Bun，外部审计 F07：写明预期，不拿 Bun 当答案。每一项都要有测试，并且在对应的错误实现上会红）：

- **去重**：同一个键到达两次，事件只存一条，观察有两条（两个账号）。号为空或 0 的两条不同消息，都入库（不去重）。号 `2^53+1` 往返不变。
- **事务**：写到一半失败（模拟 `qq_msgs` 写入报错），事件表、观察表都没有这一条。
- **乱序**：引用补全慢 60 秒，普通消息照常入库；引用补全完了以后，事件的引用字段更新。
- **补录和实时交错**：连续水位不越过未补或未证实区间，含已放弃缺口；检查位置独立供调度，两者及缺口按[补录规格](规格-QQ收图下载和断线补录.md) 5.2 原子结算。缓存首页、重复页、锚点重合不能当完整证明。实时到达不清旧洞；历史按平台时间排序并按平台号去重。补录 200 条含 @她，拦截链、闸门和内核调用为 0，热闹计数不变。
- **回合和队列**：回合进行中来一句，入库不等回合结束（屏障控制）；闸门不放行的只入库和观察；放行且被叫到的，`Stop` 后再 `Respond`（回合被打断，缓冲丢掉，不写库）；放行但没被叫到的：OwnerAsked 为真、或档不同的，`Stop` 后再 `Respond`；其余的走 `Steer`。验收：主人在群里没叫她的一句，`OwnerAsked` 为真，记忆可召回。回执延迟 10 秒，下一批闸门仍看到"刚说过话"（退避算在途段）。
- **回执三态**：确认、明确失败、结果未知各走一遍。明确失败最多 3 次，间隔 1 秒。结果未知不重试。
- **回执缺失**：适配器返回零值回执，必须报错，不是成功（盘点 4.4 第 1 条的守卫）。
- **回包非 0 的异步码**：记为结果未知，不重发。
- **回声认领**：结果未知的段、发送中的段、明确失败等待重试的段，各自被回声认领；回声先于回包到达；回声落在重试等待期（重试作废）；回声在超时之后（5 分钟内认领，之后不认）；回声在已中止之后（只记观察，不改状态）；两个账号同群同文字各一段（不串）；同账号两段同文字（先到先认）。主人手发同文字：记录实际行为（残余风险，第十节 10.4）。在"只比文字、不分账号"和"只认结果未知"的错误实现上红。
- **段间停顿**：下一段在上一段到达终态后才开始，停顿从终态算起。
- **段失败后的其余段**：某段用完重试，或结果未知，其余待发段标"已中止"，`Send` 调用数不增加。在"后面照发"的错误实现上红。
- **关闭**：队列里的段变成已中止；发送中的段等回执最多 5 秒，之后变成结果未知；关闭后到的回执不写库。
- **重启**：计划里有"发送中"的段，启动后变成结果未知；有"待发"的段，变成已中止；没有任何 `Send` 调用。
- **切档**：停顿中切档，后面的段不调用 `Send`。
- **回合的裁决**（渠道回合，不由内核写库；**已有测试（第 3 步）**）：守卫拦下 → 下一轮上下文不含该句，库里没有这句的事件行，计划 kind 为拦下，计划里没有原文。试运行 → 下一轮上下文不含该句，库里这一回复只有一行（`origin = automation:dry-run`）。回合被打断（stopped）→ 缓冲丢掉，不写库、不发；下一轮上下文不含该句。守卫出错或超时 → 照第 10.1 节第 4 步的退路（ADR-186 第 4 条，原来的"拦下，reason 记'守卫没判成'"已改掉）：假嵌入挂了 → 只比原文、没比中的照常发；假小模型挂了 → 按相似度单独判，超过门槛的拦下；连发多句只在切到退路时提醒一次，恢复时再提醒一次（测法同规格-记忆-v2 的"守卫的退路"一项）。下一轮请求体里，这一句只出现一次，字是改写后的（不是原文，也不重复，见第九节第 1 条）。
- **替换和 catchUp**（真内核端到端：现在只对着假内核测，等内核线把测试夹具抽成 `internal/turn/turntest` 再补）：渠道回合定了以后，实例里这一回合的话换成 events 那一行（带 seq）；之后的 catchUp（`hub.go:420-437`）不再把这一句追一次，请求体里只有一份。在"替换后不登 seen"的错误实现上红。
- **屏障**（真内核端到端：现在只对着假内核测，等内核线把测试夹具抽成 `internal/turn/turntest` 再补）：上一回合的回合定了处理没完成时来的新批次，它的 `Respond` 在处理完成后才发出；它的历史含上一回合已发出去的句子。
- **回合的 Steer 与 Stop、回合定了**（第九节第 4 到 6 条，内核线改了以后才能测；真内核端到端：现在只对着假内核测，等内核线把测试夹具抽成 `internal/turn/turntest` 再补，2026-10-27）：渠道会话的回合在跑时 `Steer` 找得到实例、`Stop` 能停它，不在跑时 `Steer` 返回 false、调用方改走 `Respond`。"回合定了"带的 `Said` 里，每一步有字的一句都在（步号、Clean 之后的字），连同听众，渠道回合不写库时也一样；不会有句子晚于"回合定了"才到。每个 `Respond` 恰好一个"回合定了"，包括读卡失败、找不到模型、建实例失败、上下文超限这几种早退，`TurnID` 三种结局都有。在"早退不发"的错误实现上红。
- **回调不阻塞**：`OnSettled` 的回调只入队就返回；模拟裁决慢 35 秒，之后的回合仍按序裁决、不并发（第九节之后的那一段）。在"回调里直接裁决"的错误实现上红。
- **早期出错不卡屏障**：某回合在早退处出错（结局 error），屏障照样放开，后面的批次能进来。
- **改写**：幂等（穷举或随机样本，清两遍等于清一遍，未命中的部分保持原样）；拆条和截短按字符边界，emoji 不切开；CRLF 和 LF 同样处理；分块处理和整段处理结果一致。
- **防伪造**：内容里的换行和 `[时间] 名字：` 样式被转义；伪造的行不产生新的身份行；`Text` 的行数和 `Seqs` 对得上，不混入上一批；本地零点前后各一条，时间不倒、时区是 +08:00。
- **拦截链**：优先级 10 的先于 20 的；返回"接了"以后，闸门只计数、内核都没被调用；插件报错、超时都当没接；只记录档不跑；试运行档的输出是 `origin = automation:dry-run` 的事件，不调 `Send`。戳一戳加同批的 @ 提问：内核收到提问。
- **闸门计数**：复读接了以后，闸门的"这小时热闹"计数照常加，退避照常更新；被叫到的批次复读不接。
- **听众**：QQ 群里主人发的被叫到的消息，`OwnerAsked` 为真，`Scope` 和群友的不同（两个实例）；QQ 群里群友发的，`OwnerAsked` 为假。
- **ADR-174 已知的坑**：主人问过以后，群友再问，她不说（守卫兜底：规格-记忆-v2 13.2.8 的正样本分类含"主人问过后群友再问"这一组；给那几行标记是记忆线的事，这里只验 `OwnerAsked` 正确）。
- **多账号**：两个 `self_id` 在同一个群，事件存一份，观察两份；连上后核对的号不在配置里的，不接入（断开、记日志）。同一账号绑两个角色、同一个出口绑两个适配器，启动即报错（MB 拆解第七节第 8 条）。
- **架构**：只有装配（`internal/app`）、桌面程序的入口和 `cmd/` 下的命令能依赖适配器 `internal/channel/snowluma`，其余包都不能（插件不能绕过出口；`channel/arch_test.go`。2026-10-31 从"channel 下不含 internal/onebot"改来：适配器搬进 channel/snowluma 以后，原来那条一直在查一个不存在的包）。
- **分库**：Go 的数据目录和 Bun 的库不是同一个文件（启动时检查，不一样才开）。Go 内部再按平台分库（ADR-199）：本地、QQ 各一个库文件，两个库互不含对方的行，验收见[规格-聊天记录按平台分库](规格-聊天记录按平台分库.md)第八节。
- **戳一戳**：同一个人 60 秒内第二次不回；对方是机器人不回；戳的是别人不回；自己戳自己不回。戳回去不计开口、不计退避。戳一戳的文本里带她的昵称：`Addressed` 为假，不进闸门，不计提及（MB 拆解第六节第 6 条的反例）。
- **适配器稳健性**：一帧坏 JSON 不关连接，只丢那一帧；未知通知保留，不丢；心跳 1 小时后 `events` 行数不增加（心跳进连接状态）。@ 和引用只靠段：@她的段（`Target` 是她的号）翻译后，中间件算出的 `Addressed` 为真；不依赖顶层标记（MB 拆解 2.5 节：旧链上顶层的 `is_at` 丢了，@ 检测就失效）。
- **通道门**：3 段已中止不暂停；3 段明确失败暂停；恢复（适配器报连接恢复）后清零，或主人点恢复。
- **心跳半开**：重连前关旧连接；半开超过 3 个心跳间隔判为掉线，掉线超过 30 秒后提醒触发。
- **迁移**：旧段类型到新 Kind 的映射（第三节表）都有测试；迁移来的旧图段 `Hash` 为空，两张空哈希的图不复读。
- **空会话补录**：空库首次启动的起点；协议端没有历史接口时的未补区间；翻满页数仍没到起点。
- **脱敏**：令牌不出现在任何日志和错误信息里（规格-QQ渠道第八节）。编的号码和令牌放进 `card` 的 `raw`，入库后界面和导出都查不到（清单㉑）。

**C. 改坏检查**（LESSONS，判定类和放宽类规则）：B 里的每一项，都要在一个故意改坏的实现上红过一次，提交说明里写"改坏 X 红了"。

**D. 真实样本**（每样单独问、点头再做，主人 2026-10-26 定，第十九节 A10，ADR-187 第 8 条；每组跑之前照实报估算：调用次数、模型、大概花费，主人点头再跑；AGENTS 第 4 条"花钱多的批量模型调用"，ADR-183 第 3 条对表二是同一条规矩）：

- 发送前守卫的正负样本，**各不少于 20 个**（ADR-181 第 3 条，规格-记忆-v2 13.2.8；判定类规则，LESSONS）。任何一边不够，就写"这一边没量够"，不写"都过了"。

- 拆条和改写：真实样本 5 到 10 条（核心文字功能，LESSONS 2026-10-16 的"合并前拿真实样本过一遍"）。

## 十七、禁止的偷懒写法

- **不许**把回执做成 `string | void`，**不许**把零值或 `nil` 回执当成功。
- **不许**让内核为渠道来的回合直接写句子进库（第九节第 1 条）；**不许**在库里再改一次句子的文字（写库只一次，文字是改写以后的）。
- **不许**在回合定了之前写计划或写库（拦下、试运行、打断的句子就不进库）。
- **不许**在回合定了的裁决没完成前，发起同一会话的下一回合（屏障，第 10.1 节）。
- **不许**守卫出错或超时时悄悄放行：退路照第 10.1 节第 4 步（ADR-186 第 4 条），切到退路要提醒主人、每句记走的是哪条路（日志不含原文）。原来的"出错或超时就不放行"已被 ADR-186 第 4 条改掉。
- **不许**对"结果未知"自动重发。
- **不许**段失败后，其余段照发。
- **不许**插件拿到适配器（只拿出口），**不许**戳回去绕过出口或跳过发送检查。
- **不许**补录消息进拦截链、进闸门判断，或触发回复。
- **不许**空号也去重；**不许**把空哈希当成相等。
- **不许**把心跳存进 `events`。
- **不许**在新代码里靠 `qq:` 前缀或 `qq/` 事件名认渠道或人。
- **不许**用 CQ 码字符串存库或做比较。
- **不许**用临时图片链接当图片身份。
- **不许**丢未知的通知（保留为 `other`）。
- **不许**在拦截插件报错时静默（记日志、计数，并且留一行在右侧栏）。
- **不许**让两个系统（Bun 和 Go）同时对同一个号发送，**也不许**同时写同一个库文件（规格-QQ渠道九点五；第十五节第 6 步）。
- **不许**在测试里用真实群名片、真实号、真实聊天内容（LESSONS，2026-10-19 的 f306d2f）。
- **不许**为了让测试过而放宽门槛，不做改坏检查（LESSONS，2026-10-19 的 3f36b1c）。
- **不许**把"关停适配器"这类命令开给聊天里的人（MB `chat/message_receive/bot.py:562-577` 的远程 `/offline` 分支：名单里的远程用户能关掉全部适配器；函数的 docstring 在 :526 写着"仅供本地终端使用"）。执行类只给主人 × 主窗口（AGENTS 安全边界）。
- **不许**用随机兜底句整段替换回复（MB `chat/utils/utils.py:519-530`、`:597-618`，池里有 `"()"` 和 `"懒得说"`）。超字数的走保险丝（第十节 10.1 第 3 步），拦下记"保险丝"。
- **不许**把群消息原文写进 INFO 日志（AB `event_bus.py:149-156`）。日志只记长度、会话号和结果。
- **不许**让"监听全部消息"的插件把对话变成"叫到她"（AB 内置 ALL 过滤器，`builtin_stars/astrbot/main.py:41-42`）。拦截插件只在声明的场合和开关下跑（第七节）。
- **不许**在 `OnSettled` 的回调里直接做裁决（第九节第 6 条之后的一段：回调有 30 秒时限，超时后同一个订阅者会接着送下一条，前一条还在跑）。回调只入队。
- **不许**留绕过出口的主动发送：AB 的 `Context.send_message` 不经过流水线（`star/context.py:655-736`），我们的出站都经过第十节的出口。
- **不许**把 `/` 当渠道命令的前缀：AB 的默认唤醒前缀是 `/`（`config/default.py:305`），MB 把 `/` 开头的群消息当命令（跳过防抖、重启不回填）。我们的命令用 `#`（`#sl`，第十四节）。

## 十八、已知的坑

按清单编号：

- **④ 关闭以后还在回来**：插件停掉、渠道关掉以后，还在路上的回执、回声、补录，不写库、不发消息（第十节第 10.6 节）。Bun 的做法 `qq.ts:158` 的 `live` 标记要保留，并且覆盖到回执路径。
- **⑤ 多角色、多账号、多会话**：一个群两个号，只存一份，两份观察；两个角色各有闸门和实例（第十一节）。Bun 的 `router.ts:111` 只取这一批的说话人作听众，ADR-174 上线后主人在群里问自己的事时，听众要带 `OwnerAsked`（第四节）。
- **⑤ 主人私下说的事（ADR-174 已知的坑）**：主人问过以后，那几行留在这个群实例的上下文里，群友再问，她可能说出来。给那几行标"主人私下说的，他问才答"是记忆线的事；守卫兜底（规格-记忆-v2 13.2.8 的正样本含这一组）；考题"主人问过后群友再问"在记忆线的考题集（规格-记忆-v2 第十一节）。
- **⑥ 权限判断与执行对象不一致**：听众在入口算一次，之后内核、工具的关、记忆都用同一个 `Audience`。Bun 的 `fullMemory` 在平台插件算（`qq.ts:443`），到了路由才用，两处可能不一致；Go 版只在中间件算一次。
- **⑧ 收到不等于可用**：入库和引用补全分开（第六节第 7 步）；补录的洞要结构化记录，不能只写一条通知（`qq.ts:1145-1152`）；识图等待的 8 秒、45 秒（`router.ts:19-26`）是内容插件的事，中间件只保证"收到"的通知早。
- **⑩ 失败不是全有或全无**：发送计划是逐段的；明确失败和结果未知分开；打断、守卫拦下、关闭、重启、切档各有各的终态（第十节）。Bun 的 `partial` 把它们合成一个，`qq.ts:791-795`。
- **⑪ 同一事实口径不一**：发出去的字在库之前定型一次（第十节 10.1 第 2 步）；拆条的结果存进计划（第 10.1 节第 6、7 步）；场合只由 `Conversation` 字段决定（第四节）。
- **⑬ 并发和交错**：回声先于回包到达（`qq.ts:831-833` 的 `flight.echo`），要有测试；补录和实时的水位（第六节第 4 步）；同一批几个角色同时放行（第八节）；回合进行中来的新批次（第六节第 4 步，`Steer`）。
