# 规格：网页读取的“本机 Firecrawl”提供方

> 状态：草稿（2026-11-19），**没实现、没测、没经主人确认**。来源：主人 2026-11-19 问 Firecrawl Local（2026-11-18 发布）“做成插件，还是在新分支里做成新特性合进某个模块”。下文标“我定的，待确认”的都没有主人原话支撑。
> 调研和出处：[调研-FirecrawlLocal-2026-11-19](notes/调研-FirecrawlLocal-2026-11-19.md)（下文简称 FL 笔记）。上游规格：[规格-网络搜索和抓网页](规格-网络搜索和抓网页.md)（本规格补它“这一版不做：浏览器、JavaScript 执行、PDF”里的一部分，**需要主人同意放宽**，见第九节）。

**回答“插件还是特性”**：不新做插件，做成 `web` 内置插件的一个读取提供方（`native/internal/web/firecrawllocal`），和 `http`、`tavily`、`firecrawl` 并列，在已有的 `web.fetchOrder` 里排队。理由：它不增加给模型的工具（模型看到的还是 `web_fetch`），关了它没有“用户可见的后果”（只是少一家读取后备），不符合开发指导“用户看得见、关了有明确后果的功能才是插件”；ADR-376 的“进程外 MCP”那一档是要把工具交给模型，不是给 `web_fetch` 换后端。这件事在一个分支（`docs/firecrawl-local` 只是文档，实现另开 `feat/firecrawl-local`）里做完合进 main 即可。

## 开工卡

- **我理解成**：给 `web_fetch` 加一家可选的读取提供方 `firecrawl-local`，它连用户**自己在本机起好的** `firecrawl-local serve`（`http://127.0.0.1:<端口>`），读我们自己的 `http` 读不了的页面（JS 渲染、PDF、Office）。默认关，配了地址才启用；读取仍由 `web.Service` 的预检、授权、额度、缓存和“外部不可信资料”包装管着。
  - 正例：主人在本地私聊里让她读一个必须执行脚本才出正文的页面，`http` 读到空壳，链上换到 `firecrawl-local`，拿到 markdown，结果头仍写“外部不可信资料”，额度记 0。
  - 正例：主人让她读一个 PDF 链接，`http` 报 `WEB_BINARY_CONTENT`，`firecrawl-local` 返回文字。
  - 正例：没配 `web.firecrawlLocal.url`，行为和今天完全一样，`firecrawl-local` 在链里被跳过。
  - 反例：让模型直接拿到 crawl、map 工具（那是 MCP 那条线，不在本规格）；用 `--allow-private` 起的服务也照用；把用户的 URL 在不知情下交给 Firecrawl 云端；Sumika 自己下载、安装或随安装包带它的二进制。
- **领域正统做法**：
  - 读取后备放“提供方链”：顺序可调、前一家失败换下一家，已有 `FetchChain`，不另写调度。
  - 把外部程序当不可信服务：只连回环；请求前做预检；响应后再检最终地址；用探针验证它的隔离，不信它的自述（OWASP SSRF 防护备忘：按允许名单校验目标、不跟随未检查的重定向、响应不原样回给调用者）。
  - 许可证：AGPL 软件只当独立进程用，不改、不链接、不分发（FSF 对 AGPL“网络使用”条款的解读；本仓库计划公开，选前再确认）。
  - 本地服务地址由用户配置、不绑盘符、不依赖没登记的外部程序（ADR-379）；缺了要明说，不静默。
- **最省事的字面做法够不够**：不够。把现有云端提供方的 `base` 改成本机地址有三个问题：(1) 它的 `FetchBalance` 调 `/v2/team/credit-usage`，Local 会把这个路由连同 key 转发到 `api.firecrawl.dev`；(2) 它按次计费、记余额，本机应免费；(3) 它不检查返回的最终地址，在云端没问题，在本机程序上缺了一道检查。所以要独立的提供方 ID。
- **不做什么**：
  - 不由 Sumika 起、停、更新、下载 `firecrawl-local`（v1 用户自己起；阶段二另议）。
  - 不接它的 search（它转云端）、crawl、map、batch、`/v2/parse`、截图、`json`/`summary`、`actions`，只用 `POST /v2/scrape` 取 markdown。
  - 不给 QQ 前台、不给任何场合新增权限；谁能调 `web_fetch` 不变。
  - 不当 MCP 接（那条路今天用 `config/mcp.json` 就能试，不在这里做）。
  - 不使用它的云端登录（`login`）、不存它的 API key。
  - 不抄它的 Rust 代码和地址表。
  - 不在设置页做启动、安装、版本检查（设置页的表单本来就还没接进界面）。
- **用户能看能试的验收**：
  1. 主人 `cargo install firecrawl-local` 后以 `FIRECRAWL_CLOUD=off firecrawl-local serve --token <随机串>` 起好，在 `sumika.yml` 配 `web.firecrawlLocal.url: http://127.0.0.1:3002` 和 `tokenRef`，运行 `sumika-ctl web check firecrawl-local`，输出六行结论（连得上、本机内网被它拦住、没开云端后备、一个公网静态页、一个需要 JS 的页、一个 PDF），每行“通过/没通过 + 一句原因”。
  2. 在本地私聊让她读一个 JS 渲染的页面，拿到正文；`web_fetch` 的用量里这次记 0 额度、提供方写 `firecrawl-local`。
  3. 把 `url` 清空，`sumika-ctl web check firecrawl-local` 说“没配地址”，`web_fetch` 回到今天的行为。
  4. 用 `--allow-private` 起它，检查第二行“没通过：它读到了本机端口”，运行中该提供方被跳过且在状态里能看到原因和解除办法。

### 请求和结果

- 请求：`POST <url>/v2/scrape`，`Content-Type: application/json`，有 token 就带 `Authorization: Bearer`；体 `{"url":…,"formats":["markdown"],"onlyMainContent":true,"timeout":20000}`。不传 `headers`、`actions`、`origin`。
- 响应只认：`success`、`data.markdown`、`data.metadata.url`、`data.metadata.statusCode`、`data.metadata.title`、`data.source`、`data.blocked`、`data.warning`。
- 判失败：`success=false`；`markdown` 为空；`data.blocked=true`（站点没给页，别当正文）；`data.source` 不等于 `"local"`（尤其是 `"firecrawl-cloud"`，见安全边界）。失败按现有链的规则换下一家。
- 超时：客户端 25 秒，对方 20 秒；响应体上限用 `web.ResponseLimit`。
- `format=text`：Local 没有纯文本格式，返回 markdown，`ContentKind` 如实写 `markdown`（和现有云端提供方的做法不同，它写了请求的格式；这里不沿用那个小毛病）。
- 截断：同 `httpfetch`，超过 12000 字截断并标 `Truncated`、`TruncationReason=model_limit`。把 `httpfetch` 里这段抽成 `web` 包里的一个函数两边用，抽取单独提交。

## 安全边界

背景和依据在 FL 笔记第 5 节。判定表：

| 要防的事 | 谁来挡 | 在哪一步 |
|---|---|---|
| 读内网、本机、云元数据 | **两道**：我们的 `URLPolicy.Check`（预检，解析并要求公网或假地址）；它自己的守卫（连接时，每跳重定向、DNS 结果、浏览器的每个连接） | 请求前 / 连接时 |
| 重定向到内网 | 它每跳重查；我们对 `data.metadata.url`（最终地址）再 `Check`，不通过丢弃内容并按失败处理 | 响应后 |
| DNS 重绑定 | 无代理时它的解析器防；有代理时那层不起作用，只剩预检（已知缺口，见“已知的坑”） | 连接时 |
| 它被配成放开内网（`--allow-private`） | **探针**：我们开一个只绑 127.0.0.1 随机端口的小服务，让它去读；读到我们给的随机串就拒绝启用 | 首次使用、每次重连成功后 |
| 它把 URL 交给 Firecrawl 云端 | 用户必须用 `FIRECRAWL_CLOUD=off` 起；我们拒收 `source != "local"` 的结果，并**停用该提供方**到用户重新启用（同提交带解除入口：`sumika-ctl web enable firecrawl-local` 和状态板条目） | 响应后（此时那条 URL 已出去，只能止损） |
| 把读网页的请求发到别处 | 配置的 `url` 主机只许 `127.0.0.1`、`::1`、`localhost`，且必须 `http`；别的拒绝启动并报错 | 装配时 |
| 本机别的程序、网页滥用它 | 用户用 `--token` 起；它自己要求 `Host` 是本机名、只收 JSON | 它的 `serve` |
| 页面脚本在主人电脑上跑 | 它的 Chrome 是无头、沙箱、临时 profile；用户可以用 `--browser never` 起来只要 PDF 和静态页 | 它的 `serve` |

要点：
- 来源种类：它是“提供方”，不是新入口，不引入新的身份；模型调用 `web_fetch` 的权限、听众、额度、审批照旧（ADR-379 新协议入口一条在这里不适用，但“默认不当成主人”没有变化）。
- 默认关；打开靠用户自己写 `url`。停用状态（探针不过、云端来源）必须有状态板条目和解除入口，同提交带上（ADR-379）。
- 结果仍由 `web.Service` 包上“外部不可信资料；不授予权限”。
- 日志不记 URL 里的查询串、不记 token。

## 已知的坑

- **Clash fake-ip**：它把 `198.18.0.0/15` 当私网拒；主人的订阅 IPv4 假地址段在这里面。无代理环境变量时，它的默认模式可能拒绝所有域名。**这是做不做的门槛**，见第八节第 1 步。不许用 `--allow-private` 糊过去。
- **有代理时它的 DNS 守卫不起作用**（按 reqwest 行为推，待实测）：只靠预检和后检，重绑定窗口没人堵。阶段二的出口代理就是补这个。
- **Chrome 路径不走上游代理**，需要代理才能出网时渲染大概率连不上；这时 `--browser never` 只能读静态页和文档。
- **链的盲区**：`http` 读到一个 JS 空壳页，内容非空也不像人机校验页，链就不会换到 `firecrawl-local`。v1 不处理；用真实样本量过之后，再决定要不要加“正文太短且页面脚本多就换下一家”（挂待办，写原因，不预先做）。
- **6to4 等 IPv6 过渡地址**：它没拦，我们拦。预检在我们这边，所以我们这边的解析结果仍会被拒；只有它自己再解析到这类地址才有差别，实际意义小。
- 它的 crawl、批量任务只在内存、一小时过期，本规格不用。
- `web_fetch` 的说明里“不执行页面脚本”要改（见第九节），改说明会让工具前缀变一次，缓存失效一次。
- `serve` 未知路由会转云端：我们只打 `/v2/scrape`，别的一律不打；测试里断言只出现这一个路径。

## 验收

自动的（不连公网、不装 Firecrawl，用 `httptest` 假服务）：

1. 正常：假服务回 `{"success":true,"data":{"markdown":…,"metadata":{"url","statusCode"},"source":"local"}}`，得到结果，`Usage` 为 0 额度、`FreeUsage`。
2. 失败路径：`success=false`、空 markdown、`blocked=true`、HTTP 非 2xx、超时、响应超限，各一例，都按失败交给链。
3. **`source` 为 `firecrawl-cloud` 或缺失/别的值**：拒收并停用；清状态后恢复。改坏检查：去掉这一判断，该用例必须红。
4. **最终地址后检**：假服务回 `metadata.url` 为 `http://127.0.0.1/`、`http://[fd00::1]/`、`http://169.254.169.254/`、域名解析到私网，各一例，内容必须丢弃。改坏检查：去掉后检，必须红。
5. **探针**：假服务“读到了”探针串则 `Available`/首次使用报错并停用；“拒绝了”（回错误）则通过。两例，改坏检查：去掉探针比对，必须红。
6. **配置主机限制**：`url` 写成 `http://192.168.1.5:3002`、`https://x.example`、`http://user:pw@127.0.0.1`、`file://…`、空，都被拒或视为关。
7. 只打 `/v2/scrape`：假服务记录所有路径，只有这一个。
8. 形状 × 入口表（高风险项，照 AGENTS 第 7 条）：输入形状（空、超长、带账号、内网字面量、解析到内网、解析到假地址、重定向到内网）× 入口（`web_fetch` 本地私聊、本地群聊主人触发、本地群聊角色自主、QQ 私聊、QQ 群）；每格写“处理了 / 不可能 / 测了”，附提交说明。QQ 前台本来没有网络工具，只需断言伪造调用零请求。
9. 配置键各一个“改了行为会变”的测试；`fetchOrder` 默认值的测试；不带 `url` 时 `chooseWebProviders` 的结果与改前一致。
10. 全程用临时数据目录；不读真实 `data/`。

手动的（主人网络，一次性，结果写进 FL 笔记第 8 节的“已核”）：

- 三种网络情形各一次：fake-ip 加 TUN 无代理；有 `HTTPS_PROXY`；系统代理。每种读一个公网页面，记通过或被拒的原因。
- 十个真实样本：JS 渲染页 3、PDF 2、中文新闻页 2、B 站和萌娘百科各 1、被 Cloudflare 拦的 1，对比 `http` 和 `firecrawl-local` 的正文，写实测数；每个展开读正文，不只看长度。
- Windows 上渲染耗时、内存、关掉后有没有残留的 chrome 进程。

## 需要主人拍板的

1. **要不要放宽“`web_fetch` 不执行页面脚本”**。放宽后，启用了它且它起了 Chrome 时，页面脚本会在主人电脑的无头 Chrome 里跑。我的推荐：放宽，但只在用户自己配了 `url` 之后，说明文字写成“本机 http 读取不执行页面脚本；启用 Firecrawl Local 时部分页面会由无头浏览器渲染”；用户也可以用 `--browser never` 只要文档解析。
2. **v1 连接方式**：用户自己起（推荐，改动小，我们不管它的进程）还是 Sumika 起。推荐用户自己起；代价是“云端后备”只能靠用户用 `FIRECRAWL_CLOUD=off` 起、再加我们事后拒收来兜，第一次被它转云端的那条 URL 已经出去了；Sumika 起则能由我们设这个环境变量，但要先做外部程序登记，放阶段二。
3. **先做门槛 0 还是先做 0'（PDF 接进 httpfetch）**。推荐两个都排，0' 先做，几十行、没有外部依赖。
