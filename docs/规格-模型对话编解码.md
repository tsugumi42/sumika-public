## 开工卡

- **我理解成**：内核（`internal/turn`）只说“中立的对话”：消息、内容块（文字、图片、思考、工具调用、工具结果）、工具声明、请求选项。把它变成 HTTP 请求体字节、把流式回复变回中立结果，这两件事收进一个“OpenAI 聊天”编解码器。这一步是纯搬家：**搬家前后发给模型的请求体逐字节相同**；内核里不再出现 OpenAI 聊天格式的字段名。
  - 正例：前台一轮带工具调用和思考回放的请求，搬家前后假网关收到的 body 的 sha256 相同；`internal/turn` 的非测试代码里搜不到 `"tool_call_id"`、`reasoning_content` 这些字面量。
  - 反例：
    - 把消息过一遍 `map[string]any` 再 `json.Marshal`，键序变了，缓存前缀全断；
    - 只比解析后的对象，看不出空白和键序的变化；
    - 顺手把两种转义风格统一，后台请求字节悄悄变了；
    - 在中立类型里继续存 `ThinkingField: "reasoning_content"` 这种线上字段名。
- **领域正统做法**（盘点第 8 条，都读的源码）：
  - pi-mono：`packages/ai/src/types.ts:64-76` 是协议枚举，`:430-465` 是中立内容块（思考带不透明的 `thinkingSignature`）；`api/openai-completions.ts` 的 `buildParams` / `convertMessages` 是编解码器；服务商在 `providers/*.ts`，是数据。
  - litellm：`types/utils.py` 的统一 `Message`，每家服务商一个 `transform_request`。
  - codex：`model-provider-info/src/lib.rs` 的 `enum WireApi`，服务商是配置数据。
  - 共同点：中立消息加内容块；一个协议一个编解码器；服务商差异是数据；内核不碰线上字段名。我们照这个做。
- **最省事的字面做法够不够**：把 `messagesJSON` 原样剪到别的包、类型不动，字节是一样的，但内核仍然在填 `MessagesJSON` 字符串、`Msg` 里仍存线上字段名。P2-7 一接第二家就得回头改内核，不够。只定义中立类型而不补字节对拍，又挡不住搬家时的字节漂移（坑 1～4），也不够。
- **不做什么**：
  - 不做服务商配置、预设、`compat` 开关、直连别家（P2-7）。`规格-模型配置` 第 3.1 节的 `Source.Dialect` 那段由 P2-7 改，这一步只在那里加一句“编解码器见本规格”。
  - 不收三份重试和切换循环（P5-3）。
  - 不动 embeddings、rerank、链接读取、免费接口那些另一种线上格式（盘点第 3 条）。
  - 不改 `llm.Client` 的看门狗和空闲超时，那是传输层（坑 11）。
  - 不统一两种转义风格（坑 5）。
- **用户能看能试的验收**：没有界面变化。验收靠字节对拍和 archcheck：见“验收”第 1、3 条。

## 设计

### 1. 先补整份请求体的逐字节对拍（第 1 步，只加测试）

现有对拍比的是解析后的对象，还删掉了系统提示和工具描述（盘点第 4 条），钉不住键序、空白、转义。

- 新加一组“线上字节”对拍：用固定的假网关回复加注入时钟，经真实的组装路径发出请求，取假网关收到的**原始 body 字节**（`llmtest.Handler` 的 `bodies`），整份存成 `testdata/wire/<场景>.body`，原样字节、不格式化。比对时逐字节比，不一样就打出第一处不同的位置和前后 80 个字节。
- 重录用环境变量 `WIRE_UPDATE=1`。重录前要先在 `testdata/wire/intended.md` 登记原因，照 turn 的 `INTENDED` 惯例；没登记的场景变了，测试红。
- 至少这些场景（坑 1）：
  1. 纯文字一轮；
  2. 调工具一轮（工具调用加工具结果）；
  3. 工具结果带图（另起一条 user 消息）；
  4. 思考回放：`reasoning_content` 一份，`reasoning_details` 一份；
  5. assistant 空正文写 `null`；
  6. 没闭合的调用补 `No result provided`；
  7. 停掉的那条不发；
  8. 子任务；
  9. 压缩；
  10. 后台 `memoryGenerator`（`[]llm.Message` 那条路径，`marshalNoEscape`）；
  11. 顾问审阅；
  12. 故障切换后剥掉思考的那份（`StripModelReasoning`）。
- 同时保留现有的“消息逐条字节”前缀契约测试（`prefix_contract_test.go`），不拿新对拍替代它。

### 2. 中立类型（第 2 步）

新包 `internal/llm/chat`，只放类型，不依赖 `llm`。按现有字段一一对应，不另加抽象（盘点第 6 条）：

- `Message{Role, Blocks}`：`Role` 只有 `system`、`user`、`assistant`、`tool`。
- `Block` 有五种：
  - `Text`；
  - `Image`（照 `llm.Image` 的字段）；
  - `Thinking{Text, Replay}`；
  - `ToolCall{ID, Name, Arguments jsjson.Value}`；
  - `ToolResult{CallID, Text, IsError, Images}`。
- **思考回放是不透明数据**：`Replay` 存编解码器自己认的字节，加上出处（哪个编解码器、哪个模型），内核只负责存和带回，不看里面（坑 7）。
  - 现在 `turn.Msg.ThinkingField`（值就是线上字段名）和 `ReasoningDetails`（原样 JSON），都收进 `Replay`。
  - 回放落库的格式要兼容旧行：旧库里存的 `ThinkingField` / `ReasoningDetails`，读出来能转成新的 `Replay`。
  - 这一条是落盘格式，要写测试：旧行照读，新旧两种都能回放出同样的字节。
- `Request{Model, System 的角色选择, Messages, Tools, MaxOutputTokens, Thinking, CacheKey, LongCache, NoStore, Headers}`。
  - 后面这几项开关今天就在 `llm.Request` 里，先照搬。它们该不该进中立请求，由 P2-7 的预设决定，这一步不动语义。
- 工具声明直接用 `tools.Declaration`，把 `tools.RequestJSON` 搬进编解码器。
- 中立结果 `Result{Blocks, Usage, StopReason, Replay, Route}`：`StopReason` 是中立枚举（stop / length / toolUse / error）。

### 3. OpenAI 聊天编解码器（第 2、3 步）

新包 `internal/llm/openaichat`：

- `Encode(chat.Request) ([]byte, error)`：
  - 把 `turn/loop.go:178-268` 的 `messagesJSON`、`tools.RequestJSON`、`llm.UserContent`、`llm/wire.go` 的 `chatBody` **原样**搬进来。只换输入类型，不改输出。
  - 字段顺序照今天手写的顺序；`jsjson.Quote`、`jsjson.Stringify` 原封不动（坑 4、7）。
  - 后台 `[]llm.Message` 那条路径今天用 `marshalNoEscape`，转义风格和前台不同。编码器保留这两种写法，用请求里的一个标记区分，**不统一**（坑 5）；统一留给以后，单独登记原因。
- **剥掉思考**（`StripModelReasoning`）改成在中立消息上删 `Thinking` 块，再编码，不再把字符串解析成 map 重排（坑 6）。
  - 这一处搬家后字节**会变**：今天这份是按字母重排过的，搬家后是正常顺序。这是有意的变化，在 `testdata/wire/intended.md` 登记，只影响故障切换后的那一次请求。切换模型本来就断前缀。
- `Decode`（第 3 步）：把 `llm/wire.go` 的 SSE 读取、`llm/llm.go` 里思考字段的识别、`reasoning_details` 的合并、工具调用增量拼接、用量、`finish_reason` 映射搬进来，产出 `chat.Result`。
  - 看门狗和空闲超时留在 `llm.Client`：编解码器只产出事件，不带计时器（坑 11）。
  - Magpie 的路由头（`x-magpie-provider` 等）和流内错误分类，这一步照原样留在 `llm` 包，P2-7 再移进预设。
- `llm.Client` 改成：拿 `chat.Request` → `openaichat.Encode` → 发 → `openaichat.Decode` → `chat.Result`。
- `turn` 的 `ModelCaller` 端口参数改成 `chat.Request`，`modelcall.Client` 跟着改。`PromptHashes` 改成对编码器产出的 messages、tools 片段算，保证和今天的指纹一样（坑 3）。

### 4. 内核不再出现线上字段名（第 4 步）

- archcheck 新加一条：`internal/turn`、`internal/kernel`、`internal/app` 的非测试 Go 文件里，不许出现这些字符串字面量：`"tool_call_id"`、`"tool_calls"`、`"reasoning_content"`、`"reasoning_details"`、`"reasoning_text"`、`"stream_options"`、`"max_completion_tokens"`、`"prompt_cache_key"`；也不许 import `internal/llm/openaichat`（内核只认 `chat`）。
  - `turn/compact.go` 里 `Role == "toolResult"` 这类内部同名，不在名单里（盘点第 2 条）。
- 做改坏检查：故意违规一次，规则要红；把判断改松再违规一次，确认规则不再红，证明它真的在查。

## 验收

1. **字节相同**：设计第 1 条的十二个场景，搬家前录的 `.body`，在第 2、3 步之后逐字节相同。唯一的例外是场景 12（剥思考），它的变化已登记在 `intended.md`。
2. **原有测试不改预期全过**：现有 turn 对拍（`testdata/cases`、`golden`）、前缀契约测试、`llm` 的录像回放（`replay_test.go`）、故障切换测试，预期一个字都不改，全部通过。要改预期的，先停下回报。
3. **内核干净**：设计第 4 条的 archcheck 通过，改坏检查的证据存进 `data/dev/review-p2-6/`。
4. **旧数据照读**：库里旧格式的思考回放（`ThinkingField`、`ReasoningDetails`）读出来，回放出的请求字节和改动前相同。拿一条编造的旧行测。
5. **真跑一次**：主会话在合并前，用本机 Magpie 发一轮最简单的本地私聊，看回复正常、trace 里用量和路由正常。这一条只是冒烟，不进自动测试。

## 禁止的偷懒写法

- 用 `map[string]any` 或结构体往返去拼 messages、tools。
- 为了让对拍通过去改 golden、改前缀契约测试的预期。
- 在中立类型里留线上字段名（`ThinkingField` 的值、`role:"developer"` 这种）。思考回放只能是不透明的 `Replay`。
- 把看门狗和超时搬进编解码器。
- 把后台和前台的转义风格顺手统一。

## 已知的坑（照盘点）

- 坑 1～3：字节对拍要比整份 body，`PromptHashes` 只管 messages 和 tools。
- 坑 4：messages、tools 不过结构体。
- 坑 5：两种转义并存。
- 坑 6：`StripModelReasoning` 会重排字节。
- 坑 7：思考回放改成不透明数据。
- 坑 8：解码分开验收。
- 坑 9：预设的顺序也是数据（P2-7）。
- 坑 11：计时器留在传输层。
- 坑 12：真实录像不做字节相等，只做解码回放。
