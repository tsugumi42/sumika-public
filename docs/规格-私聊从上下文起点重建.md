## 开工卡

- **我理解成**：本地私聊和主人的 QQ 私聊，实例被回收、程序重启以后再建，她看到的应该和“实例一直没断”时一样，也就是从这段对话的起点到现在的全部（有摘要就是摘要加切点之后的全部）。不再只带最近 30～59 条。
  - 正例：本地私聊聊了两百条，闲置一小时后回来，第一轮请求里能看到这两百条（或者摘要加切点后的全部）。
  - 反例：
    - 只把 `recentMessages` 调大；
    - 群聊也跟着改；
    - 重建时先裁再压，把最需要总结的前半段先丢了；
    - 每次闲置都无条件压缩花钱。
- **领域正统做法**：
  - pi-mono 按持久会话路径重放，有压缩时按压缩边界重建：`packages/coding-agent/src/core/session-manager.ts:479`、`core/compaction/compaction.ts`。
  - Codex 压缩后保留摘要加最近原文：`codex-rs/core/src/compact.rs`。
  - 共同点：会话的“起点”是持久的边界，压缩是边界前移；不按固定条数截断。
  - 我们的落法：起点由“这个会话最后一个新话题分隔”和“会话第一条”派生，不另建表。
- **最省事的字面做法够不够**：只调大 `recentMessages`，或者只在 `history.For` 里去掉锚定，都不够。
  - 重建时 `buildWith` 先裁到 `keepTokens` 再看压缩，起点一早就会被裁掉（坑 2）；
  - 主人 QQ 私聊根本不允许压缩（坑 4）；
  - “开始新话题”不写分隔，会把新话题前的全部历史带回来（坑 9）；
  - 参考块清理按旧窗口下限，会删掉起点之后的块（坑 10）。
- **不做什么**：
  - 不改 QQ 群、本地群聊、别人的 QQ 私聊（仍是锚定窗口，现有前缀契约测试一字不改）；
  - 不做“按说话人分实例”（P5-19）；
  - 不新建数据库表；
  - 不做手动压缩的界面入口（P5-18）；
  - 退出程序时不压缩（保持 `TestEarlyShutdown` 的语义：关闭时不提交摘要）；主人 2026-11-16 同意，ADR-388 修正 ADR-377 第 4 条；
  - 不做“开始新话题”的界面入口（主人 2026-11-16：默认不用关心刷新；`Hub.StartNewTopic` 留作以后“一件事一条工作线”用，接入口前要先修的两条挂在待办）。
- **用户能看能试的验收**：见“验收”第 1 条，以及运行页“重建”表里这两种场合的“丢了几条”变成 0。

## 设计

### 1. 只改两种场合

用一个明确的场合判断函数，测试钉住：
- **本地私聊**：主人在主窗口的私聊（`ownerConsoleAudience` 且不是群）。排除话题子会话（`:topic:`）、自检、悄悄话、子任务线程，这几种照旧。
- **主人 QQ 私聊**：`Channel == "qq"`、`Scene == "private"`、会话对端就是配置里的主人号、`PrivateOK` 为真。
- 其余一律照旧走锚定窗口。

### 2. 起点怎么定（派生，不建表）

- 起点 = 这个会话里最后一个“新话题分隔”（`context-break` 事件）之后的第一条算数消息；没有分隔，就是这个会话的第一条算数消息。
- 有成功的压缩快照，而且快照切点比起点新：用“摘要加切点之后的全部”，照现在 `history.For` 的有快照分支。
- **“开始新话题”要写分隔**：`RestartIn` 因为新话题触发时，写一条 `context-break` 事件（先查现有事件种类里这种事件的写法和谁在用）。检查点回退、渠道交回这两种 `RestartIn` 不写分隔，照旧。
- 按“角色 × 会话”取。前提是这两种场合的听众只有主人一个人、档只有一种。**这是要核实的断言**：第 1 步先列出这两种场合下，同一个会话能配出哪几种 `liveKey`（`Scope`、`PrivateOK`、听众渠道）。多于一种就停下回报，不许自己选（坑 11，可见性边界）。
- 参考块清理的下限（`history.WindowFloor`）要把起点算进去，不删起点之后的块（坑 10）。

### 3. 建实例的顺序：先压缩、再裁剪

对这两种场合，`buildWith` 改成：
1. 从起点（或快照切点）读出全部历史；
2. **建实例时不先裁**。原样建好以后，交给现有的 `fitHard` 在回复前处理：超过硬门槛，用活实例压缩；压缩不允许或失败，才裁到 `keepTokens`，留痕记 `over_limit_trimmed`，`dropped` 如实记。
3. 第一版不做“从库里拼材料的冷压缩”（坑 3）。理由：按第 6 条量到的数，从起点带上的历史离硬门槛差两个数量级。只有历史超过模型窗口本身时，活实例才压不了，那时 `fitHard` 的裁剪兜底会如实留痕。这个限制写进参考页和待办。

其余场合照旧：先裁再看压缩。

补上第一版漏写的一层：本地私聊本来就有后台提前压缩 `compactEarly`（`turn/hub.go:993`）——一轮结束后实例超过硬门槛的八成（本地私聊约 425K × 0.8 ≈ 340K token）就在后台写摘要，前台照常聊；失败记下当时的大小，长到 1.1 倍才重试。摘要一写好，下一轮因为 `EpochSeen` 对不上而换上，切点之后的消息原样接上。这和 Codex、Jcode 的做法一致（摘要好了就在下一个空当换上，见 `data/dev/research/调研-自动压缩各家-20261116.md`），保留，不改成“留着等”。

### 4. 主人 QQ 私聊允许压缩：挪出本规格（2026-11-16）

主人 2026-11-16 定“本地优先、QQ 排后”（ADR-388）。这一项改的是“谁能看到什么”，要单独做“形状 × 入口”表和复核，挪到以后单独一步，挂待办。第 1 步已经让主人 QQ 私聊从起点读，按第 6 条的数离硬门槛差两个数量级；真到了照裁剪兜底，留痕如实记。

### 5. 本地私聊：用户不用管的自动压缩（第 2 步，2026-11-16 改写）

目标：主人默认不用关心上下文什么时候刷新（ADR-388）。参考 `data/dev/research/调研-自动压缩各家-20261116.md`（Codex、Jcode、OpenCode、pi、Crush 读源码，Claude Code 仅文档）。

1. **空闲压缩**：独立的空闲计时，不挂在“下一次取实例时顺手回收”上。三条都满足才排：这个会话闲置满 `agent.idleCompact.after`（默认 50 分钟；Claude Code 约 54 分钟，赶在一小时缓存过期前）、实例 ≥ `agent.idleCompact.minTokens`（默认 200000，同 Claude Code；原来写的 80K 没有依据，作废）、没有在跑的压缩、也没有更新的快照；`agent.idleCompact.enabled` 默认开。做完写进 `context_epochs`（`trigger = idle`），下一条消息来时换上——缓存反正已经过期，换上不多花钱。
2. **失败**：写 `context_epochs` 失败行和 `model_runs`；同一会话 6 小时内不再试；起点不变，不丢东西。和 `compactEarly` 共用任务登记（`h.compactJobs`）和失败记录，同一份内容不付两次钱。
3. **并发**（照 Codex 的“捕获时记版本、换上时核验”，`compaction_replacement.rs:35`）：后台任务开始时记下起点、切点、旧快照 ID、模型、会话代次；写进库之前在锁里核对，变了（新话题、检查点回退、换模型）就丢掉不写；切点之后来的消息全部原样接上。
4. **界面**：正常压缩聊天里不提示，运行页重建留痕记一行；只有回复前必须同步等压缩、裁剪兜底真丢了内容这两种情况在聊天里提一行。
5. **退出**：不新开压缩请求，在跑的取消、不提交半截（Codex `async_compaction.rs:211`、pi `agent-session.ts:1479` 同样做法）。
6. **参数先量再定**：经 Magpie 的线路实际缓存能留多久没量过，“赶在过期前压”能省多少不保证。两个参数做成配置，每次触发记留痕，量一周再定默认值。主人现在一两万 token 的用量离 200K 很远，短期不会触发。

### 6. 没有分隔的老会话（2026-11-16 主会话只读量过）

- 没有任何分隔时，起点就是会话第一条。
- 真实数据（只出计数，不看正文）：
  - 本地私聊：铃花 124 条事件、约 5500 字；铃音 87 条、约 2400 字。从头带上也就一万 token 上下；
  - 主人 QQ 私聊：486 条算数消息、约 12000 字，粗估 14000 token；
  - 两种场合都没有一条 `context-break`；
  - 硬门槛约 425000（本地私聊）和 850000（主人 QQ 私聊）。
- 结论：从会话第一条带起，离硬门槛差两个数量级，不需要先打分隔，也不需要迁移。
- 以后会话变长，由现有的硬门槛压缩接手（第 3 条）。

### 6a. 新话题分隔现在没人写（主会话核过）

- Go 里没有任何生产代码写 `context-break` 事件，以前只有 Bun 写（`history.go:195` 注释写着来自 `api/event.ts`）。读的地方有三处：`history.For`、`history.go:284` 一带，以及 `turn/compact.go:246`。
- `Hub.RestartIn(characterID, conversation)` 不带原因，分不清是新话题、检查点回退还是渠道交回。
- 第 1 步要做两件事：
  - 列出 `RestartIn` 的所有调用方和各自的原因；
  - 给“新话题”单独一个入口（例如加一个原因参数，或者新加 `StartNewTopic`），由它写 `context-break` 通知事件（格式照 `IsContextBreak` 认的形状：kind 是 `notice`，`segments` 里 `notice` 是 `context-break`），再丢掉实例。另外两种照旧不写。
- 界面上“开始新话题”的按钮或命令在哪、现在调的是什么，也一并列出来。

### 7. 留痕口径

- 这两种场合正常情况下 `rebuild.dropped` 应为 0，有摘要时 `covered` 大于 0；只有裁剪兜底时才非 0。新话题之前的话是主人主动结束的，不算丢（`dropped` 只数最后一个分隔之后）。
- `sumika-ctl stats rebuild` 字段不改。

## 验收

1. **两百条加闲置一小时**：
   - 本地私聊放 200 条算数消息（假时钟，照 `prefix_report_test.go:92` 的写法），跑一轮，闲置 61 分钟，再跑一轮；
   - 第二轮请求里这 200 条都在；
   - 留痕原因是 `idle`、`dropped` 为 0。
   - 主人 QQ 私聊同样测一遍。
2. **前缀契约**：纯聊天（没有工具结果、参考块、插话）的本地私聊和主人 QQ 私聊，重建前后的请求在新的一句之前逐字节相同。带参考块的回合，比到第一块没持久化的内容之前（规格-提示词前缀稳定 7.5）。
3. **群聊不变**：`TestRebuildPrefixAnchored`、`TestPrefixRebuildEqualsReuse` 一字不改照过；再加一条测试断言 QQ 群和本地群聊的带上条数仍在 `[n, 2n)`。
4. **新话题**：开始新话题以后重建，只带分隔之后的；分隔写进了库。
5. **超过硬门槛**（用小窗口的假模型构造）：
   - 从起点读出来超过硬门槛 → 建实例时不裁，回复前 `fitHard` 压缩，用的是摘要加切点后全部；
   - 压缩失败（注入）→ 裁到 `keepTokens`，留痕 `over_limit_trimmed`，`dropped` 如实。
6. **空闲压缩**：闲置满时长、超过下限的才排；没满时长、不够大、已有更新快照的都不排；失败后 6 小时内不重试；和 `compactEarly` 不会对同一份内容各跑一次。
7. **并发和退出**：压缩期间来新消息（不丢）、开新话题、检查点回退、换模型（这三种都不写进库），程序关闭（取消、不提交，`TestEarlyShutdown` 照过），每种一条测试；正常压缩聊天里没有提示、运行页有留痕，同步等和裁剪丢内容各出一行。
8. **参考块清理**：起点之后、旧窗口下限之前的参考块，重建后还在。

## 禁止的偷懒写法

- 只调大 `recentMessages`。
- 给所有场合一起改。
- 为了让测试过去改群聊的前缀契约测试。
- 压缩失败就假装成功，或者用失败的摘要建实例。
- 退出时同步压缩，拖住关机。
