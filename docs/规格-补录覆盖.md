# 规格：QQ 补录覆盖判断

> 状态：2026-11-10 从 `native/internal/app/backfill.go`（及 `store/backfill_settle.go`、`snowluma/query.go`）反推写成，行为以 Go 现状为准；ADR-345 第 0 批的一部分。此前这些规则只在代码和 `backfill_*_test.go` 里，没有规格。
>
> 验收数据：[`testdata/shared/backfill/`](../testdata/shared/backfill/README.md)（32 个场景，Go 现行行为；Bun 冻结）。Go 的跑法在 `native/internal/app/shared_backfill_test.go`。
>
> 范围：自动补录一轮（`qqBackfill.round`）怎么扫、怎么判断"这段历史有没有补全"、怎么记缺口和水位。不含：手动补录请求（`backfill_manual_test.go`）、对齐任务队列（`backfill_tasks.go`）、媒体补扫（`backfill_media.go`）、在线定时器（见第七节"没进共用数据的"）。
>
> 为什么要写：补录判断写错不会报错，只会悄悄漏消息或悄悄把没补全的洞记成补全了（第二轮小样本报告里"最危险的一块"）。

## 一、名词

| 名词 | 含义 |
|---|---|
| 水位（检查位置） | 表 `qq_sync(account, through)`。只表示"处理到哪一刻"，**不是**"这之前的消息都齐了"。 |
| 缺口 | 表 `channel_gaps`，一行一个会话里的时间区间 `[from_ms, to_ms]`，带状态和原因。 |
| 缺口状态 | `open`（等着自动再补）、`blocked`（已扫过一次但没法证明补全，自动不再复查，只接受手动请求）、`filled`（已证明补全）、`abandoned`（放弃）。 |
| 自动缺口 | `acknowledged_ms = 0` 且（`open`，或 `blocked` 且 `last_try_ms = 0`，即升级恢复出来还没扫过的）。只有自动缺口参与每轮结算。 |
| 缺口原因 | `page-cap`（翻满页数没到起点）、`call-failed`（查询出错）、`budget`（本轮查询预算用完没轮到）、`stalled`（锚点不动或没有新消息）、`no-anchor`（首页就没有可用消息）、`broken-page`（页对不上锚点或重复号时间/序号不一致）、`unsupported`（协议端没有历史能力）、`unverified-history`（页都拿到了，但没有证据证明中间没漏）、`outage`（断线登记的空档）。 |
| 连续证明 | 表 `qq_backfill_continuity(account, conversation, from_ms, through_ms)`：这个会话从 `from_ms` 到 `through_ms` 已证明连续。 |
| 起点 `start` | 一轮要补到的最早时刻：`水位 - 60 秒`（重叠一分钟）。 |
| 页 | 一次历史查询（`HistoryPage`）的回包：消息列表 + `Latest`（这页是不是最新的、没有回退到缓存）+ `Continuous`（协议端保证页内无遗漏）。 |

## 二、一轮怎么走

`round()`，由连上后 30 秒防抖的第一轮、之后到期的缺口、重连触发。

1. `started` = 现在；`checked` = 水位（没有记录就取库里最早的 QQ 事件时间，再没有就取 `started`）；`start = checked - 60s`。
2. 选目标会话（`targets`），按这个顺序、去重：
   1. 主人私聊（配了主人才有）；
   2. 到期的自动缺口所在的会话，`budget` 原因的排在前面（上一轮预算没轮到的先补）；到期 = 距上次尝试至少 10 分钟；
   3. 有活动记录的私聊，前 30 个正常补，**第 31 个起不查询，直接记 `budget`**；
   4. 有活动记录的群；
   5. 配置里的群。
   只补"允许"的会话：私聊只限本号自己的私聊；群只限配置里 `qq.groups` 且开着群补录的。
3. 对每个目标，算这一轮要补的起点 `from`：
   - 默认 `start`；
   - 该会话有**非自动**的、没填平的缺口（受阻或放弃的旧洞）并且它的区间包住 `from`，就把 `from` 推到那个缺口的 `to_ms + 1`（旧洞只接受手动请求，自动不重翻）；
   - 该会话有**到期的自动缺口**，`from = min(from, 缺口.from_ms)`（把旧洞也纳入这一轮）；
   - 如果 `from > started`（整个窗口都在已放弃的旧洞里），**这个会话本轮不查询**，不记缺口。
4. 扫描并判断覆盖（第三、四节），得到 `coverage`。
5. 结算已有的自动缺口和登记新缺口（第五节）。
6. 所有目标都处理完后一次提交（`SettleQQBackfill`）：缺口、连续证明和水位同一个事务。**任何一步被取消或出错，整轮什么都不结算，水位不动**；已经逐条入库的消息保留。

## 三、扫描一个会话（`conversation`）

页大小 100，最多 5 页。

- 协议端没有历史能力（`Caps.History` 假）：不查询，原因 `unsupported`。
- **群**：首页不带锚点（取最新）。之后每页的锚点 = 到目前为止**最旧**（时间最早）的那条的平台消息号。后页必须**包含**上一页给的锚点（协议端通常把它放在首条，所以实际上每页第一条是上一页的锚点，只有"含不含"被检查，不检查位置），因此 5 页最多新增 `100 + 4×99 = 496` 条，不是 500。
- **私聊**：只查一页，不带锚点（私聊里两个发送者的序号不能混用，翻页没有证据意义）。
- 每页：
  - 查询出错：本页拿到的消息照收；原因 `call-failed`（预算耗尽的错误记 `budget`）；停止翻页。
  - 后页（带锚点的）必须**包含锚点**（`joined`），重复出现的平台消息号必须**时间和序号都和之前一致**（`consistent`），否则原因 `broken-page`，停止（手动补录不停，这里不涉及）。
  - 本页没有任何新消息（全是见过的），或本页没有可作下一个锚点的消息：原因 `stalled`；如果这是首页，原因 `no-anchor`；停止。
  - 同一秒的消息可以继续换锚点；只回了更新的消息不能把锚点往后挪（锚点只取不比当前最旧更新的消息里最旧的一条）。
  - 本页最旧时间 ≤ `start`：到起点了，原因清空，停止。
  - 翻满 5 页还没到起点：原因 `page-cap`。
- **入库**：只收时间 ≥ `start` 的消息，按时间从早到晚逐条提交（`Backfill: true`）。已有的（同一会话、同一平台消息号）算重复，不再写；自己发的（`self`）也照收。入库里有被拒收的消息（`Dropped`）整轮失败。

## 四、覆盖证据（这是最容易写错的地方）

扫完以后只有满足下面两条之一，才算**证明了** `[oldest, newest]` 之间没有遗漏（`covered`）：

```
covered = pagesOK && ( (latest && continuous) || (seqOK && 序号数>1 && 最大序号-最小序号 == 序号数-1) )
```

- `pagesOK`：所有页都没出错、都 `joined` 且 `consistent`，并且首页至少有一条可用消息作锚点。**后页出错、坏页会让前面页得到的结论一起作废**（不能沿用首页的证据）。
- `latest`：只看首页（不带手动锚点时）的 `Latest`，表示这是协议端最新的、没有退回缓存；`continuous`：任何一页为假就整体为假。**适配器 `snowluma` 目前的 `Continuous` 恒为假**（协议没有页内无遗漏保证，见 `query.go` 的注释），所以现实中 `latest && continuous` 不会成立，覆盖证据只来自序号。
- `seqOK`（只对群）：每条消息的协议序号 `MessageSeq > 0` 且互不相同。有 0、有重复就失效。序号连续指：收到的不同序号数 = 最大 - 最小 + 1，且至少 2 个。
- **私聊没有序号这条路**（`seenSeq` 不收集，因为私聊里两个发送者的序号不能混用）。私聊要有证据只能走 `latest && continuous`；`Latest` 为真但 `Continuous` 为假不行（场景 `private-latest-without-in-page-proof`），两个都真才行（场景 `private-latest-continuous-fills-gap`）。**现实里当前适配器的 `Continuous` 恒假，所以私聊实际上永远拿不到证据**，这条规则只是 Go 代码允许、测试覆盖的路径。

证明的区间：

- `coveredFrom = oldest`（扫到的最旧时间），`coveredTo = newest`（首页里最新一条的时间）；若 `latest`，`coveredTo = end`（本轮开始时刻）。
- 证据**只覆盖收到的两头之间**：最新一条到 `end` 之间的"尾巴"证明不了。所以 `covered` 且非 `latest` 时，只要 `coveredFrom > start` 或 `coveredTo < end`，原因记 `unverified-history`，窗口取 `[start, end]` 整段（之后用已证明的部分扣掉，见下节）。
- **不 covered**：窗口取 `[start, end]` 整段，原因没有就记 `unverified-history`。首尾时间和锚点只说明扫到哪里，**不能**从待补区间里扣掉任何中段。
- **covered 会把 `page-cap` 盖掉**：证据成立且（非最新）时，原因被改写成 `unverified-history` 或清空，由上一条决定；不会同时留一个 `page-cap`。

## 五、结算：缺口怎么变

对本轮这个会话已有的每个**自动缺口** `g`：

- 填平：`covered` 且 `from ≤ g.from` 且 `coveredFrom ≤ g.from` 且 `coveredTo ≥ g.to` → `filled`。**必须两端都被证明覆盖。**
- 否则如果到期（距 `g.last_try` ≥ 10 分钟）：状态 `blocked`，原因 = 本次原因，`tries + 1`；但原因是 `budget` 时状态保持 `open`，不加次数。
- 否则不动。
- 动过的缺口 `last_try = started`。

登记新缺口（本次原因非空时）：

1. 待登记区间默认 `[coverage.from, coverage.to]`；如果是最新或没证明，`from` 不早于 `start`（老缺口已经单独保存，到页数上限不能把"老缺口和新窗口之间整天"再记成一个洞）。
2. 如果 `covered`：把已证明的 `[coveredFrom, coveredTo]` 扣掉，剩左边 `[from, min(to, coveredFrom)]` 和右边 `[max(from, coveredTo), to]` 两段。
3. 再扣掉该会话里已有的**非自动**、没填平的缺口（受阻或放弃的旧段保留原行，新窗口只登记还没记录的部分）。
4. 剩下的每一段登记成缺口：状态 `blocked`（原因 `budget` 时 `open`），`last_try = started`。相邻的 `open` 缺口登记时会被合并。

结果是：已放弃的旧缺口不会被新尾段复活；放弃区间里"新增的尾巴"另外单独记洞。

## 六、水位和连续证明

- **水位**：一轮顺利走完（包括记了缺口）→ `max(原水位, started)`。**缺口登记成功就推进水位**，因为洞已经持久记下来了，不会因水位前进而丢；没登记缺口的失败（取消、出错）不推进。
- 实时消息入库**不**动水位。
- 在线空闲时（第一轮完成之后，不在抖动期）每分钟把水位推到 `现在 - 60 秒`；第一轮补完重连空档之前，**绝不推进水位**（否则几秒的洞会被永久跳过）。（这一条靠定时器，没进共用数据，见第七节。）
- **连续证明**（每个会话一行）：初始 `[from, from-1]`（空）。若本会话有 `open/blocked/abandoned` 缺口且最早的 `from` 比证明的起点还早，证明重置为 `[该 from, 该 from - 1]`（旧证明不覆盖新起点，不能拼成连续）。`covered` 且证明的区间和已有证明相接（`coveredFrom ≤ through+1` 且 `coveredTo ≥ from`）→ `through = max(through, coveredTo)`。最后 `through` 不超过最早未解决缺口的 `from - 1`。
- **完整覆盖**（给界面的 `complete_coverage`）：允许的会话里没有 `open / blocked / abandoned` 缺口。

## 七、没进共用数据的

这些规则在 Go 里有测试，但没法用"输入页 + 期望结果"的形状表达，共用数据没覆盖，Bun 重写时要对着 Go 的测试单独验：

- 连接防抖（连上后 30 秒才开始，三次 connected 只起一轮，稳定前掉线不查）和在线水位每分钟推进（`TestBackfillDebounceWatermark`）；
- 一轮的查询预算（120 次/10 分钟，多个会话轮流，剩下的记 `budget` 下一轮优先）和并发的活跃会话排序（`TestBackfillRoundBudget`）；
- 取消的几个并发细节：已开始的入库在停止返回前必须收尾（`TestBackfillDisconnect/入库已开始`）；
- 手动补录、对齐任务、媒体补扫（`backfill_manual_test.go`、`backfill_alignment_test.go`、`backfill_tasks.go`）；
- 10000 条规模和多角色观察（`TestBackfillScale10000`）。

## 八、对 Bun 实现的提醒

- 平台消息号和序号都可能超过 2^53，一律按字符串存、按字符串比。
- `ago_ms` 这类相对时间换算在两边必须用同一个"现在"（场景里的时钟是固定的）。
- 缺口的合并、扣除区间是整数毫秒运算，边界是闭区间；常见的坑是 `to_ms + 1`、`from - 1`、`coveredTo` 和 `end` 的取值。
- 本文第四节"covered 且非 latest → unverified-history"最容易漏：漏了就会把没证明的尾巴当成补全。
