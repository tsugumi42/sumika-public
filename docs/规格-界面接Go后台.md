## 一、交付边界与技术路线

交付一个 Windows 原生桌面程序：右下角有托盘，能打开四栏主窗口，直接读取 Go 的历史和媒体；后台接收新消息时窗口会更新；关窗口后后台继续，明确退出后所有资源收好。界面第一阶段只读的限制**已放开（2026-11-03）**：主会话要求做成完整的软件，标已读、搜索等写操作已陆续接入，本次接通本地私聊文字、停止和人工审批；QQ 发送、耳语、配置编辑仍按各自规格。后台既有的 QQ 接收、试运行能力不因界面写入口解除发送钳制或开启记忆写入。

2026-11-04 K1 分支增加可选 `api.LocalInputs`：`SubmitLocal` 返回持久输入回执，`StopLocalRun` 按 RunID/ThroughSequence 停止，`WatchLocalRun` 订阅累计正文、Revision、Outcome 和 Drained。宿主绑定可信本地身份；旧文字流共用同一 Hub。此步只增加宿主接口，未改窗口组件或启动真实 QQ；工具/插件活动整合及最终验收见内核补强 5.3（私有存档）。

### 1.1 一个程序、一套装配

- 正式桌面入口继续位于 `native/` 根 main 包，发行名暂定 `sumika.exe`。mygo 事件循环在 main goroutine；后台在工作 goroutine。一个 exe 内持有一个 Hub、一组 `store.Set`、一个生命周期宿主和一个托盘。不派生第二个后台 exe，不开 HTTP 或 WebSocket 服务端口。
- `native/cmd/sumika-go` 保留为已有无界面诊断/试运行入口，与桌面入口复用 `internal/app`，不能同时占用同一数据组。它不是桌面启动时拉起的子进程；本规格不要求删除独立诊断工具。
- 接口契约放在 `native/internal/api`：只含 DTO、读接口、可选写接口和订阅契约，不 import mygo、CrychicUI、m3e、`internal/app` 或 `database/sql`。`internal/app` 装配实现并交出接口；只有 main 的装配代码认识 app 实现，`data.go`、视图、图片加载器只依赖 api。测试从构造入口注入假实现，不再用全局 `base/live` 决定生产逻辑。
- 渲染仍用当前 CrychicUI 和已完成的消息壳、小黄脸、动图管线。m3e 后续替换组件 import 和调用，不改变 api 契约。此处不增加第二套组件包装框架。
- 正式桌面默认读 Go 数据；模拟模式必须显式选择，标题标“演示数据”。生产数据失败显示错误，不回落 mock。切换完成后移除原型的 7720 客户端、`SUMIKA_URL`、live 分派和 3 秒消息轮询；相关测试迁移到接口注入，不保留旧 HTTP 兼容通道。7720 只用于交接前冲突探测。

### 1.2 必须改造的装配边界

改造前的读码事实（旧版 `internal/app/app.go:117`）：`Open` 先挑 QQ 账号、取令牌，再抢数据锁和检查导入，随后拉模型目录；`Run` 假定存在 QQ 适配器。第 1 步已拆分为下表的两种模式；UI 接线仍在第 4 步，不在 ready 回调中同步装配。

第 1 步已实现两种模式的启动和生命周期边界；下表的角色显示资料、媒体、api 查询与托盘接线仍按后续步骤实施，桌面默认值按 ADR-209：

| 模式 | 启动内容 | 不满足前提时 |
|---|---|---|
| `archive`（建议默认） | 路径、数据锁、已有 Go 库的只读连接、角色显示资料、媒体读取、api 和托盘；不建 Hub、不读 QQ 令牌、不查 Magpie | 库不存在、配置不可读等分别报错；ADR-308 起不检查导入状态；不调用会自动建库的 `store.OpenGo` 伪装成空历史 |
| `receive`（显式选择一个 `-account`） | 同一宿主先过交接检查，再按现有 app 装配收 QQ；沿用当前单小号范围、私聊只入库、群试运行、发送钳制和记忆只读 | QQ/模型初始化失败显示原错误，不静默变成 archive 并宣称后台正常；允许用户明确重新选择“只看历史” |

拟定启动参数 `-data <目录>`、`-root <资源根>`、`-mode archive|receive`、`-account <账号>`。`receive` 未给账号时报参数错误，不自动选配置里的第一个号，不连接全部账号。已有 CLI 调用方显式选择 receive，保持当前行为。默认是否改成接收指定小号见第十一节，未决定按 archive。

数据目录和配置来源继续复用 `config.LoadIn/FileIn/DataDirIn` 的规则。桌面找根已按 ADR-248 改为 `-root` → exe 旁 `sumika.root` → 从 exe 目录往上找 `sumika.example.yml` → exe 目录；文件格式、拒绝回退和形状验收见[运行时参考](subsystems/runtime.md#go-桌面根目录与数据位置adr-248)。状态页和设置 → 数据显示当前根及来源，设置可异步原子改写 portable 文件、重启生效，演示不提供写入。参考 Telegram Desktop 的 exe 旁便携标记和现有桌面设置的临时文件改名结构，相关调研见[业界对照](notes/业界对照-我们的决定.md)第五节。无界面诊断入口（`cmd/sumika-go`）仍从当前目录往上找有 `sumika.example.yml` 的目录。桌面不依赖 cwd；带空格、中文、`# % ? &` 的目录都应可用（Windows 禁止字面 `?`）。首次安装选择便携还是 AppData 留待 ADR-248 第 4 条的初始化流程，本次不搬迁数据。

archive 的“只读”包括查询不写 `qq_read`、不刷新 blob 使用时间、不跑清理、不触发 `memory.Open` 的派生索引写入；可再生缩略缓存允许写入 Go 自己的缓存目录，但不改源媒体和业务库。receive 的库写入仍由既有后台服务负责。

## 二、原型现在从 7720 取了什么

下表按实际 Go 客户端列出 7 个路由形状；`poll.go` 复用消息路由，不是第 8 个接口。字段是客户端解码/显示所需，不能把 Bun 返回的其它字段都当成现有 UI 已接。

| 接口及调用源码 | 当前需要的响应字段 | Go 接手位置 |
|---|---|---|
| `GET /api/state`；`native/data.go:187` | `characters[]` 的 `id/name/color/status` | 角色显示快照与运行状态；不为取角色列表去连模型网关 |
| `GET /api/qq/conversations`；`data.go:195` | 每项 `conversation/kind/title/last/unread`；`last` 是下述 event | Go QQ 会话查询；补上实际观察角色集合供筛选和头像使用 |
| `GET /api/characters/:id/messages?limit=&before=`；`data.go:202` | event 数组；现在不给 `conversation`，只取该角色日常私聊 | local 库按真实 `console:<角色>` 查；话题使用 local_topics 的真实会话身份 |
| `GET /api/qq/messages?conversation=&limit=&before=`；`data.go:212` | `kind/title/events/people`，people 为 actor ID → `name/role` | QQ 页查询和人物显示投影；不在查询中刷新远程卡片/转发 |
| `GET /api/qq/faces`；`native/faces.go:303` | ID → `name/kind/char?` | 本机已有小黄脸资源的只读读取 |
| `GET /api/qq/face/:id`；`faces.go:312` | PNG 字节；ID 限 1～6 位十进制数字 | 同上按编号取 PNG，不拼任意文件路径 |
| `GET /api/blobs/:hash?w=<档>`；`native/images.go:330` | 媒体字节，可能是原格式，不能假定 WebP；动图不带 w 取原文件 | 按平台和媒体凭据取本地字节，复用解码与缓存 |

共同 event 字段（`data.go:58`）：`seq/id/channel/conversation/actor_kind/actor_id/kind/text/segments_json/created_at/origin/reply_to`。旧段（`data.go:98`）为 `type/text/hash/sticker/summary/width/height/skipped/id/name/qq/kind/super/animated/market/hidden{type,offset,size}`；旧 envelope 有 `segs/unsent/aborted/partial/notice`。

现状缺口：

1. 本地会话列表没有最后一句接口，`ui.go:80` 的 live 分支返回空事件；`data.go:242` 的本地群聊 live 分支返回 nil。`home:cabin` 等只来自 mock，不是库中的正式会话 ID。
2. `poll.go:11` 每 3 秒只取当前会话最新 20 条，第一页 200 条；短时间超过 20 条会漏中间的，旧行变更也不能靠“只加新 ID”更新。
3. `settings.go:95` 起全部来自硬编码样例；没有读取 `/api/settings`。输入框 `ui.go:148`、`demo.go:26` 只生成本窗演示回复；右侧审批卡也是样例。生产接入时移除这些可点击假结果。
4. 注释虽写“只调 GET”，Bun `/api/qq/conversations` 的 `readAt` 在首次访问时会写 `qq_read`（`daemon/plugins/qq-console.ts:190`）。Go 不能照搬这个隐藏副作用。
5. 导入器把旧段转成中立段（旧源码见删除提交 的父版本）；直接用当前 `seg` 解 Go 库会丢段。媒体路径接通本身不等于界面已兼容历史。

## 三、托盘、单实例与退出

本节使用的 mygo API 均在附录 A 列出 v0.7.1 源码行号；没有托盘专用第三方依赖。只做托盘图标和菜单，首阶段不做通知弹窗或托盘 flyout；`flyout.go` 的能力已核对，但主窗口无需变成浮动小窗。

### 3.1 启动、关窗口、重新打开

1. 先设稳定应用名 `Sumika`，再请求 mygo 单实例锁。正式应用标识固定为 `app.sumika.desktop`（拟定发行参数，不随 cwd/worktree 改变）；隔离演示和测试使用独立名称与临时数据目录。单实例锁按应用名/打包标识认，不把 QQ 账号当成应用身份。
2. 第二次双击只唤醒已有主窗口；不执行带来的配置写入、切换数据目录或连接账号。如果第二个启动要求另一数据目录，在第一窗明确提示当前目录，不能悄悄改宿主。
3. ready 后创建主窗口和托盘，显示“正在检查后台”；所有磁盘/进程探测/后台装配在 worker。托盘创建成功之前不启动 receive，满足“有托盘和原生 GUI 再起 Go”。图标随 exe 内嵌七张 PNG（16～64），按当前缩放比例下系统小图标的边长挑一张（ADR-230）；稳定托盘 ID `sumika-main`，深浅任务栏都能辨认。
4. 普通 X、Alt+F4：关闭事件取消默认动作后隐藏窗口；保留窗口对象、选中会话、已加载状态和订阅，不取消进程 ctx。恢复时还原最小化状态并显示/聚焦，沿用同一个窗口。正常主窗口保留任务栏入口；不照抄 menubar 示例的 accessory/SkipTaskbar 设置。
5. 托盘创建失败：主窗口保留并显示具体错误，不启动后台；X 走退出，不留下没有入口的常驻进程。不把这个退化状态算交付验收通过。
6. 已允许开机启动时，登录启动可先隐藏主窗，托盘正常后才继续启动；失败则显示主窗。未经决定不调用设置自启的写 API，默认关闭；不会在每次启动时强行关闭用户已有的 OS 自启项。

mygo 的单实例 API 在锁设施不可用时可能返回 true（`single_instance.go:108`），所以它是桌面唤醒机制，不能替代 `go/backend.lock`。数据锁必须在任何 Go 库打开前持有，archive 和 receive 都参与；另一 headless 后台占锁时只显示阻断页，不能接着打开另一套库。文件存在不代表锁被占，进程被杀后系统释放句柄，不按 PID 或删 lock 文件抢占。

### 3.3 唯一退出流程

状态为 `running → stopping → stopped`，启动未完成时同样可以退出。UI 线程维护退出状态；后台完成结果经有寿命守卫的投递返回。

- 菜单“退出”、应用退出事件和系统正常退出请求进入同一协调器。首次 `OnBeforeQuit` 取消默认退出，标 stopping，启动一次异步收尾；重复请求仍取消且不重复关闭。此时 X 仍只隐藏，不能越过收尾关闭事件循环。
- 先取消界面查询、媒体作业和订阅，等待这些消费者不再碰库；取消进行中的 Open，等待它完成或执行已打开资源的 cleanup。不能先把窗口真正销毁，再指望靠其回调等待后台。
- receive 调现有 Run 的取消路径，不另写一套关机：停适配器并等返回 → Pipeline/Responder.Stop/Gate/Intake → 共享 10 秒预算取消内核和审批、等路由及 Outcome、SealOutcomes → 等提前压缩、停记忆插件 → 关出口 → 交出发送锁 → 关记忆和库 → 释放数据锁 → 关闭提醒订阅及审批分析器。以 `app.go:316` 的实现为准，UI 消费者必须在关库前退出。
- archive 只关闭自己创建的查询、缓存作业和只读连接，随后释放数据锁；不凭空调用不存在的 Hub/Adapter。Open 成功但 Run 尚未开始时也必须能关闭，不能泄露锁。
- 全部完成后，将允许真正退出的状态写回 UI 线程，再调用 `App.Quit`；第二次 OnBeforeQuit 放行，OnClose 不再隐藏，OnWillQuit 销毁托盘。不能把耗时收尾放在 OnWillQuit 里，也不能在 UI 回调中阻塞等待后台。
- 日志文件（2026-11-01）：桌面是 `-H windowsgui` 编的，没有命令行窗口，后台的日志和宿主的状态变化写进 `<数据目录>/logs/desk-<日期>.log`（`native/internal/filelog`，和诊断入口的 `go-<日期>.log` 同一口径：本地日期、跨零点换文件、不删旧的）。外壳在后台线程里先开日志、再起宿主，演示数据（`-demo`）不开；数据目录没有身份证（`sumika-data.json`）时不建 `logs/`，等 receive 初始化了目录再写，所以 archive 指向不存在的目录不会被日志建出一个认不出身份证的空目录。令牌、会话号和长数字由 `app.newLogf` 在到文件之前抹掉；宿主和外壳自己的行（`host.set` 的状态、退出时的错误）只放阶段名和 `app.Open` 返回的错误。
- 总退出预算沿用 30 秒，包含 UI 消费者停止；后台的 10 秒在途预算不另重置。超时在主窗和脱敏日志说明未完成阶段，按既有异常退出约定以非零码结束；不用默认 0 假报正常退出。下一次启动仍走既有的未完成回合收尾（导入启动检查已随 ADR-308 删除）。断电/强杀没有完整收尾保证，验收必须证明重启不重发。

## 四、接口包：数据来源、快照与变更

以下为 Sumika 的 api 契约，不是 mygo API。读接口与可选写接口分开；不暴露原始 SQL 句柄、后台 App 指针或可调用渠道适配器。本地私聊写入口见 4.4.1。

### 4.1 身份和返回值

- `ConversationKey` 至少含 `Platform/Channel/Scene/Conversation`；实际数据库 conversation 原样保留。QQ 私聊含自己的号与对方号；QQ 群按群身份唯一，多号观察角色放入独立集合。事件唯一键为 `(platform, eventID)`，查询游标和引用还带 conversation；不跨库用裸 seq。
- 本地日常使用 `console:<角色>`，话题使用 `console:<角色>:topic:<ID>`。原型 `local:<角色>` 只属于演示，不能写进真实库。平台选择复用 `store.PlatformOf/PlatformOfConversation`，不在 UI 另拆前缀猜平台。
- 每个列表响应带 `items/nextCursor/hasMore`，状态区分 loading、ready（含空）、failed、unsupported；错误不转成空数组。角色和设置的一个坏分项可单独报错，不拿假默认值掩盖。
- `MessageView` 包括事件身份、平台、会话、发送者类型和 ID、显示名、origin、毫秒时间、正文、规范化显示段、unsent/partial/aborted、撤回状态及引用目标。DTO 不带 UI Element/Context/Bitmap；发送者身份不得从名字“主人”推断。`DisplayName` 由读侧按身份定：主人（`ActorKind=owner`）用入库时存下的群名片、昵称（号在段里的 `from.id`，再查名册兜底），都没有才写“主人”（2026-11-02 主人：群里引用写“主人”不对，要原本的名字；界面按 `ActorKind` 给主人的名字上强调色，引用块 `QuoteView.ActorKind` 同理）；`@` 段的名字（`DisplaySegment.Name`）由 store 填：先用同一页里这个号发言时的名字，再查名册，查不到界面显示号码，不为它另扫整个会话；QQ 的人（`ActorID` 是 `qq:<号>`，`qq_people.uid` 是裸号，查名册前去掉前缀）依次取入库时随事件存下的发言当时的群名片、昵称（Go 入库的事件才有，是最新的名字；Go 这边没有程序写 `qq_people`，导入时冻住的名册不会跟着改名），再取 `qq_people` 里本群的群名片、昵称（给导入来的旧事件和没存名字的事件兜底，与记忆取发言人名字同一个顺序）；私聊只取昵称；都没有才显示号码。外来的名字显示前过 `store.CleanDisplayName`（换行并空格、去控制和零宽字符、40 字截断），每次读都现查（不缓存），Go 入库的新消息用当时存下的名字，旧消息不会被改名追改。
- 查询结果由接收者只读持有，发布后不原地改 slice/map；跨线程只传不可变 DTO 和错误。只复制确实要隔离的集合，不为每帧重建全历史。

### 4.3 分页、排序和实时补齐

- 消息默认每页 200 条，上限 1000；参数 ≤0 或 >1000 返回参数错误，不静默扩大。SQL 按 `(created_at DESC, seq DESC)` 取 `limit+1`，截一页后正序显示。游标带平台、会话、时间和 seq；跨会话/平台游标拒绝，空游标才是最新页。相同毫秒按 seq 决胜，保留毫秒，不再乘 1000。
- 页大小指 timeline 事件数，通知/分隔也占位置，不能先删非 message 再用渲染条数判“还有更早”。撤回标记、引用摘要按本页可见事件批量查，目标不在本页也要正确；越权/跨会话目标不返回原文。
- 会话列表默认一页 200 项，允许继续取下一页，禁止沿用 Bun 的 LIMIT 200 后无入口访问其它会话。本地日常按角色稳定顺序；话题按置顶、最近活动、稳定 ID；QQ 按最新事件时间与稳定会话键倒序。无消息角色仍有日常入口，无最后时间不伪造“刚刚”。
- 最新页快照同时在读事务中取得该平台的 seq 高水位。变更后按 `seq > 水位` 分批 200 条追到当次捕获的上界，再按时间并入；这是新增事件的补齐游标，不用于历史翻页或判断已读。一次 65 条、一次 1000 条均不能漏。中途取消只更新已经完整处理的水位。
- 插入旧时间的补录有新 seq，应能进入正确时间位置；历史页和实时补齐重叠按事件键去重。补观察、撤回、发送状态修正等不增加 seq 的变化必须另触发已加载区间及会话元信息重查，不能只追新增。
- 同一会话查询按请求代次落地，A→B→A 的旧结果不覆盖重建后的 A；分页并发实时更新采用并集合并和最新行版本，不拿旧页替换整个会话。新页中的旧元数据不能把已知撤回状态退回正常。
- 复用第二版规格的消息稳定身份、前插锚点、会话 LRU：最多 6 个会话，每会话 2000 个事件；切回保留 ListState。超过容量从远离当前可见区的一端裁剪，并保留两个方向的分页入口；不能裁掉锚点后悄悄跳到别处。一万条压测走正常有界分页，统计“累计访问”与“当前驻留”两种数量，不用生产按钮一次塞一万条。

### 4.4 订阅顺序和线程

历史展示采用状态快照与失效通知。可以合并失效通知，但不能合并掉最新状态或静默漏业务记录；本地流式正文另走 4.4.1 的完整草稿回调。

1. 在后台登记订阅后才开始初始读取；借 `alert.SubscribeWithOpen` 的“先保证能收到变化再交初始状态”模式。数据库读取不能在通知登记锁中等待，避免写事务和通知锁互等。
2. 失效状态按平台/会话保存 dirty 标记；容量为 1 的 wake 只负责唤醒，不承载消息正文。worker 取走当前 dirty 集合后读取快照，读取期间再来的变更留在下一批；不在查询完成后清掉整个 dirty 集合。初始结果先发布，查询期间发生的变化随后重查，允许幂等重复，不留“取完快照还没订阅”的缺口。
3. 初始快照和同一订阅的后续快照由一个 worker 串行发布，带单调递增的投递版本。不同平台不伪装成跨 SQLite 文件的原子快照；版本只表示此订阅的投递顺序，不当持久化 event seq。订阅断开重建后重新取快照，不复用旧进程版本。
4. 存储层只在成功 commit 后标记变更；事务失败不通知。覆盖 `AppendEvent`、`AppendInbound`（含只补 observations 的重复消息）、`AppendPlan`、`EndPart`、`AbortPlanParts`、`ClaimEcho`、`Sweep/SweepPlan` 及通知入库。接线落在共用存储写路径，不能只挂 `Pipeline.OnStored`；后者只表示部分角色的新观察，不能覆盖所有写入。
5. 桌面订阅只监听当前需要的集合与缓存会话；隐藏窗口继续收后台事实，可合并成 dirty 状态，不每条消息重画整棵隐藏视图。恢复时重取最新状态并补齐再绘制；后台落库不等待 UI。
6. 读库、枚举卡、媒体读盘、解码、分页段转换和预排都在 worker；UI 线程只读 UI 模型、处理操作和接收投递。复用 `a.post`，最终通过 `Window.Update` 写回；Update 异步，不能调用后立刻读回布尔结果，也不能拿 Invalidate 代替同步。
7. 生命周期分为进程 ctx、窗口对象 ctx、会话请求 ctx。Hide 不取消前三者；实际销毁窗口或退出时取消相应对象。投递前和回调内都检查 ctx、窗口 generation 和会话 generation。概览、设置的结果另按数据源代次（`srcGen`，只在换数据源时加一）丢弃，不和会话代次共用：打开会话（含收到第一份概览后自动打开本地日常）会让会话代次加一，共用的话之后所有概览快照都被丢，接收中新来的消息就不进会话列表。源码 `content.go:172` 无“窗口已关就不执行 fn”的判断，不能依赖原型注释。
8. 查询统一可取消；默认读查询预算 5 秒，显式刷新可重试，不无限后台重试。连接失败、部分设置读取失败、媒体失败分别显示；失败刷新保留上一份成功快照并标明过时，不清成空白。订阅取消可重复调用，返回后保证不再查库；不能让退出等待一个只有 UI 回调才会关闭的 channel。

这些是数据展示的契约，不另造通用事件框架。本地流式回复使用独立的完整草稿快照；不能误用当前可合并 dirty 通知当 token 流。

### 4.5 未读和标已读

沿用 Bun 的主窗口阅读口径：QQ 会话中 `kind=message`、`actor_kind != character`、`created_at > read_at` 的可见记录计数；它不是 QQ 客户端回执。原 SQL 来源 `qq-console.ts:50`，应用时增加与消息页相同的观察可见性过滤。**不封顶**（主人 2026-11-02："实际多少就是多少"；原来数到 100 为止、显示 99+，2026-11-02 去掉）：会话列表照实显示，开销和量过的数见 量测-未读不封顶（私有存档）（一个会话 1 万条未读一次计数 7 ms，每 1000 条约 1 ms）。

有导入 qq_read 行就使用其 read_at；没有时在本次订阅首次快照用该会话最新可见事件时间作为**内存基线**，不插数据库，不把几十年历史都算新消息。基线在该会话本进程期间不变，后续消息正常增加。**读路径永远不写库**（展示查询、订阅、概览都是只读事务，T4 的审计触发器守着）。

**标已读**（2026-11-02，界面第一次写库）：单独的写入口，不借读路径。`store.MarkDisplayRead` 只写 `qq_read` 一行（会话 → 读到哪个时间，毫秒）：只往前（已有的更大或一样就不动、不通知）；夹到该会话里最新一条可见消息的时间（调用方传大了也只记真有的最新一条，不会把将来的消息提前算成已读）；会话必须在可见范围里（同一个 `validateDisplay`），没有可见消息什么也不写；本地库没有 `qq_read`，回 `ErrNoReadTracking`。写完通知同平台订阅，概览重查，列表上的数字随即归零。后台经可选接口 `api.ReadMarker.MarkRead(ctx, key, upTo)` 交给窗口（和 `AvatarReader` 一样没放进 `Reader`）；archive 下 `desktopread.Service` 的 `WithReadMark` 是关的，回 `api.ErrReadMarkUnsupported`，不碰库（archive 的库本来就是只读打开的）。

界面（`native/readmark.go`）什么时候标：数据源肯标、QQ 会话、会话列表里它有未读、第一页已取回、窗口在前台（显示着、没最小化、有键盘焦点，`OnFocus/OnBlur/OnShow/OnHide/OnMinimize/OnRestore` 跟踪）、聊天滚到了最新一条可见（`ListState.AtEnd`）。标到界面上最新一条的时间，不是"现在"。滚在中间看旧消息、窗口在后台、没有未读、本地会话都不标。写失败只记日志（桌面日志文件），不崩、不弹，同一个时间点不重试，下一条新消息或换会话再试；数据源说不标（archive）记一次，到换数据源为止不再问。聊天区底部原来的"看历史不会标为已读"去掉了。

**等主人定：archive（只看历史）下要不要标已读。** 现在照"只读"的约定不写，所以默认双击打开（archive）时未读不会消，只有"开始接收 QQ"（receive）之后才会。archive 下没有新消息进来，未读只来自导入的旧 `qq_read`，这些旧未读在 archive 下清不掉。要开：archive 的库得改成可写打开（`OpenGoReadOnly` 之外的路径），并且 `app.Desktop()` 里 `WithReadMark(true)`；这等于 archive 不再"完全只读"，所以交给主人定。

本地尚无已读持久化契约，不画虚构未读数字；可显示本次会话有新记录的临时提示。

## 五、媒体路径接线与显示段

### 5.1 平台路径和访问凭据

媒体的唯一路径是 `<data>/go/media/<平台>/<hash前两位>/<hash>`；`blobs/blob_refs/media_descriptions/media_notes/media_checks` 使用同平台库。ADR-260：桌面绑定数据根时建立 `mediastore.Reader`，在数据组排他锁保护的服务寿命中直接读取平台目录，ADR-308 起不检查导入状态，逐文件只检查 hash 格式、平台、路径和句柄，不重算全文 hash；具体契约见[运行时参考](subsystems/runtime.md#go-桌面媒体读取2026-11-04)。独立工具的 `mediastore.OpenMedia` 也不重算 hash，也不检查导入状态。写入 Put 按内容算 hash，离线 media-check 继续全文核对。

- 由后台从可信 ConversationKey 通过平台注册表选库，确认消息可见且该消息/其合法引用确实引用这个 hash，再发 `MediaRef` 给 UI。MediaRef 绑定平台、会话和来源事件；`ReadMedia` 验证凭据，不能接受 UI 传来的任意路径，也不能凭另一个平台的同 hash 放行。
- 合并转发里的媒体带 MediaRef.Forward 路径：可见 Source 事件必须带第一层 Ref，每层必须引用下一层，最后一层必须含该 hash；最多 10 层，断链、环、跨会话、树不带的 hash 一律拒绝。卡片封面也用相同媒体凭据。
- `PrepareVideo` 同样验证整条 Forward 链，终点接受 video 段自身 hash，或下载表确认 format=video 且 hash 一致的 file 段；带路径不退回顶层授权，不接受图片或封面冒充视频。文件下载动作同样验证路径，另核对节点和段下标，见[收图规格第十三节](规格-QQ收图下载和断线补录.md#十三视频和文件下载后台adr-255261)。
- hash 严格为 64 位小写十六进制。最终路径使用可信平台目录与 hash 构造；拒绝路径分隔符、绝对路径、`..`，校验现有父目录和目标的真实位置不越出媒体根，Windows 联接/符号链接越界拒绝。同 hash 在 local 与 qq 分别读取，不搜索其它平台“补图”。
- blobs 有元数据但文件已缺失时，保留文字描述和原有缺失状态，显示“本地文件未找到”；没有 blobs、没有 hash、权限拒绝、读取失败、格式无法解码、超预算分别给明确状态。不创建空文件，不回退 Bun，不访问段里的旧 URL。
- 读取服务不改 last_used_at、不回收引用、不删媒体。将来写入/清理服务也必须复用同一平台路径解析；首阶段不实现生产清理任务。验收覆盖删除一个平台的临时文件不会触碰另一平台、Bun 源文件或任何描述表。

### 5.2 界面怎么拿到图

`ReadMedia` 在 worker 返回字节和 MIME/size；UI 沿用 images.go/sniff.go 的字节头识别、静态/动态解码、缩放和错误显示。不给 UI 本地路径/HTTP URL。静态档为 128、256、384、512、768、1024、1536；tier=0 为原文件（动图和灯箱），不支持的 tier 返回参数错误。聊天宽度乘 `Painter.Scale()` 取得实际物理像素后选第一个够宽的档，首次绘制取得比例前只占位，不按固定 2 倍预先读图；屏幕比例变化后按新档重新请求。

比例采样挂在聊天根和转发查看窗口的稳定背景上，每个窗口一处；不挂在可能透明的图片入场元素上，避免实时图片等待动画显现才开始读取。图片自身的布局和入场规则继续沿用第二版规格。

2026-11-04（`fix/img-load` 分支，未合 main）：取图和解码共用两条流水线；排队项只保存媒体凭据，不预先持有原文件字节。可见图优先，列表测高时临时构建、随后不再请求的行从队列移除。见[运行时参考](subsystems/runtime.md#go-桌面媒体读取2026-11-04)及量测记录（私有存档）。

视频（2026-11-02，[规格-QQ视频](规格-QQ视频.md)第一步）：封面仍通过 ReadMedia 和图片缓存读取；视频本体不经过 20 MiB 的图片字节接口。可选 `api.VideoReader.PrepareVideo` 核对可见事件中的视频 hash，在后台复制到媒体 `.tmp/video-open/` 的带真实容器后缀文件，再由界面后台任务调用系统默认播放器。封面凭据还要对上该事件对应视频 hash 的 done 行；读消息只查库，不打开视频或封面文件。archive 启动也清超过一天的旧播放副本，不修改聊天库或媒体原件。

ADR-260 磁盘缩略图（`fix/img-load` 分支，未合 main）：

- 参考 Telegram Desktop `data/data_document_media.cpp:445-546`：先读持久缓存，缺失时后台生成、同图只生成一次、主线程发布；参考 `ui/image/image.cpp` 的尺寸准备键。参考 mygo-cloudmusic `internal/app/artwork.go:91-143`：在工人准备、主线程发布、有限并发。借结构，不逐段翻译。相关量测见本地图片加载量测（私有存档）。
- 我定的：缓存键是数据组／平台／hash／档／处理版本，路径 `go/media-thumbs/<平台>/<hash前两位>/<hash>.v1.<档>.png`。使用现有 Go 标准库 PNG BestSpeed，无损保存透明度，不加 libvips 或第二个解码库；代价是比有损 WebP 大，正式量测报告文件数和字节。后续换处理算法必须换版本，不兼容旧派生产物。
- 同一 Reader 的同图分片互斥；命中先读缓存，未命中拿锁后二次检查。沿用两路读取／解码并发预算，不另开工人。生成时先限制源字节为 20 MiB、像素为 100,000,000，宽不超过档、高不超过 4096、不放大；GIF／APNG／WebP 动图不生成缩略图。JPEG 的 EXIF 沿用当前界面口径：长边不超过 2048 才转正。
- 缩略图检查 PNG 块 CRC、尺寸与终止块，损坏或截断就重做，不为命中再解码原件或缩略像素。只有普通文件的坏内容可重做；权限错误、路径／联接／句柄错误直接返回，不吞错或绕路。
- 每次授权成功后先打开源文件并保留路径／句柄检查，命中缓存也如此；源缺失时不返回旧缓存、不创建空源、不跨平台补图。遗留缩略图是可删的孤儿派生数据，不恢复业务原件，不写聊天库。缓存路径也逐级拒绝符号链接／联接，并核对打开的句柄。
- 在最终文件同目录写唯一临时文件，写完 Sync、关闭，重新检查目录及目标后原子 Replace；取消或写入失败删除自己的临时文件。写一半被杀只留 `.partial`，永远不作为命中；同目录下超过一天的同图临时文件在下次生成时清理，不碰其它图或正在写的新文件。
- 灯箱当前及前后各一张请求 tier=0 原图，仍按像素预算解码；未到先显示聊天缩略图。动图保持原有播放产物和预算。缩略图不进备份；删除缓存后按需重建，源媒体和业务数据不变。

任务卡：用户目标是已下载图片在打开、换会话、重启后快速出现；信息架构沿用聊天图片和灯箱；无新增设置或控件，缓存归当前数据组，配置作用域不变。验收选择加载前后布局稳定、原图灯箱、125% 像素档、损坏重建、源缺失和取消；视觉参数沿现有 Telegram／MewTypeUI 基线。

保留现有预算：单文件最多 20 MiB（实际读取上限加 1 字节以识别超限，不静默截断后误报坏图）；解码前像素上限 100,000,000；同时解码 2；CPU 图片缓存 128 MiB；单动图保留帧 24 MiB、解码瞬时像素预算 64 MiB，超预算按第二版规格只留首帧并提示。图片缓存/在途任务的键从 `(hash,tier,anim)` 改成 `(platform,hash,tier,anim)`，绑定当前数据组寿命；切数据组不得复用旧结果。可见项保护沿用现有实现，预算被可见项撑破时单独报告，不声称 GPU 显存受 128 MiB 硬限。

导入只保证历史媒体。当前中立 Seg 的新入站 hash 可能为空；没有下载落盘的图显示“尚无本地媒体”，不能靠接界面临时链接腾讯下载或启动识图补写。新增实时媒体的下载由 `internal/mediafetch` 负责（[规格-QQ收图下载和断线补录](规格-QQ收图下载和断线补录.md)，2026-11-02 在分支 qq-media-backfill 上做完、未合 main；界面读 `media_fetch` 给占位文字是它的第 7 步，还没做），识图仍由渠道媒体流水线负责，其未接通不能阻挡已存在历史图片的验收，也不能宣称“所有新 QQ 图片已可看”。

### 5.3 中立段到显示段

生产 DTO 以 `types.Seg` 的 `kind/text/target/hash/ref/raw` 为正文段来源（`types/seg.go:33`）。界面直接使用 `api.DisplaySegment.Kind` 和展示字段；根包 `seg` 仅包装 DTO、段位置和下载键，不再翻译种类或逐字段复制。`blocksOf` 负责生成气泡/行内排版结果。演示旧段在 `demo_reader.go` 入口转成同一 DTO，渲染不识别旧 JSON（类型统一第一步，2026-11-07）。

- at、face/superface、emoji 仍按中立段显示。card 的完整字段、可点击正文链接、forward 的摘要和查看窗口已在[规格-链接和合并转发](规格-链接和合并转发.md)实现；video 按[规格-QQ视频](规格-QQ视频.md)显示封面、播放图标和时长，未下载时给大小或尚未下载提示；voice/file/other 仍用类型和可得名称占位。

- 新 Go 图片段的宽高和动图标记在下载落盘时写进 `media_fetch`（chat/0007），旧 done 行由 mediafetch 启动后的独立后台任务低速补齐；desktopread 沿原有展示查询事务批量取本页元数据，按 `(event_seq, idx)` 和 hash 对应，legacy 自带字段优先。读消息和订阅重查都不打开媒体文件、不占 queryGate 做文件 I/O；尺寸未知为 0，界面保留稳定的 4:3 占位。解析只读头和块结构，不解码像素，JPEG 与界面的 EXIF 旋转口径一致。
- 视频元数据在 chat/0008 的 `media_fetch.cover_hash/duration_ms/size` 和原 width/height；`DisplaySegment.Media/Cover/DurationMS/FetchState` 由同一批量查询投影，封面 hash 必须对应本段视频。新视频下载成功后后台执行 ffprobe/ffmpeg，不在消息查询路径里执行。
- file 段的实际种类存 chat/0010 的 format，转发结果在 qq/0006 加 format、size、cover_hash、duration_ms；DisplaySegment 的 FileKind / Download 供 MewTypeUI 第 4 步接入下载、图片展示与视频准备，原 kind=file 保留。普通图片读取仍 20 MiB，已核对图片文件允许读到 100 MiB；正文 / 转发的消息投影不读文件。
- 通知撤回以中立 `notice=recall` 加同会话 reply_to 识别；不能继续只认 `friend_recall/group_recall`，也不能有 reply_to 就算撤回。partial/aborted/unsent 状态分别保留，试运行记录明确写“未发送”，不伪装 QQ 已发。
- 小黄脸独立于 blob：v1 数据布局的既有资源为 `<data>/cache/qq/faces/index.json` 和 `<编号>.png`（`daemon/util/paths.ts:121`、`qq/faces.ts:24`），索引外壳为 `{version,faces}`。首阶段只读这份和已明确配置的本机资源来源，不启动 Bun 来供图，不扫描/修改真实 QQ、SnowLuma 配置。索引缺失显示 fallback 和明确缺资源状态；补资源来源时沿既有只读取法另做实现验收。

### 5.4 何时算补上 go-media-path-wiring

不得只删除 `verify.go` 中的字符串就宣布完成。ADR-216 第 4 条修正：界面后排期间，用诊断入口加测试证明生产读取路径，覆盖跨平台同 hash、源已缺失、旧段和新段；真实导入组的诊断由主会话另行安排，写代码任务不读取真实数据。界面阶段仍须验证真实窗口画出静态图/动图/小黄脸。

只有上述证明完成的实现版本，才在导入核对输出中把 `go-media-path-wiring` 改成已满足的消费者能力，记录实现版本与验收记录；旧 verify 报告不自动改写为已满足，真实启用时重新核对报告和程序版本。`real-import-authorization`、choices 和媒体能力是独立前提，本规格不替用户做 choices，不把已完成真实导入重新说成未获授权。

ADR-308 起直接读取平台媒体目录，不检查导入状态；原先的全文核对在显示路径上已被 ADR-260 改为只校验格式、路径和句柄，诊断仍核对全文。数据根沿用 `paths.Open` 的许可，允许本机配置的联接；Windows 从数据根目录句柄取得最终绝对路径，再在该根下逐级 `Lstat`，遇到 `ModeSymlink` 或 `ModeIrregular` 返回可判别的 `ErrMediaLink`，非最后一级必须为目录。检查和打开使用同一条绝对路径；打开后检查同一句柄的重解析属性，通过 `GetFinalPathNameByHandle` 取得最终路径，规范化 DOS/UNC 前缀后忽略大小写比较，不一致即拒绝。非 Windows 分支当前只做逐级 `Lstat`，不保证拦住检查与打开之间的路径替换。返回从头可读的普通文件句柄；缺文件不搜索其它平台、Bun 目录或旧 URL。诊断 `cmd/sumika-go/media_test.go` 继续覆盖内容不符、未合并 WAL 与只读文件指纹；`mediastore/media_read_windows_test.go` 覆盖同内容跨平台联接替换、重解析点句柄及非目录父路径。

诊断用法（在 `native/`）：`go run ./cmd/sumika-go -mode media-check -data "<数据目录>"`。先停 Go 后台；诊断只读打开已有 `go/backend.lock` 并持有排他锁，锁不存在或被占用就拒绝，不创建文件。SQLite 用 `mode=ro`、`query_only`、无锁 VFS 和内存 WAL 索引读取未合并 WAL，不用 immutable；后台锁保证核对期间没有协作写入者。仅输出每个平台的段数、读到、缺文件、内容不符、hash 为空、读取出错；缺文件和空 hash 不使退出码失败，联接和非目录父路径计入读取出错，内容不符及读取错误退出 1，参数错误退出 2。旧段仅在 `import_meta.version=1` 且下标、类型、身份及已有 hash 一致时补 hash；冲突保留中立段并记读取错误。核对不加载配置、不建日志、不更新业务库；成功时 stderr 为空。

新生成的 `verify.json` 在 `consumer_capabilities` 记录 `go-media-path-wiring`、`implementation_version` 和 `acceptance_evidence`，不再列为 `activation_missing`；这只证明该实现的消费者能力，不把当前数据组的内容核对、授权或 choices 改成通过。临时夹具及真实可执行文件冒烟已覆盖；真实导入组的诊断结果由主会话在另行安排的运行中记录。

历史版本 1 的改坏验收（ADR-308 后已移除启动时的导入状态检查）：18 种生产代码编译覆盖均触发对应测试失败，包括跨平台缺失兜底、去掉 hash/启动屏障/内容校验、吞读取错误、旧段补 hash/身份/hash/版本/JSON、输出路径、诊断分流、immutable 忽略 WAL、磁盘 WAL 索引写入、跳过联接保护、忽略后台锁、创建锁文件，以及 verify 残留缺项/漏写能力。覆盖和驱动均为临时验收文件，验收后删除；最终测试在恢复后的生产代码上运行。

本轮返工的 7 种改坏均实际触发对应测试失败：去掉 `ModeIrregular`、非目录父路径检查、打开后最终路径比对、句柄重解析属性检查、数据根句柄解析，以及分别把诊断总检查和逐文件读取改回默认日志；恢复后运行相关测试及真实可执行文件诊断，非法 run 日志存在时 stderr 为 0 字节。

### 5.5 引用、表情回应、头像（2026-11-02，feat/bubble-ui）

- 引用：`MessageView.ReplyTo/Reply` 早就有，界面 2026-11-02 开始用（不看 segs 里的 reply 段）。读不到原消息是 `Reply.State=Unsupported`，界面写"原消息不在本地"。
- `QuoteView.Segments` 带原消息的展示段和已解析的 `Name`；store 同一次批量查名也收集页外合法引用里的 @，不逐人扫描历史。QQ 私聊、QQ 群的引用与正文共用 `atText`，没有名字按 `config.MaskID` 打码；旧无段引用只将 `@数字` 打码。本地私聊、本地群聊仍取原文字。QQ 会话列表最后一句复用同一预览转换，预览不构建布局块或扫描链接，复制沿正文的显示块取字。
- 表情回应：`MessageView.Reactions []ReactionView`（`store.enrichDisplay` 里 `readNotices` 和撤回合成一次批量查，不多扫一遍会话；量测见回应和撤回合并查询（私有存档））。通知行本身（`kind=notice`）仍不显示成气泡。口径同引用和撤回：同一个会话、观察范围内，一条消息最多 500 个；订阅里新回应随被贴那条一起进 `Changed`。后台没存取消回应、没存她自己号贴的（见待办"表情回应：取消、悬停里的时间"）。
- 页上的 `Before`（2026-11-02）：`MessagePage.Before` 是这一页最老一条再往前的那条消息（`store.DisplayPage.Before`，同一个会话、观察范围，只认 kind=message；没有更早的消息为空）。界面只用它的发送人和时间，判断已加载的最老那一行是不是一组的第一条、是不是新的一天，前面的页加载进来以后这一行不会变（见规格-原生界面第二版（私有存档） 11.7）。不做 `enrichDisplay`，只有基本字段；每页多一次按会话索引的 `LIMIT 1` 查询。
- 头像：可选接口 `api.AvatarReader{ReadAvatar(ctx, key)}`，**不是** `Reader` 的方法（Reader 的实现多，别的分支也在加）。`desktopread.Service` 实现它，`desktopread.Reader` 嵌了 `*Service` 所以自动满足；演示数据的读取也实现了（画色块）。key 只认 `user:<4～12 位数字>`、`group:<…>`；读 `qq.db` 的 `qq_avatars`，哈希经 `mediastore.OpenMedia(data,"qq",hash)` 读，上限 5 MiB；没有的回 `api.ErrNoAvatar`。不按会话观察范围卡（头像是 QQ 公开的，接口只给本机界面）。

## 六、四种场合的可见范围

窗口是本机主窗口；“主人能在这个窗口查看已保存的内容”不等于把这些内容给当前 QQ 回合、群友或另一个角色。所有接口先验证会话和观察范围，再投影；直接调用 api 也不能绕过。

| 场合 | 首阶段可见 | 不能因此获得 |
|---|---|---|
| 本地私聊 | 当前角色的日常与已导入话题、该会话消息、允许的媒体；保留 origin 与发送者身份 | 其它角色的本地私聊自动并入当前会话；点开历史触发模型/记忆整理/执行工具 |
| 本地群聊 | 真实群目录与成员校验；共用 Composer，经 `LocalGroupWriter` 发文字、停止整轮，每群草稿独立；archive 提示启动后台，无写能力则不显示输入框（[规格](规格-本地群聊.md)） | 将 mock 的 home:cabin 当真群；私聊拼接成群；群内执行工具或审批卡；绕过成员校验 |
| QQ 私聊 | 精确的 `qq:private:<自己号>:<对方号>`，仅已接入角色实际观察到的记录与引用；名字和段按私聊显示 | 同一个对方与另一小号的私聊混在一起；因为主人正在看就改成 privateOk/fullMemory；直接发送或耳语 |
| QQ 群 | 一群一条时间线，按已观察角色集合的并集显示历史；按角色筛选时只返回该角色有观察的记录，同条多号观察只显示一次 | 未观察到的归档/陌生人记录冒充她看过；没有观察信息时回退全库；角色 A 的注入/草稿放入角色 B 面板；在 QQ 群出现本地执行能力 |

本地群聊的生产缺口来自《规格-本地会话栏》第二节与 Go 当前仅有 local_topics，属于既有功能未实现，不在本规格中发明群成员表。若实际导入报告存在其它正式本地群标识，**待核实**其有类型契约和成员来源；不能凭前缀或发言人数推断。核实前不把未知会话归入私聊、公有会话；保留数据并显示无法识别的原因。实施者须在第 1 步以构造样本核对，不读取真实库来猜。

QQ 查询按 observations 取并集，分页、会话摘要、未读、引用、媒体凭据用同一过滤器。库里为了审计保存但未被角色观察的陌生人/自检记录，不自动暴露成聊天记录；需要管理视图另走既有规格。没有观察的本地分叉消息不能套用 QQ 的过滤器一律删掉，本地话题按所有权契约读取。

既有权限保持：`policy.go:374` 的执行类工具只允许 `channel=console && privateOk`，后台按当轮 audience/OwnerAsked/Scope 判断；UI 当前选择、角色名或前台焦点不能修改它们。角色卡的“私下”只有外部平台群排除，本地群不自动算有外人（`persona.go:165`）。首阶段 api 没有发送/审批入口，查看历史不会建立新的高权限回合。

## 七、和 Bun 的交接与实施步骤

### 7.1 停写证明及保守默认

**默认：任何冲突或无法确认时，整个 Go 后台不启动、不打开业务库、不连接 QQ；mygo 只显示检查结果和退出入口。** 不选择“先连上但不发”，因为重复接收也会制造分叉历史，发送锁只能管发。

交接前由主会话准备具体清单，最终生产操作才请用户决定；本次不执行：

1. 历史交接时记录计划使用的数据组、导入 run、所选一个小号、旧后台的启动方式，以及导入快照后 Bun 是否又写了记录；ADR-308 后导入工具已退役。先停止看门/自动重启入口，再正常停 Bun，等退出；不杀整机所有 bun.exe，不修改其它服务配置。旧进程退出失败或无法确定它属于哪套数据，保持停机。
2. Go 启动预检探测固定回环 7720 以及配置里旧 console 端口：TCP 能连就视为占用，不因非 Sumika 的 HTTP 内容而放行。每端点超时 500 ms；明确连接拒绝才算该端点无监听，超时/访问错误为未知。探测本身只连接/读取，不调用 Bun 的有写副作用 GET。
3. 不枚举进程、不读命令行（主会话 2026-10-28 收窄：Bun 已退役，交接由主人手动做一次，最小充分方案就是第 2 条的端口探测加第 4 条的数据锁；进程枚举在 Windows 上权限、归属都靠不住）。交接清单里写明“先停 Bun、关闭看门和自动重启入口、确认 7720 关了再起 Go；接管后保持旧端停用”。
4. 抢 `go/backend.lock`，持锁执行第 2 条的一次旧监听检查，再打开业务库。ADR-308 起不再检查导入状态或 run 指纹；历史导入工具已退役。
5. SnowLuma WS 活着只证明协议端可连，不证明 Bun 已断开；此阶段不为探测另开一个接收连接、不发测试消息、不启动或改 SnowLuma。接收权只在上述交接完成后交给现有 Adapter.Run。

技术限制必须写清：未改造的 Bun 不持 Go 的 backend.lock，mygo 单实例锁也只管桌面，QQ 发送锁不排斥接收；7720 关闭不能原子阻止日后有人手动重启 Bun。因此“先关看门并等待确定的旧后台退出，接管后防止旧端复活”是正式接管的操作前提，不声称已有跨 Bun/Go 的接收互斥协议。不为这份规格恢复 Bun 开发。如果未来要求任意重启旧 exe 也绝无重叠，需要另定旧端也参与的接收权协议，不能用轮询包装成保证。

运行期不轮询（同上收窄），只在每次后台启动时检查一次；启动后旧端复活不会自动发现，也不会自动停收或收尾。此边界影响 QQ 私聊、QQ 群的接收交接；本地私聊、本地群聊不涉及 QQ 双收（issue #14）。

## 八、禁止的偷懒写法与已知的坑

**禁止：**

- 把托盘放进另一个壳 exe，或桌面再起 headless 子进程；为界面新增 HTTP 端口；让 view/data.go import app 实现或 SQL。
- 在 ready/绘制/UI 回调内查库、列模型、读文件、等后台关机；将 Window.Update 当同步；把一帧 Element/Context 存给 worker。
- 只换 data.go 的 URL 或直接把 Bun JSON 结构拿来解中立段；继续保留生产演示回复、假审批成功和假清理结果。
- 最新 20 条当可靠实时流；以 seq 大小当时间排序；跨库按裸 seq 去重；用姓名或“当前打开的会话”推断消息归属。
- 列表读取自动建 qq_read、刷新卡片/远程头像、补录、下载原图、触发模型、整理记忆；空结果/失败回 mock。
- Go 媒体找不到就读 shared/media、其它平台、旧 URL；只移除 go-media-path-wiring 文本；只改 UI 禁用而后端仍暴露写入口。
- 仅凭 7720 不通、backend.lock 文件存在、发送锁已拿到、SnowLuma WS 已连接，就宣称 Bun 停写或接收互斥。
- X 同时取消后台；退出时直接强杀作为正常路径；先关库再让订阅查询收尾；用一条新的全局锁串行化所有绘制和业务 I/O。
- 本次规格编辑顺手改 ADR、待办、测试基线或真实配置。实现时才按影响清单成组更新。

## 九、验收标准与具体量法
