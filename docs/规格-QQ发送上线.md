## 一、装什么、不装什么

**装**：

1. SnowLuma 适配器在同一条正向 WebSocket 上发 OneBot action，用 `echo` 对回包。文字和戳一戳的成功回包形状分开认。
2. 连上以后用 `get_login_info` 核号，用 `get_status` 看收发链路；对不上或不健康就不发。不健康且连接没断时，按固定周期再查，不把心跳当成恢复。
3. 去掉装配处的共存钳制，但默认仍不发。摘钳制要同时满足：配置把这个号的发送权交给 Go、Go 拿着跨进程独占锁、会抢同一把锁的 Bun 已经停发并放锁、登录号核验通过、守卫和发送检查都接上。缺一就保持钳制。
4. 说话档走已经有的出口状态机。字数保险丝、发送前守卫（回合的回复和复读的文字都过）、通道门的暂停接到每次发送检查、回包确认和回声确认都通知通道门、第一条失败提醒。

**不装**：

- 本地私聊、本地群聊的发送（不走 QQ，见第二节）。
- 在第七节第 4 问点头之前，不把「只做字面、不上相似度和确认」当成可以上线的做法。W8 没做完时，发送保持钳制。
- 多个小号、图片和合并转发、系统通知弹窗（mygo 还没接；提醒写日志和 `qq_alerts`，照装配第四节第 8 条）。
- 在真实群里开口。真机那一步只写「要主人点头」，群和发什么由主人当次指定。

## 二、四种场合

| 场合 | 这一步 |
|---|---|
| 本地私聊 | 不适用。不经 OneBot，也不读 `qq.goSend`。继续走现在的本地出口。复读插件的场合只有群（`repeat.go:84`），本地私聊没有复读。 |
| 本地群聊 | 不适用，发送不走 QQ。渠道是 `console`，`GateModes` 固定「说话」（`native/internal/channel/gate.go:188`），不过 QQ 适配器。复读插件是跨平台的，守卫接在插件里、不接在 QQ 适配器里（第六节），免得以后本地群开了复读就绕过。本规格不改本地出口。 |
| QQ 私聊 | 能发，但默认不回。`qq.reply` 默认关（规格-QQ渠道第十一节）；白名单外只存不回。开了以后才对 `privateAllow` 里的人走出口。会话串带她的号（规格-渠道中间件第十一节）。私聊在 `GateModes` 里本来就是「说话」（`gate.go:188-189`），所以钳制一摘、开关一开就会真发，不能只靠「群还是试运行」挡住。私聊不过群闸门，暂停仍要靠出口的发送检查挡住（6.3）。没有复读。戳回去按 ADR-189，不过文字守卫，过发送检查；戳她的人必须就是这个私聊的对方，不然只存不戳回（2026-10-31）。 |
| QQ 群 | 能发。没在 `gate_modes` 里写成「说话」的群保持试运行（`GateModes` 的默认档，装配第四节）。改成「说话」是逐群的，本规格不改任何一个群的档。复读、戳回去都走出口；复读的文字过守卫，戳回去只过发送检查。通知批不交闸门（`pipeline.go:147` 只跑拦截链），所以暂停不能只靠闸门。 |

下面说「QQ」时，私聊和群都算，除非写明只一边。

## 三、适配器真发

第 6 步的适配器明确不发：`ReadFrame` 的注释写「must not send actions」（`native/internal/channel/snowluma/snowluma.go:20`），`NewWS` 注释写「只收不发」（`connect.go:61-62`），`Send` 对文字段返回失败回执「第 6 步只收不发」（`snowluma.go:77-81`），`Poke` 返回 `ErrUnsupported`（`snowluma.go:83-84`），`Caps` 是空的（`snowluma.go:44`）。

这一步在**同一条** Universal 连接上写 action。`Event` 角色不能调 API、`Api` 角色不收事件（issue #8 对 `3bd74ac` 的 `ws-server-connections.ts` 的说明）；地址继续用装配已定的 `ws-default`，不改 SnowLuma 配置（ADR-185）。

发送许可和对应连接在同一把锁里取得；`Send`、`Poke` 的这一次调用只用取得许可的连接。旧连接失效就按本次未连上或写后未知处理，不转投重连后尚未核验的新连接。登录和状态查询也固定使用各自核验的那条连接。

### 3.1 帧

照 Bun 的 `call`（`daemon/onebot/client.ts:78-86`）：

```json
{"action":"<名字>","params":{...},"echo":"<这次的 id>"}
```

- `echo` 用适配器自己的不重复字符串（Bun 用 `s` 加递增序号，`client.ts:81`）。不要用计划号当 echo：重试是一次新的调用，echo 必须换，否则迟到的上一包会对上这一次。
- 回包只认 `echo` 相同的那一帧（`client.ts:158-163`）。对不上的 action 回包丢掉，记一行日志（不含令牌、不含原文）。
- 文字段：群 `send_group_msg`，参数 `group_id`、`message`（段数组）；私聊 `send_private_msg`，参数 `user_id`、`message`。SnowLuma 两处都返回 `{ message_id }`（SL `packages/onebot/src/actions/message.ts:135-167`、`:171-196`）。也有 `send_msg` 按 `message_type` 分流（同文件 `:81-131`）。（我定的）QQ 文字只用 `send_group_msg` / `send_private_msg`，不用 `send_msg`。另一种是 SnowLuma 档案走 `send_msg`（Bun 在 `daemon/plugins/qq.ts:775-781` 对 snowluma 档案这么做），代价是多一条档案分支，和「数组格式、动作名固定」的测试不好对。
- `message` 用段数组，不用 CQ 码字符串（规格-QQ渠道第二节）。这一步文字段只有 `{ "type": "text", "data": { "text": "..." } }`。`auto_escape` 不传（SnowLuma 默认 false，SL `message.ts:193`）。
- 戳一戳：群 `group_poke`（`group_id` + `user_id`），私聊 `friend_poke`（`user_id`）。SL `packages/onebot/src/actions/extended.ts:585-607`、`:610-630`：两个动作成功都是 `return okResponse()`，`returnsSchema.type` 为 `null`，说明写「成功时 data 为 null」。不照 Bun 自检那样一串名字轮着试（`qq.ts:984-985` 的 `friend_poke` / `send_poke` / `send_friend_poke`）：轮试会把「不支持」和「失败」混在一次调用里，出口分不清要不要重试。协议端明确说没有这个动作，才回 `ErrUnsupported`（出口对不支持不重试，`outlet_run.go:198-199`）。
- 文字的 `message_id` 按**十进制字符串**原样存，负号保留。SL 自己的例子写「成功返回的 message_id 可为负值」（`message.ts:187`、`:206`）。0、空、缺字段不算确认（规格-渠道中间件第十六节「回执缺失」）。戳一戳没有消息号，见 3.2，不把 `null` 凑成一个号。

### 3.2 回执怎么判

适配器自己的等待是 **10 秒**（Bun `TIMING.callTimeout`，`client.ts:23`），从调用开始算，包含等待核验、写入和等待回包；到点必须能取消卡住的 `Write`，登录和状态查询同样受这个上限。计时用适配器自己的钟，测试可拨钟。出口外面还有 30 秒兜底（`outlet.go:97-98`、`outlet.go:112-113`），适配器必须更短，否则兜底先到、适配器还占着连接。

确认只认 **`retcode` 是 JSON 整数 0**。缺字段、JSON `null`、字符串 `"0"`、布尔值都不是 0。这是规格-渠道中间件第十三节第 474 行（「`retcode` 等于 0 才算成功」），不放宽。Bun 把缺省的 `retcode` 当成成功（`client.ts:161`：只有 `status === failed` 或 `retcode` 非空且非 0 才 reject）。那条不照搬。

`status == "failed"` 算明确失败，不论 `retcode` 是 0、非 0 还是缺省。`retcode` 非 0 且 `status` 不是 `failed`：结果未知，不重试。规格-渠道中间件第 474 行写过，非 0 可能是「已接受、异步执行」。Bun 把任何非 0 都 `reject`（`client.ts:161`），那会让出口重试、有机会发两遍。（我定的）只有明确失败才重试；其余非 0 算结果未知。另一种是全照 Bun，代价是异步回包被重发。

| 情况 | 回执 | 出口会怎样（已有，不改口径，除 6.4 补的那次通知） |
|---|---|---|
| **文字**：`retcode` 为整数 0，且 `status` 不是 `failed`（`status` 可以缺），且 `data.message_id` 是非 0 整数或它的十进制字符串 | `ReceiptConfirmed`，`PlatformID` 为该字符串，`Via` 由出口写成 reply（`outlet_run.go:183-186`） | 段确认；`channel_msgs` 把这个号指到这次回复的事件（`outbound.go:288-292`，只在 `HasPlatformID` 时写） |
| **戳一戳**（`group_poke` / `friend_poke`）：`retcode` 为整数 0，且 `status` 不是 `failed`，且 `data` 为 `null` 或没有非 0 的 `message_id` | `ReceiptConfirmed`，`PlatformID` **留空** | 段确认。空号 `HasPlatformID` 为 false（`store/inbound.go:14-15`），`EndPart` 不写 `channel_msgs`（`outbound.go:288`）。戳一戳计划本来也不写 events（`outlet.go:483-484`）。`Receipt.Validate` 允许确认回执不带平台消息号（`types/adapter.go:67-69` 只禁止没确认的回执带号） |
| 连接没建立、动作名不存在、参数被协议端明确拒绝（`status == failed`，或还没 `Write` 就失败） | `ReceiptFailed` | 最多 3 次（`MaxAttempts`，`outlet.go:64-65`），间隔用 `Pace.Retry`（默认 1 秒，规格-渠道中间件 10.4） |
| 写出以后 10 秒没有对上的回包；写出以后连接断了；`retcode` 缺省、不是整数、或非 0 但 `status` 不是 `failed`；文字回包缺 `message_id`、为 0、或 `data` 为 `null` | `ReceiptUnknown` | **不重试**（`outlet_run.go:189-193`）。文字在 5 分钟内可以由回声认领（`outlet_echo.go:12`，`EchoWindow` 默认 5 分钟，`outlet.go:98`）。戳一戳没有字，认领函数直接放过（`outlet_echo.go:39-40`），结果未知就保持未知 |

（我定的）戳一戳的回包里如果带了非 0 的 `message_id`，仍按确认处理，但 `PlatformID` 留空，不写 `channel_msgs`。另一种是照文字去记这个号，代价是戳一戳没有 events 行，号写进去也没有事件可指（`outbound.go:289` 的 SELECT 出不了行），以后若有人给戳一戳补事件，会和这个号串上。不选。

确定在进入 `Write` 之前失败（没连上、核验没过、参数不对）：算明确失败。进入实际写操作后，无法证明一个字节都没写出的错误也按结果未知，不允许据此重发。已经匹配的回包优先采用；从等待表删除和向等待方投递在同一临界区完成，超时、取消与回包只能有一个完成点。这是清单⑩，不要合成一种错误。

### 3.3 和出口、回声的关系

出口的计划状态机、重试、停顿、关闭，这一步**不重写**。适配器只负责把一段 `Part` 变成一次 action 和一种回执。

- 回声先于回包：出口在「发送中」被认领后取消这次等待（`outlet_run.go:176-177`、`:315-318`）。适配器要守 ctx，取消后尽快从 `Send` 返回，不要再等满 10 秒。
- 认领键仍是（发送用的号、会话、去掉首尾空白并统一换行的文字）（`outlet_echo.go:11`、`:29-31`）。戳一戳没有字，只靠回包确认。
- 每个回声只认一段、先发的先认；已中止的段只记观察（`outlet_echo.go:13-16`）。这一步不加新的认领规则。认领成功要通知通道门和提醒，见 6.4：现在 `OnPart` 写明「被回声认领的不调」（`outlet.go:90`），`ClaimEcho` 只 `wakeFlight`（`outlet_echo.go:65`），`callWoken` 走到 `lost` 后不再 `partResult`（`outlet_run.go:176-177`、`:145-150`）。这一步把这处补上，不是另做一套认领。
- 平台消息号写进该渠道库的 `channel_msgs`（Go 的表；不是 Bun 的 `qq_msgs`）。只有文字段确认且号非空时写。不要在回包到达前先写一个空号。戳一戳确认不写。

### 3.4 动作清单和回执（ADR-215，2026-10-30 加，细节待真帧）

除了文字和戳一戳，链接解析的"展开"（ADR-191～194）还要这几种发送动作。它们和文字一样走出口、发送锁、守卫和通道门，只是帧和回执不同；要发哪一种、什么时候发由《规格-链接解析》定，这里只管"怎么发、怎么判发成功"。

| 动作 | OneBot action（待真帧确认） | 回执怎么判（待定） | 进不进 `channel_msgs` |
|---|---|---|---|
| 引用回复 | `send_group_msg` / `send_private_msg`，消息段带 `reply` | 同 3.2 文字 | 进，和文字一样记平台消息号 |
| 表情回应 | `set_msg_emoji_like` 一类（SnowLuma 支不支持先拿真帧确认） | 先看真帧：回包有没有 `retcode`、有没有消息号 | 不进（不产生新消息） |
| 合并转发 | `send_group_forward_msg` / `send_private_forward_msg` 一类 | 先看真帧 | 进，记返回的消息号 |

动手前先照 issue #8 那次 `get_*` 的做法，在 SnowLuma 上各录一次真帧（成功、目标不存在、无权限），把回包形状写进上表，再定回执规则；没录到的动作不发。守卫对合并转发里的每一段文字都要过一遍，不能只过外层。

| 引用 + 转发节点放进同一个 `send_group_msg` | `failed` / 1400，"message segment \"node\" is only valid inside a forward node list" | 没有 |
| 往群号 1 发 | `failed` / 100，"send group message rejected: result=110 err=发送失败，你已被移出该群，请重新加群。" | 没有 |

由此：群回应按这份打开（能力位 `ReactGroup`）；回应确认不写 `channel_msgs`，推回来的 `group_msg_emoji_like` 通知是小号自己做的，入库站对角色自己号的通知不存（`intake_notice.go` 文件头），不会多出一条"别人贴的"。**引用和转发不能一次发出**，链接解析要先发一条带引用的导语、再发转发（《规格-链接解析》8.2 那条"若不能"的做法；先发导语这一步已被[规格-链接发送改版](规格-链接发送改版.md) B4、A5 改为（ADR-360）：转发前不再另发导语，转发不带引用）。不在的群回的是 100，照明确失败处理。


## 四、登录号核验

SnowLuma 有这两个动作（SL `packages/onebot/src/actions/info.ts:7-29`、`:32-66`）：

- `get_login_info` → `user_id`、`nickname`。
- `get_status` → `online`、`good`（收发链路健康）、`time`。`good` 的定义是「在线且 `receiveHealthy`」（`:59-63`）。不能只看 `online`。

握手成功、收到第一帧之后、**任何发送之前**（包括重连以后）：

1. 调 `get_login_info`，10 秒。`user_id` 转成十进制字符串，和这条连接配置的号（`Config.Account`，`connect.go:42`）比。配置 `"090001"` 和回包 `90001` 不相等，不去掉前导零来放行；回包字符串 `"090001"` 也不是合法的无前导零十进制号，核验失败、不发。
2. 对得上，再调 `get_status`。`online == true` 且 `good == true` 才把连接标成可以发。
3. 号对不上：关掉这条连接，**不发任何 action**（已经在等的发送回 `ReceiptFailed`，原因「登录号和配置不一致」）。提醒一次，键 `qq:<号>:login`，标题写「协议端登录的号和配置不一致」，正文只说「对不上」，**不写两边的号**（号进 `Detail` 也不行；日志打码照装配第十节）。60 秒以后再连（Bun 的 `mismatchRetry`，`client.ts:23`、`:140-143`、`:186`）。连上仍不对，不重复 Raise（键还开着）。
4. 号对得上但 `good == false` 或 `online == false`，或回包缺 `good`：不发。提醒一次，键 `qq:<号>:status`，标题「协议端报收发不健康」。**连接不断也要再查**，不能只等重连。现有看门狗只在 `readFrames` 返回、一帧都没有时才关连接（`connect.go:197-204`、`:222-227`）；心跳一直在来，就不会重连，也就不会再核验。
5. （我定的）不健康期间保持这条连接（收包不停），每 **30 秒**再调一次 `get_status`，用适配器自己的钟，测试拨快、不真等。30 秒和掉线提醒是同一个数，不另造一个。某次查到 `online` 和 `good` 都是 true，才允许发，并 `Clear` 键 `qq:<号>:status`。心跳、别的事件都不算恢复。另一种是发现不健康就主动断开，等重连时再核验；代价是收包也断一个退避周期。不选。
6. 查询本身失败（超时、断线）走现有的掉线提醒（`qq:<号>:conn`，30 秒），不另造一种「当健康」。健康时不轮询 `get_status`。本步不发现「本来健康、连接没断、中途变成不健康」；要发现得另做周期查询，不在这里加。（2026-11-02 补：就绪以后看每一拍心跳的 `status.good`、`online`，变假提醒一次、键 `qq:<号>:recv`，变真 Clear；只提醒，不停发、不拆连接、不改 `status` 键，也不轮询，`native/internal/channel/snowluma/health.go`。）

`Config.Account` 仍然只是配置里的号，不是核验结果（装配第十节已经写了这个区别）。帧里的 `self_id` 和 `get_login_info` 不一致时，以 `get_login_info` 为准停发，并记日志；不把 `self_id` 改写成配置的号。同一次连接一旦发生冲突，后来的匹配帧或健康回包也不能恢复发送，只有新连接重新核验。日志去重只控制日志，不控制停发判断。

（我定的）核验没过时，适配器对 `Send` / `Poke` 返回明确失败，不返回「不支持」。不支持会让出口把段直接标失败且不重试，核验恢复后这一段也不会再发。明确失败则还能在次数内重试；核验长时间不过，三次以后通道门会计数（第六节）。另一种是核验失败用结果未知，代价是出口不重试，段停在未知，主人看不到「没发出去」。

## 五、去掉共存钳制，并且保证不同时发

装配第五节把 QQ 上算出来的「说话」一律改成「试运行」，因为 `GateModes` 对私聊固定「说话」，群里已有的「说话」也会盖过默认试运行；只靠适配器返回失败，会留下失败计划并让通道门暂停（`规格-Go后台装配.md` 第五节、第十节）。钳制写在装配处，不在闸门里。`internal/app` 在本规格起草时还没有这份钳制的实现（仓库里没有 `native/internal/app`）；摘钳制的那一步以装配第 4 步落地后的那个函数为准，名字以代码为准。

### 5.1 什么时候摘

下面几条**同时满足**才摘，缺一就保持钳制（QQ 有效档只有试运行和只记录）：

1. 配置 `qq.goSend` 为 true（新键，默认 **false**）。只作用于 `-account` 那个小号（ADR-197）。没写这个键等于 false。
2. 主人意图文件里的 `holder` 是 `go`（5.2）。意图不是发送权。
3. 本进程拿着 5.2 的独占锁，并且交接记录的 `protocol` 是 1、`state` 在抢到锁之前是 `released`（首次接管写下的 `origin: first-takeover` 记录也算；记录是本进程这一边上次留下的 `holding`、这次重新拿到锁的，照 5.2 接着发，2026-10-30 实现时对齐）。没有这份记录，或记录不是 1：即使有人把 `qq.goSend` 和 `holder` 都写成 go，也保持钳制。
4. 第四节的核验已经通过，而且当前不是「不健康、等复查」。
5. 守卫不是 nil，而且 `GuardLevel()` 是允许启用的那一档（6.2）。`settle.go:255-257` 现在是 nil 就直接放行，**不能靠那里挡**。检查放在装配的启用条件上：条件不齐就不摘钳制，说话档的 `Send` 不会被调到。
6. `OutletConfig.Check` 不是 nil（6.3）。nil 时出口直接放行（`outlet.go:529-530`），暂停、戳回去、复读、QQ 私聊都挡不住。
7. ~~复读用的听众函数不是 nil~~（2026-11-07 去掉。盘点出"拿掉复读整个 QQ 发送都会被锁住"，主人："这不行吧"；照 ADR-289"依赖要声明、不能藏在装配里"改为：复读没有听众函数时由复读自己拦下不发（`repeat.go` 的"守卫没有听众"），不再钳住整个 QQ 发送——一个功能没接好不该让所有消息都发不出去；见 notes/盘点-插件解耦-2026-11-07.md）。复读那一路的检查照旧：听众取不到就不发（6.2）。

摘掉以后，档位函数对 QQ **原样返回** `GateModes` 的结果。私聊仍是「说话」，但是否交给内核仍看 `qq.reply` 和 `privateAllow`（装配现在的「私聊只存不回」在没摘钳制时保持；摘了且 `qq.reply` 开着才回）。群仍按 `gate_modes`，默认试运行。

核验中途变不健康：只停发，不把档位改回试运行。计划会停在失败或未知，不会悄悄改成「试运行所以没发」。锁不再在自己手里（交出、或发现自己没持着）：立刻重新钳制，发送次数回到 0。这和核验不同——锁不在了，另一边可能要发。

启用条件里的「守卫不是 nil」「Check 不是 nil」写在**第一次允许真发的那个提交**里。后面的提交只提供守卫和 Check 的实现。撤掉实现以后，这两个仍是 nil，启用条件失败，不会留下「能真发但没有守卫 / 没有暂停检查」的版本。

### 5.2 Bun 和 Go 不能同时对同一个号发送

> 2026-10-28 ADR-203：Bun 退役，Bun 那边的抢锁（第十一节第 4 步）不做、不合（做好的在 claude/snd-4）；Go 侧照下面的写法持锁，用来防有人又把 Bun 开起来。下面讲 Bun 的部分留作历史。

规格-QQ渠道九点五：同一个号同时只给一边用，两边都连着就会各回各的（`:180`，ADR-007 的对象当时是 MaiBot）。Bun 和 Go 现在可以同时连 `ws-default` 收包（装配第十节；issue #8 的 2026-10-28 回复说录帧时两边都收全了）。收可以并存，**发不行**。

一份 JSON 挡不住。`daemon/plugins/onebot.ts:116` 的 `call` 直接转给 `client.call`，没有第二道开关。Bun 若在文件还不存在时已经启动，之后改文件不会让它停收、也不会等在途的 `call` 结束。先把 `holder` 改成 `bun` 再停 Go，中间两边都能发。

（我定的）互斥用操作系统的独占文件锁，加上固定的交接顺序。意图仍用 JSON，但 JSON 不授权发送。另一种是本机再跑一个互斥服务，代价是多一个要看护的进程。不选。只在文档里写「开 Go 之前先停 Bun」也不选：忘一步就会双发。

- 锁路径：`<数据目录>/go/qq-sender.lock`。要发的那一边在整个「可以发」的寿命里持有独占、不共享的锁（Windows `LockFileEx`），句柄不关就不放。拿到锁之前不调用任何发送类 action。
- 意图文件：`<数据目录>/go/qq-sender.json`。字段只有 `account`（这个小号）和 `holder`（`bun` 或 `go`）。默认文件不存在：当成 `holder=bun`。它只表示主人想把发送权给谁。
- 锁文件的内容是交接记录，不是锁本身。字段：`protocol`（整数；会抢这把锁的这一版写 **1**）、`account`、`holder`、`state`（`holding` 或 `released`）、`pid`、`releasedAt`（放锁时的毫秒时间，持有时没有）。
- 要发的一边：先抢到独占锁，把 `state` 写成 `holding`、`protocol` 写成 1、`holder` 写成自己，然后才允许发送类调用。
- 交出：先停收新的发送类调用；等在途的那些调用结束，上限 **15 秒**（10 秒的 `callTimeout` 再加 5 秒）。到点仍不回的不再新发，把这一次算结果未知。然后把 `state` 写成 `released`、写上 `releasedAt`，**然后**才关句柄放锁。不许先放锁再等在途。
- 接过：看到 `protocol == 1` 且 `state == released` 且 `account` 是这个号，自己抢到锁，再写成 `holding`。抢不到就不发。Go 在 `qq.goSend=true` 但抢不到锁、或记录不是 protocol 1 时：保持钳制，可以继续收包，发送次数为 0，提醒一次，键 `qq:<号>:lock`，标题「QQ 发送权没有交过来」。不退出进程（退出会把收也停了）。
- 发送类动作只算这五个：`send_group_msg`、`send_private_msg`、`send_msg`、`group_poke`、`friend_poke`。`get_login_info`、`get_status` 不算。（我定的）不把所有 `call` 都锁上。另一种是凡 `call` 都抢锁，代价是查询也被交接挡住。不选。
- **切回 Bun**：Go 先停发、等在途、把记录写成 `released` 并放锁，确认没有发送类调用在途，**然后**才把意图文件的 `holder` 改回 `bun`，Bun 才可以抢锁。不许先改 `holder`。
- Bun 侧认这把锁，是启用 Go 发送的**硬前置**，不是上线以后再补的一步。没做、或正在跑的 Bun 不是会写 `protocol: 1` 的那一版：Go 不摘钳制。这是对 ADR-180 的一处例外，第七节第 3 问点头才改 Bun 的代码。
- 这把锁挡得住「两边都会抢锁」的进程。挡不住有人手工把 `protocol` 写成 1，同时一个不会抢锁的旧 Bun 还在发。那种情况记在已知的坑里，交接时由主人确认旧进程已经退出（第七节第 1 问），不写成锁已经证明了。

**锁的细节（2026-10-28 补，我定的；Bun 第 4 步动手前查出这几处没写死，两边必须一字不差）**：

- 锁的字节范围：`LockFileEx(LOCKFILE_EXCLUSIVE_LOCK | LOCKFILE_FAIL_IMMEDIATELY)`，偏移 2^62（`OffsetHigh = 0x40000000`、`Offset = 0`），长度 1 字节。锁在文件内容之外，别的进程照样能读交接记录；不锁 0 起的范围（会挡住读记录）。
- 打开方式：两边都用 `CreateFileW(GENERIC_READ | GENERIC_WRITE, FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE, OPEN_ALWAYS)`。只读记录的一方用同样的共享方式只读打开。
- 写记录：只有持锁的一方写，用持锁的那个句柄原地写：截断到 0 → 整段 JSON 一次写入 → `FlushFileBuffers`。不许"写临时文件再改名"（改名会换掉被锁的文件）。读的一方解析失败（读到写了一半）就隔 50 毫秒重读，最多 3 次，仍失败按"记录不是 protocol 1"处理。
- JSON：UTF-8、不带 BOM；`account` 是**字符串**（十进制数字）；`pid` 是整数；`releasedAt` 是整数毫秒，持有时不写这个键。
- 交出的触发：①后台正常关闭时走交出（停收 → 等在途 ≤ 15 秒 → 写 released → 关句柄）；②Bun 另有本机接口 `POST /api/qq/sender/release`（只认主窗口，返回交出结果）。Go 这一版只有①。被强杀时不写 released，锁由系统在进程退出时放掉；接过的一方看到 `state` 仍是 `holding` 而锁抢得到时分两种：记录里的 `holder` 是**自己**、意图文件也指向自己（上一次就是自己在发，崩溃或断电后重启），直接接过、写成 `holding`，日志记一行"上次没正常交出，接着发"——中间没有另一边插进来，不该让日常回复停住；`holder` 是**另一边**，按"上一个持有者没正常交出"提醒一次，**不发**，等主人确认（不把另一边被强杀当成交出）。（2026-10-28 改：原来两种都不发，Bun 第 4 步做完时发现电脑重启、Bun 崩溃后会一直不回 QQ，我改的。）
- 顺序以本节正文为准：停收 → 等在途 → 写 `released` → 放锁。

锁文件和意图文件都不含令牌。日志不写号的全文，也不写 pid 以外的机器信息。

**第一次接管（ADR-216，2026-10-30 加，我定的、暂定）**：Bun 第 4 步不做以后，旧 Bun 不会写交接记录，现在的 `Take` 没有记录就拒绝，Go 没法自己起头。加一个一次性的宿主手续（不在模型能调的工具里，只能由主人在诊断入口显式触发）：

1. 先核对：Bun 后台进程不在、`127.0.0.1:7720` 连不上、看门脚本和计划任务不会把 Bun 拉起来，三样都确认才往下走，任一样认不准就停；
2. 意图文件写 `go`，交接记录写 protocol 1、`holder: go`、`state: released`，另加 `origin: first-takeover`、时间和核对结果，表示"首次接管、不是 Bun 交出"；不写成 Bun 释放过；
3. 之后照常 `Take`。已经有交接记录（任何 holder）时这个手续拒绝执行，不能拿它覆盖正常交接。

测试：三样核对各缺一样都拒绝、文件不变；已有记录拒绝；成功以后 `Take` 拿得到、记录里能看出是首次接管。

## 六、发送前守卫、字数、通道门、第一条失败

字数在裁决里。守卫有两处调用：回合裁决，和复读插件。通道门的暂停接在出口的 `Check` 上，不接在「只给闸门看的 `Paused()`」上。适配器不重复做这三样。

### 6.1 字数保险丝

改写以后按整句码点，超过 `MaxChars`（默认 200，`respond.go:103`、`:201-202`）就拦下，记「保险丝」，在拆条之前（`settle.go:8`、`:156-159`）。试运行也拦。复读按原段重发，不做这道保险丝（规格-渠道中间件 10.1，插件发的不做第 3 步）。本地会话同样走回合这道（已有），本规格不改数字。

### 6.2 守卫

`CheckOutbound` 在记忆包里**还没有实现**（`native/internal/channel/guard.go:4`；`respond.go:83` 写明 nil 就是不查）。回合签名以渠道接口为准：`CheckOutbound(ctx, text, audience) (blocked []string, err error)`（`guard.go:20-21`）。调用点在 `settle.go:273`，拼句是中间件的事（`settle.go:9-10`：本回合前面已经放行的句子接在前面），记忆包只看拿到的整段字。

**没点头之前的启用条件**是规格-记忆-v2 13.2.8 的三步都在：字面、嵌入相似度、小模型确认。复读免掉小模型那一步，字面和相似度仍要过（ADR-187 第 7 条，规格-渠道中间件 10.5）。三步没接上，就和 nil 守卫一样：**不摘钳制**。不许把「还没做相似度」报成 `embed-down`。`embed-down` 只表示嵌入服务挂了或超时（`guard.go:33`，ADR-186 第 4 条），那种时候字面没比中的可以照常发，并且按已有规矩提醒一次。没实现和挂了是两回事。

第七节第 4 问若点头先上字面：才允许启用，并且运行中的路报 **`literal-pending`**，不报 `embed-down`，也不报 `normal`。提醒一次，键 `guard:literal-pending`（和 `guard:route` 分开，免得和「嵌入坏了」混成同一条），正文写「发送前检查这一步只比对原文，相似度还没做，不是嵌入服务坏了」。恢复成三步是 W8 的事；W8 接上并从 `literal-pending` 回到 `normal` 时再提醒一次。没点头就不要实现这条路的放行。

（我定的）启动时看 `GuardLevel()`，不看 `GuardRoute()`。`GuardRoute()` 是「刚才那次判断走的路」（`guard.go:24-27`），进程刚起来还没有「刚才」。`GuardLevel()` 返回 `full`（字面 + 相似度 + 确认都接上了）或 `literal-pending`（只有字面）。没这个方法、或返回别的值：不能启用。`literal-pending` 只有第七节第 4 问点头以后才算允许启用。另一种是在配置里加一个「允许只做字面」的键，代价是键和代码能力会各说各的。不选。

字面这一步的口径（不论是 `full` 的第 1 步，还是点头以后的 `literal-pending`）：对方不该看的记忆里，去掉空白和标点以后，连续 `min(10, 记忆长度)` 个字出现在要发的字里 → 拦。记忆去掉标点后不足 6 字的跳过。照 13.2.8 第 1 步、Bun 的 `leakedBy`。

- `qq.goSend == false`（还在试运行）也跑检查：试运行照样过守卫（规格-渠道中间件 10.4「试运行的回合」）。拦下的不存原文。没摘钳制时允许守卫是 nil，和现在一样，但日志写明「没接守卫」。摘钳制以后不允许 nil。
- 本地私聊的听众能看全部记忆，规格-记忆-v2 13.2.8 写明不经过这道守卫。本地群聊按听众算；本规格不改本地出口。
- QQ 群，回合回复：`OwnerAsked == true`（触发这一轮的是主人）时，主人自己的事在允许范围内，字面比中也不拦（ADR-174；13.2.8）。QQ 群友触发的（`OwnerAsked == false`）比中就整句拦下。
- QQ 私聊：对方不是主人时，主人的私事按不允许的范围查。对方是主人（`PrivateOK`）时允许范围包含 owner，字面比中不拦。
- 守卫返回错误或整体超过 10 秒（`respond.go:104`、`:204-205`）：整句拦下，reason「守卫没判成」，不重试（`settle.go:10`）。这不是通道门的「明确失败」，不调用 `PartEnded`。

**复读不走回合。** `Repeater.intercept` 在掷中概率以后直接 `Out.Send`（`repeat.go:268`）。`SendHeld` 自己没有文字守卫；`Check` 只接通道门和风控（`outlet.go:86-88`）。「复读不用模型」不是豁免：ADR-187 第 7 条、规格-渠道中间件 10.5 要求复读的字过比原话和相似度。

- 调用位置：`repeat.go:268` 的 `Send` **之前**。同一个 `Guard`。拦下或没判成：不调用 `Send`（`Send` 会把这句话写进 events）。改调 `Outlet.Record`，来源 `automation:repeater`，kind 为拦下，reason 只写「守卫拦下」或「守卫没判成」，不含原文、不含命中的那几个字（`outlet.go:540-541`：Record 不写 events、不存原文）。不 `markFollowed`（`repeat.go:273`），因此不记冷却，库里也不出现 `origin = automation:repeater` 的消息。返回 `Passed`（`repeat.go:269-271` 已经是「没发出去就不算接了」）：这一批仍可交给闸门，不能因为复读被拦住就让她这一轮哑巴。模型若接着回，走回合那道守卫。
- 听众从哪来：复读的 `Batch` 没有 `Audience`（`types/intercept.go:45-64`）。宿主注入 `Audience func(conv) (audience.Audience, error)`。函数是 nil：不 `Send`，`Record` 一条拦下，reason「守卫没有听众」。QQ 群的听众是 `Channel=qq`、`Scene=group`、`PrivateOK=false`、`FullMemory=false`、`PersonIDs` 空。`OwnerAsked` 在第七节第 5 问没定之前按 **false**（收紧：比中就整句不跟）。不从「这两句里有没有主人」抬成 true。
- （我定的）免掉小模型用可选接口 `RepeatGuard`：`CheckRepeat(ctx, text, audience) (blocked []string, err error)`，只做字面和相似度。守卫实现了就走它；没实现就走完整的 `CheckOutbound`（比 ADR-187 更严，可能多一次确认调用，不因此放行）。`GuardLevel()` 为 `literal-pending` 时（仅第 4 问点头以后）复读也只有字面，这比 ADR-187 第 7 条窄，所以同一问一起点头，不能单独放行。另一种是给 `CheckOutbound` 加 origin 参数，代价是改 `guard.go:21` 和现有的假守卫。不选。
- QQ 私聊没有复读。戳回去没有字，不过文字守卫，只过发送检查（ADR-187 第 6 条；`qq/poke.go:103` 走出口的 poke 段）。通知里的会话和做事的人可以对不上（会话取 `target_id` / `peer_id` 落在主人的私聊，做事的人取 `user_id`、没有时取 `operator_id`，可能是别的号，也可能是空：0 一类的号归成空，ADR-221），戳回去戳的是做事的人；所以 `app/channel.go` 的 `limitQQPoke` 在私聊里还要求做事的人等于会话对方，不等就只存不戳回（2026-10-31）。

### 6.3 通道门要接到发送，不只接到计数

`OnPart` 接 `gate.PartEnded`（`gate.go:789-813`）。连着 3 段明确失败暂停（`defaultPauseAfter`，`gate.go:56`）。结果未知、已中止、守卫拦下、字数拦下都不算。中间一段确认就清零；回声确认也算这段确认（6.4）。

`PartEnded` 暂停的是闸门放行（`gate.go` 里 `channelPaused` 的那两处）。它挡不住已经在闸门前面的复读和戳回去，也挡不住不过群闸门的 QQ 私聊。通知批只跑拦截链、不交闸门（`pipeline.go:132-147`）。

装配必须把 `OutletConfig.Check` 设上。说话档每次 `Send` / `SendHeld` 都会调它，而且在写库之前（`outlet.go:462-465`）：没过就返回 `ErrSendCheck`，不写计划、不写事件、不进队列。试运行不调 `Check`（同一处：只有 `PlanKindSend` 才查），试运行本来也不出 action。

`Check` 的这一步只做通道门：`gate.Paused("qq")` 为真，且这次会话的渠道是 `qq`，就返回错误，原因带暂停理由、不带原文。风控间隔仍按规格-渠道中间件以后的步，这里不新造间隔。戳回去（`poke.go:103-107`）、复读（`repeat.go:268-271`）、回合的 `SendHeld`（`settle.go:192`）都已经把 `Send` 的错误当成没发出去。暂停时走这条，不另写一个「看到 Paused 就 return」的旁路。

`Check` 是 nil 时出口当不查、直接发（`outlet.go:529-530`）。所以 nil 不能和「已摘钳制」同时存在（5.1 第 6 条）。

暂停时 `OnPause` Raise：键 `qq:<号>:send`，标题「暂停了 QQ 发送」。恢复（连接上报 `StatusConnected` 已有的 `gate.Resume`，或主人以后在界面上点）时 Clear。`Check` 在 `Resume` 之后不再拒绝。

### 6.4 第一条发不出去，以及回声确认也要通知

（我定的）和「连着 3 段才暂停」分开。一段用完重试仍是明确失败，就 Raise 一次：同一个键 `qq:<号>:send`，标题「有消息发不出去」（方案 C3）。还没到 3 段时标题是这一句；到了 3 段改成「暂停了 QQ 发送」（同键换标题，不叠两条）。之后的失败不再 Raise，直到这个键被 Clear。Clear 的条件：后来有一段确认（回包或回声），或 `Resume`。结果未知不 Raise（不知道发没发出去，不算「发不出去」）。

回包确认和回声确认都进**同一个** `OnPart`，每一段只进一次：

- 回包确认：现有的 `partResult(..., true)`（`outlet_run.go:183-186`）保留。
- 回声确认：`ClaimEcho` 把段转成确认并 `wakeFlight` 之后要补上这次通知。`sendPart` 在 `callWoken` 里看到段已经是确认时，若这一段还没通知过，调 `partResult(..., true)`；已经通知过就不再调。回包后到、`end` 失败再走 `lost`（`outlet_run.go:188`）时，也不许再通知一次。
- 去重记在出口，按段号。不记在闸门上：`PartEnded` 没有「这一段来过没有」（`gate.go:791-808`）。确认调两次只是把失败数清零两次，眼下碰巧无害；明确失败若调两次就会少算或多算。一律一次。
- 装配的 `OnPart` 里：确认就 `PartEnded(channel, true, false)` 并 Clear 键 `qq:<号>:send`；明确失败且用完重试就 `PartEnded(channel, false, true)` 并按上面的规则 Raise。不要为回声再写一套会计数的回调。

提醒走装配已有的 `alert` 和 QQ 库 `qq_alerts`（只写 title / body，不写原文，不写号）。系统通知等 mygo，不在这一步。

## 七、要主人定的

> 2026-10-28 已定（ADR-200）：第 2 问群已定（只记在 data 里，句子没定）；第 3 问破例、按建议的范围；第 4 问**不先只做字面**，相似度做完再开发送；第 5 问不算主人在问。第 1 问没定。

1. **哪一天把这个小号的发送权从 Bun 改成 Go，并且当时跑着的 Bun 是不是会抢锁的那一版？** 例子：周二晚上你先确认旧的 Bun 进程已经退出，只留会抢 `qq-sender.lock` 的那一版；让它停收发送、等在途的 `call` 结束、放锁；然后才把 `qq-sender.json` 的 `holder` 改成 `go`、`qq.goSend` 改成 true，让 Go 去抢锁。不要先改文件再指望已经启动的旧 Bun 自己停。在你点头之前，Go 不摘钳制。这是 ADR-197「第 7 步做完说一声就开」的那一声，不由规格代定日期。锁发现不了「文件被手工改成 protocol 1、旧 Bun 仍在发」。
2. **真机验收在哪个群、发哪一句？** 例子：只在群 A 把档位改成「说话」，让她回一句你事先写好的「在的」，别的群保持试运行；QQ 私聊先不打开 `qq.reply`。规格不指定群号和句子。没点头就不连真机发。
3. **Bun 冻结要不要为这把锁破一次例？** 例子：这个小号的 `send_group_msg`、`send_private_msg`、`send_msg`、`group_poke`、`friend_poke` 在调用前抢同一把独占锁；交出去之前先停收、等在途结束再放锁。没点头就不改 Bun，Go 也不摘钳制——不能只靠你记得先关连接。我的建议是改，范围只限「抢锁、这个号的发送类 call 没锁就不发、交出前等在途」。
4. **发送上线能不能先只做字面检查，相似度和确认留到 W8？** 例子：不该让群友看的记忆是「主人下周三上午去医院复诊」。她回「他周三早上要去医院再检查一次」，去掉标点后没有连续十个字相同，字面检查放行，换了说法的私事就出去了。ADR-181 第 3 条是三种方法量完再定用哪种；ADR-186 第 4 条的「只比原文」只覆盖嵌入挂了或超时，不覆盖「还没做」。没定之前，守卫不是 13.2.8 的三步（复读再按 ADR-187 第 7 条免掉小模型、仍要相似度）就不摘钳制。若你点头先上字面，路报 `literal-pending`，不报 `embed-down`，提醒写「相似度还没做，不是嵌入坏了」；复读同样只有字面，直到 W8。
5. **复读时，两句里有一句是主人发的，算不算主人在问？** 例子：主人在 QQ 群里打出一句只有他和她知道的事的原话，另一个群友跟着打了同一句，复读概率命中。若算主人在问（`OwnerAsked` 为真），守卫按 ADR-174 不拦，她会把这句再发一遍，群友又看见一次。没定之前按假：比中就整句不跟，不调用 `Send`。我的建议是按假。

- **ADR-180**（已被 ADR-200 第 1 条改为：为这把锁破例，只限抢锁、没锁不发、交出前等在途）：Bun 只修日常 bug。5.2 要 Bun 抢锁并在交出前等在途的发送结束。未点头之前不改 Bun；Go 侧即使 `qq.goSend=true` 也不摘钳制。
- **规格-渠道中间件第二十节第 4 条**写 `get_login_info` / `get_status`「没核实」。本规格按 SL `8ffd314` 的 `info.ts` 改为「源码有；本机回包仍要假端测试，真机等主人点头」。不改那份规格的句子，实现时由主会话加一行「已被本规格改为……」。
- **规格-渠道中间件第 474 行**：本规格不放宽「`retcode` 等于 0 才算成功」。和 Bun `client.ts:161`（缺省 `retcode` 可以成功）不一致的地方，以第 474 行为准，不记成新的放宽。
- **ADR-181 第 3 条 / 规格-记忆-v2 13.2.8**（ADR-200 第 3 条：不推迟，相似度做完再开发送）：三种量完再定，W8 才把选中的那种接上。本规格没把「先只做字面」写成已定。第七节第 4 问点头以后才会在量完之前先用甲，那是对 ADR-181 第 3 条的推迟，所以放在要主人定的，不放在这里当规格已经改了 ADR。没点头就不冲突：不摘钳制。

- **ADR-187 第 7 条**：复读要过字面和相似度。第 4 问没点头时，缺相似度就不能启用，包括复读。点头以后复读会暂时只有字面，这比第 7 条窄，同一问覆盖，不单独开例外。

## 九、禁止的偷懒写法

- 不许不带 `echo` 就当成功，也不许把超时当成明确失败然后重发。不许 `retcode` 缺省就当确认。
- 不许 `message_id > 0` 才认文字。负数是合法的（SL `message.ts:187`）。不许戳一戳因为 `data` 是 `null` 就当成没成功或再重发。
- 不许号对不上仍发，不许用帧里的 `self_id` 填配置的号来「对上」。不许把心跳当成 `good` 已经恢复。
- 不许在 `qq.goSend` 默认值上做成 true。不许把 `qq-sender.json` 的 `holder` 当成已经互斥。不许没有 protocol 1 的交接记录就摘钳制。不许先改 `holder`、再停还在发的那一边。
- 不许守卫没接上、或 `Check` 是 nil，还摘钳制。不许只在 `Responder` 上接守卫、复读直接 `Send`。不许撤掉守卫或 `Check` 的实现以后，启用条件还认为可以真发。
- 不许没实现相似度时把路报成 `embed-down` 并照常发。
- 不许把拦下的句子原文写进计划、日志、`qq_alerts`。不许复读被守卫拦住以后还写一条 `automation:repeater` 的事件。
- 不许为了真机验收自己选群、自己发一句。
- 不许改 SnowLuma 的配置和数据（AGENTS 安全边界）。

## 十、已知的坑

- **② 判断单位**：字面检查看的是「本回合已经放行的句子 + 这一句」（`settle.go:9`）。只测单句会让拆开的私事漏过。复读不拆条，整段原样查。
- **③ 兜底**：核验超时不能当成号对了；`get_status` 缺 `good` 不能当成健康；心跳不能当成恢复。不认识的 `retcode`、缺省的 `retcode` 不能当成失败重发，也不能当成成功。
- **⑤ 两个号**：认领键带账号（`outlet_echo.go:14`）。测试要有「另一个号的同文字回声不认」。
- **⑩**：一段确认、一段失败、一段未知要落在三个状态上，不能合成 `partial`。第一条提醒只挂明确失败。回声把未知认领成确认，算确认，不算又一次失败。
- **⑬**：回声先到、回包后到，只发一次（出口已有测试，适配器接上以后用假协议端再跑一遍，不能只调 `Send` 的单测）。`OnPart` 也只通知一次（6.4）。
- **⑭**：Bun 仍在写它自己的库。Go 只写 `data/go/`。锁文件和意图文件是两边都读的新文件，不在 Bun 的库里。
- **⑱**：`retcode` 与 `status` 分开判（第三节）。本机 SnowLuma 版本可能旧于 `8ffd314`（issue #8：仓库只证明曾用 2.0.2）。假端按本规格的表测；真机回包和这份表不一致就停发，回来改规格，不在适配器里加「看不懂就当成功」。
- **㉑**：日志和提醒不出现 QQ 号全文、令牌、聊天原文、被守卫命中的那几个字。
- **交接**：独占锁挡不住不会抢锁的旧进程。验收用两个都会抢锁的进程；「旧 Bun 还在」靠第七节第 1 问由主人确认进程已经退出，不写成测试已经覆盖了未改的 Bun。

## 十二、验收

上面第 1～7 步的测试都在，每条断言先改坏一次会红。号、群号、句子用编的。

1. 假端整条路径：核验通过、锁是 Go 持有、交接记录 protocol 为 1、`qq.goSend=true`、守卫和 `Check` 都在、一个群是说话 → 恰好一条 `send_group_msg`，`channel_msgs` 里的号和回包一致；回声先到时 action 不发第二遍，且 `OnPart` 只通知一次。另一个群仍是试运行。QQ 私聊在 `qq.reply` 关闭时不发。本地会话的测试不出现 OneBot 帧。
2. `qq.goSend` 缺省或 false，或只有 JSON 把 `holder` 写成 `go` 而没有锁：适配器发送次数为 0，哪怕库里该群是说话。两个都会抢锁的进程交错时，同一时刻发送类 action 只有一边在发；先改 `holder` 再放锁的那一侧发不出去。
3. 守卫拦下的句子不在 `events`、不在日志、不在提醒里。复读命中时同样没有复读事件。
4. 暂停之后，戳回去、复读、QQ 私聊的发送次数都是 0。不是只看 `Paused()`。
5. 撤掉第 6 步的守卫实现（生产上 `Guard` 回到 nil）以后，即使 `qq.goSend=true`、锁和群档都在，发送次数仍为 0。
6. `go test` 跑过适配器包和 `internal/channel` 里这一步碰到的测试。不把假端通过写成真机通过。
7. 真机只在第七节第 1、2 问都有主人的当次同意、并且第 3 问允许改 Bun 以后做。第 4 问没同意时，真机用的守卫必须是 `full`，不能是 `literal-pending`。同意里要能看出是哪个群、哪一句。
