> 2026-11-16 整理：P2-3 要扩展；第 0、7 步和独立复核仍未做。
> 状态：第 1～6 步已实现（2026-11-13）；第 0 步（在真实库的只读副本上量阈值）、第 7 步（改巡检）和独立复核没做。阈值仍是**暂定**，配置 `selfcheck.*` 可调；实现中和本规格不一致的地方见第十五节。2026-11-15 加 S13（嵌入起不来），见第三节。

> 和 [规格-日志分级](规格-日志分级.md) 配套：自检的提示走 `selfcheck` 模块的 WARN 行。
> 名字注意：`native/internal/app/desktop_selftest.go` 的“自检”是 `sumika-ctl chat` 的开发对话（ADR 里的“自检会话”），和本规格无关。代码包叫 `selfcheck`，界面写“运行自检”，不要混用。

## 一、要解决什么

现在查有没有出问题，靠巡检 Sonnet 子代理在日志末尾 300 行里 grep（`SKILL.md` 第 17 行）。这有三个毛病：

1. **只看得到文字**：收到未入库这类事没有任何一行专门记它，要靠“看起来不对”去猜。
2. **没有基线**：今天 3 次“连不上”是正常还是异常，没有一个固定口径。
3. **断了就没了**：看门狗拉起以后，前一次进程的情况只剩崩溃记录。

本规格要做的是：桌面程序自己数几条**守恒关系**和**卡住的东西**，每天写一个小文件，状态行和巡检读它。它**只读、只记**：不补录、不重试、不清理、不重启、不发通知。

## 二、参考

- 守恒式（收到 = 入库 + 每一种明确的丢弃之和）：本仓库自己的 `channel` 准入和去重路径已经分了这几类（`intake.go:233/299/316`），本规格只是把它们加起来核对。不采用全量指标库（Prometheus 式的标签爆炸），量太小、只要几个数。
- 看门狗心跳（`watchdog/heartbeat.go`，ADR-365）：“进程还活着”的判断靠它，自检不另外做心跳。
- 运行质量标签（`runstats/quality.go`、`ctl_stats.go:119`）：失败率的口径直接复用，不另写一份。
- 用 `trace.db` 的表做只读查询，不新建表（理由见第四节）。

## 三、不变量（选 8 条，其余列入第十节；2026-11-14 加了第 9 条 S9，2026-11-15 加了第 10 条 S10、第 11 条 S11（MCP 隔离）、第 12 条 S12（备份抽验）和第 13 条 S13（嵌入起不来），见下）

每条写：含义、埋点（读哪里、数哪里）、判定、阈值（暂定）、误报来源和怎么压。埋点位置来自 2026-11-13 的盘点，**行号是盘点时给的，第 1 步开工前逐条复核**。

### S1 `intake.unaccounted` 收到的 QQ 消息没有去向

- **含义**：每个从协议端收到的消息帧，都有一个结局：入库、重复（补录与实时重叠）、准入丢弃、关闭时丢弃、解码失败、非消息帧。
- **埋点**：计数 `received`（`channel/snowluma/connect.go` 收到帧、解码之前，约 :540 附近）；`stored`、`duplicate`、`admitDropped`、`closedDropped`（`channel/intake.go` 约 :233、:299、:316 的各分支）；`decodeFailed`（`connect.go:544`）；`nonMessage`（翻译成“不是消息”的分支）。
- **判定**：在**空闲点**（入库队列为空、在途写为零，见第五节“静默点”）算：`received − (stored + duplicate + admitDropped + closedDropped + decodeFailed + nonMessage)`。差额不为 0 即异常。
- **阈值**：差额 ≥ 1，连续两次评估都是才报（10 分钟）。
- **误报来源**：在途消息（用静默点压掉）；补录与实时重叠（归入 `duplicate`，不算差额）；协议端发的非消息事件（归入 `nonMessage`）。
- **例子字段**：最近一次差额出现时的通道号和时间（不带消息内容）。

### S2 `intake.store_failed` 入库失败

- **含义**：消息已经收下，但写库失败，消息没进库。
- **埋点**：`channel/intake.go:316` 入库失败分支，计数 `storeFailed`，同时记最近一次的错误类别（不记错误原文，原文可能带内容；只记 `SQLITE_FULL`、`SQLITE_BUSY`、`other` 之类的类别）。
- **判定**：当天 `storeFailed ≥ 1`。
- **阈值**：1（写库失败本来就不该有）。
- **误报来源**：几乎没有。一次性的 `SQLITE_BUSY` 也要看到，所以阈值不设 2。

### S3 `outlet.receipt_unknown` 发送无回执（当天次数）

- **含义**：发出去的消息，等不到回声，按“结果未知”收场。
- **埋点**：`channel/outlet_echo.go:396`（gaveUp 分支），计数 `receiptUnknown`，按日。
- **判定**：当天 `receiptUnknown ≥ 阈值`。
- **阈值**：暂定 3 次 / 天。第 0 步要用真实发送记录看一周的基线。
- **误报来源**：真人手动发了同样的文字，回声认领失败；协议端慢。两者都会让次数偏高，所以阈值不设 1。

### S4 `turn.stuck` 回合卡住

- **含义**：回合开始了，既没有结局，也不在运行中，也不是在等主人批准。
- **埋点**：只读查询 `trace.db` 的 `turns`（`store/turns.go:60` 写 outcome 和 ended_at 的那一张）；运行中的回合 id 来自 `watchdog/heartbeat.go` 的 `RunningTurns`（进程内读，不查库）。
- **判定**：`ended_at IS NULL AND started_at < now − stuckMinutes`，并且 `turn_id` 不在 `RunningTurns` 里，并且**不在等审批**（判断方法见第十一节“待核实”）。
- **阈值**：`stuckMinutes` 暂定 30。阈值以上的每个回合计一次，同一个回合只计一次（按 turn_id 记在已报表里）。
- **误报来源**：长工具调用（要在 RunningTurns 里，不会误报，但进程重启后回合没有 RunningTurns 项，靠 `ended_at` 已被 `hub.go:260` 写成 interrupted 排掉）；停在审批卡上（排除）。

### S5 `channel.reconnect_storm` 重连风暴

- **含义**：协议端连接在很短时间里反复断开、重连。
- **埋点**：`channel/snowluma/connect.go:219`（连不上）和 `:259`（断了）各计一次“断开事件”，进一个 10 分钟的滑动窗口（环形数组，不分配）。
- **判定**：窗口内断开事件数 ≥ 阈值。
- **阈值**：暂定 6 次 / 10 分钟。
- **误报来源**：网络抖动；协议端升级重启（重启本身断一次，窗口里几次正常）。压法：阈值用“断开事件”而不是“重试次数”，一次断开里的多次退避只算一次。

### S6 `memory.compact_failed` 压缩写入连续失败

- **含义**：记忆压缩（上下文压缩写 `context_epochs`）连续几次没写成。
- **埋点**：只读查询 `events` 库的 `context_epochs`（盘点：在 events 库，`store/write.go:344` 写入）。取每个角色最近 N 条的 `status`。
- **判定**：同一角色最近 3 条的 `status == failed`，并且 `failed` 的原因不是“摘要被校验挡下”（那是正常拒收，要看原因列；**原因列是否存在要第 0 步核实**，不存在就先只看连续 failed 的条数并在状态里注明“不分原因”）。
- **阈值**：连续 3 条。
- **误报来源**：摘要被校验挡下（正常拒收，要排除）；一个角色很久没说话（没有新的压缩，不算失败）。

### S7 `model.stage_failing` 后台模型同一阶段连续失败

- **含义**：同一个 stage（守卫、总结、识图、链接翻译等后台调用）最近几次全部失败。
- **埋点**：只读查询 `trace.db` 的 `model_runs`，取每个 `stage` 最近 K 条，看 `error` 和 `error_class`（`0014_run_error_class.sql`）。
- **判定**：同一 stage 最近 K 条的 `error` 都非空，并且 `error_class` 不属于 `not_configured`、`cooldown`（这两类是“没配”和“冷却中跳过”，不算失败；具体取值第 0 步核对 `llm/failover.go:48-59`）。
- **阈值**：K = 5。
- **误报来源**：没配模型（排除）；冷却期内的跳过（排除，`failover.go:48-59`）。

### S8 `events.seq_gap` 会话序号断号

- **含义**：同一会话的 `events.seq` 应该连续；断号说明有消息丢了，或者被重复写了。
- **埋点**：只读查询 `events` 库，**增量**：每次评估从上一次记下的水位（每会话最大 seq 的 rowid 或时间点，存在自检的状态文件里）往后扫。`store/write.go:118` 是写 seq 的地方，不改它。
- **判定**：水位之后的新行里，同一会话的 seq 不连续。
- **基线**：第一次运行时，对已有的历史只统计**历史缺口数**（写进状态里，不报警）。之后只报水位以后新出现的缺口。这一点是误报的主要压法：历史上可能有手工修过的洞，不能一上线就红。
- **阈值**：新出现的缺口 ≥ 1 报。
- **误报来源**：历史缺口（基线压掉）；迁移或手工导入（第 0 步要问主人有没有做过这类操作）。

### S9 `backup.daily_stale` 每天自动备份太久没成功（2026-11-14，R-386）

- **含义**：`backup.daily` 开着，却超过 26 小时没有校验通过的“每天”备份，说明备份悄悄坏了（目录不可写、磁盘满、库取快照失败、备份目录指进了数据目录……）。
- **埋点**：读备份调度器缓存的状态（`internal/backup` 的 `Service.Status`，app 经 `Env.Backup` 注入，自检包不 import `backup`）；评估时不扫目录。
- **判定**：没开每日备份 → ok；调度还没做过第一次检查、或这一份正在做 → unknown；最近一份好的在 26 小时内 → ok；否则：这个进程里有过失败的尝试且之后没成功、或者进程已经开了超过 26 小时还没做出来 → bad，其余（刚开机，等第一次机会）unknown——关机几天再开机时前几分钟不误报。
- **阈值**：26 小时（每天一份，留 6 小时给“有角色在回复就先等”）。例子里只放最近一份好的时间和失败的类别（`SQLITE_FULL` 之类），不放原文（原文带路径）。
- 细节和测试见[规格-数据目录与备份 10.6](规格-数据目录与备份.md)；`TestBackupFresh`。

### S10 `kernel.faulted` 内核停止受理（2026-11-15，质检 X-07、后续路线 P0-4）

- **含义**：回合内核有会话（或整个内核）因为状态写不进记录库而停止受理新输入。旧写法（`lc.err`）一次收尾写库失败就让所有会话永久拒收、界面和自检都看不出来；现在故障只挡出事的会话，并且在这里可见。
- **埋点**：读回合内核现在没解除的故障（`turn.Hub.Faults()`，app 经 `Env.Faults` 注入，自检包不 import `turn`）；故障只在内存里，每次评估现取。
- **判定**：没接 → unknown；没有故障 → ok；有任何一条 → bad，`value` 是故障条数，例子里放最该先看的一条：`scope`（conversation / kernel）、`conversation`、`kind`（run_state、activity_end、requeue、startup_recover、startup_sweep）、`since`、`errorClass`（只放类别，不放原文）、`tries`（已重试次数）。
- **解除**：`sumika-ctl kernel retry`（界面里的“重试”按钮还没做）；重试成功后下一轮评估回到 ok。没人认领的活动退出记录（压缩、检查点、记忆这类不属于前台运行的活动）没写进库时，状态仍是 ok，Note 和例子里的 `strayEnds` 给条数，`kernel retry` 一起重写。重试不会自动做；程序重启也会清掉故障，重启时的恢复本来就会核对整库。
- 规则和类别见[回合内核开发指导](开发指导/回合内核.md)第 8 条和[运行时参考](subsystems/runtime.md)；测试 `TestKernelFaultedCheck`、`TestFaultOnlyBlocksTheFaultedConversation`。

### S11 `mcp.quarantined` 有 MCP 服务被隔离或断了没重连上（2026-11-15，质检 X-08）

- **含义**：有 MCP 服务因为一次已发出的调用没有结果（超时、被停止、断线、程序当时被关）被隔离，或本机服务断了、自动重连用完次数。两种都是“这个服务现在用不了、自己不会好”。
- **埋点**：app 经 `Env.MCP` 注入：读调用留痕里挡着的行（`kernel_mcp_calls` 的 dispatched、unknown，自检的只读连接）加 MCP 客户端的重连状态；自检包不 import `mcpclient`、`store`。本进程正在进行（11 分钟内）的调用不算。
- **判定**：没接 → unknown；读失败 → unknown；一个都没有（或没启用 MCP）→ ok；否则 bad，例子里放服务名、最早一次的时间、原因（固定词）。备注写怎么处理：`sumika-ctl mcp status`、`mcp release`、`mcp reconnect`。
- **阈值**：1 个服务。解除或重连成功后下一次评估恢复 ok。测试：`TestMCPQuarantinedCheck`、`TestMCPQuarantineSurvivesRestartAndReleaseReopens`。

### S12 `backup.drill_stale` 备份抽验太久没通过或最近一次失败（2026-11-15，质检 X-01、后续路线 P1-1）

- **含义**：每周自动抽验（把最新一份好备份真的恢复到备份目录旁边的临时目录、核对、删掉，规格-数据目录与备份 10.10.4）超过 10 天没有通过，或最近一次抽验失败。S9 管“每天备份有没有做出来”，这一条管“做出来的备份能不能真的恢复”：有备份但从没演练过恢复，等于没有备份。
- **埋点**：读备份调度器缓存的抽验状态（`internal/backup` 的 `Service.DrillStatus`，app 经 `Env.Drill` 注入，自检包不 import `backup`）；评估时不扫盘。记录存在备份目录里的 `.drill.json`（最近 20 条），重启后读回来，所以按存下来的时间判，不按进程开了多久。
- **判定**：没接 → unknown；每周抽验没开（每日备份关着，抽验跟着它）→ ok，备注写关着、手动 `backup verify` 仍可用；调度还没读过记录 → unknown；正在抽验 → unknown，做了 `runMaxHours` + 1 小时（最多 26 小时）以上 → bad；最近一次抽验失败（且之后没有通过的）→ bad；最近一次通过在 10 天内 → ok；一份可以抽验的备份都没有、也从没通过过 → unknown（备份本身归 S9）；否则进程（或最近一次通过）已经超过 10 天还没有通过的抽验 → bad，其余（关机很久再开机的前几分钟）→ unknown。
- **只看计入的抽验记录**：别的数据目录的备份、不是最新一份好备份的手动抽验照记但不计入“上次通过”，也不让这一条变红或转绿（规格-数据目录与备份 10.10.4）；抽验临时目录删不掉、超时都记成失败，这里会报。
- **阈值**：10 天（每周一次，留 3 天余量给关机、角色在回复先等、失败后隔一天再试）；`Thresholds.DrillStale`，不挂配置键。例子里只放时间、哪一份备份的名字、失败的类别（`StoreErrorClass`），不放文件路径和原文。
- **下一步**（备注里写）：`sumika-ctl backup verify` 手动再验一次；还不过，说明最近的备份可能不能真的恢复，看 `sumika-ctl backup list` 和日志，必要时 `backup now` 重做一份。
- 细节、测试见[规格-数据目录与备份 10.10.4](规格-数据目录与备份.md)；`TestBackupDrillStale`、`TestBackupDrillStaleThresholdIsRead`。

### S13 `embed.unavailable` 嵌入起不来或后端已移除（2026-11-15，P2-4）

- **含义**：`embed.enabled: true`，但本机嵌入没就绪（缺 exe/dll/模型文件、模型 id 或 kind 不对、服务反复退出……），或者 `embed.backend` 还是已删的 `legacy`。嵌入起不来时记忆检索退回全文检索、发送前检查只剩原文比较，必须让人看得见。
- **埋点**：app 把 `embed.Local` 现在的状态（`Status()` 的 off / starting / ready / down 和原因）经 `Env.Embed` 交给自检；自检包不 import `embed`。缺模型时 `Local.checkFiles` 的原因里带它在找的完整路径（`<模型根>/_待分类/<模型>/model_quantized.onnx` 之类）。
- **判定**：没接 → unknown；`embed.enabled: false` → ok（故意的）；ready → ok；starting → unknown；legacy → bad；off / down → bad，`value` 1，例子里放 `status` 和原因第一行（含完整路径），备注写“记忆检索先只用全文检索，修好以后重启接收”。
- **阈值**：1（起不来就是异常，不设次数）。解除：按原因改配置或补文件后重启接收；`legacy` 改成 `go-models` 并把模型放到 `embed.modelsRoot`（空 = `<数据目录>/models`）。
- **误报来源**：启动头几分钟还在加载——starting 记 unknown，不当 bad。

## 四、存在哪里（每天一个 JSON，不进业务库）

**选 `data/selfcheck/<日期>.json`，每天一个，原子写（先写临时文件再 `fileatomic.Replace`）。** 理由：

1. **不动 trace 和 events 的表结构**：trace 迁移已到 `0021`，新表要占迁移号，还要过迁移测试；自检只需要几个数字，JSON 就够。
2. **巡检读得到**：进程没在跑时，巡检仍能读到当天最后一次写下的结果（文件里有 `updated` 时间，巡检据此判断“是不是自检没在跑”）。
3. **写的路径只有一个**：自检只写这一个目录，第十一节的“只读”测试好写。
4. **量很小**：每天一个几 KB 的文件，14 天后随日志清（`logs.keepDays`，见规格-日志分级第七节）。

文件内容（一个示例，字段名定死）：

```json
{
  "day": "2026-11-13",
  "updated": "2026-11-13T10:35:00+08:00",
  "running": true,
  "checks": [
    {"id": "intake.unaccounted", "state": "ok", "value": 0, "threshold": 1, "since": ""},
    {"id": "turn.stuck", "state": "bad", "value": 1, "threshold": 1, "since": "2026-11-13T10:05:00+08:00",
     "example": {"turn": "t-1234", "started": "2026-11-13T09:30:00+08:00"}}
  ],
  "counters": {"received": 8421, "stored": 8410, "duplicate": 9, "admitDropped": 2, "closedDropped": 0, "decodeFailed": 0, "nonMessage": 0, "storeFailed": 0, "receiptUnknown": 0, "reconnects": 0},
  "baseline": {"seqGapsBefore": 0}
}
```

- `state`：`ok` | `bad` | `unknown`（查询失败、文件读不了等，**不许记成 ok**）。
- `example` 只放 id、时间、通道号和文件:行号，**不放消息文字**。通道号和会话号经 `RedactLog` 打码（它本来就会把会话号里的群号、QQ 号打成 `***`）。
- `counters` 是当天累计的内存计数，每次刷新文件时一起写。

### 4.1 计数怎么续（重启）

- 计数只在进程内递增；每 5 分钟刷新文件，关机时再刷新一次。
- 进程启动时读当天的文件，把 `counters` 加载回来**继续累计**。这样看门狗拉起以后当天的数不会从 0 重新开始。
- 崩溃时最多丢最近 5 分钟的计数，不影响判定（判定只看“状态”，计数是证据）。文件里写 `updated`，巡检能看出这一点。
- 日期翻转：过零点后新建当天文件，计数从 0 开始，**不带昨天的**。

## 五、评估的时机和静默点

- 评估周期：每 `selfcheck.intervalSeconds`（暂定 300 秒）一次，启动后 2 分钟才开始第一次（让启动期的积压先走完）。
- **静默点**（S1 用）：入库队列为空、没有在途写、距上一条收到的帧超过 5 秒（实现：距上一条交来的消息超过 5 秒，并且 `Intake.Pending()` 为 0，见第 18 条）。不满足就跳过这一次判定（不算 ok，记为“未判定”，`state` 保持上一次）。
- 评估的读库用只读连接（第六节）；单次评估总时间上限 2 秒，超时的那条标 `unknown`。

## 六、只读（硬约束）

- **读库**：新增只读打开函数 `store.OpenReadOnly(path)`，URI 带 `mode=ro`，并执行 `PRAGMA query_only = ON`。`selfcheck` 包**只能**拿到这个函数返回的“只读接口”，接口里只有 `Query` 类方法，没有 `Exec`、事务写入。
- **写文件**：只写 `data/selfcheck/`。
- **不许**：调用 `alert.Hub` 的登记以外的任何方法（v1 不登记，第十一节）；发 QQ 或发通知；调用补录、重试、清理、重启；改业务表、改 events、改 trace 的任何一行。
- **不许的写法**（测试要抓住）：`selfcheck` 包不 import `store` 里的写接口、不 import `channel` 的发送包、`app` 的发送方法；用 `go list -deps` 检查依赖（`archcheck` 风格的测试）。
- 巡检子代理（在仓库外）只读这个文件，不跑任何写命令。

## 七、报给谁（三处，都是读取，不是动作）

1. **日志**：状态从 `ok` 变成 `bad` 时写一行 `WARN selfcheck 自检异常：<id> <名称>（值 N，阈值 M，例子 …）`；从 `bad` 变回 `ok` 写一行 `INFO selfcheck 自检恢复：<id>`。同一个状态不重复写。
2. **状态行**：`sumika-ctl status` 增一行：`自检：正常`，或者 `自检：2 项异常（intake.unaccounted、turn.stuck），详见 data\selfcheck\<日期>.json`；文件超过 15 分钟没更新而桌面程序还在运行时写 `自检：未更新`；桌面程序没在运行时（`sumika-ctl status` 退出码 2）不显示这一行。`ctlproto.Status` 增一个字段是加法。
3. **巡检**（仓库外，由主会话改 `SKILL.md`，本规格只定读法）：
   - 读今天和昨天的两份文件。
   - “新增异常”= 今天 `bad`、昨天不是 `bad`。报告里单独一节 `## 运行时自检`，把 `checks` 表原样贴进去（不改写）。
   - 文件不存在，或 `updated` 超过 2 小时：写“自检未运行”，再退回 grep 日志，并注明是退回的。
   - 报告里不把 `unknown` 写成正常。

## 八、性能上限

- 计数路径：原子加，不加锁、不分配；基准 `BenchmarkCount` ≤ 30 ns/次。
- 评估：单次总耗时 ≤ 50 ms（不含 S8 的历史缺口扫描，那一次是一次性基线，允许 2 秒）。S8 的增量扫描按水位，不随表大小增长。
- 刷新文件：单次 ≤ 10 ms，文件 ≤ 64 KB。
- 内存：自检自身 ≤ 1 MB（环形窗口、各 stage 最近 K 条）。
- 如果查询超过上限，**不加索引**（加索引要改 trace 迁移，那是另一件事）：先把查询收窄（只看最近 24 小时），再决定。

## 十二、验收标准（每条都有测试）

- **B1 只读（数据库）**：用临时目录里的真 SQLite 文件，打开后执行 `INSERT`、`UPDATE`、`DELETE`、`CREATE TABLE` 都报错。
- **B2 只读（依赖）**：`go list -deps ./internal/selfcheck` 的结果不含写库接口所在的包和发送包；测试断言它。`selfcheck` 的测试用一个只记录调用的假 Store，断言评估过程中只调用了查询方法。
- **B3 S1、S2**：造一条帧走完整的收到路径，但不入库 → S1 差额为 1（在静默点）；在途时不判；写库失败 → S2 为 bad 且 `storeFailed == 1`。
- **B4 S3、S5**：造一次无回执 → `receiptUnknown` 加 1；10 分钟内造 6 次断开 → S5 为 bad，同一次断开里的多次退避只计 1 次。
- **B5 S4、S6、S7**：造一个 `ended_at IS NULL` 且超时的回合 → S4 bad；把它放进 `RunningTurns` → 不报；造 5 条失败的 `model_runs` → S7 bad；`error_class` 为冷却 → 不报。
- **B6 S8**：历史有一个缺口 → 基线记 1、不报；水位以后造一个新缺口 → 报 bad。
- **B7 文件**：刷新写的 JSON 能被解析；原子写（写一半被打断时旧文件仍完整）；日期翻转后计数归零；重启后当天计数续上。
- **B8 状态行和日志**：状态从 ok 变 bad 时只写一条 WARN，不重复；`unknown` 不写 `ok`；进程不在运行时状态行不出现。
- **B9 误报压法**：造在途消息 → S1 不判；造 `not_configured` 的 `model_runs` → S7 不报。
- **B10 性能**：计数基准 ≤ 30 ns；评估在第 0 步的副本上 ≤ 50 ms（不含 S8 的一次性基线）。
- 所有测试只用 `t.TempDir()`，不碰真实 `data/`（只允许把测试输出放进 `data/dev/test-runs/`）。

## 十三、已知的坑

- `RunningTurns` 来自心跳，心跳每 60 秒写一次，S4 判定时它可能落后一拍：要求回合“超过阈值”才判，不靠 RunningTurns 的瞬时值。
- 时钟：文件名按本地日期（`filelog.DayLayout`），时间戳写本地时间（同 `StampLayout`），不用 UTC（LESSONS：TS 那边 `toISOString` 跨零点写错文件）。
- S8 的水位存在自检的状态文件里，状态文件坏了要当作“没有水位”，重新做历史基线，**不许**把重建的基线当成新缺口报出来（这会在坏文件后第一次运行时红一片）。
- 巡检读文件时可能撞上写文件的瞬间：原子写保证读到的是完整的旧文件或新文件，巡检要做的只是 JSON 解析失败时写“读取失败”，不当正常。

## 十四、和其他规格的关系

- 数据健康度（[规格-数据与日志](规格-数据与日志.md) 第九节）：那里是“大小和增量”，本规格不管大小；日增量暴涨是第十节的以后项。

18. **复核后的修改**（2026-11-13，`fix/selfcheck-review`；复核意见逐条判断，采纳 1～7，第 8 条不改）：
    - **S1 静默点加看在途数量**：除了“距上一条交来的消息超过 5 秒”，还要 `Intake.Pending()`（队列里排着、没做完的活）为 0，经 `Env.Pending` 传给检查。拦截链、闸门在会话队列里同步跑，队列被它卡住时，后面排着的消息已经算交来、还没有结局，原先只看时间会连续两次评估后误报“没有去向”。代价：队列一直卡着时 S1 一直不判，卡住的回合归 S4。
    - **S1 加第三条守恒式 C（交接）**：适配器交给入库的帧 = 接收端（app 的 `sink`）因号对不上有意丢掉的 `sinkDropped` + 实时入口 `Intake.Inbound` 收到的 `live`。原先接收端遇到号对不上直接 `return nil`，`toIntake` 加了、`submitted` 没加，A、B 两式都看不见，适配器交出之后到入库一站之前丢的也一样。C 只在适配器数帧时（`received > 0`）才判，不数帧的假适配器不判。差额 = |A| + |B| + |C|，例子里多一项 `handoff`。`counters` 多了 `sinkDropped`、`live`。
    - **S1 基线**：进程第一次评估的基线是 0（计数器随进程从 0 开始，启动后两分钟里真丢的要报）；只有过零点才重建基线。盲区：零点那次评估把 23:5x 到零点之间已有的差额一并吸收（要报得在零点前连续两次静默点上已经报过）。
    - **S5 环形窗口 64 → 128**：配置允许 `reconnectCount` 到 100，64 格的窗口让 65～100 永远不会触发。
    - **S6 口径**：压缩阶段复用 S7 的 `benignModelError`（加上 `parse_failed`），没配模型、预算用完、全员冷却不再报成 `memory.compact_failed`。
    - **`Runner.Close` 先取消再等**：生命周期（cancel、done）单独一把锁，Close 不再先等评估持着的评估锁（最坏 19 秒）；整轮被打断时，被打断的那条结果丢掉，不覆盖上一次的判定、不记成 unknown。
    - **S8 只读连接只在启动时开一次，不改**：平台列表在一次运行里是固定的（`store.Set` 打开的那几个，没有运行中新增平台的路径），启动时打不开的会写日志、那一条标 `unknown`（状态行显示“无法判定”，不是正常），换 exe 以后重开。不会假绿，只是不自愈；偶发打不开不值得为它加一层重试。
