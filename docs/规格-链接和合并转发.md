## 零、先说人话

1. **链接**：消息里写得完整的 `http://`、`https://` 网址，在气泡里变成可以点的链接；点一下用系统默认浏览器打开（只开 http 和 https）。右键气泡：这条消息里只有一条链接时出现"复制链接""复制干净链接"，有不止一条时出现"复制所有链接""复制所有干净链接"，一行一条。"干净链接"是去掉了追踪参数的链接（`utm_*`、B 站的 `spm_id_from` 之类），决定内容的参数（B 站的 `p`、`t`，小红书的 `xsec_token`）一律保留。消息原文不改，只影响显示和复制。
2. **合并转发**：现在气泡里只写一个"[合并转发]"（`native/bubble.go:226`），点不开。要做的是：气泡里显示一张转发卡片（标题、前三行预览、条数），点开一个查看窗口，把里面每一条按原样列出来（名字、时间、文字、图、表情、链接、引用）；里面套着的转发可以一层层点进去，有返回。库里没有这棵树时，在"正在接收 QQ"的情况下向 SnowLuma 取回来存好；取不到就照实写取不到的原因。
3. **不做**：不给角色或记忆整理展开转发；不展开短链、不联网查链接；不改向 QQ 发送转发。小程序/分享卡片版式本次已纳入，见 1.4。

## 二、链接

### 2.1 识别：一个通用入口

新加 `linkreader.FindURLs(text string) []Found`（和 `Extract` 并列，**不改 `Extract` 的行为**，linkplugin 在用它）：

```go
type Found struct {
    Start, End int    // 在原文里的字节位置，[Start, End)
    Raw        string // 原文片段，一个字都不改（显示用）
    Open       string // 点击时交给浏览器的地址：Raw 的地址部分折成半角（见下），其余原样
    Clean      string // 干净链接，见 2.4；清洗失败时等于 Open
}
```

规则（凡是"沿用"的都是 `extract.go` 现状；"新增"的是通用入口和 `Extract` 不同的地方）：

| 项 | 规则 |
|---|---|
| 起点 | `http://`、`https://`（不分大小写）。**沿用**全角写法 `ｈｔｔｐｓ：／／` 也算起点。**只认带协议头的**；裸域名（`github.com/x`、`www.baidu.com`）、`ftp:`、`file:`、`javascript:`、`mailto:`、`magnet:` 都不认——"不认不完整的"。linkreader 里 `wideHosts` 那条"裸域名也认"只属于 X、B 站的展开，通用入口不用 |
| 起点前一个字符 | 沿用 `isURLPrefix`：前一个字符是字母、数字或 `._-/:@%+`（全角先折成半角）就不是起点，免得从 `xhttp://`、`a@http://` 里捡 |
| 终止字符 | 沿用 `boundary`：空白、`[]{}<>"'` 反引号、反斜杠、`，。；！、（）【】《》「」『』`。**新增**：ASCII 圆括号 `(`、`)` 成对时算 URL 的一部分（`https://en.wikipedia.org/wiki/Foo_(bar)`），遇到没有配对的 `)` 就在它前面停；全角括号 `（）` 照旧一律终止 |
| 汉字 | **汉字一律停**（`https://a.com/x看这个` → 停在 `x`；`https://a.com/p?x=1看这个` → 停在 `1`）。比 `Extract` 更严（它进入查询串以后汉字不停），理由见 2.7 第 2 条 |
| 全角问号、井号 | **新增（和 `Extract` 不同）**：`？`、`＃`（全角）**不算查询串的起点，算终止**——中文聊天里 `https://a.com/x？` 的 `？` 是句末标点。`Extract` 把它们当查询串起点会继续吞后面的字，通用入口不这么做 |
| 末尾标点 | **新增**：地址末尾反复裁 `. , ; : !`（不分有没有查询串）；末尾单独一个 `?` 也裁（`https://a.com/x?`）。查询串里的 `=`、`&`、`%XX` 不裁 |
| 全角字符 | 协议头、主机、路径里的全角 ASCII（`ｈｔｔｐｓ：／／ｅｘａｍｐｌｅ．ｃｏｍ／ａ`，U+FF01～U+FF5E）认作对应的半角；`Open` 里折成半角，`Raw` 不动。**查询串和片段不折**（可能是签名，沿用 `foldWidth` 的规矩）。全角句号 `。`（U+3002）是终止字符，不是点 |
| 校验 | 候选交给 `net/url.Parse`：协议必须是 `http`/`https`；`Hostname()` 非空；**有 `userinfo`（`user:pass@`）的不认**（`https://a.com@evil.com` 这类冒充）；主机里必须有一个 `.`，或者是 `localhost`，或者是 IP 字面量（含 `[::1]`）；端口随便（浏览器打开，不受 linkreader 联网取数的端口限制）；含控制字符、反斜杠不认 |
| 长度 | 候选超过 **2048 字节**（和 `types.MediaRefMax` 一致；我定的）：整个不认，保持普通文字，**不截断**成残缺的链接 |
| 数量和扫描量 | 一条消息的所有文字段合起来最多认 **20 条**（超过的保持普通文字，菜单里不提示，只复制前 20 条）；单个文字段只扫前 **64 KiB**。起点用 `linkStart` 这种线性扫描，不用有回溯的正则（超长输入 + 反复起点不能超线性） |
| 去重 | 一条消息里按 `Clean` 去重，保留第一次出现的顺序；显示时每个出现的位置都可点（去重只管菜单） |

**卡片和分享段里的链接怎么算：**

- 只有 `json` 卡片（`Seg.CardJSON` 非空）。字段按 `card.go` 的 `cardPaths` 白名单（`meta.detail_1`、`news`、`music`、`video`、`miniapp` 下的 `qqdocurl/jumpUrl/url/sourceUrl/shareUrl/targetUrl/musicUrl/legacyUrl/pcJumpUrl`），**不递归抓任意字符串、不抓封面图地址**（`FromCard` 的注释同样）。取出来的值交给通用入口 `FindURLs` 过一遍同样的校验，不是 http(s) 就丢。
- `xml` 卡片不提链（只有预览，不当 JSON，规格-链接解析 3.1）；`card_too_large`、`card_malformed` 的卡片不提链。
- 卡片的跳转地址进菜单；有标题的 JSON 卡片按 1.4 画版式，点击整张卡片打开原链接（2026-11-02 主会话定）。
- 引用块里被引用那条消息的文字不算（引用预览是 20 字截断的，链接多半是残的；那条消息自己的气泡里才算）。
- 转发查看窗口里每个节点是一条小消息，同样识别、同样有菜单（范围是那一个节点）。

### 2.2 数据怎么流到界面

界面不解析 JSON、不碰库（规格-界面接Go后台 4.x）。

1. **文字里的链接**：`msgFromView` 在后台把 DTO 转为缓存块：有段走 `blocksOf`，无 Segments 的本地消息、旧记录或缺段数据走 `textBlocks`。两者都在转换时调用 `linkreader.FindURLs`，绘制的 `docOf` 只读 `m.blocks`。`run.Link` 保存 `Open`、`Clean`、`Raw`；同样式文字仅在 Link 相同的情况下合并。演示流式消息也在文字更新时重建缓存，绘制不重新识别。
2. **卡片里的链接**：`desktopread/media.go` 的 `displaySegments` 在 `SegCard` 一支里用 `CardJSON` 算出来，放进 `api.DisplaySegment.Links []string`（原样的地址，已过校验）。界面把它们和文字里的链接合成这条消息的链接表 `msg.links []linkRef`（按"文字段在前、卡片在后，各自出现的顺序"，按 `Clean` 去重）。
3. 界面包可以 import `linkreader` 的这两个纯函数（`FindURLs`、`CleanAny`）。**第 0 步先核对 `internal/archcheck` 允许根包 import `linkreader`**；不行就把纯的那部分（找链接、清洗、表）拆成 `internal/linkclean`，`linkreader` 反过来调它——表仍然只在一处（2.4）。

### 2.3 点击

- 画法：链接是 `ui.Link(c, 显示的字, "")` + `Clicked()`（mygo `docs/ui/link.md` 的"Other actions"：URL 给空串，点击由我们处理），打开动作在我们手里。这样才能在打开前再校验一遍，而不是把字符串交给 `ui.Link` 自己打开。`Element.Cursor` 给手型；悬停显示 `Tooltip`（完整的 `Open` 地址，长的截断到 200 字）。
- 打开：`c.OpenURLThen(open, done)`；`open` 是 `Found.Open` **再过一遍**"解析后协议是 http/https、没有控制字符和反斜杠"（不用 `ui.SafeToOpen`：它放行 `mailto:`），不过就不开。打开出错（没有默认浏览器）：气泡下面不加东西，进桌面日志一行（只写主机名，不写整条地址，地址里可能带令牌）。
- **打开的是原链接（`Open`），不是干净链接**：表可能删错，原链接是发的人给的；"干净"只在复制时由主人选。（暂定，第九节问题 1。）
- 样式：强调色字、下划线（设计语言第 296 行；悬停下划线加粗用 `Underline` 的变化代替）；在主人自己（右边）的气泡里文字色是 `AccentText`，链接色要在强调色底上读得出——用 `AccentText` 加下划线，不用强调色（强调色底上强调色字看不见）。键盘 Tab 能走到、Enter 打开（`ui.Link` 自带，路线 A 才有，见 2.5）。
- 长链接：和普通文字一样折行；在 `/`、`?`、`&`、`=` 后允许折（`Span` 不支持的话，退路是按 32 个字一段插零宽空格 U+200B 到**显示用**的字里，**复制出来要去掉**，`copyMap` 同一个办法；选 A 还是选这个在第 0 步看 `RichText` 的折行行为）。

### 2.4 干净链接：表放一处

**位置**：`linkreader/tracking.go` 重写成**按主机分表的唯一出处**，`Recognize`（X、B 站展开）和 `CleanAny`（通用）都调同一个函数 `stripTracking(host, rawQuery)`；测试在同一个包。不再有第二份表。

**入口**：`CleanAny(raw string) (clean string, err error)`：解析；折全角地址部分；协议和主机名转小写；去掉 `userinfo` 的链接直接拒（不认就不清）；按主机选表；删追踪参数；**不改**路径、片段（`#…`）、表外参数的编码、重复次数、空值、顺序（沿用 `cleanQuery` 的写法：参数名解一次码匹配，值只检查能不能解码，不重新编码）；清洗后没有参数就不留孤零零的 `?`。查询串里有非法转义（`%zz`）：不清洗，返回原样（**不丢链接**，`cleanQuery` 现在返回 `false` 会让 `Recognize` 整条拒掉，通用入口不能照搬）。

**幂等**：`CleanAny(CleanAny(u)) == CleanAny(u)`（写穷举测试，LESSONS"清理类变换先写清两遍 = 清一遍"）。

**匹配规则**：

- 参数名**不分大小写**比较（`tracking.go` 现状是 `strings.ToLower(key)`；规格-链接解析第六节写"区分大小写、`utm_` 前缀只匹配小写"，**与代码不一致，以代码为准**，实现时同一个提交把那一节改成不分大小写）。理由：`shareRedId` 这类名字大小写混用，`UTM_SOURCE` 也真实存在。
- 主机匹配按 `Hostname()` 的**后缀边界**：`bilibili.com` 匹配 `bilibili.com` 和 `*.bilibili.com`，不匹配 `notbilibili.com`、`bilibili.com.evil.cn`（精确后缀 + 前面是 `.`）。
- **通用表只对所有主机生效；站点表只对它的主机生效**。**绝不能**让未知主机落到 X 的表（`isTracking` 现在的 `else` 分支就是这个坑）：写成"站点表 = `map[后缀]表`，没有命中的主机只用通用表"，并加测试：`https://example.com/a?s=1&t=2` 清洗后原样不变。
- 删除原则：**只删"名字本身就是分享来源 / 点击标识 / 设备标识、值不决定页面内容"的参数**；拿不准的不删。下面表里"待实测"的一律不启用（写进表里是为了不重复调研）。

### 2.5 行内排版（第 0 步先验证，这是这份规格里最大的实现风险）

`bubble.go` 的行内块用 `ui.RichText(c, spans...)`，含小黄脸的块靠 `Span.ObjectWidth` 的行内框和 `ui.ShapeRichText(...).Objects()` 预排出框的位置（`inline.go`，缓存在块上的 `inlineLay`）。mygo 的文档说 `RichText` 的 `Children` 里的 `Text`、`Link` "continue the paragraph after its spans"，也就是**接在 `spans` 后面**，不能和 `spans` 交替。所以：

- **路线 A（首选）**：没有小黄脸的行内块，如果含链接，整块改成 `ui.RichText(c).Children(func(){ ui.Text(...); ui.Link(c, 字, "")...})`，链接是真的 `Link` 元素（键盘能到、读屏念成链接）。没有链接的块**完全不动**，现有路径零回归。
- **混合块已验证走 A**：2026-11-02 在 ui.NewTester 构造“文字 + ObjectWidth 脸 + Link + ObjectWidth 脸 + 文字”，三个子元素同一基线且 X 严格递增，点击得到唯一原链接。做法是父 RichText 不传 spans，脸用子 RichText(spans...)；链接保持 ui.Link，脸的绘制和复制仍用父段落的相同 spans 预排。探针已删除，产品交互由 TestMessageLinkActions 验收。
- 复制：选中链接的字复制出来是**原文**（`Raw`）。路线 A 下 `CopyData` 给的 parts 要核对链接元素的字有没有进来；核对不过就把"含链接的块"的复制还原放进 `copyMap`（和脸同一套）。

改坏检查：去掉 PopoverMenu → TestMessageLinkActions 缺复制菜单变红；停用 FindURLs 扫描 → TestFindAndCleanURLs 变红，已恢复。PopoverMenu 的条目由 Tester.Texts()/Click 验证；它画在窗口里，Tester.Menu()/ChooseMenuItem 只适用于系统菜单。


### 2.6 右键菜单

**选 mygo 的 `Element.PopoverMenu`，不选 CrychicUI 的 `overlay.ContextMenu`，也不选 `Element.ContextMenu`（系统菜单）。** 主人要求"照 CrychicUI 菜单组件的写法"，这里解释偏离了哪、为什么：

- CrychicUI 的 `overlay.ContextMenu(c, label, target, list, chosen *int, open *bool)` 是**自己读 `target.RightClicked()`、自己管 `open` 和 `chosen`** 的组件。气泡壳是 `Selectable()` 容器，右键本来就由 mygo 弹"复制 / 全选"；两套同时读右键会弹两个菜单（`ContextMenu` 文档："最里面有菜单的元素拿到点击"，但 CrychicUI 的是读事件不是注册菜单，不参与这个仲裁）。它也没有"复制 / 全选"这两项，要自己重做。每条消息还得存一份 `open`、`chosen`（一万行的列表里每行一份）。
- `PopoverMenu` 是**同一个菜单构造器**（`func(m *ui.Menu)`），由 mygo 按主题画在窗口里（"MyGo draws in the window with the theme's look"），样式和 CrychicUI 的菜单是同一个主题来源；`m.EditItems()` 把"复制 / 全选"放回去；不用每行存状态。
- 选系统菜单（`ContextMenu`）的话外观和应用其余部分不一致，也不是 CrychicUI 的样子。
- 选中音：CrychicUI 的菜单在选中时 `sound.Play(sound.Select)`；`PopoverMenu` 没有，我们在 `Chosen()` 分支里补一次 `sound.Select`（用的是同一个 `sound` 包，和 `lightbox` 的 `sound.Swipe` 同类）。

菜单内容（挂在每个气泡壳上；一条消息有几个壳——`mface` 单独成壳——每个壳都挂，范围都是"这条消息"）：

| 这条消息里的链接数（去重后） | 菜单 |
|---|---|
| 0 | **不挂 `PopoverMenu`**，右键保持现状（mygo 自带的"复制 / 全选"） |
| 1 | `复制链接`、`复制干净链接`、分隔线、`m.EditItems()` |
| ≥ 2 | `复制所有链接`、`复制所有干净链接`、分隔线、`m.EditItems()`；写到剪贴板的是**一行一条**（`\n` 分隔，末尾不加换行），顺序是链接表的顺序 |

- "链接"= `Open`（发的人写的，全角地址折成半角，其余原样）；"干净链接"= `Clean`。两列条数相同（都按 `Clean` 去重，原链接取每组第一次出现的）。
- 菜单项文字不随条数以外的东西变（mygo 在选中之后再跑一次 `build`，"按位置和标签"认选中的那一项，标签必须稳定）。
- 写剪贴板用 `c.Services().WriteClipboard(text)`（UI 线程）。条数很多时（≥ 2 条）菜单项后面不写条数，免得标签变。
- 链接 ≥ 21 条时（超过 2.1 的 20 条上限）菜单里不提示，只复制前 20 条；气泡里超出的保持普通文字。（我定的；这么多链接的消息很少。）
- 键盘：菜单键或 `Shift+F10` 在壳有焦点时也能开（mygo 的 `PopoverMenu` 自带）。

### 2.7 禁止的偷懒写法和已知的坑

**禁止：**
1. 对未知主机用 `xTracking`（或任何站点表）。
2. 用 `ui.SafeToOpen` 当"只开 http(s)"的判断（它放行 `mailto:`）。
3. 点击时把"显示的字"直接交给浏览器，不再校验协议和字符。
4. 为了好看把链接显示成短的或改写 `Raw`；消息原文、`text` 列、复制出来的字都不改。
5. 把 `*` 通配当参数名匹配（只有 `utm_` 一个前缀）；用"含 `share`/`source`/`token` 的都删"这种规则（会剪坏 `xsec_token`、`token=` 签名）。
6. 在清洗里 `url.Values.Encode()`（会重排、重新编码、丢重复）。
7. 清洗时联网、展开短链。
8. 从引用预览、`xml` 卡片、封面图地址里提链。
9. 绘制回调里（`Draw`、`Layout`）找链接或清洗——在段转块那一步做一次存起来。
10. 为了让 URL 能折行去改消息文本；要折行只改显示，并保证复制还原。

**已知的坑：**
1. 括号：`(https://a.com/x)` 圆括号不配对，`)` 在地址外；`https://a.com/Foo_(bar)` 成对，在地址里；`（https://a.com/x）` 全角括号一律是外面。
2. 汉字紧贴链接：`Extract` 进入查询串以后汉字不停，`https://a.com/p?x=1看这个` 会连"看这个"一起吞进去。通用入口**一律在汉字处停**（测试写一条"查询串里的汉字不属于链接"）。真有汉字参数值的链接，QQ 复制出来多半是百分号编码的，手打的会被截短，接受这个损失。
3. 路径里的中文：`https://zh.wikipedia.org/wiki/中文` 会停在 `wiki/`。QQ 里复制出来的是 `%E4%B8%AD…`，手打的才有汉字；接受这个损失，不为它放开汉字规则。
4. 末尾标点：`https://a.com/x.` 的点不属于链接；`https://a.com/x.html.` 同理；但 `https://a.com/x?q=a.b` 的点在中间保留。
5. `Raw` 里有 U+FFFC 的占位字符：`cleanText` 在段转块时已经去掉，识别发生在去掉之后；找链接用去掉之后的字，位置对得上（测试）。
6. `ts`、`t`、`s` 这类短名字是最容易剪坏页面的（`ts` 在 B 站是追踪、别处可能是时间点）——**只在它们的主机上删**，是表的结构保证的，不靠记性。
7. `xsec_token`、`token=`、`sign=`、`signature=`：一律不在任何删除表里。
8. `igshid` 之类放通用表还是站点表：放通用表是因为 Instagram 分享出来的链接常被别的站转载带着。想收紧就搬进 `instagram.com` 的站点表，不影响别的。
9. 同一个链接在一条消息里出现两次：显示两处都可点，菜单里只一条。
10. 路线 B（混合块）里链接没有键盘焦点，读屏也不念成链接；这是退路的代价，写在设置里的无障碍说明之前先问主人。

## 三、合并转发的设计

### 3.1 气泡里的卡片

新块种类 `blockForward`（和 `blockMface` 一样**单独成壳**，不和前后的字挤在同一个气泡里；`shellGroups` 里加一支）。卡片用什么组件（LESSONS"先读组件库，逐个对应"）：

| 要的 | CrychicUI 里最接近的 | 结论 |
|---|---|---|
| 聊天记录卡片（标题 + 几行预览 + 条数 + 点开） | `chat.LinkPreview`（标题、主机、封面的卡）、`chat.Forwarded`（气泡顶上"转发自 X"一行） | 都不合：`LinkPreview` 要封面和主机，`Forwarded` 是单条转发的页头。用 `kit.Card` + `kit.Muted` + `icon.Must("forward")`（`chat.Forwarded` 用的同一个图标）自己排，排法照 `LinkPreview` 的内边距 |
| 点开的窗口 | `overlay.Modal`（带标题、关闭按钮、缩放进场）、`overlay.FullscreenModal` | 用 `overlay.Modal`，宽度默认 `Space(110)`（440 DIP）；点进里层时标题换成里层标题，左上加返回按钮 |

卡片的内容（在气泡壳里，壳最宽 `Space(80)` = 320 DIP）：

```
┌─────────────────────────────┐
│ ⤳ A和B的聊天记录              │   标题：节点里不重复的名字，最多 3 个用"和"连，
│ A：今天谁去                    │   多于 3 个写"前两个名字等"；全是空名字写"聊天记录"
│ B：[图片]                     │   预览：前 3 个节点，"名字：内容"，一行，截到 20 个字加…
│ A：我先看看…                  │   内容：文字原样；其余写占位：[图片] [表情] [语音] [视频] [文件] [合并转发] [卡片]
│ 查看 12 条聊天记录             │   条数：顶层这一层取到的节点数；有没取下来的写"12 条（还有 3 条没取下来）"
└─────────────────────────────┘
```

- 没有树（没取到或者还在取）：标题写"聊天记录"，没有预览行，最后一行写状态："正在取回…"（接收模式且在取）/"没取回来，点开看原因"。卡片本身**一直可点**（点开才显示原因或重试）。
- 卡片是一个可聚焦的按钮（`ButtonBase`），读屏念"聊天记录，12 条，按下打开"。点击目标整个卡片，高度大于 32。
- 复制：卡片区不参与文字选择（和 `mface` 一样不进 `copyMap`）；右键菜单：这条消息有链接才有（2.6）。
- **预览文字是不可信的外部内容**：只显示，不拼进任何别的东西；名字、文字里的 U+FFFC 去掉；截断按 rune。

卡片所需数据：`DisplaySegment.Forward *ForwardBrief`（`Title`、`Lines [3]string`、`Count`、`Missing`、`State`）。`desktopread` 收齐本页的 Ref，用一条参数化 IN 查询取名字、`json_array_length`、`truncated` 和前 3 个节点，任何大小的树都不整棵搬到摘要路径。摘要按 `(id,fetched_at)` 缓存，LRU 上限 2000。

### 3.2 查看窗口

- 用 `overlay.Modal`（标题 = 当前层的卡片标题；关闭按钮 = CrychicUI 自带的 `Close`，改成"关闭"）。窗口里：返回按钮（栈深 > 1 才有）、节点列表（滚动）、底部一行小字（"共 12 条"/"还有 3 条没取下来"/取不到的原因）。
- 每个节点 = 一条小消息：名字（粗小字）+ 时间（`HH:mm`，隔天时在名字旁写日期）+ 内容。内容**复用主聊天的同一套画法**：把节点翻成一个 `*msg`（`forwardNodeMsg`），走 `blocksOf` → 行内块（小黄脸、链接）/ 图组（`imageGroup`，网格、看大图）/ 占位块；气泡壳按"别人（左边）"画，不套入场动画（`anim = false`），不画时间在壳外那一套（那是 bubble-ui 的 `bubbleRow`，这里自己排）。同一个名字（`uid` 和 `name` 都相同）连着的节点只在第一条写名字（**纯显示，不当身份用**）。
- 节点里的段怎么显示：

| 段 | 显示 |
|---|---|
| `text`、`at`（名字取不到按 MaskID 打码，all 写全体成员，非法 target 写某人）、`face`、`superface` | 同主聊天（含链接）；卡片前三行预览也不直出 at.Target |
| `image`、`emoji` | 有 `hash`：图（缩略图 + 点开看大图，授权链见 F1）；没有：`imageNote` 的占位（"[尚无本地媒体]"/"[图片已过期]"…，同主聊天；F3 之前全是前者） |
| `reply` | 引用块：被引用内容取树时内嵌的 `message`，存在 `raw` 里（只留纯文字预览，截 `types.RawMax`）；其中 `@数字` 按 MaskID 打码，没有内嵌就写“[回复了一条消息]”。点引用块不跳转（原消息不在树里）。样子照 `quoteBlock` |
| `forward`（里层） | 同气泡里的卡片（3.1），点一下压栈进入 |
| `card`（`json`） | 复用 1.4 的完整卡片版式、点击浏览器和本地封面，跳转链接进该节点菜单 |
| `card`（`xml`，没解成 `forward` 的） | 灰字 `[聊天记录（预览）]`，下面最多 3 行预览（`<title>` 里的文字，F5 才做；之前只显示 `[卡片]`）+ 一行"里面的内容取不到" |
| `video` | 复用正文 `videoBubble` 与 `PrepareVideo`；有本地 hash 可播放，有封面、时长就显示；无 hash 明确写尚未下载或已知失败原因。当前转发下载器不排视频，无视频元数据列，不自行增加自动下载 |
| `voice`、`file`、`other` | 灰字占位，同主聊天（`[语音]`、`[文件：名]`、`[kind]`） |

- 层数和条数上限（界面一侧）：栈深最多 **10**（和取树一致）；一层最多显示 **200** 个节点（取树一侧已限，界面再按 200 兜一次，防止导入的 Bun 树更大）；超出的写"后面还有 N 条没显示"。
- 返回：点面板外、返回按钮、`Esc`、`Alt+←` 都只退一层，最外层才关闭窗口。开着看大图时 `Esc` 先关大图；关闭按钮始终关闭整个查看窗口。**键盘守门**（LESSONS"挂在 window 上的键盘监听先问是不是自己的"）：窗口开着时，主聊天的键盘处理不响应。
- 本次采用自排查看层：`overlay.Modal` 的关闭动作会立即交回，装不下逐层返回与保留退场内容；`forward.go` 照它的 dialog/heading 用 kit.Card、CrychicUI 按钮、同一主题和入场。关闭后保留标题、节点、尺寸和媒体缓存 200 ms，取消等待、丢弃旧结果，到时清栈、取消媒体读取并释放缓存。每层保留自己的 `ui.ListState`，出栈同时清掉底层切片的旧层指针。后台将节点内的内容拆平为虚拟行：每行最多 8 块，图片组每 20 张拆块（我定的），只构建可见行和列表预留范围。

### 3.3 嵌套转发

- 里层 = 另一行 `qq_forwards`。节点里的 `forward` 段（`ref` = 里层 id）画成卡片，点一下：栈里压入里层 id，`ReadForward(里层)`。
- **循环保护**：栈里已经有的 id 不再压（防 id 成环）；深度到 10 不再压，卡片点开后显示"更里面的聊天记录不再展开（最多 10 层）"。
- 返回：弹栈，回到上一层原来的滚动位置（每层各存一份滚动位置）。
- 进入里层、返回或关闭时，同步结束被取消层的 busy，保留 dirty；请求代次挡住已排队的旧回调。刷新会把栈内各层标脏，返回父层时补读积压的变化。
- 里层没存（取不到）：同顶层，显示原因 + 在接收模式下可重试，重试走"先取外层"（3.5）。

### 3.4 状态和原因（界面上的话）

| `ForwardView.State` | 窗口里显示 |
|---|---|
| `ready` | 节点列表 |
| `ready`，`Missing > 0` | 节点列表 + 底部"还有 N 条没取下来" |
| `fetching` | "正在从 QQ 取回聊天记录…"（逐层时写"正在取回第 N 层…"）；关窗口就取消等待（ctx 取消），**不取消后台已经开始的取回**（取回的结果照样存库） |
| `not_receiving` | "现在没在接收 QQ，没法取回这条聊天记录。开始接收后再点开。"（归档模式：没有适配器，不会联网） |
| `unavailable`（SnowLuma 回 `payload is empty` 等） | "QQ 那边已经取不到这条聊天记录了（可能过期了）。"+ 重试按钮（只有接收模式有） |
| `timeout`、`not_connected`、`connection_lost` | "QQ 没有及时回话。"/"和 QQ 的连接还没准备好。" + 重试 |
| `refused`（连接还没核验通过 / 号不对） | "QQ 连接还没核验通过，暂时不取。"（不重试） |
| `too_deep` | "更里面的聊天记录不再展开（最多 10 层）。" |
| 陌生人 | 同普通消息自动取树、自动下图，不再有 stranger 拦截状态（第九节第 7 条） |

原因文字是固定短语，**不带协议端原话、不带 id、不带地址**（`errQuery` 的写法）。

### 3.5 数据和读接口

**可选纯读能力与独立取回动作**（我定的：保持基本 Reader 的只读契约，界面不碰库）：

```go
type ForwardReader interface {
    ReadForward(context.Context, ForwardRequest) (Result[ForwardView], error)
}
type ForwardActions interface {
    FetchForward(context.Context, ForwardRequest, time.Duration) (Result[ForwardView], error)
}

type ForwardRequest struct {
    Source EventRef   // 哪条消息里的转发（授权的根：这个 id 必须出现在这条事件的段里，或在这条事件已授权的树里）
    ID     string     // 要读的转发 id
    Via    []string   // 点开的路径：从最外层到父层的 id（取不到里层时 SnowLuma 要先取外层，见下）
}
type ForwardView struct {
    ID      string
    Group   bool
    Nodes   []ForwardNode // 最多 200
    Missing int           // 没取下来的条数（树上的 truncated）
    Fetched int64         // fetched_at，毫秒
    State   string
    Depth   int           // 正在取回的层数
}
type ForwardNode struct {
    UID, Name string   // 名字缺省时 Name 为空，界面写"（无名）"
    At        int64    // 毫秒；0 = 没有时间
    Segments  []DisplaySegment // 已经整理好，界面不解析 JSON
}
```

- 读：`desktopread` 先校验授权链：`Source` 这条事件在这个会话里、它的 `forward` 段 `Ref` 是 `ID`，或 `ID` 在 `Via` 的路径上（每一层都能在上一层的 `forward` 段里找到）。**都对不上就报 `ErrForwardRef`**，和 `ReadMedia` 同样（不能凭一个 id 读任意树）。
- 树的 JSON 在 `desktopread` 里整理成 `DisplaySegment`（复用 `displaySegments` 的转换，节点里的 `image` 的 `hash` 授权用转发链，见 F1），**限制**：整棵树 JSON 超过 **4 MiB** 的不读（报 `ErrForwardTooLarge`，窗口显示"这条聊天记录太大，没有显示"）；节点数超 200 截到 200 并记 `Missing`。
- **媒体授权链**：`MediaRef` 加可选 `Forward []string`（从最外层到这个图所在的层的 id 路径）。`ReadMedia` 校验：`Source` 事件的某个 `forward` 段 `Ref` = `Forward[0]`；`Forward[i+1]` 在 `Forward[i]` 这棵树的某个节点的 `forward` 段里；`hash` 在最后一层树的某个节点的段里。路径最长 10。任何一环对不上都是 `ErrMediaRef`。没有这条链的 hash 不能读（hash 不是能力凭证）。
- 取回（`FetchForward`）：接收宿主 `forwardfetch` 执行（3.6），desktopread 先按同一授权链验根和 Via；archive 不注入工人，返回 not_receiving。wait > 0 在后台等到完成、失败、ctx 取消或最长 60 秒；关窗口仅取消等待，后台已开始的工作继续存库。ReadForward 自身 5 秒超时，不请求网络。
- 摘要：3.1 的 `ForwardBrief` 由 `desktopread` 在读消息页时算（同一份树解析代码）。
- **只读契约的实现决定（我定的）**：`api.ForwardReader.ReadForward` 是可选纯读能力，`api.ForwardActions.FetchForward(ctx,request,wait)` 是独立取回动作；基本 Reader 不变。归档模式不注入取回工人，动作返回 not_receiving，不联网。ForwardRequest 仅 Source、ID、Via，原草案的 Fetch / Wait 移到动作接口。desktopread 先验证同一授权链，再把请求交给宿主工人。

### 3.6 接收宿主：取树

**位置**：新包 `native/internal/forwardfetch`（常驻包，不是一次性的）；适配器侧在 `snowluma` 加一个可选接口，照 `feat/qq-media-backfill` 里 `types.MessageReader` 的写法：

```go
// types：适配器的可选能力。取不到、没连上、对不上都返回 error，不返回半棵树。
type ForwardReader interface {
    Forward(ctx context.Context, account, id string) (ForwardTree, error)
}
type ForwardTree struct { // 一层
    ID    string
    Group bool
    Nodes []ForwardNode // UID、Name、Time（秒）、Segs []Seg（中立段）
}
```

`snowluma.Adapter.Forward`：`a.query(ctx, "get_forward_msg", {"id": id})`（走同一个只读通道：同一时刻一个、隔 2 秒、单次 45 秒）；回包 `data.messages[]` 逐条翻：
- 节点的段数组直接交给现有的 `segments()`（和收消息同一份翻译，一个地方）；
- `uid` = `str(user_id)`（经 `qqID`），`name` = 群里转发优先 `sender.card`、其次 `sender.nickname`，都空则空；`time` = `time`（OneBot 秒）；`group` = 任一节点有 `group_id`；
- `reply` 段：现有 `segments()` 只读 `id`（放 `Seg.Target`），**转发节点里要多读内嵌的 `message`**：取其中的纯文字拼成预览，截 `RawMax`，放 `Seg.Raw`；回包里的 `qq`、`time`、`seq` 不存（界面只显示预览，不显示被引用的人）；
- 回包不是对象、`messages` 不是数组、`retcode != 0`、`status == failed`：整层不要，返回固定类别错误；**一个节点的 `message` 不是数组**：这一个节点留空段（不丢整层）；
- 一层的节点数超过预算时在翻译前就截断，记 `Missing`。

**取树的参数**（我定的，照 Bun 的 10 层 / 200 条，Go 里重新落成代码和测试）：

| 项 | 值 | 说明 |
|---|---|---|
| 层数 | 最多 10 层 | 第 11 层的 id 不取，节点里的 `forward` 段留着 id；树上不另记 |
| 条数预算 | 从顶层起，**所有层合计 200 条** | 一层取到会超预算时只取到预算为止，剩下的记 `truncated`（没取下来的条数）；预算用完不再往里层取，**不存空树** |
| 时限 | 单次 45 秒（`queryTimeout`）；一棵顶层转发整个取完最多 5 分钟 | 超了放弃剩下的层，已取到的存下 |
| 并发 | 同一个 id 同一时刻只取一次（合并等待者）；全局一个工人 | 适配器的通道本来就是一个在途 |
| 取一层之间 | 隔 2 秒（`queryGap`） | 10 层 = 至少 20 秒；不是在会话队列里做，不挡消息入库 |
| 存 | 取到一层就存一行 `qq_forwards`（`id`、`tree_json`、`fetched_at`）；已有的同 id **不覆盖成更差的**（新取的节点数少于库里的就不换） | 里层单独一行 |
| 嵌套顺序 | **先取外层、紧接着取它的里层**（SnowLuma 的缓存里这时有里层，不用联网；见 1.3） | |
| 重启后单取里层 | 先试里层；回 `payload is empty` 就用 `Via` 的外层依次重取一遍（外层的回包不用，存着的树不动），每次重取后再取里层一次；同一个外层 10 分钟内只重取一次；最多往上 4 层 | SnowLuma-529；Bun 的 `forwardAncestors` 同款 |

里层单独重取前，从授权根扣除目标子树之外所有已存层的节点和图片；已下载的图也扣额度，`forward_limit` 不另扣。起始深度是 `len(Via)+1`，不能把一次点击当成新的顶层额度。

**什么时候取：**

1. **收消息时自动取**：Config.OnStored 只做非阻塞入队，只对 QQ 新存消息；不看 Observed。陌生人私聊、自检、补录、自己的号和普通消息一致；准入层仍先挡非白名单群。
2. **连接后补扫**：工人启动不扫；首次连接和每次重连成功（`StatusConnected`）后，和收图下载一起补扫近 7 天内有 `forward` 段、`qq_forwards` 里没有这个 id 的消息；每次最多入队 50 个（我定的，避免一开机连发几十次查询）。
3. **主人点开时取**（`FetchForward`）：库里没有 → 入队并等 wait；陌生人的也取，仍走同一个限速通道。
4. 开关：`qq.forward.fetch`，默认 `true`（我定的）；关了就只读库里已有的。要同步改 `native/internal/config`、`sumika.example.yml`、参考页。

**收尾**：`Close` 取消在途请求、等工人退出，之后不写库；关机顺序放在 `app.go` 的"2 关入口"一步里，在 `intake.Close` 之后、关库之前（和 `mediafetch` 同位置）。

**要补的缺口**（别一笔带过）：`feat/qq-media-backfill` 的回填是 `SetSegHash` 用 `json_set` 改 `events.segments_json` 的 `$.segs[idx]`，键是 `media_fetch(event_seq, idx)`——**管不到 `qq_forwards.tree_json`**。

## 四、禁止的偷懒写法（合并转发）

1. 把整棵树（可能 200 条 × 10 层）原样塞进每条消息的显示数据或每条她的上下文。
2. 取不到时存一棵空树（`nodes: []`）；预算用完时存空树（Bun 踩过）。
3. 用 `nodes[].uid` 当"是不是同一个人 / 是不是主人"的依据（转发里的号常常是同一个占位号）；名字更不行。
4. 凭一个 id（或一个 hash）读任意树 / 图，不走授权链。
5. 在会话队列里（`OnStored` 同步地）联网取树；取一棵大转发会挡住后面所有消息（待办第 196 行 Bun 时代就记过）。
6. 让界面线程等网络：`ReadForward` 在后台线程，窗口先显示"正在取回"。
7. 关窗口时立刻清内容，让退场动画播空壳。
8. 界面把协议端的原话、id、地址当错误文字显示。
9. 沿用 Bun 的 `forwardTitle` 用全角冒号切名字（名字里有冒号会切错）：Go 的树节点有独立的 `name` 字段，不拼了再切。
10. 把陌生人自动取树误当成“转发内容可以给角色看”；本任务只改桌面显示。
11. 在 `desktopread` 里联网（它只读）。

## 五、已知的坑（合并转发）

1. **节点时间的单位待核对**：OneBot 是秒；Bun 存的 `nodes[].time` 单位没法从 Go 代码确定（Bun 的代码在 sumika-bun，本机没有）。第 0 步从 sumika-bun 克隆后核对；Go 新写的按秒。读的时候 `At = time × 1000`，值 ≤ 0 当没有时间。核对前，界面对 `time` 大于 `1e11` 的值（明显是毫秒）按毫秒读，防止显示成几万年后。
2. 名字可能为空；节点可能没有时间；节点的 `message` 可能为空数组（显示"（空消息）"）。
3. 转发里的 `uid` 常常全是同一个占位号：不用它做头像、不用它分组以外的任何事。
4. **里层图的地址**：Bun 时代遇到"转发里套着的群图 SnowLuma 给的是私聊图地址，服务器回已过期，文件名是 32 位十六进制（图片的 MD5）时按群图老地址再取一次"（qq.md）。2.3.3 的 `makeLegacyForwardImageElem` 可能已经改善；F3 实测时看 `expired` 的比例，不照搬那个补丁。
5. **SnowLuma 的转发缓存在内存里**（512 棵、重启就空）：重启 SnowLuma 之后，库里没有的旧转发，里层大概率取不到，只能取外层再取里层，外层也过期就真的没了。写进窗口的"可能过期了"那句话里。
6. 同一份内容被转发两次：外层 id 不同、里层 id 相同（SnowLuma-529 笔记）；`qq_forwards` 按 id 存，里层只存一行，两个外层都指向它。
7. 取一层 2 秒起步，10 层嵌套的第一次点开要等 20 秒以上：窗口里逐层显示进度（"正在取回第 2 层…"），先显示已取到的外层。
8. 一棵树的 JSON 很大时（Bun 库最大 156 条、100 张图）读和解码都在后台线程；放大十倍验收（第七节）要量。
9. xml"聊天记录"：2.3.3 多半已经解成 `forward` 段（1.3），所以"打不开"的 Bun 时代问题在 Go 上可能不存在；还留成 `xml` 的（没有 `m_resid` 也不匹配 `MultiMsg_` 文件名的）是什么样，**需要一帧真数据**才能定，见 F5。
10. 看大图叠在查看窗口之上、`Esc` 的先后、焦点还给谁：Tester 里验，真窗口也要主人手点一遍。
11. 转发消息本身被撤回：卡片仍显示"已撤回"的小字（bubble-ui 的 `notesOf`），点开仍读库里的树。

## 八、和 bubble-ui 的衔接

读的是分支 `feat/bubble-ui` 工作区里**还没提交**的改动（`git diff`，2026-11-02），以它合进 main 之后的样子为准；下面写的是需要对齐的接缝，落地时重新核对一遍。

| bubble-ui 里的 | 这份规格怎么接 |
|---|---|
| `a.shellOf(c, m, anim, quoted bool, k int, children)`（原来是函数 `shellOf(c, mine, anim, children)`） | 转发卡片、链接菜单都挂在这个壳上；`blockForward` 单独成壳，传 `quoted=false`；`k` 的取名接缝（`probeOf("shell:id:k")`）测试要用 |
| `bubbleShell(c, mine, withQuote)`、`quoteRadius`（引用块与壳同心） | 转发卡片**不是引用块**，不进 `withQuote` 逻辑；卡片在壳里作为一个块，内边距按壳（有引用时 Space(2)+左右垫 Space(1)）。查看窗口里的 `reply` 段画引用块时**复用 `quoteBlock`**（`quote.go`），圆角用 `quoteRadius`，不另写 |
| `m.quote = quoteOf(v)`（引用来自展示 DTO 的 `Reply`，`blocksOf` 里 `reply` 段不再画） | 转发节点里的 `reply` 段不走 `m.quote`（树里没有原消息），自己传一个预览；与 bubble-ui 的 DTO 字段无关，不冲突 |
| `blocksOf` 的 `case "reply":` 空分支、`case "forward": note("[合并转发]")` | 我们只动 `case "text"`（切链接）和 `case "forward"`（改成 `blockForward`）；其余不碰 |
| `row.go` 的 `bubbleRow`（时间在气泡外面紧挨着、和气泡底边对齐；多个壳时跟着最后一个壳） | 卡片是一个壳，行为和 `mface` 一样；不碰 `bubbleRow`。查看窗口里节点自己排版，不用 `bubbleRow` |
| 表情回应、头像（后续） | 表情回应挂在壳上，和链接菜单无关；头像在行的左边，与卡片、链接无关。**右键菜单**如果它们也要加项（比如"回应"），都往同一个壳的 `PopoverMenu` 里加，**不要再挂第二个**（mygo："最里面有菜单的元素拿到点击"，两层各挂会互相盖）——本规格的 2.6 菜单构造要做成"一个返回项列表的函数"，让别的功能加项而不是各挂各的 |

合并顺序：bubble-ui 先合。若它的改动在我们开工前又变了，以 main 上的 `shellOf`、`bubbleRow` 签名为准；我们新加的代码放在新文件 `links.go`、`forward.go`、`forward_view.go`，对 `bubble.go` 只改上表那两个 `case` 和 `inline` 里生成 span 的那一小段，减少冲突面。

## 九、要主人定的问题

默认值都是收紧或保守的那一边；主人不回就按默认做。

1. **点链接打开的是原链接还是干净链接？** 默认**原链接**（表可能删错，页面能打开最要紧；干净链接只在复制时用）。选干净的话，打开前你看不到被删的参数，万一表里有误删就打不开。
2. **卡片（小程序、分享）里的链接要不要能点？** 已定：整张卡片可以点，打开原链接。2026-11-02 主会话定：卡片现在有版式，Telegram、QQ 都是点卡片就打开；菜单同时保留复制链接。字段和输入表见 1.4。
3. **右键菜单用主题画在窗口里的样式**（`PopoverMenu`，和 CrychicUI 同一套主题），**不是**系统自带菜单，也**不是** CrychicUI 的 `overlay.ContextMenu` 组件本身（它会和"复制 / 全选"抢右键，2.6）。这是对你"照 CrychicUI 菜单组件"的一处偏离，要你点头。
4. **链接里被识别成追踪的参数表**，第 2.4 条的站点表：小红书的 `xsec_source` 我默认**保留**（二手资料说可删，但它和令牌成对）；微博、抖音、淘宝京东的分享参数**没查到可信出处，默认不删**。你手里有这几家的真实分享链接样本的话，给我几条（可以自己改掉个人信息），我按样本补表。
5. **转发里的内容要不要给她看？** 等主人定；这一版不做，她仍只看到 [合并转发]，记忆整理同样不展开。
6. **记忆整理要不要读转发内容？** 默认**不读**（ADR-093 第 5 条：转发是别人转来的话，不当成这个群里有人说了这些）。
7. **陌生人发来的转发要不要自动取？** 已定（ADR-244）：自动取树、转发里的图照下，不按 stranger 或观察记录挡取回。
8. **桌面程序点开转发时向 SnowLuma 发查询，算不算可以？** 这是只读查询（`get_forward_msg`），走 2 秒间隔的限速通道，只在"正在接收 QQ"时发，一次点开最多 10 层；默认**允许**。你之前说过 QQ 工具的风控风险你清楚，这里只确认"主人点开也会触发联网"这一点。
9. **转发里的图最多下多少张？** 默认一棵顶层转发 **60 张**，多的显示"这条聊天记录图太多，没有下载"。Bun 库里最大一棵 100 张；想全下就改 100，磁盘大一些。
10. **层数和条数上限**沿用 Bun 的 **10 层、合计 200 条**（我定的；SnowLuma 取的一侧没找到上限，要真机实测一次，待办第 51 行）。
11. **链接单条上限 2048 字节、一条消息最多认 20 条**（我定的）：超了保持普通文字，不截断。
12. **转发卡片的标题**：用"A和B的聊天记录"（节点名字去重后最多 3 个）；你更想要固定的"聊天记录 · N 条"也可以，改一行。
