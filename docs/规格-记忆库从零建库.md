## 开工卡

- **我理解成**：角色记忆库和主人共用池用同一份基础建表语句，放在 `internal/memory` 一处。程序启动时（不是只看历史模式），给有角色卡、没有记忆库的角色自动建一个当前结构的空库：基础表，加上 0001 起的迁移，加上护栏的版本表。建好后照常打开。“记住”（`remember`）默认对所有角色开。三份工具里的建表抄本改成调同一个函数。
  - 正例：全新数据目录，放一张卡，配置里不写 `memory`。启动后 `go/characters/<id>/memory.db` 出现。在本地私聊里说“记住我喜欢喝乌龙茶”，`remember` 成功；重启后问“我喜欢喝什么”，召回里有这一条。
  - 反例：
    - 在已有库上无条件执行 `CREATE TABLE IF NOT EXISTS`，列不对的库会被蒙混过关；
    - 在 `memory.Open` 里顺手建库，每个只读调用都可能去建库；
    - 只改默认值不建库，等于“记了但丢了”（ADR-377 代价一节）；
    - 悄悄改主人的真实配置。
- **领域正统做法**：
  - 一种是“基线”：Flyway 的 `baselineOnMigrate` / `baselineVersion`，把已有的库标成“基线已应用”，新库从基线建起，之后的迁移两边共用（Flyway 文档 Baseline 一节）。
  - 另一种是 Rails：新库用 `db:schema:load` 一次建到位，已有库跑迁移（Rails Guides “Active Record Migrations”第 7 节 Schema Dumping and You）。
  - 我们照第一种，但基线放在 goose 之外。原因：goose v3 不认 0 号版本（`NumericComponent` 拒绝小于 1 的号），版本表的 0 号行被 goose 自己占用，`ApplyVersion` 会真的执行而不是“只标记”，见盘点第 5 条。
  - 具体落法：护栏的“新建”分支先执行基线，再跑 0001～0003。已有基础表、没有 goose 表的 Bun 旧库，护栏现在就按 0 版处理（`AcceptNoGoose`），只跑 0001 起的迁移，正好就是“已有库 = 基线已应用”。
- **最省事的字面做法够不够**：
  - 照路线字面写一个 0000 号 goose 迁移，做不到（见上）。
  - 只在 `openMemories` 里执行一遍建表语句不够：这样会绕开护栏，没有 `sumika_schema`，没有同文件互斥，失败了也没人收拾。
  - 只把默认值改成开、不建库，等于记了但丢了。
- **不做什么**：
  - 不做新建角色向导和首次设置向导。Go 里两样都没有（盘点第 7 条，[界面清单](界面清单.md) 第 55 行）。ADR-377 第 2 条“本地私聊后台整理首次设置时问一次”挂到向导那条待办。
  - 不改主人的真实配置。真实配置里显式写着 `characters: [suzune]` 的照旧；要不要改成 `"*"`，换 exe 时问主人。
  - 后台整理默认仍关（ADR-377 第 2 条）。
  - 不动 `memory-v2.db` 的机制。它是派生索引，按需建，没有迁移（盘点第 4 条）。
  - `memory-migrate` 命令仍然不新建库。
  - 不动冻结的里程碑夹具（`store/testdata/milestones/`）和 Bun 代码。
- **用户能看能试的验收**：见“验收”第 1、2 条。

## 设计

### 1. 一份基础建表语句

- `internal/memory/shared.go` 的 `ownerPoolSchema` 改名为导出常量 `BaseSchema`，全仓只留这一份。
  - 注释写明三点：它等于 Bun 版 `memory.db` 的五张基础表；**它是冻结的基线，以后加表加列只走 `migrations/` 新文件，不改它**；导出只是给建库和测试夹具用。
  - 加一条测试把它钉住：`BaseSchema` 建出来的表和列正好等于 `baseColumns`。
- `openOwnerPoolDB` 改名为 `openBaseDB(ctx, file, fresh)`，共用池和角色库都用它。fresh 时建父目录、建空文件、执行 `BaseSchema`。

### 2. 角色库的新建入口

新加 `memory.CreateIfEmpty(ctx, file, snapshotDir, relName string) (created bool, rep dbguard.Report, err error)`。

- **只在“空”的时候建**，空指三种情况：文件不存在；0 字节；只有 `sumika_schema`、没有别的用户表。这正是护栏 `Decide` 给 `ActionCreate` 的条件（`dbguard/decide.go:82-83`；`UserTables` 不算 `sumika_schema`，见 `probe.go:38`），由护栏判定，不自己另写一套。
  - 先只读 `dbguard.Inspect`。判定不是 `ActionCreate`（有用户表）的，**立刻返回 `created=false`，不做任何别的检查**。之后交给 `memwrite.Open` / `memory.Open` 走原来的路，已有库在启动时的行为和改动前完全一样。（复核 C1：第一版对所有已有库加了列检查，缺列的旧库以前能只读挂、改后整体不启动，属于这一步不该带进来的变严，已去掉。）
- **位置先查**（复核 M2）：建库前确认库的位置是 `<数据目录>/go/characters/<角色>/memory.db`，而且已经存在的每一级（`go`、`characters`、角色目录、文件本身）都不是符号链接、联接或别的重解析点。
  - 不许建到数据目录外。
  - 和 `paths.CheckMemoryPath` 共用同一套判断（LESSONS“门和检查共用同一个算位置的函数”）：把它拆成一个内部函数，带一个参数表示“文件和末几级目录可以还不存在”，两个入口都调它。
  - 有链接就按建库失败处理（第 3 条的软退）。
  - 角色 id 先过 `memory.ValidCharacterID`，不合法的不建（复核 S1）。
- **走护栏**：`dbguard.Open` 跑 memory 轨，`OpenDB` 用 `openBaseDB`。
  - fresh 时先执行 `BaseSchema`，**放在一个事务里**，要么全建、要么一张不建（复核 M1；共用池同样受益）。护栏再跑 0001～0003、写版本表。
  - `OpenDB` 回调收到 `fresh=false` 直接报错“不是新建”，不在已有库上开可写连接（复核 S2）。
  - 建完以后 `sumika_schema` 里 memory=3，goose 版本表最大号是 3，和共用池从零建一样（`memory/guard_test.go:15-29`）。
- 父目录 `go/characters/<id>/` 不存在就建。
- **调用前就在的空文件**（0 字节或只有 `sumika_schema`，复核 M1）：
  - 先把它连同 `-wal`、`-shm`、`-journal` 挪到同目录的一个旁名（例如 `memory.db.empty-<时间>`），然后按“文件不存在”新建，护栏失败时会把新文件删干净。
  - 失败了再挪回原样；成功了就删掉旁名那份。它没有用户表，也就没有数据。
  - 这样“下次启动自动再试”对这种文件也成立。
- **失败**：返回护栏的 `Unavailable`（原因词 `create_failed` 等），或位置检查的错误。返回值里只有护栏这次的判定真是 `ActionCreate` 时，才标成“建库失败”；ctx 被取消时直接返回取消的错误，不标成建库失败、不发提醒（复核 S2）。
- `MigrateGuarded`（`memory-migrate` 用）照旧“不新建”。

### 3. 接进程序：`app.openMemories`

- 记忆插件启动时总是开着：`openMemories` 末尾用 `hub.Use` 挂上，`use` 无条件设成开（`turn/plugin_reconcile.go:516`），不读 `plugins.memory.enabled`。所以建库不看插件开关。运行中在界面关掉插件，不影响已经打开的库。
- 角色没有 `memory.db`（或者是空库，见第 2 条）：
  - 调 `CreateIfEmpty`；
  - 日志写一行“角色 X 没有记忆库，已新建空库（路径）”；
  - 然后照常往下走 `memwrite.Open`。
- **建库失败不拦启动**：这个角色退回今天“没有记忆库”的合同，也就是不挂记忆、守卫是真正的 nil、QQ 群和非主人私聊钳成试运行。另外做三件事：
  - 日志写一行；
  - 提醒一条（每个角色一个键，写明角色、路径、原因词）；
  - 下次启动自动再试。提醒只在内存里，重启后本来就没有，所以不用写“建成后清掉”的代码（复核 S3）。
  - 理由：“记忆库坏了就整体不启动”保护的是已有数据（`TestSend57BrokenMemoryDBStopsOpen`）。新库没有数据要保护；今天加一张卡、没有库，程序也照样起。不能因为一张新卡挡住主人另外两个角色的收发。
  - 照 ADR-379，这个停用状态的状态条目就是那条提醒，解除办法是修好原因（比如腾出空间）后重启。
- 建库在 `memwrite.Open` 之前做。写入是否开照旧走 `memwrite` 的前提检查（见下面），建了库不等于开写。
- 只看历史（archive）模式不走 `openMemories`（`desktop_memory.go:19` 的注释），所以不建。要核对这一点，并写测试。
- 角色卡读不了：没有库的跳过、不建、不挡别的角色；已经有库的照旧整体失败。两个分支都要有 app 层测试（复核 S6）。
- 建库成功以后，`memory.Open` 或 `OpenIndex` 再失败（比如角色目录里有一个坏的 `memory-v2.db`）仍然整体失败。这和已有库的角色碰到坏索引时一样，是改动前就有的行为，这一步不改，写进参考页（复核 S1）。
- **全新目录下写入前提怎么满足**（`memwrite.decide`，`memwrite.go:293` 起）。按顺序：
  1. 名单：第 5 条之后默认包含所有角色；
  2. 路径：库在 `go/characters/<id>/` 下、没有链接，自动建的就在这里；
  3. 已迁移：`CheckSchema`，自动建完就是 3；
  4. 首次开写的备份：`BackupMemoryDB` 拷进备份目录（`cfg.Backup.Dir`，空就兜底到数据目录旁的 `BackupRoot`）。
  - 测试只能让这几项真的满足，不许为了过而放宽任何一项。备份目录算不出来时照旧只读，并记原因 `backup_failed`。

### 4. 发送钳制和可见性的变化（高风险，进复核表）

- **发送**：
  - 现在：没有记忆库 → 守卫是 nil → QQ 群和非主人私聊被钳成试运行（`TestSend57NoMemoryDBContract`）。
  - 自动建库以后：“没有库”只剩“建库失败”这一种情况（第 3 条）。新建的空库有守卫，守卫是不是 full 照旧看嵌入（`GuardLevel`），发送照旧要过 `qqSendMode` 的七项检查（`qq.goSend` 默认关，`config.go:300`）。新角色和已有库的角色同等对待，**不另外放宽**。
  - 主人现在两个角色都已经有库，换 exe 后行为不变。
  - `TestSend57NoMemoryDBContract` 改成三个子测试：
    1. 建库失败（注入）→ 守卫是真正的 nil，群和私聊都钳住，有提醒（原合同加提醒）；
    2. 没有库 → 自动建，守卫在；嵌入没就绪时群和非主人私聊仍钳住；
    3. 嵌入就绪、七项都满足 → 跟档位走，和已有库的角色结果相同。
- **可见性**：新角色有了库，就能召回主人共用记忆（`shared/owner-memory.db`）。共用池按设计是给所有角色共用的，以前新角色召回不到，只是因为它没有库。这是可见性默认值的变化（AGENTS 第 4 条），**主人 2026-11-16 同意放开**（原话“共用记忆可以放开”）；写进参考页。
  - 范围是“数据目录里所有有卡（`characters/<id>/card/character.yml`）的目录”，不只是新装的角色，实验卡也算（复核 C2）。主人的真实数据目录现在只有铃音、铃花两张卡，两个都已经有库（2026-11-16 只看目录名核过），换 exe 后不会新建任何库。

### 5. “记住”默认开（ADR-377 第 1 条）

- `memory.write.characters` 的默认值从 `[]` 改成 `["*"]`，`"*"` 表示所有角色。
  - 显式写 `[]`：全部只读，不变。
  - 显式列名单：只开这些角色。主人现在的 `[suzune]` 不受影响。
  - `"*"` 不能和具体名字混写，配置检查报错，报错里说清楚“写了 `*` 就是全部角色，要只开几个就去掉 `*`”。设置页现在对这个键只显示不编辑（`settingsreg` 里是 `Label`）；以后做名单编辑时，在 `*` 上加名字要先去掉 `*`，这一条写进 `records.go` 的注释。
  - `memory.write.summarize` 同样认 `"*"`，默认仍是 `[]`。
- `internal/config` 给 `MemoryWrite` 加两个方法：`Remembers(id) bool`、`Summarizes(id) bool`。
  - 全仓直接拿 `Characters` / `Summarize` 做 `slices.Contains` 的地方，一律改调这两个方法。现知的有：`app.go` 的 `openMemories` 两处、`model_summary.go:43`、`memwrite.Wanted`、`cmd/core-check`、`cmd/turn-check`、`cmd/memory-shadow/issue17_checks.go`、`cmd/e2e-run/data.go`。动手前用 grep 再列一遍。

## 验收

1. **全新目录**：全新数据目录加一张卡，配置里不写 `memory`。`App.Open` 之后：
   - `memory.db` 存在；
   - `sumika_schema` 里 memory=3，goose 最大号是 3；
   - 每张表的列（用 `pragma table_info` 比）和“Bun 形状的旧库迁移到 3”的结果相同。
2. **端到端**：在同一个目录里，本地私聊经假模型脚本调用 `remember`。必须走真实工具路径：模型回工具调用 → memplugin → 写库，不许直接调 `Remember` 方法（LESSONS“新工具接进后台后验收覆盖完整路径”）。然后关掉程序、重新打开，召回（`memory_search` 工具或参考信息块）能找到这一条。
3. **旧库不被重跑建表**：
   - Bun 形状的旧库（`memtest.BunShaped`，带编造数据）启动后，数据一条不少；
   - `TestMemoryMilestonesUpgrade`、`TestMigrateBunShaped` 照样通过；
   - 已经迁到 3 的库，启动前后主文件字节相同。
4. **只在空的时候建**：
   - 有表的库（包括列不对、裁剪过列的）：`CreateIfEmpty` 不碰、不检查，启动结果和改动前一样（用改动前就有的夹具对照）；
   - 0 字节文件：建；
   - 只有 `sumika_schema`、没有别的用户表：建。
5. **建库失败**：注入三种失败（父目录被文件占住、`OpenDB` 返回错误、迁移失败）。迁移失败要用**完整的迁移文件**加一个坏的 0004，保证 0001～0003 真跑过。结果都是：
   - 程序照常启动，别的角色照常挂记忆；
   - 这个角色不挂记忆，守卫 nil、QQ 钳住，有一条带角色和原因词的提醒；
   - 调用前不存在的文件不留下（`-wal`、`-shm`、`-journal` 也不留）；
   - 调用前是 0 字节或只有 `sumika_schema` 的文件，失败后字节和原来一样；
   - 去掉注入再启动一次，自动建成。三种原始形状（不存在、0 字节、只有 `sumika_schema`）各测一次。
   - `BaseSchema` 半路失败（注入让第二条语句失败）后，文件里一张基础表都没有。
5a. **链接**：`go/characters/<角色>` 是指向数据目录外的联接，或者 `memory.db` 是悬空符号链接时，不在外面建任何文件，按建库失败软退并提醒；`paths.CheckMemoryPath` 原有的测试照过。
6. **启动时插件开关不影响建库**：配置里写 `plugins.memory.enabled: false` 也照样建、照样挂（核对现状如此；如果核对发现启动时其实读了这个开关，停下回报，不自己补分支）。
7. **只看历史模式**：不建库。
8. **默认值**：
   - 默认配置下 `Remembers(任意角色)` 为真，`Summarizes` 为假；
   - `characters: []` 时全部只读；
   - `["*", "a"]` 过不了配置检查；
   - 设置页显示“全部角色”；
   - 照主人真实配置的形状（显式只列一个角色，测试里用编造的名字）配置时，没列的角色仍只读。
9. **删抄本**：三份工具里不再有建表语句。`native/` 下的**非测试 Go 文件和 `.sql` 文件**（除 `store/testdata/milestones/`）里，`CREATE TABLE facts`（含 `IF NOT EXISTS` 写法）只出现在 `memory` 包的 `BaseSchema` 一处，用 archcheck 钉住。测试文件里的全量抄本（和 `BaseSchema` 列一样的那几份 `bunSchema`）改调 `memtest`；故意裁剪列的夹具留着，在它旁边写一行注释说明是故意的旧形状（机器分不出“故意裁剪”，所以测试文件不进 archcheck，靠复核看）。
10. **发送**：见设计第 4 条的三个子测试。

## 禁止的偷懒写法

- 在 `memory.Open`、`memwrite.Open`、`OpenIndex` 或任何只读路径里建库。
- 在已有库上无条件执行 `CREATE TABLE IF NOT EXISTS`。
- 绕开 `dbguard.Open`，直接 `os.OpenFile` 加 `Exec`。
- 写 0000 号 goose 迁移，或者手插 `goose_db_version` 行。
- 为了让测试通过，把 `TestSend57NoMemoryDBContract` 或 `TestMemoriesSkippedWithoutDB` 整个删掉。合同要改写，不许删。
- 读写真实 `data/`、改主人的配置。

## 已知的坑（照盘点）

- 坑 1、2：goose 没有 0 号，也没有“只标记”的接口。
- 坑 3：旧库重跑建表。
- 坑 4：建库必须在 `memwrite.Open` 之前。
- 坑 5：几方同时建库。一律走 `dbguard.Open`，进程内有同文件互斥，跨进程有数据目录锁。
- 坑 6：`memory-v2.db` 建不出来会让整个角色记忆打不开。新建的角色目录要可写。
- 坑 8：开写前备份的探针要求迁移后的表，所以必须在迁移完成后才允许开写。
- 坑 11：默认值一改，影响面不只一个常量。
