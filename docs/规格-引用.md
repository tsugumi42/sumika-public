# 规格：引用和分块消息（本地私聊）

状态（2026-11-08）：后台做完，已合 main；界面另做。

用户原话（2026-11-08，给了 Claude 桌面版的截图）："不单只是引用，最好还能针对引用内容回复消息……还能在一次用户消息里引用多个不同片段……还要保证这一个消息回复里面不同引用的回复和不属于引用的普通消息内容能够分开理解……这个格式要能让模型看懂，也要能够准确记录。"更早的要求（待办"/goal、/loop、回复引用和其他实用功能"第 ③ 点）："框选文字进行部分引用会更准确"；设计原则"引导加简单兜底，不给模型束手束脚"。

参考：[调研-agent客户端实用功能](notes/调研-agent客户端实用功能-2026-11-08.md) 第 1.3 节；QQ 收到引用时给模型的那一行（`channel/line.go` 的 `FormatLine`，「↪引用 名字：内容」）；QQ 出站引用见[规格-表情包和引用回复](规格-表情包和引用回复.md)。采用：reply_to 列照用（存第一个引用块的出处），分块和片段放进 `segments_json`，不加列、不迁移；"引用名字、时间、片段"的信息量同 QQ 那一行。不采用：QQ 把引用内容截 20 字的做法（本地引用的重点就是那一段，截 1000 字）；QQ 一条消息只能带一个引用，QQ 那边不改，本地结构不影响它。

## 一、做什么、不做什么

主人在本地私聊（主窗口，`local/console/private`）里的一条消息由**有序的几个部分**组成，顺序有意义：

1. 若干个**引用回复块**：被引用的出处（会话 + 事件 + 选中的片段 + 偏移）+ 针对这一段的回复文字 + 这一块自己的附件；
2. 一段或多段**普通文字块**：不属于任何引用的话，也可以带附件。

只填文字的旧输入等价于只有一个普通文字块，行为一字不变。

不做：本地群聊（`console:group:`）、QQ 引用（这两处的引用是“悄悄话”，见[规格-群聊引用和路由](规格-群聊引用和路由.md)；本规格只管本地私聊，互不影响）、引用图片或媒体段（只引文字；被引消息没有文字就拒绝）、**选中文字后浮层里的"开始侧边对话"（以后做）**。附件只做数据结构，真图怎么给模型由 `feat/real-images` 那条线做（第五节写了接口位置）。

## 二、接口

`native/internal/api/quote.go`：

| 类型 | 字段 |
|---|---|
| `LocalPart` | `Quote *LocalQuote`（非 nil 是引用回复块，nil 是普通文字块）、`Text`、`Attachments []LocalAttachment`；每块至少要有文字或附件 |
| `LocalQuote` | `Ref EventRef`（`Conversation` 必须等于发送的会话键，`Event.EventID` 是事件 id，`Event.Platform` 留空或等于会话平台）、`Text`（选中的文字，空白 = 整条）、`Start`、`End`（选区在原文里的字符 rune 偏移 `[Start, End)`，可选） |
| `LocalAttachment` | `Kind`（`image` 或 `file`）、`Media *MediaRef`（媒体库里的图，只收本会话、不带转发路径）、`Path`（本地文件路径）、`Name`（显示名，可选）；`Media` 和 `Path` 二选一，`file` 只收 `Path` |

两个发送入口：

- `api.LocalInputSubmission`：`Text`（旧）或 `Parts []LocalPart`（新），**二选一**，两个都给报错；
- `api.LocalPartsChat.SendLocalParts(ctx, key, parts, draft)`（可选接口，`DesktopReader` 实现）；`SendLocal(text)` 就是 `[]LocalPart{{Text: text}}` 的转发。

读回：`api.MessageView` 新增 `Parts []MessagePart`（分块消息才有，按发送顺序）：

| 字段 | 含义 |
|---|---|
| `HasQuote`、`Ref` | 是引用回复块、被引用事件的引用 |
| `Quote Result[QuoteView]` | 出处，`Ready` 时 `Text` 是被引原文、`Snippet*` 是选中的片段（见下）；被引那条后来看不到时 `Unsupported`，不交任何原文 |
| `Text` | 这一块的文字 |
| `Attachments []LocalAttachment` | 这一块的附件（`Media` 带回完整凭据） |

`MessageView.Text` 是各块文字用换行连起来的样子；`MessageView.ReplyTo`、`Reply` 对应**第一个引用块**（只看一个引用的界面照旧能用）。`QuoteView` 新增：`Snippet`（选中的那段，整条引用时等于原文）、`SnippetStart`、`SnippetEnd`（在 `QuoteView.Text` 里的字符偏移，都是 0 表示没有定位）、`SnippetWhole`、`SnippetFallback`（选中的文字不在原文里，`Snippet` 是原文开头）、`SnippetTruncated`。

## 三、校验（发送时）

在桌面入口 `DesktopReader.resolveLocalParts`（会话所有权校验之后）调 `desktopread.Service.ResolveParts`：

1. 每个引用块的目标用 `store.ReadDisplayEvent` 取，和读投影、媒体凭据是同一套范围校验和可见性过滤（`validateDisplay` + `displayFilter`），只在 `Ref.Conversation` 这一个会话里按 id 找，不另写一套；目标必须是 `kind=message`、没撤回、不是她没说出口的（`automation:dry-run`、`automation:self-skip`）、有文字。任何一条不满足都是同一个错误 `desktopread.ErrQuoteTarget`，别的会话、不存在、看不到不区分，别人探不出别处有没有这个 id。
2. 选中的文字：位置对得上就用；否则在原文里找第一处；都找不到不拒绝，退回原文开头 200 字、标 `Fallback`，记一行日志（只写会话和事件 id，不写正文）。片段超过 1000 字截到 1000，标 `Truncated`。
3. 附件：种类要是 `image` 或 `file`；`Media` 走 `mediaRow` 核对（凭据对得上本会话可见的事件，不带转发路径），`Path` 非空且不含 NUL；两个都给、都不给都拒绝。
4. 块：每块要有文字或附件；最多 20 块（`MaxParts`）；`Text` 和 `Parts` 不能同时给。
5. **任何一块不合格，整条都不发，也不写库、不请求模型**；错误写明是第几块（"第 2 块：……"），`errors.Is` 仍能认出 `ErrQuoteTarget` 等。不只拒那一块再发其余的：那样主人会以为整条都发出去了。界面要保留输入框和各块，提示是哪一块不行。
6. `turn.validateInput` 再收一道：`Input.Parts` 只能出现在本地私聊、主人身份的输入上；`SteerIn` 会清掉在跑那一轮自己的分块。
7. 只有一个没有引用、没有附件的普通块：`ResolveParts` 返回 `parts == nil`，整条走和旧纯文字输入完全一样的路径（不写分块存档、不设 reply_to、给模型原话）。

## 四、存档

主人这条事件照常存：`events.text` = 各块文字用换行连起来（记忆、搜索、导出看到的是干净的话；单个普通块就是原话）；另外：

- `reply_to` = **第一个引用块**的被引事件 id；
- `segments_json.local_parts` = `[]history.Part`，按顺序，每块：`quote`（`id`、`name`、`at`、`clock`（HH:MM，引用当时按本机时区定下）、`text`、`start`、`end`、`whole`、`fallback`、`truncated`）、`text`、`attachments`（`kind`、`name`、`path`、`hash`、`conversation`、`event`）。键叫 `local_parts` 是因为 `parts` 已被 QQ 出站计划占用。

`SubmitLocal` 路径里这条事件的 `segments_json` 本来就放着输入幂等凭证，分块时变成 `{"kernel_input_digest":...,"local_parts":[...]}`，仍整串比较：同一个 `ClientKey` 同一份输入重试是幂等的，换了块报冲突（`inputDigest` 已把分块算进去）；没有分块时输入摘要、存档的字节与加这个字段之前一模一样（`Input.Parts` 带 `omitempty`）。

名字、时间、片段都在发送当时定下并存档，之后改名、改时区、被引消息撤回都不影响她看到的那一段，重建历史也一样。读回时每个引用块的被引事件按原范围和可见性重新取（`DisplayRow.QuoteTargets`，和 `Reply` 同一套），看不到的块 `Quote.State` 为 `Unsupported`。

## 五、给模型的格式

没有任何引用、只有一个普通块：**原话**，不加任何标记（有附件时在后面每个附件一行占位，仍没有头）。其余（含只有一个引用块）用结构化写法，措辞固定、测试逐字核对（`history.Said`）：

```
（主人这条消息分了 3 个部分，按顺序排列。每个【回复 N】只针对它自己引用的那一段，【另外】的话不针对任何引用。）
【回复 1】引用了 示例角色 在 12:00 说的：「第二句在那」
主人对此说：这句是什么意思 [图片：截图]
【回复 2】引用了 主人 在 11:58 说的：「先说一段」
主人对此说：这句我是随口说的 [文件：C:\示例\笔记.txt]
【另外】另外今晚吃什么 [图片]
```

- 【回复 N】的 N 只数引用块，按出现顺序；【另外】是普通文字块，各自一行起头；
- 引用名字、片段用和 QQ 一样的转义（方括号换全角、"↪"换成"→"、多行片段换行后缩进），伪造不出框架头；片段被截断时在片段末尾加 `…（已截断）`；名字为空写"对方"；时间为空时写"引用了 名字："（旧存档兜底）；
- 引用块没有文字也没有附件时写"主人对此说：（没有写字）"（校验会拦，但写法要稳定）；
- 附件占位：图片 `[图片：名字]`（没有名字写 `[图片]`），文件 `[文件：路径]`；**以后接真图的位置是 `history.attachmentLines`**：模型能看图时那里改成交给模型的图片段、文字里只留编号占位，`feat/real-images` 那条线接；现在只有文字占位，识图描述可以直接放进 `Name`。

只影响这一条新消息，缓存只追加：

- 当轮：`runTurn` 追加用户消息时用 `history.Said`；中途插话（steer）送到时同样（`steer.parts`）；
- 重建：`history.SaidBy` 读 `segments.local_parts`；含引用块时要求 `reply_to` 等于第一个引用块的 id，对不上、片段为空、存档损坏都当没有分块，只给 `events.text`；所以实例重建、压缩后回放得到的文字和发送当时逐字一样；
- 不改历史、不给插件的检索文字（`Input.Text`、`OnLocalStored` 是各块文字连起来的样子，不含标记）。

## 六、sumika-ctl

`feat/ctl-chat` 的 chat 命令（给 sumika-ctl 加聊天命令）截至本规格完成时没有合进 main，这一项不做。以后加法：chat 的发送命令可重复写 `--quote <事件id>[:<片段>]`，后面紧跟的文字（`--reply <文字>`）成为这一块的回复，最后不属于引用的话是普通块；组成 `[]api.LocalPart` 走 `SubmitLocal` 的 `Parts`；不传位置，后台按文字找；被拒时把"第 N 块：……"原样报给命令行。

## 七、界面接线要注意

1. 偏移是字符（rune）偏移，不是字节也不是 UTF-16 单元；Go 里 `[]rune`。显示文字和 `MessageView.Text` 不同（表情占位、链接展开）时，传 `Text` 为选中的文字、`Start`、`End` 留 0，让后台按文字找。
2. 原文里同一段文字出现多次时，没传位置或位置对不上，后台取第一处；要精确高亮第几处就传对位置。
3. 高亮：`SnippetStart/End` 是 `QuoteView.Text` 里的偏移；`SnippetFallback` 时没有定位，只显示 `Snippet`（原文开头）；`SnippetWhole` 时整条都是引用；`SnippetTruncated` 时界面自己折叠，后台已截到 1000 字。
4. 气泡里按 `MessageView.Parts` 的顺序画每一块：引用块画"出处 + 片段 + 回复文字 + 附件"，普通块画"文字 + 附件"；`Parts` 为空就是普通消息，画 `Text`。点引用块跳回原消息用 `MessagePart.Ref`；原消息不在当前页时界面自己翻页。`Quote.State` 为 `Unsupported` 的块只画回复文字，不画片段。
5. 被拒（"第 N 块：……"）整条没发、没写库：保留输入框和各块，指出哪一块不行（"引用的消息已经看不到了"、"附件来源不对"等）。
6. 发送入口：纯文字仍可用 `SendLocal`；分块用 `SendLocalParts`（`api.LocalPartsChat` 类型断言取）或 `SubmitLocal` 的 `Parts`；只读、测试用的实现可以不实现，界面没取到就隐藏"引用"。
7. 输入框上方的引用条对应一个还没发的引用块；用户在几个引用条之间和普通文字之间的顺序就是 `Parts` 的顺序。

## 九、已知的坑

- 引用只存片段和当时的名字，不存原消息的媒体；被引消息之后撤回或看不到，主人那条的结构化文字仍是她当时看到的样子，读回时该块 `Quote.State` 取决于原消息是否还可见。
- 附件里的 `Media` 凭据只在发送时核对一次；之后媒体被清理，读回时凭据仍在，界面取不到图时按"图片已不可用"处理。
- `events.text` 不含标记，所以记忆整理、搜索、导出看到的是干净的话；要看她当时看到的样子读 `history.SaidBy`。
- 结构化写法的固定措辞（`partsHeader`、【回复 N】、【另外】、"主人对此说："）改了就等于改了所有带分块消息给模型的文字，旧存档重建出的文字会跟着变，缓存前缀随之重算一次；要改先想清楚。

## 十、图片附件的显示（2026-11-09，分支 `feat/attach-images`）

起因（主人 2026-11-09）："图片预览会不会长得太丑了？希望可以点开看大图，发出去的时候也没有预览，消息还特别长条。"

参考与采用：
- **本仓库的图片气泡**（[mediabubble.go](../native/internal/chatui/mediabubble.go)，照 Telegram Desktop）：只有图时铺满气泡、图加配文时图在上铺满宽度、多张按张数分行拼相册、按宽高比在加载前占位。采用：分块消息里的图直接用同一套 `albumLayout`、`albumGroup`、时间牌子，不另画一套。
- **看大图**（ADR-260，`chatLightbox`）：采用，同一条消息的图可以左右切换；输入框里的缩略图也走它。
- **Codex 桌面版的附件区**（拆解（私有存档）"附件与粘贴"）：附件圆角 = 输入框圆角 − 内距，和设计语言的同心规则一致，采用。它的缩略图只有 24 像素，不采用：这里缩略图要能看清是哪张。
- 可点范围不小于 24（WCAG 2.2 的最小目标尺寸）：关闭钮看得见的圆是 20，可点范围 24，透明的一圈在圆外面。

做法：
1. **取图走同一份缓存**。附件只有本地路径、没有后台的媒体凭据，所以用一个"本地文件"凭据（平台 `attach-file`，哈希位写路径，`native/attach_images.go`）。图片缓存的键、档位、淘汰、失败重试、看大图都照消息图片的老路走，只有"怎么取字节"在 `imageStore.fetch` 里按平台分流成直接读文件（上限和发送一致，20 MiB）。文件被删或读不到就是取图失败，气泡里画占位和文件名，大小不变，点一下重试。
2. **宽高进数据**。`history.Attachment` 加 `width`、`height`（`omitempty`，不迁移）：发送时读文件头量好存下（`mediastore.ReadImageMeta`，已按 EXIF 转正，和界面解码方向一致）；老记录每次读回时补量（只读文件头，在后台线程，不回写），读不到是 0，界面按 4:3 占位。输入框挂图时同样量好，待发气泡用它，和存好后的气泡是同一个比例，接替时不跳（LESSONS"虚拟列表为图片、视频存宽高并按比例占位"）。
3. **展示段**。分块消息的图附件在 `msg.segs` 里追加图片展示段，`PartAtt{Show, Pos, Width, Height}` 记它的序号；点开大图、右键菜单、被引时的缩略图都复用消息图片的现成逻辑。待发气泡（`pendingParts`）和存好后（`chatParts`）走同一个 `bindPartImages`。
4. **排法**。第一块有图时，图铺满气泡（贴着左右边，圆角由气泡裁），块里的引用卡在图上面、自己离气泡上、左、右、下各一个竖内边距，文字和标签自己缩进；有没有表情回应、注释都一样（表情回应条离左、右、下和上面的图各一个竖内边距，时间挂在条的行尾；注释和时间同在一块牌子里）。顺序是引用、图、文字、文件标签。第一块没有图、图在后面几块里时，图缩在内边距里、用最小内层圆角。（2026-11-10 `fix/image-msg-layout` 起：此前引用在图上方、表情回应、注释时图会退回带圆角、缩进的旧排法。）
5. **"长条"的根因**：`measure()` 里分块消息一律 `Blocky = true`，后面 `if l.Blocky { Fit = TextW }` 把气泡取满整列宽。改成和普通消息一样按内容量宽：文字最长一行、引用块（名字和片段）、文件标签、相册宽，取最大。
6. **输入框缩略图**：72 的方块、`Cover` 铺满、圆角和外框同心、没有底下那圈灰；点缩略图看大图，关闭钮是它的兄弟元素，点它只移除。缩略图只解 384 宽的小图（一张 8000×6000 的照片整张解开要 192 MB，缩略图 0.44 MB）。文件、文件夹、折叠的粘贴三种小标签（高度、圆角、关闭钮）同一族不变，截图一起看过。

验收对应：`native/internal/chatui/parts_images_test.go`、`composer_images_test.go`、`native/attach_images_test.go`、`native/internal/desktopread/attach_dims_test.go`。

已知的坑：
- 拖进输入框的图只记路径：发送后原文件被挪走或删除，气泡里显示"图片没取到"和文件名（粘贴的图存在媒体库，不受影响）。以后要稳，可以在发送时把拖入的图也复制进媒体库。
- EXIF 方向只在长边不超过 2048 的 JPEG 上转正（`decodeStatic` 的老规矩）；宽高量法与它一致。
