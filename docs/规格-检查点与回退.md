C9 专项复核 OMP 同一 `tools/checkpoint.ts`：实际实现只返回会话 rewind 请求，没有文件恢复 I/O 路径；summary 的 git-based 字样不能当并行文件恢复的证据。本轮速度优化优先检查串行包 I/O、重复整理和实际 Windows 调用，再量并发；不削弱逐文件 CAS、持久发布或路径边界。

选择内容寻址的原始字节快照，不依赖 git exe、仓库状态、attributes、换行转换或 hooks。仅用 Go 标准库和已有 x/sys：当前需求是有界文件恢复，不引入版本库 SDK。与 shadow git 相比，原始字节和路径边界更容易验证，代价是 PowerShell 捕获要读取有界工作目录。

目标：每个内置 write/edit/powershell 真正执行前有可冷恢复的检查点；恢复到某一步之前或某回合第一次写入之前；恢复本身可撤销。先交后台与 sumika-ctl，界面只定接口。聊天、模型账本、审批历史、已发送消息、外部命令副作用均不回退。

沿用：Invocation 的 RootID/RunID/StepID/ToolID/Scope、审批、Lifetime、ResultStore、工具真实退出。新增：检查点原始字节存储及回退服务。一次性：临时 smoke/量测/改坏脚本，验收后删除，不进入运行依赖。

## 二、捕获时机和范围

1. 每次 write/edit 审批通过、项目说明前置完成之后，在真正调用执行体前捕获参数解析后的目标；同一步执行完（成功、业务错误、取消都算）捕获后态。未知是否写成不能按“没变化”处理。
2. （已被 2026-11-08 修订改为：powershell 只拍分析出的目标文件，不再扫整个工作目录。）保存时只保留前后不同的文件。扫描包含未跟踪文件、二进制和空文件；不读取用户 Git 索引、不应用 .gitignore。
3. 工作区是本轮 CWD，不自动扩到 Git 根；不追 .git 文件到主 checkout。write/edit 目标在 CWD 外时该调用明确拒绝：检查点模式不能承诺范围外恢复。
4. 固定排除任何层级 `.git`（文件也排除）、`node_modules`、`.venv`、`vendor` 目录及 Sumika 当前数据根；整目录 shell 扫描另外排除现有 policy 的受保护目录和 `.env` 类文件，不能借一次命令审批批量读取凭据。显式 write/edit 指向固定排除路径拒绝；普通受保护文件只有原 Gate 已逐次批准该目标才捕获。shell 结果写明这些目录/受保护文件、工作区外路径、后台派生进程和网络/数据库/系统状态不受恢复保护；这是备份范围，不是沙箱。不能声称 shell 所有副作用可撤销。
5. 不在 prompt 入口全量复制；回合检查点是本 RunID 第一条变更记录。无文件变更的执行仍留身份/状态，避免把未执行、没变化、未知混为一谈。子任务经过同一内置执行入口，保存原子 Scope/Invocation，另存可信 RestoreOwner：foreground 为自己，child 由宿主读取 EcosystemStore.Task(RunID) 的 TaskRecord.Owner，校验任务 RootID/ParentRunID 和 internal:RunID 一致后绑定。主人 list 在原本地会话下列出所属 child 的独立记录，按 ID 显式恢复；不凭 Root 授权、不复活子授权、不把 internal 会话伪装成 console。
6. 一个服务级互斥门串行化内置变更捕获、真正执行、后态持久化和回退；跨会话也走它。取消等待可退出。门持有到实际工具退出及后态保存，不能 timeout 后提前释放。普通只读工具不占门。

### 2026-11-08 修订：拍不成也照做、命令只拍目标文件

起因：真实程序里让角色跑 `Get-Date`，工作目录（约 2.18 万个文件、12GB）超过 10,000 个文件的上限，`Run` 返回 ErrLimit，工具不执行，整轮失败。用户原则：引导加简单兜底，不给模型层层限制，不写防御性代码，不打临时补丁，参考成熟项目。用户后来又问“快照设计大部分 agent 都会全局用吗？不是的话默认不开也没关系吧”，据此收窄范围。

借鉴：
- Claude Code：只给自家写、改文件工具留快照，跑 bash 不追踪（见上表 checkpointing 一行）。本实现 write、edit 照旧默认拍；powershell 只拍分析出的目标文件。
- Codex：`codex-rs/core/src/config/mod.rs` 的 GhostSnapshotConfig（`ignore_large_untracked_files/dirs`）说明它对大目录的做法是跳过和告警而不是中止；当前树该配置已是 legacy，快照本身不再生成（同文件注释）。借“太大就跳过并说明，不挡住动作”。
- opencode-v2：未找到可借的快照源码（`packages/core/test/snapshot.test.ts` 只有测试），不引用。

规则：
1. write、edit：目标文件正常拍。
2. powershell：审批门已用 `policy.Analyzer` 拆过命令；执行前用同一分析器再分析一次（常驻进程、毫秒级；不改 kernel 和审批接口，不把判定结果穿过 turn。分析超时或没有分析器按“看不清”）。得到 `policy.Verdict` 后：
   - `ReadOnly`：不拍，不留记录，结果不加话。
   - 目标清楚（没有 Opaque、Unclear、Runs、MethodRisk、MustAsk，`FileTargets` 非空，命令里没有 git、curl、wget、robocopy、xcopy、icacls、attrib、mkdir、md、new-item、ni、expand-archive 这类改动列不全的）：只给 `FileTargets` 里工作目录内、不在固定排除范围内的普通文件拍快照；含通配符、目录、链接、工作目录本身、不能保存的文件名的，按看不清处理；工作目录外和固定排除的目标略去，略去后没有目标就不拍。
   - 看不清：不拍，**不再扫整个工作目录**，工具照常执行，结果里写“这次没拍快照（看不清这条命令会动哪些文件），改动不能用检查点回退。”，并留一条 `skipped` 记录。
   - 库里仍保留 `Paths == nil` 的整目录捕获：旧记录（`Whole`）的 recovery 要用它，库层测试也用；应用层不再调用。
3. 拍不成不阻止动作：捕获前的 ErrLimit（文件数、目录项、深度、字节、单文件超限、存储容量或记录名额腾不出）、拍的时候文件在变（ErrConflict）、非普通文件或不能保存的文件名，都视为“拍不成”：工具照常执行，结果里加“这次没拍快照（原因），改动不能用检查点回退。”，写一行 slog 警告，记录里留 `Status = "skipped"` 和 `SkipReason`。记录本身也存不下时只执行、不留记录。
4. 仍然拦住的：链接（ErrLink：硬链接、联接可能把写入带到工作目录外，拍不了快照时更不能放过）、身份和授权失败（`Admit`：ownerScope、子任务绑定、`Authorize`）。所有会执行的路径都先过 `Admit`，包括只读和看不清的命令；`ErrUnavailable`、读写错误、取消不放行。
5. 后态保存失败（命令建了超过预算的文件）：命令已执行，结果照常交回并附“不要重跑，改动不能用检查点回退”，记录保持 `interrupted`，不再让整轮失败。
6. `skipped` 记录：没有快照内容；`list` 显示“未拍快照”和原因；预览、恢复它得到 `ErrNoSnapshot`（“这次执行没有拍快照，不能用检查点回退”）；它不挡住同回合其他记录的 step、turn 回退（它动过的文件由当前状态与后态的 CAS 比对把关）；不产生 Notices；和别的记录一样被清理。
7. 清理（用户 2026-11-08：“快照本身也要做好清理，不然占用空间很大”）：规则是 30 天、100 条、512 MiB，由旧到新删，除被 pin 的以外不分状态，包括 interrupted、partial、skipped。触发时机：拍新快照前，以及服务打开时各清一遍；没有 record.json 的孤儿目录在打开时清掉。腾不出（全被 pin、单次预留超过总容量）按第 3 条处理，不中止。

新增 `tools.checkpoints.enabled`，默认 true（我定的暂定资源/恢复行为；权限不变）。关闭时明确没有自动快照。其他限额固定在服务 Options，不扩配置面。

## 三、存储、容量和冷恢复

落点 `Paths.CheckpointsDir()` → `<data>/go/work/checkpoints/`。每条随机 128-bit ID 的目录有 `record.json` 和原始字节包 `data.bin`；SHA-256 → offset/bytes 索引定位包内对象，同条 before/after 相同内容只存一次。元数据含版本、sequence、创建时间、完整 Invocation、RestoreOwner、RunFirstID、工作目录、根身份、工具名、状态、路径及 before/after 的存在位、hash、bytes、mode。RunFirstID 在同 Run/Scope/CWD 的后续记录中沿用；首条被轮换后 turn 明确不可用，不以剩余首条缩小承诺。不接模型指定的落盘文件名，ID/hash/包名和偏移长度在边界校验。

先追加完整 before 对象到 data.bin，再一次 Sync/Close 包文件，之后原子发布 pending 元数据，之后才执行工具；执行后追加 after 并在 ready 发布前 Sync/Close。减少的是每对象 Sync，不省略执行前的持久化屏障。正常收尾把只被变化文件引用的对象写入独立 `ready.bin`、Sync/Close，再原子发布引用新包名/索引的 ready 元数据，最后删旧包；崩溃始终至少有元数据引用的旧包可用，不原地重排偏移。对象或元数据保存失败返回基础设施错误，不能继续派工具或重跑原命令。取消后的收尾用 WithoutCancel；仍受固定采集限额，不能无界扫描。进程重启遇 pending：列为 interrupted，保留 before；禁止正常回退（缺可信 after），通过显式 recovery 预览冻结当前内容再审批恢复，不自动执行。

整理函数分别返回“结局元数据是否已持久发布”和收尾错误；新包索引仅在元数据发布成功后更新返回记录，旧包回收错误不会抹去已提交结局。恢复结局保存失败时返回记录和当前进度为 interrupted，保留实际完成路径与逆 ID；不把仅在内存里设过的 ready/partial 当成已保存。

对象已写成但 pending 未发布即崩溃的目录，在下次服务打开且取得应用已有数据组排他锁后删除（只删固定 ID 目录内、没有 record.json 的自有材料）；有 pending 的绝不清理。所有枚举分批每次最多 128 项，目录项和深度预算也用于后态 WithoutCancel 收尾；超限保留 before、标 interrupted，不把后态当完整。

轮换先将 record.json 持久改名为 record.delete，再删除该 ID 目录的包和退役元数据。删除中断留下的目录没有正式元数据，冷打开按上述自有孤儿规则继续清理；未退役且正式元数据引用缺包仍报损坏，不吞掉。借 Kopia content_manager.go 的逻辑删除与 maintenance/pack_gc.go 的物理回收分离，仅借顺序、不移植其跨客户端宽限期。

恢复逆记录在工作区 I/O 前持久保存 After 目标路径；按同一排序和逆 ID/序号确定同目录材料精确名。每次恢复另建 `materials.jsonl` 身份日志，先持久发布日志名；临时文件独占创建后、正文写入前，或源文件移动为墓碑前，追加父目录和文件的卷号/文件索引并 Sync。冷打开只检查这些精确路径，同时比对原工作根、父目录、文件身份；Windows 用 FileDispositionInfo 删除已核验句柄，核验后换入同名文件也保留。缺登记、登记截断、身份不符、目录替换均保留材料并告警，不凭名字认归属、不遍历工作区。其它平台没有句柄删除原语时拒绝回收，返回错误；不退回按名删除。

工作区已移动、根身份变化、父目录换路或材料清理失败时，仅拒绝回收并记录 checkpoint_id 和错误告警，后台仍可打开存储、列出记录；后续恢复的根身份/路径边界照旧拒绝。存储元数据或引用包损坏仍在打开阶段报错，不与可选的工作区材料回收混为一类。

我定的预算：单文件 16 MiB；一次扫描及合并恢复计划 10,000 个普通文件、20,000 个总目录项、深度 64、64 MiB 原始字节；单记录最多 before+after 128 MiB，元数据最多 8 MiB；整个存储 512 MiB（包括元数据），保留最多 100 条、30 天。到期、条数、空间超额时由旧到新移除记录，除被 pin 的以外不分状态（2026-11-08 起 interrupted、partial、skipped 也清）；容量腾不出时这次不拍快照、工具照常执行（2026-11-08 修订）。捕获前按最坏双包 256 MiB + 双份元数据 16 MiB 预留空间；单目标预留 64+16 MiB；合并计划逆操作按同一完整预算预留。清理发生在新捕获前和服务打开时，服务持门；不启动定时扫描。恢复时 pin 计划引用的记录，不让为逆操作腾空间的轮换删除目标。恢复旧记录若已过期明确报 expired/unavailable。

选择依据（Windows 临时目录原语验证，非产品性能验收）：10,000 个互异 4KiB 文件逐对象 Sync 的首次捕获 25,295.985 ms；单包按阶段 Sync 的首次捕获 2,086.425 ms，后两遍 1,279.313 / 1,360.902 ms。原语同时证明 os.Root 越界拒绝、Rename 覆盖及二进制/CRLF 原样。输出在任务 scratch 的 primitive-probe.log / packed-probe.log；因此换包内内容寻址，不放宽 C9 的 10s。最终仍须跑正式服务的三遍验收。

目录及对象不交给 result_read 任意访问；摘要作为现有工具结果的一部分，经现有 finalizeTool/ResultStore 留证。检查点 ID 只能由精确 RestoreOwner 的本地私聊读取，原执行 Scope 仍保留审计。SHA 相同不产生跨 Scope 读取许可。

## 四、恢复计划与提交

后台接口由桌面 `api.CheckpointActions` 提供 ListCheckpoints、PreviewCheckpoint、RestoreCheckpoint，以及 ReadCheckpointProgress、WatchCheckpointProgress、CancelCheckpointRestore；key 均通过现有 localCharacter 所有权校验。mode 为 step / turn / recovery / resume。recovery 冻结当前内容并撤回缺后态或部分恢复的已完成部分；resume 仅接受 pending/interrupted/partial 的恢复逆记录，使用文件发布前已持久冻结的 After 目标完成剩余部分。二者都重新预览、冻结 version 并单次审批，不自动重做。

计划按选中记录的执行 Scope + 工作目录选链，把每个路径首次 before 作为目标、最后 after 作为期待当前态；路径间的记录链必须连续，否则冲突（中间人工改动也不能悄悄抹去）。遇其他执行 Scope 后续重叠变化拒绝，父和 child 也不自动合并。普通 plan 要求当前存在位、原始 SHA 和 mode 都等于期待态；缺失、外部更改、目录替代均冲突。version 为计划、当前文件状态和记录水位的 SHA-256；审批后重新生成、必须一致。没有 force 参数。

Windows 链键使用实际父目录的卷/文件身份及 FileCaseSensitiveInfo：仅不区分大小写的目录用系统 RtlUpcaseUnicodeString 的大写表生成叶子键，现存与缺失叶子一致；目录规则未知时保留敏感。句柄路径比较使用 CompareStringOrdinal(TRUE)，不用 strings.ToLower/EqualFold 的通用 Unicode 折叠。Before/After 的展示名分别保留，计划的 Path 为目标名、CurrentPath 为当前名；同字节但仅大小写改名也进入恢复，逆检查点保存两边名称，可再次撤销。工作目录链绑定 RootIdentity；跨域重叠也使用同一套文件键。

显式 recovery 冻结非整树记录的当前态时，Windows 从已打开并核验的文件句柄取实际目录项路径，再以该拼写扫描；不能用请求别名覆盖真实名称。逆 pending 的 Before/After 分别保存改名前后名称；发布后硬退出仍能恢复仅大小写差异。

恢复总是：取得变更门 → 验证计划及所有目标对象的 hash/字节数 → 冻结逆操作并持久化 pending → 逐文件原子替换/删除 → 保存真实完成路径与结局。每个替换用同目录可写临时文件，Sync、Close、原子 Rename；快照为只读时，持久发布后由同一发布句柄设置属性并再次 Sync，错误进入 partial。不得先删旧文件，不解除现有用户目标的只读属性。删除只对该记录明确从不存在变成存在的普通文件，不能递归删目录。新建的空父目录可保留，避免误删用户并行建立的目录。

恢复删除先将普通目标持久改名为同目录 `.sumika-checkpoint-<逆ID>-<序号>.delete`，同一目标卷的改名屏障成功后才清理墓碑、登记 Done，全部完成后才能发布 ready。墓碑清理本身无需充当目标名删除屏障；中断时最多遗留已登记的自有材料。屏障错误进入 partial，进程退出保留 pending；显式 recovery 从逆包恢复，不依赖目标卷与检查点卷相同。

发布 worker 各复用一个已打开的父目录 Root 和目录文件句柄；按相对叶子做 I/O，减少 Windows 为每个操作逐段重开父路径。初次打开核对目录实际路径，每个文件仍核对实际文件句柄，临近替换/删除再核对父目录句柄最终路径。Windows 发布的源以 NtCreateFile 相对目录句柄打开，目标使用 NtSetInformationFile + FILE_RENAME_INFORMATION.RootDirectory，相对叶子改名后 FlushFileBuffers 同一源句柄；不再按 Root.Name 拼绝对路径。其它平台 rename 后同步父目录。缓存不等于缓存安全结论。目录不存在时只在 pending 已持久发布的恢复阶段补建；换目录或 worker 退出先关自有句柄，关闭错误进入 partial 结局，所有 worker 真实退出后才释放服务门。

跨文件不宣称原子事务。第二个文件失败，记录 partial 和已完成列表，保留逆操作；错误包含 inverse ID，主人可预览 recovery 撤销已完成部分。进程在恢复中被杀同样保留 pending，不自动重放。恢复成功的新记录可按 step 再恢复，达到撤销回退。重复提交旧 version 必须冲突，不能重新覆盖。

恢复会写真实文件，所有入口始终经过现有 Approvals 的单次卡片；Options 只有 once/deny，不认 yolo、对话或始终授权。卡片展示工作目录、目标步骤/回合、相对路径、存在变化、hash、总字节和不可撤销范围。审批发生在取得变更门前；审批期间不挡其他工作，批准后重算 version。服务只接受宿主提供的可信 owner Scope，模型 JSON 不带角色、账号、Authority 或工作目录。

宿主 restore 在预览和批准后都检查 RestoreOwner 的本地会话没有活动/排队输入及所属 child，忙则要求先停止，不替用户自动取消工作。恢复提交在 Hub 同一输入准入锁下占用该会话专属屏障，Submit/Respond/StartInternal 都不能越过；屏障内完成版本复核、恢复、事实/通知和 Live 失效。只要可能已改文件，partial、取消和结局保存失败同样失效旧 Live，再放开屏障。捕获/恢复共用服务门；其他会话之后的写入仍是新操作，不承诺阻止恢复结束后的编辑。旧 Authority 只作历史归属，不当授权：每个入口用当前 localInputScope 和 authority.Resolve 重检；重启若同一个完整 Scope 重签成功可读旧记录，已撤权且未重签则拒绝。

Restore 不调用模型、不新建根预算、不退款旧 token/tools、不删除 steps。创建宿主独立恢复步骤（Kind foreground，原 Root 关联，新的 Run/ToolID），登记 Lifetime、StepStart/StepEnd；审批同 Invocation。完成事实与逆 ID 写工具结果；变更保存失败照实返回。每条恢复记录同时是按精确 RestoreOwner 保存的持久宿主通知源（真实完成路径、ready/partial/interrupted 状态、inverse ID），不依赖原 Root 工具结果配对。下一回合准入时由现有 Config.Materials 接纳到当前 Root，材料 ID 为 checkpoint:记录ID:当前RootID 的稳定摘要（kernel_material_inputs.id 为全库主键，不能跨 Root 复用同 ID）；调 PutKernelMaterial，冷重建按 KernelMaterials 投影成独立宿主资料。新 Root 同样能读到最近恢复事实。幂等接纳、Scope 隔离，不改聊天事件、不自动重做工具；通知源保存失败会阻断恢复，结局写失败保留 pending 待 recovery。

恢复操作按精确 owner Scope 登记 context；独立状态锁不占文件变更门。准备、restoring、finalizing 每 200ms 发布累计状态，计数仅在逐文件持久发布成功后增加。界面订阅保留最新累计值及终态，关闭等待查询退出；服务只保留活动操作及一个最近终态，冷查询由持久逆记录投影。取消只作用于指定 owner+目标/逆 ID，停派后等待所有 worker、包和目录句柄及结局发布结束才返回，不能把取消请求已受理当作 I/O 已退出。终态同时列 Completed、Remaining；出错但发布可能已经发生的未完成项不宣称未动，显式 recovery/resume 重新扫描实际状态。

进度同时包含 OutcomeSaved 和 Error，并贯穿桌面 API、ctl JSON 的 outcomeSaved/error 和文本 status/cancel。OutcomeSaved=false 的终态明确要求重新预览 recovery/resume；当前 Completed 为实际完成路径，冷开 pending 只能投影为 interrupted，未落盘 Done 和错误正文不可重建。已保存 ready/partial 的冷查询 OutcomeSaved=true；冷开不补造上次进程的错误文本。旧包清理失败时结局可能已保存，仍按 ready/true 暴露收尾错误。

订阅创建分两步：宿主同步调用 WatchProgress，绑定当前活动操作或在独立状态锁下登记等待观察器，再在 goroutine 调 ProgressWatch.Run。Restore 登记新操作时在同一把锁内按精确 owner+目标/逆 ID 绑定匹配观察器并移出等待表；不靠轮询发现短操作。没有活动操作时先发目标 ID 的 idle，历史 ready/partial/interrupted 只用于查询。绑定后一直观察同一操作对象，按其 done 结束；即使回调暂停、Run 尚未启动，或多次不匹配恢复覆盖最近终态，也保留本次结局。等待期间 context 取消会释放登记，Run 因回调错误、撤权或取消返回也会释放；订阅 Close 取消查询 context 并等待 Run 退出。

## 六、sumika-ctl 与界面契约

`sumika-ctl [--json] checkpoint list <本地会话>`；`checkpoint preview <本地会话> <ID> [step|turn|recovery|resume]`；`checkpoint restore <本地会话> <ID> <version> [模式]`；`checkpoint status <本地会话> <目标或逆ID>`；`checkpoint cancel <本地会话> <目标或逆ID>`。restore 保留同步最终回复，等待期间另一条 ctl 可查阶段及已恢复 N / 共 M 或取消。cancel 返回时所有恢复 I/O 已退出，给出已完成/未完成路径与逆 ID；继续操作使用该逆 ID 重新 preview recovery（撤回）或 resume（续做），再 restore 并在主窗口单次批准。不接受 force、approve、任意文件路径或审批模式参数。list 最多 100 条，权限、错误码沿用现有入口。

未来界面：工具卡挂检查点 ID 与“查看变化”；会话右栏按回合/步骤列出时间、变化路径/字节、状态；“回退”先 preview，再现有审批。失败显示已恢复路径和逆 ID，不能只写“失败，请重试”。本轮不画 UI，也不修改角色卡。

## 十一、C9 正式口径与三遍量测（依据 ADR-271）

主人 2026-11-05 以 ADR-271 确认本口径：常用规模量延迟，10,000 文件作为吞吐、可取消、有进度的压力测试；大小写改名、只读文件继续支持。原 C9 失败结论及当时的数字、退出码原样保留（见存档（私有存档））：最终原门槛恢复 24.35/25.32/24.64 秒、捕获 11.14/10.88/11.43 秒，仍是旧口径下的失败。

延迟预算参考 [NN/g 原文 Response Times: The 3 Important Limits](https://www.nngroup.com/articles/response-times-3-important-limits/)（1993，2014 补充）：0.1 秒是即时反应、1 秒是保持思路连续、10 秒是注意力及长任务反馈边界；原文未规定 P95。沿用量测前冻结的 <100ms 捕获、<1s 常用恢复工程预算，不按本轮结果倒改阈值。

| 档位 | 固定工作负载及统计 | 正式验收 |
|---|---|---|
| 常用回退 | 1 / 10 / 50 个变化文件，每个 4,195 字节，含二进制与 CRLF；每档每遍 21 个独立 fixture，共三遍。P50 取第 11 个、P95 取第 20 个（排序、nearest rank），保留所有单次值 | 单文件捕获 P95 <100ms 沿用即时反应预算；三个档位恢复 P95 <1s，按 NN/g 思路连续边界。恢复包括逆包、CAS、Sync、持久改名、结局保存及实际 I/O 退出；Preview 在恢复计时前另行执行 |
