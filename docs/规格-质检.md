## 一、挑什么（四类）

| 类 | 规则（第一步全部用规则数，不调模型） |
|---|---|
| 工具摩擦 | ①同一轮里失败的工具调用后 3 步内出现同名工具、参数相似（归一化后编辑距离 ≤ 30% 或同一路径）的调用；②同一命令一轮里跑 ≥ 2 次；③Edit 报找不到原文，随后又读同一文件；④命令或参数里出现已知坑：`/tmp`、`> nul`、`cmd /c start` 看到就算；`/c/` 式盘符路径只在同一次调用报错、或同一段命令的程序是 .exe / powershell / pwsh / cmd / go / python / py 且把这种路径当参数时才算（Git Bash 自己用 `cd /d/...` 没问题）；heredoc 写含反斜杠的内容只在同一次调用报错、或之后 3 步内又 Write / Edit / 再次 heredoc 写同一个文件时才算；CRLF 警告文字只记“观察”，不进反复出现（2026-11-11 改，见第七节） |
| 成本异常 | ①某会话相邻两轮缓存命中率掉 ≥ 30 个百分点且输入总量没大变（多半是前缀被改）；**相邻两轮间隔 > 5 分钟的不算（缓存已过期）**，会话第一轮和压缩后第一轮不算；②单轮输入总量超过该会话中位数 3 倍，**且输入总量 ≥ 20k**，会话第一轮和压缩后第一轮不算（trace 认不出压缩，只排每组第一轮）；③群聊里调了回复模型，但前 10 分钟内同角色同群没有任何放行记录（enter / forced / merged），只记“观察，待核对来源”（ADR-352 第 5 条；原写法“skip 之后又有调用”已废，见第七节） |
| 插件和网络 | ①`task_runs` 按 模块 × 类别 × 站点数失败和退回次数，和前 7 天平均比；②连通性：Magpie `127.0.0.1:3425`、代理端口、SnowLuma 连接状态各探一次（只连本机、只读，不发消息） |
| 反复出现 | 同一条模式（类别 + 归一化后的特征）在最近 7 天里出现在 ≥ 3 天，标“该修到工具层” |

每条命中记：类别、特征（归一化后，比如“Bash：`/tmp` 路径”）、次数、估计多花的 token（失败那一步到成功那一步之间的输出 + 输入增量；算不出写“未估”）、一个例子的位置（会话 id + 时间，**不带原文**；命令只保留程序名和参数形状，路径里的用户名、群号、QQ 号打码）。

## 二、出什么

一份 Markdown，三节：

1. **摩擦榜**：按估计多花的 token 排前五，每条一行“类别｜特征｜次数｜约多花 token｜例子位置｜建议（修工具 / 写 LESSONS / 观察）”。
2. **成本和网络**：命中异常、暴涨轮次、失败率比 7 天平均高一倍以上的插件和站点、连不上的服务。
3. **反复出现**：连续上榜 ≥ 3 天的，写“建议修到工具层”。几乎天天出现（7 天里 ≥ 6 天）的“常驻”最多占两行，其余写“另有 N 条常驻”。

没有命中写“没有”。第一步不调模型；第二步可选在最后用便宜模型把三节压成三五句话（只给它表格，不给原文）。

## 五、禁止的偷懒写法

- 不许把聊天原文、命令全文、完整路径放进报告。
- 不许在第一步就调模型做判断（规则先跑出来，看清误报再说）。
- 不许为了让榜单好看去掉某类命中；规则改了在本规格写清楚。

## 七、试跑记录

### 2026-11-11 第一次真跑（改规则之前）

- 范围最近 24 小时，命中 350 次。摩擦榜前五里 `/c/` 盘符路径 254 次、heredoc 含反斜杠 56 次，这两条占了大半。
- 误报原因：
  - `/c/` 盘符路径：Git Bash 里 `cd /d/Projects` 本来就能用，真正的坑只是把这种路径交给 Windows 程序。
  - heredoc 含反斜杠：写 Python、正则时反斜杠是正常内容。
  - CRLF 警告：git 的常规提示，几乎每天都有。
  - 单轮超过中位数 3 倍：会话第一轮、压缩后第一轮、总量很小的会话都会触发。
  - 缓存命中率骤降：规则里没排除缓存过期。第一次的 3 次命中间隔分别约 54、24、23 分钟。
  - 常驻命中把“反复出现”占满。
  - “门槛没放行的角色也调了模型”10 次：全是配对错误（见下）。
- 改法：见第一节对应各条（2026-11-11 同日改）。

### 门槛那条的核实（只读 trace 副本）

- 原写法：拿 `gate_decisions` 里 skip / muted 等“没放行”的那一行，去配 2 分钟内同角色同群的 reply 调用。10 次命中全部是错配：同一批消息里，skip 的前后几秒到几十秒都有 enter，那次调用是 enter 触发的。skip 之后的调用不能算“没放行却调用”。
- `gate_decisions` 和 `model_runs` 之间没有能直接关联的 id（门槛行只有 seq / batch，模型行有 turn_id / root_id，两边不互相引用）。
- 改成反过来看：最近 7 天群聊里 275 次 reply 调用，270 次前 10 分钟内同角色同群有放行记录；5 次没有，集中在同一个群。这 5 次来源待核对（可能是上一轮回复拖得很久、别的入口触发、或门槛记录缺失），所以规则只记“观察，待核对来源”，不判定为 bug。放行记录写入见 `native/internal/channel/gate.go`（593、639、752 行 enter / forced）。

### 缓存命中率骤降 3 次的核实

- 三次的相邻两轮间隔分别约 54、24、23 分钟，模型和线路没变（同一个 deepseek 路由），输入总量约 7k，6 个调用里有 3 个是实例新建后的第一步（rebuild 记 fresh）。
- trace 里没存请求原文（`request_json` 为空），能比的只有 `sections_json` 的段 hash 和 `context_json` 的分类计数。系统提示词前 7 段（core、persona-*、scene-group、platform-qq、shell-pwsh）三次的 hash 都没变；变的只有末尾追加的 memory 段，那是本轮追加的参考信息，不在前缀里。
- 结论：缓存过期为主。第 2 次命中读到 0（连没变的前 7 段也没命中），是典型的缓存整个没了；第 1 次的历史条数从 43 降到 31（群聊“只带最近的话”的滑动窗口，`native/internal/turn/turn.go:504` 起的 `CompactKind = "trim"`，实例重建见 `native/internal/turn/hub.go:1386` `rebuildIn`），可能叠加了窗口滑动；第 3 次历史只增不减，命中从 6272 降到 2048，也是过期后的部分命中。能直接证明的只有“间隔都超过 5 分钟”，窗口滑动是推测，缺少请求原文无法证实。
- 因此加了“间隔 > 5 分钟不算”，3 次都不再命中。如果以后要查前缀被改，需要 trace 存请求的分段 hash 或前缀长度。

### 改规则后重跑
