# 规格：给她看真图（私聊先做）

状态（2026-11-16 对账）：Go 侧图片入模已合 main（分支 `feat/real-images`、`feat/media-wait`）：本地私聊和 QQ 主人私聊直给、`read` 读图、等图、跨轮保留及迟到补图已实现。群聊直给、累计上限、真实模型实测仍按待办。下面第一、二节是 10-22 的 Bun 历史规则，Go 现行做法见下一节“Go 实施方案”。本次不调整真实 vision 配置或恢复旧脚本。

依据：待办"给她看真图"（2026-10-20 主人："那感觉直接给回复器也行"）；2026-10-22 主人："我觉得本身对于支持多模态的在独立发几张图的时候直接给就够了，以后可能也不太会有（但还是有兜底）非多模态的模型了。如果只是我们自己用的话，其实兜底只给合并转发都行。"；"识图按照数量直接走上下文试试？"。参考：MaiBot 的规划器、回复器直接附原图（`notes/MaiBot流程对比-2026-10-19.md`）、QQ-agent 按需取原图（深度复核（私有存档））；识图短提示词实验（私有存档） 里量到：识图中位 12.9 秒，私聊发图她等不到。

## Go 实施方案（2026-11-08，feat/real-images）

参考并采用本规格 ADR-138 的单消息上限与只追加缓存规则、识图规格的 1024 长边及失败可查规则、现有 `mediastore.Reader` 的路径检查；工具读图照 pi-mono `packages/ai/src/api/openai-completions.ts` 的 convertMessages（tool 消息只放字，图跟在这串结果后面作为一条 user 消息，仅模型声明能看图时发）。以下为本轮 Go 范围；下文 Bun 实现保留作历史。原则：引导加简单兜底，不给模型层层设限。本地私聊的图走 main 的消息块（`history.Part` 的图片附件）：引用回复块里的图、本机上传的图（`SendLocalImages`，存进媒体库后作为第一块的附件）同一条路；插话（steering）不带图，仍是文字占位。

- 模型能力以本轮冻结的 `/v1/models` 为准，仅 `modalities.input` 明确包含 `image` 才直给；缺字段或只有 text 均不带图。2026-11-08 本机目录已验证 Luna、Haiku、DeepSeek Flash 声明 image，Beam Free 只声明 text。
- llm 提供图片内容结构及 OpenAI `image_url` data URL 序列化；无图片的请求保持原字符串格式。turn 在追加本轮 user 消息前由宿主准备图片，`Msg` 保留图片内容；上下文估算每图计 3000 字符，不把 base64 当文字估算或写入追踪库。
- 用户消息直给：仅本地私聊、QQ 主人私聊的新输入。逐条按已落库事件读取自己的 image 段，沿用事件所属平台、会话与观察关系；不接受调用方指定任意文件或图片地址。两个群场合、非主人、合并转发不直给。`vision.direct` 默认 true，`vision.directMax` 默认 4，超过上限整条不带图（不截前四张）。
- 图片从 Go 媒体库读取，等待既有下载完成后准备；静态图保留比例缩至长边不超过 1024，不放大；动图取首帧。读不到、解码失败、配置关闭、模型未声明能力、超过上限、含合并转发均在日志写一行"真图走识图描述 … reason=…"，文字里用事件已有的 `seen` 描述，没有就保留原来的 `[图片]` 占位。
- 等图（2026-11-08，feat/media-wait）：QQ 图片下载和算哈希是异步的，消息一到回复就开始，图常常还没落盘。直给场合（主人私聊、本地私聊）组本轮请求前，先等这条消息里的图下完：订阅库的变更通知，不轮询不 sleep；上限 `imageWait` 8 秒（日志里下载多在几秒内完成，再久回复就像卡住了）；等的时候写一行"等图 … 还有 N 张没下完"，等到写"等到图了 … 用时"。群聊不直给，不等。
- 没能给她看的图，文字里追加一行占位 `[图片没给你看：原因]`，原因分：还没下载完（等了几秒）、太大没下载（too_big）、链接过期、地址不在允许范围、下载到的不是图片、下载失败、原件不在本机，让她能如实说，不假装看见。终态（too_big、failed 等）立刻返回，不等到上限。
- 超时后图才下完且这一轮还没结束：走 `Hub.LateImages` 补给她。图在这一轮下一次请求之前作为一条 user 消息追加（只追加，不改前面；不存事件，重建后原消息上的图会按事件取回）；这一轮已结束就写"补图没送上"。没有用 steering 通道本身（它是持久 inbox 里主人说的话，会存事件、带"主人插话"前缀），只借同一个"步骤开头追加"的时机。
- `read` 工具读图片：长边缩到 1024、转 PNG，随工具结果交给模型；结果文字只写 `Read image file [image/png]`，图片字节不进 steps、结果存档和日志。拼请求时图作为紧跟这串工具结果的一条 user 消息（`Attached image(s) from tool result:`）发出，模型不能看图就不发。上下文快满时较早的工具图片先省略（`slim`）。
- 缓存只追加，图跨轮保留（主人 2026-11-08 定，照 Claude Code、Codex 把图留在历史里）：图只进活实例的本轮消息，随后工具往返与下一轮原样保留；实例重建（工作上下文恢复、压缩后换快照）时，宿主按事件从媒体库把图重新取回、放回原来那条消息上，文字不变，不存 base64、不回写事件。取回用和第一次直给同一套条件（模型能看图、`vision.direct`、数量上限、非合并转发），取不到的留文字占位并写一行"真图重建未带"。上下文超过软门槛时，较早的主人图片和工具图片不再随请求重发（`slim`，只改这一次请求），下次重建仍会按事件取回。工具读到的图片重建后只剩结果文字，要看再读一次。事件、inbox、模型追踪、日志不得存图片 base64。
- 模型调用记录：主回合的请求照旧走 `modelcall`（`model_runs.stage=reply`），`context_json` 多写 `"images":{"user":n,"tool":m}` 表示这次请求实际带了几张图（没带图不写）。
- 本轮不补后台识图：Go 侧仍没有调用识图的地方，`model_runs` 里的识图记录都是 Bun 时代留下的。主模型不能看图时的描述兜底等识图接入（接入必须走 `modelcall`，见[运行页规格](规格-运行页.md)）。
- 主窗口：后台已能收图（`api.LocalImageChat.SendLocalImages`：每消息最多 16 张、每张 20 MiB、合计 80 MiB，只收字节、不收路径和 hash），但输入框的粘贴、拖入、附件入口未接，本轮不改界面。

验收：临时库覆盖单图、多图、超限、能力缺失、原件失败、四场合与身份边界；检查第二轮请求保留第一轮图片、重建后只带文字及追踪无 base64；`read` 读图片的结果文字、附件位置、不能看图时不发、旧图省略。真实模型试验在指定 scratchpad 保存带字图片、请求图片数量/尺寸/哈希、模型回答和输入用量。

## 一、做什么

QQ 私聊里主人（或朋友）发来一条带图的消息，满足下面全部条件时，这一轮的 user 消息 = 那一行文字 + 图片本身（图片放在文字后面）：

1. 配置 `vision.direct` 开着（默认开）；
2. 这个角色在用的模型能看图（pi 的 `Model.input` 含 `image`）；
3. 这条消息自己的图（`segs` 里的 image）不超过 `vision.directMax`（默认 4）张，且**没有合并转发里的图**（`forwardImgs`）；
4. 每张图都能读到本地文件、能预处理成功（和识图用同一个预处理 `util/vision-prep.ts`：静态图长边 1024、长图分段、动图抽帧拼格）。

不满足任何一条：照旧走识图描述（私聊等最多 `PRIVATE_VISION_WAIT_MS` 45 秒）。

## 二、细节

- **文字那一行不变**：仍是 `[时间] 名字(身份)：[图片][图片]`（`saidBy`），不填描述，也不等识图；后台照旧把这几张图看一遍、存描述、存进 `segments.seen`（记忆、轮次总结、表情包库、重建对话都读文字）。
- **图留在这个实例的历史里**：和这一批文字一起，不在轮后拿掉（拿掉就是抽走历史中间的内容，缓存全断，LESSONS"每轮变化的内容只能追加在末尾"）；每张图按 3000 字符估算进上下文用量（`util/context.ts` 已有）。**实例要重建时**（闲置释放、压缩、超上限）历史从事件库读，读到的是 `seen` 里的描述，图自然换成转述，不多断一次缓存。
- **群聊不动**：群聊的闸门、开口检查读的是文字行，第 1 步不碰。
- **本地主窗口**：现在没有发图入口，不涉及。
- **失败兜底**：读不到文件、预处理出错、模型不支持图片，一律退回描述路径，不报错。

## 三、禁止的偷懒写法

- 不把 base64 图片整份写进追踪库（`model_runs`）、日志、记忆；图和描述不进库的规矩不变。
- 不为了"直接给图"跳过后台识图：描述是别的地方要的。
- 不拿"模型是多模态的"当判断：看 `Model.input` 里有没有 `image`，没声明时 `llm.ts` 默认当 `['text','image']`，这一点在已知的坑里写明。

## 四、已知的坑

- **连发多条单图消息**（2026-10-22 实测：7 条各 1 张图在 1 秒内到）：每条都满足"≤ 4 张"，累计 7 张图进同一轮上下文；前 6 轮被后一条打断（`Request aborted`，各 130～380 毫秒），最后一轮输入约 3876 + 缓存 6912 token、首字 8.3 秒。`directMax` 只限一条消息，累计上限还没做（待办）。
- 走了哪条路只在日志里看得出：路由对带图的私聊消息写一行 info（"直接给她看 N 张图（准备 N 毫秒）"或"走识图描述"）。

- `llm.ts` 在 Magpie 目录里没声明 `modalities.input` 时默认给 `['text','image']`；某个模型其实不能看图又没声明，请求会被服务商拒绝，这一轮出错（还没做自动退回；真遇到了，关 `vision.direct`）。
- 图留在历史里，一个实例里发了很多张图会越攒越大；`directMax` 只限一条消息，不限累计。靠上下文软 / 硬门槛和压缩兜底。
- 主模型自己读图也要"想"：deepseek-v4.1-flash 带图的回复时间和 token 要实测（见验收）。

## 五、验收

- 测试：私聊带 2 张图 → 发给模型的 user 消息是 `[文字, 图, 图]`，路由没等识图；超过上限、有合并转发图、模型不支持图片、读不到文件 → 走描述路径；后台识图照常存 `seen`；重建实例后历史里是描述不是图。
- 旧代码放回去会失败；再用另一种方式改坏（改错上限、不检查模型能力）也要失败。
- 实测（真实私聊）：发 1 张、3 张、5 张图各一遍，量：回复用时（对比走描述的 45 秒等待）、输入 token、缓存命中、她接得准不准；汇报数字，不写"看着可以"。
- `bun run test:log` 退出码 0，`typecheck` 退出码 0。
