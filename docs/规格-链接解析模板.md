## 一、模板语言

一条模板是一段文字。用户只需要记住五件事：

1. `$名字`：占位符，换成字段的值。名字写中文或英文都行（`$标题` = `$title`），名字后面紧跟别的字时可以写 `${标题}`。列表见第三节，设置页有按钮一键插入。
2. 其余文字原样输出，包括空格、标点、真实换行；也可以写 `\n`。要输出 `$ [ ] \` 本身，写 `\$ \[ \] \\`。
3. `[ ... ]`：可选段。里面任何一个占位符没取到或为空，整段（连同里面的分隔符）都不输出。例：`播放 $播放[｜点赞 $点赞]`。可以嵌套；外层只含子段、自己没写字段时（一行统计 `[
[播放 $播放][｜点赞 $点赞]]`），子段至少有一个输出才输出，否则整行连换行一起省略。落在行首的字面分隔符（｜ | · 、 ， , /）自动去掉，所以第一项缺了也不会留下孤零零的竖线；字段的值里的字符不动。
4. 裸占位符（不在方括号里）没取到，输出“未返回”，和现在的输出一致，不留空洞，也不把缺失冒充成零。值为空字符串（比如没有标签）输出空。
5. 排版用的占位符：图片类（`$封面 $卡片 $视频 $图片`）出现在哪，图就发在哪；`$分段` 另起一条消息；`$合并转发` 之后的内容进合并转发，`$节点` 把转发分成下一个节点；`$正文` 把帖子的正文块（文字、图、引用）按原顺序摆到这里。

选可选段而不是 `$if` 的理由：写法只有一对括号，漏写也只会多出一段字，不会整条解析失败；错误提示也容易给（括号没配对、占位符不存在，指出第几个字）。

写错时：保存前和预览时都用同一个解析器，报“第 N 个字：不认识 `$标题1`，你是不是想写 `$标题`”“括号没有配对”，不崩、不保存。已经保存的模板如果以后因升级变得非法，运行时退回该站点的内置默认并写一行日志，不发空消息。

图片的位置规则：
- 一条消息里，文字和图片按模板里出现的顺序成为消息段；没有 `$分段` 就是同一条消息。
- `$视频` 总是单独一条消息（QQ 视频不能和文字混发），写在哪都一样；下载关着就什么也不发。
- `$封面` 取第一张图或缩略图；没有就不输出，不留空行（图片类占位符两侧的空白换行会被去掉）。
- 开头的引用（回复原消息）和结尾的“发过 N 次”“还有 N 条没处理”“正文未完整取得”由代码追加到第一条消息，不由模板管。

每个站点有“直发模板”和（有合并转发形态的）“转发模板”；转发形态的站点是 `bilibili-dynamic`、`bilibili-article`、`x`、`pixiv-artwork`、`pixiv-novel`、`douyin-note`。配置里转发模板的键是 `<站点>-forward`。

每个站点三项设置（`linkReader.expand.sites.<站点>`）：

| 键 | 默认 | 含义 |
|---|---|---|
| `forward` | `auto` | `auto` 按代码规则（见下）选直发或转发；`always` 总是转发；`never` 总是直发（图多于直发上限时只发前几张，文字末尾标出发了几张、共几张）。没有转发形态的站点只有 `auto`、`never` 两个取值（R-218） |
| `forwardOver` | 仅 `bilibili-dynamic`、`bilibili-article` 为 100（专栏 2026-11-12 加，见规格-链接发送改版 B3“复核修订”第 5 条；专栏设 0 和别的站一样是不按字数，一律转发用 `always`），其余 0。**x、telegram 自 ADR-391 起不再读它**，旧配置照旧能读入、不报错 | B 站等按字数的站点：正文超过这么多字折成合并转发；0 为不按长度折。在 `auto` 下和其他条件一起用 |
| `forwardOverBytes` | 仅 `x`、`telegram` 为 16500，其余不能写（写了报错）。范围 1000～17500，0 拒收 | 实际会发出去的文字（直发模板渲染出的全部文字：链接、作者、时间、译文或原文、翻译自）超过这么多 UTF-8 字节折成合并转发（ADR-391，规格-链接发送改版 B16）；合并转发里每个节点的文字也按这个上限拆 |
| `descLimit` | 仅 `pixiv-novel` 为 300，其余 0 | `$简介` 最多多少字，超出截在最近的标点后，补“……”和“完整内容见原文”（规格-链接发送改版 B10）；0 不截 |

`auto` 的代码规则（`linkexpand.autoForward`；图数上限各站统一是 `expand.directImageMax`，默认 3，见规格-链接发送改版 B3）：X 的“短”需要同时满足正文没被截断且直发模板渲染出的全部文字不超过 `forwardOverBytes`（UTF-8 字节，默认 16500，ADR-391）、图不超过上限（疑似拆开的横幅按拼回后一张算；自定义模板写了 `$拼图` 时三张及以上的自带图发一张拼图）、视频 ≤1、无引用、非文章、不图视频混排；pixiv 作品页数不超过上限直发、否则转发（图一张都没取到按 0 张，直发一条文字）；抖音图集、pixiv 小说恒转发；B 站动态的“短”要同时满足正文没被截断且不超过 `forwardOver`（默认 100）字、没有视频和动图、没有引用和投票；B 站专栏的“短”是正文没被截断且不超过 `forwardOver`（默认 100）字、没有视频；Telegram 是直发文字不超过 `forwardOverBytes`（UTF-8 字节，默认 16500）、至多 1 个视频且不和图混排。短而图不超过上限的一条消息直发，其余整条进合并转发；只因图多进的转发在准备完图后不超过上限、没有视频就收回成一条消息（没有转发形态的站点由发送形状处理，同样适用）。合并转发一层、最多 80 节点、文字超过 `forwardOverBytes` 字节拆节点仍由代码保证，模板不能越过（第三节的 `$正文` 在转发里照旧按这些规则成节点）。

- 视频、Article 长文、引用、投票等其他形态的规则不变：`auto` 仍把它们交给合并转发；视频和动图直发时仍单独一条消息；引用和长文仍按原有转发规则。设置里的合并转发模式（`always`、`never`）和手写模板仍然优先；`never` 下的多图帖有拼图用拼图，没有拼图就把全部图直发。
- 顺手修的错：转推数以前读错了统计键（模板读 `retweets`，取数端存的是 `reposts`），真实帖子里“转发”一项从来不显示；现已改对，并有回归测试。
**X 拆图拼回（2026-11-10，分支 `feat/link-split-panorama`）**：有人把一张横幅拆成几张竖条发（例：4 张图高都是 2272，宽 2240、1077、1077、1078，合起来 5472×2272），一条条看不出整体。识别出是拆开的就在本地拼回一张发；拿不准一律按普通多图发。

- **参考与取舍**：不用 fxtwitter 的 `mosaic`（那是网格，每张图缩成格子，不是无缝拼接）。参考的是成熟图像库里“感知哈希”和“接缝能量”两种判断（dHash：缩成 9×8 灰度比相邻像素；接缝：比相邻两列），代码自写，全在 `linkexpand/panorama.go`，不新增依赖。
- **两段判断**：
  1. `Build`（还没有像素）：X 帖子自己有 ≥2 张图、没有视频、取数端给的每张图宽高都有、高度相差 ≤1 像素，才算“候选”。候选时不用 `mosaic`，图按顺序排成普通图片项，第一张带 `PanoramaN`（组里几张）；`auto` 转发判断里这一组算一张图。没有宽高（旧缓存、vx 线路）的走原来的路。
  2. `Prepare`（有像素）：整组图用 `loadImage` 下载（`name=large` 退档照旧，退档后高度对不上会被下面第 1 步挡下），解码后依次判断，**任一步不过就按普通多图发**：
     1. 解码后高度相差 ≤1；
     2. **先认变体**：相邻两张的 dHash 汉明距离必须大于 `panoVariantMaxDist`，近的是同一画面的几个版本（换表情、换衣服、线稿差分），不拼；
     3. **接缝要有信息量**：左图最右、右图最左各 `panoBand` 列，缩成 `panoRows` 行后的亮度标准差都要不低于 `panoMinEdgeStd`；纯色、留白的边缘上“接得上”不算证据，不拼；
     4. **接缝对得上**：两条边缘的平均绝对差不超过 `panoSeamAbs + panoSeamRel × 图内相邻列的平均绝对差`。
  宽度是否相同**不参与判断**（等宽切分也有）。阈值（`panorama.go`）：`panoVariantMaxDist`=10、`panoMinEdgeStd`=8、`panoSeamAbs`=6、`panoSeamRel`=2、`panoBand`=3 列、`panoRows`=96 行。取值依据：测试里的正例（真实比例切条、等宽切条、六条、各自过 JPEG 质量 70～92 后）dHash 距离 18～48、边缘标准差 23～58、接缝差 2.7～5.6 且不超过图内同距离差的 1.3 倍；反例（纯色背景变体集、只改脸的变体集、白底线稿差分、不相干同高图、顺序颠倒、少一条）分别被变体、信息量、接缝三道挡下，各道删掉一道对应测试就红。真实样本（2026-11-10，`link-probe -stitch` 对一条真实的公开推特拆图帖（帖号不入库），4 张 2272 高、宽 2240/1077/1077/1078）：dHash 距离 24、21、29，边缘标准差 39～58，接缝差 1.5～2.4 对图内 1.2～2.1，通过，拼出 5472×2272、1.48 MB 的 JPEG，目视无缝。
- **拼接**：`draw` 横向拼成一张，JPEG 质量 92（输入全是 PNG 才用 PNG）；超过 `imageMaxMB` 就用 `xdraw.ApproxBiLinear` 每次缩到 80% 再编码（最多 6 次），仍超限按普通多图发。没有找到现成的像素边长上限，只按体积限。解码、判断、拼接、编码放在一个后台协程里，限时 `panoramaTimeout`（5 秒），超时或失败都按普通多图发，不报错；拼好的图和卡片一样过 `imageTransport`。
- **发送**：默认只发拼好的一张（在文字下面的图片位置）。设置 `linkReader.expand.panoramaOriginals`（插件页“拼接后另附原图”，默认关）开了，原图放进一个合并转发附在后面；没拼成时这个转发里的图不发（原图已经按普通多图发过了）。
  - 已被规格-链接发送改版 B3“复核修订”第 3 条补上：没拼成时按普通多图发，图数超过直发上限（默认 3）就改成合并转发（站点设成 never 时拆成每条最多 3 张），不再把 4 张原图挤在一条里（2026-11-12 样张复核 #25 X-07）。
- **禁止的偷懒写法**：用 fx 的 mosaic 当拼回结果；用“宽度不同”当判断依据；只比接缝不先认变体（纯色背景的变体集接缝“完美”）；接缝信息量不够时当“接得上”；超时时报错或不发图；拼接阻塞文字部分。
- **已知的坑**：一张退了 `large` 档而别的没退，高度对不上，会被挡下（正确）；纯色或白底线稿的真拆图也会被当成拿不准而不拼（宁可少拼）；测试用的“长图”不能是单纯渐变——渐变切成条后条条的 dHash 一样，会被误当变体集，所以测试图用多个低频二维正弦叠加加渐变；dHash 对竖条整体感知，窄条（宽 <1/8 高）可能不稳，所以只拿相邻两张比较。
- **范围**：先做 X。Bluesky、pixiv 的多图走的是另一套图片项排布，没有同样的宽高候选判断，记进[待办](待办.md)，没有接。

**卡片的两处毛病（同日）**：WebP 封面（Steam 创意工坊）以前解不开、卡片上印“封面下载或解码失败”，原因是封面常是 VP8X 扩展格式，`golang.org/x/image/webp` 只认基础格式；`linkcard` 现在导入已在 `go.mod` 里的纯 Go 解码器 `github.com/gen2brain/vpx/webp`（根包的动图解码本来就用它），动图取第一帧。没有封面的页面（Mastodon 帖子之类）卡片不再留一大块“封面不可用”空白，直接不画封面区；有封面但没取到才画占位块并写明原因。正文开头只是一条链接时（Mastodon 常见），卡片标题改用外链卡的标题，没有再用作者，不写网址。

后续（用户 11-09 提）：推特等站点的翻译功能，记在待办。

默认模板里，除标题、链接这类必有的字段，每一行、每个统计项都写成可选段：取不到的字段不显示，连同它的分隔符一起省略（用户 2026-11-08 要求，不再写“未返回”）。一行统计写成“外层可选段里只有子段”（`[⏎[播放 $播放][｜收藏 $收藏]]`）：子段一个都没有，整行连同换行一起省略；缺了第一项，落在行首的字面分隔符自动去掉。

新站点的默认模板没有“重构前的硬编码输出”可比，基线是 `linkexpand/newsites_test.go` 里写死的期望文字（编造的取数结果，含字段缺失的样本）。过滤规则：取数端标了 `unsupported`（只有封面、没有媒体文件，如 Spotify 试听、TikTok 视频、Steam 预告）的媒体不排进消息；没有标题、只有作者或媒体的结果（TikTok 没写文案的视频）也能展开，什么都没有才回失败文字。不拦截成人内容：Steam 的年龄限制、Bluesky 和 Misskey 的敏感标记只在平台给了才写一行，和 pixiv 的“分级”同一做法（ADR-323）。

回归基线：`testdata/build_golden.json` 里 43 个样本，字段齐全的 36 个与重构前的硬编码输出逐字相同；另外 7 个“有字段取不到”的样本（`bili-opus-notitle`、两种 B 站格式的 `bili-video-nostats`、`github-bare`、`pixiv-norating`、`pixiv-novel-bare`、`x-short-nostats`）按上面的规则有意改成省略“未返回”，其余部分不变（改动前后的对照在提交说明里）。

## 六、进度表情（开始、完成、失败）

用户原话：“当它开始接收时，先点一个表情回应，再开始搜索和获取内容；在成功发出消息之后，把表情回应换成另一个。……完全看不出它进到哪一步了。”

接口查证：
- 封装已有：`types.PartReact`（`Ref` 原消息号、`EmojiID`），`snowluma/call.go` 的 `reactAction` 发 `set_msg_emoji_like`，`message_id` 为 JSON 数字（群里是负数）、`emoji_id` 字符串；成功回包 `data: null`，不产生新消息号；走唯一出口和现有限流、发送许可（`goSend` 等条件不齐时 `permitLink`/出口拒绝，零帧）。
- 撤回：SnowLuma 的 `set_msg_emoji_like` 有第三个参数 `set`（布尔，默认 `true`），传 `false` 就是取消自己贴过的这个表情（本机打包源码的动作定义里能看到 `set: f$1.bool().default(true)`，并会推 `group_msg_emoji_like` 通知，`sub_type: remove`）。`types.Part` 之前没有这个字段，本次加 `Unset bool`（只对 `PartReact` 有效），`reactAction` 在为真时带 `"set": false`；`outlet.go` 的 `partJSON` 与计划持久化、`fake`、`contract` 同步。
- **私聊不可做**：2026-10-30 真帧，私聊 `set_msg_emoji_like` 回 `failed/100`，`wording` 为 “emoji reactions are not supported on private messages”（SnowLuma 源码里同样是只有群才允许）。所以私聊的三阶段仍是：开始用 `privateStatus` 文字（现状），完成靠结果消息本身，失败回一句写死的“没解析出来”（ADR-344，原来的 `failureText` 配置已删，文字不再可配）；不在私聊调用表情接口（现有守卫保留）。群里失败不发文字，只换失败表情。

阶段与时机（群）：
1. 开始：入队成功、取得发送许可后、取数之前，贴 `startEmoji`（现状，只是以前默认空）。
2. 完成：这条链接的结果计划全部确认（`Outcomes` 里没有 failed/aborted）后，撤掉开始表情（`Unset`），贴 `doneEmoji`。结果有被拒媒体但文字版确认了，也算完成（用户拿到了内容）。**结果不明、一段都没确认送到的不算完成**（2026-11-14，规格-链接发送改版 B15）：不贴完成也不贴失败，只撤掉开始表情（结果不明时群里可能已经有了，失败表情会说谎；以前按送到算，群里什么也没出现却贴了完成）；至少有一段确认送到（含补发的文字版）才贴完成。
3. 失败：取数失败（群里不发文字、只记日志；私聊回一句“没解析出来”）、取到但没有可发内容（`Draft.NoContent`，同样处理）、结果没能入队或计划终态是失败、`permit` 中途被撤，撤掉开始表情，贴 `failEmoji`。
4. 一条消息里有多个链接时只贴一次开始、最后按“有没有任何一个链接成功”收尾：全部成功贴完成，全部失败贴失败，有成有败贴完成（用户拿到了东西），失败的链接各自有失败文字说明。
   多个链接并发取数、按原顺序发，前面的发完就发，不等全部取完（2026-11-13，R-378）：同时取数不超过一条消息的展开上限，同平台的限速排队由取数层管；重复的链接（取到才知道规范链接相同）记“去重”并空出名额，再取下一个候选；撤回、关闭时所有在途取数一起取消。第一条发出去时后面的还没取完，“还有 N 条没处理”按当时还没启动的条数算，之后发现有重复时可能多说一两条。
5. 表情回应失败只记一行日志，不影响内容发送；撤不掉开始表情时照样补完成/失败表情；任一步发送许可不齐（`goSend` 没开、会话被撤权、关了展开）一个表情都不发。

配置（`linkReader.expand`，群里按会话名单生效；和展开同一份名单，没有单独的会话开关）：

| 键 | 默认 | 含义 |
|---|---|---|
| `startEmoji` | `289` | 开始；空串关闭本阶段 |
| `doneEmoji` | `124` | 完成；空串关闭 |
| `failEmoji` | `9` | 失败，也是失败时唯一的提示（不发文字）；空串关闭 |

默认编号选择（QQ 系统表情，`emoji_id` 字符串）：289 = “睁眼”（[QQ 开放平台表情表](https://bot.q.qq.com/wiki/develop/api-v2/openapi/emoji/model.html)，近似“我看到了、在看”，比 👍 更像“处理中”）；124 = “OK”（同表，直接表示“好了”）；9 = “大哭”（同表，“没成”的意思最清楚，另有 5、173 可换）。仓库里**真帧验过的只有 76（赞）**，这三个编号在 SnowLuma 真机上还没验，所以：一，默认值是我定的、可随时改；二，验收清单里留“真机贴一次三个编号”；三，如果某个编号协议端拒绝，只记日志，不影响内容。原规格第八节写的“不擅选默认”在 2026-11-08 被主会话改为“给默认值”，已在该节标注。

私聊开始文字、撤回时机、多链接合并等“不确定怎么办”的情形一律按上面保守处理：宁可少贴，不贴错。

## 七、单张图被拒不再封整个会话

> 第 3 条（阶梯、拆单元）、第 8 条（无回执核实）和下面的形状 × 入口表已被[规格-链接发送改版](规格-链接发送改版.md) A1、A2 节改为：未确认 / 没回包时等回声（默认 2 秒），没回声就判整条没送到、整条转图重发，翻历史改为可选（默认关）；阶梯写死成 原样 → 整段静态图一起转 180° 同容器重发 → 文字版，不再拆单元。分类判据、能力缺失、通道门、出口不重试照旧。实现合 main 前，下面仍是现状。

用户反馈（某个群，2026-11-08 21:16）：一张推特图被协议端拒收（日志“协议端拒绝”，重试 3 次），补发的文字版没写原因；随后日志写“之后这种媒体退成文字，重启后重新试”，下一条链接的图片直接降成“图片未下载：这种图片在这里发不出去”。

根因：`failureCategory` 只认回执文字里有没有“不支持”，而适配器对协议端 `status: failed` 一律回“协议端拒绝”，内容审核拒收和能力缺失分不开，于是一次拒收被记成“这个场合发不了图片”（ADR-310 的收紧本意是“能力缺失”）。

判据（来自 SnowLuma 源码里真实存在的报错文字，见 `UNSENDABLE_TYPE` 一类）：
- **能力缺失**：回包 `wording` 含 `cannot be sent`、`unsendable`、`only accepts text`、`is not supported in`、`only valid inside`、`no executable send semantics`、`不支持`（例：`message element "image" cannot be sent to this contact`；2026-11-09 去掉了宽泛的 `not supported`）。适配器把它归为 `协议端不支持这类消息`。
- **这一张被拒**：其余所有 `status: failed`（内容审核、单张太大、链接过期等，协议端没给可分辨的文字）。**分辨不了时按这一张被拒处理，不关闭能力。**
- **发送出了问题**：没连上、没写出去、取消等本地原因，既不是拒收也不是能力缺失。
- **结果不明**：没回包、超时、写出后断线、没配号，以及 SnowLuma 说 `delivery was not confirmed`。其中“发出去了但没拿到回执”（没回包、超时、`delivery was not confirmed`）先核实一步（见下面第 8 条，ADR-333）：到了算成功、没到算被拒，查不了才仍是结果不明（不换形式也不补发）；断线、没配号这类不核实，直接是结果不明。

处理：
1. 只有“能力缺失”才降级该场合的这种媒体；降级带 10 分钟有效期（`mediaBlocks` 记到期时间），到期后下一条链接再试一次，成功就保持恢复、失败再降 10 分钟。不再需要重启。
2. 补发的文字版加一行原因，放在内容之后、链接之前：
   - 这一张被拒：`图没发出去：QQ 拒收了这张图`（视频、动图同理；一段里有多张写“这组图”）。
   - 能力缺失：`图没发出去：这个群暂时发不了图`（私聊写“这个会话”）。
   - 发送出了问题：`图没发出去：发送时出了问题`。
3. **图发不出去后按阶梯换形式（ADR-331 起，ADR-333 改了顺序）**。用户原话：“卡图片导致消息只有文字怪难看的”“要是能提前知道某张图发不发得出去就能更灵活一点了……要么就对特定平台的图可以启用优先合并/转图的方式”。顺序固定：

   **正常发 → 直接发并把静态图转 180° → 合并转发里把静态图转 180° → 才退文字版**（文字版带原因、试过哪几种、原链接）。

   2026-11-09 17:45 的实测推翻了 ADR-331 里“合并转发（不转）可能发得出”的假设：同一张被卡的图，普通发和不转的合并转发都是“没拿到回执”且确实没进群，转 180° 直接发和合并转发里转 180° 都发出去了。所以不转的合并转发不再是常规一级。它只留给转图帮不上的情形（`plain`）：协议端说这个场合发不了这种段（能力缺失，换个容器可能行）、动图和视频（不能转）、`rotateOnReject` 关着。

   - **换形式的触发**：回执是 `failed`，类别为“协议端拒绝”（这一张被拒）或“协议端不支持”（能力缺失）；或者回执是“没拿到回执”的结果不明、核实后确定没进群（第 8 条，按“这一张被拒”算）。转 180° 只对“这一张被拒”有意义，能力缺失、动图、视频不走转图那两级。
   - **查不了的结果不明不换形式、不补发**：断线、没配号、核实时历史取不到或没翻到尽头。日志写“结果不明（可能已经发出去了），不换形式、不补发”，运行页记 `link · form_degrade`（结局 `degraded`，标签“某形式：结果不明”或“核实：查不了”）。
   - **一条里只有问题图换形式**：被拒的那一段里有多张图或图文混排时，拆成单元（连续文字一个、每张图一个，转发里一个节点多张图则拆成一图一节点，显示名不变），每张图单发一次（只有一张图时原段被拒已经说明是它，不再单发确认），谁被拒只处理谁，别的图原样发出。被拒段**之后**被出口中止的段是被连累的，原样补发，不跟着变形（它们从没发出过）；前一段结果不明（不管核实结论是到了、没到还是查不了）时后面被中止的段同样补发。做不到的情形：视频（文件、可能上百 MB）和超过 32 MB 的图出口发完就释放、没有备份，被拒后只能退文字，文字版写明。
   - 合并转发的节点显示名用作者名（缺则“链接内容”）；节点里的图、说明文字（卡片语义）原样带过去。
   - 转 180° 由发送端对**备份的整张静态图**做：卡片是渲染好的整张图，封面已画在里面，所以封面一起转；视频缩略图、封面单发时是普通静态图，同样处理；只转 PNG / JPEG，不加噪点、不改尺寸、保持格式；动图不转。开关是 `rotateOnReject`（默认开），管两个转图的级别；关着时阶梯是 直接发 → 不转的合并转发 → 文字。
   - **每个网站可选发图方式**（`linkReader.expand.platforms.<网站>.imageMode`，设置页“网站与页面类型”里每个网站一行“发图方式”）：`auto`（默认）普通发优先；`rotate` 直接发转 180° 优先；`forward` 合并转发里转 180° 优先。按阶梯从选定的那一级开始，不成再往后，直到文字版。动图、视频不转，不受它影响；只有静态图的段才按方式起步。显式选了 `rotate` / `forward` 就是用户的决定，不再看 `rotateOnReject`。
   - **按图记结论**（不再有“一张被拒封整个群”）：内存里按“会话（渠道、群号或私聊对象）+ 图片内容哈希”记每种形式被拒（含核实确定没进群）或发成过，6 小时到期、最多 512 条。**查不了的不记**。同一张图再来：已知发成过的形式先试，已知被拒的形式跳过；整段的图在直接发上都被拒过，就不再往 QQ 提交，直接走阶梯。**场合级降级（`mediaBlocks`，10 分钟）只在能力缺失且每一级（直接发、合并转发）都没发出去、文字版确认后才记**；直接发能力缺失但合并转发发出去了，不记。
   - 文字版原因写明试过哪几种：`图没发出去：QQ 拒收了这张图（直接发、转 180° 直接发、转 180° 的合并转发都被拒）`（动图只有 直接发、合并转发 两种；关着旋转、能力缺失也是这两种）。
   - 日志与运行页：每一步一行日志（段号、单元号、形式、结果、为什么换下一级，不含正文和地址），并记 `link · form_degrade`（结局 `ok`、`failed`、`degraded`；标签“形式：成功 / 被拒 / 能力缺失 / 结果不明 / 没准备成 / 文字版：成功 / 核实：到了 / 核实：没到 / 核实：查不了 / 原图晚到 / 撤回补发：成功 / 撤回补发：没撤”，后三个是规格-链接发送改版 B15 加的）；两个转 180° 的形式另记 `link · rotate_retry`（`ok` / `failed` / `degraded`）。只记类别和固定标签，不写真实聊天内容。运行页的 `link · form_degrade` 和 `send · rejected` 都查得到。
4. **出口不再原样重试**：协议端明确拒绝（回执文字以“协议端拒绝”开头，`types.IsRejection`）出口只发一次，类别 `send · rejected`；结果不明本来就不重试。只有没连上、没写出去这类本地失败，以及协议端回 `failed` 却没有可识别拒绝措辞的（NT 忙、限流、临时 `send failed`）才最多试 3 次：适配器的 `rejectionWords`（审核、风控、格式、体积一类）和 `capabilityWords` 才算拒绝，其余写“协议端报发送失败”，不带“协议端拒绝”前缀，链接插件当“发送出了问题”处理：不换形式、不记按图的被拒结论。旧行为（拒绝也试 3 次）是群里重复收到同一张图的原因之一。
5. **SnowLuma 的“没拿到送达回执”不是拒绝，也不一定是到了（ADR-333 改写后半句）**：`index.mjs` 的群发送在 `result=0` 但 `sequence` 为空时抛 `delivery was not confirmed`，回包是 `status: failed`；旧代码当拒绝，于是出口试 3 次、旋转又试 3 次，同一张图重复发 6 次（日志 21:16:20 / 22 / 24、21:19:20 / 21 / 23 各三条，正好对上）。适配器现在先认 `unconfirmedWords`（`delivery was not confirmed`、`no message receipt`、`before retrying`、`failed: no response`、`timed out` 等）→ 结果不明。能力缺失的字样也收窄到 SnowLuma 真有的措辞（`cannot be sent`、`unsendable`、`only accepts text`、`is not supported in`、`only valid inside`、`no executable send semantics`、`不支持`），去掉了宽泛的 `not supported`。
6. 提醒：换形式、旋转都等于对 QQ 的内容审核换个样子再发一次；它只对“协议端明确拒收”的图生效，风险在这个账号上，由用户承担。
7. **换形式的被拒不数进通道门**：阶梯上每一级被拒都会让出口回一次明确失败，若都喂给通道门，一张图三级都被拒（或两张图接着被拒）就连着 3 段失败，整个 QQ 被暂停，文字版也发不出去。`app/send.go` 的 `onQQPart` 对 `linkOrigin` 来源、类别为协议端拒绝的段不调 `PartEnded` 也不弹“发不出去”提醒（确认仍然清零计数）；整个阶梯不成时由链接插件自己发文字版并回失败。测了 `TestLadderRejectionsDoNotPauseQQGate`、`TestTwoRejectedImagesDoNotPauseQQGate`、`TestTransientFailureIsRetriedAndNotRemembered`。
8. **无回执时核实一步（ADR-333）**。出口对“没拿到回执”照旧只发一次、不重试（同样的内容重试没有意义）；链接展开在这之后查一次历史，看这一条到底进没进群（`linkplugin/verify.go`）：
   - **查什么**：群里取源消息之后的消息——`get_group_msg_history` 带锚点（源消息的平台消息号）和 `reverse_order=false`，SnowLuma 向服务器取“锚点及更新的消息”（`SsoGetGroupMsg` 往新的方向走，所以拿得到 SnowLuma 没实时收到的）；一页 50 条，满了就以最新一条为新锚点接着翻，最多 4 页，页间隔 2 秒（适配器 `HistoryAfter`，只读，不发任何消息动作）。私聊没有锚点翻页，取服务端漫游的最新一页，页里必须有源消息。锚点没回来、页是空的都按查不了。为什么不用无锚点的最新页：SnowLuma 的无锚点群历史以“本地最新序号”为锚向旧的翻，看不到本地没收到的更新消息，证明不了“没有”。
   - **等多久**：第一次查前等 4 秒，没找到再等 6 秒查第二次；每次查询最多 10 秒（适配器自己的 45 秒不等），整个核实最多约 30 秒，期间这条链接的展开占着一个 worker。到点、被取消、历史取不到都是查不了。
   - **怎么认“就是这一条”**（全部成立）：发言人是自己的号、在这个会话里、平台时间不早于这一次发送开始前 8 秒（本机时钟比 QQ 快几秒很常见；落在窗口外 30 秒内的同形状自己号消息记为疑点，不当到了也不判没到）；不是这次展开里已经确认的别的段（按平台消息号排除）；形状对得上（直接发：图片段数一样、文字去掉首尾空白一样、不是转发；合并转发：恰有一个转发段、没有图）；图的标识——发出去的图的 md5 是协议端自己记的图片标识（SnowLuma 上传日志写的 `md5=` 就是它，收到的图 `file` 是“<md5>.扩展名”，旧式图片地址里也有它），候选里读得出 32 位十六进制标识的必须有一个等于我们发的 md5（强对上）；全都读不出（NT 的 `file` 可能是不透明的 fileId）就只凭前几条（形状对上）；读得出却对不上不算到了，但页里若有这样形状一致的自己号消息，也不断言没到，按查不了。历史页里个别消息翻译不了时（发送者为 0、会话对不上、时间不是秒），适配器带回能翻译的部分、不再翻后面的页、不声明翻到了尽头：找到就是到了，找不到是查不了。
   - **为什么可靠**：同一个号、同一个会话、发送开始之后、形状一样、图的标识一致或读不出，这个窗口里同时出现另一条无关消息的可能极小；判断偏向“到了”，只有历史翻到了尽头、窗口里确实没有对得上的消息才判“没到”，所以宁可少补发也不重复发。
   - **三种结论**：到了（算成功，不补发；运行页 `link · form_degrade` 标签“核实：到了”）→ 没到（按“这一张被拒”走下一级，记进按图的结论，标签“核实：没到”）→ 查不了（仍是结果不明，不换形式、不补发，不记结论，标签“核实：查不了”，日志写原因）。
   - **残余风险**：SnowLuma 向服务器取历史失败时会静默回退到本地库（`getGroupHistory` 的 catch），本地库里没有的也会被判成“没到”，这时会多发一次别的形式（可能重复）；回包里分不出来源，只能靠“锚点必须回来”这一条挡掉一部分，这一项 Go 端无法消除（需要 SnowLuma 在回包里标出来源再改成按查不了）。形状对上但标识读不出时，同一窗口里自己号恰好手动发了同形状的消息也会被误认为到了（不会重复发，只会少补一次）。
   - **通道门**：核实出“确实没到”的和“明确被拒”同类，不数进通道门的连续失败，不暂停 QQ（出口本来就不为结果不明调 `OnPart`，所以门里没有这一步）；测了 `TestUnconfirmedAndNotLandedGoesToRotated` 里的 `gate.Paused` 断言。
   - **不扩大范围**：普通聊天回复、别的插件遇到“没拿到回执”照旧只是结果不明，等回声认领；核实只在链接展开的图发送上做。

## 十、设置页、`sumika-ctl`

## 十三、发出的消息连到原消息（引用显示“原消息不在本地”）

用户反馈（2026-11-08）：群里有人发了推特链接，解析消息带引用，界面却写“某人 / 原消息不在本地”，被引用的那条明明就在上面。

查到的原因：界面的引用块（`native/quote.go`）只认事件上的 `reply_to`（本地事件 id）。收消息时 `store/inbound.go` 会按平台消息号把 reply 段连到 `reply_to`；但出口发消息落库（`channel/outlet.go` 的 `sendHeld`）建发出事件时一直没有写 `reply_to`，只在段里存了被回复那条的平台消息号。所以**所有**带引用的发出消息都是这样，不只链接展开；已落库的历史里，带引用的发出消息目前只有链接展开发的（`origin` 为 `automation:link-reader`）。

改法：出口落库时算出这次回复的是库里哪条事件，直接写 `reply_to`。先认发起方给的源事件（`Part.SourceSeq`，链接展开就是因为那条消息才发的，不用再靠平台消息号反查），再按第一个带引用的消息段里的平台消息号反查，找不到就留空，不猜。普通回复、复读等别的发送路径走同一个出口，一起好了。

历史补录：`native/cmd/reply-backfill`（可重跑；默认只数，`-apply` 才改；改之前把聊天库整份复制到 `<数据目录>/backups/reply-backfill-<时间>/`，一个事务里改，只改 `reply_to` 为空且按平台消息号能连上的行；先 `sumika-ctl quit`）。2026-11-08 在真实库的只读副本上量过：带引用的发出消息 32 条，`reply_to` 全空，32 条都能连上（副本已删，输出只有数字）。真实库什么时候补由用户决定。

测试：`internal/app/reply_target_test.go` 走“收到链接 → 解析 → 发出 → 回声”，断言发出事件的 `reply_to` 等于原消息的事件 id，界面读到的 `ReplyTo`、`Reply` 有内容；`cmd/reply-backfill/main_test.go` 在临时库上验只补该补的、重跑不变、备份在改之前。

## 十四、合并转发的节点名和卡片文字（2026-11-09，ADR-338）

用户原话：“就用她自己的头像，然后名字可以再插件页自定义吗？留空默认就是她的QQ名字。如果外边的描述也可以自定义就也在插件页留编辑功能”；“测试自定义功能，就写亚托莉吧。标题、俩预览、底部摘要、外显现在就自定义为内容的标题（字数过多自动用省略号防止超限）、内容字数、图片数、up名字”。

参考及采用：SnowLuma 本机打包源码 `send_group_forward_msg`、`send_private_forward_msg` 的参数（`readForwardPreviewMeta`、`buildForwardPreviewElement`）——`source` 是卡片标题、`news` 是 `[{text}]` 预览行、`summary` 是底部摘要、`prompt` 是外显（聊天列表和通知里那一行）；四项都没传时 SnowLuma 用默认（标题“群聊的聊天记录”、预览取前几个节点的第一行、摘要“查看N条转发消息”、外显“[聊天记录]”）。节点带 `name` 和 `uin`。占位符沿用本规格的模板机制（`linktemplate` 的解析、可选段、转义），卡片文字另用一个只有文字占位符的集合。没有核到 QQ 客户端对这四项的显示上限，SnowLuma 也不截。

### 配置

`linkReader.expand.forward`，全部不写就是现在 QQ 默认的样子（节点名除外，见下）：

| 键 | 默认 | 含义 |
|---|---|---|
| `nodeName` | 空 | 合并转发里每个节点的显示名，最多 40 个字，不能含换行和控制字符；空 = 她自己的 QQ 昵称（从连接核验时 `get_login_info` 的回包取），取不到昵称退回这条路径原来的名字（正常路径 `link-reader（外部内容）`，降级路径作者名或“链接内容”） |
| `source` | 空 | 卡片标题（模板） |
| `news` | 空 | 卡片预览，最多两行，每行一段模板 |
| `summary` | 空 | 卡片底部摘要（模板） |
| `prompt` | 空 | 外显（模板） |

**头像和号永远是她自己的**：节点的 `uin` 由适配器固定为连接自己的号，配置没有“填别人的号”这一项，外部内容也改不了。**默认值变了**：以前节点名固定是 `link-reader（外部内容）`，现在留空就是她的 QQ 昵称（用户要求）。节点名不再标出“这是外部内容”，外部来源仍靠节点的内容和链接本身。

示例（`sumika.example.yml` 里是注释掉的）：`source: "$标题"`、`news: ["$字数", "$图片数"]`、`summary: "$UP主"`、`prompt: "$标题"`。节点名“亚托莉”是用户个人配置，由用户写进真实配置，不进仓库。

### 占位符（四项通用，不分站点）

| 写法 | 值 | 缺时 |
|---|---|---|
| `$标题 $title` | 标题；没有标题的帖子用正文第一行 | 都没有 |
| `$字数 $chars` | “共 N 字”：正文字数，pixiv 小说用站点给的字数 | 0 字或没取到 |
| `$图片数 $图数 $images` | “N 张图”：内容里的静态图数，pixiv 以作品页数为准，动图和视频不算 | 0 张或没取到 |
| `$UP主 $作者 $author` | 作者名（只取名字，不带账号） | 没取到 |
| `$站点 $site` | 同各站点的 `$站点`，如“B站动态”“X 推文” | 站点没有 |

规则：没有 `$分段`、`$合并转发`、`$节点` 和任何图片占位符，写了会报“不认识”。**模板里直接写的占位符有一个缺（或为空），整项退回 QQ 默认**，不留“未返回”的空壳；写在 `[ ]` 里的缺了只省这一段。预览两行里缺的那行不出，另一行照常。换行换成空格，每项只占一行。字符串前后空白去掉。

### 显示长度

超长自动截断（2026-11-13 起走统一的截断写法 `linktrunc.Display`：截在最近的标点后，补“……”，不另起一行）。长度按显示宽度算：全角字（汉字、全角符号、中文引号、表情）算 1，半角字母数字符号算 0.5，“……”算 2。上限是**保守取的、没有在 QQ 客户端上逐项核实**：标题 16、预览每行 18、摘要 18、外显 16（单位都是全角字）。以后在真机上量到实际上限再改常量（`linktemplate/card.go`；`RenderCard` 只渲染不截，截断在 `linkexpand.BuildCard`）。节点名的 40 字和读侧 `cardNodeName` 一致。

### 谁来做

- 正常路径：`linkexpand.Build` 末尾对每个合并转发段调用 `applyForward`：节点名按设置，卡片按内容渲染，挂在 `Part.Card`；`Preparer` 带到 `types.Part`。
- 降级路径：`linkplugin/degrade.go` 的 `asForward` 把消息包成转发时同样套节点名和卡片；转发拆单元、转 180°、备份、克隆都带着卡片和“用昵称”标记。
- 发送：`snowluma` 的 `forwardAction` 只传有的项（空项不传，让 QQ 用默认）；节点 `Self` 为真且核验时记下了昵称就用昵称，否则用节点上的名字。昵称在每次核验成功时更新，重连不清。
- 出口守卫：节点名和卡片文字都过发送前检查。
- 设置页：链接解析里的“合并转发”分组，见第十节；`sumika-ctl link preview` 的输出多一行卡片。
