# 规格：看门狗（心跳、守护进程、异常退出记录和通知）

> 状态：已合 main（2026-11-13，接线提交；代码 `native/internal/watchdog/`、`native/watch.go`、配置 `watchdog` 一节）；真机验收和开机自启切换待主人在场（见待办）。依据 [ADR-365](决策记录.md#adr-365看门狗桌面程序写心跳守护进程拉起并盯着它异常退出留记录弹通知取代-adr-109-第-5-条推翻不要守护进程)；用户 2026-11-13 同意“每分钟心跳、守护进程拉起、桌面通知、留崩溃记录”。
>
> 参考：Bun 时代的 `scripts/supervise.ts`（ADR-109 第 5 条：异常退出自动重启、逐次拉长等待、10 分钟里崩 5 次就停；退出码 0、69、78 不重启，75 立刻重启）；它随 Bun 后台一起移进了存档，Go 版的正式启动链上从来没有对应物。采用其中的“限次数、区分正常退出”和退出码 75 的约定；不采用逐次拉长等待（本规格用固定的几秒）。

## 一、背景和现状

2026-11-12 19:37 前后 `sumika.exe` 无声退出，没有关机诊断、没有系统事件，7 个小时没人发现，QQ 消息一直没收。11-13 已加 `logs/crash.log`（`native/crashlog.go`，`runtime/debug.SetCrashOutput`）：Go 运行时崩溃时留下调用栈。但被外部结束、内存耗尽被系统杀掉这类“没有 Go 崩溃信息的退出”仍然无声，而且退出之后没人拉起。

启动链的现状（2026-11-13 读码确认）：

- 开机自启是 mygo 写的 Run 项：`HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 里 `Sumika` = `"<exe>" --mygo-opened-at-login`，**直接启动桌面程序，没有守护进程**。
- `scripts/supervise.ts`、`data/logs/supervise.log` 都不存在（Bun 后台移进存档时一起走了）；Go 里没有任何监护桌面程序的代码。`native/bunchild.go` 的 `bunSupervisor` 只看护桌面程序拉起的 Bun 子进程，和本规格无关。
- Go 桌面程序的退出码：正常退出 0；单实例已有一个在运行时直接 `return 0`；`quitBudget`（30 秒）内收不完后台时 `mygo.App.Exit(1)`；参数错误 2；没接住的 panic 是 2；被任务管理器结束是 1。没有任何地方用 75。

## 二、整体

```
开机 / sumika.exe -watch
   └─ 守护进程（sumika.exe -watch，不开窗口，不碰 mygo）
        └─ 桌面程序（sumika.exe，不带 -watch，环境变量 SUMIKA_WATCHED_BY=<守护进程号>）
             ├─ 每 60 秒写 <数据目录>/run/heartbeat.json
             └─ 退出流程一开始就在心跳里记 quitting
   守护进程每个检查周期写 <数据目录>/run/watchdog.json
```

选型：**同一个 exe 当守护进程**（`-watch`），不另做 `sumika-watch.exe`。理由：换 exe 的流程不变（主会话本来就只编一个 sumika.exe）；数据目录、配置、根目录的定法直接复用 `resolveDataDir` 和 `config.LoadIn`，不用再写一份；`ctl quit` 让桌面程序退出 0，守护进程跟着结束，exe 文件随之解锁，所以“换 exe 前先 quit”照旧够用。代价：守护进程占一份 exe 的内存映像（十几 MB），可以接受。

守护进程在 `runMain` 解析完参数后立刻 `return runWatchdog(...)`，**不碰 mygo.App**（没有单实例锁、托盘、窗口）。它自己的单实例用 Windows 命名互斥量 `Local\SumikaWatchdog-<数据目录哈希>`：一个数据目录只许一个守护进程。

## 三、心跳

`<数据目录>/run/heartbeat.json`，每 `watchdog.heartbeatSeconds`（默认 60）秒原子写一次（先写 `.tmp` 再 `fileatomic.Replace`）：

```json
{"pid":4242,"startedAt":"…","time":"…","version":"(devel) abc12345","phase":"receiving","runningTurns":1,"quitting":false}
```

- 在桌面程序真正的入口 `runMain` 才打开（`heartbeatEnabled`，和 `crashLogEnabled` 同理）；演示（`-demo`）、远端界面（`-backend-url`）、测试里不写。数据目录定下来之后（`shell.ready` 后台线程里 `initSettings` 之后、`host.start` 之前）开始；开始前不写，靠守护进程的“刚拉起宽限”。
- 心跳由独立协程写，**只能看出整个进程有没有卡死**（运行时死锁、整进程挂起、被调试器停住），看不出界面线程卡住：界面线程卡住时心跳照写、管道服务照回，后台照常收消息，不当卡死。
- `quitting`：`beforeQuit` 第一次进入退出流程时，在后台线程里先写一次带 `quitting:true` 的心跳，之后每次心跳都带着。用途见下一节“退出码”。
- 写失败只记一次日志，恢复时记一行，不刷屏。

## 四、守护进程（`internal/watchdog`）

### 4.1 拉起

拉起 `os.Executable()`，参数是自己的参数去掉 `-watch`（`-data`、`-root`、`-account` 原样传），环境变量加 `SUMIKA_WATCHED_BY=<守护进程号>`（桌面程序读完就 `Unsetenv`，不传给它再起的子进程）。每次拉起前重读配置里的 `watchdog` 一节：改了下次拉起生效；配置读不了用默认值并写日志，**不挡着桌面程序起来**。数据目录读不到时，守护进程的记录先落在 `%LOCALAPPDATA%\Sumika\watchdog`（`os.UserCacheDir`）。

### 4.2 退出怎么分类

| 情形 | 处理 |
| --- | --- |
| 退出码 0 | 正常退出（托盘退出、`ctl quit`、单实例已有一个在运行）。守护进程**不拉起、不通知**，自己也结束。拉起后不到 10 秒就退出 0，日志里写明多半是单实例 |
| 退出码 75 | 桌面程序要求重启（ADR-070 的约定，现在没人用）。运行满 10 秒：不留记录、不通知，立刻重新拉起；不满 10 秒（启动循环）按崩溃算 |
| 退出前心跳里 `quitting` 为真（pid 要对上） | 用户要的退出，只是收尾出了非零码（典型是 30 秒收不完走 `Exit(1)`）。**不拉起、不通知**，守护进程结束 |
| 系统正在关机或注销（`GetSystemMetrics(SM_SHUTTINGDOWN)`） | 不拉起、不通知。判定在异常退出之后、拉起之前各做一次（中间隔 `restartDelaySeconds`，让系统有时间把守护进程一起带走） |
| 其他（非 0 / 75 的退出码，包括被任务管理器结束的 1） | 异常退出，见 4.3 |
| 拉起本身失败（找不到 exe 等） | 同样按异常退出，原因写“拉起失败”，计入连续崩溃 |
| 卡死被杀 | 见 4.4，之后按异常退出 |

被任务管理器手动结束 sumika.exe 无法与崩溃区分，会被拉起并通知；要停就用托盘退出或 `sumika-ctl quit`。

### 4.3 异常退出

1. 写 `<数据目录>/logs/incidents/<年-月-日_时分秒>.md`（同一秒重名加 `-2`）：原因、退出码、进程号、运行时长、窗口内第几次、**拉起前后 `crash.log` 新增的部分**（超过 64 KB 只留尾巴；文件变小当作被清过，从头读）、`desk-<日期>.log` 最后 60 行（日志写入时已脱敏）。原日志不挪动不删。
2. 更新 `run/watchdog.json` 的 `lastIncident`。
3. 超过连续崩溃上限（`crashWindowMinutes` 分钟里第 `crashLimit` 次）：**不再拉起**，弹通知“Sumika 反复异常退出，已停止自动重启”，状态写 `gave-up`，守护进程退出码 1。
4. 否则等 `restartDelaySeconds` 秒，再次检查关机，拉起；拉起成功之后弹通知“Sumika 刚才异常退出，已经自动重启”，正文写原因和事件记录文件名。

### 4.4 卡死判定

每 30 秒检查一次（`ParamsFrom` 里的 `CheckEvery`，不进配置）。

- 参照时刻：读 `heartbeat.json`，**`pid` 必须是自己拉起的那个进程**（上一次运行留下的旧文件不算数）；对得上取心跳时间，限期 `stuckMinutes`（默认 5）；没有这个进程的心跳，取拉起时刻，限期 `startGraceMinutes`（默认 3）。
- 没超限期：什么也不做。超了：用控制接口探测——`ctlproto.Dial` 管道、发 `status`、核对回话的 `pid` 就是我们拉起的进程，时限 10 秒（`status` 在界面线程忙时最多要约 5 秒才回，不能用更短的）。**探测通了：不是卡死**（比如长回合里心跳协程被饿住），只记一行日志，之后不再重复记，直到心跳恢复。
- 探测不通要**连着两次**（相隔一个检查周期）才杀（`Process.Kill`），然后走 4.3，原因“卡死”。杀了 15 秒仍没退出（杀不掉）：守护进程放弃，状态 `gave-up`。
- 睡眠/挂起：两次检查的间隔超过 3 个检查周期，认为电脑睡过，从醒来这一刻起重新算，这一轮不判卡死。

### 4.5 状态文件

`<数据目录>/run/watchdog.json`：`pid`、`startedAt`、`updatedAt`（每个检查周期刷新）、`state`（`running` / `gave-up` / `stopped`）、`childPid`、`restarts`、`lastIncident`。守护进程重启时把上一份的 `lastIncident` 带过来。“守护进程在不在”= `state=running` 且 `updatedAt` 在 3 分钟内且进程号还活着。

## 五、开机自启

Run 项由 `watchdog.Autostart` 管，值名沿用应用名（`Sumika`，和 mygo 写的同一项，所以是替换不是新增）：

- 开：`"<exe>" -watch`，并清掉任务管理器“启动”页的禁用标记；关：删 Run 项和禁用标记。
- 读：Run 项是 `-watch` 写法或 mygo 以前的 `--mygo-opened-at-login` 写法（路径要指向当前 exe）且没被任务管理器关掉，都算开着。
- 迁移：桌面程序启动时（`ready` 后台线程，开日志之后）若发现 Run 项还是 mygo 的旧写法并且指向当前 exe，改写成 `-watch` 写法，别的什么都不动（连“被任务管理器关掉”的状态也留着）。指向别的路径、用户自己加了参数的一律不碰。
- 托盘“开机自动启动”和 `sumika-ctl autostart on|off` 都经 `shell.openAtLogin / setOpenAtLogin`，这两个函数在正式运行时换成上面的实现；演示和远端界面仍用 mygo 的。
- 不用 mygo 的 `SetOpenAtLogin`：它把参数写死成 `--mygo-opened-at-login`，Run 项带不了 `-watch`，而且它的 `OpenAtLogin` 只认自己写的那一种值。

**`Sumika.lnk`（桌面快捷方式）仍直接启动桌面程序**，不经守护进程；需要的话把快捷方式的目标改成 `"<exe>" -watch`（见待办）。

## 六、sumika-ctl status

`status` 的回复多一栏 `watchdog`（`ctlproto.WatchdogInfo`）：`running`（守护进程在不在）、`supervised`（这个桌面程序是不是它拉起的）、`pid`、`state`、`restarts`、`lastIncidentAt` / `lastReason` / `lastFile`（最近一次异常退出）。文字输出多两行：`守护进程：在（进程 N，这一轮已重新拉起 K 次）`（或“已停止拉起”“状态文件太旧”“没有（桌面程序是直接启动的，崩了没人拉起…）”），以及 `最近一次异常退出：…`。演示数据没有这一栏。守护进程已经放弃、桌面程序也没在运行时 `status` 连不上（退出码 2）：靠桌面通知和 `logs/incidents/` 发现。

## 七、配置键

`sumika.yml` 的 `watchdog` 一节（`native/internal/config/watchdog.go`，示例见 `sumika.example.yml`）：

| 键 | 默认 | 范围 | 作用 |
| --- | --- | --- | --- |
| `heartbeatSeconds` | 60 | 5～600 | 桌面程序写心跳的间隔 |
| `stuckMinutes` | 5 | 2～120 | 心跳多久没更新才去探测；至少是 `heartbeatSeconds` 的三倍 |
| `startGraceMinutes` | 3 | 1～60 | 刚拉起还没第一次心跳的宽限 |
| `crashLimit` | 3 | 1～20 | 窗口里异常退出这么多次就不再拉起 |
| `crashWindowMinutes` | 10 | 1～240 | 数连续崩溃的窗口 |
| `restartDelaySeconds` | 3 | 0～60 | 异常退出之后等几秒再拉起 |
| `notify` | true | — | 弹桌面通知 |

不进配置的：检查周期 30 秒、探测时限 10 秒、探测连续不通次数 2、杀不掉的等待 15 秒、`minUptime` 10 秒、事件记录里 desk 日志 60 行、crash.log 上限 64 KB。

## 八、通知

Windows 桌面通知经 `powershell.exe`（Windows PowerShell 5.1，系统自带；不用商店版 pwsh，它没有 WinRT 投影）调用 `ToastNotificationManager`，脚本用 `-EncodedCommand` 传，标题和正文走环境变量，不拼进脚本。守护进程没有自己的应用标识，借 Windows PowerShell 的标识弹，通知上显示的来源是“Windows PowerShell”。弹不出来（专注助手开着、PowerShell 被禁用）只记日志，不影响拉起。通知通过 `Notifier` 接口注入，测试里换成假的。

## 九、禁止的偷懒写法

- 不另起一套监护：Bun 时代的 `supervise.ts` 已在存档，本规格是 Go 版唯一的一套；`bunSupervisor` 是另一件事（看护 Bun 子进程）。
- 不用“进程不在了”代替“退出码”：必须拿到真实退出码才能区分正常/异常；不用 `tasklist` 轮询。
- 不靠心跳超时就杀：必须探测控制接口、连续两次不通、且回话进程号对得上。
- 不用固定时长的 `sleep` 当同步；时钟、子进程、通知、探测全部注入，测试拨假时钟。
- 不读写真实 Run 项、真实管道、真实桌面通知做测试（注册表只用临时子键）。
- 不在守护进程里碰 mygo.App（它会抢单实例锁、初始化窗口系统）。
- 不让配置读坏挡住桌面程序启动。

## 十、已知的坑

- **换 exe**：守护进程和桌面程序是同一个 exe 文件，守护进程活着时 exe 被占用写不进去。换 exe 的顺序仍是先 `sumika-ctl quit`（桌面程序退出 0，守护进程随之结束），换好后用 `sumika.exe -watch` 或开机自启重新带起。
- **手动起的实例**：先手动起了不带 `-watch` 的 sumika.exe，再起 `sumika.exe -watch`，被拉起的那个因为单实例直接退出 0，守护进程随之结束，已经在跑的那个不受守护。
- **关机**：关机时系统结束进程的先后不定；靠 `SM_SHUTTINGDOWN` 加 3 秒延迟兜底，仍可能在注销瞬间多出一份事件记录，是误报，不会多拉起一个（拉起前再查一次）。
- **崩溃信息仍可能为空**：被外部结束、被系统因内存杀掉、卡死被我们杀，都没有 Go 的崩溃输出，事件记录里 crash.log 一节是空的，只剩退出码和 desk 日志。
- **被 Claude 桌面应用的空闲自更新连带结束**（2026-11-13 查实，11-12 19:42 和 11-13 08:36 两次）：从 Claude 的 Bash 或 PowerShell 工具里起的守护进程和桌面程序，在 Claude 空闲自更新时（它的 main.log 记 `[stealth-update]`，AppX 事件 `TerminateApplications`）一起被结束，来不及写任何东西，`run/watchdog.json` 永远停在 running。**启动、换 exe 用任务计划**：`schtasks //Run //TN SumikaDeskOnce`（Git Bash 里写双斜杠，PowerShell 里单斜杠；任务的动作是 `sumika.exe -watch`，父进程是 svchost，不在 Claude 的进程树里）。对账兜底：守护进程启动时拿旧的 `run/watchdog.json` 对一遍，旧状态是 running、旧守护进程和旧桌面程序的进程都不在、旧状态写在这次登录以后（重启、注销本来就结束所有进程）、心跳没带退出标记，就记一行“上一个守护进程没留结束记录……”和一份 `external_kill_suspected` 事故记录（退出码写“未知”），并让 `sumika-ctl status` 的最近一次异常退出指向它；旧的 `watchdog.json`、`heartbeat.json` 覆盖前各留一份 `.prev`。旧守护进程还活着（另一个实例在跑）一概不报、不动 `.prev`。不弹通知。
- **注册表看起来被隔离**：从 Claude 的 Bash 里读当前用户 Run，有 Sumika 这一项；从任务计划里读（真环境），没有，别的项都在。原因多半是 Claude 是 AppX 应用，它的包目录里有私有的注册表文件（`Packages/Claude_*/SystemAppData/Helium/User.dat`），它起的进程对当前用户注册表的读写落在那里。所以 Claude 里起的 Sumika 报“开机自动启动：开”不作数，任务计划起的报“关”才是真话；要真开，从任务计划起的 Sumika 上跑 `sumika-ctl autostart on`。Run 项和 exe 路径的比较已改成按文件认（大小写、`\\?\` 前缀、正斜杠、`.`/`..`、8.3 短名、引号都不影响），但这不是上面那个差异的原因。
- 退出码是 `int`，Windows 的 NTSTATUS 类退出码（如 `0xC0000005`）在事件记录里同时写十进制和十六进制。

## 十一、验收标准与对应测试

| 标准 | 测试 |
| --- | --- |
| 正常退出不拉起、不通知、不留记录，守护进程结束 | `TestNormalExitDoesNotRestart`、`TestInstantZeroExitIsNormal` |
| 崩溃后写事件记录（含新增 crash.log、desk 尾部，不含旧内容）、拉起后通知、状态更新 | `TestCrashWritesIncidentRestartsAndNotifies` |
| 通知开关 | `TestNotifyOffStillRestarts` |
| 连续崩溃停止拉起并通知；窗口外的不连着算 | `TestCrashLoopStopsRestarting`、`TestCrashesOutsideWindowDoNotAccumulate` |
| 退出过程中的非零码、关机都不拉起；别的进程号的 quitting 不算 | `TestQuittingNonZeroExitIsNotCrash`、`TestQuittingFromOtherPidIsIgnored`、`TestSystemShutdownIsNotCrash`、`TestShutdownDuringRestartDelay` |
| 75 的两种情形 | `TestExit75RestartsQuietly`、`TestExit75LoopIsCrashLoop` |
| 拉起失败计入崩溃 | `TestSpawnFailureCountsAsCrash` |
| 卡死：连着两次探测不通才杀；探测通了不杀；心跳新鲜不探测；宽限；别的进程号的心跳不算；睡眠不误判；杀不掉放弃 | `TestStuckChildIsKilledAfterTwoFailedProbes`、`TestStaleHeartbeatButProbeAnswersIsNotStuck`、`TestFreshHeartbeatNeverProbes`、`TestStartGraceBeforeFirstHeartbeat`、`TestHeartbeatOfOtherPidIsIgnored`、`TestSleepGapDoesNotLookStuck`、`TestUnkillableStuckChild` |
| 真子进程的退出码、杀进程、整个循环（崩一次再正常退出） | `TestStartExecExitCodesAndKill`、`TestSupervisorWithRealProcesses` |
| 探测只认我们拉起的进程 | `TestProbeConn` |
| 心跳原子写、读坏了报错、退出标记、失败只记一次 | `internal/watchdog` 的 `TestHeartbeat*`、`TestBeater*` |
| 开机自启读、写、迁移，注册表读写（临时子键） | `TestAutostart*`、`TestRegistryRunStore`、`TestMigrateAutostartAndToggleFunctions` |
| 启动对账：没留结束记录且进程都不在才报；正常结束、停止拉起、另一个实例在跑、桌面程序还活着、上次登录之前、正在退出都不报；覆盖前留 `.prev` | `reconcile_test.go` 的 `TestReconcile*` |
| 开机自启的路径比较按文件认（前缀、斜杠、大小写、`..`、短名、引号），不同文件不误认 | `TestAutostartOnNormalizesPaths`、`TestAutostartOnExpandsShortPaths` |
| 配置默认值、范围、三倍关系 | `internal/config` 的 `TestWatchdog*` |
| 桌面程序一侧：心跳随 ready 开、演示/远端/测试不写、`status` 带守护进程一栏 | `watch_test.go`、`cmd/sumika-ctl` 的 `TestHumanOutputWatchdog` |
| 改坏检查（正常退出被拉起、卡死不看探测等）各让对应测试变红 | 见 ADR-365 影响清单里的记录 |

真机验收（要主人在场，不在本分支完成）：用新 exe 带 `-watch` 起，任务管理器结束 sumika.exe，30 秒内应当看到桌面通知、`logs/incidents/` 新增一份、`sumika-ctl status` 里“最近一次异常退出”；再 `sumika-ctl quit`，不应再被拉起。
