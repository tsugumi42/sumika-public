## 零、先说人话（给主人）

记忆已经在 Go 后台里跑（你的 QQ 私聊第一档写入开着），但"她记了什么、凭哪句话记的、谁放行的"现在只能看日志或去翻库文件。桌面程序里"记忆"那一页还是空占位。这份规格把它做出来，分两步：

1. **第一步，只看不改**：选一个角色，列出她记的事（事实、约定、喜好、边界）和片段；能按种类、按状态、按范围、按会话筛，能搜；点开一条，看到：
   - 它现在算什么：**你确认过** / **她自己提升的**（攒够了几次证据）/ **导入的**（从旧版带过来、没记过是谁放行的）/ **听说的，待确认**（已攒几次）/ 已撤销 / 被新的取代；
   - 它能在哪些地方被想起（只在你在场的地方、某个群、和某人的私聊、所有地方）；
   - 出处：**哪天、哪个会话、哪句话**（原话从聊天记录里按那一条取出来，不抄进别处，被撤回的不显示）；
   - 变化过程：谁在什么时候写下、放行、取代、撤销，原因是什么。
   这一步页面上没有任何会改库的按钮。
2. **第二步，能动手**：撤销、恢复、把"听说"的确认成有效；真删和"忘掉某个人 / 某段对话"只有你亲手点、点两次才做。第二步里有几条"谁能做什么"的默认值（比如能不能撤销"你确认过的"，恢复以后回成什么）要你定，第十二节。

页面显示这个角色**所有场合**的记忆（这是你一个人的桌面程序），但每条都标清范围，免得你误以为"她在群里也会说"。

## 一、范围

**做**：
- 第一步：只读的记忆页（列表、筛选、搜索、详情、出处、变化过程、最近变动）；给界面用的读接口和它的服务；装配；放大十倍的量数。
- 第二步：撤销、恢复、确认待确认；真删；忘掉某人 / 某段（都要先看影响几条）。

**不做（各有去处）**：

| 东西 | 为什么不做 / 去处 |
|---|---|
| 共用库 `owner-memory.db`（ADR-162） | Go 里还没有。做了以后多一个来源，列表里加一栏"主人的事（所有角色共用）"，第一步不显示 |
| 近期记忆 `recent_notes`、条目 `entries`、`rejected`（AI 没通过）、淡忘 | 规格-记忆-v2 第三～六节，Go 里没有表也没有代码。页面看到不认识的状态就如实写出那个词，不编栏 |
| 顶上选"全部角色"合在一起翻 | 每个角色是单独的库，合着翻页要另做；第一步一次看一个角色，角色按钮上带条数 |
| "试一下她会想起什么" | 要调召回（要嵌入、会碰召回日志），不是纯读；排在第二步之后 |
| 滑卡片确认（`SwipeStack`） | 第二步稳了以后再看，待办"更多地方用滑卡片" |
| 改字、改范围 | 改字 = 新建一条取代旧的（保住"当时记的是什么"）；改范围是"谁能看什么"的默认值变化。都放第二步以后，要主人定（第十二节 Q7） |
| 从出处跳到聊天页那一句 | 要先有跨页面跳到某条消息的办法（待办"记忆页的后续"） |
| 导出 | 没人要 |

## 三、谁能看到什么、谁能做什么

### 3.1 页面本身

- 记忆页是**桌面程序主窗口的一页**，只有坐在这台电脑前的你能看到。读接口 `api.MemoryReader` 只交给桌面窗口；**不交给** `ctlserver`（`sumika-ctl`）、渠道中间件、对话循环、工具、记忆插件。用架构测试钉住：`turn`、`channel`、`memplugin`、`tools`、`ctlserver` 不能依赖 `internal/memview`，也不能依赖放着记忆类型的整个 `internal/api`（Go 的依赖图只到包，分不出类型；这五个包今天本来就不依赖 api。哪天某个包真要用 api，先把记忆类型拆进自己的包再改测试；`archcheck/memview_test.go`）。
- 页面显示**所有场合**的记忆，不套 `AllowedScopes`（那是"她在某个场合能想起什么"，页面是"库里有什么"）。但每条标清范围，并且告诉你她在四种场合里各想不想得起（3.2）。
- 页面读到的内容**不进模型上下文、不进日志、不进别的库**：日志只写计数和 ref（照 memory 包的 Logf 约定），搜索词不写日志，出处原话只在内存里、关掉详情或换角色就丢。

### 3.2 范围标签怎么写

已被 ADR-242 改为：范围标签只解释来源，不表示在哪里能想起。详情里的本地私聊、本地群聊、QQ 私聊、QQ 群都写想得起；过期、撤销、被取代、隔离线仍决定当前能否召回。QQ 的披露规则由角色提示词和守卫执行。

|范围值|来源标签|
|---|---|
|`public`|公开来源|
|`owner`|主人场合的来源|
|`conv:<会话>`|来自〈会话名〉|
|`person:<id>`|和〈人名〉的私聊来源|
|空、未知或畸形值|范围不认识（原文前 40 字），不伪造来源|

页面使用显式主人共用库与当前角色库的只读 SQL 视图；列表、搜索、计数、详情、证据、修订和变化通知都包含共用事实。共用事实在来源会话后显示“主人共用，由〈角色〉得知”；其他角色的专属库不参与查询。原话仍走当前角色的事件来源，不能因共用而读取未见原文。实现与验收见[记忆召回不分场合](规格-记忆召回不分场合.md)。


### 3.3 出处原话

- 事实：`source_seqs`（JSON 数组，每个是整数）加 `conversation` 列；证据行自带（会话, seq）；片段：`from_seq..to_seq` 加 `conversation`。**按（会话, seq）取**，会话决定去哪个平台库（ADR-199）。
- 取原话走这个角色的**事件来源**（`memory.EventSource`，装配用 `memsource.NewMulti`，和 recall_raw 读原话是同一条路）：`Events(会话, seq-1, 1)` 取一条，核对序号和会话都对得上；撤回（`Revoked`）、"这个角色看见过"（`Seen`，QQ 会话看 observations；本地会话只认 `console:<自己>`）、识图简述都用它现成的。**取不到别的角色没看见的事件**。（原来写的"走展示投影 `ReadDisplayEvent`"改了：那个按事件 id 取、不是按 seq，要另加一个函数；事件来源本来就按（会话, seq）走。）
- 被撤回的消息显示"这句话后来被撤回了"，**不显示正文**；找不到的（导入时没对上、聊天记录被清）显示"原话找不到了"，不报错、不影响别的行。
- 一条原话截 200 字，图片只显示占位和识图简述；**不复制进别处**：不进记忆库、不进日志、不进缓存文件、不进剪贴板（页面不做"复制原话"按钮）。内存里最多留 20 条（超出的从最早取的开始丢，丢掉的回到“看这一句”），关详情、换角色、离开记忆页就清。原话用**不可选中**的文字画：能选中就能 Ctrl+C 进剪贴板，和“不进剪贴板”冲突。
- 导入的旧事实 `source_seqs` 记的是整批几十句（规格-记忆管理第九节第 6 条）；Go 新写的按 ADR-231 只有恰好一行。显示：序号数 ≤ 3 全显示；多于 3 条时只显示前 3 条，写"这条是整批总结的，共 N 句"。旧规格那个"按字面重合挑最像的三句"的启发式**不做**（第二步以后看有没有人要）。

### 3.4 读的时候遇到的形状（缺、空、0、类型不对）

每个入口（列表、计数、详情、证据、出处、搜索、变化轮询）读同样的列，所以一张表一次定死，实现照表写、测试照表出：

| 形状 | 处理 | 测 |
|---|---|---|
| 库里没有 `confirmed_by` 列（没迁移的 Bun 库） | 按空读，状态标"导入的"；页面顶上提示"这个库还没迁移" | `TestBrowseUnmigrated` |
| 没有 `item_scopes` 表 | 退回 `scope` 列单值（同 `scopesOf`） | 同上 |
| 没有 `fact_evidence` 表 | 证据为空，详情写"旧库没有证据记录" | 同上 |
| `fact_revisions` 没有 `before_json` / `after_json` 列 | 当 null，变化过程只写 op、谁、时间、原因 | 同上 |
| `episodes` 没有 `status` 列 | 全当 active | 同上 |
| `status` 是不认识的词、`kind` 是不认识的词 | 原样显示那个词，状态筛选放进"其他" | `TestBrowseUnknownStatus` |
| `created_at` 为空或 0、`learned_at` 为 0 | 排在最后，时间显示"不详"，不显示 1970 年 | 同上 |
| `source_seqs` 不是数组、含非整数 / 负数 / 超大数 / 重复 | 当没有；序号去重，只取前 50 个 | `TestBrowseSourceSeqs` |
| `source_seqs` 为空 `[]` | 详情写"没有记下出处" | 同上 |
| 证据行的会话和事实的会话不一样 | 取证据行自带的会话，不用事实的 | `TestQuoteUsesEvidenceConversation` |
| 角色没有 `memory.db`（`openMemories` 里跳过的） | 角色按钮灰着，右边写"还没有记忆库"，不报错 | `TestOverviewCharacterWithoutDB` |
| 角色 id 不合法（带路径分隔符、冒号、`..`） | 参数错误，不拼路径（`ValidCharacterID`） | 同 memory 包的 B17 测试 |
| `ref` 畸形（`f:`、`x:1`、超长、带引号） | 参数错误；SQL 一律绑定参数，不拼 | `TestRefValidation` |
| 游标是别的筛选条件下发的、被篡改 | 参数错误（游标里带筛选条件的指纹） | `TestCursorBoundToFilter` |
| 搜索词含 `%`、`_`、`\` | 转义后按字面搜（`LIKE … ESCAPE '\'`） | `TestSearchEscapes` |
| 搜索词为空 | 等于不搜 | 同上 |
| 库在读的时候被后台整理写（读事务和写事务交错） | 每个查询一个短读事务；列表和计数可能差一拍，页面不假装一致，用变化标记提示（四点五） | `TestBrowseWhileWriting` |
| 查询超过 5 秒 / 上下文取消 | 返回失败 + `Stale`，保留上一屏的值 | `TestBrowseTimeout` |

### 3.5 敌对输入

记忆正文、`subject`、`attributed_to`、`speaker` 都可能是群友说的话变来的（任意字符串）：

| 输入 | 处理 |
|---|---|
| 正文里有 Markdown、HTML、链接、`ignore previous instructions` 之类像指令的话 | 一律当纯文本画：不解析 Markdown、不开链接、不做任何"执行"。页面从不把记忆正文送给模型 |
| 正文里有换行、制表符、零宽字符、控制字符、一万字 | 列表里并成一行、截 120 字；详情里控制字符和零宽字符换成可见的占位，显示前 2000 字，其余折叠 |
| 正文里有长串数字（QQ 号） | 照样显示（你自己的屏幕，且这是数据本来的样子）；**日志、报错、测试里不出现**（待办"记忆正文里写着群友的 QQ 号"是记忆本身的问题，不在页面解决） |
| `subject` / `attributed_to` / `speaker` 写成"主人""我""system" | 身份标签只由数据里的类型和 id 定（`owner` / `self` / `qq:<号>` 的形状），**名字只用来显示**，不当"这是你"的依据；人名取自认人那一处，取不到显示打码的 id（用项目现成的 `config.MaskID`：星号加最后两位；"同名的两个群友"靠它区分） |
| `conv:`、`person:` 里的 id 是别的角色没看见的会话 | 照实显示范围；取原话时的观察过滤挡住它（3.3） |
| 同名的两个群友 | 显示名旁边带打码 id，不合并 |

## 四、技术路线

### 4.1 三层，各管一件事

| 层 | 在哪 | 管什么 |
|---|---|---|
| 读库 | `internal/memory/browse*.go`（新文件，不改旧文件） | 一组只读函数：开只读连接、列表、计数、详情、搜索、最近变动。**用 memory 包自己的 `scopeGroups` / `scopesOf` / `Item.Expired` / `quarantined`，不另写一套口径**（边界清单 ⑪）；证据计次抽出一个共用函数（见下） |
| 服务 | `internal/memview`（新包） | 生命周期、5 秒时限、一次一个查询、订阅和变化轮询、取出处原话（连聊天库）、取名字、打码。对外实现 `api.MemoryReader` |
| 界面 | `native/memorypage.go`（新文件）；`ui.go` 只把 `a.rail == 2` 那个占位分支换成一行调用 | 画页面，不碰 SQL |

类型加在 `internal/api/memory.go`（新文件，只增不改 `api.go`，别的分支同时在改它）。`api.MemoryReader` 是**单独的接口**，不塞进现有的 `Reader`（演示用的 `demo_reader.go` 不用跟着改）。

**证据计次要一份**：待确认"已攒 1 / 3 次"必须和提升时的算法一字不差（`write_confirm.go` 的 `tally` 和 `occasions`：本人说的每行一次、转述按说话人去重、至少 1 次本人）。现在它是写事务里的方法。第一步第一个提交把它抽成接收 `*sql.DB` / `*sql.Tx` 都行的纯函数，写事务和页面共用，带一个"抽出来以后写事务行为不变"的测试；页面不另抄一遍规则。三个配置（`confirmOccasions`、`autoConfirm`、`confirmKinds`）由装配经 `MemoryOverview` 带给页面，页面不读配置文件。“攒够会不会自己提升”不能只看配置：装配给 `BrowserOptions.AutoNow`，每次读详情时问写入侧现在的实际状态（`Memory.AutoConfirming()`：可写且整理开着且 autoConfirm 开；只看历史、整理没开成、前提检查没过都是否），页面据此写“攒够就会自己提升”还是“没开自动提升，要你亲口放行”。

### 4.2 怎么读

- **自己的只读连接**，照 `db.go` 的 `openReadOnly`（`mode=ro`、`query_only`、`busy_timeout(5000)`）。**两条**：一条跑查询（`MaxOpenConns 1`，服务里再加 `queryGate` 一次一个，照 `desktopread`），一条只做变化轮询（4.5），免得一个慢查询把变化通知也堵住。不借用后台那条 `*Memory` 的写连接，不开 `memory-v2.db`（那是写方的派生文件）。
- 记忆库是 WAL（Bun 建的），读不挡后台的写、后台的写也不挡读。**不确定 Go 的副本是不是 WAL**（副本是备份拷出来或 `VACUUM INTO` 出来的，`journal_mode` 写在文件头）：第一步第一个提交先查一次，不是 WAL 的话每个查询一个短事务、查完立刻释放，并把查到的写进提交说明。
- 每个查询：`enter` 登记（服务关了就返回 `ErrClosed`）→ 5 秒时限 → 等 `queryGate` → 查 → 查完再看一眼 ctx（取消了就丢结果）。**查询在后台 goroutine，结果经 `Window.Update` 发布**（mygo-maintenance），界面线程不碰库。
- 查询是否过期：每个请求带一个递增的请求号，旧请求回来时请求号对不上就丢（连点筛选、连敲搜索词时不让旧结果盖新的）。

### 4.3 列表、搜索、分页（大数据量）

目标规模：每个角色上千条事实、几千个片段、上万条证据和修订（现在真实库是几百条，见规格-记忆-v2 第二节；按十倍设计）。

- **列表不走 `Items()` 全读**，走 SQL 游标分页：`ORDER BY created_at DESC, id`，条件 `(created_at, id) < (游标)`（不用 offset）；每页 50；界面滚到离底 10 行取下一页（`navigation.InfiniteList` 的 `more` 回调）。游标是不透明字符串，里面带筛选条件的指纹，换了筛选条件拿旧游标要报参数错误。
- 事实和片段是两张表，**列表一次只看一种**：顶上的种类胶囊是"事实 / 约定 / 喜好 / 边界 / 片段"，前四个是 `facts.kind`，"片段"切到 `episodes`。不做两张表的 UNION 排序。
- **筛选**（都是 AND）：状态组、种类、范围类型、会话、关于谁。
  - 状态组由（`status`, `confirmed_by`）算：**你确认过**（active + owner）、**她提升的**（active + ai）、**导入的**（active + 空）、**听说，待确认**（candidate）、**已撤销**、**被取代**、**其他**（不认识的状态，或 active + 不认识的 confirmed_by）。
  - 范围类型：所有场合 / 主人场合 / 某个会话 / 某人私聊；用 `item_scopes` 的前缀匹配。
  - 会话、关于谁：下拉里放最多 20 个，按条数排；其余靠搜索。
- **搜索**：`LIKE '%词%' ESCAPE '\'`，查 `text`、`subject`；词能解析成人（名字或别名，经认人那一处）时再加 `subject IN (…)`。**不用 FTS**：那张全文表在旁边的派生文件里、只收有效和待确认的、要三个字起，页面要连撤销的和两个字的都搜到（同旧规格第九节第 2 条）。几千行上万行的 `LIKE` 是毫秒级，第一步量；搜索结果最多 200 条，到了写"只显示前 200 条，换个更具体的词"。敲字后停 250 毫秒才发查询；新查询取消旧查询。
- **计数**：胶囊上的数字用一条 `GROUP BY` 查完（事实按 `kind, status, confirmed_by`；片段按 `status`），连同角色按钮上的总数、隔离报告一起放进 `MemoryOverview` 快照；变化轮询发现库变了才重算。**计数不随搜索词变**（避免每敲一个字查一遍全表）。
- **不加索引、不改表**：页面只读，不在真实库上做迁移。如果 `fact_revisions(fact_id)` 没有索引而修订行数上了几万，详情的修订查询会整表扫；第一步量，量出来慢再单独走迁移（那是写库，要备份、要主人点头），不在这一步偷偷建。

### 4.4 详情、证据、出处、变化过程

点一条，右栏取详情（一个请求），分块返回，慢的块不挡快的：

1. **字段**（一次查完）：正文、种类、状态组、`confirmed_by`、范围标签、关于谁、`attributed_to`、`speech_act`、`temporal` / `valid_to`、`origin`、会话、创建和学到的时间、取代关系（`superseded_by` 指向的那条，点一下跳过去）。
2. **她现在想得起吗**：一个徽标，由和召回同一套函数算：有效或待确认、没过期（`Expired`）、没被隔离（`quarantined`）才是"她想得起"；过期写"暂时的，已经不再给她"；被隔离写"止血线藏着它"；撤销、被取代写"她想不起"。**范围里的场合表列在详情里**（3.2）。
3. **证据**（只事实）：待确认的写"已攒 N / M 次，其中本人说的 K 次"（共用函数）；列表最多 20 行（天、会话、说话人、是不是本人说的），"再显示 20 行"；每行的原话点开才取。
4. **出处原话**：按 3.3，详情打开时取前 3 条，其余点开才取；一次详情最多发起 10 次聊天库查询，每次走同一个 5 秒时限。聊天库某个平台读不到（没挂、被占用）时，那一块写"现在读不到〈平台〉的聊天记录"，别的块照常。
5. **变化过程**（只事实）：`fact_revisions` 新的在上，每行：时间、谁（`summary` →"整理"，`remember` →"你让她记"，`owner` →"你在界面上"，`migration` →"导入"，别的原样）、做了什么（add / supersede / revoke / restore / confirm / scope / migrate / purged 各一句人话）、原因；有 `before_json` / `after_json` 的把"状态、放行者、范围"的变化写成"待确认 → 有效，放行者：她自己"。每页 20 行。
6. **片段**：没有修订表，只显示状态、范围、会话和 `from_seq..to_seq` 里的头尾几句（最多 3 + 3，中间写"中间还有 N 句"）。

**最近变动**：列表上方有个"最近变动"入口，列 `fact_revisions` 按 `id` 倒序的前 50 行（主键倒序，不扫表），每行带对应事实的正文开头。用途是回答"这几天她自己提升了哪几条、整理撤销了什么"（规格-记忆-v2 4.4 末尾要的每周报表的底子）。

### 4.5 变化通知（这是个洞，选一个定死）

聊天库有 `store.ChangeSub`，`memory.db` 没有。三个办法：

| 办法 | 好处 | 坏处 |
|---|---|---|
| A. 给 `*Memory` 的每个写入口加回调 | 即时 | 要改 memory 包的写路径；只管同进程的写（别的工具写了不知道）；回调里出错会拖写事务 |
| B. 读连接上 `PRAGMA data_version` 轮询 | **不改任何写路径**；任何进程的提交都能发现；一条 PRAGMA，几乎没开销 | 最迟晚一个轮询间隔 |
| C. 轮询 `max(fact_revisions.id)` | 不依赖 SQLite 特性 | 片段的变化看不到，要再加一条 |

**选 B**（我定的）：专用的第二条只读连接，**只在订阅活着时**每 2 秒执行一次 `PRAGMA data_version`（页面不在前台、订阅关了就不轮询）；值变了就重算计数并发布新快照（快照里带 `Revision`，只在同一次订阅里递增）。注意 `data_version` 只对"别的连接的提交"变，所以这条连接绝不用来写，也不和查询共用。

**列表不自己乱跳**：计数立刻更新；列表不立刻重排。库变了而你正看着列表时，列表上方出一条"有 N 处变化，点这里刷新"（用 `Revision` 比较），点了才重取第一页并保持选中项；选中项被撤销或取代了，详情栏顶上写"这条刚刚变了"，不自动关。你什么都没点、列表在最顶端、没有选中项时，才自动刷新。

### 4.6 界面（先对一遍 CrychicUI 的组件，装不下的照最接近的排）

版本：CrychicUI 跟 `native/go.mod`（2026-11-02 本地缓存是 2026-10-27 那一版），先读它的 `AGENTS.md`；"组件库该有的状态和动效"见[规格-组件库需求清单](规格-组件库需求清单.md)。**CrychicUI 的列表类组件多半只收字符串**（`MasterDetail` 收 `[]string`、`FilterChips` 收 `[]string`），装不下带标签和徽标的行，所以行本身自己排（用 `ui.Row` / `ui.Column`），外框、状态、过渡用它的。

| 页面上的块 | 用什么 | 装不下的地方 |
|---|---|---|
| 页面外框、标题 | `layout.PageHeader`（同别的页）；三栏用 `layout.SplitPane` 或照 `ui.go` 现有的 `ui.Row` 排法 | 列宽照会话页：左 300、右栏至少 380 |
| 角色切换 | `navigation.NavRail` 同款竖栏太重；用 `choice.ChipChoice`（单选胶囊） | 角色按钮上带条数：`ChipChoice` 只收字符串，标签写成"铃音 · 236"，数字由我们拼 |

| 搜索框 | `input.DebouncedSearch`（停顿后才报告） | `form.AdvancedSearch` 在 mygo 0.6.3 上有一个测试不过（规格-原生界面原型第一节），**不用**；先用 `DebouncedSearch`，量一下手感 |
| 列表 | mygo 的 `ui.List`（带 `ItemKey`，选中、悬停用 `ui.ListRow`）外面不套 `navigation.InfiniteList`（它把每一行都建出来，上千条不行；实际做法：用 `ListState.Visible()` 看离底 10 行就取下一页，失败后不自己重试） | `data.VirtualList` 的行数固定、高度是选项，不适合追加分页，**不用**；行内容自己排：正文一行 + 一行小字（状态组、范围标签、时间）；照 `chat.ConversationList` 的行（悬停、选中颜色、`kit.Arrive` 入场） |
| 详情栏标签 | `navigation.UnderlineTabs`："详情 / 出处 / 变化" | — |
| 字段 | `display.DescriptionList`（键值行带分隔线） | 范围标签、状态用 `display.Tag` / `display.StatusBadge` |
| 变化过程 | `data.AuditTrail`（谁、做了什么、什么时候）或 `data.TimelineList` | `Audit` 只有三个字符串，"状态 A → B"我们拼进 `What` |
| 空状态、加载、出错 | `feedback.EmptyState`、`feedback.SkeletonList`、`feedback.ErrorState`（有"重试"） | 空状态要分：角色没记忆库 / 筛选后没有 / 搜不到 / 库没迁移 |
| 第二步：确认、危险操作 | 撤销用 `overlay.ConfirmDialog`；真删、忘掉某人用 `overlay.DangerDialog` 再配 `form.TypeToConfirm`；撤销后的"撤销撤销"用 `feedback.UndoToast` | 按钮红色等由它的组件自己定，不自己画 |

**界面文字**按[设计语言](设计语言.md)第十一节：常驻一行，细的折叠；状态词用 3.2 和 4.3 里那几个整词，不写"active / candidate"；按钮旁不摆两三个字的状态；第一步详情里不出现按钮，也不写"敬请期待"。

**场合和尺寸**：窗口按主人的屏幕 2560×1440、缩放 125%（逻辑 2048×1030）排；小窗口（宽 < 1100 逻辑像素）时详情栏改成盖在列表上的一层，不挤成三栏。

**打开页面时的状态**：记住上次选的角色、筛选、搜索词、选中项和详情停在哪个标签（只在内存里，进程退出就忘）；**出处原话不记**（3.3，离开就清，回来点开的重新取）。

**什么时候算“在前台”**：记忆页被选中、并且主窗口显示着没最小化（关窗口只是隐藏，托盘常驻时记忆页不该继续轮询）。只有在前台才有订阅和在途查询：宿主给读服务时不订，切到别的页、窗口隐藏或最小化时取消订阅和在途查询（`Close` 等它们退出，晚到的结果靠代次丢掉），回来重新订、第一份快照到了就整页重取（列表、选中项的详情，开着“最近变动”的也重取；旧的行先留着，新的到了整份换掉）。`Rev` 每次订阅从 0 数起，回来后的第一份快照不能和走开前的比，所以不比版本、一律重取；选中项的状态组和走开前不同就标“这条刚刚变了”。
库没有新提交也要重算的情况：某个角色的概览没算成（5 秒时限到了、闸被占着）时，订阅里每隔 10 秒（`memview.Options.Retry`）重算一次，恢复时 `Rev` 加一；一直失败时不重发一样的快照。

## 五、第二步：能动手

> 第二步**还没有拿到主人的任何一条默认值**（第十二节）。下面写的是推荐做法，主人答了再写 ADR 并改这里。第一步不依赖它们。

### 5.1 写入走哪条路

- 页面的动作**只能经 `internal/memory` 的写事务**（`Memory` 上新增 `Manage*` 方法，新文件 `manage.go`），在同一个事务里改状态并记一行 `fact_revisions`（`by = owner`，`reason` 以"记忆页"开头；旧 Bun 的页面也用 `owner`）。**不许在界面或服务里裸 SQL 写库**。
- 动作只对 `Writable()` 为真的角色可用，也就是默认所有角色（`memory.write.characters` 默认 `["*"]`），显式名单时只有列了的、前提检查（库是 Go 的副本、迁移过、备份做了）都过了的角色（`memwrite.Open`）。否则按钮不出现，详情栏写原因（"这个角色的记忆写入没开"，原因码照 `memwrite` 的）。**这是 Q1：页面要不要有自己独立的开关**，推荐不要。
- 动作带"我看到的样子"：`expect = {status, confirmed_by, 最近一条修订的 id}`；事务里重读，对不上就拒绝，回"这条刚刚变了，刷新看看"。理由：整理在另一个连接里同时写（边界 ⑬、⑭），页面看到的可能已经过期。
- 动作成功后走 memory 包已有的出口（同 `remember`）：刷新条目快照、同步派生的全文和向量表。**不另写 `unindex`**（Go 的派生表是整张从 `memory.db` 重建的，撤销后下一次同步它就没了；第二步动手前读 `apply` 末尾的刷新入口，确认撤销也走它，不走就补，不在管理方法里手写 DELETE）。
- 忘掉某人、真删这两类会让"在途的整理结果"作废：事务里 `BumpGeneration`（世代号加一），在途批次提交时对不上就整批丢掉（规格-记忆-v2 13.2.4 第 6 步）。

### 5.2 谁能对什么做什么（默认值，推荐，待主人定）

行是被动的对象，列是动作；"二次"= 弹确认框，"输入"= 还要输入一个词。

| 对象 | 撤销 | 恢复 | 确认（放行成有效） | 真删 |
|---|---|---|---|---|
| 有效 · **你确认过** | 能，二次 | — | — | 先撤销，再在已撤销里 |
| 有效 · **她提升的** | 能，直接（有"撤销"提示条，10 秒内点它就撤回） | — | 能（把放行者改成"你"，她以后不能再动它）| 同上 |
| 有效 · **导入的**（放行者空） | 能，二次（写明"旧版留下的，整理动不了它"） | — | 能（同上） | 同上 |
| **待确认** | 能，直接（等于"丢掉"） | — | 能 | 同上 |
| **已撤销** | — | 能，回到撤销前的状态，**不直接变有效**（见下） | — | 能，二次 + 输入 |
| **被取代** | 不做 | 不做 | 不做 | 不做（它是"当时记的是什么"，跟着新的走） |
| 片段（有效） | 能，直接（片段只能撤销，ADR-076 第 3 条） | — | — | 先撤销 |
| 片段（已撤销） | — | 能 | — | 能，二次 + 输入 |

- **恢复回成什么**：读这条最近一次 revoke 修订的 `before_json`，回到当时的 `status` 和 `confirmed_by`；读不到（旧库没有 `before_json`、或者撤销时没记）就回**待确认**，不回有效。理由：旧规格第九节第 4 条是"恢复成有效、不是待确认"，那会让"丢掉的待确认"一恢复就变成每轮都给的有效事实，**比撤销前放宽了**；恢复只能回到撤销前的样子，不能更宽（AGENTS「动手前先读」第 7 条：兜底只能收紧）。这条和旧规格不一样，Q3。
- **确认**：`status = active`、`confirmed_by = owner`、**范围一个字不动**（同 `confirmByEvidence`，不同于 `remember` 的 `promote` 会并范围）。理由：页面上点"确认"的候选，范围可能是某个群（`conv:…`），点一下不应该悄悄让它所有场合都想得起；要放宽范围是另一个动作（"改范围"，第一步和第二步都不做，Q7）。
- **取代关系**：确认一条"想取代旧事实"的候选，旧事实仍是 `ai` 放行的 → 同事务取代；旧事实是你放行的或导入的 → 不取代旧的，两条并存，页面提醒"旧的还在，要不要撤销它"（因为这是你亲手点的，不套 W2 的"受保护则不提升"，但也不替你动旧的）。Q4。
- **真删**：只能删已撤销的；删前自动备份这个角色的库（`memory.BackupMemoryDB`），备份失败就不删；删的是行和派生数据，`fact_revisions` 里这条以前的记录也删（撤销原因里可能写着内容），只留一行 `purged`（不留原文）；`fact_evidence`、`item_scopes` 里的行一起删。**删完要再搜一遍**：全库按这条的 id 找，确认 `facts` / `episodes` / `fact_evidence` / `fact_revisions`（除 purged）/ `item_scopes` / `memory-v2.db` 的四张表里都没有它（ADR-034 第 6 条）。
- **忘掉某人**（默认只对当前角色，确认框里能勾"所有角色"，ADR-076 第 2 条）：先 `dryRun` 给出会影响几条，再做；做 = 逐条**撤销**（可恢复），不是真删。**"某人"在这里怎么算**要主人定（Q5）：推荐窄的——`subject` 是他的事实，加范围是 `person:<他>` 的事实，加以他的私聊为会话的片段；**不**撤销"在群里提到他"的事实和片段（里面有别人的信息），而是在确认框里列出"另外还有 N 条提到了他，要不要一起撤销"让你选。一次最多 500 条，超了分批（返回 `more`）。
- **忘掉某段对话**：`{会话, 从, 到}`。事实：**全部出处都落在这一段里**的撤销；一部分在段外的列出来让你逐条看；片段：区间有交集的撤销。同样 `dryRun` 先、再做、做 = 撤销。（语义较复杂，第二步动手前补一小节再做，不在第一步里。）

### 5.3 第二步的验收（先列在这里，做的时候写测试）

1. 每个格子的动作：能做的做成、不能做的（被取代的）被拒；`expect` 对不上被拒，测"整理在页面看到之后改了这条"的交错。
2. 撤销 → 召回里没有它；恢复 → 回到撤销前的状态（有 `before_json` 和没有两种）；候选撤销再恢复回到候选，不是有效。
3. 确认后 `confirmed_by = owner`，范围一个字没变；整理之后再来的证据不会把它降回去。
4. 真删：未撤销的被拒；备份失败被拒；删完全库再搜找不到；`fact_revisions` 只剩 `purged`。
5. 忘掉某人：`dryRun` 的数和正式做的数一样；"在群里提到他"的没有被撤销；在途整理的结果被世代号丢掉。
6. **改坏检查**：拆掉 `expect` 比对、拆掉 `BumpGeneration`、拆掉"备份失败不删"，各自对应的测试要红（拆被测的保护本身，不是另造一个泄露）。
7. 只读的角色（`Writable()` 为假）：页面没有按钮，接口返回"写入没开"，库一个字节不变。

## 八、禁止的偷懒写法

- 不许用 `Memory.Items()` 当页面的数据源（它不含撤销的和被取代的，也会把全部条目读进内存）。
- 不许在 `memview` 或界面里另写一份范围、过期、隔离、证据计次的判断，只能调 memory 包的同一批函数。
- 不许用 offset 分页；不许把用户输入拼进 SQL；不许用 FTS 派生文件当搜索源。
- 不许在界面线程里查库；不许让旧请求的结果盖掉新请求的。
- 不许把记忆正文、搜索词、出处原话写进日志、报错、测试输出、临时文件；报错只带 ref 和原因码。
- 不许复制出处原话进别处（库、缓存、剪贴板）；不许显示被撤回的消息正文。
- 不许把读接口交给 `ctlserver`、渠道、对话循环或工具。
- 第二步：不许在管理方法之外裸 SQL 写库；不许跳过 `expect` 比对；不许在真删前不备份；不许"恢复"变得比撤销前宽；不许对被取代的东西做任何动作。
- 测试只用 `t.TempDir()` 里编的库，名字、群号、QQ 号都编；**绝不读写 `data/` 里真实的记忆库**。

## 九、已知的坑（对着边界清单）

- ④ 生命周期：关窗口只是隐藏（规格-界面接Go后台），退出走托盘。服务的 `Close` 要取消在途查询和订阅并等它们都不再碰库才返回；轮询 goroutine 和查询 goroutine 都登记在 `enter` 里。测：订阅活着时关服务，库文件能立刻被删掉（Windows 上文件被占用是真问题）。
- ⑤ 状态归属：同一条记忆有三个"状态"（`status`、`confirmed_by`、范围）。页面只显示一个"状态组"，但筛选和详情都要能追到原值，**不要把组合压成一个枚举存回库**。
- ⑧ 到达与可用：整理刚写完一批，派生的全文向量表还没跟上——页面不看派生表，所以不受影响；但"她现在想得起吗"徽标看的是 `Memory` 的内存快照还是库？**读库，不读内存快照**，写完到快照刷新之间可能差一拍，徽标上不写"实时"。
- ⑩ 失败前已有成果：详情分块取，某一块失败（比如聊天库读不到）不丢别的块；列表翻页失败保留已取的页，只在底部写"没取到，点这里重试"。
- ⑪ 同一事实不同口径：范围、过期、隔离、证据计次都复用 memory 包的函数（4.1）；状态组的计算只在 `browse` 里一处，计数和筛选共用它。
- ⑬ 并发：读 vs 整理写（短读事务，`TestBrowseWhileWriting` 造一个边写边翻页的交错）；两个请求连发（请求号）；第二步页面写 vs 整理写（`expect`、世代号）。
- ⑭ 非原子更新：第二步"忘掉某人"是逐条撤销，中途失败有一部分已撤销。每条一个事务，返回 `{done, failed, more}`，页面照实写"撤销了 N 条，还有 M 条没成功"，不假装全成或全败。
- ⑯ 空值与非法值：3.4 那张表。
- ㉑ 隐私被复制：正文里的长数字（QQ 号）、出处原话、搜索词都不进日志和别的库（3.1、八）；截图给人看是主人的事，页面不提供"复制"和"导出"。
- 记忆页和聊天页读的是两个库：详情里一块是记忆库、一块是聊天库，任何一个读不到都要可降级。
- 名字不另存一份：群名、昵称取自认人那一处（feat/names-ui 在做），取不到显示打码 id；不在记忆库里加"显示名"列。

- **Q1 页面的写入要不要有自己独立的开关**：推荐不要，页面的动作和 `remember`、整理共用 `memory.write.characters`，一道门、一套前提检查（库是 Go 的副本、迁移过、备份做了），免得出现两条写进库的路各有各的保护。（另一种：页面有自己的开关。好处是只想用页面管理、不想让她能 `remember`；代价是写库的前提检查要拆成两份。）默认所有角色（`*`），显式名单时只有列了的；名单为空时，第二步的页面是只读的，按钮不出现。
- **Q2 撤销能动谁**：推荐上面 5.2 那张表——你确认过的、导入的、她提升的、待确认的都能撤销，前两种要二次确认。（另一种：你确认过的不许在页面撤销，只能用 `remember` 带 `replaces` 换掉；更紧，但你在页面上看到"这条不对"却不能直接处理。）这是"谁能做什么"的默认值。
- **Q3 恢复回成什么**：推荐回到撤销前的状态，查不到就回待确认。（另一种：照旧规格，恢复成有效。更省事，但"丢掉的听说"恢复一下就成了每轮都给的有效事实，比撤销前宽。）
- **Q4 确认一条"想取代旧事实"的候选，旧的是你放行的或导入的**：推荐两条并存、提醒你要不要撤销旧的。（另一种：直接取代，你点了就是你的意思。更利落，但你可能没注意到它顶掉了一条你确认过的。）
- **Q5 "忘掉某人"算哪些**：推荐窄的——`subject` 是他的事实、范围是 `person:<他>` 的事实、以他的私聊为会话的片段；"在群里提到他"的列出来让你选。（另一种：宽的——所有出处里有他说的话的都算。会撤销很多条，其中有别人的信息；做了不容易看清。）
- **Q6 "她提升的"事实要不要在页面上默认排在前面**：推荐按写入时间，不特殊排；"最近变动"里能看到她最近提升的（我的取舍：页面是审计用的，不是待办列表）。（另一种：把"待确认"置顶当成待办。会把页面变成一个必须清空的队列，不是本意。）
- **Q7 改字、改范围什么时候做**：推荐第二步稳了以后再说。改字走"新建 + 取代旧的"（`remember` 的 `replaces` 已有），改范围是"谁能看什么"的默认值变化，要先有具体例子再问你。
