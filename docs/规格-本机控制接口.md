## 一、要什么

桌面程序（`sumika.exe`，常驻托盘）开着的时候，主人和 Agent（Claude Code 里的铃音）都能在命令行里对它做托盘能做的事，并拿到结果：

```
sumika-ctl status                 看现在的状态
sumika-ctl receive start|stop     开始 / 停止接收 QQ（等于托盘那两项）
sumika-ctl window show            把主窗口叫出来
sumika-ctl logs [-n 50]           看桌面程序日志的最后几行
sumika-ctl gate list              列出各群的档位（只记录 / 试运行 / 说话）
sumika-ctl gate set <会话或句柄> off|dry 把一个群调成只记录或试运行
sumika-ctl auto-receive on|off    启动后自动接收 QQ（ADR-227 第 3 条，默认关）
sumika-ctl autostart on|off       开机自动启动（等于托盘的勾选项，默认关，ADR-209）
sumika-ctl quit                   退出（等于托盘的"退出 Sumika"）
sumika-ctl backfill status         读取账号对齐 / 媒体分项与最近快照
sumika-ctl backfill gaps [--cursor <游标>] [-n 100] 读取已登记缺口与脱敏句柄
sumika-ctl backfill retry <缺口句柄> 仅补这条原区间，当场返回 accepted / JobID
sumika-ctl backfill run            对已就绪的接收账号排入对齐任务
sumika-ctl checkpoint list <本地会话> 列出本地主窗口私聊 / 所属话题检查点
sumika-ctl checkpoint preview <本地会话> <ID> [step|turn|recovery] 取得变化与版本
sumika-ctl checkpoint restore <本地会话> <ID> <version> [模式] 等主窗口同会话单次批准后恢复
sumika-ctl chat [--character <id>] [--new] [--timeout 120s] "<文字>" 自检对话：以主人身份往角色的自检话题发一句话，等这一轮结束（第八节）
sumika-ctl whisper create --selftest --character <id[,id]> --source-text <文字> [--quote-name 名字] --say <文字> [--timeout 120s] | whisper status <批号> | whisper cancel <批号> 自检悄悄话（[规格-群聊引用和路由](规格-群聊引用和路由.md) 第十一节）：来源是命令行给的文字、挂在第一个角色的自检话题上，请求里没有任何会话 id 字段，没有 `--selftest` 一律 `invalid`；`whisper log --conversation <自检会话> [--batch <批号>] [--limit N] [--cursor <游标>] [--with-thinking]`、`whisper log --conversation <自检会话> --entry <条目id>` 读右侧栏“对话日志”的同一份投影（只认自检会话，真实会话读不到，思考原文默认不输出），`whisper list [--selftest]` 列批号、角色、状态（不带正文）；`group`、`whisper send` 还没做
sumika-ctl goal [show|set <目标>|edit <目标>|pause|resume|clear] [--character <id>] 目标模式，和输入框里的 /goal 同一套逻辑（第十节）
sumika-ctl loop [list|add [间隔] <任务>|edit <编号> [间隔] [新任务文字]|pause <编号>|resume <编号>|remove <编号>] [--character <id>] 定期任务，和输入框里的 /loop 同一套逻辑；add、edit 还认 `--every|--daily|--weekly --at|--self`、`--new-chat|--same-chat`、`--notify`（第十节）
sumika-ctl trust [--character <id>] 项目说明（AGENTS.md 等）拒绝过的，想改主意：清掉“这次运行里不再问”，下一次发消息重新弹卡；不会当场替主人信任，和输入框里的 /trust 同一套逻辑（规格-审批分级 8.6）
sumika-ctl stats usage [--days N | --year Y | --all] [--by task|model|day|week] [--full] 运行页的用量统计，只读（第九节）
sumika-ctl stats resources 运行页的资源：进程表（CPU、内存、显存）、主程序内部、后台队列，现在这一刻的，只读（第九节）
sumika-ctl stats quality [--days N | --all] [--task <类别>] [--failures N] 运行页的质量：成败、失败原因类别、耗时分位、最近的失败，只读（第九节）
```

每个命令都能加 `--json`，输出一个 JSON 对象给 Agent 读；不加就是给人看的中文。

检查点扩展在 `feat/checkpoint-lsp`：协议仍为 v1，可选 `CheckpointBackend` 不可用时报 readonly。服务端只接完整本地 console 私聊键、32 位 ID、64 位 version 和固定 mode；不收任意路径、force 或审批模式。命名管道认证不能代替恢复批准，走同一桌面动作、单次审批、Hub 屏障和 CAS；不在宿主 op 锁里等待主人答卡。结果及边界以[检查点规格](规格-检查点与回退.md)为准。


## 二、技术路线

1. **传输**：Windows 命名管道 `\\.\pipe\sumika-ctl-<当前用户 SID>`，演示模式另起 `…-demo`（和单实例一样，正式和演示分开）。用 `github.com/Microsoft/go-winio` 的 `ListenPipe`，`SecurityDescriptor` 只给当前用户（`D:P(A;;GA;;;<SID>)`），拒绝远程客户端。**不开任何网络端口**。非 Windows 先不做（返回"不支持"）。
2. **协议**：一次连接一个请求、一个回复，各是一行 JSON。请求 `{"v":1,"cmd":"receive","args":["start"]}`；回复 `{"ok":true,"data":{…}}` 或 `{"ok":false,"error":"…","code":"…"}`。`v` 不认识就回 `code:"version"`。单个请求最多 64 KB，读写各 5 秒超时（`receive start --wait` 例外，见下）。
3. **服务端**：在桌面程序里，`shell.ready()` 之后起、唯一退出流程（`beforeQuit`）第一步就关。每个命令调的都是托盘用的同一个函数（`host.startReceive`、`host.stopReceive`、`shell.showMain`、`mygo.App.Quit` 等），不另写一套；碰窗口的操作照 mygo 的规矩回到界面线程做。服务端不缓存状态，每次现查宿主。
4. **客户端**：新命令 `native/cmd/sumika-ctl`（Windows 的命令行程序，不加 `-H windowsgui`，输出能直接打在终端里）。连不上管道就退出码 2，说"Sumika 没在运行"。退出码：0 成功；1 命令执行失败（`error` 里写原因）；2 没在运行或连不上；3 被拒（权限、参数不允许）；4 协议版本不对。
5. **`receive start` 的 `--wait`**：默认立即回"已开始"和当时的阶段（已被第六节改为：不带 `--wait` 最多等 0.2 秒，很快做完的当场回结果）；加 `--wait[=60s]` 时等阶段落定（接收中 / 受阻 / 回到只看历史），回最终阶段和原因；超时退出码 1。
6. **`gate set`**：只许 `off`、`dry`，也就是只许往"不开口"的方向调。**`speak`（让一个群真开口）不进这个接口**：AGENTS 写着"在真实群里开口先问主人"，命令行是 Agent 也能直接调的，放宽类的操作留给界面上主人亲手点。会话写完整的会话身份（`qq:group:<群号>`），或者 `gate list` 给的句柄（第六节）；不认识的会话、本地会话、私聊一律拒绝（code `invalid`）。档位改动照现有的 `SetGateMode`，写进运行记录库，同时写一行日志（谁改的：`ctl`）。只看历史（archive）模式下库是只读的，`gate set` 回 code `readonly`，提示先开始接收。
7. **`logs`**：读桌面程序自己的日志文件（接管前小补丁加的 `desk-*.log`）的最后 N 行（最多 500），原样返回；日志在写入时已经打码，这里不再加工，也不读别的文件。
8. **`status --json` 的字段**：`mode`（archive/receive）、`phase`、`reason`、`account`（打码后的小号）、`noRecv`、`connection`、`alerts`（没恢复的提醒，标题和时间；已被第六节改为：只有标题和正文，没有时间）、`autoReceive`、`autostart`、`dataDir`、`version`、`pid`、`watchdog`（守护进程那一栏：`running`、`supervised`、`pid`、`state`、`restarts`、`lastIncidentAt`、`lastReason`、`lastFile`，见[规格-看门狗](规格-看门狗.md)第六节；演示模式没有；文字输出多“守护进程：…”和“最近一次异常退出：…”两行）、`runningTurns`（正在跑的回合数，只数还在跑的、每个会话最多一个；换 exe 之前先看它，不为零时退出会切断回合；只看历史、后台没开好、演示模式是 0；`status` 的文字输出多一行“正在跑的回合：N”）。号码一律照界面上的打码规则。

## 三、禁止的偷懒写法

- 不许开 TCP / HTTP 端口，哪怕只听 127.0.0.1（别的程序、浏览器页面都连得上）。
- 不许另写一套"开始接收""退出"的逻辑：必须调托盘用的同一个函数，退出必须走唯一退出流程。
- 不许把 `speak` 藏在别的参数里放进来；不许接受任意 SQL、任意文件路径、任意配置键。
- 不许把密钥、令牌、完整号码写进回复或日志。
- 宿主在发布 `Reason` / `NoRecv` 前与日志共用 `app.RedactLog`；`status`、`receive start` / `stop`、失败回复的 `error` / `data.reason` 和界面只读脱敏快照。已知令牌取配置原文、环境变量展开值及密钥文件；读取失败时隐藏自由文本详情，不退回原始错误；`filelog` 不读配置或密钥。
- 测试不许连真实的管道名（用带测试名的管道名），不许读写真实 `data/`。

## 四、已知的坑

- 管道服务端在退出流程里要先关，再等后台收尾；不然 `quit` 的回复发不出去、客户端卡 5 秒。`quit` 的做法：先回"正在退出"，再触发退出。
- 两个请求同时来（比如 `receive start` 和 `quit`）：宿主的 `op` 锁会串行化，第二个等到第一个做完；客户端 5 秒超时只管读写，不管宿主执行多久，执行久的照实回。
- 第二次启动 `sumika.exe` 只唤醒（单实例），不受这个接口影响；`sumika-ctl` 不会把程序拉起来，没开着就报"没在运行"。
- 演示模式也开管道（名字带 `-demo`），但 `receive`、`gate`（`list` 和 `set`）、`auto-receive` 回 code `demo`（已被第六节改为这几条；`status`、`logs`、`window`、`autostart`、`quit` 照常）。
- Windows 上管道名区分大小写不敏感，SID 字符串照原样拼，不转小写。

## 五、验收

1. 每个命令一个测试：起一个带测试名的管道服务端，后面接假的宿主，客户端发请求，断言调到了托盘用的同一个函数、回复字段和退出码对。
2. 权限：服务端的安全描述只有当前用户 SID（断言 SDDL 字符串）；远程客户端被拒（断言打开管道时带了拒绝远程的标志）。
3. `gate set` 的形状表（句柄和打码另有一张表，见 `internal/ctlserver/gate_handle_test.go` 开头）：`off`、`dry` 过；`speak`、空、大小写变体（`SPEAK`、` speak`）、不认识的值、私聊会话、本地会话、不存在的群、只看历史模式，各一格，全部拒绝且库没变。
4. `quit` 走唯一退出流程：断言 `beforeQuit` 被调用、后台按顺序收尾、客户端拿到"正在退出"的回复。
5. 程序没开着时，客户端 2 秒内退出码 2。
6. 架构测试（`internal/archcheck`）：`cmd/sumika-ctl` 只依赖协议包，不链接后台（客户端要小、要快）。
7. 真机：主人开着桌面程序时，`sumika-ctl status --json` 能读到和"后台状态"页一致的阶段；`receive start --wait` 和托盘点一样的结果。这一条要主人在场，结果写进提交说明或待办。

## 六、实现时定下的细节（2026-11-01，规格里没写到、或做的时候选了一种的）

- **包的切法**：协议和客户端共用 `internal/ctlproto`（请求 / 回复 / 错误码 / 退出码 / 管道名，客户端只许依赖它）；服务端 `internal/ctlserver`（参数校验、命令表，后端是一个接口）；桌面程序的接线在 `native/ctl.go`、`native/hostgate.go`；群档位的窄接口在 `internal/app/gatectl.go`（后台不交出 `store.Set`）。
- **请求可选字段**：`wait` 只用于 receive start；`n` 用于 logs 与 backfill gaps，gaps 默认 100、上限 200；新增 `cursor` 只用于 backfill gaps。保留 v1，其他命令夹带无关参数服务端回 invalid。
- **错误码**：`version`、`invalid`、`denied`、`readonly`、`demo`、`failed`、`timeout`；`not-running` 只有客户端自己会生成。退出码：`readonly`、`timeout`、`failed` 是 1；`invalid`、`denied`、`demo` 是 3（`demo` 在这个模式里永远做不了，`readonly` 先开始接收就能成，所以不同）；`version` 是 4；`not-running` 是 2。
- **`receive start` 的两种回法**：不带 `--wait` 最多等 0.2 秒，很快做完的当场回，慢的回"已开始"和当时的阶段（`settled: false`）；带 `--wait` 等宿主的 `startReceive` 返回，默认 60 秒、上限 5 分钟，超时回 `timeout` 并带当时的阶段。做完却没在接收（回退到只看历史、没有小号、受阻）都是 `failed`，`error` 就是宿主状态区那句原因，`data` 带阶段。客户端等回复最久 90 秒，`--wait` 时是 wait 加 20 秒。
- **`status` 的 `alerts` 只有标题和正文，没有时间**：界面读到的 `RuntimeAlert` 本来就没有时间字段，要时间得先给提醒登记处和读取接口加（没做）。小号、提醒文字里的长数字打码。`connection` 是界面读到的同一份快照里的连接文字，取不到是空。
- **`gate list` 的群号打码，群用"句柄"指**（按复核后的安排改的：第一版写的是群号不打码，要改成打码得另给一个指群的办法，就是句柄）：每行的 `conversation` 是打码的会话（`qq:group:***01`，和日志同一个 `config.MaskID`），另有 `handle` 和 `handleClash`，其余照旧（群名、`mode`、`source`、接收中才有的 `actual`）。句柄 = `HMAC-SHA256(本机密钥, 完整会话号)` 的前 8 个小写十六进制字符；密钥是 32 字节随机数，第一次要用时生成，存在 `<数据目录>/go/desktop-settings.json` 的 `handleKey` 里（不进任何回复和日志），所以同一台机器上稳定、换数据目录会变，拿到句柄反推不出群号。`gate set` 的会话参数认两种写法：完整的 `qq:group:<群号>`（用户自己知道号），或恰好 8 个小写十六进制字符的句柄；完整写法必须带 `qq:group:` 前缀，所以裸的 8 位数字只会当句柄。句柄由服务端在现在认识的群里解析成完整会话，解析出来以后照旧走全部校验（档位只许 `off`、`dry`，`speak` 配句柄也在档位这一道就被拒，连 `GateList` 都不调），没有群对得上回 `invalid`。两个群的句柄撞了：`gate list` 里两行都标 `handleClash`，`gate set` 用这个句柄回 `invalid` 并要求写完整群号，不猜。`gate set` 的回复里会话也是打码的并带 `handle`。后端交上来的非群会话的行在服务端丢掉。
- **"认识的群"**：QQ 库里有这个群的消息，或群名表（`qq_groups`）有它，或档位表里已有它自己的一行（Bun 导入来的、还没消息的群）；写法对但哪里都没有的回 `invalid`（"没有这个群"）。
- **自动接收存哪里**：`<数据目录>/go/desktop-settings.json`（`{"autoReceive": true}`），先写临时文件再改名，没认识的键原样留着；文件读坏了按"关"并写日志，用户点开关时直接换成新的；数据目录还没初始化（没有 `sumika-data.json`）不写、也不建 `go/`。托盘菜单读缓存，读写文件都在后台线程。不动 `sumika.yml`。
- **起和关的先后**：`ready()` 的后台线程里：开日志 → 定数据目录、读开关 → 起管道 → 起宿主 → 开着自动接收就走 `host.startReceive`。`beforeQuit` 第一步 `closeCtl`（关监听、取消在途，不等）；`quit` 命令先回"正在退出"、关连接，再调 `mygo.App.Quit`（它回界面线程触发 `beforeQuit`）。服务端不读写界面线程的字段：`status` 读 `host.current()`（有自己的小锁，宿主正在打开后台时也当场回），窗口操作走 `a.post`。
- **拒绝远程客户端的标志是 go-winio 固定带的**（`makeServerPipeHandle` 里 `FILE_PIPE_REJECT_REMOTE_CLIENTS`），我们的代码没有地方能设，`internal/ctlserver` 的测试钉住 go-winio 的版本和那一行源码，升级库时它会红、提醒回头确认。管道已被别的进程占着（抢名字）时 go-winio 建第一个实例用 `FILE_CREATE`，开不出来只记日志，不接手。
- **日志**：只记会改状态的请求，办完以后一行，只有命令名、子命令和结果（`控制接口：receive start → 成功`；被拒是 `gate set → 被拒（invalid）`，没做成是 `→ 没做成（readonly）`，读不懂的请求记 `收到读不懂的请求 → 被拒（invalid）`；结果只用固定的词和错误码）；调用方是哪个进程没有记（go-winio 的连接不直接给，要自己调 Win32，没做）；`status`、`logs`、`gate list` 是只读的，Agent 会反复轮询，不记；请求里别人给的文字（命令名、参数）不原样进日志，不认识的命令只记一句固定的话。群档位的细节由后台自己写，群号经现有出口打码。
- **复核（2026-11-01）后又改的几处**：
  - 外来文字（群名、提醒、连接状态、日志行、错误原因）里的终端控制字符：服务端出去前清一遍（`ctlproto.Clean`），客户端给人看的输出再过一道（`cleanWriter`），`--json` 再转义 `encoding/json` 放过的 DEL 和 C1；群名最多 20 个字，文本输出里括在引号里，帮助里说明这是原文、只当数据看。日志一次 `Printf` 只写一行（换行换成两个字符 `\n`）。
  - 客户端连上管道以后核对另一头：`GetNamedPipeServerProcessId` 取进程、查它的用户 SID 和自己比，对不上或查不到都回 `denied`（退出码 3）；打开管道被拒（权限）也是 `denied`。"没在运行"的提示不再带管道名（里面有用户 SID）。管道名被占开不成时，桌面程序在状态区写一句。
  - `receive stop` 在后台本来就没起来（受阻）时算成功，阶段和原因照实给；`autostart` 等界面线程超时说"是否生效还不确定"；退出开始后在途命令失败统一回"正在退出"。
  - 收连接偶发出错时退避重试（8 次为限），不再从此没人接。
  - `gate list` 列有消息的群改成在索引上按会话号跳着找（150 万条消息 0.5 毫秒，原来 402 毫秒），因为它在宿主的 `op` 锁里跑。
- **`--demo`**：客户端的全局选项，连演示实例的管道（名字多一个 `-demo`）。

## 七、补录扩展（2026-11-04，feat/gap-backend）

范围及逐条验收见[补录缺口规格](规格-补录缺口界面与自动对齐.md)第五、九节。服务端经可选 BackfillBackend 调宿主 `native/ctl_backfill.go`，宿主调用同一后台的 api.GapReader / BackfillActions；客户端仍只依赖 ctlproto。status / gaps 在 archive 可读，retry / run 回 readonly；demo 只读演示快照，不补录。两条写命令仅排入已连接协调器，不启动接收、不放宽群档位。

缺口句柄为 HMAC-SHA256(本机现有 handleKey, 平台 / 账号 / 会话 / 缺口 ID / 原始闭区间) 的前八位小写十六进制。跨页冲突与当前行失配拒绝，不能以裸 ID 或完整会话回退。gaps 游标绑定账号摘要和页位置，不带原始会话号。沿用 invalid / readonly / demo / failed 和原退出码，固定 data.reasonCode 区分 stale-gap / cooldown / busy / unavailable。accepted 只表示接收，completed 仍须看 completeCoverage 和剩余缺口。

密钥读取失败回 failed / io 和固定短原因，不把设置路径、URL 或原始 I/O 错误带入回复。写动作成功日志仅记固定子命令及后台生成的任务 ID；status / gaps 轮询不记日志。

## 八、自检对话 chat（2026-11-08，feat/ctl-chat）

**要什么**：开发助手（本机 Claude Code）像用户一样，在正在运行的 `sumika.exe` 里和角色对话，用来测真实程序；不污染用户的聊天记录和角色记忆。

**命令**：`sumika-ctl chat [--character <id>] [--new] [--timeout 120s] "<文字>"`，加 `--json` 输出结构化结果。请求多三个可选字段 `text`、`character`、`new`，时限放在 `wait`（协议仍是 v1）；**请求里没有会话 id**，服务端按角色自己拼会话，所以这个命令碰不到 QQ、群聊或别的会话。

**会话怎么定**：自检话题是本地库 `local_topics` 里的一行，话题 id 固定、可辨认：
- 默认话题 `selftest-<角色>`，会话串 `console:<角色>:topic:selftest-<角色>`，标题"自检"；不带 `--new` 就接着该角色**最新的**自检话题继续聊（上下文保留）。
- `--new` 开一个没用过的话题 `selftest-<角色>-<时间>`，标题"自检 月-日 时:分:秒"，上下文清空；之后不带 `--new` 的接着它。
- 认串的唯一函数是 `audience.IsSelftest`（只认这两种形状，角色段、话题段不许空和带空白）。

**角色缺省**：用桌面后台现在接收的那个角色（`App.character`），不在角色目录里就取目录里第一个。指定的角色不存在回 `invalid`。主窗口界面上"选中"的角色在界面线程里，控制线程不跨线程取。

**怎么发**：走和界面发消息同一条路（`DesktopReader.sendLocal`：准入、角色和话题所有权、同会话同时只跑一轮、审批、停止），没有另开的后门；只看历史（archive）模式先回 `readonly`，不碰库。这一轮的寿命不跟管道连接走（停在审批上时命令先回，回合要留着等用户点），只有到时限才取消。

**结果**：`data` 里有 `status`（done / waiting_approval / timeout / stopped / error / busy）、`reply`（她这一轮最后说的话）、`draft`（超时或等审批时已说出的半截）、`tools`（这一轮真的调用过的工具：名字、参数摘要、结果摘要、状态、是否出错，取自运行记录 `steps` 表，不是从她的话里凑的）、`model`、`route`、`elapsedMs`、`approval`（停在审批上时的卡片：id、工具、对象、原因、预览）、`error`、`turnId`、`topic`、`conversation`。只有 done 回 ok 和退出码 0；其余回 ok 为假、退出码 1（timeout 的 code 是 `timeout`，别的是 `failed`），`data` 照样带完整结果。字数：一句话最多 4000 字；回复最多回 32000 字；工具参数摘要 200 字、结果摘要和审批预览 300 字；时限默认 120 秒、上限 5 分钟。

**自检会话里不污染什么**：
- 内核在自检会话里存的每一条事件（用户方的话、插话、她的回复）都带 `selftest` 标记（`segments.tags`，和渠道自检同一个标记；`AppendInputEvent` 的摘要里也带，幂等比较两边一致），"她看到了新事件"的通知也带 `Selftest`（在通知的唯一出口补，不靠各调用点记得填）。在界面里手打进自检话题的话同样被标。
- 记忆整理丢掉带它的行（`memory.dropReason`）；记忆插件收到自检的通知不排整理。
- `remember` 在自检会话里不进工具声明表（`For` 里按会话串认），万一被调到执行也直接拒，所以自检里说"记住……"不会写进长期记忆。`memory_search`、`recall_raw` 照常（后者只在本会话里找）。
- 链接插件不取自检会话里的链接；`segments.tags` 带 selftest 的行链接插件本来也跳过。
- 本地私聊没有往 QQ 或别处发消息的出口，QQ 库不会多一行；执行类工具照常走审批，审批模式由用户的配置决定，这条命令没有任何绕过审批的路径，也**不替用户批**：停在审批上就返回 `waiting_approval` 和卡片，回合留着，用户在界面上批或拒；这时再发一句回 `busy`（带着这张卡），不发。
- 界面：自检话题就是一个普通话题，标题以"自检"开头，会话列表里能看到；列表按最近活动排序，所以自检过之后它会在前面。想隐藏要等界面做话题归档。

**到时限**：取消这一轮、等它收尾（最多 10 秒）、回 `timeout` 带已说出的半截；话题随后空出来可再发。**正在跑时再发**：回 `busy`，不发、不取消在跑的那一轮。**模型报错**：回 `error` 带（打码后的）原因，不当成功。**管道连不上**：退出码 2。客户端等回复最久 `timeout` 加 20 秒。

**日志**：只记 `控制接口：chat → 成功/没做成（…）`，不记用户说的话和她的回复。

**验收对应的测试**：`internal/ctlserver/chat_test.go`（形状表）、`internal/app/desktop_selftest_test.go`（真装配里的存储标记、QQ 外发、列表、`--new`、busy、超时、审批、模型报错、archive）、`internal/turn/selftest_test.go`（每条事件和通知的标记）、`internal/memplugin/memory_tools_test.go`（remember 不在、事件视图读出自检）、`cmd/sumika-ctl/chat_test.go`（参数、输出、退出码）。

## 九、运行页统计 stats（2026-11-08，feat/runstats-usage，第 1 步只有 usage）

范围、做法和逐条验收见[运行页规格](规格-运行页.md)第三、六、十二节。这里只记协议上的事：

- 命令 `stats`，子命令放在 `args[0]`，现在认 `usage`、`storage`、`quality`、`spans`、`resources`；不带子命令回 `invalid`，不给假数据。请求多一个可选字段 `stats`（`days`、`year`、`all`、`by`、`full`），协议仍是 v1；别的命令带 `stats` 回 `invalid`，`stats` 里夹带不认识的字段整个请求被拒。
- 校验只在服务端：`days`、`year`、`all` 至多写一个，`days` 在 1 到 3660，`year` 在 2000 到 2200，`by` 只认 `task`、`model`、`day`、`week`；一个范围都不写是最近 7 天（含今天），按本地时区的零点算。命令行把 `--days 0`、`--year -1` 这类写法变成 -1 交给服务端回 `invalid`，不悄悄当成"没写"。
- 服务端先查全量（分组行数很少），出去前按 `by`、`full` 裁：`task`（默认）给类别，加 `--full` 才在类别下列模型；`model` 给模型；`day`、`week` 给按天、按周。`totals` 总是在。
- 只读命令：`readOnly()` 里有它，不写"改状态"的日志；演示模式回 `demo`；宿主没接统计回 `failed`；后端的带码错误（超时是 `timeout`，退出码 1）原样传回。
- 数据：类别用 ASCII 键（`foreground`、`memory`、`guard`、`vision`、`compact`、`child`、`advisor`、`goal`、`loop`、`unknown`），`wired` 为假的类别没有记录时调用方写"未接入"，不写 0；认不出的 purpose/stage 单列成 `unknown` 行并带 `raw` 原文（截短、清过控制字符）。输入是总输入（未缓存 + 缓存读 + 缓存写），输出已含思考，没拿到用量的次数单独给。`source` 是 `rollup`（读 `usage_rollup` 汇总表）或 `raw`（直接查 `model_runs`），两者结果一致。
- 桌面程序接线在 `native/ctl_stats.go`：每次请求只读打开 `go/trace.db`，用完关；不接受路径、SQL。测试：`internal/ctlserver/stats_test.go`（形状表、裁剪、模式）、`cmd/sumika-ctl/stats_e2e_windows_test.go`（真管道加真统计服务的端到端）。
- **`stats resources`（第 5 步，feat/run-resources）**：`args[0]` 是 `resources`，不带位置参数，也不接受 `stats` 字段里的任何选项（资源是现在这一刻的，没有范围）。回复是 `ResourcesReport`（`internal/ctlproto/resources.go`）：进程表（exe 名、类别、登记的标签、父子关系，CPU、内存、提交、GPU、显存；没读到的数是 null，不是 0）、主程序内部（来自 `runtime/metrics`）、固定七行的后台队列（没注册的 `wired` 为假，写"未接入"）。命令行没有前一次采样，后端自己隔 250 毫秒采两次，所以 CPU 不是空的；报告里不放命令行和路径，MCP 服务只写配置里的服务 id。后端是 `ctlserver.ResourcesBackend`，桌面程序里在 `native/ctl_stats.go`，采样器不开 trace.db。测试：`internal/ctlserver/stats_test.go`、`cmd/sumika-ctl/stats_e2e_windows_test.go`。
- **`stats quality`（第 4 步，feat/runstats-quality）**：同一个 `stats` 命令，`args[0]` 是 `quality`。请求的 `stats` 字段多两个：`task`（只看某个任务类别或模块，认 `foreground`、`memory`、`guard`、`vision`、`compact`、`child`、`advisor`、`goal`、`loop`、`unknown` 和 `send`、`link`、`media`、`backfill`、`memory_pass`、`storage_clean`）、`failures`（"最近的失败"列几条，1 到 500，不写是 50）。服务端把关：质量不收 `year`、`by`、`full`；usage、storage 带 `task`、`failures` 回 `invalid`；`--days`、`--all` 互斥照旧。回复是 `QualityReport`（`internal/ctlproto/quality.go`）：每类任务和模块的成功、失败、超时、取消、退化、没做、重试、失败率、p50、p95，原因分布，最慢的环节，`unknown` 占比和是否标红，最近的失败，回合层和工具表。报告里不放会话名、号码、URL、令牌、模型回复原文，场合只写"本地私聊 / 本地群聊 / QQ 私聊 / QQ 群"。测试：`internal/ctlserver/quality_test.go`、`cmd/sumika-ctl/quality_e2e_windows_test.go`。

## 十、目标和定期任务 goal、loop（2026-11-08，feat/goal-tails）

**要什么**：[目标和循环规格](规格-目标和循环.md)里的 /goal、/loop 在 GUI 能做的大部分事，命令行也能做，方便测试和 Agent 操作；做完整周期（看、建、改、暂停、继续、结束），不只是建。

**命令**：写在第一节的命令表里。`goal` 不带子命令等于 `show`，`loop` 不带子命令等于 `list`；文字可以不加引号分成几个词，服务端用空格接起来；目标原文以 `-` 开头要先写 `--`。请求仍是 v1：`cmd` 是 `goal` 或 `loop`，`args` 是子命令和文字，角色用已有的 `character` 字段；没有 `wait`、`text`、`new`。

**怎么做**：服务端把子命令拼成和输入框里一样的斜杠命令全文（`goal set X` 拼成 `/goal X`，`loop remove 3` 拼成 `/loop stop 3`），后台用同一张命令表和同一批处理函数执行（`App.callSlash`，输入框也走它），不复制逻辑，所以输入框的行为变了命令行跟着变。

**日程选项（`feat/loop-edit`，2026-11-10）**：`loop add|edit` 多一组选项，请求里放在 `loop` 字段（`every`、`daily`、`weekly`、`at`、`self`、`newChat`、`notify`），和定期任务页的表单是同一批字段（见[目标和循环规格](规格-目标和循环.md)“页面里新建和修改”）。`--every 30m`、`--daily 09:00`、`--weekly 1,3,5 --at 09:00`（周一是 1、周日是 7）、`--self` 四选一；`--new-chat`、`--same-chat` 二选一；`--notify content|errors|none`。写了任何选项，后面的文字原样当任务说明，不再拼斜杠命令，后台走和页面同一个 `AddLoop`、`EditLoop`；`edit` 只改写了的项，不写任何选项又不写新文字回 `invalid`；选项只用于 `loop add|edit`，别处出现回 `invalid`。形状表在 `internal/ctlserver/slash_loop_test.go`。结果的 `loops[]` 多 `kind`（interval、daily、weekly、self）、`at`、`days`（周一是 1、周日是 7）、`notify`、`newChat`。

**会话**：和 chat 一样，请求里没有会话 id，固定是该角色最新的自检话题（没有就建默认的），话题里存的行带 selftest 标记。设目标会把目标原文当主人这一条发给她，她在后台自动续轮，所以绝不会写进真实的主聊天。要换干净的话题，先 `chat --new` 开一个。

**校验**（服务端是关口，形状表在 `internal/ctlserver/slash_test.go`）：
- 子命令必须在表里，大小写变体不收；`show`、`pause`、`resume`、`clear`、`list` 不带参数。
- 文字最多 4000 字、不带控制字符；目标不能以 `/` 开头，免得借目标再发别的斜杠命令。
- `loop edit|pause|resume|remove` 必须写编号（`3` 或 `#3`，从 1 开始），不像输入框那样省略编号就是"全部"，免得命令行一句话停掉所有任务。
- 后台再核对一次：拼出来的全文被解析成的子命令必须是命令行要的那个，否则回 `invalid`。例如目标文字恰好是 `pause`、任务文字以 `stop 3` 或 `edit` 开头，输入框里会被当成别的命令，命令行里一律拒绝，不会误暂停。

**结果**：`data` 里有 `character`、`topic`、`conversation`、`reply`（命令的回复，和输入框里发同一条命令得到的系统行同一句话，也存成这个话题里的一条系统行）、`started`（这条命令让她排上了一轮：设目标、继续目标、新建定期任务）、`goal`（这个会话现在的目标，没有是 `null`：文字、状态 active 或 paused、轮数、轮数上限、已用 token、暂停原因、上次判断、状态行）、`loops`（这个会话的定期任务，含已停止的，没有是 `[]`：编号、状态、任务文字、间隔秒数、已跑次数、下次时间、列表行）。一轮在后台跑，命令不等；想看结果用 `goal show`，想看她说了什么看话题。

**错误**：写法不合格、撞了子命令词、间隔写错回 `invalid`（退出码 3）；命令自己的错（没有这个目标、编号不存在、会话正在生成请先停止）回 `failed`（退出码 1），原文给出；只看历史模式回 `readonly`；演示模式回 `demo`。

**日志**：只记 `控制接口：goal set → 成功/没做成（…）` 这样的固定词，不记目标和任务文字；`goal show`、`loop list` 是只读的，不记。

**验收对应的测试**：`internal/ctlserver/slash_test.go`（形状表、拼出的全文、错误码、日志）、`cmd/sumika-ctl/slash_e2e_windows_test.go`（真管道端到端：`--json` 输出、退出码、`--` 之后的原文）、`internal/app/ctl_slash_test.go`（真装配里设目标到达成、自检话题、完整周期、撞词被拒、系统行）。

## 十一、备份 backup（2026-11-14，R-386，feat/daily-backup）

**模型经 shell 工具跑 sumika-ctl（ADR-382，2026-11-15）**：只读子命令（status、logs、gate list、backfill status|gaps、checkpoint list|preview|status、link preview|template、stats …、proactive log、artist list、backup list、whisper status、goal show、loop list、mcp status、kernel faults）照档位走；其余全部、认不出的子命令、没登记的新子命令、光写的 goal 和 loop，任何档位（含 yolo）都要主人点卡，只能批这一次，不产生能被“这个对话”“始终允许”授权的键（`policy/selfctl.go`）。

- **判定**：分析器拆得清的，逐条简单命令各自看被执行的程序——程序是 `sumika-ctl`（裸名、`.exe`、绝对和相对路径、引号、`&` 调用、续行、`;`、`&&`、管道、`$( )`、脚本块里的都算）且子命令不在只读名单；`go run` 一个路径含 `cmd/sumika-ctl` 的包（`-C` 目录含它、或同一条命令里先 `cd` / `Set-Location` / `pushd` 进了它的目录再 `go run .` 也算；包后面的参数交给只读判断，`go run ./cmd/sumika-ctl status` 照原档位）；`schtasks`、`Set-Alias` 这类把命令行当参数去起进程或存别名的命令参数里有它；`env`、`xargs`、`nohup`、`time`、`timeout`、`conhost`、`wt`、`winpty`、`forfiles`（`/c` 后的整条）、`runas`、`command`、`sudo`、`gsudo`、`doas`、`start`、`nice`、`ionice`、`stdbuf`、`watch`、`setsid`、`exec`、`call`、`builtin`、`busybox`、`unbuffer` 这类“把后面的参数当命令去执行”的包装程序，跳过它的选项、`VAR=值`、时长之后第一个词是 sumika-ctl 就按 sumika-ctl 判（名单写在 `policy/selfctl_run.go` 的 `argRunners`，判据在注释里；名单外的程序参数里提到不算，所以 `xargs rg sumika-ctl`、`rg sumika-ctl docs` 不问）。被执行的程序名去掉路径、`.exe .cmd .bat .ps1 .com` 和末尾的点后是 `sumika-ctl` 或以 `sumika-ctl-` 开头（构建后试跑的新版、留着的旧版）都算；文件操作里出现这些名字（`Copy-Item`、`Move-Item`、`Remove-Item`、`go build -o`）不算。只读子命令后面带不认识的选项（不在 `ctlKnownOpts` 里、也不是 `--json`/`--demo`）也按要问；`TestSelfCtlKnownOptionsCoverUsageLines` 读用法文字里每个只读子命令那一行的选项核对这张表（续行说明里的选项不查）。别的程序的参数里只是提到这个词（`rg`、`git commit -m`、`go build|test|vet`、`Set-Content`、`Remove-Item`、`Get-Process`）不算，照原来的规则走。分析器看不清的（`cmd /c`、`bash -c`、`pwsh -c`、`iex`、变量当程序名、语法错、分析失败）退回文字规则：文字里出现 `sumika-ctl` 且后面不是只读子命令就问；续行（反引号加换行、反斜杠加换行）先折成空格再判。
- **防什么、不防什么**：这是一道减速带，不是墙。防的是模型顺手、或被提示注入后照技能页里的命令去跑 `sumika-ctl`。防不了存心绕的：工作区里改名的副本、8.3 短名、通配符、指向不含这个字样的程序的别名、先写脚本再跑——这些在 yolo 下本来就是“能跑工作区里的任意程序”；也管不到 `mcp_call`（它交给判定的是空参数，主人若配了能跑 shell 的 MCP 服务，yolo 下可以经它绕过）。直连控制管道、改数据目录这两条路由别的规则挡着（三档都问）。残留（第三次复核确认，这条规则不再迭代）：看不清的写法里只是提到这个词，仍会被问一次（不能选“这个对话都允许”）；替换或删除控制程序本身（`Move-Item`、`Remove-Item`、`go build -o`）不拦，这条规则防的是“跑它”不是“换它”；拼接出来的程序名（`& ('sumika-' + 'ctl') quit`）靠“看不清就问”的普通规则，是普通的问，可以被“这个对话都允许”覆盖；上一次工具调用里定义的函数和别名带不到下一次（每次调用新起一个进程），所以分两步定义再调用不成立；包装程序名单没列到的、带不常见选项的包装写法（值类选项没登记到 `argRunnerValueOpts`）可能漏。后续由 P4-3 用“管道服务端判断调用方是不是 Sumika 的子孙进程”补上。
- **名单不会悄悄过期**：新加命令或子命令必须登记进 `ctlReadOnlyList` 或 `ctlAskList`。`TestSelfCtlEverySubcommandClassified` 从服务端命令分发表（`route`）、协议里的子命令常量和用法文字（对缩进不敏感）取命令，缺哪个没分类就红；`TestPolicyReadOnlyListMatchesServerReadOnlyTable`（ctlserver）逐键核对策略的只读名单和服务端 `readOnly` 表，策略当只读而服务端当会写要红，策略更严的只能是显式例外（现在是光写的 goal、loop）。
- **名单里有副作用但留着的两条**：`gate list` 首次使用会生成本机句柄密钥并写进设置文件；`link preview` 会联网取链接并写 24 小时缓存。都不碰安全边界。

`sumika-ctl mcp status | mcp release <服务> --reason "原因" --accept-unknown-risk | mcp reconnect <服务>`（P0-3，规格-MCP客户端 2.4）：`status` 只读，列各 MCP 服务的状态和被隔离的旧调用；`release` 是主人接受“旧调用结果未知”的风险后解除隔离，原因必填并必须带 `--accept-unknown-risk`，缺哪样都被拒、不调后端，日志只记“mcp release”不记原因原文；`reconnect` 让自动重连用完次数的本机服务再连一次，不能解除隔离。只看历史模式拒绝，演示数据模式拒绝。

`sumika-ctl backup now [--media none|stickers|all] [--wait[=60s]]` 做一份手动备份（原因记“手动”，不会被自动删），`backup list` 列出备份并给总览（份数、按原因各几份、实际占用、轮换规则和 `backup.alertGB` 提醒线、备份目录和所在盘剩余空间）。`backup now` 默认等 60 秒，到点没做完回“已开始，没做完”（退出码 0），用 `backup list` 看结果；已经有一份在做（每天自动的或别的手动的）就失败。`backup list` 只读。archive 模式也能 `backup now`。`backup restore <备份名> --to <新目录的绝对路径>` 把一份校验通过的备份恢复成一个不存在或为空的新目录并核对、`backup verify [<备份名>]` 抽验一份备份（恢复到临时目录、核对、删掉、记下结果）：都在后台做、默认等 60 秒，不改配置、不切换，都不是只读（任何档位要主人点）；见[规格-数据目录与备份 10.10](规格-数据目录与备份.md)。细节、校验和形状 × 入口表见[规格-数据目录与备份 10.7](规格-数据目录与备份.md)。

## 十二、内核故障 kernel（2026-11-15，质检 X-07、后续路线 P0-4）

`sumika-ctl kernel faults` 列出回合内核现在没解除的故障：整个内核（启动时整库的恢复或清扫没做成，所有会话都停止受理）或某个会话（收尾状态、活动退出、插话重排写不进记录库，只挡这个会话，别的照常），每条带角色、会话、什么时候、日常说法的原因、最近一次的原始错误、已重试几次。只读。

`sumika-ctl kernel retry [<角色> <会话>]` 重试：重写每处没写成的写入并读回确认，全部确认才恢复受理；不写角色和会话 = 全部故障（内核的先）。没恢复就失败（退出码 1），回复里带着还没恢复的那些和新的原因，故障保持，不说成功；这个会话还有一轮在收尾、或这条故障正在重试、或内核故障时还有运行在跑，回“稍后再试”（内核故障重试要求没有任何运行和活动，再做一次整库清扫会把在跑的当成上个进程没收尾的）。

校验：只认 `faults`、`retry`；`retry` 的参数要么都不写，要么角色和会话都写且都不空；别的一律 invalid、不碰后端；演示数据模式一律拒。重试会改库，记控制接口日志（只写“kernel retry”，不带会话号）。**重试是主人和运维的操作，不注册成模型能调的工具**（`TestRetryFaultIsNotInAnyModelToolList` 守着）。实现：`internal/ctlserver/kernel.go`、`internal/app/ctl_kernel.go`、`ctl_kernel.go`（根包）、`cmd/sumika-ctl/kernel.go`。
