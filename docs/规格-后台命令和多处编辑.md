# 规格：后台命令和一次改多处

> 状态：2026-11-08 在 `feat/tools-bg-patch` 实施，已合 main。来源：待办“补齐通用本地工具”的①②（主人 2026-11-08）。参考：Claude Code 的 Bash `run_in_background` + BashOutput + KillShell（后台起、按编号取增量输出、停）；Codex 的 exec 会话（等 N 秒或到结束再返回）；Claude Code 的 MultiEdit、Codex 的 `apply_patch`（一次改多处）。采用：Claude Code 的“起 / 取 / 停”三件；Codex 的“等到结束或超时”。没做：`apply_patch` 跨文件补丁、写 stdin 交互。

## 一、后台命令

### 工具

| 工具 | 参数 | 审批 | 说明 |
|---|---|---|---|
| `powershell` | 原有 `purpose`、`command`、`timeout`，新增 `background`（布尔，默认 false） | 和普通命令一样，起的那一下审一次 | `background:true` 时立刻返回编号 `bg-N` 和 pid，不等命令结束 |
| `process_output` | `id`（必填）、`wait`（秒，选填，最多 300） | 不审批 | 只给上次取过之后新出现的输出，末尾一行状态（运行中 / 已结束、退出码、累计输出）；`wait` 时等到进程结束或满 N 秒再返回 |
| `process_stop` | `id`（必填） | 不审批 | 杀整棵进程树，等它真的退出（最多 5 秒），返回停之前没取过的输出 |

### 为什么是“参数 + 两个新工具”

- 起进程用 `powershell` 的参数，不另开工具：审批卡、危险命令判定（`Classify`、受保护路径、灾难性命令）、“这个对话里都允许”的同类判断、检查点、超时上限都按工具名 `powershell` 走，一个后台工具要把这些各接一遍，漏一处就是审批旁路。审批卡标题改成“在后台运行 PowerShell 命令”，主人知道这条不会回来。
- 取和停是新工具：它们的参数、结果形状和 `powershell` 完全不同，塞进同一个工具要靠 `action` 枚举，模型更容易用错。
- 取输出和停止不审批：只能碰这个对话里自己起的、起的时候已经审过的进程。Spec 登记为 `self` + `owner-console`：场合仍由 owner-console 挡住，QQ 和群聊既看不到也调不动。

### 行为和限制

- 归属：编号归“角色 × 对话”（来自宿主放进 ctx 的身份，不看模型给的参数）。别的对话的编号一律回“没有这个编号”，不透露它在不在。
- 上限：每个对话同时最多 8 个在运行；第 9 个拒绝，报错写上限、原因、现有编号和命令，让她先 `process_stop` 或等结束。已结束的不占名额，记录每个对话最多留 16 条，超出丢最早结束的。
- 生命周期：不跟起它的那次工具调用的 ctx，这一轮停下、回合结束它继续跑。收掉它的只有 `process_stop`、命令自己的 `timeout`（后台没有默认 120 秒，也不封顶 600 秒；写了才到点停）、程序退出（`App.closeProcesses` 调 `tools.StopAllBackground`）。命令自己退出时，它启动的子进程随命令的作业一起结束，和前台命令一样。
- 输出缓冲：每个进程在内存里留最后 1MB，超出丢最旧的（从字的开头切）。取输出时如果有没来得及取就被丢掉的，开头标明“最旧的 N 已经丢掉”。单次取最多显示最后 2000 行或 50KB，更长的标明只显示了最后一段。不写磁盘。
- 结束后：再取如果还有没取过的先给；取完以后再取，回“已结束……没有新内容”（不是错误结果）。已结束的再 `process_stop` 回“不用再停”。
- 不进检查点：后台调用返回即结束，文件变化发生在以后，起的这一下不拍检查点，也不附“已捕获”的提示。
- 防卡死：状态行带已运行秒数，轮询的结果不会连续相同；结束后反复取同一句才会触发“连续重复”提醒，这正是想要的。不为 `process_output` 单开豁免。

### 已知的坑

- 商店版 PowerShell 的子进程会脱离作业（见 `proc_windows.go`）：`process_stop` 用 taskkill /T 兜底，程序被强杀时这些子进程仍可能残留。
- 子代理（`task`）起的后台命令归子代理自己的对话；子代理结束不会自动收，只有 `timeout`、`process_stop`、程序退出会收。
- 编号只在本次程序运行内有效；重启后她再取旧编号会得到“没有这个编号”。

## 二、一次改多处

`edit` 原本就带 `edits` 数组（照 pi 的 edit），这次核对并补测，没有重做：

- 同一个文件的多处修改放进同一次调用的 `edits`，每处都对照原文件匹配、互不重叠、各自唯一；**全部成功才写入一次**，任何一处失败（找不到、出现多次、重叠、空 oldText、改完无变化）整个文件一个字节都不动。
- 报错里写 `edits[N]`（从 0 数起）指出是哪一处，描述里告诉她“改正那一处再整体重发”。
- 审批卡的预览用同一个 `edittext.Apply` 算出合并后的 diff，所以预览和实际写入一致；预览失败时直接显示同样的报错。
- 不做 `apply_patch`：跨文件补丁需要自己的解析、跨文件原子性（任何一个文件失败回滚其他）和新增 / 删除 / 改名的审批卡，工作量和风险都比同文件多处大；等有真实需求再单独开规格。

## 三、验收

- 后台：持续输出的命令分两次取（第二次不带第一次的内容）再停，停后再取报“已结束”；第 9 个拒绝；别的对话取不到、停不了；程序退出清理后进程树真的退了（文件不再增长）；输出超 1MB 丢开头并标明（单元 + 真命令各一）；`wait` 在结束时提前返回；`timeout` 到点停；起它的 ctx 取消不带走它。测试：`native/internal/tools/background_test.go`。
- 场合：`TestPluginToolAudience`（`native/internal/turn/plugin_tools_test.go`）里本地私聊以外的六种听众既看不到 `process_output`、`process_stop`，`policy.Decide` 也回 deny。
- 多处编辑：`TestEditPreviewMatchesExecution`（`native/internal/edittext/edit_preview_test.go`）新增“三处全成功”“三处里第二处失败，原文件不变”，预览与执行逐项比对。
