# 规格：检查统一入口（CI 收口第 1 步）

> 状态：草稿（2026-11-19）。来源：主人 2026-11-19 说“总感觉我们这套流程很……到处都是补丁的样子”，同意按[待办](待办.md)顶部第 6 条的顺序收口（“好，就按这个顺序收口吧”），这是其中第 1 步。参考：[规格-脚本迁Go](规格-脚本迁Go.md)（“落点”一节，第 6～9 步的方向提前）、[规格-提交前检查](规格-提交前检查.md)（钩子现在挑什么）、[规格-每日整套](规格-每日整套.md)（CI 上的整套怎么跑）、[规格-合并走PR](规格-合并走PR.md)。

## 开工卡

- **我理解成**：提交钩子、推送钩子、PR 上的 CI、每日整套，都只调用一个程序 `sumika-dev`，由它决定跑什么、怎么准备环境、怎么汇总结果。`lefthook.yml` 每个钩子只剩一行，CI 的 yml 只剩“装工具链 + 调一行”。
  - 正例：CI 上要把临时目录换成长路径，这件事写在 `sumika-dev ci test` 里；本机手跑同一条命令，走的也是这段代码。
  - 反例：现在这样，同一件事在 `ci.yml`、`nightly.yml` 各写一遍 pwsh；lefthook 里“程序不在就现编”复制了 6 遍，几项并行同时现编，抢输的报“文件正被占用”（2026-11-19 两次）。
- **领域正统做法**：仓库里放一组标准入口，本机和 CI 调同一组，CI 只多一个总入口：GitHub 的 [Scripts to Rule Them All](https://github.com/github/scripts-to-rule-them-all)（`script/test` 由 `script/cibuild` 调用，CI 服务器只认 `script/cibuild`）。Go 项目常见的是 `make ci` / `mage ci`。我们的入口已经有了（`sumika-dev`，规格-脚本迁Go），缺的是把钩子和 CI 都接到它上面。
- **最省事的字面做法够不够**：只在 lefthook 和 yml 里把现有命令包一层 `sumika-dev xxx`、里面再原样去调 bun 脚本，不够。现编撞车还在，环境准备还散在 yml 里，等于换个地方贴补丁。
- **不做什么**：
  - 不改各项检查本身的判断（文档检查、隐私扫描等的规则不动）。
  - 不迁合并队列、`go-verify`、`nightly.ts`。本机每日整套的去留看收口第 3 步。
  - 推送前检查第一批不改档位（见“待主人定”）。
  - 不做缺外部依赖的统一判断，那是收口第 2 步；这里只给它留好汇总的位置。
- **用户能看能试的验收**：
  - 打开 `lefthook.yml`，每个钩子一行。
  - 打开 `ci.yml`、`nightly.yml`，测试部分一行。
  - 新开一个 worktree，第一次提交不再莫名失败。
  - PR 的运行摘要页上列出红的包。

## 设计

### 1. `sumika-dev hook pre-commit`

- lefthook 只留一项：`run: <现编一次> && sumika-dev hook pre-commit`。按暂存区文件挑检查，在一个进程里并行跑，所以程序最多现编一次，撞车也就没有了。
- 已迁进 Go 的检查（隐私、文档、冲突标记、gofmt、ui-skill）直接调包里的函数，不再起子进程。
- 还没迁的照原样起子进程：
  - `bun run typecheck`（`scripts/`、`test/` 有改动时）；
  - `bun test ./scripts/friction-report.test.ts`（改了它时）；
  - `bun scripts/gen-rpc.ts --check`（协议有改动时）。
  - 每一项写明“迁完删”，规格-脚本迁Go 那一步删到哪项，这里同提交删哪项。
- `precommit-fast.ts go-vet`（vet 暂存的 `.go` 所在的包；改了 `go.mod`、`go.sum` 时 vet 整个模块）迁进来做成一项，删掉旧脚本里对应的分支。
- 摘掉 `Server类型检查`、`Server测试` 两项：冻结代码不验收（ADR-378），`precommit-fast.ts server-tests` 一并删。在规格-提交前检查里登记摘除。
- 挑选规则（哪些文件触发哪项）照搬现在 lefthook 里的 glob，写成一张表。测试逐项覆盖“改了 X → 跑 Y、不跑 Z”。
- 输出：每项一段，先写项名，结尾一行汇总“几项过、几项红、几项没挑上”。任何一项红，退出码就是 1。

### 2. `sumika-dev hook commit-msg <文件>`

就是现在的 `check commit-msg`，只是挂到 `hook` 名下，让 lefthook 三个钩子的写法一样。

### 3. `sumika-dev ci test [--full]`

- CI 只调这一条（PR 和推 main 的 `ci.yml` 不加参数，`nightly.yml` 加 `--full`）。本机也能手跑同一条命令：经 `slot.ts` 取名额，等名额迁 Go（脚本迁 Go 第 6 步）以后由它自己取。
- 按顺序做下面几件，谁红都不挡别的，最后汇总退出码：
  1. 准备环境，只改给子进程的环境变量，不动本机系统设置：
     - Windows 上 `TEMP`、`TMP` 是 8.3 短名时，换成长路径的专用目录（现在 `ci.yml` 里“临时目录用长路径”那段搬进来，原因照抄）；
     - 去掉 git 插到 `PATH` 最前面的 libexec 段（推送检查现在就是这么做的）。
  2. `go vet ./...`；带 `--full` 时再跑 `go tool mygo vet .`。
  3. `go test -count=1 -timeout 20m ./...`，不带 `--full` 时加 `-short`：
     - 在 Windows 上用新进程组起子进程（`CREATE_NEW_PROCESS_GROUP`），测试往所在进程组发 Ctrl 信号也波及不到调用方；
     - 输出边跑边写到 `--out` 目录（默认 `ci-out/`），同时转到标准输出。
  4. 检查脚本的 bun 测试，名单仍取自 `scripts/server-verify.ts` 的 `SCRIPT_TESTS`，等这些脚本迁完再删。
  5. 只在 Linux 上跑文档检查，带 `TZ=Asia/Shanghai`（原因同 `ci.yml` 现在的注释）。
- 汇总：
  - 写一份 `ci-out/summary.md`：各步过没过、红的包和用例名（从 `go test` 输出里挑）、用时；再留一节“跳过原因”给收口第 2 步填。
  - 在 GitHub 上运行时（有 `GITHUB_STEP_SUMMARY`），把这份汇总追加进去。
  - yml 用 `actions/upload-artifact` 把 `ci-out/` 整个传上去。
- 两个 yml 只剩下：checkout、setup-go、setup-bun、`bun install --frozen-lockfile`、Linux 装系统包（rg、fd、字体，这是 runner 的事，留在 yml 里）、编好 `sumika-dev`、`sumika-dev ci test`、上传 `ci-out/`。

### 4. 程序怎么编出来

- lefthook 三个钩子各一行“程序不在就现编”。现在每个钩子里只剩一个进程会去编，钩子之间又是一个跑完才轮到下一个，所以不会再撞。保留兜底：`mv` 失败但正式文件已经在了，就删掉自己的临时文件，用现成的。
- 兜底现编要带上和自我重编一样的摘要 `-ldflags`，否则编出来的程序摘要是空的，第一次运行又会重编一遍（通知钩子复核时发现的同一个问题）。
- CI 里用 `go build -o` 先编到 `bin/`，再执行。

## 禁止的偷懒写法

- 子命令里只是原样转调 bun 脚本、lefthook 换个名字。已迁的检查要直接调函数。
- 在 yml 里另加环境处理或平台特判。要加就加进 `ci test`，并写明原因和日期。
- 为了让 CI 变绿，在 `ci test` 里跳过某个包或某条测试。偶发红按收口第 5 步的隔离名单处理，那一步要先写 ADR。
- 并行项共用同一个输出文件或临时目录。

## 已知的坑（2026-11-19 试跑踩过）

- pwsh 会把 `-test.v` 这类以 `-` 开头、中间带点的参数在点那里拆开；命令行要用 Go 的 `exec` 传，不经 pwsh 转。
- 测试程序要在包目录里起，因为 `testdata` 按相对路径读；`go test` 自己会这样做，不要绕过它直接起测试程序。
- Git Bash 底下跑 `go test`，四条“拒绝读取 / 独占打开”的权限用例会红；直接由 Go 起子进程，不经 bash。
- 在 pwsh 里直接跑整套时 runner 失联过一次，原因没查清，所以用新进程组隔开。
- `GITHUB_STEP_SUMMARY` 按 UTF-8 追加，不要覆盖。
- lefthook 传进来的路径相对仓库根，用正斜杠。

## 验收

1. `lefthook.yml` 的 pre-commit、commit-msg 各只剩一项；`ci.yml`、`nightly.yml` 跑测试的部分只剩一步 `sumika-dev ci test`。
2. 新 worktree 第一次提交：并行改动 5 种文件，连续 10 次都不出现“文件正被占用”。改坏检查：把 pre-commit 换回 lefthook 并行各自现编，要能复现撞车（留一次输出作对照）。
3. 挑选表逐项测试：改了 X 跑 Y、不跑 Z；冻结的 `server/` 改动什么都不挑。
4. 同一个提交，改前改后各跑一次 CI：两格过了的包数相同，红的包相同；每日整套 `--full` 一次，179 个包全过（2026-11-19 第三次试跑的基线）。
5. `ci test` 单元测试：短名临时目录会被换成长路径；某一步红了其余照跑、最终退出码是 1；汇总里列出红的包。
6. “触发路径 × 运行环境”表（AGENTS 第 7 条，这是钩子和检查本身）。
   - 行：主仓库、worktree、程序不在、源码改了、编不过、CRLF 工作区。
   - 列：pre-commit、commit-msg、手跑 `ci test`、GitHub 上的 `ci test`。
   - 每格写“变 / 不变 / 不适用 / 没验证”。
7. 独立子代理复核过了才合。

## 顺序（每步单独 PR，能单独撤回）

1. `hook pre-commit`、`hook commit-msg`，改 `lefthook.yml`，摘掉冻结的两项。
2. `ci test`，改 `ci.yml`、`nightly.yml`。
3. 推送前检查：等主人定（见下）。

## 待主人定

- **推送前检查要不要统一成只扫隐私。** 现在推往 main 的会跑整套隐私、Bun、Go 检查，其余只扫隐私（ADR-398 时定的）。2026-11-19 起 main 有分支保护，改动都经 PR 合，每次合之前 CI 已经跑过完整检查。直接推 main 只剩管理员绕过这一种情况，而绕过本来就是检查自己坏了的时候。我的建议是统一成只扫隐私，`pre-push.ts` 里整套那一档和它用到的本机验证记录一起删掉，入口改成 `sumika-dev hook pre-push`。这会改掉 ADR-398 那一套的做法，要你点头，点头后写新 ADR。
