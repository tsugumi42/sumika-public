## 一、为什么挂在钩子上

几种做法比过（npm 上的版本和日期是 2026-10-26 查的）：

| | lefthook 2.2.2（2026-10-13，MIT） | husky 9.1.7（2024-11，MIT）+ lint-staged | simple-git-hooks 2.14.0（2026-08，MIT） | 一个脚本，手动跑 |
|---|---|---|---|---|
| 按改了哪些文件挑检查 | 自带（`glob`） | 要加 lint-staged | 没有，自己写 | 自己写 |
| 提交 / 推送时自动跑 | 是 | 是 | 是 | **否，还是靠记得**（F01 的根因） |
| 配置进仓库、几个 worktree 和会话共用 | 是（钩子装在共用的 `.git/hooks`） | 是 | 是 | — |
| 维护 | 活跃 | 快两年没发版 | 活跃 | — |

选 lefthook。GitHub Actions 和分支保护先不做：私有仓库的分支保护受套餐限制（审计 F01 查过），本地钩子已经能挡住"红着提交、红着推送"；要不要再加云端那一层等主人定。

## 二、跑什么（2026-10-26 在本机量的耗时）

**提交前（pre-commit），按暂存区里改了的文件挑，并行跑：**

| 改了什么 | 跑什么 | 耗时 |
|---|---|---|
| 任何文件 | 隐私扫描：暂存区新增的行里有没有本机认识的真实号码、私人字符串（邮箱等）、像密钥的串、本机的真实昵称和群名（不认识的长数字、邮箱只提醒）（`native/bin/sumika-dev.exe check private --staged`） | 不到 1 秒 |
| 任何文件 | `native/bin/sumika-dev.exe check docs --staged`：和不带 `--staged` 的 `sumika-dev check docs` 同样的检查，读的是暂存区里的版本，别的会话改了一半没暂存的文件不拦这次提交（2026-10-26 加的 `--staged`） | 约 0.8 秒 |
| 任何文件 | 冲突标记：暂存区新增的行里有没有没解决的 `<<<<<<<`、`>>>>>>>`（`native/bin/sumika-dev.exe check conflicts`；`=======` 可能是标题下划线，同一个文件里还有前两种才算）。2026-10-30 加：合 ui-go-2 时 80062b2c 把两处冲突连标记一起提交了。一红一过：主仓库、worktree、CRLF 内容、中文路径（强制转义）各试过 | 不到 1 秒 |
| `*.ts`、`*.tsx` | `bun run typecheck` | 约 3.1 秒 |
| `native/**/*.go`、`native/go.mod` | 暂存的 Go 文件 `gofmt -l`，`native/` 里 `go vet ./...` | 约 2.5 秒 |

**写提交说明时（commit-msg）**：`native/bin/sumika-dev.exe check commit-msg <说明文件>` 查标题——"类型(模块): "后面超过 40 个字、带分号、整行带 ADR 编号就拦；合并、回退不查（2026-10-27 加，主人嫌提交说明太长；写法的依据见 对照-提交说明写法（私有存档），规矩在上级 AGENTS「提交」第 1、2 条）。正文不查。

## 三、隐私扫描

- 号码（2026-11-11 改：以前按“长得像不像”拦，浏览器 bug 号、时间常量、UUID 的零都被拦，误报登记又要在 D9 和这里各登一遍；现在按真实值对，D9 删了）：
  - **拦**：和本机认识的号码完全相同，5～12 位，写在哪都算（文件内容、文件名和改名后的名字、下划线后、JSON、网址、提交说明）。名单现读本机：Go 聊天库 `qq.db`（出现过的人和会话、`qq_people`、`qq_groups`，`qq_sync` 等表的 `account`）、MaiBot 库 `person_info`、`chat_sessions`、`mai_messages`、`bot_platform_accounts`、群名表、`sumika.yml` 的 `qq` 段和其他 QQ 相关键（按 YAML 读，注释、端口、超时这类不算）。
  - **也拦**：本机不认识、但紧跟在 qq、uin、user_id、群、号、账号、好友这类词后面的 8 位以上数字；11 位手机号（不在网址里）。AI 会话读了本机 QQ 记录把样本贴进文档时，这些人 Sumika 库里没有。
  - **提醒，不拦**：其余本机不认识的 8～11 位数字，不以 0 开头，不在网址里，前面不是 bug、issue、#、max-age 这类，不是日期、2026 年前后的秒级时间戳、版本号。
- 私人字符串：`data/dev/private-strings.json`（不进 git，字符串数组，比如主人的真实邮箱）里的，不分大小写，`+tag` 和 `%40` 写法也认，出现就拦；推送前连作者、提交者的名字和邮箱一起扫。别的邮箱只提醒，noreply、示例域名（example、invalid、test、localhost）不提醒。
- 推送前范围里的合并提交也扫：用 `--remerge-diff`，只看自动合并结果到实际提交之间改的（冲突解决时手写进去的）。
- diff 里 `+++ ` 只在每个文件的块头里认作文件名，正文以 `++ ` 开头的新增行照样扫。
- 密钥：`sk-`（要在词头）、`gh?_`、`Bearer`、`api_key = …` 这类；名字：本机 MaiBot 库（只读）`person_info` 的昵称、群名片，加群名表和 `qq_groups` 的群名，3 个字以上的。聊天库里几百个人的昵称不进名单（不少是常见英文词，试过全仓误报四千多处）。
- 规则放宽或收紧后照 LESSONS 跑全部现有文件和历史：2026-11-11 新规则下，现有文件里认识的号码 0 处；HEAD 全部 4582 个提交里有 2026-10-12～10-26 的旧提交带认识的号码和名字（钩子上线前后），见待办“历史里的号码和名字”。
- 只打印打了码的内容和位置；名单只在内存里，不写文件、不打印原文。
- 误报：确认不是真实的以后，用 `--allow` 把它的哈希加进 `data/dev/private-scan-allow.json`（数据目录，不进 git；只存哈希）。认识的号码和私人字符串只能按“值 + 文件”登记，只对那个文件放行；其余按值登记。先按值登了一个不认识的数字、后来它进了名单，照样拦。
- **名单读不到就拒绝**（2026-11-11 独立复核第 1 条改；以前是“不算通过也不拦”，新规则拦号码全靠名单，悄悄降级等于放行）：没有 Go 聊天库、认识的号码一个都没有、任一名单读失败，退出码 2，提示里写数据目录在哪；确实要跳过（比如新机器还没恢复 data/）加 `--allow-missing`。MaiBot 库、群名表、配置缺了只在第一行写“缺 …”。读失败的报错只写是哪个来源、什么类，不带出文件内容。worktree 里没有 data/，名单一律读主工作区的（按仓库根解开 `--git-common-dir`，从子目录跑也一样）。
- 改了扫描或质检脚本，提交前会跑它们自己的测试（lefthook “扫描自测”）。

## 四、禁止的偷懒

- `git commit --no-verify`、`git push --no-verify`（上级 AGENTS 本来就禁止跳过钩子）；检查红了改代码或补基线，不绕。
- 检查命令后面接管道把退出码吞掉；"环境没装好"当成通过（缺 go、缺名单都要说出来）。
- 为了让钩子快一点把该跑的检查挪走，不留记录。

## 五、验收

1. 故意改坏四种，每种都被挡住、退出码非 0：类型错误（`.ts`）、文档检查错误、Go 对拍红（改一句提示词；2026-11-01 起提交前不跑 Go 对拍，ADR-225，这一格改由推送前的 go test 挡）、暂存区里有一个真实名字（用本机名单里的，输出只有打码的样子）。
2. 只改文档的提交：钩子总耗时在 3 秒以内（量出来写进提交说明）。
2.5. **每一项检查都至少真跑过一次红、一次过**（2026-10-26 补：第 1 条的四种改坏没有一种带 .go 文件，"Go格式"那项在 Windows 上一直是坏的——直接写在 lefthook.yml 里的 `test -z "$(gofmt -l …)"` 被拆坏了引号，暂存了 Go 文件就红；后端那条线发现，f85961dc 改成 `scripts/check-gofmt.ts`，2026-11-19 起是 `sumika-dev check gofmt`）。以后加一项检查，同时补上它的一红一过。
2.6. **推送钩子只测受影响的包（ADR-218）的环境 × 路径表**（2026-11-01 补跑，复盘-2026-10-31 指出 只量了挑包逻辑）。用一个临时分支上的两个提交：绿 = `cmd/soak` 里加一行注释，红 = 同包加一个必红用例；"推送"是 `git push --dry-run`（照样走 lefthook 的 pre-push，什么都不传上去），"手跑"是把 ref 行喂给 `bun scripts/pre-push.ts`。挑出的都是 1 个包（共 57 个）。
