# 规格：本地合并队列

> 状态：2026-11-08 起草并实现于分支 feat/merge-queue（ADR-320），已合 main；试用一段时间后再定是不是唯一的合并方式（ADR-320 第 3 条）。
>
> 2026-11-19 已被 ADR-398 改为：合 main 走公开仓库的 PR，只看 CI；本地队列只在 GitHub 不可用时兜底（[规格-合并走PR](规格-合并走PR.md)）。
>
> 参考了：
> - **GitHub merge queue**：采用"排队的分支依次合上前面已合完的基线、在合并后的树上跑检查、绿了才进主干"；采用"红了踢出队列、后面的接着来"；没采用云端、分支保护和"同时多个分组并行验证"（本机只有一个验证名额，并行验证就是回到互相追 main）。
> - **bors（bors-ng）**：采用"main 只能由队列推进，进 main 的就是验过的那个合并提交"和"批次里一个红了不拖累已经绿的"；没采用 try 分支和批量合并再二分（本机一条条验，每条的耗时可以接受，二分省不了多少）。
> - 本仓库自己的 [规格-提交前检查](规格-提交前检查.md)：验证用现成的 `go-verify`，结论写进验证记录，推送钩子复用。

## 一、要解决什么

当天并行六七条分支时：分支 A 验完，main 被 B 合进来又变了，A 只好重验；两个 `go test` 名额各自把包并行铺满所有核，按墙钟写的测试接连偶发红（ADR-320 依据）。队列让合并顺序化：每次验的就是要进 main 的那棵树，验完直接进 main，不再追 main。

## 二、命令

```
bun scripts/merge-queue.ts add <分支> [--title "合并标题"] [--body-file 文件]
bun scripts/merge-queue.ts status
bun scripts/merge-queue.ts run [--watch]
bun scripts/merge-queue.ts remove <分支>
```

| 命令 | 做什么 |
|---|---|
| `add` | 排到队尾。分支必须是已有的本地分支，不能是 main，不能重复。标题默认 `合并 <分支>`，要写成项目的提交标题格式（`feat(模块): …`，30 字左右写行为，不带 ADR 号）；`--body-file` 的内容当合并说明的正文（调用方自己写三到八行和署名行），读进来存在状态里，之后文件删了也不影响。在任何 worktree 里都能敲。 |
| `status` | 在跑的（分支、阶段、执行者 pid，执行者已经不在会注明）、排队中的（顺序、标题、加入时间、"等主工作区干净"等标记）、最近 20 条结果（绿或红、耗时、红的原因、冲突文件、输出文件路径、绿的合并提交号）。 |
| `run` | 执行者，见第四节。队列空了退出（退出码 0）；队首验好了但主工作区不干净且没开 `--watch`，退出码 3；已有执行者，退出码 4；`--watch` 一直等新条目。 |
| `remove` | 从队列里删一条，顺手清掉它验好待快进的记录。正在跑的那条（执行者还活着）不删，报错说明。 |

分支是按**名字**排的：`run` 取到它时才读分支当时的提交，排队后又往分支上提交的会一起合进去。

## 三、状态文件和锁

放在 git 公共目录（`git rev-parse --git-common-dir`），所有 worktree 共用，不进 git：

| 文件 | 内容 |
|---|---|
| `sumika-merge-queue.json` | `queue`（条目：id、分支、标题、正文、加入时间、`waiting`、`ready`）、`running`（当前在跑的条目、执行者 pid、阶段、开始时间）、`results`（最近 200 条；每条分支、标题、时间、绿或红、原因、冲突文件、耗时、输出文件、合并提交、分支当时的提交） |
| `sumika-merge-queue.json.lock` | 读改写的短锁：独占创建（`wx`）、写入持有者 pid，持有者没了或超过 60 秒算过期；拿不到等 15 秒后报错 |
| `sumika-merge-queue.runner` | 执行者锁：同样独占创建；已存在则读 pid，进程还活着就认输，已经没了就删掉重来 |

- **写入原子**：先写同目录下带 pid 和随机后缀的临时文件，再改名覆盖；Windows 上改名遇到 EPERM（杀毒扫刚写的文件）隔一会儿重试八次。读的人要么读到旧的整份、要么读到新的整份。文件缺失或写坏读成空队列（`add` 之后不会丢掉别人刚排的条目是靠短锁，不是靠改名）。
- 测试用环境变量把路径指到临时目录：`SUMIKA_QUEUE_STATE`（状态文件）、`SUMIKA_QUEUE_WORKTREE`（专用 worktree）、`SUMIKA_QUEUE_OUT`（输出目录）、`SUMIKA_QUEUE_VERIFY`（验证用的 bun 脚本）。
- `ready`：一条已经验绿、只差快进的合并提交（提交号、基线 main 的提交号、分支提交号、结论行、输出文件）。快进被主工作区挡住后留着，下一轮 main 和分支都没动就直接快进，不重验。同时在 `refs/sumika-queue/<id>` 留一个引用，防止被 gc。

## 四、流程（`run` 取队首一条）

1. **拿执行者锁**，没拿到退出（退出码 4）。起跑时把残留的 `running` 清掉：只有一个执行者，残留的一定是上次死掉的。
2. **取队首**，读分支当前提交。分支没了记红"分支不存在了"；分支已经在 main 里记绿"已经在 main 里，没有要合的"。
3. **专用 worktree**（默认主工作区下 `.claude/worktrees/_queue`，没有就建，建时从主工作区拷 `vendor/bin`）：`merge --abort`（有就中止）、`reset --hard`、`clean -fd`（不加 `-x`，被忽略的 `vendor/bin` 留着），再 `checkout --detach` 到当前 main。
4. **合并**：`git merge --no-ff -F <说明文件> <分支提交>`，说明是标题加正文。
   - 有冲突：记红，原因"冲突"，列出冲突文件（`diff --diff-filter=U`），`merge --abort`，worktree 回到 main；不验证，不动 main，下一条接着来。
   - 没有冲突却失败（比如合并提交的 commit-msg 钩子拦了标题）：记红，原因写 git 的第一行报错。
5. **验证**：在专用 worktree 里跑 `bun scripts/go-verify.ts`（合并后那棵树里的版本；工作目录必须是 worktree 根，因为 go-verify 里全是相对路径），环境变量 `SUMIKA_TEST_LANE=verify`；测哪些包由 `scripts/go-affected.ts` 的 `pick()` 一处决定（ADR-362）：改到的包，加源码改了的包的**直接导入方**（只一层，不带根包，只改 `_test.go` 的不带；直接导入方自己没有测试文件时，穿过它选最近的有测试的导入方），总带 `internal/archcheck`；自己没有测试文件的包改了，照旧带全部导入方；`go.mod`、提示词、检查脚本等改了就整套。结论行里写“挑包：改到的 N 个包 + 导入方 M 个 + archcheck”；输出边跑边写 `data/dev/test-runs/queue-<分支>-<时间>.txt`，开头记分支提交、基线、合并提交。超时 60 分钟停掉并记红。
6. **红**：退出码 2 是 go-verify 的环境问题（树不干净、找不到共同祖先），记"环境错误"，其余记"验证红"，原因从输出里取最多三行 `--- FAIL`、`FAIL`、`有检查红了` 等关键行（没有就取最后一行）。不动 main，专用 worktree 回到基线。
7. **绿**：
   1. 取 go-verify 输出里最后一个"合并说明可以写：…"之后的内容当结论行（取不到写"go-verify 退出码 N"）。合并提交已经存在，结论行只能事后加：用 `git commit-tree <同一棵树> -p <基线> -p <分支> -F <标题+正文+结论行>` 重做一个提交，并断言树对象号和验过的一模一样，再把专用 worktree `reset --hard` 过去。不用 `commit --amend`：amend 会触发 pre-commit，在整棵合并树上再跑一遍检查。树不变，推送钩子按树认的验证记录照样命中。
   2. **确认 main 还是开始时那个提交**：不是，说明验证期间别人动了 main，回到第 3 步重新合、重新验，最多三轮，仍然追不上就记红"main 一直在变"（防止无限转）。
   3. **快进 main**：
      - main 在主工作区检出着：`git status --porcelain --untracked-files=no` 有输出（已跟踪文件有未提交改动）就**不碰**，该条标"等主工作区干净"，**留在队首**（后面的不抢先，因为它们要建在这条合进去之后的 main 上），记下 `ready`；否则 `merge --ff-only <合并提交>`。未跟踪文件不算脏（主人多个会话下主工作区常年有零散未跟踪文件，快进不碰它们）；快进自己因为未跟踪文件冲突失败也归到"等主工作区干净"。
      - main 没有在主工作区检出（主工作区在别的分支上）：`git update-ref refs/heads/main <合并提交> <开始时的提交>`，带旧值，等于原子的 compare-and-swap。
      - 快进时发现 main 又变了：回第 3 步（算一轮）。
8. 记结果，出队，取下一条。队空退出；`--watch` 则每 3 秒看一次新条目；队首在"等主工作区干净"时没开 `--watch` 就退出（退出码 3，`ready` 保留，下次 `run` 直接快进），开了每 10 秒再看一次。

执行者出了意外（例如建不出专用 worktree）：不把条目记红也不丢，直接报错退出，条目留在队里。

> 2026-11-14 ADR-378：下面“队列自己不推送”已被 ADR-378 改为：队列空闲时自动把 main 推上 GitHub，推前隐私扫描照旧，扫出东西就不推并写报告。实现待做（后续路线 P5-16），在那之前仍是不推送。

## 五、和推送钩子、go-verify 的关系

- `go-verify` 照旧把验过的树写进 git 公共目录的 `sumika-go-verified.json`（按 Go 会读到的那几处的树、执行测试的那几个脚本（`go-verify.ts` 的 `RUNNERS`，2026-11-12 起）和 go 指纹认，不按提交号认）。队列快进进 main 的提交和验过的树一样，所以之后在主工作区 `git push`，推送钩子直接命中记录，不再重跑。重做合并提交只改说明，不改树。
- 钩子测的是当前工作区：快进后主工作区的 main 就是验过的树。主工作区不在 main 上（只推进了 main 引用）时，推送钩子测的是工作区而不是推出去的提交——这是 [规格-提交前检查](规格-提交前检查.md) 已知的限制，这里没有改变。
- 队列自己不推送、不跑推送钩子；合并提交在专用 worktree 里创建时，commit-msg 钩子会照常跑（合并提交的标题要写成项目的格式，或者以 `Merge ` 开头），pre-commit 不跑。
- 手动 `bun scripts/go-verify.ts` 仍然可用（分支上先自己验一遍也行），不改变记录的写法。
- 大包分进程（2026-11-09 主人：“这测试这么久？”）：`-short` 时先跑别的包，再一个一个跑根包、`internal/app`、`internal/memory`、`internal/turn`：`go test -p 1 -exec scripts/go-shard.cmd`，每个分六个进程，整套不分；`SUMIKA_ROOT_SHARDS=1` 关掉。不能和别的包挤在一起分进程：`internal/app` 单独 161 秒，挤在一起 467 秒，还会误红。预算和写法见[规范-测试耗时](规范-测试耗时.md)。

## 六、测试名额分两档

`scripts/run-low.ps1` 对 `go test` 按环境变量 `SUMIKA_TEST_LANE` 排队，两档是两把不同名字的全局互斥量，同时最多一个验证加一个开发测试：

| 档 | 谁用 | 互斥量 | 说明 |
|---|---|---|---|
| `verify` | 合并队列、推送钩子、每日整套 | `Local\sumika-go-test-verify` | 一个名额，独占；`go-verify.ts` 的 `runLow()` 一处设好，所以 go-verify、pre-push 自动走这一档；直接跑整套时命令前面自己带 `SUMIKA_TEST_LANE=verify` |
| `dev`（默认） | 开发中的代理和会话 | `Local\sumika-go-test-dev` | 一个名额；参数里没有 `-p`（含 `-p=N`）时在 `test` 后插入 `-p N`，N 是逻辑核数的一半，至少 1 |

值不是这两个，退出码 2 报错。只有 `go test` 占名额，`go vet` 不占。持有名额的进程被杀时系统自动放开，下一个等的人拿到时当作拿到（被遗弃的互斥量）。旧的 `Local\sumika-go-test-slot-0/1` 退役。

## 七、禁止的偷懒

- 验证红或冲突时不动 main；不用 `--no-verify`、不用 `git push`、不 `reset` main。
- 不在队列外直接往 main 上快进、不拿"上次验过"代替这次在合并后的树上验（`ready` 只在 main 和分支提交都没变时才复用）。
- 不吞退出码：go-verify 的退出码原样记；超时、被杀当红。
- 不靠增加重试把偶发红盖过去：红了就是红，原因和输出文件留着，墙钟类测试照旧当 bug 修（ADR-320 第 3 条）。

## 八、已知的限制

- 根包（约 76 秒）和间接导入方不在每次合并的验证里，由每天的整套测；只改底层包时队列比以前多测几个到几十个包（ADR-362 的估计：包耗时总和 36～390 秒，墙钟少于总和）。
- 同一时间一个执行者，验证是一条一条的：队列越长，排在后面的等得越久；这是换来"每条都在前一条合完的 main 上验"的代价。
- 执行者要自己起（`run` 或 `run --watch`），`add` 不会自动起。
- 专用 worktree 是新开的，没有 `node_modules`：go-verify 本身不用，但合并提交的钩子（lefthook 的路径写死了主工作区的 `node_modules`）能不能跑取决于主工作区的依赖在不在。
- 分支排队后被改写（rebase、强推）会按新的提交合；删了就记红。
- 主工作区的 `.git/info/exclude` 里有 `**/.claude/worktrees/`，别的克隆没有这条时，专用 worktree 会显示成未跟踪目录。
- `remove` 只拒绝执行者活着时正在跑的那条；执行者死了、条目残留 `running`，`remove` 才删得掉。

## 九、验收

1. `scripts/merge-queue.test.ts`、`merge-queue-2.test.ts`、`merge-queue-3.test.ts`（共用 `merge-queue.testlib.ts`，2026-11-12 拆成三份好让 bun test --parallel 按文件分进程；用临时 git 仓库，全局配置也指到临时文件，验证用可替换的函数代替 go-verify）：
   - 排队顺序，验第 N 条时树里已经有前 N-1 条，合并提交的标题、正文、结论行、第二个父提交对；
   - 冲突记红（原因、文件）、main 不动、专用 worktree 干净、后面的照常合；
   - 验证红（含退出码 2 环境错误）main 不动、原因和输出文件路径写下来；
   - 验证途中 main 被改：重新合、重新验，新合并提交接在别人的提交后面；一直在变：三轮后记红；
   - 主工作区有已跟踪文件的改动：不快进、条目留队首、后面的不抢先，改动原样；干净后接着快进且不重验；未跟踪文件不算脏；
   - main 没在主工作区检出：用带旧值的 update-ref 推进；
   - 两个执行者互斥（同进程、命令行退出码 4、持有者进程没了的锁算过期）；
   - 状态文件原子写：写到一半失败原文件完好且没有临时文件残留；六个进程同时 `add` 不丢条目；坏文件当空队列；
   - `add` 的拒绝、`remove` 不删正在跑的、分支已在 main 里、分支被删。
2. `run-low.ps1` 分档：用假的 `go` 手动试过——dev 档自动加 `-p 6`（本机 12 个逻辑核），已有 `-p=2` 不重复加，`-parallel 3` 不算 `-p`；verify 档不加；两个 verify 排队（共 6 秒，串行）、dev 同时跑；值写错退出码 2。
3. 没有跑的：用真的 go-verify 和真的 main 走一遍完整流程（任务限制），留给第一次真实试用，并按 ADR-320 第 3 条记重验次数、偶发红次数、排队到合进 main 的时长。
