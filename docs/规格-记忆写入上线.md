## 三、每一步都守的几条

1. **谁能看到什么，只能收紧**。这份规格的任何一步，都不能让任何人在任何场合比现在看到更多；每步都有一张四种场合表（本地私聊、本地群聊、QQ 私聊、QQ 群）和敌对输入表，最后一列写"比现在多看到的人"。写入本身会让库里多出新内容，这不叫放宽——它们的可见范围照规格-记忆-v2 4.2 由程序定，W5 的场合过滤还把第一阶段限在主人自己的 QQ 私聊。
2. **身份按类型认，不按名字认**：主人是 `ActorKind` / `Origin` 说了算（`owner`、`peer`），不是群名片叫"主人"就是主人。每一步的敌对输入都包括"冒充主人的名字"和"伪造的行头"。
3. **每一步一个提交序列、能整个撤掉**；改了行为的同一个提交里改文档（规格-记忆-v2 4.4、13.2.4 等被改写的句子），然后 grep 一遍旧说法。
4. **提示词和解析同一步生效**（LESSONS「换了输出格式的提示词」）：W3 要改整理提示词，草稿放 `data/dev/`，解析、测试、提示词文件、版本号在同一个提交里换上，换完看一眼最近的整理有没有"解析失败"。
5. **验收数字从输出里抄**，提交说明写命令、退出码、几个包；偶发红写这个包整组通过的那一次（LESSONS）。改坏检查要拆掉被测的保护本身，不是另造一个泄露。在假库 / 造的数据上量的数（游标位置、耗时、P50 / P95）在提交说明里写明是假库的数，不当真实数据的结论。
6. **写进文档的次数、时间从记录里取**，不凭印象；写 ADR 前看本地 main 的最后一号。行号会漂，文档里引代码优先写函数名。
7. **临时文件一律写 scratchpad 或 `t.TempDir()`**，不写 `/tmp`、`%TEMP%`；实现和测试**不读写** `仓库根/data` 里的真实数据。仅有的两处例外：W5 的 `memory-prepare`（只读源库、只写备份和一份不含正文的报告）和 W6 的拷贝 / 估算 / 真跑。W5 的 `memory-prepare` 要主人点头；W6 的拷贝 / 估算 / 真跑，主人已经同意影子整理（"影子整理可以，跑吧"，Q1），仍按 W6 的花费上限守。两处都**由主会话跑，不交给实现子代理**；输出里只留计数，不留聊天正文。

**W1a 具体做什么**

- **守卫完整的判定加一条（`GuardLevel`）**：嵌入就绪**并且**当前模型的句向量预热完成，才报 `full`；预热没完成时报 `literal-pending`，发送继续钳在试运行。理由：现在 `GuardLevel` 只看 `Status()`，换模型当天 `memory_sentences` 全部失效，预热期间守卫在退路（只比原文）上、发送却已放行——这是计划内的、自己造成的降级，不是 ADR-186 第 4 条批准的"嵌入真的挂了"。（隐私复核 6 与代码复核 21 合并。）**实现（W1a，2026-11-02）**：「预热完成」= 守卫能用的全部条目（有效的，和待确认的事实）的句向量都在库里；没记住之前 `GuardLevel` 每次现数一遍（只读 `length(vec)`，几毫秒），数到 0 就按模型名记住，之后不再查库——所以重启后库里本来是齐的不用等后台那一趟，写入新条目也不会把已经 `full` 的守卫降成 `literal-pending`、让 remember 之后的那一句回复被钳在试运行。**同一个函数 GM7 还要再加一条"门槛标定过的模型才报 `full`"**（规格-Go本地模型 2.7 的"门槛绑模型"，只收紧；主人 2026-11-02 认可，ADR-233 第 1 条；后合的解冲突，顺序见上"谁先合"）。
- **句向量预热**：`EmbeddingReady` 之后在后台补 `memory_sentences`（带取消，接进 `fix/memory-vectors` 已有的 `stopVectors`）。范围：所有 `active` 条目和 `fact` 候选的全部句子（不按某个听众的 `denied` 取），用 `contentHash(VectorPrompt + "\x00" + text)` 和 `TypeDocument`，模型是当前模型；换模型后旧模型的行按 `model` 判作废，顺手清掉。**分批、批间放开 `sentenceGate`**：现在补句向量要先拿 `sentenceGate` 并受守卫 2 秒时限管，预热如果整段持锁，守卫调用会排队到超时。
- **写入之后同样异步补句向量**：W5 开写后每批整理新增的条目、片段（一个片段可能十几二十句）不要留给下一次守卫判断在 2 秒里现算；提交后和补向量一起排（同一个 kick）。（2026-11-02 核过：`SyncVectors` 只管 `memory_vectors`，不碰 `memory_sentences`，所以接在了 `kickVectors` 的协程里，补完 `memory_vectors` 之后接着补句向量，写入之后的那一趟自动带上；测试 `TestWriteKicksSentenceWarmup`。）
- **补向量和预热的批量改小**：Python 版（`server.py`）每个模型一把锁、整批持有，一批 64 条约 3.4 秒，而守卫嵌入限时 2 秒、召回嵌入限时 3 秒，换模型后的重算期间每次撞上一个大批就超时、走 `embed-down` 退路，提醒反复发和恢复。Go 版只在每一行的前向上持锁、不整请求持有（规格-Go本地模型 2.5 的"锁"一行），守卫最多等一行的时间，所以对 Go 版这条不是持锁问题，批量仍然取小是为了让一次请求短、取消粒度细。生产补向量批量起步 **8**（两边同一个数）；最终数按 GM7 的实测（它的验收 9）写进提交说明，使每批在 Python 版上持锁不到半秒。
- **向量**：`VectorPrompt` 保持 `raw-v1`（`index.go`），gte 查询和库存都不加前缀。模型名变了，`SyncVectors` 按 `model` 把全部向量判成过期并重算；重算是确定的，库里约六百条，批量 8 时总墙钟要实测。
- **`EmbedTyped`**：`embed.Typed` 只有守卫路径在用（`outbound.go`）；召回查询（`recall.go`）和补向量（`index.go`）调的是普通 `Embed`，`VectorPrompt` 的注释也写"两边都没有前缀"。gte 没有前缀，两边结果相同，所以**现在无影响，本步不改这两条路径**；以后换带前缀的模型（Qwen3-Embedding 带指令前缀）之前，要同一步把召回和补向量也改成 `EmbedTyped`。已在待办挂了一条（「召回和补向量路径改用 EmbedTyped」）。旧桥下 `EmbedTyped` 退化成 `Embed`（不带 `input_type`），所以这条在 `legacy` 上本来就没有区别。（复核建议"同步改"或"降级措辞"二选一，选了降级。）
- **门槛**：`GuardThreshold` 保持 0.70，**不改**。理由：ADR-202 的 0.70 是 `cmd/guard-eval` 在 `gte-multilingual-base` 上量的，换成 gte 是让生产和量的条件**一致**，反而比现在（生产是 Qwen、门槛从没在 Qwen 上量过）更靠得住。**不引用绝对数**：起草时写的"三遍拦住 30/30、误拦 2～3/30"是 ADR-202 的原始记录，2026-10-28 重造负样本后变了（规格-记忆-v2 13.2.8：28 条合成记忆、33 正 / 30 负，0.70 下三遍 32/33、31/33、31/33，误拦均 2/30，0.75 降为 30/33、29/33、29/33，"不能再称全拦"）。这一步要证明的是**判断没变**：同一份数据、同一轮次，Go 与 Python 逐样本的"拦 / 不拦"决定相同、最大相似度差在向量门槛内（做法见规格-Go本地模型 2.7、GM7-5、GM7-6）。但那是合成数据，真实群负样本仍是缺口（ADR-202 第 2 条），不并进这一步。
- **让量的和用的是同一份**：把生产的 `outboundSentences` 导出（`memory.OutboundSentences`），`guard-eval` 的 `sentences` 改成调用它、删掉复制品。以后切句改了，量门槛的工具自动跟着。这是 LESSONS「每个读同一门槛的程序一起改」的落实。
- **重排**（只改接线，起草时多写的开关删掉）：
  - 新增配置 `memory.rerank.model`（空 = 关，默认空）、`memory.rerank.k`（默认 40）、`memory.rerank.timeoutSeconds`（默认 5，**单独**的时限，格式照 `config.go` 现有的数字型时长键（`idleMinutes`、`approvalMinutes` 那种），不引入 `5s` 字符串解析：`RerankClient` 自带 30 秒，重排慢时 `memory_search` 会把整轮卡到 30 秒）。
  - `Options.Reranker` 在 `Open` 时固定，而嵌入晚于记忆就绪（`EmbeddingReady`）。所以给一个**懒绑定的包装**：嵌入未就绪时返回错误，让 `reorder` 退回原顺序；就绪后才真去调。`backend` 是 `legacy` 而 `memory.rerank.model` 非空时，重排不可用（旧桥没有 `/v1/rerank`）：包装直接返回带原因码 `rerank-unsupported-legacy` 的错误，`reorder` 退回原顺序，启动时提醒一次，不在每次调用时刷屏。
  - 重排只在明确回忆（`ModeExplicit`，即 `memory_search` 工具）上用：在 `reorder` 调用前加条件 `q.Mode == ModeExplicit`。普通召回走拼参考信息那个 5 秒钩子，`bge-reranker-v2-m3` 40 对在 CPU 上可能超过 3 秒的 `RecallTimeout`。
  - **不加** `Options.RerankAllModes`、**不加** `memory-eval -mode explicit`：`memory-eval` 的非寒暄题本来就是 `ModeExplicit`，且已有 `-rerank-url / -rerank-model / -rerank-k`。真正新的只有一点：线上 `memory_search` 走 `TopK: 12` 的 Hits 分支，评测现在不带 `TopK`，A/B 要走同一条分支，所以给 `memory-eval` 加 `-topk`（默认 0 = 不变）。
- **重排 A/B**（W1 之内的单独一个提交，用 `cmd/memory-eval`）：R0 无重排、R1 `bge-reranker-v2-m3`（K=40），同一次运行里轮流跑三遍，三遍同向才算数。判断（我定的，起步值）：事实·换说法前 1 提高 ≥ 3 个点或前 5 提高 ≥ 2 个点，P95 增量 ≤ 2 秒，越权 0，才把配置示例里的默认改成开；否则保持关。"没差"是预期中的一种结果（盘点第 5 节），不算失败。

**已知的坑**

- 边界 ⑧（收到不等于可用）：进程活着 ≠ 模型能用，所以有"预热成功才就绪"；句向量没补齐 ≠ 守卫完整。
- 边界 ⑲（缓存复用与失效）：旧的 `memory_sentences` / `memory_vectors` 按模型名失效；回到 `legacy` 也是同样重算一次（向量是派生数据，在 `memory-v2.db` 里，可以删了重建；回滚的两条路见规格-Go本地模型第六节第 6 条），所以 W1 可以整个撤回。
- 边界 ④：`EmbeddingReady` 触发的后台补齐要带取消，关闭流程里先停它再关库（`fix/memory-vectors` 已有 `stopVectors`，预热句向量要接进同一个）。
- 跨模型的向量不能混用：补齐没做完时，召回只用已经是新模型的那些，没有就只用全文（`SyncVectors` 的 `next` 只收模型对得上的）；W1 写成测试。
- `memory-eval` 的 `-embed-model` 的名字是服务里的 id（`gte-multilingual-base`），和 Bun 时代的 `qwen3-embedding-0.6b-local` 不是一回事；想和旧桥 A/B 要改配置里的名字。
- 守卫 / 召回嵌入时限是写死的 2 秒 / 3 秒：Go 版后端的单句耗时比 Python 版短（调研笔记：约 17～20 ms 对 22 ms），但批量 8 的取值以实测为准。

### W2：取代保护——AI 只能取代 AI 自己写的事实，而且不能凭一条待确认就取代

**现状的洞**：`supersede` 和 `revoke` 都是"黑名单"：只有 `confirmed_by = 'owner'` 的拦得住 AI，其余有效事实（包括所有从 Bun 导入、`confirmed_by` 为空的）AI 想顶就顶。整理提示词本来就让模型"和已知事实矛盾就 upsert_fact 并填 supersedes"（`prompts/summarize.md`），已知事实里有导入的。结果：一次整理，导入的有效旧事实被标成"被取代"，从召回里消失，新事实却只是待确认。

第二个洞（复核后加）：整理写的新事实一律是待确认，但 `insertFact` 照样先 `supersede`。W3 之后哪怕白名单放开了 `confirmed_by = 'ai'`，模型一次提到"茶"，也能把攒了三次证据的"咖啡"挤出有效集，召回里只剩一条"听说"——**升级要三次，被顶掉只要一次**，证据门槛被绕过。

**技术路线（我定的）**：两件事，都在写事务里判断，不加列、不回填。

1. **白名单**：整理（`Batch.By != ByRemember`）只能取代、撤销 `status = 'active'` 且 `confirmed_by = 'ai'` 的事实；其余一律不动。`confirmed_by` 是空、空串、`owner`、不认识的值，都算"受保护"。主人自己（`ownerActs()`，即 `remember`）可以动任何有效事实，不变。
2. **整理写的候选不在写入时取代任何有效事实**：`insertFact` 里整理路径遇到 `supersedes`，不调 `supersede`，只把"想取代谁"记在新候选那条 `add` 修订的 `after_json`（`wants_supersede: <旧编号>`），计数 `supersede_deferred`，新候选照写。真正的取代发生在 W3b 提升这条候选的**同一个事务**里，并且过 1 的白名单；写入时就取代的路只留给 `remember`。

- 实现点：一个函数 `protectedFromAI(confirmedBy string) bool`（`!= "ai"` 即真），`supersede` 和 `revoke` 都调它；不要在两处各写一份比较。被挡下的取代计数 `supersede_protected`（和"在模型看到它以后被别人改了"的 `supersede_lost` 分开，不然报告里分不出原因），被挡下的撤销 `revoke_protected`（和 `revoke_noop` 分开）。
- 效果：现在没有任何代码写 `ai`，所以 **W3 之前，整理什么有效事实都动不了、也不会因为一条候选就让旧的消失**；W3 之后，只有被 AI 攒够证据提升的（`confirmed_by = 'ai'`）整理才能动，而且要等取代它的那条自己攒够证据。候选（待确认）不在取代范围里——`supersede` 本来就只动有效的，这一步不改。
- **提升时想取代的旧事实受保护怎么办**（我定的，W3b 用）：旧事实还是 `active` 但 `confirmed_by` 不是 `ai`（导入的、主人放行的）→ **这条候选不提升**，留着，计数 `confirm_blocked_protected`，写进 W6 报告 D 节（"需要你来动"）。理由：提升了两条会同时有效且互相矛盾，而受保护的那条背后有主人的放行或导入时的有效身份，不该被 AI 凑出来的三次证据压过去。旧事实已经不是 `active` 了（被别人取代、撤销）→ 不取代，照常提升。
- **为什么不选"迁移加 `written_by` 列、回填 `legacy`"**：①要对真库多迁移一次（加列也是改真库，要备份、要主人在场），白名单一行代码就能做到同样的保护；②"谁放行过"这件事 `confirmed_by` 已经记了，再加一列是两个状态要同步；③导入的行回填出来也只是"和空一样受保护"，信息没增加。以后记忆页想显示"来源"再加列不迟。代价：导入的有效事实里本来是 Bun 的整理 AI 写的那部分（`fact_revisions.by = 'summary'` 的 `add` 修订），也被当成"受保护"，AI 动不了、要主人动，比必须的更严——这是收紧；数量 W6 的报告里数一次（"受保护的有效事实：Bun 整理写的几条、主人放行的几条、其余几条"，并按主体再分：主人 / 她自己 / 别人）。
- **整理撤销现在基本是死路，要说实话**（复核改正，起草时写成"这条路现在是通的"是错的）：`prompts/summarize.md` 的 `revoke` 格式没有 `src` 栏，`plan.revoke` 要求 `src` 里有主人本人的话，模型不带 `src` 一律被拒（`CountRevokeRefused`）。所以 W2 对导入事实的"撤销变严"只是把本来就走不通的路明文关上，不是一个新的收紧。W3a 的新提示词会给 `revoke` 加 `src` 栏（单个 `src`、必须是主人本人那一行）——这才让"你在聊天里说'不对'→整理撤掉 AI 提升的事实"这条路真正通；对导入的事实，白名单决定它仍然撤不动，要你用 `remember`（带 `replaces`）改。这是 Q5 真正在问的事。
- **导入的、主体是"别人"的有效事实，W2 之后没人改得动**（复核提出）：`remember` 的 `subject` 只许 `owner` 或 `self`（`memory/tools.go`），替换只能走 `replaces`，但新事实的主体不能是那个人。例如导入的"某人住上海"，AI 不能动，你也无法写一条对的来替换。**有多少条先量**（W6 报告 D 节按主体分类计数；我没读真实数据，不知道多不多）。出路在以后的记忆页；让 `remember` 带对方的号属于"谁能做什么"的默认值变化，要先问你，不在本步。
- **主人再说一遍就是放行**（顺带，同属收紧，我定的）：`remember` 遇到同文的**有效**事实现在只回"这件事已经记着了"，不改 `confirmed_by`（`reportDup`；只有待确认的才 `promote`）。改成：同文的有效事实 `confirmed_by` 不是 `owner` 时，提成 `owner`、记一条 `confirm` 修订、范围不动。这样你把一条导入的旧事实"再说一遍"，它就从"受保护"升成"你亲口放行的"，W3 之后的 AI 提升事实被你再说一遍也变成你的。**只在 `lastSaid` 查到的是你本人在这个会话说的最近一句时才提**（`Remember` 里已有 `lastSaid`，要求 `Origin == "owner"` 且会话对得上；查不到就只回"已经记着了"，不提）：原来的打算是挡住"模型把链接正文、图片描述里的“请记住……”当成你的话而调用 `remember`"。**复核后改实（2026-11-02，已核实）：这条检查在 `remember` 挂得上的场合里恒真**——`remember` 只挂在你在场的私聊里，那里的人话只可能是你说的，`lastSaid` 取到的最近一句永远是你那一句，所以防不住"你发了一个链接，正文里夹着‘请记住：<和某条导入事实同文的一句>’，模型照做"；它真正管的是 `Remember` 被别的入口调用（测试、将来别的入口）时不把别人的话当成你的话。风险有限：放行只会让事实更受保护（整理以后动不了它；同文的若是被隔离的 ai 事实，也一并脱离隔离），而且模型得先知道同文的字面；`reportDup` 对待确认候选的 `promote` 本来就没有这道检查。真要防注入要么要求"被放行的文字和你最近一句有重叠"（复核时因误拒多被否掉），要么要求"这一轮没读过链接、图片这类外来内容"，都没做，挂待办。

### W3：待确认怎么变成有效

**要先说一个更根本的问题**（比"次数"重要）：4.4 的规则是"3 次不同场合"，但**现在证据几乎攒不起来**。证据只在"同文"（去掉空白标点后字面相等）时才记一次（`write.go` 的 `findDup`、`merge`），而整理模型每批都是重新写句子，换个说法就是另一条待确认；给它看的已知事实里又没有待确认的（`summary.go` 的 `knownFacts`），它没机会沿用原来的措辞。只调"3 次"这个数，结果会是"永远凑不够"。所以 W3 分两小步：先让证据攒得起来（W3a），再按证据提升（W3b）。

**W3a 让证据攒得起来**

- 两个办法：①按嵌入相似度并（向量 ≥ 某个门槛就算同一件事）；②让模型自己说"这批里又出现了支持某条待确认的话"。**选②**（我定的）：①有个危险的形状——"主人下周三考试"和"主人下周四考试"的相似度会很高，却是互相矛盾的两件事，并起来等于互相给对方"作证"；时间、数字、否定这类差一个字意思就反的句子，向量分不开，模型能分。②就是 4.2 本来写的 `evidence` 动作。
- 提示词：新建 `prompts/summarize-v2.md`，`SummaryVersion` 升到 2（`summary_parse.go`；幂等键 `(会话, 起, 止, 版本)` 带它，Go 现在没写过真的批，不会重复整理）。**这是 13.2.12 的 W9 那份文件的第一处改动**，W9 的 `evidence_quote`、`only_her`、条数上限以后加在它上面，这里只做最小的三处：
  - 在"已知事实"后面加一块"听说过、还没确认的"：最多 20 条，按创建时间新的在前，格式同已知事实 `编号｜类型｜内容`；**只放这个场合看得见的**（走 `CanSee(it.Scopes, AllowedScopes(整理用的听众))`，和 `knownFacts` 同一个可见集合；因此 `evidence` 只可能在候选本来就看得见的会话里发生）；候选不带"已有几次"，免得模型为了凑次数去写。候选的正文来自任意说话人，**和 `knownFacts` 一起过 `escapeUserText`**（`knownFacts` 原来只换了换行符、没有转义，二次注入面在这里新增，所以先单独补上：W3a 第一个提交 `factLine`，候选块用同一个函数）。
  - 加动作 `{"op": "evidence", "id": "…", "src": [消息序号]}`：对话里有人再次说到、或明确确认了这条听说的事，才写；"你觉得合理"不算。**`src` 只收一个序号**（复核点出：`source()` 当时会在多行里挑"本人说的那一行"，模型可以把一句与候选无关的主人的话夹进 `src` 里，让程序把这次算成"本人说的"；`upsert_fact` / `candidate` 的 `src` 这一条路后来也由 ADR-231 收成恰好一行，见 W3 的"实现记录（ADR-231）"）。
  - **`revoke` 加 `src` 栏**（单个序号，必须是主人本人那一行，`ownerSaid`）。这样"你在聊天里说'不对'→整理撤掉 AI 提升的事实"才真的走得通；对导入 / 主人放行的事实，W2 的白名单仍然挡着。同一个提交里改提示词、解析（`plan.revoke` 由"`src` 里有任一行是主人的话"收紧成"唯一那一行是主人的话"）、版本号。
- 解析（`summary_parse.go`、`summary_scope.go`）：`evidence` 在 `plan` 里变成 `EvidenceOp{FactID, Evidence}`，由程序校验后才交给 `apply`：①`id` 必须在这一批**给它看过**的候选里（编的编号、没给它看的编号丢掉，计数 `evidence_unknown`）；②`src` 那一行必须在这一批里，且是真人的话（`origin` 为 `owner` 或 `peer`；她自己的话、别的角色、`human`、`external`、补录、自检都不算，计数 `evidence_not_human`）；③`BySubject` 由程序按"那一行的说话人是不是这条事实讲的那个人"算（身份比较，不比名字），**只在那一行本身成立才为真**；④`day` 取证据那句话的时间，不取现在，按本地时区；⑤同一 (事实, 天, 会话) 还是一次（`fact_evidence` 主键已保证）。模型输出里的 `status`、`confirmed_by`、`scope`、`written_by` 一类字段一律丢。
- **新动作要同时进两处**（复核点出）：`write.go` 的 `validate` 默认分支报"不认识的动作"，`run()` 里的 `switch` **没有 `default`**，新的 `EvidenceOp` 只加一处会被静默忽略。`evidence` 占 `maxOps = 20` 的名额，不单算（保守）。
- **用户覆盖提示词的坑**：`prompts.Store` 先读数据目录里 `config/prompts/<名字>.md`，没有才读出厂的（`internal/prompts/prompts.go`）。新文件名是 `summarize-v2`，你以前存过的 `summarize.md` 覆盖版**不会**影响它；但以后你（或界面）在 `config/prompts/` 里编辑 `summarize-v2.md`，很可能把候选块的占位符 `{{candidates}}` 删掉，新代码读到的就不含候选块，`evidence` 永远不会出现，功能默默失效。做法：启动时和每次整理前检查实际读到的整理提示词里有没有 `{{candidates}}`，没有 → W3a 整个不启用（不给候选、不认 `evidence`）、计数 `prompt_stale`、提醒一次，说清是哪个文件。

**W3b 按证据提升**

- 在 `apply` 的**同一个事务里**，记完一条证据以后检查：这条事实 `status = 'candidate'`，`kind` 在 `memory.write.confirmKinds` 里（默认 `[fact, preference]`，见下面 `promise` / `boundary` 一条和 Q4），并满足计次规则（下一条）。满足就 `UPDATE facts SET status = 'active', confirmed_by = 'ai', speech_act = …`，记一条 `confirm` 修订（`by = summary`，原因"攒够 N 次不同场合"，before / after 里有证据行数）。**范围一个字不动**：这是它和 `remember` 的 `promote` 的唯一区别——`promote` 会并上范围，这里单独一个函数 `confirmByEvidence`，不复用，也不碰 `item_scopes`。
- **计次规则**（复核后收紧，我定的，起步值）：①`fact_evidence` 里不同 (day, conversation) 的行数 ≥ `memory.write.confirmOccasions`（默认 3，ADR-160 的"2～3 次"取严的那头）；②其中至少 1 行 `by_subject = 1`（"关于某人自己的事，至少 1 次本人说"，规格-记忆-v2 4.4 第 1 条；那一条是我 2026-10-26 的建议、主人没确认过，这里照办，只比 ADR-160 严）；③**`by_subject = 0` 的行（别人转述）按说话人去重，每个说话人整个候选最多算 1 次**——"同一个陌生人隔三天各说一遍"是 1 次，不是 3 次，"一个人多天"和"几个人各投一票"得到的次数不一样；④**转述的证据只在候选本来就看得见的会话里算**：`recordEvidence` 在整理路径上带一个 `Allowed`（这个会话的 `AllowedScopes`），`by_subject = 0` 且候选对这个会话不可见的，不记（计数 `evidence_hidden`）。理由：同文查重按 (主体, 文本) 全库查、不看范围，别的会话里一个看不到这条候选的人说同一句，不该替它投票。
- **想取代旧事实的候选**：提升时读它 `add` 修订里的 `wants_supersede`（W2）。旧事实还是 `active` 且 `confirmed_by = 'ai'` → 在同一个事务里取代它并提升；旧事实受保护 → 不提升（`confirm_blocked_protected`）；旧事实已不是 `active` → 不取代，照常提升。
- **`promise` 和 `boundary` 不自动提升**（我定的，比 4.4 更严，Q4）：它们是固定要点，每轮都给、直接塑造她的行为；群友在三天里说三遍"别回复我"就让它变成有效的约定，不该。它们仍然是待确认，等你 `remember` 同文放行。做法：默认的 `confirmKinds` 里没有它们；要让它们也能自动提升，是改这个配置键（主会话 2026-11-01 定的，暂定，主人没确认：默认不含，能改），不是改代码。
- **默认只记账不动手**（我定的，Q3 一并问）：`memory.write.autoConfirm` 默认 `false`。条件满足时不改状态，只记计数 `would_confirm`（进 `memory_jobs.counts_json` 和日志）。**不往 `fact_revisions` 写**（复核点出：`fact_revisions` 是"只增不改"的历史，拿它记"如果开了会怎样"会混进历史，而且每条事实只能写一次，开关打开后已经攒够的候选不会补）。W6 的影子跑在副本上强制打开，让你在报告里看到"如果开了，会提升哪几条"。你抽检觉得行，再把它改成 `true`。
- **`autoConfirm` 由关变开时扫一遍**：打开的那次启动（以及以后每次启动，成本是一条查询）对现有候选跑同一个 `confirmByEvidence`（同一规则、每条一个事务、记 `confirm` 修订），这样报告里列的那批候选不用等各自再来一次证据，才和你看的报告对得上。
- **对 ADR-160 原话的一种读法**（我定的）：ADR-160 说"至少 2～3 次不同情况下的正面证据，**在 AI 蒸馏时都判定为通过**，才能算数"。每日蒸馏和 AI 复核（4.4 第 2 步）现在没有（第 3 步的东西）。这里的读法是：每一次证据本身就是整理模型在**另一批、另一天、另一个会话**里独立判断"这句话认真陈述了这件事、不是玩笑转述"之后写出来的（提示词原则本来就有"反讽、玩笑、假设、转述别人的话不当成事实"），所以"每次都判定为通过"已经满足；4.4 的每日复核等第 3 步有了蒸馏再叠一层。另一种读法是提升前再单独调一次模型，把条目和这几次的原话一起给它复核——更稳，每次提升多一次调用（很少发生，量小），代价是要先有"读原话"的口子；W6 的报告里会同时列出每次证据的原话，你抽检时就能判断这个读法够不够。
- **主人再说一遍**：见 W2（同文有效事实提成 `owner`）；候选被你 `remember` 同文照旧 `promote` 成 `owner`，与 AI 提升互不干扰（`confirmed_by` 已是 `owner` 的，AI 提升不会覆盖）。

| 3 个不同的 (天, 会话)，其中至少 1 次本人（`by_subject = 1`），其余要么也是本人、要么来自互不相同的说话人 | 提升 |
| 同一天、同一个会话说了 5 遍 | 算 1 次，不提升 |
| 3 次都是别人转述（`by_subject` 全 0） | 不提升 |
| 同一个别人隔三天各转述一遍（`by_subject` 全 0，同一说话人） | 1 次，不提升 |
| 1 次本人 + 同一个别人转述两天 | 本人 1 + 转述 1（同说话人只算一次）= 2 < 3，不提升 |
| 1 次本人 + 两个不同的别人各转述 | 3 次，提升（转述的会话都要看得到候选，否则不记） |
| 转述的证据来自候选看不到的会话（同文合并进来的） | 不记（`evidence_hidden`），不计次 |
| 3 次其中 1 次她自己说的 / 补录 / 自检 / 另一个角色说的 | 这些行不进证据，不算 |
| `subject = self`（她自己的事） | 证据只能来自真人的话，而真人说"你喜欢猫"不是本人说，永远不提升（收紧，不是 bug） |
| `subject = ""`（别人的事但没认出是谁） | `bySubject` 要求 `subject != ""`，永远不提升（收紧） |
| 主人在私聊里说"小明喜欢猫"（`subject` 是别人，说话人是主人） | `by_subject = 0`、同一说话人只算 1 次，永远凑不够 3 次（要小明自己也说过一次）——第一阶段只有主人的私聊，所以**别人的事不会自动提升**，要主人 `remember`（收紧，不是 bug） |
| `kind` 是 `promise` / `boundary`（默认配置下不在 `confirmKinds` 里） | 不提升，等主人 |
| 已经 `revoked` / `rejected` / `superseded` | 不提升（只动 `candidate`） |
| 证据来自 3 个不同的群 | 3 次（会话不同）；范围按 `merge` 本来的规矩：本人说的并上、转述的不动——提升不再多并 |
| 证据对应的消息整理之后被撤回了 | 证据行仍然算数（`EventSource.Revoked` 目前没人用来降级）；已知的坑，见下 |
| `autoConfirm = false` | 不改状态，只记 `would_confirm` 计数 |
| 同一批里模型对同一条写了两次 `evidence` | 一次 |
| 事务内与别的会话并发提升同一条 | 第二个看到已经是 `active` 就不动（事务内重读状态；扩 `TestSupersedeRechecksStateInTheTransaction` 的写法） |
| 候选带 `wants_supersede`，旧事实受保护 | 不提升（`confirm_blocked_protected`） |

**具体参数**：`confirmOccasions` 3（实现里最少按 2）；`confirmKinds` `[fact, preference]`；候选块 20 条；`autoConfirm` false；`SummaryVersion` 2；`maxOps` 20（`evidence` 同占）。

**禁止的偷懒写法**：用向量相似度并候选；信模型给的状态、编号、`by_subject`；`evidence` 的 `src` 收多个序号；提升时复用 `promote`（会并范围）；候选块里显示"已有几次"；候选块和 `knownFacts` 不转义；把提升放在读路径（召回里）或定时任务里而不是写事务里（两个会话同时提升会各算各的）；提示词改了解析没改（反之亦然）；`validate` 和 `run` 只改一处；`promise` / `boundary` 顺手也提升；dry 模式下偷偷改状态；用 `fact_revisions` 记 `would_confirm`。

**已知的坑**

- 两条互相矛盾的说法各自攒到 3 次，会出现两条都有效的矛盾事实。W3 不解决（那是 `dispute` / 蒸馏的事，第 3 步），但"新候选明确想取代旧事实"的那一种已经由 `wants_supersede` 处理；W6 的报告里单列"同一主体同时有效的相似事实对"给你看。
- 模型把"相关但不是同一件事"的话当成证据（`evidence` 的精度）——精度要在影子里量：报告里每条证据附原话，你抽检"这句话真的支持那条事实吗"；如果量出无关证据不少，再加"证据那行与候选的嵌入相似度 ≥ 门槛才算"（起草时不设，没有数据支撑）。
- **候选块只放最近 20 条的后果**：从 Bun 导入的待确认（2026-10-25 的副本上铃音库约 180 条，范围多是 `owner`，当前以导入核对为准）很快会被开写以后 Go 新写的候选挤出前 20，之后模型再也看不到它们，也就永远攒不到证据，它们会一直以"听说"的身份每轮最多出 1 条。这不一定要改（它们本来就旧、也没人再提），但影子报告里"为什么旧的那堆一条都没提升"会被问到，所以 W6 的报告 C 节单列一行"导入的待确认：共几条、几条在候选块里能被看到"。真要让旧的也有机会，是把候选块改成按相关度挑而不是按时间（需要本批文字的向量，W3 不做）。
- 提升后进了 `knownFacts`（有效的才给模型看），之后整理能取代它——这正是 `confirmed_by = 'ai'` 要的行为，但取代要靠新候选自己攒够证据（W2）。
- 提升改变的是召回里的呈现：待确认每轮最多 1 条、标"听说"；有效的照常给（规格-记忆-v2 4.4）。守卫早就把 `fact` + `candidate` 都当禁看集合（`outbound.go` 的 `CanSee` 分支），所以提升不改变守卫看的集合。
- 边界 ⑬（并发的具体交错）：两个会话几乎同时给同一条候选记第 3 次证据——事务内记证据后**重新数**行数再决定，不用事务外的计数。
- 整理之后被撤回的消息，证据行不降级：先记在这里，量不出问题就不改；真要改是 `EventSource.Revoked` 接进证据的读路径。
- 同文合并按 (主体, 文本) 全库查重、不看范围，这是已有行为；本步只管"证据是否计次"，不改它。

**实现记录（ADR-231，2026-11-02，分支 `night/memory`，没合 main）**

主人 2026-11-02 选的是“只认恰好一句当事人的话”（“先这样吧 后续看有问题再说”）。整理的 `upsert_fact`、`candidate` 现在和 `evidence`、`revoke` 一个口径：

- **谁算本人说的**：`source()`（`summary_scope.go`，`fact()` 是唯一调用方）只有在 `src` 恰好引用一行、并且那一行是当事人说的，才把这条算 `BySubject`。两行以上一律不算，哪怕每一行都是当事人说的。当事人按 `ActorKind` / `ActorID` 认，不比名字，群名片叫“主人”的群友不算。
- **同一个序号写两遍也是两行，不去重**：`parseSrc` 把去重前写了几个带出来（`sumOp.srcN`），`source()` 用它判“恰好一行”；存进 `source_seqs` 的仍是去重后的，和以前一样。这里比 `revoke`、`evidence` 紧（它们的 `[5,5]` 去重后算一个，旧测试不变）。
- **不算本人说的时**：事实照样写，走原来“不是本人说的”那条路：证据记成转述（`fact_evidence.by_subject = 0`），`attributed_to` 写证据那一句的说话人；它不能当“当事人自己说过”的那一票，也不能把新的范围并进已有的同文事实。
- **多行时证据挑哪一句**：不再“本人说的优先”，取第一句人话（`origin` 是 `owner` / `peer`，她自己的、系统的行跳过），证据的 `origin`、发生时间也跟着这一句。原因：多行时本人那一行已经不能给整条背书，再让它决定挑哪一句，等于旧办法的后门开了一半。代价：当事人在后、别人在前的两行，`attributed_to` 写前面那个人。
- **提示词**：`summarize-v2.md` 里 `src` 的说明（1～3 个序号）不改；提示词等做 A/B 时再跟着改，现在模型写多行只会多记成转述（待办“整理 `src` 的提示词说明要跟着 ADR-231 改”挂着）。
- **边界**：这一层挡得住模型把无关的一句当事人的话夹进 `src`，挡不住有意只引一行当事人的话（比如只引一个“对”），信任边界不变（ADR-231 第 4 条）。

### W4：只读期的 remember——她怎么说才不误导

**现状**：`remember` 在主人的私聊里挂着（`memplugin/plugin.go` 的 `Setup`），只读时 `Remember` 返回的是 `ErrNotWritable`，被工具层的通用分支转成"记忆这边出了点问题，这次没记上，过一会儿再说一次"（`toolErrorText`）。"过一会儿再说"是假的：只读期说多少次都记不上。

### W5：写入开关（两个）和开之前的检查

**两个开关**（Q7，我定的，推荐）：`remember`（主人在私聊里让她记，不调模型，只写范围 `owner`）比后台整理（调后台模型、把聊天变成候选）安全得多，所以拆开：`memory.write.characters` 里的角色 `remember` 就可写；其中再列进 `memory.write.summarize` 的才做后台整理。两个都默认空 = 全部只读。这和"检查不过就保持只读、不部分打开"不矛盾：那条说的是**前提不满足时**不许退到半开；这里是你**明确配置**的两档：前提 1～3（名单、路径、迁移）或开写前的备份不满足时两档都不开；整理自己的前提（前提 5：后台模型、`catchUp`）或开整理前的备份不满足时只关整理，`remember` 照开。好处：先只开 `remember`，立刻消掉 W4 的"如实说记不了"，也给后面的影子抽检留时间。另一种是不拆、一个开关全开，主人的话是"那专门开工作流把写入做好"，没有逐项表态。

**已知的坑**：边界 ⑫（运行环境是输入的一部分）——数据目录、备份目录都是环境，检查要读真实路径，测试用 `t.TempDir()`；边界 ⑩——开到一半失败要能看出"哪一步没过"，所以每条前提一个原因码；边界 ⑭（更新不可能总是原子完成）——备份成功、打开失败时库没改，下次启动看到同指纹备份就跳过；边界 ④——关闭流程里排程已有先停后关库的顺序（13.2.5），开关打开后关闭流程要在真库上再走一遍；`SkipPlace` 不动游标的代价是别人的私聊每来一条都读一次事件，量小，计数里看得出。

**已知的坑之一（已由 ADR-231 定为恰好一行，实现在本分支）：整理的 `src` 写多行时，一句无关的当事人的话让整条算“本人说的”。**2026-11-02 复核时发现：整理的 `upsert_fact` / `candidate` 的 `src` 提示词允许写 1～3 个序号（解析上限 `maxSrc` 是 10），`source()`（`summary_scope.go`）原来在多行里只要有一行是当事人说的，整条就算 `BySubject`，别人转述的事实里夹一句和内容无关的当事人的话，就被当成本人说的；它决定三件事：证据算不算本人说的（W3b 要至少 1 次）、`attributed_to` 记不记、同文合并时范围并不并（`scopes_widened`）。主人 2026-11-02 在两种收紧办法里选了“只认恰好一行当事人的话”（“先这样吧 后续看有问题再说”），写成 ADR-231：`upsert_fact` / `candidate` 和 `evidence`、`revoke` 一个口径，做法、四种场合的表和测试见 W3 的“实现记录（ADR-231）”。`evidence`、`revoke` 的“恰好一个序号”检查在 `summary_scope.go`（`plan.revoke`、`plan.evidence`），不在 `summary_parse.go`（那边只读出序号、去重）。提示词 `summarize-v2.md` 里 `src` 的说明（1～3 个序号）这次没改：提示词等做 A/B 时再跟着改，现在模型写多行只会多记成转述。默认 `places` 只有 `owner-private`，主人的私聊里没有群友，不会多出冒充的风险，但这条在默认场合也改结果：主人自己连着说的两三句被一起引用时，从本人说的改记成转述（细节见 W3 实现记录里的“对默认配置的真实影响”，ADR-231 第 3 条“几乎不改结果”的说法不准）；放开群场合以后，别人借当事人一句话变成本人说的这条路才真正被堵上。

**已知的坑（同上）之二：止血隔离管不到“线之后整理把新范围并进线之前的事实”。**隔离只看创建时间和提升时间（`quarantine.go` 的 `quarantined`）；线之前创建的事实，被线之后的整理同文合并、本人说的时候把范围并上去（`write.go` 的 `merge`，往 `item_scopes` 加行，main 上就有），不在隔离范围里，应急时这一种写入撤不掉。这次合并在 `fact_revisions` 里留了一条 `op = scopes` 的修订（带前后范围和时间），以后可以按它撤回线之后并入的范围；现在是已知限制。

### W6：影子整理工具

**是什么**：`native/cmd/memory-shadow`。在**副本**上把真实的整理跑一遍，出报告给你抽检。它和规格-记忆-v2 13.2.1 的"不做影子写"不冲突——那条说的是"Go 不在 Bun 还在写的真库上影子写"；这里全程只碰 `-work` 目录里的副本，真库只在拷贝那一段被读。

**技术路线**

1. **拷**：把指定数据目录里的 Go 聊天库组（每个平台的库、`trace.db`，含 `-wal` / `-shm`）和该角色的记忆库（`go/characters/<id>/memory.db` + `memory-v2.db`）拷到 `-work` 目录。源路径先过 W5 的 `paths.CheckMemoryPath`（不拷 Bun 原库）。照 `memory-eval` 拷库的写法；拷完对副本 `PRAGMA integrity_check`，不过就重拷。**拷之前先拿数据锁**：`datalock.LockExisting(<数据目录>)`（只读诊断用的那个，不会为了拿锁去建文件），被别人拿着（桌面程序或 Go 后台在跑）就拒绝启动并提示"先退出桌面程序"。这样拷到的是静止的库（没有后台一边收消息一边写 WAL 的半截状态），也让"重活一次只跑一样"成立。
   - **锁只持到拷完并核对完副本**（前后指纹一致、记忆库和 `-wal` 与源逐字节相同、副本 `integrity_check` 通过才放；指纹对不上或 `integrity_check` 不过要重拷，锁一直拿着。复核点出起草时自相矛盾：一边说"锁持到拷完"，一边说"跑完再记一次指纹、因为持着锁后台不可能在写"；真跑几小时，锁拷完就放则指纹必然变，整个真跑都持锁则桌面程序和 QQ 接管几小时起不来）。所以工具**只证明"拷贝那一刻的一致"**：记忆库算 SHA-256、聊天库只记大小和修改时间，拷贝前后各记一次，不一致就把这次标成"无效"重拷；**不声称"全程没动"**。"拷完不再碰原库"用测试证明（见下第 7 点），不靠指纹。拷贝期间后台是退出的，工具在开始前就打印这一点和拷贝耗时（聊天库很大时拷贝时间就是 QQ 空档；是否改成 SQLite 在线备份、不抢独占锁，待核聊天库大小）。
2. **`-work` 的位置**：必须在 `<数据目录>/dev/` 下，**并且 `git check-ignore` 命中**（工具自己调一次）；在数据目录的 `go/`、`characters/`、`shared/` 里面、或者就是它们的父目录、或者不被 git 忽略 → 报错退出。理由（隐私复核点出）：一个相对路径的 `-work ./x` 会把整套聊天库副本和报告放进仓库工作树，隐私钩子只扫暂存的新增行里的名字和号码，扫不出聊天正文。默认 `<数据目录>/dev/memory-shadow/<时间>/`。启动时先清掉上次崩溃遗留的副本目录（只清这个前缀下、带本工具标记文件的）。
3. **游标**：**默认用副本里的真实游标**（导入搬过来的游标 + 只读期新来的，`-cursors real`），所以影子跑出来的就是"开后台整理的第一刻真会处理的那一段"（复核点出：起草时"种游标"是另造的窗口，验的不是真开时走的那条路）。可选 `-cursors seed -last <N 天>` / `-since <日期>` 给提示词 A/B 用：副本上直接用 SQL 给每个会话写 `summary_state.last_seq` = 窗口起点前一条；这种模式在报告里大字写"不是真实游标"。`ReopenSummary` 只处理"停了的会话"，不能种游标。
4. **开**：`memory.Migrate`（副本；导入来的是空操作）→ `memory.Open(Writable: true, SummarizeEnabled: true, Events: memsource.NewMulti(副本的 store, 角色), Gen, Prompts, Embedder)`。`Gen`：`-gen fake`（固定回复，测试和估算）、`-gen real`（走真实的网关和后台模型，花钱）。嵌入：可选；不配就只有全文，向量那部分在报告里写"没算"。
