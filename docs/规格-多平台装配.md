# 规格：多平台装配（接第二个平台之前把写死 QQ 的三处理顺）

> 状态：2026-11-01 起草。三步都在 2026-11-01 做完：第 1 步准入按渠道分发、第 2 步平台登记统一、第 3 步装配单元（主人："现在做也行，比如Telegram"；接 Telegram 本身是另一件事，没做）。
>
> 依据：主人 2026-10-31："1-3、5都可以修复"。来源是研究铃音的架构审查第 1～3 条，逐条核实后定 P2，不是接第二个平台前的阻塞，见 审查-架构与模块结构（私有存档）。方向：ADR-177（平台各自独立，QQ 只是插件）、ADR-199（每个平台一个库文件）、ADR-197（只切 QQ 小号）。

## 一、要解决什么、不做什么

现在的 Go 后台底下（Roster、Outlet、Intake、Pipeline、按平台分库的 Set）已经按渠道建模，写死 QQ 的只在三处：

1. **准入**（`internal/app/channel.go` 的 `admit`、`admitNotice`、`stranger`、`dispatch`）：对任何渠道都按 QQ 的白名单和 `Resolve("qq", …)` 判。
2. **平台登记**（`internal/store`）：`PlatformOf` 的登记、`OpenGoReadOnly` 固定开 `local` 和 `qq`、`ReadDisplayConversations` 只有这两种分支，各写各的。
3. **装配**（`internal/app`）：`App` 只有一个 `*snowluma.Adapter`，`openChannel` 直接建 QQ 的适配器。

不做：第二个平台本身；多个 QQ 小号（另一条待办）；插件统一（GitHub issue #16）；审查第 4、6 条。

## 二、不能变的

- **QQ 的行为一字不变。** 四种场合的准入和可见范围、发送的七个条件和默认钳制、复读和戳回去、关机顺序、`Open` 失败时的清理顺序都不变。现有测试只加不改：要改一条现有断言，就说明改动碰了 QQ 的行为，停下重想。
- **认不出的渠道一律拒。** 这是现状，不是新默认：`Intake.check` 先拒没登记的号（`intake.go:244`），`PlatformOf` 拒没登记的渠道，`dispatch` 对未知渠道只记日志。本规格只把它钉进测试，并在准入这一层再加一道"没登记就丢"。
- 不在运行时开放注册：平台和渠道的登记只在代码里一处写死，测试可以自己造一份传进去，生产代码没有往全局表里加东西的口子。

## 三、三步（每步单独提交、单独合进 main、能单独撤）

### 第 1 步：准入按渠道分发（审查第 2 条）

- **技术路线**：`app` 里按渠道名查一张策略表，每项有 `admit`、`admitNotice`、`dispatch` 三个函数。`"qq"` 这一项就是现在的四个函数改名（`qqAdmit`、`qqAdmitNotice`、`qqDispatch`，`stranger` 在 QQ 策略里照旧用 `"qq"`），行为不变，包括 ADR-221 第 4 条的"做事的人没说是谁就按会话对方认"。查不到策略的渠道：消息和通知都返回 `Admission{Drop: true}` 并记一条日志；`dispatch` 记日志、不往下走。
- **禁止的偷懒写法**：查不到就落回 QQ 的策略；查不到返回空的 `Admission{}`（空的就是放行）；在通用层留着写死的 `"qq"` 字符串。
- **已知的坑**：被踢下线的通知没有会话、渠道名是空的，查表会把它丢掉，所以"被踢下线照收"留在查表前面（2026-11-01 动手时发现，测试钉住）。端到端发一帧到不了 `admit`（`Intake.check` 先拒了没登记的号），所以验收用直接调 `admit`、`admitNotice` 的单元测试，形状照 `admit_notice_test.go`。
- **验收**：虚构渠道 `fakeplat` 的群消息、私聊消息、群通知、私聊通知四种都是 Drop；QQ 的现有测试全部原样通过；改坏检查：去掉"查不到就 Drop"、改成落回 QQ 策略，各红一次。

### 第 2 步：平台登记统一（审查第 3 条）

- **技术路线**：`store` 里把登记做成一个值 `Registry`：有序的平台列表，每项是渠道名、平台名（库文件名）、只读打开时是不是必须有。`DefaultRegistry` 只有 `console → local` 和 `qq → qq`，都是必须有。`NewRegistry` 校验：渠道名不能空、平台名过 `ValidPlatform`、渠道和平台都不能重复。`Set` 带着打开它时用的那份登记，`For`、`ForConversation` 读它；包级的 `PlatformOf`、`PlatformOfConversation` 照旧读 `DefaultRegistry`（导入 Bun 历史那一路只有这两个平台，不改）。新增 `OpenGoWith(p, reg)` 打开登记里的全部平台；`OpenGo(p, 平台…)` 照旧，渠道对照用默认登记。新增 `OpenGoReadOnlyWith(ctx, p, reg)`：必须有的缺了照旧报错，其余登记过但文件不存在的跳过；`OpenGoReadOnly` 等于用默认登记调它。
- **桌面这边不改**（动手前核过）：按会话取历史的校验（`validateDisplay`）、会话列表（`ReadDisplayConversations`）、`desktopread` 的 `keyOf` 都只认 `local`、`qq`，对没写过显示规矩的平台本来就是收紧的：会话列表一条不列，按会话取历史报 `ErrDisplayScope`。新平台要显示时再写它自己的规矩（QQ 那段按角色和可见范围过滤，是"谁能看什么"的收紧逻辑，不能直接套）。这一步只加测试把这个现状钉住。
- **禁止的偷懒写法**：做成运行时能往里加东西的全局 map；会话列表、历史校验对认不出的平台落回 QQ 的规矩。
- **已知的坑**：`OpenGoReadOnly` 原来缺一个库就整体报错，登记了新平台以后，老用户没有那个库会打不开历史，所以只有"必须有"的缺了才报错。保留"`telegram` 没登记就拒"的测试（它查的是默认登记）。零值的 `Registry` 什么都没登记，用它查渠道一律报错，不会落到哪个库。
- **验收**：用一份带虚构平台 `fakeplat` 的登记打开 Set：建出它的库、`For("fakeplat")` 拿得到、事件写得进去，桌面会话列表里没有它、按会话取它的历史被拒；包级的 `PlatformOf("fakeplat")` 照旧报错；只读打开时它的库在就开、不在就跳过，缺了 `qq` 照旧报错；`NewRegistry` 拒重复和非法名字；默认登记下的现有测试全部原样通过。

### 第 3 步：装配单元（审查第 1 条）

- **技术路线**：`App` 里的单个 `adapter *snowluma.Adapter` 换成按渠道的装配单元列表，每个单元有渠道名、适配器、账号、第 1 步的策略、启动和停止。`Roster`、`Outlet`、`Gate` 仍然全局一份：`Roster` 的校验拒绝同一个号绑两个角色、拒绝重复账号，`Outlet` 拒绝同一个渠道两个适配器，拆成每渠道一份会丢掉这些校验。`sendLock`、`modeOf`、`limitQQPoke`、`qqPrivateReplyOK` 留在 QQ 单元里。`Options.Account` 仍是一个号。`openChannel` 照旧只建 QQ 这一个单元；打开的平台库从各单元的渠道经第 2 步的登记表算出来。`a.adapter` 留着指 QQ 那一项的适配器（发送门要看它就绪没有，现有测试也直接用它）。测试多装渠道走 `Options.ExtraChannels`（和 `NewEmbed`、`LinkFetcher` 一样只供测试），三个函数缺一个 `Open` 就报错。每个单元有自己的接收端，只认自己的号；连上以后清的是自己渠道的通道门，QQ 的日志文字不变。
- **具体参数（不能动的顺序）**：正常关机照 `shutdown` 现在的步骤：停适配器 → 关入口 → 取消内核并等审批落库 → 压缩和记忆插件收尾 → 关出口 → 交还发送锁 → 关记忆、库、提醒。`Open` 中途失败照 `cleanup` 现在的顺序。有多个单元时，"停适配器"一步停全部单元，其余步骤不变。
- **禁止的偷懒写法**：每个渠道各建一套 Gate、Outlet、Roster；借这次改动顺手挪动、重排和这件事无关的代码（界面那条线也在改 `app.go`，ADR-220，diff 只动必须动的行）。
- **复核发现、当场改了的**（2026-11-01）：① QQ 以外的平台渠道没有自己的发送规矩，出口里又有了它的适配器，私聊默认档位是说话，会绕过 QQ 那套七个条件直接发——改成除了 QQ 和本地，一律只记录、不发；② 关机第 1 步原来无限等所有适配器，一个不认取消的适配器会把交还发送锁、关库一起拖住——改成最多等到关机时限；③ 多装渠道的适配器名要和渠道名一样，库路径也过"不许落在 Bun 目录"的检查。留着没改的：被踢下线的通知没有渠道名，按号在名册里找账号，两个渠道同号时分不清（名册原来的设计，接第二个平台时再看）。
- **已知的坑**：`modeOf` 是链、闸门、出口、回合共用的唯一一份有效档位，`takeSendLock` 的默认钳制、`checkQQSend`、`guardFor` 都和出口、复读的配置绑在一起；搬进 QQ 单元时保持"默认钳制，拿不到发送权就保持 0，撤掉检查或听众不能摘钳制"的先后（`channel.go` 第 81～85 行的注释）。动手前先 `git fetch`，看界面那条线有没有在 `internal/app` 上分叉。
- **验收**：一条 app 测试把 `channel/fake` 当作第二个渠道和 QQ 一起装上（给它一份最小的策略和第 2 步的虚构平台登记），它收到的一帧落进它自己的平台库、QQ 库里没有；QQ 的全部现有测试原样通过；关机后两个适配器都停了。改坏检查：只停第一个单元 → 红；第二个单元的帧落进 QQ 库 → 红。

## 四、提交和合并

每一步：只跑相关包写代码 → `bun scripts/go-affected.ts <文件>` 挑包 → `go vet`、`go test` 退出码 0 → 单独一个提交合进 main，挑了几个包、结果写进说明 → 推送 → 当天把本规格开头的状态和待办改成真实进度。第 3 步动 `internal/app` 前先看第 1、2 步有没有被界面线的改动冲到。
