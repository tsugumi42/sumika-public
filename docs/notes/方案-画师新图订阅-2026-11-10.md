## 结论先行

1. **结构**：插件只做“发现新作品”，其余全复用。发现（每个账号的最近作品列表，新写）→ 取详情（link-reader 现成）→ 去重（新写）→ 排版（沿用链接解析的模板）→ 发送（`Outlet.Send`，来源 `automation:artist-feed`）。轮询**不调模型**，不走 /loop（/loop 是每次开一轮对话，烧 token、不合适）。
2. **取数路子**：
   - 推特：第一档用 FX 的 `/2/profile/<账号>/statuses`（匿名，旧实测 39 个账号里 30 个返回了内容，有的账号会空或 404，所以不保证）。**RSSHub 的推特路由现在必须配凭据**（登录网页版的 `auth_token` cookie，或付费开发者 API 的 key），等于把“要账号”从 Sumika 挪到了 RSSHub，没有好处，不推荐。要登录态时直接走 mygo WebView 兜底。
   - Pixiv：匿名网页接口 `ajax/user/<uid>/profile/all` 拿作品号，再用现成的单作品取数（[未验证]，先探）。R18 作品匿名看不到，会被跳过。RSSHub 的 Pixiv 路由要 `PIXIV_REFRESHTOKEN`，不推荐。
   - Bluesky：公共 AppView 的 `getAuthorFeed`，无需任何凭据，最省心。
   - B 站：匿名主页动态接口 10-30 实测被 412 风控，要 cookie 或签名；排在后面，不抢第一批。
   - 小红书匿名取不到（规格-链接解析 4.16），不做。
3. **去重**：两层。先按“平台 + 作品号”去重（精确）；再按图片感知哈希跨平台去重（pHash 64 位 + 更细的 dHash 256 位两个都近才算同一张，宽高比也要接近，只和同一画师最近 30 天比）。**关键风险是差分图**（同一画师发表情差分，哈希几乎一样），所以不能只用 64 位 pHash。哈希库推荐自己写约 100 行（用已有依赖 `golang.org/x/image`），不引 goimagehash（最后更新 2024-01、依赖 2018 年的 nfnt/resize）。
4. **频率**：每个账号默认 30 分钟查一次，所有账号串行、请求间隔 2 秒以上并加抖动，遇到 412/429/Cloudflare 挑战页就把这个平台整体退避，不硬刷。首次关注只记基线，不补发历史。
5. **第一步**：先花半天做“探针”（对主人真实的关注名单，每个平台各查几次，确认三个列表接口能匿名返回），然后做 X + Pixiv + Bluesky 的发现层和不含哈希的最小闭环（先写后发、按作品号去重），发到一个测试群或主人自己的 QQ 私聊，就能天天用。去重、插件页、B 站、WebView 依次往后。
6. **要主人拍板的点**见最后一节。

## 一、每个平台怎么拿“某账号最近的新作品”

### 1.1 推特 / X

| 路子 | 要什么凭据 | 现状 |
|---|---|---|
| FX 第三方 `api.fxtwitter.com/2/profile/<账号>/statuses` | 无 | [实测] 10-30 查 39 个机构账号第一页：30 个非空、共 582 项（含转推）；SpaceX、Reuters 当次空/404，不解释成账号不存在。列表项带作者、媒体（`media.all` 有序）、`quote`。第三方服务，挂了/改版/限流都不由我们控制 |
| 官方 syndication、oEmbed | 无 | [实测] 只能取单条，不是账号时间线 |
| RSSHub `/twitter/user/:id` | 见下 | 见下 |
| mygo WebView（登录态） | 主人自己在窗口里登录 | 见 1.1.2，兜底 |

#### 1.1.1 RSSHub 的推特路由到底要什么

[读码] `lib/routes/twitter/api/index.ts`：有 `TWITTER_THIRD_PARTY_API` 或 `TWITTER_AUTH_TOKEN` 就走网页接口（web-api），否则有 `TWITTER_CONSUMER_KEY`/`SECRET` 就走开发者 API，三者都没有时直接抛 `ConfigNotFoundError: Twitter API is not configured`。`user.ts` 的 `requireConfig` 列的也是这几项。命名空间说明页写明：推荐方式是配置“已登录的推特网页版 `auth_token` cookie”（可逗号分隔多个）；用户名密码登录的方式已被注释掉；开发者 API 是“Pay-Per-Use”（按用量付费）。

- 自建：要装 Node 或 Docker，再填一个真实账号的 `auth_token`。**这个账号 cookie 还是要主人给**，只是填进 RSSHub 而不是 Sumika，多了一个要维护的进程，并没有绕开。
- 公共实例（rsshub.app 等）：[未验证] 官方指南页只说“可以换成自建或任意公共实例”，没写公共实例对推特的限制。推特路由需要实例主人配凭据，公共实例是否配、会不会限流，我没法确认；就算能用，也等于把关注名单交给第三方，并且是靠别人的账号在抓，随时可能失效。不推荐。
- 通用限流：自建的 RSSHub 对出站请求有全局每秒 10 个的上限、可按主机配 `REQUEST_RATE_LIMITS`；路由缓存默认 5 分钟[文档]。
- 结论：推特不走 RSSHub。FX 匿名为第一档；FX 对某个账号拿不到时才用 WebView 兜底（或者提示主人“这个账号需要登录态”）。

#### 1.1.2 WebView 兜底（最后一档）

- 能不能挂：[读码] mygo v0.8.3 有 WebView 窗口的 `Page`：`LoadURL`、`Eval(code)`（在页面里跑 JS 并取回结果）、`OnDidFinishLoad`、`OnWillNavigate`、`SetAuthHandler`（只管 HTTP 认证，不管网站登录）等。Windows 用系统 WebView2。我没看到现成的 Cookie 读写接口，但 `Eval` 在页内跑 `fetch`，请求会自带页面的登录态，不需要把 cookie 拿出来。
- 怎么拿登录态：主人自己在这个窗口里打开 x.com 登录一次（密码只输进网页，我们的代码不接触）；之后后台每次到点，在隐藏/最小化的窗口里 `LoadURL` 账号主页，等 `OnDidFinishLoad`，用 `Eval` 取页面里已渲染的推文列表（或页内 `fetch` 网页版接口）。[推断] 读已渲染的页面比调用推特的内部 GraphQL 稳，不用管签名参数（RSSHub 里有一整套 `client-transaction-id`、`gql-id-resolver`，可见内部接口的签名有多麻烦）。
- [未验证]：登录态是否跨重启保留（取决于 WebView2 用户数据目录怎么放，要查 mygo 有没有设）；无窗口/后台运行时 WebView2 是否正常；每个账号页加载要多少秒；主人的 Edge/Chrome 登录态不能直接借用（浏览器数据加密，且我们不去碰）。
- 代价：多几个 WebView2 进程（2026-10-23 原型里 WebView 版图表多出约 6 个进程、360 到 390 MB，ADR 里当时主人的态度是“那一堆进程处理掉吧”）；内存主人说不算成本，但这是常驻后台。建议**只在需要时拉起，查完就关**。
- 风险：用主人自己的账号做自动化访问，推特可能限制或封号。主人已表示自己承担，提一次，不重复。频率给得更低（兜底档默认 2 小时一次，最少 1 小时）。
- 位置：做成发现层的一个“适配器”，和 FX 适配器同接口，主人在插件页给某个账号选“取数方式：自动 / 只用 WebView”。

## 二、去重

### 2.1 目标和难点

同一张图出现在 X、Pixiv、Bluesky，尺寸和压缩不同（比如推特 `name=orig` 与 Pixiv 原图在像素、JPEG 质量、有无元数据上不同）。要把它们认成同一张，同时不把**差分图**（同一构图、只改了表情或小物件）误认成同一张。

### 2.2 做法

1. 精确层：`(平台, 作品号)` 唯一。同一作品被重复列出（置顶、转推、翻页重叠）一律丢弃。
2. 感知哈希层，对每张图计算并存两个哈希：
   - pHash 64 位（缩到 32×32、灰度、DCT、取左上 8×8、按中位数二值化）。耐缩放、JPEG 重压缩、轻微调色。
   - dHash 256 位（9×… 的更细网格或 16×16 差分）作为“细节哈希”，用来分辨差分图。
   - 两个都近才算同一张：初始值 pHash 汉明距离 ≤ 6 **且** 细节哈希的归一化距离在一个更严的门限内；宽高比差 ≤ 3%。
3. 阈值怎么定：**不拍脑袋**。文献和常见实现里 64 位 pHash 的“相似”门限多取 ≤ 10 左右、“几乎相同”取 ≤ 5 左右（[推断] 凭通用经验，具体数字以后以样本为准）。办法：收集主人真实关注画师的样本——同图跨平台对（应判同）、同画师的差分图对（应判不同）、完全不相关的对——写一个小对拍程序画出距离分布，选两类之间的间隙。门限做成配置项，默认保守（宁可多发一张，不要漏掉新图）。
4. 只和“同一画师（绑定的所有账号）最近 30 天的图”比。画师条目可以绑多个平台账号，这是跨平台比较的前提；不同画师之间不互比。数量级是每人几十到几百张，线性扫描足够，不需要 BK 树。
5. 谁留谁丢：先到先发，后到的标为重复并记日志（可选在插件页显示“被判为重复：X 的这条 = Pixiv 的那条”，方便主人发现误判）。不做“等更高画质版本再发”，那会拖延。
6. 多图帖子：逐张算哈希。规则：该帖所有图都命中已发的图 → 整帖跳过；有一部分是新图 → 整帖照发（简单），可选“只发新图”开关，默认关。不命中任何旧图 → 当新作。
7. 视频、动图（ugoira、GIF）：不做图片哈希，只靠作品号；取不到图的帖（纯文字）不发（画师订阅默认只要带图的）。
8. 误判兜底：宁可重复也别漏。门限边缘（疑似区间）的处理做成选项：默认“照发并在日志里标疑似重复”。

### 2.3 哈希从哪来

发送本来就要下载图（要进受管理的媒体资源，见规格-链接自动展开第六节），哈希在下载后顺手算，不额外取一次图。解码耗时以每张几十毫秒量级估计（[推断]），放后台，不卡界面。

|---|---|---|---|---|
| [corona10/goimagehash](https://github.com/corona10/goimagehash) | BSD-2-Clause | 843 | 2024-01-21（最新版 v1.1.0） | 有 AverageHash、DifferenceHash、PerceptionHash、可调尺寸的 Ext 版本；依赖 `nfnt/resize`（2018 年版本，已停更）。两年没动，但算法固定、够用 |

### 2.5 存哪

新建一个小库（见第六节“存储”）的 `images` 表：`(artist_id, platform, post_id, idx, phash BLOB(8), dhash BLOB(32), width, height, seen_at)`，按 `(artist_id, seen_at)` 建索引，查询时取该画师近 30 天的行到内存比。哈希是从图片算出来的派生数据，不含图本身，也不进 git。

## 三、频率和调度

- 调度器：插件自带一个轻量定时器（启动随后台起停），不走 /loop。/loop 每次开一轮模型对话，这里不需要模型；参考“主动联系”的“导演不调模型，只决定什么时候醒”。可复用 `loop.Schedule` 的校验和“下一个钟点”算法，如果以后要做“每天某时汇总一次”的模式。
- 默认间隔：每个账号 30 分钟；插件页可改，下限 10 分钟（兜底 WebView 下限 1 小时）。[推断] 画师发图一天几次，30 分钟延迟可以接受；想更快的人是少数。
- 自适应（可后做）：最近 7 天没发过新作的账号降到 2 小时一次；刚发过的保持原间隔。
- 请求礼貌：全部账号串行；同一平台两次请求之间至少 2 秒，加上 ±20% 抖动（旧实测就是 2.1 秒间隔，122 次没触发限流）；各账号的起点错开，不在整点同时开查。
- 平台级退避：任一请求返回 412/429/403 挑战页，把该**平台**整体暂停，从 1 小时起指数退避、上限 24 小时，插件页显示“X 暂停到 xx:xx（原因）”；不换出口、不补 cookie 硬闯（沿用旧笔记的“遇 412/429 停那个平台”）。恢复后先查一个账号试探。
- 失败不刷屏：连续失败的账号在插件页标红并记日志，只在状态**变化**时（正常→失败、失败→恢复）通知主人，不每轮发。
- 睡眠/离线：程序没开着错过的轮次不补跑，启动后各账号查一次（沿用定期任务的做法）；这时新作按发布时间顺序发。
- 一次最多发几个：每个账号每轮最多 3 个新作品，超出的合成一条“还有 N 条未发，点开画师页看”；每个目标会话 5 分钟内最多 5 条，避免刷屏和 QQ 风控（风控主人清楚，这里只是节流）。

### 首次关注怎么处理历史（不刷屏）

- 新增账号后立刻做一次“静默基线”：取最近一页作品，**全部标记为已见、不发送**，同时算哈希入库（这样后面别的平台发同一张也能去重）。
- 只发“发布时间晚于加入时间”的作品；置顶、旧帖被抬出来也按发布时间挡掉。
- 插件页给两个按钮：“试发最新 1 条到这里”（发到主人自己指定的测试会话，用于确认格式和连通性，不算正式推送）、“补发最近 N 条”（默认不勾，N 最大 5）。

## 四、发到哪

- 插件**保持中立**：只管“关注列表 → 发到哪些会话”，不加内容过滤。能不能往某个群/私聊发，由主人在“在哪里用”里自己配（沿用插件页“平台 + 四种场合 + 只在这些/除了这些”的控件）。
- 发送走 `Outlet.Send`，来源填 `automation:artist-feed`（[读码] `outlet.go:311-321` 只允许 `character` 和 `automation:<插件名>`）。出口本身有账号绑定、最新政策、先写后发和三态收尾，不绕开。
- 发送格式：复用链接解析的排版——对一个新作品等价于“取到这条链接的详情，按主人选的样式（卡片 / 图文 / 混合，规格-链接页面类型和样式）排版”。在标题行前加一行画师名和平台，例如“某某 · Pixiv · 新作”。多图沿用 link-reader 的图数限制规则。
- 一个要先核实的接口：[未读码确认] `linkexpand` 现在的数据流是“实时消息入库 → 提链 → 取数 → 排版 → 出口”，入口是入站消息。新插件需要从“一条链接 + 目标会话”直接进排版和发送。第一步要先看 `linkexpand` 里 `Build` 能否脱离入站消息调用；不能的话，把“排版 + 入队”抽成一个对外函数（小改动）。
- 本地窗口怎么办：本地私聊/本地群聊没有“发到”的概念（展开 action 在本地恒为 0）。[推断] 本地目标先不做；主人要在本地看到新图，可以以后做成“主窗口通知 + 一个信息流页”，另开一条，不在本方案。
- 内容政策：link-reader 已有成人/敏感过滤和“按会话开关，缺省关”（规格-链接自动展开第三节）。新插件**不新增过滤**，但取详情时会带出 `xRestrict` 等标记；是否沿用“每个会话自己的成人开关”见最后的拍板点。

## 五、插件页上配什么

沿用插件页的框架：一张卡，折叠一行（图标、名字“画师订阅”、一句话说明、总开关），展开后分两段。

**在哪里用**：平台（QQ；本地暂不支持）→ 场合（QQ 私聊、QQ 群）下拉“全部 / 只在这些 / 除了这些 / 不开”→ 会话挑选。默认全“不开”，新装后不会往任何地方发。

**设置**：

| 项 | 控件 | 默认 | 说明 |
|---|---|---|---|
| 关注的画师 | 列表，每行：画师名、已绑定的账号小标签（平台图标 + 账号）、状态（正常/暂停/失败）、最近一次发现时间 | 空 | “添加画师”弹框：贴任意作品链接或主页链接，自动识别平台和账号（复用链接识别）；同一画师可添加多个平台账号 |
| 每个账号的取数方式 | 下拉：自动 / 只用 WebView | 自动 | 只有推特、B 站显示 WebView 选项 |
| 每个画师发到哪 | 小标签 + “添加”（只从已知会话里挑，不手输号码） | 继承“在哪里用” | 可给某个画师单独指定一批会话；没指定就发到插件范围内全部选定会话 |
| 查询间隔 | 数字（分钟，10～1440） | 30 | 每个账号可覆盖 |
| 每轮最多发几个 | 数字 1～10 | 3 | |
| 去重 | 总开关 + “严格程度”分段（宽松 / 默认 / 严格） | 开 / 默认 | 展开可看被判为重复的最近记录；“严格”= 门限更小、更少误判差分图 |
| 只发有图的作品 | 开关 | 开 | |
| 包含转发/转推 | 开关 | 关 | |
| 排版 | 跟随链接解析的样式（卡片 / 图文 / 混合） | 图文 | 不另做一套模板 |
| 发送间隔 | 数字（秒） | 20 | 同一会话两条之间 |
| 安静时段 | 开关 + 起止时间 | 关 | 可选，本方案不强加；开了则这段时间攒着，之后按顺序发 |
| 运行状态 | 只读：每平台状态、下次查询时间、最近错误、被退避到几点 | | 出错置顶，红色角标 |
| 按钮 | “立即查一次”“试发最新 1 条”“补发最近 N 条” | | 试发只发到主人指定的测试会话 |

生效方式：增删画师、改间隔马上生效；WebView 相关项需要重启或重新拉起窗口（看实现）。后台没接上的项不显示。

## 六、风险和工作量

### 6.1 存储

[推断] 新开一个小库 `data/go/artistfeed.db`（具体放哪由现有 store 迁移约定定，要对照 `native/internal/store/migrations/` 的做法），表：
- `artists`（id、显示名、创建时间）
- `accounts`（artist_id、platform、handle、平台内数字 ID、间隔、取数方式、cursor/最近见到的作品号、状态、下次查询时间）
- `seen_posts`（platform、post_id、artist_id、发布时间、首次见到时间、状态：基线/已发/重复跳过/被过滤）
- `images`（见 2.5）
- `deliveries`（post、目标会话、状态：待发/已入队/已发/失败/未知、尝试次数）——**先写后发**，重启后按状态恢复，不重复发（沿用主动联系规格第 4 节“先写后发”的做法）。

测试只用临时数据目录，不读写真实 `data/`。

| 风险 | 说明 | 处理 |

## 七、需要主人拍板的点

1. **主人关注的画师大概在哪些平台、有多少个？** 决定第 1 步先接哪几个、间隔怎么定（20 个和 200 个不是一回事）。如果主要是推特 + Pixiv，就按第 6.3 节走。
2. **推特第一档用 FX 匿名**，接受它“个别账号拿不到”的情况，拿不到再走 WebView？（推荐。RSSHub 不推荐，因为它也要账号 cookie。）
3. **成人内容**：插件本身不加过滤，是否沿用链接解析那套“每个会话自己的成人开关，缺省关”？（推荐沿用：这是主人自己的配置，不是插件新增的限制；不沿用则 Pixiv R18 作品匿名本来也取不到。）
4. **同图不同平台，发哪一份**：先到先发（推荐，简单），还是等 Pixiv 原图（画质好但延迟）？
5. **疑似重复（门限边缘）默认照发还是跳过**？推荐照发并标记，宁多勿漏。
6. **本地窗口要不要也收到新图**（信息流页/通知）？本方案先不做，只发 QQ。
7. 画师有**多个账号**时，是否以“画师”为单位管理（推荐，去重需要）？
8. WebView 兜底是否确定放最后一步（不影响前五步）？
