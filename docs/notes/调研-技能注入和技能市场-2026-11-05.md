# 调研：技能怎么注入、技能多了怎么挑、从哪装（2026-11-05）

> 来源：Sol 只读调研（全文在 `docs/inbox/2026-11-05_pstack与技能自动注入.md`，本机，不进 git），主会话核对过结论和出处链接。挂在待办"技能系统"那一条。没有改代码。

## 一、几家怎么做（摘要）

| 做法 | 谁在用 | 谁挑 | 放在哪 | 对前缀缓存 |
|---|---|---|---|---|
| 回复前另调小模型挑，挑中的名字和描述拼进系统提示 | Alma（[读码] `alma/win/asar-out/out/main/index.js`） | 配置的工具模型 | 系统提示里 | 不友好：挑到新技能，前缀就变；它用"累计挑过的"减少变动，减不掉 |
| 固定目录常驻，正文由主模型调工具读 | Claude Code、DeepSeek Harness（[读码] `packages/skill/tool-skill/src/index.ts`）、Hermes | 主模型 | 目录在前缀，正文是工具结果追加在末尾 | 友好；目录变了在末尾追加通知，压缩或新会话再重建（Hermes `agent/skills_index_delta.py`） |
| 工具多了先检索候选，模型再决定 | Anthropic Tool Search | 检索 + 主模型 | 候选展开在当前位置 | 文档说明展开的定义不动前面的缓存 |

出处：Anthropic 缓存 <https://platform.claude.com/docs/en/build-with-claude/prompt-caching>；Tool Search <https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool>；Hermes 技能 <https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/features/skills.md>。

## 二、完成率的实测

- Vercel（2026-01-27，<https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals>）：交给模型自己决定加不加载 skill，完成率 53%，和不给文档一样；明确让它调用，79%；把文档索引常驻，100%。模型常常觉得"我会"，就跳过了技能。
- Anthropic advanced tool use（<https://www.anthropic.com/engineering/advanced-tool-use>）：工具库很大时，先检索再给模型，比全部塞进去的结果好。
- 没找到"自动挑技能对缓存命中率影响"的外部实测。我们自己的证据只有 LESSONS「模型与用量」里那次：内容插到中间，命中率从中位 95% 掉到 80%～87%。

## 三、主人的要求（2026-11-05）

- 技能会非常多："用户的skill可能确实会超级多，我自己都可能会装几百个skill"。所以要有小模型来挑，模型关掉的时候用纯算法兜底："有时候可能确实会需要小模型，或者关掉的时候纯算法兜底"。
- 要连技能市场来装和更新，也要能直接从 GitHub 仓库装："skill.sh 的市场连接用于更新安装是需要的，也可以支持直接走GitHub仓库装（Magpie有类似的实现，可以借鉴）"。
- 验收方法："以后要做，就质量和缓存一起量"，主人答"对"。
- 主人对 Alma 的感受："alma确实很多破坏上下文和影响回复速度的设计问题，也是我喜欢它回复效果但是不喜欢整体交互体验的原因之一（它在Windows也超级卡）"。

## 四、我的建议（还没成规格）

1. 人设、底线、身份、权限这些不做成技能，常驻。
2. 技能少的时候：一份固定短目录常驻在前缀；正文等主模型调 `load_skill` 时，作为工具结果追加在末尾，之后不删不改；目录变化在末尾追加通知，压缩或新会话时再重建。
3. 技能多的时候（几百个）：每轮先由小模型或纯算法（关键词、BM25、嵌入相似度）挑出几个候选，**候选追加在当轮末尾**，不改系统提示；主模型最终决定加不加载，也能自己再搜、主人也能点名。小模型关掉就只走算法。挑选器出错时退回"只有短目录"，不影响聊天。
4. 安装和更新：接 skills.sh 市场，加上直接装 GitHub 仓库；照 Magpie 的实现来（做的时候先读 Magpie 源码）。装进来的技能只是说明书，真正的权限照旧由后台的工具和审批管（ADR-238）。
5. 验收：同一批任务交替跑几种做法（只有目录 / 小模型挑 / 算法挑），各量完成率、该加载没加载、加载了无关的、缓存命中（cache read 占比、第一个变化的位置）、首字耗时、总花费；角色聊天另外盲评人设有没有被技能带偏。

## 五、挑选用检索 / 精排 / 路由模型（同日补，Sol 调研，全文在收件箱 `2026-11-05_技能挑选用检索和精排.md`）

主人问：挑选交给"决策模型"（嵌入、精排、路由），会不会比生成式小模型又快又准。查到的：

1. 快是真的：不生成文字，省掉逐字输出的时间。
2. 准不一定：公开评测里通用嵌入、精排都有输给 BM25 的例子；一项 528 个工具的实验 Top-5 召回，BM25 80%、语义检索 89%，另一个基准上 BM25 反而更强。中文技能的效果没有公开数据，要自己量。
3. 所谓"路由模型"不全是非生成式：Arch-Router-1.5B 其实输出 JSON；RouteLLM 选的是强弱大模型，不是选技能。真正只打分的有 Strands Decider、Jev 等。
4. 最难的不是排第一，是判断"这轮不需要技能"、多技能组合、多轮指代；必须允许候选为空，分开验收。
5. 建议流程：BM25 + 本地嵌入召回 → 需要时小精排 → 分数线（允许为空）→ 候选追加在当轮末尾 → 主模型决定。4B 的精排太重，不当每轮默认。
6. 建议预算（还没实测）：几百个技能时挑选 p50 ≤ 100 毫秒、p95 ≤ 250 毫秒。
