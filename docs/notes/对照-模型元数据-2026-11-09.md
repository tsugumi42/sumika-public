# 02 模型元数据：单次输出、上下文窗口、能力怎么跟着模型走

> 只读调研，2026-11-09。没有改 Sumika 任何代码，没有提交。
> 起因：主人问"放宽到 120 次请求、800 万 token、单次 32768、60 分钟"这类数是不是写死了、能不能跟官方或服务商数据；"回复到上限"是不是直接跟模型设置走就行；以及"和标准 Agent harness 不太一样"。
> 证据标记：【取到】实际取回数据并统计；【读码】读了源码（带路径行号）；【读文档】只读文档；【推断】没核实。

## 一、结论（先看这个）

1. **能跟，而且别家都在跟。** 但"服务商返回"这一层很不齐：OpenAI 的 `/models` 什么限额都不给，DeepSeek、Anthropic、OpenRouter 给，Magpie 也给。所以必须分层：用户覆盖 > 服务商或网关返回 > models.dev 本地缓存 > 保守默认。**models.dev 只补空，不盖已报告的值。**
2. **优先序里"服务商返回"必须在 models.dev 前面，有实测证据**：同一个模型，Magpie 报的窗口比 models.dev 小，因为 Magpie 知道请求实际落到哪条渠道（Codex 订阅、中转）。`gpt-6.1-sol` Magpie 报 500000，models.dev 写 1050000；`gpt-6-astra` 272000 对 1050000；`grok-4.7` 256000 对 500000；`deepseek-flash` 输出 232000 对 393216【取到】。照 models.dev 的数发会超窗口被拒。Magpie 自己的顺序也是"这个模型 > 这个服务商的 `*` > 服务商自己的列表 > models.dev"（`_external/magpie/docs/reference.md:1309-1310`）【读文档】。
3. **主人问的两个问题，答案是：主对话已经在跟，子代理那条没跟。**
   - 主对话：`native/internal/turn/loop.go:337` 是 `min(b.MaxOut, max(1, b.Window - 估算 - 4096))`，`MaxOut` 来自模型报的 `max_output_tokens`（`turn/turn.go:338-345`）。回复上限本来就跟模型走，不是写死的【读码】。
   - 后台守卫、顾问也已经按模型报的 `MaxOutputTokens` 封顶（`app/guarddeps.go:148-152`、`advisor/runtime.go:252-256`）【读码】。
   - **没跟的**：`config/kernel_budget.go:44` 的 `RequestOutputTokens: 4096`，经 `modelcall/client.go:151` 和 `turn/internal_run.go:179` 生效，是子代理每次请求的输出上限。它和模型无关，所以派子代理写大文件会撞 4096。这就是上一轮"子代理写大文件"的根因【读码】。
   - 还有两处小的写死：`turn/turn.go:339` 模型没报输出上限时按 8000；`llm/llm.go:86-94` 没报窗口时按 128000【读码】。
4. **"放宽到 120 次请求、800 万 token、单次 32768、60 分钟"里，只有"单次"该跟模型；另外三个是岗位预算**（防失控的总额），不是模型属性，不该跟 models.dev。建议：单次输出改成"0 = 跟模型"，仍被岗位的 `maxOutputTokens` 总额封顶；请求数、总 token、时长继续是用户可调的预算，但默认值的依据要写明。
5. **models.dev 能取，数据够新**：我用本机代理取到 `https://models.dev/api.json`（5.97 MB，235 家服务商，8940 个模型）。用户常用的 DeepSeek v4、GPT 6、Claude 5、Grok、Agnes 全在（第三节）。但不能原样信，要过滤和消歧义（第三节）。
6. **这份调研推翻了规格-模型配置拍板问题 9 的建议**（"不内置、不联网取"）。改成：**不内置快照；联网取作第三层，缓存到本机；离线用任意年龄的缓存；没缓存就落到保守默认并标"未报告"。**

## 二、各家返回什么（取到的）

### 2.1 models.dev（`https://models.dev/api.json`）【取到】

顶层是 `{服务商ID: {id, name, env[], npm, api, doc, models{}}}`；210 家有 `api`（基础地址），所以它也能给"预设服务商"的默认地址。每个模型的字段（出现次数/8940）：

| 字段 | 内容 | 备注 |
|---|---|---|
| `limit.context` / `limit.output`（全有）、`limit.input`（1728） | 上下文窗口、单次输出上限、单独的输入上限 | OpenAI GPT-5 系 `context=400000, input=272000, output=128000`：窗口含输出，输入另有上限 |
| `modalities.input/output` | `text/image/pdf/audio/video` | 够判断能不能看图 |
| `reasoning`（bool）、`reasoning_options`（6863） | `[{type:toggle}, {type:effort, values:[...]}, {type:budget_tokens, min}]` | 能直接得到"能开哪些档位"，比 `reasoning_levels` 细 |
| `tool_call`、`structured_output`、`temperature`、`attachment` | 能力开关 | |
| `cost`（8545） | input/output/cache_read/cache_write/reasoning，每百万 token 美元；`tiers` 按上下文分档 | 和用量页的价格缓存是同一件事 |
| `status`（981） | `deprecated`906、`beta`74、`alpha`1 | |
| `type`（452） | `image/embedding/video/speech/transcription/reranking/realtime/chat` | 没有 `type` 就是普通聊天 |
| `canonical_model_id`（7605） | 指向原厂模型 | 转售商的条目靠它对回原厂 |
| `provider`（790）、`experimental` | 单个模型覆盖线路（`npm`、`api`、`shape: responses/completions`） | |
| `family`、`release_date`、`knowledge`、`open_weights`、`description` | 说明性 | |

**用户常用模型在不在**（官方条目，括号是 context/output）：

- DeepSeek：官方 `deepseek` 条目有 `deepseek-flash`（1048576/393216，文本+图片，档位 low/high/max）、`deepseek-v4-pro`（同上，仅文本）。**官方条目里没有 `deepseek-v4-1-flash` 这个名字**；它出现在 venice、mistral、kenari 等转售商，输出上限从 50000 到 1048000 各不相同。官方 `/models` 里这个模型叫 `deepseek-flash`（见 2.4），Magpie 目录里是 `auto/deepseek-flash` 和 `opendesign/deepseek-v4.1-flash`。
- GPT：`gpt-6-astra`、`gpt-6-luna`、`gpt-6-sol`、`gpt-6.1-sol`、`gpt-6.1-terra`、`gpt-5.6*` 都在，1050000/128000，input 上限 922000，档位 none 到 max。
- Claude：`claude-opus-5`、`claude-opus-5-5`、`claude-sonnet-5`、`claude-sonnet-5-5`、`claude-haiku-5-5`、`claude-fable-5`、`claude-fable-5-1` 全在，1000000/128000。
- Grok：官方 xAI 条目 `grok-4.7`（500000/500000）、`grok-4.6`、`grok-4.5` 等。输出上限等于窗口，这是**数据可疑**的典型（见下）。
- Agnes：官方 `agnes` 条目有 `agnes-2.5-flash`（512000/65536，档位只有 toggle）、`agnes-3.0-flash`、`agnes-2.5-pro-alpha`（1000000/65536）；`agnes-2.0-flash` 标 deprecated。

**拿 Magpie 的 51 个模型按"裸模型名"去 models.dev 对：46 个命中、5 个没命中**（`devin/swe-2`、`devin/swe-2-flash`、`qoder/lmodel`、`opendesign/deepseek-v4.1-flash-eco`、`agnes-ai/agnes-video-2.5-flash`）。没命中的就是"未知模型"的真实例子。

**数据要过滤，不能原样用**：

- 159 条 `context=0`（多是图像、语音模型）；1189 条 `output >= context`（多是转售商把输出写成窗口，如 orcarouter 的 `grok-4.6` 500000/500000）；OpenRouter 的输出上限常是窗口的 90%（943718/1048576）。规则：`output >= context` 或 0 时，输出上限当未知。
- **同名模型在不同转售商里输出上限差很大**：`grok-4-7` 在各家是 65536 到 524288，`gpt-6-astra` 是 50000、128000、1050000。所以**按裸名全表取第一个会选错**。消歧义顺序：先找原厂条目（`canonical_model_id` 指向的那家，或 id 前缀/maker 对应的服务商）；原厂没有、而各家命中的数完全一致，取这个数；不一致就取保守的最小值并标"来源不一致"。别按 provider 字段去配 Magpie 的 `owned_by`：Magpie 报 `codex`、`grok`、`opendesign`，models.dev 是 `openai`、`xai`、`deepseek`，对不上。
- `status: deprecated` 标灰，不隐藏（和"不替主人选模型"的精神一致；opencode 是直接过滤，`_external/_mc/opencode/packages/core/src/plugin/models-dev.ts` 的 `snapshots()`）。
- `type` 不是空也不是 `chat` 的，不进聊天模型目录。

**体积**：全量 5.97 MB（gzip 约 0.6 MB）。只留需要的字段（限额、模态、思考档位、状态、类型、`canonical_model_id`）压到约 1.67 MB（gzip 约 0.12 MB）。

### 2.2 本机 Magpie 网关 `GET /v1/models`【取到】

只读，用公开的客户端标识，没有读也没有输出任何密钥。回 `{object, data[51], first_id, last_id, has_more}`。每个模型：

- 必有：`id`、`object`、`owned_by`、`display_name`、`magpie_label`、`type`（都是 `model`）、`created`（全是 0）、`created_at`（假的 2025-01-01）、`reasoning`、`reasoning_levels`、`supported_reasoning_levels`（`[{effort}]`）、`supported_parameters`、`tool_call`。
- 几乎都有：`context_length`、`context_window`、`max_input_tokens`（三者相等，50/51）、`max_output_tokens`（50/51）、`modalities`（49/51，有的只有 `input`）。缺的是 `devin/swe-2`（没有任何限额）。
- 部分有：`pricing`（18/51，字符串，单位是每 token 美元）、`native_endpoints`（39/51）、`service_tiers`（7）。
- 注意：`context_window` 在 Magpie 是总窗口；DeepSeek 官方同名字段的定义是"输入加输出的总容量"（见 2.4），两者含义一致。
- 随手发现：`reasoning_levels` 有 `["light","balanced","deep"]` 这种非标准档位（`auto/deepseek-v4.1-flash-free`），`agnes` 的是空数组但 `reasoning: true`。`turn.Effort` 现在能处理"报过档位才映射"，这两种要有用例。
- 文档：`/` 返回 200（页面），`/v1/models/<id>` 也可取；文档在 `_external/magpie/docs/reference.md`，第 64 行写明它用 models.dev 补名字、思考档位、没有列表的服务商；第 1296-1330 行写限额的优先顺序和"只有完全没人知道限额的模型才按 16384 发"【读文档】。**所以 Sumika 连 Magpie 时，Magpie 已经做过一遍 models.dev 合并，Sumika 不要再盖一层，直接信它返回的**。

## 三、Sumika 现在有什么【读码】

- `llm.Model`（`native/internal/llm/llm.go:35-53`）：读 `context_length`、`context_window`、`max_input_tokens`、`max_output_tokens`、`modalities`、`reasoning`、`reasoning_levels`、`supported_reasoning_levels`，另有 `MagpieLabel`。
- `Window()`（`llm.go:86-94`）：三个字段谁有用谁，都没有按 **128000**。
- `limits()`（`turn/turn.go:338-345`）：输出上限没报按 **8000**。
- 窗口、门槛：`ContextLimits.window(model)`（`turn/turn.go:311`）在 `agent.context.window` 为 0 时跟模型，封顶只能往小设；硬门槛 = `min(窗口×hardRatio, 窗口−reserve)`，软门槛 = 窗口×softRatio（`turn.go:296-312`）。所以**压缩门槛已经跟着窗口走**，缺口只在"窗口本身不知道时的兜底值"。`sumika.example.yml:256-263` 里 `window` 示例是注释掉的，写明"不写就跟着模型自己报的长度（ADR-062）"。
- 主对话输出：`turn/loop.go:337`，`min(MaxOut, max(1, Window − piEstimate − 4096))`（照 pi 的 `clampMaxTokensToContext`）。
- 子代理和岗位预算：`config/kernel_budget.go:44` 默认 `MaxRequests 24、MaxTools 60、MaxTokens 524288、MaxOutputTokens 32768、MaxDurationMs 900000、RequestOutputTokens 4096`；`modelcall/client.go:151` 取 `min(RequestOutputTokens, 总输出额余量, 总 token 额余量−输入估算)`，再被请求自带的 `MaxCompletionTokens` 夹小。
- 能力：`SupportsImages()` 要求明确的 `image`；`turn.Effort`（`turn/turn.go:178-`）按报的档位映射；`api.ModelOption.ContextReported` 只是布尔（`app/models.go:260`）。
- **没有任何 models.dev 的 Go 代码**。Bun 时代 `daemon/util/prices.ts` 用 models.dev 取价，缓存路径在数据目录规格里登记为 `cache/prices/models-dev.json`（`docs/规格-数据目录与备份.md:213`）；`docs/subsystems/agent-and-console.md:197` 写用量页"第一次没有缓存会去 models.dev 取一次"。Go 侧是否还有取价没找到。
- `cmd/sumika-models` 是**本机嵌入和重排服务**（`internal/localmodels/server`），和聊天模型元数据无关，名字容易误会。
- 规格-模型配置：拍板问题 9 现在是"不内置、不联网取，来源只有服务商 `/models` + 手填，都没有标未报告"；3.2 节"不内置能力表"；第八节"禁止偷懒写法"里有"内置一份常见模型能力表当事实来源"（**注意**：这条禁的是"内置当事实来源"，本稿的"联网取、缓存、只补空"不违反它，但字面要改清楚）；第十节验收 6 管能力优先级；十个待答问题里问题 9 是唯一和本稿直接相关的。ADR-044 第 1 条"可脱离 Magpie 独立运行"；ADR-098 "默认不替主人选模型"；ADR-142 第 4 条"怎么配多个来源另出规格"。
- 主人的批评"模型页太依赖 Magpie……完全不是正常 harness 的模型配置设计"。模型元数据这块的具体表现：窗口和输出限额只认 Magpie 风格字段；直连 OpenAI 时 `/models` 什么都不给，就会掉进 128000 和 8000 两个静默兜底。

## 四、设计

### 4.1 取值优先顺序（每个字段单独走一遍，不是整条记录）

字段：`contextWindow`、`maxInputTokens`、`maxOutputTokens`、`input[]`（模态）、`reasoning`/档位、`status`、`cost`。

| 层 | 来源 | 说明 |
|---|---|---|
| 1 | 用户覆盖 | `providers.<id>.models.<模型>.contextWindow / maxOutputTokens / input / reasoning`（规格 3.1 已有）；还加两个"整家"的写法：`providers.<id>.modelDefaults`（Magpie 的 `*` 同款），以及全局的 `agent.context.window` 继续作为只能往小设的封顶 |
| 2 | 服务商或网关返回 | `GET {baseUrl}/models` 里读到的字段（Magpie、Anthropic、DeepSeek、OpenRouter 有）。**读到的值就信，不拿 models.dev 去"纠正"** |
| 3 | models.dev 缓存 | 只在第 2 层这个字段为空时补；按第三节讲的消歧义顺序匹配；匹配结果带"来源不一致"标记时取保守值 |
| 4 | 保守默认 | 窗口 **32000**、单次输出 **4096**、不能看图、不发 `reasoning_effort`；明确标"未知"并在界面标红，不伪装成正常值 |

要点：

- **每个字段记来源**：`user / provider / modelsdev / default` 四值。界面和日志都显示来源，这样"为什么这个模型窗口是 272K"能回答。
- **窗口和输出在同层取**：不要窗口来自第 2 层、输出来自第 3 层。Magpie 报了窗口 272000，却用 models.dev 的 128000 输出，没有问题；反之 models.dev 的输出 393216 配 Magpie 的窗口 1000000 才有问题（它会按它的窗口算，但未必和这条渠道的输出配套）。同层缺哪项，那一项才降到下一层，并在来源里写清。
- **未知模型怎么办**：第 2、3 层都空时（如 Magpie 的 `devin/swe-2`、`opendesign/...-eco`），走保守默认，状态写"未知模型，限额按保守值"；选这个模型时弹一句提示，可在模型行上手填。**不拿别的模型的值顶替**（和 ADR-098、规格第八节一致）。
- **保守默认的数为什么改**：现在窗口 128000、输出 8000。Hermes 兜底 256K 但警告去重（`model_metadata.py:2323`），opencode 的兜底输出 32000，omp 是 64000。**窗口按大了的后果更坏**（压缩触发太晚，请求被拒，规格第九节第 6 条已经担心过本机小模型），所以窗口兜底取小：32000；输出兜底可以放宽，因为窗口夹得住。具体数是起步值，没有实测。

### 4.2 离线、刷新、放哪

- **放哪**：`<数据目录>/cache/models-dev.json`（数据目录规格第 213 行已为取价缓存预留 `cache/prices/models-dev.json`，建议合并成同一份：价格就是这份数据里的 `cost`，不要两份各取一次）。只存瘦身后的字段（约 1.7 MB，gzip 约 0.12 MB），不存 `description`、`experimental` 之类。写入原子替换；坏文件改名隔离，不当空表（Hermes 做法）。不含 key，不进 git。
- **何时刷新**：启动时**不阻塞**，后台取；缓存没过期（4 小时，起步值，Hermes 同值，理由是 ETag 条件请求很便宜）就不取；带 `If-None-Match`，304 只更新时间；失败退避 5 分钟（Hermes、opencode 都是 5 分钟量级）；用户手动"刷新"按钮强制取；取回后正文摘要没变就不通知界面。热路径（每轮取窗口）只读内存，不做网络。
- **离线**：用任意年龄的缓存；没缓存就落到第 4 层（保守默认），界面写"没联网，没有模型资料缓存"。**不内置快照**：快照要跟发布一起更新，而 Sumika 是自用、不发布，缓存加手填够用（opencode 的快照是为了首次启动无网也有列表，Sumika 首次启动靠服务商 `/models` 就有列表）。首次启动又无网又连的是 OpenAI 这类不报限额的服务商，才会全落到默认，这时靠手填。
- **来源**：直连 `https://models.dev/api.json`，经配置的代理（本机 `127.0.0.1:7897`）；可配置 `modelsDev.url` 换镜像、`modelsDev.enabled: false` 关掉（等价于 opencode 的 `DISABLE_MODELS_FETCH`）。响应上限 16 MB，超了当读不懂；解码失败保留旧缓存。
- **隐私**：请求只发 GET，不带任何用户数据、不带 key。

### 4.3 单次输出：按上限还是留余量，思考占用怎么算

先说事实（别家怎么算）：

- **opencode**：`min(模型 output 上限 或 兜底32000, 256000)`，再按窗口剩余空间夹：`剩余 = 窗口×(1−1%) − 已测输入 − 估算输入×1.15`，下限 1024（`_external/opencode-v2/packages/core/src/session/model-request.ts:86-92`，常量在 `:49-62`）。
- **omp**：请求默认 `model.maxTokens`；发之前按"窗口 − 提示词 token − 64"夹，下限有常量，**服务商端自己在窗口处截断的（如 Claude API）就不夹**（`_external/_mc/omp/packages/agent/src/output-budget.ts:84-96`）。注释里点明原因：DeepSeek V4 输出上限约 38 万、窗口约 100 万，提示词一过"窗口减输出上限"就整个请求被拒，远早于压缩触发。
- 思考占用：**omp 把思考预算加在回答预算上面**（`maxTokensWithThinkingBudget`，`_external/_mc/omp/packages/ai/src/stream.ts:1536-1541`），但只用于 Anthropic 的预算式思考和 Google（它们的 max_tokens 里包含思考，且思考预算是单独字段）。**Sumika 走 OpenAI 兼容、发 `reasoning_effort`，没有单独的预算字段，`max_completion_tokens` 本身就包含思考 token**，所以不照抄 omp 的"加在上面"，而是：上限取模型的输出上限，思考档位调高时不额外加（模型端自己分配），截断了（`stop=length`）要能被识别、不当成功。

对 Sumika 的建议：

1. **默认值取"模型报的输出上限"，不人为留余量**，因为这个值本来就是"含思考的最大值"，实际用多少由模型自己决定；贵的不是上限而是实际生成量。
2. **再按窗口夹**（Sumika 主对话已有这一步，`loop.go:337`），夹法改成 opencode 那种：窗口留 1%，估算误差 ×1.15，下限 1024，替换固定的 4096 余量。原因：固定 4096 在窗口 100 万时过保守、在窗口 32000 时又可能不够；比例加估算误差更稳。**这是一处行为变化**，要用对拍钉住（现在是照 pi 的写法）。
3. **服务商自己在窗口处截断的不夹**（omp 的 `stops-output-at-context-window`）：Sumika 暂时没有这个标记，先不做，记为后续。
4. **输出上限等于窗口**（models.dev 里 xAI 的 500000/500000）按"未知"处理，走第 4 层 4096，除非用户手填。否则请求会被"输入+输出超窗口"拒。
5. **岗位预算的"单次"**：`RequestOutputTokens` 默认改成 0，含义"跟模型的有效输出上限"，仍受岗位 `MaxOutputTokens`（总额，默认 32768）封顶。这样子代理写大文件时，单次能用到模型上限，而总输出由岗位总额控制失控。同时注意 `MaxOutputTokens: 32768` 现在是**整个岗位根的输出总额**，不是单次；它比模型单次上限（12.8 万）小得多，所以放宽单次时要同步看总额，否则一次就吃光（`modelcall/client.go:151` 里 `min` 会把单次夹到总额余量）。
6. **回复写到上限的提示**：这条本来就是"回复直接跟模型设置走"，主人的判断对。按上面做，上限就是模型的上限；到了上限还截断就是真的写满了，才有"回复写到上限"的提示价值，不是我们的配置造成的。

### 4.4 上下文窗口和压缩门槛怎么跟

- 窗口用 4.1 的优先序取值；`agent.context.window` 继续是"只能往小设的封顶"（现行），界面分开显示"模型报的 / 你设的 / 实际用的"（`turn.go:296-300` 的注释已经要求设置页分开显示）。
- 压缩门槛的公式不变：硬门槛 = `min(窗口×hardRatio, 窗口−reserve)`，软门槛 = 窗口×softRatio。窗口来源改变后自动跟。Codex 的做法值得参考但不必照抄：它把"可用窗口"按 95% 算、自动压缩按 90% 算且配置值也被夹到 90%（`openai_models.rs:573-590`），Sumika 的 0.85 和 0.7 已经更保守。
- **窗口来源是第 3、4 层时门槛要更保守**：来自 models.dev 但"来源不一致"，或来自保守默认时，`hardRatio` 取 min(配置值, 0.75)，并在界面标出。理由：Magpie 实测里 models.dev 的窗口比实际渠道大一倍以上，信过头的代价是请求被拒。
- 窗口为 0 或负数、`reserve ≥ 窗口`：现有 `hard()` 会给出非正数，要有保护（`window-reserve ≤ 0` 时取窗口×0.5）；这是边界清单里的"0、负数"一格，我没有核实现有代码是否已处理。

## 六、验收要点（用假 HTTP 服务和临时目录，不读真实 data，不打真实模型）

1. 优先序四层逐字段：两边都有时取服务商（272000 对 1050000 的真实例子）；服务商空取资料库；都空取保守默认并标未知。
2. 资料库数据：`output ≥ context`、`context=0`、`type` 非聊天、`deprecated`、`canonical_model_id` 指向原厂、同名多家且不一致取最小。
3. 缓存：原子写、坏文件隔离不当空表、304 只更新时间、响应超限当读不懂、刷新失败保留旧缓存、离线用任意年龄缓存、热路径不联网。
4. 子代理单次输出：默认 0 跟模型；模型报 128000 而岗位总额 32768 时单次被夹到总额余量；模型没报时走保守默认 4096。
5. 主对话输出夹法：窗口 32000、窗口 100 万两种；估算偏差；下限 1024；输出上限等于窗口按未知。
6. 界面：用 `ui.NewTester` 验来源角标；悬停写两边数值；手填后"恢复"只清自己的。
7. 形状 × 入口（高风险检查按 AGENTS 第 7 条，我只列了和本稿相关的几行，没有逐格验证）：

| 输入形状 | 资料库解码 | 服务商 `/models` 解码 | 用户覆盖 | 请求发出 |
|---|---|---|---|---|
| 空、缺、null | 字段当未知 | 同左 | 空 = 没覆盖 | 走下一层 |
| 0、负数 | `context=0` 当未知；负数丢弃 | 同左（现状 `Window()` 已按正数判断） | 拒绝并指出键 | 夹到下限 1024，不发 0 |
| 类型错误（字符串当数字） | 整条丢弃并记一次日志 | 当未报告 | 整节拒绝保留旧值 | 不适用 |
| 异常与敌对（超大响应、控制字符的 id、重复 id） | 响应上限；含控制字符的条目丢弃 | 同左 | 不适用 | 不适用 |
| 四种场合（本地私聊、本地群聊、QQ 私聊、QQ 群） | 与场合无关 | 与场合无关 | 只有主窗口能改 | 窗口夹法对四种相同，各留一条用例 |
