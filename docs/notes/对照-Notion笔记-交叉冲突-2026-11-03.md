## 1. 跨组冲突：两边是什么，采用哪边，怎样调和

### 1.1 全局记忆与发言分寸：采用 ADR-242，拆开召回与披露

**两边的主张：**记忆组、群聊组、架构组和媒体组引用的多篇旧笔记，把“当前场合检索不到”当作防止泄露的主要手段。Notion 079《跨群、私聊与多人关系的信息边界》甚至建议，当事人在群里主动问起私聊内容时，也优先回私聊确认。ADR-242 则明确选择：同一角色在本地私聊、本地群聊、QQ 私聊、QQ 群都想得起，主人本人问就答，其他情形由角色判断，不再靠拿不到挡住。

**采用 ADR-242。** 这是明确的用户选择，更符合“在哪和她说过都记得”的陪伴连续性。旧笔记仍有价值的是来源、受众、主动提起的适宜性及暗示式泄露，不能把它们重新解释成场合召回 ACL。

**调和方式：**

- 召回判断：是不是这个角色的记忆、原话是不是她见过的。
- 披露判断：现在谁在听、谁在问、是否主动提起、来源是什么。
- 执行授权：是否可以把资料交给工具、其他角色或外部服务。

当前 `AllowedScopes` 同时影响召回与守卫禁说集合；只让它返回全部，会使旧守卫失去禁说对象。迁移必须一起处理自动召回、搜索、原话、固定要点、实例状态和发送守卫。

出处：Notion 079《跨群、私聊与多人关系的信息边界》§4～6；ADR-242，[决策记录:2878](../决策记录.md)；[scope.go:61](../../native/internal/memory/scope.go)、[outbound.go:136](../../native/internal/memory/outbound.go)、[render.go:39](../../native/internal/memory/render.go)。

### 1.2 角色隔离与公共材料：共享知识不等于共享经历

**两边的主张：**记忆组强调角色经历独立；群聊组保留公共说法库；媒体组提出共享角色识别资料和媒体索引。混在一起，容易得出“既然共享，就把所有资料放一处”的结论。

**采用分用途共享。** ADR-096 已决定说法与黑话合库；ADR-162 又明确主人自身事实和偏好共用，而角色与主人的约定、共同经历及“只告诉你”各自保存。ADR-242 第六条保留了这项例外。

**调和方式：**

| 内容 | 建议归属 |
|---|---|
| 通用梗释义、可公开的接法材料 | 公共材料；角色分别保存适配、屏蔽和使用状态 |
| 主人自身事实和偏好 | 按 ADR-162 的窄例外共用 |
| 角色的经历、关系、主观看法、“只告诉你” | 角色独立 |
| 已核实的作品与角色目录 | 可研究共享；模型猜测不能直接进入共享权威目录 |
| 原始媒体和出现记录 | 当前继续按平台保存，遵循 ADR-199 |

不为此先建一个跨记忆、说法、媒体、关系的总数据库。

出处：Notion 058《通用 Agent 记忆》、007《媒体指纹、表情包去重与网图溯源》、008《视觉偏好画像》；ADR-096、162、199、242，[决策记录:925](../决策记录.md)、[1820](../决策记录.md)、[2302](../决策记录.md)、[2894](../决策记录.md)。

### 1.3 脱敏与可辨认来源：按用途处理，不把全面匿名化铺到所有路径

**两边的主张：**Notion 047《中文聊天记录脱敏调研》建议姓名、学校、机构、地址等一起替换；媒体组据 ADR-103 指出，回溯学习后来只批准替换号码和链接。记忆组与群聊组又要求保留“谁说的、说的是谁”，否则会张冠李戴。

**采用 ADR-103 已定的回溯学习范围。** 名字照发，号码替换、链接只留域名，原始库保留原文。这不等于公开报告、搜图上传、网页搜索词和跨角色委派都获得相同披露许可。

**调和方式：**同一来源保留可信身份，在不同出口决定给出哪些内容；不先把身份信息全部破坏，再让模型猜回人物关系。当前待办“去掉号码、真名”与 ADR-103 冲突，应按用途纠正，不能让 NER 成为实时学习和本地聊天的共同前置。

出处：Notion 047《中文聊天记录脱敏调研》；ADR-103，[决策记录:1032](../决策记录.md)；[待办:247](../待办.md)。向外部搜图服务上传的独立边界见 Notion 007 §7。

### 1.4 聊天短描述与可信视觉证据：短回复保留，知识写入补证据

**两边的主张：**媒体组建议短描述优先；Notion 087、088 要求区分观察、身份推测、OCR、语用和来源；记忆组希望消费可靠、可追溯的材料。

**两者可以同时成立。** ADR-137、165 选择的是日常聊天描述简短，不是批准把短描述当成已核实知识。Notion 088 本身也明确采用分级复核，不要求每图调用两三个模型。

**调和方式：**日常接图走短路径；明确问角色、出处、截图细节，或准备写入可复用知识时，再补相关证据。记忆消费时保留分析版本、来源及待核实状态。纠错要能找到依赖旧描述的派生记忆。

当前 `memsource.images` 按 hash 取最新成功 brief，不核当前分析版本与人工核对状态，正是媒体与记忆交接处的缺口。

出处：Notion 088《识图结果可信性》§3～4；ADR-137、165，[决策记录:1515](../决策记录.md)、[1853](../决策记录.md)；[memsource.go:442](../../native/internal/store/memsource/memsource.go)。

### 1.5 自动成长与事实可靠性：先记录反馈，不能把热闹直接变成成功

**两边的主张：**群聊组希望语言习惯、群内规范和关系从相处中形成；记忆组防止反思变成长期指令；媒体组又发现 reaction 数据只有新增、没有取消。现有《人设成长》规格把五分钟内有人接话、笑或贴回应算作“接得好”。

**更符合需求的是有证据、可撤销的成长。** 角色可以长出新习惯，但不能因为另一条话题恰好热闹、几个 AI 互相附和，或取消回应没记下来，就自动强化。

**调和方式：**先分开实际动作、观察到的反馈和归因判断；明确纠正、目标本人反馈优先。群规范、关系和策略保留反例与适用条件。经历进记忆，策略候选另行试验，不把“这个群以后少说话”伪装成事实长期注入。

出处：Notion 061《行为学习》、080《对话重要性判断与多层记忆反刍》、094《MaiBot 行为学习历史实现审计》；[规格-人设成长:55](../规格-人设成长.md)、[规格-记忆-v2:201](../规格-记忆-v2.md)、[display_reactions.go:9](../../native/internal/store/display_reactions.go)。

### 1.6 多阶段社交推理与低延迟：职责分开，不恢复固定两次模型调用

**两边的主张：**Notion 095、096 等建议先选动作再写话；群聊组与架构组希望理解、决策、表达可分别诊断；性能要求又反对每轮无条件增加模型调用。

**采用 ADR-172 的现行取舍。** 两段式做过实验，明确不上生产。可以改善对象、上下文、参考材料和动作出口，不必先恢复 Planner＋Replyer 两次调用。

复杂场景是否按需增加规划，应由同集质量与成本比较决定。媒体识别、外部检索和重排同样按缺口触发，不能每轮全跑。

出处：Notion 095《弱模型社交认知辅助层》、096《MaiBot 社交 Agent 总架构》；ADR-172，[决策记录:1933](../决策记录.md)；规格-两段式说话:3（私有存档）。

### 1.7 统一插件与尽早可用：统一最终契约，不强迫本地流式套 QQ 出口

**两边的主张：**架构笔记 009、010 建议 LocalAdapter 统一本地渠道；界面与早上验收要求尽快接通本地输入。当前 Hub 已承担本地落库，再套完整 Intake/Outlet 会形成两个写入者。

**采用当前本地会话服务的落法。** 新合入的 `api.LocalChat` 复用 Hub，本地最终历史、流式草稿、停止和审批各有明确身份。以后本地群聊需要统一的会话、成员和调度契约，但不要求每个 token 走 QQ 式发送出口。

插件统一也应围绕稳定身份、能力、启停和收尾，不先补齐通用 EventBus、任意 UI 扩展和完整工作流。一个功能挂多个接口，管理上仍是一款插件。

出处：Notion 009《Go 插件数量、职责盘点与 LocalChannel、LinkReader 设计》、010《插件统一规范》§1、4、6；ADR-177；[api/localchat.go:34](../../native/internal/api/localchat.go)、[desktop_chat.go:49](../../native/internal/app/desktop_chat.go)。

### 1.8 Telegram 默认、自定义主题与编辑：三个目标分别验收

**两边的主张：**界面组要求按 Telegram 对数值和行为；用户又要求颜色、圆角、字号、半透明可自定义。旧笔记还保留 Telegram／Discord 混搭、自定尺寸及“所有提示词可编辑”的方案。

**采用 Telegram 默认＋显式用户定制。** 默认值来自固定 Telegram 源码版本；用户修改是自己的主题，不保留旧界面作为隐含覆盖。主题库参数存在、主题编辑页存在、所有组件实际使用这些参数，应分别记账。

“编辑可以自定义”也不能只交主题颜色。人设和风格预设的编辑是另一条既有需求；ADR-175 只开放这两类，core、平台、场合和后台岗位归开发维护。

出处：Notion 025《界面字号与组件尺寸》、032《聊天界面对照》；ADR-175、245～247；[待办:47](../待办.md)、[324](../待办.md)；`mewtype/theme/theme.go:17`。

### 1.9 后台运行、角色发言与角色互联：共享运行记录，分别定义完成条件

**两边的主张：**记忆组要每日整理，媒体组要延后搜源，群聊组要主动分享，架构组要定时任务、子代理和角色委派。全部做成“到时间给角色发一句话”，会混淆任务执行、投递和完成。

**采用共同运行记录、独立业务调度。** 记忆整理成功是事务提交；搜源成功是取得相应证据；投递成功是消息回执；工作子代理还需要任务结果。角色社交不必工单化，长任务也不能只靠一条“已送达”结案。

睡眠期间照跑但不发言已有用户采纳记录；还没定的是醒后如何结算。角色委派“先不 fork、只传消息或受控原文引用”也已有记录，不应重新问整套方向。

出处：Notion 010 §2、4，104《OpenAI dots》、106《Lody》；角色互联与定时自动化:95（私有存档）；ADR-235，[决策记录:2789](../决策记录.md)。

### 1.10 只追加与纠错、上下文预算：追加更正，压缩时正式换纪元

**两边的主张：**架构组保护缓存前缀；记忆与媒体组要求撤销错误、替换过期事实；界面组要求内存有界。不能把“只追加”理解成永远不清理，也不能每轮重写旧工具结果与记忆块。

**调和方式：**原始记录与修订留在存储；当前上下文对已经给过的旧事实追加更正；达到预算时通过正式压缩、重建切换纪元。大工具结果首次只给有界内容和宿主绑定的续读引用。

当前记忆注入主要按 ref 去重，尚未形成规格要求的“编号＋版本＋下一轮更正”完整路径。这会影响媒体纠错和长期事实更新，优先于继续叠反刍层。

出处：Notion 035《长对话上下文、提示词缓存与省 token》、048《各家提示词缓存规则》、058《通用 Agent 记忆》；[规格-记忆-v2:228](../规格-记忆-v2.md)、[memplugin/plugin.go:312](../../native/internal/memplugin/plugin.go)。
