### 2. 每个分类下的具体设置项

下面的"控件"是值的类型：文件型（Claude Code 的 JSON、Codex 的 TOML）写的是值类型，界面型写的是页面里实际用的控件。"生效"只写源码或官方文档明确写过的，没写的标"未找到"。

**通用 / 启动**
- 开机自启、最小化到托盘、关闭窗口时的行为：Cherry（开关和单选），生效未找到。
- 语言：LobeHub 的 `responseLanguage`，Open WebUI 的语言下拉框，Goose 的 Language 下拉框（选项很多）。Cherry 的 `settings.agent.language` 也有对应项。
- 时区：LobeHub `timezone`。Codex 有 `time_format` 类的键，未逐项核对。
- 界面动效：Codex `[tui].animations`，默认 `true`；LobeHub `animationMode`，取值 disabled、agile、elegant。
- 上下文菜单：LobeHub `contextMenuMode`，取值 disabled、default。

**外观**
- 配色模式：Claude 桌面版是 Light、Match System、Dark 三档；Cherry 是 system、light、dark 加窗口风格（透明）；Open WebUI 有 Light、Dark、OLED Dark、System。控件是单选。

**模型与服务商**

### 3. 交互上的共同做法

**布局**
- 左侧分组导航 + 右侧内容：Cherry（`settingsMenu.ts` 里按 `groupKey` 分组，数组顺序就是菜单和搜索的顺序）、OpenHands（`settings-navigation.tsx`，手机端有抽屉）、Claude 桌面版（侧栏式）。
- 顶部页签 + 弹窗：Open WebUI（`SettingsModal.svelte`，页签 id 有 general、interface、notifications、shortcuts、tools、usage、personalization、account、audio、connections、about，非管理员看不到管理页签）；Goose 是顶部 9 个页签（Models、Local Inference、Chat、Agent、Prompts、Keyboard、Auth、App 等）。
- 配置文件为主、界面为辅：Claude Code 和 Codex 都是 JSON / TOML 文件为主，`/config` 只是一个"常用选项"菜单。Claude Code 文档原话是 `/config` "lists a short set of personal options ... not every settings key"。

**从别处进入设置**
- Claude Code：聊天里的 `/config`（还有 `key=value` 形式，如 `/config verbose=true`）、`/status`（看哪些设置文件被加载了）、`/model`、`/effort`，以及权限弹窗里的"Yes, and don't ask again"，它会把规则写进 `.claude/settings.local.json`。
- Goose：Permission Rules 是独立的全屏页，从扩展列表进。
- LobeHub：设置可以用 URL 导入导出，`https://lobehub.com/?settings={...}`，支持 `keyVaults` 和 `languageModel`。但文档的例子把 `apiKey` 直接放进 URL，这和 Sumika 的规矩冲突，不建议照搬。
- LobeHub 桌面端：权限引导直接深链到 macOS 系统设置对应的隐私面板（`x-apple.systempreferences:...`）。
- Claude Code 的设置错误弹窗：JSON 错误时，启动时弹窗，可以让 Claude 帮忙修，或者退出，或者不带坏设置继续。

**危险操作确认**
- Claude Code：`bypassPermissions` 不能由项目文件开启，只能写在用户级或托管设置里。托管可以用 `disableBypassPermissionsMode` 整体禁用。
- Open WebUI：删除和清空记忆都有确认框，正文写"This action cannot be undone"（此操作无法撤销）。
- Cherry：需要重启的设置用 `app.relaunch` 弹确认框。

**保存方式**
- 自动保存（即时）：Claude Code 的 `/config` 选中即写文件；Claude Code 的设置文件改了会热加载（`permissions`、`hooks`、`apiKeyHelper` 等）。
- 生效需重启或新会话：Claude Code 的部分键只在会话启动时读（文档列了 `model` 等，但它们有 `/model`、`/effort` 这类会话内切换入口）；Goose 的默认模式只对新会话生效；Claude Code 的 `outputStyle` 从下一条消息开始生效；Cherry 外观项要重启。
- 点保存：Open WebUI 的 General 页有 Save 按钮，源码里有 `Save`。LobeHub 的设置是即时写入，未找到"保存"按钮。

**恢复默认、导入导出**
- 导入导出：LobeHub 支持 URL 导入导出（见上）。Claude Code 没有设置导入导出，但 `--settings` 可以单次传入 JSON 或文件路径。
- 恢复默认：未找到。Claude Code、Codex、Goose、Cherry、OpenHands 的源码和文档里都没有搜到统一的"恢复默认"按钮。

### 4. 值得借鉴的设计

1. **权限模式用一句话说明，并写明对新会话和已有会话的影响。** 出处：Goose `crates/goose-provider-types/src/goose_mode.rs`（Auto、Approve、SmartApprove、Chat 四档，每档一句话），以及 `ui/desktop/src/components/settings/chat/ChatSettingsSection.tsx`（"新会话使用此模式，已有会话保持当前模式"）。对 Sumika：审批模式的几档都要有这样一句说明，并写清对当前会话是否立即生效。

2. **设置来源分层，并让用户能看到值来自哪一层。** 出处：Claude Code 官方文档 settings 页，四层（托管、命令行、项目本地、项目共享、用户），官方还给了 `/status` 的"Setting sources"行，显示哪些文件已加载。同时规定：高层覆盖低层，列表类键合并而不是覆盖。对 Sumika：数据目录的 yml 和界面设置有多层来源时，设置页可以标"来自哪里"，避免用户改了不生效。

3. **危险开关不能由仓库或项目文件开启。** 出处：Claude Code 官方文档 settings 页，`permissions.defaultMode` 的值 `auto` 和 `bypassPermissions` 不从项目或本地文件生效；`examples/settings/settings-strict.json` 和 `settings-bash-sandbox.json` 给了组织的收紧样例。对 Sumika：和 AGENTS.md 的"只有主人 × 主窗口能用执行类工具"一致，危险档位只允许从用户级配置或界面里开启。

4. **设置搜索做成注册表，新分区不注册就搜不到，并允许中文别名。** 出处：Cherry Studio `src/renderer/components/settingsMenu.ts`（注释写"添加设置分区必须在这里注册，否则搜不到"）；`src/renderer/pages/settings/GeneralSettings/general.search.ts`，里面的 `aliases` 有"开机自启"、"自启动"这类中文别名。对 Sumika：设置页搜索可以照这个结构做，中文别名直接写进注册表。

5. **网络类设置带测试按钮，测试结果分类报告。** 出处：Cherry `GeneralSettings.tsx` 的代理区，单选三档（不用、系统、自定义），测试结果分为直连、经代理、绕过、回退，错误分超时和不可达。对 Sumika：QQ 或模型服务商的连接设置，也可以加"测试"按钮，并把失败原因分类，比只报"失败"有用。

**不建议照搬的：**
- LobeHub 把 `apiKey` 放进 URL 参数的设置导入（`docs/self-hosting/advanced/settings-url-share.mdx`）。这违反 Sumika"密钥不进 URL、不进日志"的规矩。
- Codex 把大部分设置放在 TOML 文件里，界面覆盖不全。Claude Code 的 `/config` 也只列部分键，文档明说"not every settings key"。两者都让用户在文件和界面之间来回找。Sumika 如果做界面，建议要么覆盖全部键，要么在界面上明确标出"还有哪些只能改文件"。

**可以参考但要小心的：** OpenHands 的设置表单由后端返回的 schema 生成（`src/hooks/query/use-agent-settings-schema.ts`，请求 `SettingsService.getSettingsSchema`）。这样新加的配置项不用改前端，但要求后端 schema 稳定，适合 MCP、插件的配置表单，不适合核心的权限类设置。
