## 一、结论先行

T3 Code 是一个**只做“控制台”的壳**：不自己写智能体，而是把 Codex、Claude Code、Cursor、OpenCode 等现成命令行智能体统一接成“线程”，自己管线程列表、审批、diff、worktree、排队，并且服务端和界面分离（网页、桌面、手机都连同一个服务端）。Sumika 的智能体内核是自己写的，所以它最核心的“多后端适配层”我们**现在用不上**；值得借的是壳里的几处细节和一个性能纪律。

最值得借的三点：

1. **长会话的“有预算的窗口”**：冷开和翻页按约 1 MiB 编码字节、10 个用户轮、500 行封顶；工具的大输出不进事件，走单独的“命令输出中转站”，展开那一行才订阅。理由：这是它最硬的性能纪律，而且有会红的预算测试；Sumika 的聊天历史要上万条，正好同类问题（ADR-056 要求量卡顿）。
2. **线程分区加撤销通知**：置顶 / 进行中 / 已收起（settled）/ 贪睡（snoozed）/ 归档，拖动即换状态，每次状态变化弹 5 秒“撤销”，`mod+z` 触发最近一次。理由：Sumika 会话列表现在只有归档，主人跑多条线时缺“放一边”的状态；撤销通知便宜、体验提升大。
3. **“从这条重新说”**：在已发的话下点“从这里编辑”，对话回退到那句话之前，可选“只回退对话”或“文件也回到那一轮之前”；文件回退仅在独立 worktree 里提供，且别的会话也占着该目录时拒绝。理由：Sumika 已有 `native/internal/checkpoint`（在分支上、未合 main），缺的是把它和“回退对话”接成一个入口，并照它的拒绝条件做保护。

好评和吐槽的归纳在第三节。一句话：好评集中在“一个界面管多个智能体、手机能远程、开源能 fork、diff 按轮次”，吐槽集中在早期不稳、默认 Full access、默认遥测、worktree 吃磁盘。

## 二、它本身是什么（架构）

### 2.1 形态与技术栈 [读码]

- 一个 Node 的 WebSocket 服务端包住各家智能体的命令行或 SDK，网页、桌面（Electron）、手机（React Native）三个客户端连它（`AGENTS.md:1-3`、`README.md:3`）。monorepo：`apps/{server,web,desktop,mobile,marketing}`，`packages/` 里有 `contracts`（线上协议的类型）、`client-runtime`（三个客户端共用的连接和状态）、`provider-*`（各家智能体适配）、`source-control-*`（GitHub、GitLab 等）。
- 网页：React、TanStack Router、Zustand、Tailwind 4、Base UI 组件、dnd-kit 拖拽、**LegendList 做消息虚拟列表**（`apps/web/package.json:15,24,30,41,93`；`components/chat/MessagesTimeline.tsx:49`）、**Tiptap 做富文本输入框**（`package.json:42-56`）、`@pierre/diffs` 与 `@pierre/trees` 做 diff 和文件树（`package.json:32-33`）。
- 服务端用 Effect 写（`docs/internals/effect-services.md`），SQLite 存状态（`~/.t3/userdata/statev2.sqlite`，`AGENTS.md` 测试数据一节）。
- 它给自己定的四条“永不妥协”：开源、性能、远程可用、多端（`AGENTS.md:9-31`）；Theo 的话：“最小的模型，让正确行为不令人意外”。

### 2.2 怎么接各家智能体 [读码]

- 一个统一的适配器接口 `ProviderAdapterV2SessionRuntime`（`packages/provider-core/src/server/ProviderAdapter.ts:617`）：`ensureThread` / `resumeThread` / `startTurn` / `steerTurn`（:661）/ `interruptTurn`（:677）/ `respondToRuntimeRequest`（:689）/ `readThreadSnapshot` / `rollbackThread` / `forkThread`，加一条事件流 `events`。事件类型是个联合：`provider_turn.updated`、`node.updated`、`turn_item.updated`、`command_output.delta`、`runtime_request.updated`、`plan.updated`、`turn.terminal` 等（`:75-190`）。
- 适配器自己声明**能力**，上层按能力分支而不是按名字分支：会话、线程（能否回滚、分叉）、轮次（能否中途插话、能否靠“中断再重开”实现插话）、审批、子代理、检查点等十一类（`docs/orchestration-v2/provider-capability-system.md:1-60`）。能力说谎会出事：Antigravity 能存检查点但不能回滚对话，所以回退在改文件**之前**就拒绝（`docs/internals/providers.md` “Capabilities must describe…”一段）。
- Claude 走官方 Agent SDK（`apps/server/package.json:39`；`ClaudeAdapterV2.ts:67`），Codex 走它自己写的 `effect-codex-app-server` 包，说 Codex 的 app-server JSON-RPC 协议（`CodexAdapterV2.ts:82-84`）。适配器文件合计约 8 万行测试和实现（`wc -l`）。
- 不把某家的字段泄漏给别家：“应用 id 是主键，provider id 只是引用”（`docs/orchestration-v2/README.md` 不变量 1-2）。换 provider 时在线程里插一份**交接摘要**，回到旧 provider 时续它原来的原生线程加增量摘要（`provider-switching-and-context.md:1-45`）。
- 同一个驱动可以开多个“实例”（两个账号），按实例路由，互不共享可变状态（`providers.md` 开头）。探测健康时不许有副作用：开会话可能启动 MCP、跑钩子、弹登录浏览器，所以探测只做初始化（`providers.md` “Setup must not happen as a health-check side effect”）。

### 2.3 事件溯源与线程模型 [读码]

- 概念：`AppThread` > `Run`（用户可见的一轮）> `ExecutionNode` 树（工具、审批、子代理）；provider 线程只是挂在下面的原生句柄（`orchestration-v2/README.md` “Minimal Mental Model”）。只有根节点完成才算这一轮完成，子代理先完成不影响父轮。
- 命令先决定事件，**不做任何外部 I/O**；`EventSink` 在同一个数据库事务里提交事件、投影、命令回执和待执行副作用（outbox）；副作用由 effect worker 在提交之后执行并把结果喂回来（`docs/internals/overview.md` “Durable intent and side effects”）。命令回执保证重试幂等。
- 事件日志只留约一天（供断线重放和命令重试），旧事件被投影维护删掉，所以**投影不能从日志重建**（同文件）。
- 检查点：用**隐藏的 git ref**（`GitVcsDriver.ts:1298` 的 `update-ref`）记录工作区状态，不往用户分支加提交；`CheckpointStore` 提供 capture / restore / diff / listAuthoredPaths / delete（`checkpointing/CheckpointStore.ts:44-67`）。Codex 的 `turn/diff/updated` 通知被它主动关掉，diff 全从检查点算（`providers.md` 最后一段）。

### 2.4 流式与长会话性能 [读码，预算数字来自 `docs/internals/performance-regressions.md`]

- 冷开和历史翻页约 1 MiB 编码字节封顶；含用户轮的窗口再限 10 个用户轮（旧页 20）或 500 行，其他窗口 75 行。查询在解码前就按同一规则截。
- 原始命令输出、动态工具结果体、内联文件改动体**在线上边界被丢掉**（保留失败标志和结果 id），要看才取；推理文本、命令行、搜索结果在展开那一组工作时才发。
- 命令实时输出走 `orchestration.subscribeCommandOutput`，只有展开的命令行才订阅；输出增量**不是**编排事件，先进 `CommandOutputHub`，每条命令留一个有界尾巴，每个订阅者限速（`CommandOutputHub.ts`）。理由原文：忙碌的命令会淹没事件库、阻塞所有线程的写入。
- 重连先尝试回放至多 128 个线程事件 / 1 MiB，超了就退回快照。左侧栏的初始数据只含活动线程，归档单独查询。
- 预算写成测试：`vp run test:perf:v2-wire`，传输预算集成测试给 900 行的一轮和“全是已收起线程的侧栏”各设了解码字节和行数上限。
- 前端纪律（`docs/internals/web-ui.md`）：React Compiler 全开，lint 禁手写 `useMemo/useCallback`；大组件的处理函数用稳定回调，避免旧渲染的闭包留在内存里；虚拟列表滚动位置在换线程时于绘制前恢复（`MessagesTimeline.tsx:711-716`）。

### 2.5 审批和权限 [读码 + 文档]

- 四档运行模式：`approval-required`（监督）/ `auto-accept-edits` / `auto`（用 provider 自带的自动审查）/ `full-access`（`packages/contracts/src/providerPolicy.ts:25-32`）；**默认是 full-access**。每线程设置，项目可覆盖环境默认；管理员的“托管策略”可以给上限（`providerPolicy.ts:36-45`，`managed-policy.md`）。
- 审批卡四个回答：取消 / 拒绝 / 本会话总是允许 / 批准，主按钮只露“拒绝”“批准”，其余收进“更多”菜单；选项可带警告图标和提示（`components/chat/ComposerPendingApprovalActions.tsx:25-30,41-48`）。子代理的审批显示在父会话里并写明子代理名字（`permission-modes.md`）。Claude 有一条：审批挂着时直接打字回复 = 拒绝并把话当反馈告诉那个代理。
- 异步问题（Codex 的提问是通知，不是等待中的 RPC）被存成持久的 `user_input_request`，答案和一条用户消息在**一个事务**里提交，重复提交只回同一个回执（`providers.md` “Protocol traps”）。

### 2.6 排队、插话、停止 [读码]

- 三种发法：原位插话（provider 原生支持）、“中断再重开”式插话、排到下一轮（`feature-lifecycles.md:60-101`）。服务端命令里 `deliveryIntent: auto | steer | restart`（`contracts/orchestrationV2.ts:3206`）。
- 边界处理很细：界面还显示在跑、实际上这一轮已完成时，插话自动变成新一轮（`Orchestrator.ts:5941-5957`）；停止之后的普通发送自动排队，不再往一个收不到的轮里插话，并解除停止的暂挂（`:5958-5967`）。
- 停止 = `run.interrupt` + `holdQueue`：同时暂挂队列、结束该线程的 PR 监视、丢掉子任务欠的唤醒，并**深度优先**停掉所有委派子线程（`feature-lifecycles.md:254-260`）。中断请求返回不等于已停，要等 provider 发回终态（同文件 :235-245）；超时单独有错误类型“provider 没在时限内确认停止，进程可能还在跑”（`ProviderAdapter.ts` `ProviderAdapterInterruptTimeoutError`）。
- 界面：设置里选“后续消息默认排队还是插话”；`mod+Enter` 取相反；`mod+shift+Enter` 把最早排队的一句改成插话；光标在输入框开头按 `Alt+↑` 编辑最近排队的一句（`docs/user/composer.md` “Send while the agent is working”）。排队列表最多先显示 3 行，其余折叠（`QueuedRunsControl.tsx:52`），每条可编辑、取消、升级为插话，排队内容存在**服务端**（手机重启也在）。

### 2.7 diff、worktree、线程管理 [文档 + 读码]

- 线程可以各开一个独立 worktree；新线程可“同一个提示发给多个模型”（按住 Shift 点模型），每个模型一个线程一个 worktree。diff 面板按**轮次**看（检查点之间的 diff），也有 PR 文件已读标记、行内评论（`components/diffs/AnnotatableCodeView.tsx`、`DiffCommentAnnotation.tsx`）。
- 线程分区：置顶、活动、已收起、贪睡、归档；服务端按 PR 合并或闲置自动“收起”（`ThreadSettlementService.ts`，`overview.md` “Thread settlement is server-owned”）；服务端存顺序，多设备同步。
- 不挂项目的线程各有一个 `~/.t3/scratch/日期-首句-短id` 文件夹，之后可“变成项目”（`thread-sidebar.md`）。
- Worktree 默认不自动清理，社区有人清出 500 GB，设置里有“自动清理”（`docs/user/faq.md:76`）。

### 2.8 输入框与键盘 [读码 + 文档]

- 键位是可编辑的规则表，每条 `key + command + when`，`when` 是布尔表达式（如 `composerFocus && draftThreadRoute`），冲突按“快捷键加上下文”检测（`packages/contracts/src/keybindings.ts:1-110`、`apps/server/src/keybindings.ts:85-130`）。命令约 90 个：线程跳转 `thread.jump.1-9`、模型选择器 `modelPicker.jump.1-9`、`thread.stop`、`thread.undo`、`composer.stash`、`diff.toggle`、`commandPalette.toggle` 等。
- 输入框：富文本（按 Markdown 实时渲染，光标进来显示标记）；粘贴 ≥32 KiB 自动变文本附件；↑ 在空输入框回看上一条发过的话；`Ctrl+S` 暂存草稿（含附件，附件保留 24 小时）；“引用到输入框”可给引用的那段回复加评论；可选的“建议下一句”（Labs，复用提示缓存，Tab 采纳）；语音输入。
- 命令面板：线程、项目、主题、动作混排，结果行按视口租用 VCS 和 PR 查询，滚出视口就释放（`performance-regressions.md` “Command palette results…”）。

### 2.9 给智能体用的编排 MCP [文档]

- 服务端在 `127.0.0.1:<端口>/mcp` 开一个带令牌的 MCP，provider 会话启动时按“环境 + 父线程 + 实例 + 会话”发凭据，会话结束作废；工具包括建子代理、等结果、取消、列线程、增量读线程、发消息、改名、定期任务（`orchestrator-mcp-server.md:1-60`）。理由：“用户能触发的能力，智能体也应该能通过 MCP 触发”（`AGENTS.md` “Agents.”一条）。

## 四、对 Sumika 的启发（逐条：优势、思路、能变成什么、底子、做不做）

### 4.1 有预算的历史窗口和输出分流  —— 做（挂界面缺口里的长历史验收）

- 优势：长会话冷开不卡、不丢滚动位置，预算有测试守着。
- 思路：把“发给界面的量”当成需要预算的资源：字节上限 + 条数上限 + 大结果体延迟到展开，实时输出走旁路而不是进事件库。
- 在 Sumika 里：mygo 聊天区按窗口取历史，工具输出和命令输出体只给摘要，展开才取；命令实时输出走单独通道、有界尾巴。
- 底子：Go 后台已有 history 包和会话分页（`native/internal/history`），聊天视图有渐进加载测试（`native/chatviewer_progressive_test.go`）；ADR-056 要求十个角色上万条消息实测。没找到“按字节预算”和“输出体延迟”的现成做法，需要核对 `docs/subsystems/runtime.md` 后再定具体数字。
- 现在做：做，但只借“预算写进测试”这个习惯，数字按我们自己的实测定，不照抄 1 MiB / 500 行。

### 4.2 线程分区、拖动换状态、撤销通知  —— 做撤销通知；分区以后

- 优势：多线并行时，“放一边”和“收起”让列表保持干净；撤销比二次确认轻。
- 思路：状态是服务端存的；每个状态变化可撤销 5 秒；拖拽时只显示将发生的动作。
- 在 Sumika 里：本地私聊会话列表加“置顶 / 收起 / 贪睡”，归档、收起、删草稿都弹“撤销”。
- 底子：`native/convlist.go` 有会话列表，有归档（`docs/信息架构.md`）；没有贪睡和自动收起。
- 做不做：撤销通知先做（小、通用、符合“反向状态要有出口”）；贪睡、拖动、自动收起以后，等主人真的多线并行再说。

### 4.3 从这条重新说（回退对话 + 可选回退文件）  —— 以后，先把检查点合进 main

- 优势：改主意不用开新会话；文件回退有明确的拒绝条件，不会误伤别的会话。
- 思路：对话回退和文件回退是两个选项，文件回退只在隔离目录里提供；provider 不能回滚对话时，**先拒绝再动文件**（`providers.md` “Capabilities must describe…”）。
- 在 Sumika 里：“从这里重发”入口，沿用 `native/internal/checkpoint` 的预览和恢复，对话回退走内核历史截断。
- 底子：检查点和恢复接口已写在 `feat/checkpoint-lsp` 分支，未合 main（`docs/subsystems/agent-and-console.md` “Go 检查点动作接口”）。
- 做不做：以后。前置是检查点先合 main；Sumika 没有独立 worktree，所以文件回退的拒绝条件要换成“这轮之后有没有别的写入者”。

### 4.4 输入框细节：↑ 回看、Ctrl+S 暂存、引用到输入框并加评论、建议下一句  —— ↑ 回看和暂存做，其余以后

- 优势：都是小动作，但天天用得到。
- 在 Sumika 里：空输入框按 ↑ 取回上一句（只恢复文字，不恢复附件，条件它写得很清楚：输入框为空、未编辑过、光标在首行）；Ctrl+S 暂存草稿含附件；建议下一句要多花一次请求，跟 /goal、/loop 的额度账一起考虑后再定。
- 底子：Sumika 的 `docs/规格-排队插话停止.md` 已有回车插话、Alt+回车排队、停止暂挂队列、重启后 held 的话可重发，**和它的做法基本同构，而且停止分三段、重启后恢复比它的文档写得更细**，这一块不用借。草稿在 `docs/信息架构.md` 有设计，没查到暂存。
- 做不做：先做 ↑ 回看与暂存，小。“键盘 mod+Shift+Enter 把排队的变插话”和“Alt+↑ 编辑排队的”可以照它的键位补进排队规格，我们现在只有每句的“取消排队”。

### 4.5 排队界面的两个细节  —— 做（补进排队规格）

- 排队超过 3 条只显示前 3 条加“展开”（`QueuedRunsControl.tsx:52`）；排队内容存服务端；**别人（访客）说的话，主人可取消不可改写**（同文件 `editable: context?.guest === undefined`）。
- Sumika 的对应：群聊里别人的话进排队时不可编辑，主人只能取消（和“不冒充”的原则一致）。底子：规格里排队只写了本地私聊，群里的来源标注要对一遍。

### 4.6 审批卡：主按钮只露两个，其余收进“更多”  —— 以后，要对照设计语言

- 它的做法：拒绝/批准在外，取消和“本会话总是允许”收进菜单；有警告的选项带图标和悬停说明；Claude 审批挂着时直接打字 = 拒绝并附反馈。
- Sumika 现状：卡上是四个回答，拒绝可写原因，写了原因就原样告诉她（`规格-审批分级.md` 第一节）。**这一点比它细**（它的拒绝没有原因输入，只有“打字回复”这个 Claude 专属路径）。
- 做不做：不照搬“收进更多”，我们四选项一眼可见更利于主人决策；“审批挂着时直接在输入框打字 = 拒绝并附原因”可以考虑，因为它把“拒绝加原因”变成零额外点击。以后，等审批卡设计复查时一起看。
- 它的**默认 Full access** 是反面教材：和 Sumika“只有主人 × 主窗口，每次审批”的安全边界相反，不借。

### 4.7 键位做成可编辑规则表（key + command + when）  —— 以后

- 优势：快捷键可查、可改、能检测冲突；`when` 上下文避免全局冲突。
- Sumika 现状：`docs/信息架构.md` 和 `界面模式规范.md` 提了快捷键，但没有“命令表 + 用户可改”的设计。
- 做不做：以后。Sumika 的焦点在输入框、命令面板、会话切换少数几个；等快捷键超过十来个再做。但“命令面板里每个动作都有同名的键位命令，名字统一”（`docs/internals/consistency-action-names.md`）这条约定现在就值得抄：给命令面板的动作起稳定的命令名。

### 4.8 能力驱动的多后端适配层  —— 不做（现在）

- 优势：加一个新 provider 不必改上层；按能力分支，不按名字。
- 为什么不做：Sumika 的智能体内核是自己的 Go 内核（`native/internal/kernel`、`turn`），QQ 和本地私聊共用一套；主人要的“多个模型”是模型切换（走 Magpie），不是接别家的智能体外壳。接 Codex / Claude Code 当后端是另一件事，且 `docs/notes/对照-成熟Agent与Sumika后台-2026-11-03.md`、`对照-Go现成Agent框架-2026-11-09.md` 已讨论过内核路线。
- 值得记一条：如果以后要让 Sumika 当壳去控别的智能体，T3 的 `ProviderAdapterV2SessionRuntime`（上面 2.2）加能力声明是现成的最好参考，并且它明确要求“能力说谎要在动文件前拒绝”。把这份笔记记作那时的第一份读物即可。

### 4.9 编排 MCP（智能体自己管线程）  —— 以后

- 优势：智能体能建子代理、读别的线程、定期任务，且凭据按“环境 + 线程 + 会话”收窄、会话结束作废。
- Sumika 底子：`/goal`、`/loop`、提醒和定期任务已有（`docs/规格-目标和循环.md`、`规格-提醒`），MCP 接入在待办里（`待办.md` 285 行）。
- 做不做：以后；做 MCP 时借它的凭据收窄方式，和 ADR-330 的 MCP 登记并看。

### 4.10 事件库只留一天、投影不可重建  —— 不做

- 这是它为了重连和幂等做的取舍；Sumika 的原始聊天库按平台分库、要长期保存（ADR-199），不能照搬。只借“命令回执保证重试幂等、副作用提交后再执行”的思路，Sumika 内核的输入号和账本已经在做同类事。

### 4.11 不借的

- 默认 Full access、默认遥测（和我们的隐私和安全边界相反）。
- 远程隧道（T3 Connect）、Tailscale、手机端：主人的使用场景是本机 + QQ，QQ 已是“远程”入口。
- 多模型同一提示并发各开 worktree：Sumika 是伴侣，不是代码并行工具。
- 不拿它的界面当样式参考：官方图是纯黑底和极简列表，主人要求的界面参考是 Claude desktop、Codex、Hermes desktop；且用户评价对它的界面两极。

## 五、顺手核对的两点

- 它的排队、停止、插话语义和 Sumika 现有规格是同一族（插话进下一个安全点、排队等整轮、停止暂挂队列）；差别在于它把“服务端存队列、手机端离线排队”做进了协议，而 Sumika 靠内核输入号和 held 恢复，已能覆盖本机场景，不需要改。
- 它的文档里反复出现的写法值得学：**每个“不变量”后面都跟着它出过的事故**（如 `pull-request-file-revisions.md` 写了接口注释与实现相反的真实事件）。我们的 LESSONS 已是同一路数。
