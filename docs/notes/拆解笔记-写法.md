# 拆解笔记的写法（2026-10-20）

> 不挂：这是写拆解笔记的规范，AGENTS「动手前先读」第 3 条和各份拆解笔记开头引用它。

起因：2026-10-20 主人看 `docs/notes/` 里参考别家客户端的笔记，"很多都很浅，都是对着当时我们设计的角度去看的，没有完整地研究过，而且也不是精确到具体设计的代码内容，可能会失真"。从这天起，拆别家客户端照这份写；以前的"对照 / 深挖"笔记照旧留着，拆解笔记写好后在旧笔记开头加一行指过去。

## 一、四条规矩

1. **先完整写它本身，不带我们的视角。** 正文按它自己的结构写（它有哪些页面、组件、状态、数据怎么流），不按"我们当时想做什么"挑着写。跟 Sumika 的对照、"可以借什么"只放在最后一节，而且单独成节。
2. **每一条都有出处，精确到代码。**
   - 开源：`仓库@提交号 路径:行号`，关键处贴 3～10 行原代码（只贴需要的那几行）。
   - 闭源但能拆包（Electron 的 app.asar 等）：拆到草稿目录（只读，不改安装目录），写 `包内路径 + 附近的标识符或字符串`；压成一行的文件写字节偏移或附近的唯一字符串，让别人搜得到。
   - 只能看的（没源码、没装）：写清是官网文档哪一页、截图存在 `data/dev/拆解-<名字>/` 的哪张。
3. **每一条标可信度**，三档：`[读码]` 读过实现代码；`[实测]` 跑起来量过、看过；`[推断]` 只凭名字、文档、上下文推的。`[推断]` 不能写成结论句。
4. **具体到能照着做**：尺寸、间距、圆角、颜色、时长、曲线、阈值、条数上限、默认值、状态有哪几种、什么时候切换、错误怎么显示——有数就写数，有枚举就列全。

## 二、一个客户端拆成几份

文件名 `拆解-<名字>-<部分>.md`，部分按需要挑：

| 部分 | 写什么 |
|---|---|
| `总览` | 版本、许可证、技术栈（库和版本）、目录结构、进程和模块怎么分、数据存哪；全部页面 / 组件清单（每个一行，链到下面几份）；最后一节"对 Sumika 的启发"（这是唯一能写对照的地方） |
| `界面` | 每个页面、每个组件：长什么样（结构、尺寸、颜色令牌、圆角、阴影）、有哪些状态（空、加载、出错、选中、禁用……）、在不同窗口宽度下怎么变 |
| `交互` | 每个操作从按下到结束的完整流程：键盘快捷键、焦点去哪、确认和撤销、拖放、右键菜单、通知；状态机写成"状态 → 事件 → 新状态" |
| `动效` | 每个动效：触发、属性、时长、曲线或弹簧参数、进和出的差别、减少动态效果时怎么办 |
| `架构` | 前后端通信（协议、事件名、消息格式）、会话 / 消息 / 工具调用怎么存、断线重连、长对话怎么处理、模型调用和提示词怎么拼、权限和审批怎么判 |

每份开头写：看的是哪个版本（提交号 / 安装包版本）、怎么拿到的、哪些没看（没看的明确写出来，别让人以为看全了）。

## 三、不做的

- 不抄大段代码和提示词原文（版权；关键几行可以引）。闭源应用里的提示词只转述行为和数字。
- 不运行来路不明的程序；不改安装目录；拆包、克隆都放会话草稿目录，结论落进这里。
- 不为了"对我们有用"删掉它本身的内容。
