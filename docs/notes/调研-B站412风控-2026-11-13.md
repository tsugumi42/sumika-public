# 调研：B 站 412 风控（2026-11-13）

> 挂：[待办](../待办.md)“B 站链接补齐的收尾”；改动在分支 `fix/bilibili-412`（`native/internal/linkreader`），做法和没做的事见本文第五节。

起因：2026-11-13 主人确认 B 站的 412 连累到本人浏览（本机共用出口 IP）。拍板：412 以及等价的风控码算限流，整个 bilibili 平台冷却；按调研做“减少触发”的正当客户端改动；不做伪造登录、借账号或 cookie、代理池换 IP、绕验证码。

本轮调研没有请求任何 B 站接口，只读源码、文档和本地代码。**有依据的**和**推测的**分开写。

## 一、412 机制要点

有依据的（按证据强度）：

1. **412 有两层含义。** HTTP 状态 412 和 JSON 码 -412 都当风控处理。fork 文档 `errcode.md` 把 -412 写成“请求被拦截（客户端 ip 被服务端风控）”，即 IP 级别（Goooler 的 fork，非上游快照，未验证）。
2. **412 是 IP 级风控。** 本地笔记 `data/dev/bilibili-link-coverage/01-源码盘点.md:107` 记录，2026-10-30 的匿名动态 feed 请求第一次就 412：IP 的信誉可能已经被标记，不只是请求量超标。
3. **-352 与 UA、WBI 参数有关。** fork 文档 `errcode.md:34`：“UA 或 wbi 参数不合法”。我们自己的实测也支持：只写 `Mozilla/5.0` 时 `seasons_archives_list` 回 -352；curl UA 访问专栏也回 -352（`专栏正文取法.md:41`）。
4. **频率类错误码。** -799（请求过于频繁）、-509（超出限制）见 `errcode.md:45、61`；我们的记录里 `x/space/arc/search` 无签名回 -799，专栏 `x/article/view` 回 -509（`覆盖表.md` 第 3 节）。
5. **WBI 签名是 Web 端的签名鉴权。** `wbi.md:3` 称“目前被认为是一种 Web 端风控手段”（文档说法，未验证）。我们的记录里 `x/v2/reply/wbi/main` 无签名回 -403，所以评论走旧接口 `x/v2/reply`。
6. **yt-dlp 对 412 不退避。** `ytdlp_bilibili.py:1405-1414`：412 直接抛“please wait and try later”，-352 抛“rejected”，不重试、不 sleep。
7. **PiliPlus 对 412 不特判。** 重试拦截器只对网络层错误重试，带 response 的错误（含 412）直接透传（`lib/http/retry_interceptor.dart`）。

推测的（无数据支撑）：412 的解除时长（分钟还是小时）、IP 信誉阈值、同一 UA 多久请求量会触发、随机 UA 是否有效、`bili_ticket` 是否真的降低风控概率（fork 文档称“可降低”，来源是社区 issue #903，未验证）。

## 三、改动前我们缺什么

1. 412 之后没有冷却，且会连发：限速只在 429 时冷却；`biliView` 遇 412 后依次发 nav、wbi/view，-352 时再来一轮，一条被 412 的链接发 3 到 5 次请求。
2. 默认 UA 是裸串 `Mozilla/5.0`，正是本地实测触发 -352 的写法；只有合集接口一处特例换了 UA。
3. 生产环境没有请求间隔（`channel.go` 没传 `MinInterval`）；预算每分钟 10 次，可以瞬间打完。
4. 网络层重发那一次 `client.Do` 没经过预算。
5. 访客标识（finger/spi）只在专栏路径、风控之后才带；普通请求完全不带 Cookie。
6. WBI 签名只在 view 风控后才加（先发裸请求，再签名重试）。
7. B 站请求直连，用本机出口 IP：风控会连累本人浏览。

## 四、没有实现的（超出“正当客户端”边界）

- 伪造设备或风控指纹：PiliPlus 的随机 payload、yt-dlp 的 `dm_img_*`、biliup 的本地随机 buvid、APP 端 BUVID 和 fp 算法。
- 复刻前端风控票据：`bili_ticket` 的 hmac 票据（效果未验证）。
- 代理池换 IP、借用登录账号取数。

## 五、实现情况（分支 fix/bilibili-412）

规格和参数见[规格-链接解析 4.2.2](../规格-链接解析.md)，代码在 `native/internal/linkreader`。对应第四节推荐清单：

| 序 | 做了吗 | 说明 |
|---|---|---|
| 1 冷却 | 做了 | 412、-352、-412 平台冷却 15 分钟起翻倍到 2 小时；-509、-799 冷却 5 分钟；412 后不再做 nav、wbi 重试；专栏不再请求 `x/article/view`（它匿名常回风控码，会连累整个平台） |
| 2 UA | 做了 | 所有 B 站请求用固定版本的桌面 Chrome UA，删掉合集接口的特例 |
| 3 请求间隔、下调预算 | 没做 | 调研标为推测，每条视频链接要多等 4 到 6 秒，预算数值没数据定；冷却、请求头上线后 412 还回来再做。网络重发计入预算：做了 |
| 4 访客标识 | 做了 | 首次请求 api.* 时取一次 `finger/spi`，缓存 6 小时，只带 api.* 主机；取不到不挡主请求 |
| 5 WBI | 没做 | 当前所有接口都是不要求签名的老路径（没有 `/wbi/`），没有要签的；原先 view 风控后的签名回退已删 |
| 6 记录次数、告诉用户 | 没做 | 冷却中请求返回 `rate_limited`，评论等已有文案；次数统计没有消费者，先不加 |
