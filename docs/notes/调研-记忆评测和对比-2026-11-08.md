# 调研：记忆整理的质量门槛，和成熟记忆系统怎么对比（2026-11-08）

> 参考来源（主人 2026-11-08 原话）："整理也可以开一下用来测试效果，应该有一个清晰的门槛来确认整理的质量。有没有相关的比较成熟的测试可以用来对比？最好是可以跟那些已经有的其他优质、成熟的记忆系统进行测试对比。"另问："那个记忆系统设计还可以一直持续优化下去吗？"
> 参考过：`docs/notes/对照-成熟记忆系统-2026-11-07.md`（系统设计对照，本篇不重复）、`docs/archive/notes/调研-表二评测出题-2026-10-27.md`（题库核对）、`data/dev/memory-eval-/报告-复测3.md`（整理提示词自建样本重测）、codex/memory-quality 分支上的 `docs/规格-记忆质量.md`（main 上还没有这份）。
> 方法：WebSearch / WebFetch 查摘要页和厂商页，**没有读论文全文**；分数几乎都是作者或厂商自报，标"自报"；查不到的标"未核实"。试跑在本机用临时目录、不碰 `data/`，共 183 次 `auto/claude-haiku-5-5` 调用。

## 先说结论

1. **bench-t2 不能直接用来量"整理"。** 它的 B4 `-c` 题只测"压缩上下文以后 agent 还答不答得出来"（Go 壳里 `compact` 调的是 `hub.Compact`，写 `context_epochs` 摘要），不经过 `prompts/summarize-v2.md`，也不经过 `SummarizeBatch`。整理要另量。
2. **没有哪个公开基准专门打分"写入侧"。** LongMemEval、LoCoMo 等都是端到端：灌对话、提问、看答案对不对。想量整理本身，要两层：自己口径的写入指标（召回、误记、重复、矛盾），加一个端到端的小子集（LongMemEval）做和别家的对照。
3. **建议的对比基准是 LongMemEval，不是 LoCoMo。** LoCoMo 有第三方审计称答案键错误率 6.4%、判分器会放过 62.8% 的故意错答（审计方自己的结论，未经同行评审），另外 mem0 与 Zep 为它公开互相质疑。LongMemEval 有弃答题、知识更新题，更贴近"整理"要做的事。
4. **公开分数不能直接和我们比。** 模型、判分器、嵌入、托管版还是开源版都不同，MemDelta 一类的工作已经证明只改嵌入模型就能让结论翻转（见第二节）。能比的只有"同模型、同数据、同判分"下自己跑出来的数。
5. **试跑结果（16 题，写入侧→回答）：整理后的记忆答对 10/16（排除弃答题 9/15 = 60%），同一批题给完整原始对话答对 13/16（12/15 = 80%），什么记忆都不给 1/16（只对了弃答题）。** 样本很小，不能当结论，只证明这条路走得通、能出数字。

**两个必须记住的警告：**

- [MemDelta](https://arxiv.org/abs/2606.29914)（2026-06，单人论文，摘要）在 LongMemEval-S 上一次只改一个变量：只换嵌入模型准确率就差 6.2 个点；Mem0 比 MiniLM-RAG 高 11 点、比云端嵌入 RAG 低 1.2 点；全文塞进上下文和 RAG 谁强取决于模型家族；agent 自己管记忆（42%）不如普通检索（47%）。结论：**同一个嵌入、同一个答题模型、按题型分开报、写入成本一起报**。
- 同一批 gpt-4o-mini 答案换一版判分提示，LoCoMo 分数能从 55.8% 到 81.4%（[来源](https://braindetox.kr/en/posts/memory_benchmark_scores_reliability_2026.html)，二手分析）。所以判分提示和判分模型必须钉死，并随结果一起存。

## 三、bench-t2 现状

- **是什么**：`native/cmd/bench-t2` 是"表二"统一执行器（656 行）：读 `scripts/bench-t2/tasks/` 的题库，每次（题 × 壳 × 第几次）建临时目录起壳（Go 自己的壳或 omp），量资源，从 Magpie 网关账本对回请求，结果写 `data/dev/bench-t2/<时刻>/`；有 `-dry`（不调模型，查判分不是恒真）。题库有 b1（工具任务）、b2、b3、b4（记忆）、b5（从日志统计）。
- **B4**：`scripts/bench-t2/import-longmemeval.ts` 从 LongMemEval cleaned oracle 裁 10 问：事实 3、改主意 2、合起来 2、没有答案 3；每问各出 `-c`（压缩一次再问，`keepTokens: 1000`）和 `-n`（不压缩的对照）两道，共 20 个任务；答案是几种说法的包含匹配，改主意的另写旧值，回复里说到旧值判"要人看"；只能叫 Sumika-B4，不是官方分。
- **它测的是什么**：在 agent 里灌一段长历史，手动压缩上下文，再问。Go 壳的 `compact` 步骤调 `hub.Compact(...)`，摘要写 `context_epochs`（`native/cmd/bench-shell/main.go` 第 235～242 行）。**整个过程不跑整理提示词。**
- **缺什么（对"量整理"而言）**：① 不覆盖整理（summarize-v2、证据升级、取代、撤销）；② 只有 10 题，且全是英文；③ 判分是包含匹配，对"主观偏好、需要推理的答案"不够；④ 不量误记、重复、矛盾；⑤ 每次要起一个完整 agent 壳，慢且贵，不适合改一句提示词就跑；⑥ 没有和别家系统对比的通路。
- 本次没有跑 bench-t2 的 `-dry`（前提不成立，没必要）。已有的 `native/cmd/memory-shadow`（离线整理影子，真实生成器被 `realGenReady = false` 关着，见复测报告）和 `cmd/memory-eval`（只量召回）也都不是端到端基准。

## 四、建议的门槛

分两层。**第一层是硬门槛，第二层是和别家比的参考，不当合并条件。**

### 第一层：写入侧（自建样本，自己的口径）

照 `docs/规格-记忆质量.md` 已有的约定："不足正负各二十条不宣称完整质量验收"、"三轮同方向才说改善"。样本的真实聊天部分只放本机，不进仓库。

| 指标 | 定义 | 建议的"过"线 | 依据 |
|---|---|---|---|
| 抽取召回 | 标了"该记"的正例里，至少有一条动作记到了该事实（宽松），另报严格口径 | ≥ 80%（独立新样本，不是调提示词用的那批） | 复测报告已建议"召回 ≥ 80%"；复测 3 独立批只有 71% / 69% |
| 误记率 | 负例窗口里写出 upsert / candidate 的比例；先剔除"窗口里其实有别人说的真实事实"再报 | ≤ 5%（原口径别超过 15%） | 复测报告建议 ≤ 15%；剔除后 4% 已经达标，建议把线收紧，并同时报两个口径 |
| 无依据扩写 | 误记里"把一句感叹扩成具体事实"的占比（复测里的 W05 那种） | 0 条算过，≥ 1 条要人看 | 复测 3 的真误记全是这一类 |
| 重复率 | 一批里与已知事实 / 候选意思相同却又新写一条的比例 | ≤ 5% | 业界通行口径没有统一值，**此线是我的建议，未核实**；Mem0 开源版"只新增不去重"是已知弱点 [来源](对照-成熟记忆系统-2026-11-07.md) |
| 取代正确率 | 该用 `supersedes` 的更新题里，旧事实被正确取代、且没误伤别的 | ≥ 90%；误伤 0 | Zep 的失效误伤是已知 issue（#1728），对照 MemoryAgentBench 的选择性遗忘一项 |
| 矛盾残留 | 一次整理后，同一主体同一属性同时有两条有效事实的比例 | ≤ 2% | 同上，建议值 |
| 解析失败 / 非法动作 | JSON 解析失败、引用了没出现过的编号 | 0；试跑 87 批为 0 / 0 | 试跑实测 |
| 弃答 | 记忆里没有的事，答题时不编 | 弃答题 100%（试跑 1/1） | LongMemEval 的 `_abs` 口径 |

每次改动固定样本 + 固定种子；**两遍不一致比例**也要报（复测里有）。门槛以三轮同方向、且独立批通过为准。

### 第二层：端到端（LongMemEval 子集，和别家比）

- 子集：从 oracle 里按题型分层抽 50 题（含 ≥ 5 道 `_abs`），种子写死，抽题清单存仓库。
- 报：总体准确率、按题型分开的准确率、弃答准确率，**同时报"完整原文给模型"的上限和"什么都不给"的下限**，再算 **保留率 = 整理后答对 ÷ 上限答对**。保留率比绝对准确率更能说明整理丢了多少（试跑：8/12 ≈ 67%）。
- 建议的过线：**保留率 ≥ 85%、弃答 ≥ 90%**；这是我的建议值，没有公开口径可引（未核实），先当"目标"，等 50 题的数出来再定。
- 判分钉死：同一个判分模型、同一份判分提示（试跑里是照 LongMemEval 官方五类判分意思写的英文提示，**不保证逐字相同**，未核实），保存每题答案和判定。对外只叫 "Sumika-LME50"，不叫官方分。

## 五、对比方案（具体步骤）

统一条件：答题和判分模型 `auto/claude-haiku-5-5`（Magpie `http://127.0.0.1:3425/v1`），同一批 50 题，同一份判分提示，同一个嵌入模型（本地 gte-multilingual-base 或 mem0 开源默认，统一选一个）。

**A. Sumika（已能做，试跑脚本即雏形）**

1. 把试跑脚本（`scratchpad\membench\run.py`）整理成 `scripts/memory-bench/`（Bun/TS 还是 Go 由主会话定；Go 版放 `native/cmd/memory-bench` 更贴合"整理走真实代码"）。关键是**让整理走真实的 `SummarizeBatch` 和解析代码**，而不是脚本复刻提示词；复刻只能验证提示词，验证不了解析和事务保护。
2. 抽题：`python run.py plan` 同类脚本按种子分层抽 50 题，输出题单。
3. 提取 → 回答 → 判分三步缓存、可断点续跑，每步记调用数。
4. 回答侧要**加上真实召回**：现在试跑是把全部记忆条目塞给答题模型，等于没过 `recall.go` 的门控和 8 条上限。第二阶段改成建临时记忆库，用 `cmd/memory-eval` 同款的召回取前 8 条再答题，两版（全给 / 召回 8 条）都报。

**B. mem0 开源版（装依赖，等主会话定）**

1. `git clone https://github.com/mem0ai/memory-benchmarks`（Apache-2.0），放 `_external\`，用独立虚拟环境。
2. 读它的 README 确认参数；已知有 `--backend oss`、`--predict-only`、`--evaluate-only`（来自搜索结果，具体选项名未核实）。后端用 `oss`，向量库用它默认的 Qdrant（本地）。
3. 把它的 LLM（抽取、答题）和判分都指到 Magpie 的 OpenAI 兼容地址、模型 `auto/claude-haiku-5-5`；嵌入用和 A 相同的模型。**要确认它的抽取提示词用的是开源版那套，不是托管版**。
4. 题目换成同一批 50 题（用 LongMemEval 的 `question_id` 过滤）。
5. 先 `--predict-only`，再用**我们自己的判分脚本**统一判分，别用它自带的，保证两边同一把尺。

**C. Zep/Graphiti（可选，第二批）**：要装 Neo4j 或 FalkorDB，成本高，A 和 B 的数出来再决定。

**报告格式**：一张表，行 = 系统（Sumika 全给 / Sumika 召回 8 条 / mem0-oss / 完整原文上限 / 无记忆下限），列 = 题型准确率、弃答、保留率、提取调用数、提取输入输出 token、回答时每题注入 token。成本也要报（MemDelta 的建议）。

**调用量估算**（单位：次，haiku）：50 题 oracle 约 270 提取 + 150 回答 + 150 判分（三个条件）≈ 570；mem0 同量级再加它的抽取，约 ≈ 300～600；整套 500 题 oracle 约 3500～5000。**S 版只抽 50 题就要 ~4000 次提取，建议先不做。**

## 六、持续优化：做成每次改动都能跑的回归

1. **固定样本**：写入侧样本（正负各 ≥ 20，标签在跑之前写入文件）一份；LongMemEval 子集一份，种子写死。已有的 `cases*.json` 是真实聊天，只放 `data/dev/`，不进仓库；仓库里只放编造的合成样本和 LongMemEval 子集题单。
2. **固定入口**：一条命令，输入"提示词路径 / 模型 / 样本集"，输出一页：每项指标、两遍不一致数、调用数、token 数、与上一次的差。输出存 `data/dev/memory-bench/<日期>/`，别写进 worktree。
3. **独立批**：调提示词用的那批叫训练批，门槛只认没参与调整的独立批；每过一轮换一批新的（复测 3 的教训：第三批 75% 里有针对它改句的成分，独立批只有 71%）。
4. **嵌套进现有门禁**：提示词文件变化时，钩子提醒跑回归，不拦；合并说明里写数字。
5. **每次只改一个变量**：提示词、模型、嵌入、召回分开改分开报（MemDelta 的结论）。

**还有哪些大的提升空间**（结合试跑和现有规格，都是推断，需要各自单独验证）：

- **取代会丢"旧值的时间"**。试跑里 `4dfccbf7`（问"从开始上尤克里里课到决定把吉他送去保养隔了多少天"）：第一批写了"计划 2 月底带吉他去保养"，后一批写了"2 月 25 日去保养了"并填 `supersedes`，旧条目变 old，回答时只看有效条目，**"决定的日期"这条信息整个丢了**，答成同一天。规格里"取代不删、修订历史只增不改"，召回时没把"旧值 + 它的日期"一起给时间类问题。建议：召回遇到时间推理类问法时，带上被取代的旧条目和日期（或者在新条目文字里保留"原计划……"）。
- **助手方说的话不记**。`8464fc84`（助手推荐了一家店，用户后来问店名）整理没记，因为提示词只记主人的事实。对角色扮演可能是对的；对"助手做了承诺 / 给了建议"的场景要靠"角色自己做了什么、答应了什么"那一条（episode 标准里有，提示词事实栏没有）。要不要补由产品决定。
- **事实粒度粗，细节靠 episode 兜底**。试跑 87 批共写 105 条事实 + 35 条候选 + 85 段经历（几乎每批都选了 yes；私聊规则偏向 yes），平均每批 1.6 条事实。多会话数数题（`0a995998`、`9ee3ecd6`）这类需要把散在各处的小物件拼起来的题，两个都挂；但完整原文给模型这两题也都错，说明一部分是答题难，不全是整理丢信息。
- **候选当"信息缺失"**。`4d6b87c8` 里"待看列表 25 部"其实记成了有效事实，但答题模型被后面"会加入两部"的记录带着猜 27，没敢给 25。召回时把"之后又说要加"的未确认条目和确定值放一起，容易让模型自己推算。可以考虑回答侧提示"以最近一次明确给出的数字为准"。
- **整理批内去重 / 合并**：同一件事分几批写了几条的比例，试跑里没单独量，建议加进回归（重复率）。
- **召回侧**（`recall.go`）：全文 + 向量 + RRF，最多 8 条。试跑没覆盖，第二阶段补。规格里已有"RRF 判不了真没命中、要看相似度绝对值"的待办。
- **中文**：试跑用的是英文对话，提示词和记忆文字是中文；想知道真实中文表现，要用 PAL-Bench / ZH-4O（如果数据可得）或按 Ground Truth First 的办法自建中文合成样本。

**记忆系统能不能一直优化下去？** 能，前提是有这套固定回归。没有它，每次改提示词只能靠"看起来更好"，复测 1～3 已经显示同一提示词在不同批上差 10 点以上；有了它，优化空间主要在上面三处（取代保留时间、召回时带旧值、事实粒度），每一条都能单独量。

## 七、小规模试跑结果

**设置**：`scratchpad\membench\run.py`（脚本和全部缓存都在 `%USERPROFILE%\AppData\Local\Temp\claude\a286551153f5fca7\063a8f31-3fad-4edd-9096-834bdec341c1\scratchpad\membench\`，含 `extracted.json`、`results.json`、`cache\`）。

- 数据：LongMemEval `longmemeval_oracle.json`（cleaned 版，MIT），从 HF `xiaowu0162/longmemeval-cleaned` 下载，14.7 MB，只放在 scratchpad 的 `data\` 下。
- 抽样：种子 20261108，按题型取 单会话用户 3、单会话助手 1、偏好 2、时间推理 3、知识更新 3、多会话 3，另加 1 道知识更新弃答，共 16 题；限制每题原文 < 4 万字以控制调用数（**这会偏向较短的题**）。
- 提取：每个会话按时间顺序，每 6000 字一批，用 `prompts/summarize-v2.md` 原文（`{{name}}` 填"小澄"，`{{speakers}}` 填"主人 → owner；角色 → self"；已知事实 / 候选按批滚动累计，只处理 `upsert_fact`、`candidate`、`supersedes`、经历，`revoke` 和 `evidence` 未实现；消息里的方括号换全角、换行并成空格，照线上 `escapeUserText` 思路）。模型 `auto/claude-haiku-5-5`，Magpie，不碰 `data/`。
- 答题：三个条件——整理后的记忆（有效事实 + 候选标"未确认" + 经历，全部给）、完整原文、什么都不给；同一个答题提示。判分：haiku，仿 LongMemEval 官方五类判分意思写的提示（时间题容许差一天、知识更新题认新值、偏好题按评分细则、弃答题看是否承认不知道）。**不是官方 GPT-4o 判分，不能和公开分数比。**
- 调用：提取 87 + 回答 48 + 判分 48 = **183 次**（上限 300），0 次解析失败；提取阶段提示词输入约 34.6 万 token、输出约 11.8 万 token（含思考）。

**结果**

| 题型 | 整理后记忆 | 完整原文 | 什么都不给 |
|---|---:|---:|---:|
| 单会话用户 | 3/3 | 3/3 | 0/3 |
| 单会话助手 | 0/1 | 1/1 | 0/1 |
| 单会话偏好 | 2/2 | 2/2 | 0/2 |
| 时间推理 | 1/3 | 2/3 | 0/3 |
| 知识更新 | 2/3 | 3/3 | 0/3 |
| 多会话 | 1/3 | 1/3 | 0/3 |
| 弃答 | 1/1 | 1/1 | 1/1 |
| **合计** | **10/16** | **13/16** | **1/16** |
| 不含弃答 | 9/15（60%） | 12/15（80%） | 0/15 |

- 保留率（整理后答对 ÷ 完整原文答对，不含弃答）：8/12 ≈ 67%。另有一题（`gpt4_59149c78`）整理后答对而完整原文答错，说明答题 / 判分本身有噪声。
- **样本量太小**：15 题的 60% 的 95% 置信区间大约 36%～80%（Wilson，我自己算的），不能说"整理比原文差 20 个点"，只能说"这条路走得通，数字和复测的召回（约 70%）同一量级，没有矛盾"。
- **判分噪声一例**：`gpt4_76048e76`（自行车和汽车哪个先处理）整理后的回答是"The bike. ……"，与标准答案 bike 一致，但判分模型判了错；人工改判则整理后记忆是 11/16（不含弃答 10/15）。上表保留判分原始结果，没有改。
- 其余失败的原因：1 道助手方说的话不记；时间类 1 道（取代丢了旧值日期，见第六节）；知识更新 1 道（答题侧被"会加入两部"带偏）；多会话 2 道（原文也答不出，整理和答题都难）。我只看了其中 4 题的记忆条目，其余按答案文本推断，**归因未全部核实**。

## 八、需要主人定的事

1. **要不要把试跑脚本升级成仓库里的回归工具**，以及做成 Go（走真实 `SummarizeBatch`）还是 TS 脚本。我倾向 Go，理由是复刻提示词验证不了解析和事务保护。
2. **要不要装 mem0 开源版**（`mem0ai/memory-benchmarks`，Apache-2.0，要建独立 Python 环境，拉 Qdrant 和一堆依赖）。装的话先 50 题 oracle，约 300～600 次 haiku 调用。
3. **子集规模**：50 题 oracle 约 570 次调用（三条件）；500 题 oracle 约 3500～5000；S 版不建议。
4. **门槛数字**：召回 ≥ 80%、误记 ≤ 5%（原口径 ≤ 15%）、保留率 ≥ 85%、弃答 ≥ 90%，重复率、矛盾残留是我的建议值，需要拍板或先量一轮基线再定。
5. **要不要补一份中文样本**：按 Ground Truth First 的做法合成，或找 PAL-Bench / ZH-4O 的数据。
6. **本笔记引用的 `docs/规格-记忆质量.md` 只在 codex/memory-quality 分支上**；合并前请确认链接和数字没冲突。
