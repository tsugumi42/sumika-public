# 调研：火星插件（重复链接、重复图片提醒）

> 日期：2026-11-13。状态：调研笔记，未定稿；还没有规格，也没有一行实现。

> 许可证原则：GPL 项目只读不嵌（RedditRepostSleuth 是 GPL-3.0）；Meta PDQ 是 BSD，三个 Go 移植是 MIT，可以用，要保留版权声明。
> 起因：主人想给 QQ 群（以后也给 Telegram）做“火星”插件：群友发了 3～7 天内群里别人发过的链接或图片（内容图，不是表情包），机器人 @ 他，说“你火星了！原消息在这里↑”，并引用窗口内最早那条原消息。话术固定、可自定义，不用大模型。

## 一、结论先说

推荐方案一段话：**做成平台无关的“出现记录 + 判定策略”两层**。记录层把每张入库的内容图存成一条“出现”（会话、发送者、时间、平台消息号、sha256、256 位 PDQ 感知哈希、宽高、是否动图、质量分），链接则存规范化后的编号。**同图判定分两段**：先用 sha256 精确命中，不中再用 PDQ 汉明距离 ≤31 在窗口内线性扫描召回候选，最后从媒体库读回两张原图，做 256×256 灰度 4×4 分块相关确认（暂定平均 ≥0.95 且最差块 ≥0.85）。**判定策略完全另写**，吃“信号”不碰图：入口过滤（机器人自己、表情包、动图、过小、低信息量）→ 窗口内找“他人更早的出现”→ 静默规则（复读链、同一场讨论、自己重发、已表情化）→ 冷却 → 档位（只有精确命中或过了第二段才发话，只过粗段的静默记录）。**表情化不靠“被很多人发过”，靠“跨多天出现多个独立事件”**：几小时内三个人发同一个段子算一个事件，仍然报；同一张图隔了好几天又被零散发过多次才降级成表情。发话前延迟 5～10 秒（主人定）、收到撤回就取消，发错的先撤回就不会误报；已发出的提醒在对方两分钟内撤回时，机器人也撤回自己那条。验收靠离线回放群里历史消息：产出候选、主人判对错、量误报率，再定阈值；阈值现在全是起点值。

三个要主人先知道的事：

1. 单靠哈希挡不住“同模板聊天截图”误撞（合成数据里 PDQ ≤31 的误撞约 38%），第二段是必须的，不是可选优化。
2. QQ 对“拖进聊天框的收藏表情、GIF”到底发出什么标记，我们**没有真实样本**，所以表情包判断不能只靠标记，这条设计里至少有三层兜底（标记、动图/尺寸、跨日事件数）。
3. 这一版会漏掉“同一张图被重新裁剪、加白边”的情况（几何变化，哈希和分块相关都会失败），是有意接受的漏报。

### 主人补充要求（2026-11-13，和本篇冲突处以这里为准）

调研代理写本篇时还没收到这几条，下文没改到的地方一律按这里：

1. **要 OCR，要字数门槛和文字重复度**（推翻 2.3“OCR 第一版不做”）：图里认出的字数过门槛（起点 20 字）就比两张图的文字重复度，过阈值才算同一张图；字少的图只看图像两段式，阈值从严。文字重复度也正好解决“同模板聊天截图”误撞和“只改一个字”分不出的问题。长段子纯文字消息同样按字数门槛 + 重复度比（这条是主会话的理解，待主人确认）。OCR 候选：Windows 自带 OCR（零依赖，要中文语言包）、RapidOCR（PaddleOCR 的 ONNX 版，已有 onnxruntime 依赖）、tesseract 最后；选型要实测中文截图准确率和耗时。
2. **平台界面字样覆盖率**：OCR 后统计推特（转帖、引用、查看翻译、时间和浏览量行）、B 站（UP主、投币、三连）、Instagram / Facebook（Like、Reply、查看全部评论）、QQ / 微信聊天截图（时间分隔条、“撤回了一条消息”）等界面字样的覆盖率；越高越像帖子或评论区截图（内容图，该报）。字少又没有界面字样的更像靠画面传播的梗图，阈值从严；纯画面梗图仍然难判，接受漏报。
3. **撤回等待 5～10 秒**（默认 8 秒，可配），不是下文写的 20 秒。
4. **合并转发第一版不做**：整理梗图、吃瓜聊天记录的人会在头尾加引流图或文字，整条比会误判。以后的思路（只记一笔）：比内部条目，头尾一两条单独对待，中间大部分重合才算同一份。
5. **话术固定、可自定义，不用大模型**（和本篇一致）。
6. 实验脚本和原始输出已存到 `data/dev/mars-research-/`（`main.go`、`out/`）。

## 二、同图判定

### 2.1 同类做法和相互矛盾的地方

| 项目 | 指纹 | 阈值 | 对我们的意义 |
|---|---|---|---|
| koishi-plugin-mars-image（唯一叫“火星”的 QQ 项目，1 星） | dHash 9×8、64 位，最近邻取样缩放 | 距离 ≤6（相似度 90%） | 缩放用最近邻，对重压缩更敏感，不照抄；白底黑字时相邻像素常相等，位数少，聊天截图容易撞 `[调研转述]` |
| sleroq/bayan（Telegram，Go） | 取 `Photo[0]` 最小缩略图，算 pHash、dHash | pHash <10，dHash <15 | 自己的复核工具把“同模板”单列为误报来源，和我们的难点⑤同构 `[调研转述]` |
| nodobot、Telegram-Repost-Bot | blockhash 8 位 / average_hash，**严格相等** | 0 位 | 对重压缩无效，不用 `[调研转述]` |
| RedditRepostSleuth（GPL，只读） | imagehash dHash，hash_size=16，即 256 位 | 默认匹配度 86%，约 35.8 位；子版块可设 92% | 最成熟，思路是两段式（见下） `[读码]` 出处 `core/celery/task_logic/ingest_task_logic.py:83,103`，`sleuth_config_clean.json:34` |
| Meta PDQ | 亮度图→Jarosz 滤波降到 64×64→DCT 取 16×16→与中位数比较，256 位 | 距离 ≤31；质量分 <50 丢弃 | 白皮书写明：小字在 64×64 降采样里不可读，这是难点⑤的来源 `[读码]` `pdq/cpp/hashing/pdqhashing.cpp:154-198` |

RedditRepostSleuth 的两段式值得照着想（不抄实现）：第一段用 256 位哈希召回（最多 250 条）；命中“人工标注的 meme 模板”之后，第二段改用 1024 位哈希复核，模板匹配度提到 96～97%，它自己的 FAQ 也承认“很多模板换了字也出同一个哈希”。它的模板来自用户举报投票（得票 ≥10 才建模板），处理举报的函数在快照里是注释掉的，所以它的“误报反馈闭环”实际是关着的 `[读码]`。我们没有人工投票，换成第二段分块相关加离线评测里主人判对错。

### 2.2 合成实验结果（调研代理量的）

数据是合成的：40 张同模板聊天图（5 个气泡，只换随机汉字，黑体）、40 张不同字数的图，8 种变换（JPEG 75/40、缩 0.5/0.75/0.33 加 JPEG、加白边 3%、裁 2%、裁 1.5% 加缩 0.8）。用的是 Go 的 JPEG 编码器，不是 QQ 的；单一字体；没读任何真实数据 `[实测，合成，不是真实群数据]`。

| 哈希 | 同图仅重压缩/缩放，最大距离 | 同模板不同内容，两两距离（780 对） | 判断 |
|---|---|---|---|
| PDQ256 | 4 / 8 / 18 / 14；缩 0.33 为 28 | 最小 20，p5 26，中位 34 | ≤16 时零误撞，≤31 时约 38% 误撞 |
| dHash256 | 最大 24 | 最小 31，中位 46 | ≤32 时误撞 0.6% |
| dHash64 | 最大 7 | 中位 12 | ≤8 时误撞 12.2% |
| pHash64 | 最大 4 | 中位 4 | ≤4 时误撞 70%，不能用 |

第二段（256×256 灰度，4×4 分块，逐块皮尔逊相关）：

| 对比 | 平均相关 | 最差块 |
|---|---|---|
| 同图仅重压缩 | ≥0.985 | ≥0.955 |
| 同模板不同内容 | ≤0.783 | ≤0.612 |
| 整条气泡改了 | 0.89～0.98 | — |
| 只改一个字 | 0.987～0.999 | 和缩 0.33 的重压缩（0.985）分不开 |
| 加白边、裁剪 | 0.43～0.66 | 失败（对位置对齐敏感） |

读法：重压缩和同模板之间的间隙很大，两段合起来能挡住同模板误撞；挡不住的是“只改一个字”（算同图，对火星可以接受，属于策略层决定）和几何变化（漏报）。“整条气泡改了”的一部分落在 0.95～0.98，会被暂定阈值判成同图，这是阈值要在真实数据上标定的原因。

### 2.3 方案

**第 0 步，只出信号，不判政策**：宽高、面积、是否动图和帧数、是否带 alpha、PDQ 质量分、PDQ 距离、第二段相关值、窗口内同图出现次数和去重发送者数。

**第 1 步，召回**：
1. 精确快路径：`Seg.Hash`（内容 sha256）相同直接命中，不进后面两步。
2. 解码（动图先取首帧，v1 够用），按 EXIF 转正，带透明的铺到白底，缩到 ≤512，算 PDQ256，存 32 字节，**带算法版本标签**（比如 `pdq256-v1`）。换实现或升级要重算，不能混比：两个 Go 移植拿 C++ 标准向量对拍的容差都是 16 位，其中一个自己记了不同 Go 解码器会差到 16～18 位。
3. 窗口（默认见第七节）内线性扫描汉明距离（每条 4 次 popcount，窗口里几千条量级很小，没量；到百万级再考虑多索引哈希 MIH）。候选阈值取官方默认 ≤31，在合成数据里重压缩正例大多 ≤18，≤31 是留了余量，误撞交给第二段。
4. 质量分 <50 的图不进召回，只当弱信号：这类基本是纯色或近纯色图。**注意质量分挡不住文字截图**：合成聊天截图 40 张质量分全是 100，只有一个 6 字气泡的图也是 100，所以不能指望它识别“低信息量的聊天截图”。

**第 2 步，确认**：
1. 从媒体库读回候选原图，做 256×256 灰度 4×4 分块相关。暂定“平均 ≥0.95 且最差块 ≥0.85”判同图（区间中间偏保守，需要真实数据重标定）。
2. 宽高比相差 >5%：几何变了，相关值不可信，v1 直接放弃，接受漏报。
3. 候选原图读不到（见第六节，媒体库有没有清理策略没查到）：按“只过粗段”处理，静默记录，不发话。

**动图**：v1 默认不参与报，但照常入库（首帧 PDQ 加动图标记和帧数），后面“表情化”统计要用。动图转成静态图后的比较，以后再做多帧（存首、中、末帧，静态图去对每一帧取最小距离，参照 vPDQ 的做法）。

**文字截图专门处理**：没有查到现成方案。RedditRepostSleuth 的 OCR 代码（EAST + tesseract）存在但没接线；gocv（Apache-2.0）要装 OpenCV 4.12.0 并开 cgo，对 Sumika 太重；gosseract 在 Windows 要 vcpkg 加 MinGW，也不推荐。v1 不做 OCR，用第二段分块相关替代 `[读码]`（RRS 的 OCR 调用处只剩注释：`image_search.py:229-230`、`app.py:98`）。以后真要做 OCR，可以考虑 onnxruntime 上跑 PaddleOCR/RapidOCR 的 ONNX 模型，Sumika 的 `go.mod` 已有 `younland/onnxruntime`，但兼容性没验，Go 封装库都很不成熟 `[推断]`。

### 2.4 链接

链接的“同一性”用规范化编号，不是内容：`linkreader.Recognize(raw)` 已经把 x.com/twitter.com/BOOTH/B 站等认成 `Platform + Kind + ID`，`Clean` 是正式写法（不带追踪参数）`[读码]`。做法：
- 认得的平台：键取 `Platform + Kind + ID`。
- 认不得的链接：只在“路径非空”时按规范化 URL（小写域名、去 www/m、去追踪参数、去片段和末尾斜杠）比，域名首页不比。
- 排除：`Kind == "live"`（直播间每天重复发）、解析不出的短链。
- 短链（b23.tv、t.co）：每次分享生成的短码很可能不同，不解析就几乎一定漏（`[推断]`，没有出处，实测一下就知道）。已有别名表 `TraceStore().LinkAlias / PutLinkAlias` 和 `Fetcher.Resolve` 可用 `[读码]`，但要在热路径里发 HTTP 解析，成本和失败处理要在规格里定（解析失败就不比，不要拿短码比）。
- QQ 小程序卡片里的链接走已有的 `linkreader.ParseCard`，和展开插件取链接的方式一致 `[读码]`。

## 三、该不该报

### 3.1 没有任何现成项目同时处理了这几件事

最像的是 koishi `mars-image`：复读规避只管“同一个人”60 秒内同图满 3 次，别人跟着复读会被当火星；冷却和复读记录都在内存里，重启清空；排除表情靠元素类型 `face/mface/marketface/sticker/emoji` 加“宽高都小于 360”；没有专门处理 GIF `[调研转述]`。AstrBot 的 `astrbot_plugin_reread` 的复读链规则是“内容一变整条链立刻重置，不允许中间穿插”，默认图片阈值 3，`need_different` 默认开（同一人连续发同图清空窗口）`[调研转述]`。Telegram-Repost-Bot 的 `/whitelist`（回复一条消息，把它的图或链接设为永久豁免）和 PureImage 的“原消息被删就当新图”都值得借 `[调研转述]`。

### 3.2 表情包和内容图怎么分

没有找到专门做“反应图 vs 内容图”的开源项目，也没有可直接用的阈值。信号全是推测，要靠离线评测校准 `[推断]`：

| 信号 | 怎么用 | 可靠度 |
|---|---|---|
| 平台标记（`SegEmoji`、商城表情、face 段） | 本身不报；指纹要存，供“同一张图被拖成普通图”时静默（见 3.4 规则 1） | 标记在就一定是表情；**标记不在不能证明是内容图**（拖进聊天框的收藏表情、GIF 会变普通图，且 `sub_type` 取决于发送方客户端，pallas 的注释是旁证 `[调研转述]`） |
| 动图（多帧 GIF/WebP） | v1 入库但不报 | 绝大多数是反应图；漏报 GIF 段子图 |
| 尺寸（宽高都小于一个值） | 排除；起点沿用 mars 的 360，要拿真实图校准 | SnowLuma 的 image 段没有宽高，必须下载后读 `[调研转述]` |
| 跨多天出现多个独立事件 | 降级为表情，不再报 | 见 3.3，这是对难点④的回答 |
| 作为回复发出、紧跟别人消息、不带文字 | 降低置信度，不硬排除 | 弱信号 |

**为什么“被很多人发过就当表情”不可靠**：这是主人指出的，今天已有三个人几小时内发了同一个段子的图，这应该报。7 天窗口里“段子爆发”和“表情常用”分不开，所以**不能拿发送人数当表情信号**。

### 3.3 表情化：数“事件”，不数人

- 把同一指纹（距离聚类）的出现，按“相邻两次间隔 < G”合成一个**事件**（G 起点 6 小时）。几小时内三个人发同一个段子 = 1 个事件。
- 长期只存指纹和时间（不存图，30～90 天），当“事件数 ≥3，且跨度 ≥ 窗口长度”时，该指纹降级为表情，不再报，也在统计里标出来。起点值，评测里可以直接数“有多少指纹会走到这一步”。
- 这条依赖较长的指纹保留期，是本方案相对 mars（只存窗口内）多出来的东西。

### 3.4 规则清单（按判定顺序）

起点值全部可配，评测之后再定。

1. **入口过滤**：发送者是自己或已知机器人 → 不记录（避免自触发；Sumika 的链接展开会往群里发推文图，这些不能进记录，否则真人发同一条推文截图会被说成火星）。动图、过小、质量分 <50 → 入库但不报。`SegEmoji`、face、商城表情 → **本身不报**，但**建议仍然只存指纹**（带“被标记成表情发过”的标记，成本只多一次 PDQ，`Seg.Hash` 的注释说 emoji 段也有 sha256）：同一张图有时带表情标记发、有时被拖成普通图发（难点②），之后普通图命中“曾被标记成表情发过”的指纹，直接静默。这比尺寸和跨日事件数都硬，是应对难点②最好的证据。采不采用见第七节问题 11。`[推断，未验证]`
2. **找“他人更早的出现”**：窗口内匹配到的记录里，只看发送者不同的。**最早的一条就是发送者自己**（自己是原发）→ 不报，自己重发不算火星。有别人更早的 → 引用其中最早的一条。
3. **复读和讨论静默**：命中的上一次出现距现在 ≤5 分钟，**或**（还在该群最近 10 条消息以内，**且**距现在 ≤15 分钟）→ 不报。条数条件必须有时间封顶：冷清的群里 10 条可能跨几个小时，会把主人点名要报的“几小时内三个人发同一个段子”误静默。理由：复读是几十秒内的连续行为，调研给的参考值是 90 秒（no-repeat 的间隔是 20 秒，mars 是同一人 60 秒）；这里放宽到 5 分钟是我为了覆盖“讨论”加的，**没有出处**，评测里量。对 meme 复读也在这一条里（连发的 meme 都落在链里）。`[起点值，推断]`
4. **同一人连发**：同一人同指纹 60 秒内 ≥3 次，不报并进冷却（mars 的做法）。
5. **回复关系**：这条图消息本身是引用了原消息发的，或是回复了原消息的回复 → 不报。有文字评论（“刚才那张”）只当弱信号。
6. **表情化**：命中 3.3 的指纹 → 不报。
7. **多图消息**：一条消息 N 张图，要命中 ≥ min(N, 5) 张才报一次，引用其中最早的那条原消息（沿用 mars 的规则，避免“刷图包”整包被报）。
8. **冷却**：同一发送者 60 秒内最多触发一次；同一原图每 10～30 分钟最多报一次，防止三个人连着发时机器人连报三遍；群级每小时设上限；同一人对同一原图永远只报一次。
9. **档位**：精确命中或第二段通过 → 发话；只过粗段 → 只静默记录（mars 的 `notify=false` 思路）。理由：误报比漏报伤人。

### 3.5 误发和撤回

- **发话前延迟**（主人定 5～10 秒，默认 8 秒；调研原建议 20 秒）：这段时间里收到发送者撤回该消息的通知，就取消，不发话。手滑发错多半在这个窗口内撤回。通知通道已有：`types.NoticeRecall`，入库时会连上被撤回的那条 `[读码]` `internal/channel/types/event.go:38`、`internal/channel/intake_notice.go:138`。
- **已发话后对方撤回**：对方在 2 分钟内撤回，机器人撤回自己那条提醒。链接展开插件已经有“撤回刚发的消息”的装配处门槛（自己号、本次刚认领、2 分钟内）`[读码]` `internal/linkplugin/expand.go` 的 `ExpandOptions.Recall`（注释里写了门槛），可复用。`types.Part` 里没有“撤回”这种 Kind（只有 message/poke/forward/react），撤回是宿主在装配处接进来的，不是 Part `[读码]` `internal/channel/types/adapter.go:16-19`。
- **原消息被撤回**：删掉对应出现记录，不再引用，另有别人更早的就改引用那个。PureImage 也是这么处理 `[调研转述]`。QQ 有群撤回通知，Telegram 没有对应通知，要另想 `[推断]`。
- **转发发错群**：识别不了，只能靠撤回。
- **豁免**：对机器人的提醒回复“不算”之类的固定指令，该指纹永久豁免，只有主人或管理员能用（借 Telegram-Repost-Bot 的 `/whitelist`）。要不要做放第七节问。

### 3.6 话术

固定可配，多条随机选，占位符 `{at}{name}{time}{count}`，没有大模型。引用失败（见 6.5）要换一条**不带箭头**的话术，比如“{name} {time}前发过同样的”，否则“原消息在这里↑”会指向空处。

## 四、离线评测方案（只设计，不跑）

目标：在群里的真实历史上回放，产出“会报的候选”，让主人判对错，量误报率，再定阈值。

### 4.1 数据

- 来源：Go 后台各平台独立的聊天库，只读副本，不碰真实 `data/`；做法照 `cmd/memory-eval`（把库及 WAL/SHM 拷到系统临时目录，在副本上跑；见 `docs/subsystems/go-tools.md`）`[读码]`。
- 先出一份覆盖报告，不做判定：每个群每天的图片数、多少有 `Seg.Hash`、多少原文件还在媒体库里（第二段要读原图）、动图占比、表情标记占比。这些数我们现在都没有 `[未验证]`。
- 只在主人同意后才跑真实数据（AGENTS 的验收规则里“测试绝不读写真实 data”，评测工具是例外，要明确问）。

### 4.2 两阶段，参数扫描不重算图

- **阶段 A（重）**：遍历图片，算 PDQ、读宽高、候选配对、第二段相关值，结果缓存成信号文件（每对一行）。PDQ 单线程约 17 ms/张，5 万张约 15 分钟 `[调研代理实测]`（1080×788，含缩放，调研代理本机）；用 `bun ../scripts/slot.ts go run ./cmd/mars-eval …`（AGENTS：开发中走 `dev` 名额），不和别的重活叠着跑。
- **阶段 B（轻）**：策略回放。纯函数：信号加**注入的时钟**，扫阈值（PDQ 距离、相关阈值、静默窗口、事件间隔 G）。不用墙钟等待，不用 sleep（LESSONS：固定毫秒等待会把机器负载误判成行为失败）。

### 4.3 标注

- 候选分层抽样：按 PDQ 距离桶、按被哪条规则静默（抽静默的样本才能估漏报）、按是否动图；合成实验推荐起步约 200 对，之后按需要扩。
- 一个自包含的标注页（图用内嵌缩略图，带导出和导入按钮，主人填写中换页前先提醒导出，LESSONS 第一条）：每对显示两条消息的上下文（发送者按编的名字显示，前后各 N 条）、距离、相关值、系统的决定和理由。
- 标签：真火星 / 复读 / 同一场讨论 / 表情 / 手滑 / 不是同一张图（误撞）/ 是同图但不想报。
- 输出落 `data/dev/`（不进 git），名字、群名打码；评测代码本身不含真实数据；合并前照 LESSONS 用本机昵称表扫描新增行。

### 4.4 指标

- **误报率**：已发话的候选里，不是“真火星”的比例，报 Wilson 区间上界。要把上界压到 5%，零错误也要约 60 个样本（三之律：3/n）；所以样本数要先算好。
- **漏报估计**：从“被静默的候选”里按静默理由分桶抽样标注，估计每条规则杀掉了多少真火星。
- **切分**：按时间切一半调阈值，一半留作验证，避免调出来只对这批数据有效。
- **回归夹具**：“三个人几小时内发同一个段子”做成测试用例（只存哈希和脱敏元数据，不存真实图）。

### 4.5 评测入口

新增 `cmd/mars-eval`，参数风格同 `memory-eval`、`guard-eval`；写进 go-tools 参考页。

## 六、和 Sumika 现有零件的对接

## 七、风险和待主人定的问题

### 风险

- **同模板聊天截图误撞**：第二段挡住大部分，但“只改一个字”仍判同图，“整条气泡改了”有一部分会被暂定阈值放过（见 2.2）。合成数据，真实数据要重标定。
- **几何变化漏报**：别人对同一张图重新裁剪或加白边，哈希和分块相关都会失败。接受漏报，以后用局部特征匹配再说（需要纯 Go 的成熟 ORB/SIFT，没有系统查过 `[未验证]`）。
- **QQ 的动图、表情转码行为没验证**：保留 GIF、转静态、还是重压缩，不知道；设计上三种都要能处理。
- **引用静默失败**：发出去没有引用，会让话术指向空处。
- **图片哈希在升级时漂移**：不同 Go 解码器和版本会让距离差到 16～18 位，换实现要整批重算。
- **NapCat 已停更**：`NapNeko/NapCatQQ` 的 main 在 2026-11-12 只剩 README，可读源码是 fork；SnowLuma 的上游也被归档。这和插件逻辑无关，但影响以后依赖哪个适配器 `[调研转述]`。
- **Telegram**：`file_unique_id` 官方说随时间、不同机器人保持一致；同一图重新上传是否变化没查到，要用机器人发两次对比 `[调研转述，未验证]`；Telegram 有明确的 photo、animation、sticker 三种类型，表情判断比 QQ 容易得多；没有撤回通知这一条前面提到。
- **链接展开的图被当成原图**：见规则 1，机器人自己的记录不入库。

### 请主人定

1. **窗口默认几天**：3 天还是 7 天（可配，mars 支持 1～7）。
2. **误发撤回**：发话前延迟已定 5～10 秒；剩下的是“已经发出提醒后，对方 2 分钟内撤回，我也撤回自己那条”要不要？
3. **同一场讨论的静默窗口**：5 分钟或最近 10 条，要更保守还是更放开？
4. **同一个段子几个人发都报吗**：每个人都报（冷却 10～30 分钟防刷屏），还是只报一次？
5. **动图 v1 不报**，同意吗？以后想报哪一类（比如 GIF 段子图）需要主人给样本。
6. **多图消息**：一条消息里好几张图，命中几张才报？（合并转发已定第一版不做。）
7. **“不算”豁免指令**要不要做；谁能用（只主人，还是群管理员）。
8. **链接展开和火星的先后**：同一条消息里的链接是火星时，还要不要继续展开？

11. **表情标记的指纹要不要也存**：带表情标记发出的图只存指纹（不报），之后同一张图被拖成普通图发出时直接静默（见 3.4 规则 1）。建议要。

### 现在做不做

这是主人主动提的需求，排不排队由主会话看待办顺序定；本篇只给分段结论：

- **链接这一半：底子齐，可以先做。** 规范化编号、别名表、卡片取链接、引用发话出口、撤回都有现成的，不依赖图片的任何不确定项；先写规格（含静默规则、冷却、撤回、话术）再做。要先核实的只有“短链别名能不能只查表不发 HTTP”。
- **图片这一半：先补三件事再开工。** ①在测试群让主人发几种图（收藏表情拖入、GIF 拖入、普通段子图、转发），让我读事件日志，把“QQ 到底发什么”钉死；②核实第六节“要核实”的两处（下载完成的钩子、媒体库保留策略）；③做 `mars-eval` 回放真实历史、拿到真实阈值。这三件没做，规格里的数（相关阈值、尺寸门槛、静默窗口、事件间隔）只能是起点值。
- 评测和阈值标定是图片这一半的前置，不是收尾。
