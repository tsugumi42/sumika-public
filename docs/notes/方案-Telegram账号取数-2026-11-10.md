## 结论先行

1. **库：选 gotd/td，不用 TDLib。** 纯 Go（`go.mod` 里没有看到 cgo 依赖，没编译验证 `[推断]`）、MIT、活跃维护；Sumika 是 Go 1.27.3，gotd 要求 1.25，没问题。TDLib 要带 C++ 动态库、要 cgo 或 JSON 接口，Windows 上打包和升级都更重，而我们只需要“读几条帖子、下几个文件”，gotd 全覆盖。
2. **两类链接多半都能取到，但都没实测，不能当结论。** 私有频道 / 群只要账号是成员，`t.me/c/<数字>/<号>` 走 `channels.getMessages` 正常取 `[读码]`。被标记“porn”的公开频道：这个标记是客户端自己按平台过滤的，服务器照常给数据 `[推断]`（依据见第四节），所以很可能能取到；但这是本方案最关键的未确认点，第一步探针专门验它。
3. **凭据存储不能“复用现有密钥库”。** `native/internal/secrets` 是只读 Bun 密钥文件的，只有解密没有加密（见第二节）。要新写一个 DPAPI 加密的会话存储，实现 gotd 的 `session.Storage`，单独一个文件，不碰 `secrets.bin`。
4. **风险提一次：** 这个账号会被 Telegram “自动列入观察”；只读、低频、有人贴链接才取、不进群，是社区公认最安全的用法，但没有任何官方保证封号概率。另外 ToS 1.5 条禁止拿 Telegram 数据做 AI，Sumika 会把帖子给模型看，这条主人要知情（第三节）。
5. **第一步最快验证：** 一个不进 main 的探针程序，主人本人登录一次，对一条 `t.me/c/` 和一条被标记频道各取一帖，只打印不下载（第七节）。预计半天写完。

## 一、用什么库

### 1.1 gotd/td

- 登录：`telegram/auth/flow.go:51` 的 `Flow.Run` 依次问手机号、验证码、两步验证密码；要实现的是 `UserAuthenticator`（`flow.go:168`，含 `Phone`、`Password`、`AcceptTermsOfService`、`SignUp`、`Code`）。只登录已有账号，`SignUp` 返回错误即可。`auth.Client.IfNecessary`（`telegram/auth/status.go:36`）先查是否已登录，已登录就不再走流程。
- 两步验证密码不落内存明文：`PasswordHashProvider`（`flow.go:120`）让 Flow 改调 `PasswordHash` 直接拿 SRP 应答，配合 `telegram/auth/srpguard`（用的是 memguard）。对应主人要求的“Sumika 只转发”。
- 扫码登录：`telegram/auth/qrlogin/qrlogin.go:30` 的 `NewQR`，`Export` / `Import`。手机号和验证码都不经过 Sumika，只剩两步验证密码。可作第二种登录方式；官方示例 `examples/userbot` 有 `--qr`。
- 会话存储：接口是 `session.Storage`（`session/session.go:103-105`，`LoadSession` / `StoreSession`，注释强调存储安全很重要，泄露后别人能以主人身份登录）。官方 `session.FileStorage`（`session/storage_file.go:39-47`）是明文 `0600` 落盘，**不能直接用**。`telegram.Options.SessionStorage`（`telegram/options.go:118-120`）接它。
- 解析目标：`peers.Manager.Resolve`（`telegram/peers/resolve.go:28`）认 `t.me/xxx`、`tg://resolve?domain=`；公开频道名走 `ResolveDomain`（`resolve.go:160`，底层 `contacts.resolveUsername`）。数字形式走 `ResolveChannelID`（`telegram/peers/id.go:56-75`）：先在 peer 存储里找 `access_hash`，找不到就用 0 去取，拿到 `CHANNEL_INVALID` 就返回 `PeerNotFoundError`。数字 id 与 Bot API 形式的换算见官方 `/api/bots/ids`（加 取负）。**所以登录后必须先把对话列表拉一遍填充 peer 存储**（官方 `examples/userbot` 的 `--fill-peer-storage`，用 `telegram/query/dialogs`），且 peer 存储要持久化，否则每次重启都要重拉。
- 取消息：`telegram/query/messages/get_messages.go:24` 的 `GetMessages`，对频道自动走 `channels.getMessages`（文件头注释说传错会取回无关消息），返回里可能夹 `MessageEmpty`（不存在或无权限）。相册：`telegram/query/messages/media_group.go:25` 的 `GetMediaGroup`，围着给定号取前后各 9 条，按 `grouped_id` 过滤（`maxMediaGroupSize = 10`，同文件第 11 行），**用户关注的多图帖就靠它**。
- 下载：`telegram/downloader`，`downloader.go:34` 默认分块 512 KiB，`Download`（`downloader.go:82`）返回 Builder，`builder.go` 里 `WithThreads`、`WithProgress`，`Stream`（263）/ `ToPath`（302）。官方文档 `/api/files`：`upload.getFile` 的 limit 不超过 1 MiB，且一个请求不能跨 1 MiB 边界；`FILE_REFERENCE_EXPIRED` 要刷新引用（gotd 有 `telegram/downloader/fileref` 和 `telegram/query/...` 里的刷新，没细读）；同一数据中心并发限制看配置项（官方说小于 20 MB 一档、大于一档，具体数值在 app config，`[没查到]` 数值）。
- 限流：`tgerr.AsFloodWait`（`tgerr/flood_wait.go`）、`tgerr.FloodWait` 会睡到时间到；下载器内置遇到 FLOOD_WAIT 会睡了重试（`telegram/downloader/retry.go:71`）。请求层面用 `gotd/contrib` 的 `floodwait.Waiter` 中间件自动等待重试，`ratelimit` 中间件限速；官方 userbot 示例用的是 `ratelimit.New(rate.Every(100ms), 5)`（`examples/userbot/main.go:172`），我们要比它慢得多（第六节）。
- 许可证 MIT；Windows 无专门限制，示例都是跨平台的 `[推断]`。

### 1.2 TDLib

BSL-1.0（宽松，要保留许可文本）。官方、最稳、功能全、自带本地数据库和媒体缓存。代价：C++ 库，Windows 要自己编译或找预编译的 `tdjson.dll`，还要带 OpenSSL / zlib；Go 里要 cgo 绑定或自己写 JSON 接口层；升级要跟着重新编译。对 Sumika（单 exe、希望“少依赖系统”，见记忆“方舟式便携”）不划算。**除非 gotd 实测踩到解析或协议层的坑，才回头看 TDLib。**

## 二、账号和凭据

### 2.1 api_id / api_hash

- 官方流程 `[文档]`：用官方客户端注册账号，登录 my.telegram.org 的“API development tools”填表，得到 api_id、api_hash；**一个手机号只能绑一个 api_id**；开发者通知会发到这个手机号。
- 库自带的 `TestAppID` / `TestAppHash`（`telegram/cfg.go:26`）是公开的测试值，官方说公开的示例值用于正式用途会得到 `API_ID_PUBLISHED_FLOOD` 报错 `[文档]`，gotd 自己的测试里也把这个错当可重试错误处理（`telegram/builder.go:111`）。gotd 的 `examples/tdesktop-mimic` 注释也明说测试值只用来验连通性、不登录。
- **结论：用主人自己在 my.telegram.org 申请的。** 测试值不用于登录：这是别人公开的 id，会被限流，共用一个 id 的账号都会被一起盯上。自己的 id 绑在主人账号上，不能重新生成，gotd 说明里特别强调不要分享（`SUPPORT.md`），所以：不进 git、不进日志、不放示例配置。
- 官方条款 `[文档]` `/api/terms`：要用自己的 api_id（2.x）、不得让客户端代用户做用户不知情的事（1.4）、保护用户隐私（1.1）。1.5 条见下一节。条款是按“发布给别人用的应用”写的，**个人自用工具是否同样适用，文档没说清 `[没查到]`**，按保守理解遵守。

### 2.2 登录流程放在 Sumika 设置页

- 设置页只做“表单 → 后台 → Telegram”的转发：手机号一步、验证码一步、两步验证密码一步，后台实现 `UserAuthenticator`，每个方法在 channel 上等界面传值（超时 5 分钟取消）。输入只在内存里，用完清零，**不写日志、不写磁盘、不进错误信息**；错误信息里手机号只保留末四位。
- 也提供扫码登录（页面里显示二维码，主人用手机 Telegram 的“设置 → 设备 → 连接桌面设备”扫），这样验证码也不经过 Sumika。两步验证密码仍要输入。
- `Flow.Run` 必须在 `client.Run` 的回调里执行，所以登录是一次连接生命周期：设置页点“登录”→ 后台开连接、跑流程 → 成功后会话已由 `SessionStorage` 保存 → 断开。
- 登录后主人能在手机 Telegram 的“设备”列表里看到这个会话（名字取决于设备信息，见第六节），可以随时在手机上终止，等于远程“退出登录”开关。`[推断，通用行为]`

### 2.3 会话存 DPAPI 加密文件（工程缺口）

现状 `[读码]`：`native/internal/secrets/secrets.go` 头注释写明“只读 Bun 的 v1 密钥文件……不迁移明文，不写回”，`dpapi_windows.go` 只有 `CryptUnprotectData` 的 `unprotect`，没有加密方向；QQ 令牌是 `app.go:950` 读 `secrets.Open(a.paths.SecretsFile())`（`config/secrets.bin`），写入只能靠 Bun，而 Bun 已退役。所以 Go 里现在没有任何“写一个秘密”的东西。

做法：
1. `secrets` 包补一个 `protect`（`CryptProtectData`，当前用户、无附加熵、`CRYPTPROTECT_UI_FORBIDDEN`，镜像现有的 `unprotect`）和 `SealedFile{Path}`，实现 `LoadSession` / `StoreSession`：内容用 DPAPI 加密后，临时文件换名写入（避免写一半断电）。
2. 一个文件放 `data/config/telegram-account.bin`（`paths.go` 加 `TelegramAccountFile()`；`data/` 本来就不进 git，用 `git check-ignore -v` 验证，见 LESSONS）。里面存：api_id、api_hash、会话字节。peer 存储单独放 `data/go/telegram/peers.db`（不是秘密，但带 access_hash，也别进 git、别进日志）。
3. 不写进 `secrets.bin`：那是 Bun 的格式，Go 写进去会和“Bun 的设置里解锁”互相踩。
4. 日志：gotd 的 logger 默认接上 zap / 自己的实现，**设成 Warn 级别**，并确认没有把原始字节、验证码打出去（探针里先测）。
5. 换电脑：DPAPI 绑当前用户和机器，换机后会话打不开，需要重新登录。这对只读取数工具可以接受（记忆“方舟式便携”：重装后跑一次挂回去）。

## 三、风险（提一次）

- **自动观察**：官方 `[文档]`“所有用非官方客户端登录的账号会被自动列入观察”，滥发、刷量、造假浏览数“永久封号”。gotd 的 `SUPPORT.md` 转述 MadelineProto：只用来被动接收、不发送、不用 VoIP 号、做限速；被误封可以写 recover@telegram.org 说明用途。官方页同时说“自动生成的邮件会被识别并封禁”，所以申诉信要主人自己写。
- 社区经验（博客级，来源不权威，只作参考）：只读风险低于发送；循环无间隔地打同一个方法，会从 30 秒的等待升级到封号；一次短时间 resolve 几十个用户名会触发长达十几小时的限制；有一篇说 2025 年中起 Telegram 对疑似违规改成“只读”冻结而不是删号（单一来源，未核实）。没有任何来源给出“多少次算安全”的官方数字。
- 本方案的做法：账号只读、不发消息、不加入任何群频道、不调 `messages.readHistory`，也不调增加浏览数的接口 `[推断]`（`getMessages` 本身不增加浏览数，这是常识，没查官方原文）。ToS 1.4 禁止“篡改已读状态”，本方案不碰。
- **ToS 1.5**：“禁止使用、访问或汇总从 Telegram 平台取得的数据来训练、微调，或以其他方式开发、增强或部署人工智能、机器学习模型及类似技术”（`[文档]`，只读到该句前半，后半是“或以其他方式参与……的开发、增强或部署”，另指向 Telegram 的内容授权和 AI 抓取条款，全文没读）。Sumika 会把解析出的帖子正文和图给模型做回复，字面上可能落在“部署”里；个人自用、不外发、不训练是否算违反，**文档没说清**。主人说过自己账号的风险自己担，这里只说一次：这条比封号更可能是实际会被执行的条款，条款原文建议主人自己读一遍再决定。
- **从账号取到的内容再转发到 QQ 群**，会带来 QQ 侧的风险（图被 QQ 风控），而不是 Telegram 侧，见第五节“是否标记”。

## 四、被标记频道在 API 层面能不能取到

两套互不相同的机制，下面分开写。

### 4.1 机制 A：`restriction_reason`（平台限制，客户端过滤）

- 数据：频道对象和消息对象都带 `restriction_reason: Vector<RestrictionReason>`，每项有 `platform`、`reason`、`text` 三个字段（`_schema/telegram.tl:174`、`:204`、`:2162`；官方 `/constructor/restrictionReason`：platform 可为 ios、android、all，可用 `-` 连接，如 `android-ios`；reason 的例子是 porno、terms）。官方只写了“若这个 reason 在客户端配置 `ignore_restriction_reasons` 里，就忽略”，没有写服务器是否不发数据。
- 官方桌面版的做法 `[读码]` `tdesktop\Telegram\SourceFiles\data\data_peer.cpp:140-160`（`UnavailableReason::Extract`）：只取 `platform == "all"` 的限制；只有商店版才额外认 `ios`（Mac App Store 版）或 `ms`（Windows 商店版）。也就是说：**官方桌面版（非商店版）根本不理会只标 `ios` 的限制**，该频道照常显示。
- 主人说的“ios porn 标记”正好是这一类。所以：服务器在 MTProto 里照常给频道和消息，标记是跟着对象一起发来的数据，隐藏由各客户端自己决定 `[推断]`。我们自己写客户端，**只要不去执行这条过滤，就能取到**。
- 不确定：① 这个频道的标记是不是只有 `ios`，还是同时有 `all`；有 `all` 的话官方桌面版也会隐藏，服务器是否也拒绝发数据我没有证据 `[没查到]`。② `terms` 类（版权、违规）的 `all` 限制，服务器可能另有处理。③ 网页版 `t.me/xxx?embed=1` 显示“can’t be displayed”是服务端网页的另一条路径，**不能拿它来预测 MTProto 的结果**。
- 所以第一步探针要打印：频道的 `restriction_reason` 全部三个字段，以及能否取到消息、媒体。

### 4.2 机制 B：账号“敏感内容”开关

- 数据：`account.getContentSettings` 返回 `sensitive_enabled` 与 `sensitive_can_change`；`account.setContentSettings` 设置（`_schema/telegram.tl:2180`、`:3655`；gotd 生成了 `tg/tl_account_get_content_settings_gen.go`、`tl_account_set_content_settings_gen.go`）。官方文档只写“Only users can use this method”，没写 `sensitive_can_change` 的含义和哪些客户端能打开 `[文档，缺]`。
- 官方桌面版 `[读码]`：`data_peer.cpp:633-662`（`setUnavailableReasons`）把 reason 为敏感的那一项摘出来，设成 peer 的 `SensitiveContent` 标志（`data_types.h:348`），之后的显示与否由账号的敏感内容设置决定（`history_item.cpp:4925`），没有细读那条调用链。
- 公开的 bug tracker 线索（搜索摘要，没打开原文）：有些国家的账号 `setContentSettings` 返回 403 `SENSITIVE_CHANGE_FORBIDDEN`，被改成俄语区手机号后选项才出现，说明能不能改与号码所在地有关。**主人的账号能不能改，只能登录后查 `sensitive_can_change` 才知道。**
- 本方案的取舍：**只读 `getContentSettings` 记录状态，不替主人去改**（改账号设置不是“只读”，也影响他手机上的显示）。若探针发现某些帖子被拦在机制 B，再让主人自己在 Telegram 的设置里（网页版 / 部分平台的“隐私和安全 → 敏感内容”）决定要不要打开，打开后重试。是不是所有官方客户端都有这个开关，我没查到，不乱说。

## 五、怎么接进 Sumika

### 5.1 位置

做成**链接解析的一个取数后端**，不做单独的“Telegram 账号”插件被反向调用。理由：Sumika 的约定是“插件只通过宿主公开接口交互，`internal/app` 装配，不互相 import 实现”（AGENTS.md 技术约束）。具体：
- 新包 `native/internal/tgaccount`：只管 gotd 客户端、会话文件、登录状态机、限速、取消息、下载；不 import `linkreader`。
- `linkreader` 里定义一个小接口（比如 `TelegramPostSource{ Get(ctx, ref) (Post, error) }`），识别出 `t.me/c/...`、被拦的 `t.me/<频道>/<号>` 后调用；`internal/app` 里把 `tgaccount` 装进去。`ContentFetcher`（`linkreader/cache.go:16` 的 `Fetch` / `Resolve`）已经是这种拆法；`StagedFetcher` 的 `Metadata` / `Complete` 两级刚好对应“先给文字，再按需下图”。
- 取数顺序（可配置）：`网页版优先，取不到或被拦再用账号`（默认）/ `只用账号` / `不用账号`。`t.me/c/` 网页版必然取不到，直接走账号。
- 结果走现有缓存（`linkreader.Service` 的结果缓存和 TTL），同一链接 24 小时内不重复请求；带出处标记 `source: telegram-account`，被标记频道的结果带 `restricted: [platform, reason]`，方便后面按需处理。

### 5.2 插件页（设置里的“链接解析 · Telegram 账号”）

- 状态：未配置 / 未登录 / 已登录（显示账号昵称和手机号末四位）/ 暂停中（遇到 FLOOD_WAIT，显示解除时间）/ 出错（最近一次错误一行）。
- 按钮：登录（手机号 / 扫码两种）、退出登录（调 `auth.logOut` 并删本地会话文件，这样手机上的设备列表里也消失）、开关（总开关；“只用于私有频道”“也用于被网页版拦的公开频道”两个子开关）。
- 数字：今日已取 N 条 / 上限 M，缓存占用多少 MB，一键清缓存。
- 界面说明按设计语言第十一节：常驻一行，细的折叠。

### 5.3 媒体下载和缓存

- 现有链接媒体的视频上限是 `video.maxMB`（`config/link_file.go:213` 的 `LinkVideoMaxMB`），图片上限看 `linkreader/image_limit.go`，我这次没细读具体数值 `[没查到]`；账号取数沿用同一套键，不另起。建议默认：单张图 ≤ 20 MB、单个视频 ≤ `video.maxMB`（现有默认值落地时对齐）、单帖总计 ≤ 100 MB，超限只给“有 N 个视频未下载（xx MB）”这类文字。
- 缓存位置：走现有的 Go 媒体库 `paths.GoMediaDir()`（`data/go/media`），下载先写临时名、完成后换名，失败删临时文件；不放 `shared/media`（那是 Bun 的旧库）。
- 下载并发：同一时刻只下一个文件，线程 1～2；相册一张张下，张间隔 ≥ 1.5 秒。
- 视频缩略图 / 预览：优先取 `Document` 自带的缩略图（`downloader` 取 `thumb_size` 的位置，gotd 的 `AsInputDocumentFileLocation(thumbSize)` 有，见 ISSUES.md 里 #376 一条）；大视频只下缩略图，等主人确认再下全文件（对应 `StagedFetcher`）。

## 六、风控参数建议（只读低频）

| 项 | 建议值 | 依据 |
|---|---|---|
| 全局请求节奏 | 任意两个 RPC 间隔 ≥ 2 秒，不并发（官方 userbot 示例是 100ms × 突发 5，我们更保守） | `examples/userbot/main.go:172` 作对照；数字本身是我定的，无官方来源 |
| 触发时机 | 只在有人贴出链接时才取一次；不订阅频道、不轮询、不翻历史、不加群 | 社区经验 |
| `resolveUsername` | 结果缓存 ≥ 7 天；一小时内最多 10 个不同用户名 | Telethon 文档称短时间约 50 个就会 flood（二手信息） |
| 单帖请求数 | 解析 ≤ 1 次（缓存命中为 0）+ `getMessages` 1 次（相册一次窗口取 19 条）+ 文件下载若干块 | `media_group.go:25` |
| 日上限 | 默认 100 条链接/天，可配置，到了就退回网页版并在插件页显示 | 我定的 |
| FLOOD_WAIT | 用 `floodwait.Waiter` 中间件睡到点；等待 > 60 秒就放弃这次请求、插件页显示“暂停到某时刻”、整体暂停取数到那时；**连续两次 FLOOD_WAIT 就自动关开关**，等主人看 | 社区经验：不要用紧循环重试 |
| 连接 | 用时连、空闲 2 分钟断；连着不断反而像常驻机器人 | `[推断]` |
| 设备信息 | 默认用 gotd 默认的诚实设备信息，名字改成易认的（如 `Sumika link reader`），主人在手机设备列表里一眼认出来；`DeviceTDesktopWindows()` + `TDesktopResolver()`（`telegram/device.go:61-75`）能伪装成官方桌面版，**不默认用**：自己的 api_id 配上官方桌面版的标识本身不一致，而且与 gotd 文档的精神相悖；只作最后手段 | `[推断]` |
| 网络 | 沿用 Sumika 的代理设置，固定出口，不要来回换 IP | 登录地点跳变是常见风控信号 `[推断]`；gotd 支持自定义拨号（`dcs.PlainOptions` 的 `Dial`，`telegram/dcs/plain.go` 约 210 行），未验证 SOCKS5 |
| 首次登录 | 先正常用一两天手机上的账号，再登录；避免新装、新号第一天就接 | 社区经验 |
| 申诉预案 | 可选：登录前给 recover@telegram.org 写一封说明用途的邮件（MadelineProto 文档的建议，gotd 的 `SUPPORT.md` 转引） | 主人自己决定，要自己写 |

## 七、分几步做、每步多大

### 第 0 步：探针（半天，不进 main）

`native/cmd/tg-probe/`（或放 `<临时目录>`，不进仓库更好），命令行程序，参数：api_id、api_hash 从环境变量读，会话文件路径由参数给（先用 gotd 的 `FileStorage` 放 `%TEMP%` 下自建目录，用完删），不下载文件。流程：
1. 登录（手机号 + 验证码 + 两步验证；或扫码）。
2. `getContentSettings`，打印 `sensitive_enabled` / `sensitive_can_change`。
3. 拉一遍对话列表填充 peer 存储。
4. 对一条 `t.me/c/<数字>/<号>` 与一条被标记的公开频道帖：解析 → `GetMessages`；打印频道的 `restriction_reason`（三字段）、消息的 `restriction_reason`、媒体类型与大小、`grouped_id`；多图帖再跑 `GetMediaGroup` 打印张数。
5. 全程限速 2 秒一次，总共不到 20 个请求。

这一步能一次回答：两类链接能不能取、相册能不能拼全、机制 A / B 哪个生效、`sensitive_can_change` 是什么。**探针结果出来前，后面几步都不开工。**

### 第 1 步：账号包和加密存储（1～2 天）

`secrets` 补 `protect` 与 `SealedFile`（带改坏检查：篡改一个字节必须读失败；删文件后读返回 `ErrNotFound`）、`tgaccount` 包（客户端生命周期、登录状态机、限速中间件、取单帖）。全部用假服务器测：gotd 有 `tgtest`、`tgmock` 可以起本地假 Telegram（`tgtest/`、`tgmock/`），不需要真登录。命令行 `sumika-ctl` 里加一个 `tg login` 作为过渡的登录入口。

### 第 2 步：接进链接解析（1 天）

`linkreader` 识别 `t.me/c/...`，加 `TelegramPostSource` 接口、取数顺序配置、结果字段（文字、图、视频、相册、`restricted` 标记）、缓存；`internal/app` 装配；配置键按 AGENTS.md 的顺序改。测试：假 Source 覆盖“网页版取不到 → 退到账号”“账号未登录 → 清楚的失败提示”“被限流 → 退回网页并带说明”三条路径，四种场合（本地私聊、本地群聊、QQ 私聊、QQ 群）下可见性不变（沿用 `TestLinkVisibilityAcrossScenes` 的做法）。

### 第 3 步：设置页（1～2 天）

登录表单（手机号 / 验证码 / 密码三步）、扫码、状态、退出登录、开关、用量、清缓存。按设计自查验收。放在界面主线稳定之后再做，之前可以靠 `sumika-ctl` 登录。

### 第 4 步：媒体和相册（1 天）

按第五节的限额下图、相册拼图、大视频只给缩略图、缓存清理。

## 八、需要主人亲自做的事

1. 在 my.telegram.org 用自己的手机号登录、申请 api_id 和 api_hash（要手机收验证码，只能本人操作）。申请完别发给我，探针和后续配置都从环境变量或 Sumika 设置页读，我不碰它。
2. 想好用哪个账号（主号还是小号）。主号的风险是“万一被封，手机上的号也受影响”；小号的问题是私有频道要把它加进去、手机上要另装登录。这是主人的账号，主人定。
3. 登录那一步亲自输入验证码和两步验证密码（探针运行时在终端里输入）。
4. 读一遍 ToS 1.5 条（<https://core.telegram.org/api/terms>），确认 Sumika 把帖子给模型看、个人自用这种用法自己能接受。
5. 决定：被标记频道的内容（梗图为主）能不能发到 QQ 群。Sumika 现有的可见性规则可以继续用，但图被 QQ 风控是另一个风险，建议默认只给本地和主人私聊，群里要不要打开让主人定。
6. 可选：登录前给 recover@telegram.org 写一封说明用途的邮件。

## 九、没查清的清单

- 被标记频道的 `restriction_reason` 是只有 `ios` 还是含 `all`；服务器对 `all` 是否仍给数据。
- `sensitive_can_change` 的确切含义，以及主人账号能不能改。
- ToS 1.5 对“个人自用工具给模型看帖子”的适用范围；ToS 整体是否覆盖不对外发布的个人工具。
- `getMessages` 是否一定不增加浏览数、不标已读（常识，没查官方原文）。
- 官方对用户账号的 FLOOD_WAIT 阈值：Telegram 对用户账号不公布限额。
- gotd 走 SOCKS5 代理的现成写法（要读 `telegram/dcs` 与示例，探针前补）。
- 文件下载的并发配置项数值（`small_queue_max_active_operations_count` 等，在 app config 里）。
- Sumika 现有图片上限的具体数值（`linkreader/image_limit.go` 没细读）。
