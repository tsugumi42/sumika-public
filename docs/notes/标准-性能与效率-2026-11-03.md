# 标准：性能与效率（2026-11-03）

> 用户 2026-11-03："不能为了过测试妥协改变标准，不知道标准就先去网上找找权威和社区都认可的标准。" 正文由 Sol 联网调研整理（只读，未重新测量）；以后的验收对着第末节的表量，不过就改代码，不改门槛。出处链接在正文里，未逐条复核的以原文为准。

先说人话：**界面响应和帧预算有成熟依据；聊天客户端的内存、日志大小、AI 首字速度，没有一套所有软件通用的合格线。** Sumika 应把两类要求分开：有外部依据的体验目标，以及明确标成“暂定”的项目资源预算。暂定值也要在测试前写定；超线后查原因，不能按结果倒改门槛。

现有记录已经说明：Sumika 的常见帧耗时较短，但仍有超过 100 ms 的长帧；大规模会话概览存在秒级耗时。现在最缺的是**输入到画面呈现的端到端计时、完整进程范围的资源测量、文件增长及清理验收**。

本次只读核查了 `native/`、相关规格和 `docs/notes/`，做了网络搜索；没有访问真实 `data/`，没有运行程序或测试，没有修改文件。下文的 Sumika 数字均来自已有文档，未重新测量。

资料分为三类：

- **权威标准／指南**：官方平台文档、成熟人机交互研究。下文多数是指南，不是强制认证规范。
- **大厂公开指标**：厂商自己公布的目标、线上统计或实验。可以参考，不能直接当作行业合格线。
- **社区经验值**：个人测量、问题报告。条件不全时只说明现象，不能据此确定普遍门槛。

**界面响应：100 ms、1 秒、10 秒分别对应不同体验。**

INP 测量点击、触摸、按键到下一次绘制的延迟，**不直接测量滚动和悬停**。它也不要求异步查询在 200 ms 内全部完成；“按钮已经有反馈”和“查询结果已经可用”需要分别记录。

帧预算由刷新率直接决定：

| 刷新率 | 一个刷新周期 | 验收含义 |
|---|---:|---|
| 60 Hz | **16.67 ms** | 滚动和动画需要持续赶上这一呈现周期 |
| 120 Hz | **8.33 ms** | 若宣称支持 120 Hz 流畅交互，必须按此单独验收 |
| 144 Hz | **6.94 ms** | 同理，不能用 60 Hz 的合格结果替代 |

**应用绘制耗时、两次呈现的间隔、输入到屏幕更新的延迟，是三个不同指标。** 应用耗时低于 16.67 ms，仍可能因为排队、调度、GPU 或合成器而错过呈现。静止窗口没有必要持续画满刷新率；掉帧率只应在滚动、动画等应当更新的区间统计。

冷启动、热启动、恢复窗口也必须分开：

- **冷启动**：重启后或文件／系统缓存未热时，新建进程并达到可用状态。
- **热启动**：进程已退出，缓存仍热，重新创建进程。
- **恢复窗口**：进程一直存在，从托盘或隐藏状态恢复。

[Slack 2019 年官方发布说明](https://slack.com/blog/productivity/introducing-a-more-efficient-slack-desktop-experience)公布启动快 **33%**、内存最多减少 **50%**；没有在正文提供可复现的绝对冷／热启动秒数。此次查到的 Telegram、Discord、QQ、微信资料，也不足以建立一套条件一致的启动时间排行榜。不能从相对改善百分比反推出绝对合格线。

这些来源没有提供五款客户端在相同条件下完整的“空闲／聊天／滚动 CPU”数据，不能补成一个看似精确的比较表。

后台空闲的可靠原则是**尽可能不做工作**。[Apple《Energy Efficiency Guide for Mac Apps》](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/AppNap.html)（2016）明确写道：用户没有交互时，理想状态是应用完全空闲，并建议主动暂停不必要工作，不等待系统替应用节流。它没有规定“必须低于 0.1% CPU”。

对 Sumika，CPU 百分比建议统一成：

\[
C_{\text{单核}}=100\times
\frac{\Delta\text{用户态 CPU 秒}+\Delta\text{内核态 CPU 秒}}
{\Delta\text{墙钟秒}}
\]

这里一个逻辑核满载为 100%。如果换成整机归一化口径，需要再除以逻辑处理器数量，并注明口径。任务管理器截图里四舍五入的 `0%` 不能证明完全不耗 CPU。

内存至少同时记录：

- **Working Set**：实际驻留物理内存，受系统回收影响。
- **Private Bytes／PrivateUsage**：进程私有提交量，更适合检查长期增长。
- **Go 堆**：解释 Go 对象分配，不能覆盖 D3D、驱动、ONNX Runtime 等全部资源。
- **GPU 显存和自有子进程**：分别列出，再报告整个产品的资源范围。

**SQLite：官方有机制和做法，没有“所有查询必须几毫秒”的保证。**

[SQLite 官方的 Many Small Queries Are Efficient](https://www.sqlite.org/np1queryprob.html)以 Fossil 为例：一个 50 条目的页面执行约 200 条 SQL，通常总生成时间低于 **25 ms**，其中只有少量时间在数据库引擎中。示例 SQL 记录于 **2016 年**。这说明本地小查询可以很快，不能据此承诺任意查询都应低于 1 ms。

以下做法有官方依据：

| 做法 | 官方依据及年份 | 验收时需要注意什么 |
|---|---|---|
| 同时存在读写时使用 WAL | [Write-Ahead Logging](https://www.sqlite.org/wal.html)，SQLite 官方，WAL 自 2010 年提供，文档持续维护 | 读写可以并行，**同一数据库仍只有一个写者**；应用自己若只开一个连接，读写仍可能在连接池排队 |
| 管理 checkpoint，避免长读事务长期占住快照 | 同上 | 默认约 **1000 页**触发自动 checkpoint；4 KiB 页时约为 4 MiB，但不是 WAL 的硬上限 |
| 批量写入使用事务 | [SQLite FAQ 第 19 条](https://www.sqlite.org/faq.html#q19)，官方，2024 年专门更新说明 | 官方强调把多个 INSERT 包在一个事务里，摊薄提交成本。旧文“约 60 次事务／秒”是机械硬盘示例，**不是现代 SSD 性能标准** |
| 认识 `journal_size_limit` 的生效时机 | [PRAGMA journal_size_limit](https://www.sqlite.org/pragma.html#pragma_journal_size_limit)，官方持续维护，2026 查阅 | 限制的是提交／WAL 重置后留下的文件大小；**不阻止正在使用的 WAL 临时增长** |
| 删除数据后检查空闲页与文件回收 | [VACUUM](https://sqlite.org/lang_vacuum.html)，官方持续维护，2026 查阅 | 删除行通常留下可复用页面，文件未必立即缩小；VACUUM 可能需要约数据库大小两倍的空闲空间 |
| 备份使用数据库支持的机制 | 同上，`VACUUM INTO` 文档 | 可生成一致快照；不能把复制一个活动中的 `.db` 文件视为完整备份 |

批量大小没有通用的“100 条最佳”或“1000 条最佳”。建议用固定负载测吞吐、提交延迟、读查询被阻塞的时间，再冻结批量参数。不能靠关闭持久化、少存字段、漏存观察关系来通过性能验收。

Sumika 目前已设置 WAL、`journal_size_limit=4194304`、`busy_timeout=5000`、外键和单连接，见 [store.go](/仓库根/native/internal/store/store.go:65)。**5 秒 busy timeout 是等待锁的容忍上限，不是查询可以耗时 5 秒的体验目标。**

**AI 对话：首个流块、首个正文、整轮完成必须分别测。**

[NVIDIA《LLM Inference Benchmarking: Fundamental Concepts》](https://developer.nvidia.com/blog/llm-benchmarking-fundamental-concepts/)（Vinh Nguyen 等，2025）定义并比较了 TTFT、端到端延迟、ITL／TPOT、每用户和全系统吞吐量。文章特别指出：空响应不应算首 token，不同工具的公式可能不同。

[Microsoft Azure OpenAI 性能与延迟指南](https://learn.microsoft.com/en-us/azure/ai-services/openai/how-to/latency)（官方持续维护，2026 查阅）同样要求把延迟与输入／输出 token 数、模型、部署负载放在一起看，没有承诺所有聊天请求都应在固定秒数内完成。

建议记录五个时刻：

1. 用户提交。
2. 界面显示已接受／排队／正在处理。
3. 模型请求发出。
4. 第一个非空正文到达，以及正文真正呈现在窗口。
5. 整轮结束；QQ 场景另记实际发送完成。

网关 TTFT 不包括 Sumika 请求前的查询和排队，也不等于用户看见正文的时间。思考内容、工具调用参数、SSE 心跳也不能冒充正文。

用户可接受范围的证据如下：

| 来源、作者／机构、年份 | 分类 | 能支持的结论 | 不能推出的结论 |
|---|---|---|---|
| [Mitigating Response Delays…](https://arxiv.org/html/2507.22352v1)，Mykola Maslych 等，ACM CUI 2025 | 同行评审研究 | 比较 **1.5、4.0、6.5 秒**的语音虚拟角色响应，超过约 4 秒时体验变差；自然会话反馈可缓解部分影响 | 这是 VR／语音场景，不能直接写成中文文字聊天 P95 必须 4 秒 |
| [LLM Inference Performance Engineering](https://www.databricks.com/blog/llm-inference-performance-engineering-best-practices)，MosaicML／Databricks，2023 | 大厂工程经验 | 用 **100 ms/token，即 10 token/s**举例，约对应 450 英文词／分钟，快于一般英文阅读；强调先确定输入输出长度再定目标 | 不能据此宣称 10 token/s 对所有中文任务都足够，或 30 token/s 是行业强制线 |
| [How we built our multi-agent research system](https://www.anthropic.com/research/multi-agent-research-system)，Anthropic 工程团队，2025 | 大厂公开实验 | 并行化使复杂研究任务耗时最多减少 **90%**，从小时级变成分钟级；Agent 约用普通聊天 **4 倍** token，多 Agent 约 **15 倍** | 复杂研究不能和短聊天共用一个“10 秒完成”的标准；也不能只比速度，不比完成质量 |

对普通短聊天，**首个可见正文 P50≤1 秒、P95≤2 秒可以作为暂定体验目标**；对思考、工具、研究任务，应预先分组，分别报告。不能把慢请求事后改叫“复杂任务”而排除。

输出速度至少同时给出同模型的 token/s 和可见字符/s。一次返回的 chunk 可能有多个 token，不能把 chunk 数当 token 数。对于一个具体请求，可按 NVIDIA 的口径算：

\[
TPOT=\frac{t_{\text{最后 token}}-t_{\text{首 token}}}{N_{\text{输出 token}}-1}
\]

还应记录流中最长停顿，避免平均速度掩盖长时间停字。

提示词缓存方面，没有查到厂商通用的“命中率必须达到 80%／90%”标准。[OpenAI 缓存文档](https://developers.openai.com/api/docs/guides/prompt-caching)要求可匹配的稳定前缀，并说明模型、路由、保留期等条件；[历史 Cookbook](https://cookbook.openai.com/examples/prompt_caching101)所说的**延迟最多降低 80%**，不是命中率目标，该示例目前也标记为归档资料。

建议分开报告：

- 请求命中率：有缓存读取的请求数／符合缓存条件的请求数。
- token 命中率：缓存读取 token 总数／总输入 token 数。
- 前缀保留率：前一次可复用前缀有多少仍被完整保留。

OpenAI 的总输入通常已包含缓存读取；另一些提供方把未缓存输入、缓存写入、缓存读取分开报，必须先归一化。应使用总量相除，不能简单平均每次请求的百分比。冷请求、过期、压缩、切模型等情况要单列，同时保留整体结果。

**文件：先区分必须保留的数据和可以重建的产物，再规定容量与寿命。**

[Microsoft 应用数据指南](https://learn.microsoft.com/en-us/windows/apps/design/app-settings/store-and-retrieve-app-data)（官方持续维护，2026 查阅）区分本地数据、设置、缓存及临时数据；大型、本机专属数据应放在本地数据位置。文档没有统一规定日志必须保留几天或缓存最多几百 MB。其打包应用的系统清理行为，也不能直接套到未打包 Go 程序。

对 Sumika，建议的文件归属如下；这是验收清单，不是要求迁移当前目录。

| 文件类别 | 应放在哪里／留下什么 | 寿命与限制 |
|---|---|---|
| 配置、角色卡、加密凭据、聊天库、记忆库 | 用户选定的数据根；普通安装可采用专属 LocalAppData 目录；便携模式用明确指定的数据根 | 属于持久数据，不能为通过磁盘预算自动删 |
| SQLite 辅助文件 | 数据库旁的 `.db-wal`、`.db-shm`；必要的锁文件 | 运行中存在正常；按连接关闭、checkpoint 和恢复流程判断，不按“多了文件”判失败 |
| 媒体原件 | 受管理的媒体目录，内容去重并保留引用 | 消息仍依赖且无法重新取得的原件，不能当普通缓存处理 |
| 缩略图、可重建索引、下载缓存 | 专属 `cache/` | 应有容量上限、淘汰策略，删除后可重建 |
| 下载中间文件、解包临时文件 | 专属临时目录或专属临时子目录 | 成功／失败／取消后清理；崩溃残留在下次启动按年龄回收，不能清理其他实例正在用的文件 |
| 日志、诊断、性能记录 | `logs/` 与显式诊断输出目录 | 日志需按大小和时间轮转；ETL、堆转储不应默认持续产生 |
| 模型权重与运行时 | 明确的模型安装目录 | 单独报告下载、安装体积与版本，不能混进“小缓存”预算 |
| 备份、导出、用户保存的报告 | 明确的备份根或用户选择的位置 | 按各自保留规则处理；不以普通缓存策略删除 |

[Go 日志轮转库 lumberjack](https://github.com/natefinch/lumberjack)提供了常见机制：按文件大小切分、按数量和年龄删除、压缩旧文件。它默认单文件 **100 MB**，默认年龄和数量不限制；示例为 **500 MB、3 份、28 天**。这些是库默认值与示例，**不是桌面应用标准**。

Sumika 已有 [数据与日志规格](/仓库根/docs/规格-数据与日志.md:46)，不应重新发明另一套保留期：

- 日志单文件 **20 MB**；7 天后压缩、14 天后删除。
- 模型调用明细 **14 天**；调试／错误完整请求 **7 天**。
- 工具完整输出 **30 天**；后台判断 **30 天**。
- 固定日负载下，**除媒体外每天 <20 MB**。
- 数据目录 **5 GB 提醒线**，超过提醒，不自动删除。

但该规格主要来自旧后台。当前 [Go filelog](/仓库根/native/internal/filelog/filelog.go:83)能确认按日期追加、跨日换文件；在本次检索范围内，**没有找到对应的大小切分和过期日志清理实现**。不能把旧规格“已实现”的状态直接算到 Go 版。

另一个需要修正口径的地方是旧规格“WAL 始终不超过 4 MB”：SQLite 官方不支持把 `journal_size_limit` 解释成运行中的硬上限。验收应同时检查**活动 WAL 峰值、checkpoint 是否受阻、空闲回收后的残留大小**。

**Windows 上的测量应能区分应用工作、系统等待和真正呈现。**

| 要量什么 | 推荐方法 | 能证明什么／局限 |
|---|---|---|
| 启动、交互、UI 线程等待、磁盘与 CPU | [ETW＋WPR／WPA](https://learn.microsoft.com/en-us/windows-hardware/test/wpt)，Microsoft，官方持续维护，2026 查阅；按交互加 TraceLogging 起止事件 | 统一时间线上定位 CPU、排队、I/O、线程等待；需要正确选择采集项 |
| 实际呈现与掉帧 | 在相应 WPR 图形采集配置中记录 D3D／DXGI／DWM 事件，对齐应用帧标记和呈现事件 | 单独的 mygo 耗时日志不足以证明显示结果；严格物理输入到发光延迟还需要外部高速摄录等测法 |
| Windows CPU／内存归因 | [PerfView](https://github.com/microsoft/perfview)，Microsoft 开源工具，持续维护，2026 查阅 | 可分析 ETW CPU 栈；其 .NET GC 分析不能当成 Go 堆分析 |
| 主进程及子进程 CPU | `GetProcessTimes`，记录用户态＋内核态差分；完整进程范围需跟踪短命子进程或使用合适的 Job Object 计数 | 不应每秒另起 PowerShell／CIM 进程测自己 |

| Go CPU、堆、阻塞与锁 | [Go Diagnostics／pprof](https://go.dev/doc/diagnostics)，Go 官方，持续维护，2026 查阅 | CPU／heap／block／mutex 分别解释不同问题；采集有开销，官方建议避免互相干扰 |
| Go 调度与 GC 趋势 | [`runtime/metrics`](https://go.dev/src/runtime/metrics/description.go)，Go 官方，持续维护，2026 查阅 | 记录分配、存活堆、调度延迟、GC 暂停等；**`/cpu/classes/total` 是可用 CPU 容量时间，不是实际进程 CPU 消耗** |
| 文件增长 | 前后目录清单：相对路径、类别、数量、逻辑字节及实际占用；另记录写入量 | 数据库净增长、磁盘写入量不是一个数；WAL 回收后的净增长应另算，硬链接去重 |

Microsoft 的响应指南给出基本采集方式：

```powershell
wpr -start GeneralProfile -filemode
# 执行事先写定的场景
wpr -stop "<临时报告目录>\Trace.etl"
```

这只是后续测量示例，本次没有执行。图形呈现需要额外选择适合的采集配置。

测量条件应在运行前固定：Release 构建、机器与电源状态、屏幕刷新率、2560×1440／125% 缩放、窗口尺寸、数据库规模、图片／动图／长文本组成、网络和模型路由。基线测量与受压测量分开；Microsoft 建议基础采集前让整机 CPU 低于约 5%，这不是要求产品在真实使用时只能运行在空闲机器上。

次数与分位数建议如下。**样本数是本报告的统计实践建议，不是平台官方要求。**

| 场景 | 建议次数与报告方式 | 限制 |
|---|---|---|
| 冷启动、热启动、恢复 | 各先做 **30 次**，报 P50、最大值、逐次结果；P95 标为探索值 | 新装后的着色器编译、迁移、模型首次加载单列，不能事后随意丢掉 |
| 查询、普通交互、短聊天 | 每个固定场景／数据档位至少 **200 个观测**，报 P50、P95、最大值和失败数 | P95 尾部约十个样本，仍有不确定性 |
| P99 验收 | 建议累计 **10000 个观测**，同时给置信区间或跨批次波动 | P99 尾部约百个样本；相关样本不能当成完全独立样本 |
| 滚动与动画 | 每档至少 3 遍，各遍包含足够长的活动区间，报帧数、P50/P95/P99、错过呈现周期比例、长停顿次数 | 不能只报平均 FPS；不能把三遍的三个汇总值当成帧分布 |
| 空闲 | 稳定后连续 **10 分钟**，1 秒采样；窗口可见／托盘隐藏分开 | 连着 QQ 心跳、无消息，与完全离线也应分开 |
| 长期常驻 | **72 小时**固定剧本；同时保留完整曲线与预先声明的比较窗口 | 不靠强制 GC 后的堆稳定替代自然运行的进程内存稳定 |

Google SRE 在 [Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/)（2016）强调尾延迟和直方图，并要求区分成功、错误及其耗时。超时不能从统计里消失。压力场景还应从**预定到达时间**计入排队，避免系统越慢、发请求越少，反而漏掉拥堵。

**Sumika 当前证据有四个关键限制。**

第一，[十倍界面量测](/仓库根/docs/notes/量测-界面接Go后台十倍-2026-10-31.md:19)使用 10 个角色、一万条群消息、动图和长消息的合成数据。正式模式六遍“首屏”中位约 **790 ms**，各遍帧 P95 的中位 **5.55 ms**。第二轮工作集峰值 **140.2／141.8／143.4**，私有峰值 **179.2／180.9／182.0**。原文写 MB，但 [采集脚本](/仓库根/native/tools/bench.ps1:18)除以 PowerShell `1MB`，实际是 **MiB**。

其中“首屏”标记在 [applySnapshot](/仓库根/native/session.go:163)应用数据后写出，尚不能证明画面已呈现；每遍还有 **2 帧 >100 ms**，来源未核实。滚完整个列表约 28～30 秒包含脚本每步等待，不能当作纯处理吞吐。

第二，[未读量测](/仓库根/docs/notes/量测-未读不封顶-2026-11-02.md:8)记录：

- 10 万条未读，单次计数七次中位 **113.5 ms**。
- 大规模概览七次中位 **1.23～1.42 秒**。
- 未读全部归零后仍要 **1.08～1.18 秒**。

[回应／撤回查询量测](/仓库根/docs/notes/量测-回应和撤回合并查询-2026-11-02.md:8)记录：取一块 200 行相关通知，在 2 万／10 万／30 万事件时，七次中位分别为 **8.3／38.7／124.9 ms**。这些是中位值，不能写成 P95。

第三，[Go 后台规格中的挂机记录](/仓库根/docs/规格-Go后台.md:474)确实完成 **72h0m0.037s、129584 回合**。但历史过程需要完整保留：

- 原首尾窗口下，Working Set **+10.023%**，未过 `<10%`。
- 观察曲线后通过 ADR-219 改为跳过第一小时，再重算同一份 CSV：Working Set **40.6→40.8 MB，+0.530%**；PrivateUsage **+0.288%**；协程 **10→10**，按新规则过线。
- 这是**修改判据后的重分析**。以后可以采用固定预热窗口，但必须在新运行前冻结；不能把这份记录描述为原门槛下一次过线。
- 负载是假网关内核，不包括完整桌面、真实 QQ 和全部自有模型子进程。[采样器](/仓库根/native/cmd/soak/sample.go:24)有数据库总字节，但没有完整日志／缓存／媒体分类和 CPU 列。

第四，已有量测入口不等于已有合格结果：

- [记忆页规模测试](/仓库根/native/internal/memview/scale_test.go:81)会报查询 P50/P95、订阅 CPU 和堆；默认空闲段 **20 秒**，需显式设为 600 秒才覆盖十分钟。
- [早期 mygo 对照](/仓库根/docs/notes/对照-Electrobun与mygo-2026-10-26.md:19)记过五分钟空闲 CPU `0／0／0%`、流式输出约单核 **12%**，但属于旧原型，且后台范围不同。
- [模型运行记录](/仓库根/native/internal/turn/loop.go:485)已有正文首字、总耗时、缓存和 token 字段；首字从步骤开始计，包含部分本机准备工作，不能直接当作网关 TTFT。此次未读取真实运行数据，无法提供当前聊天 TTFT／token/s。
- [记忆召回对比](/仓库根/docs/notes/对比-嵌入模型记忆考题-2026-10-28.md:14)有 gte 方案 **P50 13 ms／P95 18 ms**的历史记录，覆盖当时的库副本和配置，不能扩展成当前整轮延迟。
