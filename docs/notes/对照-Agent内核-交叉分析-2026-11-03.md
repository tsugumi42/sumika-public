## 2. 矛盾、遗漏及核对后的正确说法

三份主要结论一致。需要纠正的是时效、过度概括，以及合并建议时容易丢掉的前提。

1. **“流式回调没有运行身份”须收窄为：旧全局回调仍缺身份，桌面本地草稿已局部解决。**

   P§2、V§2、C§2 都以 `OnDelta`、`OnTool` 为主要现状。当前 [api/localchat.go:13](../../native/internal/api/localchat.go) 已定义带回合、步骤的完整草稿；[app/desktop_chat.go:49](../../native/internal/app/desktop_chat.go) 将它绑定到经后台核验的会话；[hub.go:1459](../../native/internal/turn/hub.go) 已发布累计正文。正确缺口是**跨入口统一、思考／工具状态、活动运行快照及重连**。外部借鉴仍是表①的 pi 事件类型、v2 输入接纳和 Codex 回合归属。

2. **ADR-242 的旧过滤确实还在，而且不能只改 `Recall`。**

   三份都正确指出设计与实现未对齐。本次核实：[Recall:394](../../native/internal/memory/recall.go) 调用旧 `AllowedScopes`；[RecallRaw:264](../../native/internal/memory/tools.go) 据此限制会话；[outbound.go:126](../../native/internal/memory/outbound.go) 又用同一集合挑守卫需要检查的记忆。

   **若只把 `AllowedScopes` 改成全部，守卫的 `denied` 集合也会变空。** 正确改造要分开表达“她能想起什么”和“当前场合对外表达怎么判”，同时更新来源渲染。现有 [render.go:37](../../native/internal/memory/render.go) 主要输出时间、正文和旧 owner 标记，尚不等于 ADR-242 要求的逐条“谁、场合、会话”。这正是 P§10.1、V§10、C§10 的来源契约应落实的位置；Codex 对原始、继承、摘要来源的区分见 `_external/codex/codex-rs/core/src/context_manager/history_user_authorization.rs:151`。

3. **pi 的普通会话恢复与 durable 恢复不能合并成一种能力。**

   P§3、7、10.3 已区分，本次源码支持其口径：coding-agent 依赖普通 agent-core，`_external/pi-mono/packages/coding-agent/package.json:49`；durable 的工具另行保存执行意图，只在旧记录与当前策略都为 `safe` 时重跑，`_external/pi-mono/packages/durable/src/harness/tool.ts:180`。不能据此声称“采用 pi 会话记录就有跨进程任务续跑”。Sumika 当前 [SweepInterrupted:55](../../native/internal/store/turns.go) 是保守终结和未知结果记录，适用语义不同。

4. **统一事件协议不等于全量事件溯源，也不等于可靠逐 token 重放。**

   V§2 的限定必须保留：v2 `_external/opencode-v2/packages/core/src/bus.ts:214` 默认 `persist=false`，事务投影仍会提交。Codex 明确将正文、思考增量和审批请求等列为瞬态，`_external/codex/codex-rs/rollout/src/policy.rs:160`。Crush 的 `PublishMustDeliver` 也可能超时丢失，`_external/crush/internal/pubsub/broker.go:13`。

   正确建议是：**终态和累计状态可恢复，在线增量有明确交付契约**。Sumika 已有 [approval/subscribe.go:48](../../native/internal/approval/subscribe.go) 和 [desktopread/service.go:218](../../native/internal/desktopread/service.go) 可复用，不需要先换全仓存储模型。

5. **v2 的“统一 schema 解码”并非无条件严格校验所有声明。**

   V§5 的总体描述成立，但应补上源码限定：`_external/opencode-v2/packages/core/src/tool/runtime.ts:74` 中，原始 JSON Schema 转换不出 codec 时会直接返回输入值。因此值得借的是共同边界和结果契约，不能直接把该实现当成“无法处理的 schema 必然拒绝”的范本。Sumika 当前入口也已有 JSON／对象检查和工具自检，[loop.go:81](../../native/internal/turn/loop.go)；正确缺口是声明与字段验证的一致性。

6. **Sumika 已有提前压缩；v2 多出来的是候选采用条件。**

   P§4、V§4、C§4 不构成“有／没有后台压缩”的矛盾。Sumika 已在 [acquire:997](../../native/internal/turn/hub.go) 发现新 epoch 后重建；v2 则先保留候选，达到压缩条件再使用，并检查首条消息、指令、模型和保留锚点，`_external/opencode-v2/packages/core/src/session/compaction.ts:330`、`_external/opencode-v2/packages/core/src/session/compaction.ts:953`。其预计算还默认关闭，`_external/opencode-v2/packages/core/src/session/compaction.ts:262`。缓存收益须实测，不能因设计更细就写成已经更快。

7. **“执行上下文放进 trace”还缺保留期契约。**

   P 的统一投影与 C 的独立执行上下文可以合并，但 C§3、建议第 2 项中的 trace 落点不能直接套普通诊断清理：现有 [数据与日志规格第四节](../规格-数据与日志.md) 规定模型明细 14 天、工具全文 30 天；而 [子代理规格§6.1](../规格-子代理.md) 暂定任务和结果不自动删除。

   正确做法是**同一个库里区分恢复必需状态、被引用结果和可过期诊断记录**；不能让明细清理删除未完成任务的恢复依据，也不能为恢复默认永久保存每次完整请求。

8. **“恢复模型历史”不能顺带改变思考回灌政策。**

   Codex 的 `_external/codex/codex-rs/core/src/session/rollout_reconstruction.rs:14` 能恢复更完整的执行窗口，但 Sumika [右侧栏规格§4.2](../规格-右侧栏她在想什么.md) 明确要求落库思考只供展示，不从库读回请求。当前热实例与冷重建也确有这个差别，[loop.go:31](../../native/internal/turn/loop.go)、[history.go:122](../../native/internal/history/history.go)。本次建议恢复已执行状态、必要材料和结果引用；不承诺逐字复原整个热实例。

9. **三份不能作为同一冻结版本的性能基线；ADR-247 也要准确引用。**

   C 文首写 Sumika 基点 `1181083e`，文末版本表写 `0fafdef5`，见 [C:3](对照-Agent内核-Codex和Crush-2026-11-03.md)、[C:267](对照-Agent内核-Codex和Crush-2026-11-03.md)。本次以实际抽查的工作区实现为准，没有性能比较结果。

   [ADR-247](../决策记录.md) 的正式范围是 Telegram／mewtype 界面替换。本任务要求“不留旧兼容”，内核改造应同样贯彻一次迁完相关调用者、删掉被替代接口；不把 ADR 原文本身扩大为已批准的任意内核重写。

## 4. 建议先做的五项

这是内核改造的依赖顺序建议，**不覆盖待办顶部的现行排期**。ADR-242 的记忆线照常推进，不必等待前面三项；子代理继续遵循已有生态层顺序。

量测统一参考 [性能与效率标准](标准-性能与效率-2026-11-03.md)。下面均是拟定验收，未在本次执行。旧、新版本使用相同负载交替比较至少三遍；固定查询／短聊天场景按该标准积累足够观测，报告 P50、P95、最大值、失败数和排队时间。“暂定”门槛仍须在跑之前冻结。

**1. 先统一有效调用说明与模型记账，对应表③、⑧。**

- **落包**：`llm`、`turn`、`app`、`store`，调整 `memory.Generator` 的请求说明；记忆业务仍按需只消费正文。
- **第一步**：沿现有[右侧栏规格§4.1](../规格-右侧栏她在想什么.md)，列清回复、重试、压缩、整理、守卫的调用归属和唯一记录者；把有效模型、档位、用途、回合／批次、实际请求尝试、用量完整性带到调用边界。不要另加一套观测框架。
- **怎么量**：每次实际派发恰好对应一份记录；成功、取消、失败、回复不可解析分别可认；未知用量不写成完整零。比较加记录前后的本机调度／持久化开销，采用标准中暂定 **P95≤50 ms／转换**；同时记录每百调用新增字节，避免记录请求全文导致增长失控。
- **对上待办**：[“她在想什么”第 2 步](../待办.md)、[后台装配后续](../待办.md)。主要现状证据是 [memoryGenerator:113](../../native/internal/app/guarddeps.go) 与 [runRow:486](../../native/internal/turn/loop.go)；外部参照表⑧。
- **切换要求**：迁完生产调用者，移除被替代的正文专用适配路径；已有历史记录的未知字段保持未知，不伪造补齐。

**2. 把运行身份与快照订阅收成共同契约，对应表①。**

- **落包**：`turn`、`api`、`app`、`desktopread`、`store`、`channel`；审批保留已有版本模型。
- **第一步**：从现有 `LocalDraft` 和 `Settled` 出发，定清受理身份、回合、步骤、尝试、工具调用的关系；将输入“已受理／已接纳”及模型“已完成”与渠道“已计划／已确认送达”分开。实现快照加后续变化，暂不为所有输入引入跨重启自动执行。
- **怎么量**：同角色多会话交错、重试、插话、取消和重连后，正文及终态归属错误为 0；慢消费者不能拖住其他会话，恢复后累计正文一致。界面提交反馈按暂定 **P95≤100 ms**；短聊天首个可见正文按暂定 **P50≤1 s、P95≤2 s**，网关 TTFT 单列；本机转换开销仍按 50 ms 目标量。
- **对上待办**：[带身份流式事件](../待办.md)、[右侧栏第 3 步](../待办.md)、[流水线可视化](../待办.md)。后者消费同一身份，不另建节点事件体系。当前基础见 [api/localchat.go:13](../../native/internal/api/localchat.go)、[approval/subscribe.go:48](../../native/internal/approval/subscribe.go)；外部参照表①。
- **切换要求**：迁完旧 `OnDelta`／`OnTool` 等消费者后删除旧契约；桌面、渠道、插件不长期保留两套可独立推进的运行状态。

**3. 完成 Hub 的停止准入与排空，再补容量和整轮预算，对应表⑥、⑦。**

- **落包**：`turn`、`app`、`approval`、`channel`；执行容量在共同工具入口控制。
- **第一步**：先实现已有待办中的 `Hub.Drain(ctx)`，覆盖已受理、排队、活动回合、提前压缩和必要收尾；记录“对调用方超时了，但底层还没退出”的工作。正常排空后才能交出关库条件；未排空须明确返回剩余工作。
- **怎么量**：停止准入后新工作受理为 0，正常排空后迟到写库为 0；固定剧本重复装配／关闭，File／Process 句柄不持续累积，协程回到预定基线。随后量 10／50／100 会话及混合工具批次的执行峰值、等待分布、私有内存和完成率，再冻结容量；容量必须计算未退出工作。整轮预算统计重试、压缩和未来孩子的派发，不能只数成功请求。
- **对上待办**：[Hub.Drain](../待办.md)、[审批收尾](../待办.md)、[工具次数上限](../待办.md)、[商店版 PowerShell 子进程归属](../待办.md)。并发容量没有找到专门条目，应并入这次范围，不能用 B7 压测通过代替容量控制。当前分散等待见 [app.go:464](../../native/internal/app/app.go)；外部参照表⑥、⑦。
- **切换要求**：完成后移除 app 中为 Hub 补等回合的替代逻辑；组件仍负责自己的资源，Hub 不吞并记忆整理等独立业务排程。

**4. 让来源与接纳账本贯穿召回、原话和上下文投影，落实 ADR-242，对应表②、③。**

- **落包**：`memory`、`memplugin`、`turn`、`history`、`memsource`、`store`，以及已有资料来源插件。
- **第一步**：先列出共享旧范围门槛的入口表：自动召回、`memory_search`、`recall_raw`、固定要点、来源渲染、发送守卫及相关评测；把召回资格与表达判定拆开，再一次改齐。材料保留原始事件／记忆引用、来源角色、说话人、场合、会话和生成方式；摘要不能提升来源身份。
- **怎么量**：同角色在**本地私聊、本地群聊、QQ 私聊、QQ 群**对同一组事实都可召回；每条来源可核对，待确认仍有标记；不扩大其他角色记忆访问，不新增本地执行能力。分别统计答对、遗漏、编造、误归来源和不当对外表达，不能只验“返回了几条”。比较召回耗时、注入 token 和非压缩请求前缀复用，保留既有 **≥90%** 前缀要求；缓存 token 命中率另量。
- **对上待办**：[ADR-242 落地](../待办.md)、[召回追原文](../待办.md)、[右侧栏逐条记忆](../待办.md)。关键现状见 [outbound.go:126](../../native/internal/memory/outbound.go)、[render.go:37](../../native/internal/memory/render.go)；外部参照表②及 C§10。
- **切换要求**：移除旧场合过滤及 `qq.memoryAll` 兼容语义；工具授权、工作区信任和资料外发许可继续使用各自契约，不能从“记忆全量召回”推导授权。

**5. 给本地工作建立可恢复材料、受控全文和工作压缩，对应表②、④、⑤；为子代理复用，对应表⑨。**

- **落包**：`turn`、`history`、`store`、`tools`、`prompts`；子代理实施时复用同一内部上下文机制。
- **第一步**：沿[子代理规格§6.1](../规格-子代理.md) 把上下文序列／快照存取与聊天 Events 解开，定义已执行步骤、结果引用和压缩覆盖切点；先明确恢复所需状态及其保留规则，再接工作摘要。工具执行契约同步补参数校验与全文引用，避免摘要继续要求“重新查询一次”。
- **怎么量**：同一固定工作题经过连续压缩、实例回收和重启，仍能指出目标、已完成步骤、下一步和原结果；已完成副作用重做次数为 0，未知结果保持未知。比较任务成功率、恢复耗时、额外模型请求和 token、原结果读取耗时及磁盘增长。已有 [快照后 2000 事件缺口](../待办.md) 要在同一序列契约中解决，不能声称完整恢复却继续静默跳过中段。日增长沿既有固定负载 **非媒体每天 <20 MB** 量，恢复材料与短期诊断分别列。
- **对上待办**：[计划清单随压缩保留](../待办.md)、[大输出与清理](../待办.md)、[QQ 长聊裁尾损失量测](../待办.md)、[子代理／生态层](../待办.md)、[Super-agent 分层估量](../待办.md)。外部参照表②、④、⑤、⑨。
- **切换要求**：聊天与工作是两类材料、共用一套循环和压缩机制；不复制第二套 Agent。QQ 是否启用摘要单独决定，孩子仍不自动续跑、不直接发平台消息。
