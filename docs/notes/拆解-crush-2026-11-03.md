### 2. 进程、goroutine 与前后端分离

[读码] 默认入口走 `setupLocalWorkspace`，TUI 与 App 在同进程；只有 `CRUSH_CLIENT_SERVER` 被解析为 true 才走 client/server。服务端可使用 Windows named pipe、Unix socket 或 TCP；HTTP 路由挂在版本化 API，另有 OpenAPI/文档入口。因此“已有分离接口”成立，“默认启动就是后台服务＋独立客户端”不成立。出处：`crush@3b1f860 internal/cmd/root.go:257-289`、`internal/server/server.go:41-90,93-102,151-168`。

[读码] 并发以 Go goroutine 和 context 为主：系统提示和工具表初始化经 `readyWg.Go` 分开做；MCP 在 App 启动时异步初始化；首次真实用户输入的会话标题另起 goroutine；子代理在工具调用中运行；LSP 在首次读相应文件时按需启动外部语言服务器。没有固定“一会话一条 OS 线程”的结构。出处：`crush@3b1f860 internal/agent/coordinator.go:862-894`、`internal/app/app.go:201-225`、`internal/agent/agent.go:835-845`、`internal/lsp/manager.go:103-119,159-245`。

[读码] 服务端是可消费的 API，但本次读到的是仓库内 `internal/client`、`internal/proto` 和 HTTP/OpenAPI，不应写成已经提供独立、稳定承诺的公开 Agent SDK。出处：`crush@3b1f860 internal/server/server.go:161-165`、`internal/server/proto.go:16-25,78-95`、`internal/cmd/run.go:180-189`。

### 3. 一轮从输入到结束

[读码] 主链如下，应用层与循环层有明确接缝：

1. `Coordinator.run` 等提示词/工具初始化；非交互运行有限等待 MCP，交互运行不等待慢服务器；快照当前主 agent，刷新模型和工具，合并采样与 provider 参数。
2. `sessionAgent.Run` 在会话锁内选择取消入场、排队或成为 active；登记 cancel 句柄后才释放锁。
3. 取会话与摘要后的历史，保存本轮 user 消息；构造 Fantasy agent，开始流式调用。
4. 每次 `PrepareStep` 刷新有效工具、合入普通插话、修正媒体结构、放缓存标记、创建这一步的 assistant 消息。
5. 文本/思考/工具调用/工具结果回调分别更新消息；每步结束更新 finish、usage、cost。
6. `StopWhen` 检查上下文压力和重复工具交互；若需压缩，先停循环，再摘要，必要时以原请求继续。
7. 收尾结算未回答的 tool call；flush 消息后发布 `RunComplete`；再把排队请求交给下一轮。

出处：`crush@3b1f860 internal/agent/coordinator.go:320-436`；`internal/agent/agent.go:633-879,880-978,1039-1161,1165-1410`；`internal/agent/settle.go:82-143`。这是读码流程，不是运行时序测量。

## 二、工具系统：类型化内置工具、实时目录与 MCP 桥

### 1. 定义、注册和按角色减工具

[读码] 内置工具通常以 Go 参数结构的 JSON tag 和 `description` 描述输入，描述正文通过 `go:embed` 嵌入 Markdown，再用 `fantasy.NewAgentTool` 构造。部分工具明确调用 `NewParallelAgentTool`，例如 `agent`、`agentic_fetch`、Sourcegraph。schema 的实际生成和默认调度属性属于 Fantasy，不应仅凭 Go 结构体就声称应用自己实现了完整 JSON Schema 校验。出处：`crush@3b1f860 internal/agent/tools/view.go:27-50,88-103`；`internal/agent/agent_tool.go:15-43`；`internal/agent/agentic_fetch_tool.go:66-69`；`internal/agent/tools/sourcegraph.go:18-22,62-65`。

[读码] `buildTools` 先创建候选工具，再按 `Agent.AllowedTools` 过滤，加入 MCP，根据 `AllowedMCP` 再过滤，最后按 `Info().Name` 排序。coder 的候选包括 shell、读搜改文件、todo、问题、LSP、MCP 资源与自省工具；plan 只取只读导航、`agent` 和 `question`；task 只取只读检索。task 和 plan 的 `AllowedMCP` 默认是空 map，表示不允许 MCP；nil 才是不限制。出处：`crush@3b1f860 internal/agent/coordinator.go:899-1013`；`internal/config/config.go:1072-1153`。

[读码] `question` 仅在主代理且 `interactive` 时加入；LSP 导航/编辑工具由配置与 `auto_lsp` 决定是否加入。新工具不是永远向所有 agent 公布。出处：`crush@3b1f860 internal/agent/coordinator.go:953-980`。

### 2. 一次返回多个 tool call 时的并发与顺序

[读码] Crush 明确预期 Fantasy 会并行调用工具回调，所以 `sanitizedToolCalls`、`completedToolCalls`、`answeredToolCalls` 使用并发安全 map。每个完成结果单独创建 tool 消息，使用 `ToolCallID` 关联；结果在数据库中的写入先后不能当成模型调用先后。出处：`crush@3b1f860 internal/agent/agent.go:865-877,1044-1081`。

[读码] 重建下一轮请求时，`preparePrompt` 先按 ID 收集结果，再在对应 assistant 调用之后重新插入；`toolResultsForCalls` 遍历 assistant 的 tool call 列表，按其顺序取结果，保证 call/result 邻接，不允许中途夹入 user 消息。找不到结果时合成错误，不把孤儿结果留在请求里。这个“持久历史顺序 → API 请求合法顺序”的转换在 Crush 本身可直接核对。出处：`crush@ internal/agent/agent.go:1622-1714`；`internal/agent/settle.go:26-59`。

### 3. 工具注入、动态目录与延迟加载

[读码] 每次 `PrepareStep` 重新复制 `a.tools`，按 channel 来源和仓库禁用 MCP 过滤；`SetTools` 允许 MCP 目录变化后替换工具表。channel 输入只得到来源 channel 的工具和普通工具；本地输入保留所有 channel 工具。执行 MCP 时还会再查 channel，不完全依赖模型是否看得到。出处：`crush@3b1f860 internal/agent/agent.go:150-176,891-909,1724-1753`；`internal/agent/tools/mcp-tools.go:99-109`。

[读码] MCP 的工具发现是 `ListTools`，存入进程全局 `allTools`，根据配置 `enabled_tools/disabled_tools` 过滤；桥接为 `mcp_<server>_<tool>`，把 schema 的 `properties` 和 `required` 转为 Fantasy `ToolInfo`。`RefreshTools` 会刷新目录，注册/续连复用同一个登记入口。出处：`crush@3b1f860 internal/agent/tools/mcp/tools.go:27-59,114-205`；`internal/agent/tools/mcp-tools.go:23-97`。

[读码] 当前模式是“连接与目录准备好后，将全部已准入 schema 放入当前工具表”，不是“只注入工具索引，再由模型搜索并拉取某个 schema”。在 `buildTools/GetMCPTools/Tool.Info/PrepareStep` 没有看到 deferred-schema 或 tool-search 工具。这里的延迟主要发生在 MCP 异步连接、目录刷新和 LSP 进程启动，不应混为工具 schema 延迟加载。出处：`crush@3b1f860 internal/agent/coordinator.go:899-1013`；`internal/agent/tools/mcp-tools.go:23-97`；`internal/agent/agent.go:891-909`。

[读码] MCP 有 stdio 启动路径、Streamable HTTP 与 SSE 传输分支；连接状态枚举为 disabled、starting、connected、error、needs auth。维护每服务器的续连互斥锁和 generation，避免配置重建途中旧连接回写。OAuth handler 支持恢复 token/客户端登记，供连接与续期使用。出处：`crush@ internal/agent/tools/mcp/init.go:74-110,149-175,1175-1352`；`internal/oauth/mcp/handler.go:102-105,203-249`。

### 4. 工具结果、截断和媒体回填

[读码] 结果是 `fantasy.ToolResponse`，含文本、error 标记、metadata、StopTurn，也可为图像/音频等媒体。用户拒绝权限会返回 error＋`StopTurn=true`；普通 hook deny 默认只拦本工具，hook halt 才结束整轮。出处：`crush@3b1f860 internal/agent/tools/tools.go:79-86`；`internal/agent/hooked_tool.go:61-76,83-108`。

[读码] 没有在 `OnToolResult` 看到统一按 token 截断所有结果的总闸门；主要在工具内部限额。shell 工具按 ANSI 显示宽度判断 `30,000`，保留约前后各 `15,000`，完整内容另写 spill 文件并返回路径；stdout/stderr 分别处理后再拼接，所以不是整条结果严格 30,000 的总预算。出处：`crush@3b1f860 internal/agent/agent.go:1060-1081`；`internal/agent/tools/bash.go:53-57,465-520`。

## 三、上下文管理：全窗口摘要、缓存断点与实报/估算分离

### 1. 压缩触发、切法和模型

[读码] 自动摘要在每步结束后的停止条件中判断：窗口 `cw>200,000` 时，剩余不超过 `20,000` token 触发；`cw<=200,000` 时，剩余不超过窗口的 `20%` 触发；`cw==0` 不自动摘要；`DisableAutoSummarize` 可禁用。使用最近一次 `PromptTokens+CompletionTokens`，不是单纯消息条数。出处：`crush@3b1f860 internal/agent/agent.go:58-61,1136-1155`。

关键判断，摘录 `crush@3b1f860 internal/agent/agent.go:1145-1152`：

```go
if cw > largeContextWindowThreshold {
    threshold = largeContextWindowBuffer
} else {
    threshold = int64(float64(cw) * smallContextWindowRatio)
}
if (remaining <= threshold) && !a.disableAutoSummarize {
    shouldSummarize = true
```

[读码] 手动 `Summarize` 与自动摘要共用 `summarize`，触发值区分 manual/auto；会话 busy 时返回 `ErrSessionBusy`；`PreCompact` 可阻止。摘要使用 `a.models().Large`，构造没有工具的 Fantasy agent，system prompt 换成嵌入的 `summary.md`，历史材料来自当前有效窗口。不是使用 small 模型，也不是把旧历史直接静默删掉。出处：`crush@3b1f860 internal/agent/agent.go:1413-1489`。

[读码] 切法是“当前有效窗口整体交给摘要模型 → 新建一条 `IsSummaryMessage` 的 assistant 消息 → 成功后更新 `SummaryMessageID`”。后续只取摘要及其后的消息，并把摘要在请求副本里变成 user 角色；没有在这条实现中看到按 token 保留最近若干完整原文轮次的独立 tail-split。原始记录仍在库里，摘要指针只决定发送窗口。出处：`crush@3b1f860 internal/agent/agent.go:1430-1466,1540-1557,1772-1793`；`internal/session/session.go:51-65,204-234`。

[读码] 摘要提示要求保留当前任务、完成与未完成工作、文件与行号、技术上下文、成功/失败命令、策略、风险和具体下一步；`buildSummaryPrompt` 另把当前 todos 及状态加入摘要请求。它主要面向编码工作交接，没有独立结构化的“压缩后保留对象表”校验器。出处：`crush@3b1f860 internal/agent/templates/summary.md:1-67`；`internal/agent/agent.go:2392-2405`。

[读码] 自动压缩后，如果截断的最后 assistant 有 tool calls，会将原请求改写成“上一会话太长被中断，原请求为……”并排回队列继续；若 `PreCompact` 阻止，则这一轮结束，不继续撞同一上限。摘要调用同样记录费用，成功后窗口 prompt 计数归零、completion 计数设为摘要输出或估算。出处：`crush@3b1f860 internal/agent/agent.go:1247-1270,1543-1557`。

### 2. 缓存标记的位置与稳定性

[读码] `getCacheControlOptions` 为 Anthropic、Bedrock、Vercel 返回 `ephemeral`；环境变量 `CRUSH_DISABLE_ANTHROPIC_CACHE=true` 使其返回空 options。构造运行时给最后一个工具加标记；每次 PrepareStep 清掉旧消息 options 后，给最后一段 system 消息及最后两条消息重新标记。若 provider 有 `SystemPromptPrefix`，再把该前缀插到消息最前面。出处：`crush@3b1f860 internal/agent/agent.go:811-821,891-897,931-950,1575-1591`。

[读码] 缓存亲和性不只依赖上述断点：`sessionHeaders` 用会话 XXH3 哈希设置 `x-session-id` 和 `x-session-affinity`；OpenRouter 另在未配置时补 `session_id`，同样用会话哈希。它们表达上游路由亲和性，不能保证服务商一定命中提示词缓存。出处：`crush@3b1f860 internal/agent/agent.go:1594-1605`；`internal/session/session.go:28-33`；`internal/agent/coordinator.go:809-820`。

[读码] 稳定措施：工具名称排序；skills 发现遍历后排序；system prompt 构造与初始工具构造分开初始化，不是每一个流式 delta 重新组装前缀。出处：`crush@3b1f860 internal/agent/coordinator.go:862-894,1002-1004`；`internal/skills/skills.go:290-299`。

## 七、打断、插话与排队：同会话串行，步骤边界接纳

### 1. 三种输入生命周期

[读码] `messageQueue` 按 session 保存 `[]SessionAgentCall`。busy 时入队直接返回；真正合入模型发生在下一次 `PrepareStep`：普通无 RunID 的输入保存为 user 后附加到请求，带 RunID 的输入留在队列，等当前 run 结束后独立运行。它不会在正在生成的 token 流中实时重写输入，也不会因每条插话自动取消当前调用。出处：`crush@ internal/agent/agent.go:237-240,448-491,691-710,907-929`。

[读码] 带 RunID 的“排下一轮”和普通“下步插话”在协议层不同。`crush run` 的 client/server 路径为本次提交生成 UUID；只认可匹配 RunID 的终局事件并输出其文本，忽略别轮的 live message，避免挂到忙会话后被上一轮的结束误终止。代价是该路径并非始终逐 token 输出本轮内容。出处：`crush@ internal/cmd/run.go:282-300,346-385,415-450`。

[读码] `AddNote` 是第三种旁路：只在下一轮 prompt 前追加宿主注记，不存成聊天、不立刻驱动 run。它和队列消息不是同一个含义。出处：`crush@3b1f860 internal/agent/agent.go:2145-2164`；`internal/agent/host_context.go:10-18`。

### 2. 取消的竞态边界

[读码] `AcceptedRun` 表示“已接收但尚未交给 active/queue”的保留句柄；每次接收有递增序号。Run 和 Cancel 使用同一把 session dispatch mutex。Cancel 覆盖 active context、已接收但未激活的序号上界、已排队内容；取消以后的新接收序号更大，不被旧取消毒化。active entry 的 deferred 删除还比较指针身份，避免旧 run 收尾删掉新 run 的取消句柄。出处：`crush@3b1f860 internal/agent/agent.go:202-212,339-442,551-567,652-735,2087-2143`。

[读码] 取消入场也保存 user＋canceled assistant；清掉带 RunID 的排队项也发布 cancelled `RunComplete`，否则等待方可能永久等不到自己的终局。排队到下一 run 的交接先保留新的 AcceptedRun 再释放锁。出处：`crush@3b1f860 internal/agent/agent.go:502-537,575-596,663-690,1307-1410`。

[读码] TUI 提交先乐观标 busy，再通过异步 command 调 AgentRun，HTTP 接收与最终结果分开；有排队内容时 Escape 先清队列；无队列时第一次 Escape 进入取消确认状态，第二次在计时窗口内才真正 Cancel，也会取消当前 bang command。出处：`crush@ internal/ui/model/ui.go:5431-5508,5651-5704`。

### 3. 后台任务的排队不是消息排队

[读码] shell 支持显式后台和自动后台。`RunInBackground` 立即用独立 context 启动，先等 1 秒检查快速失败；前台命令默认等 60 秒，尚未完成则转后台；转后台前 ctx 取消会杀当前 shell。后台通过 `job_output/job_kill` 查询/停止，不随工具返回自然结束。运行上限默认 50 个，完成的任务不占运行名额。出处：`crush@3b1f860 internal/agent/tools/bash.go:26-32,53-57,335-463`；`internal/config/config.go:480-498`。

[推断] 这提供“长命令不占住一轮工具等待”的能力，但不是把所有后台模型任务、消息、审批统一塞进一个持久任务调度器；本次看到的 prompt queue、background shell manager、异步 title 是不同所有者。

## 十、做得特别值得拆的七项设计

这里的“特别”指本实现有清楚结构和适用价值，不声称其他家都没有。

1. **接收、排队、活动、终局分别建模。** `[读码]` AcceptedRun/序号覆盖接收窗口，RunID 关联独立运行，RunComplete 收口终局；取消不会只查一个 active bool。`[推断]` 好处是多客户端、忙会话继续运行和刚提交即取消都能有明确归属。代价是当前 queue/steering 行为隐含在 RunID 是否为空里，接口理解成本较高。出处：`crush@ internal/agent/agent.go:339-491,652-735,1307-1410`；`internal/cmd/run.go:282-300`。
