## 1. pi 的扩展接口

### 注册、发现和加载

| 维度 | 行为与出处 |
|---|---|
| 入口 | 默认导出工厂函数，签名 `(pi: ExtensionAPI) => void \| Promise<void>`。工厂返回值不是销毁函数。[契约] `P/dist/core/extensions/types.d.ts:1517` |
| 文件约定 | 目录直属 `.ts`、`.js`；下一层子目录的 `index.ts`、`index.js`；或 `package.json` 的 `pi.extensions` 声明。扫描不继续递归。[读码] `P/dist/core/extensions/loader.js:584` |
| 发现来源 | `discoverAndLoadExtensions()` 依次收集项目 `.pi/extensions`、全局 agent 目录的 `extensions`、显式配置路径，按解析后的绝对路径去重。[读码] `P/dist/core/extensions/loader.js:671` |
| 执行方式 | Jiti 导入，检查默认导出确实是函数；按路径顺序逐个导入、初始化。[读码] `P/dist/core/extensions/loader.js:464`、`:553` |
| 加载失败 | 记录 `{path,error}`，继续加载后面的扩展。初始化期间暂存的运行时注册、flag 默认值和事件订阅有提交／丢弃处理。[读码] `P/dist/core/extensions/loader.js:197`、`:420`、`:513` |
| 内联扩展 | 可直接从 factory 创建，不必落成文件。[读码] `P/dist/core/extensions/loader.js:546` |

### 错误隔离

- 普通通知、input、context、message_end、tool_result、provider payload/header 等：捕获处理器异常，发 extension error，继续后续处理器。不能依靠“抛异常”实现安全拦截。[读码] `P/dist/core/extensions/runner.js:816`、`:852`、`:890`、`:990`。
- **`tool_call` 是例外**：runner 不吞异常；session 向上传播，core 把准备失败转换为错误工具结果，工具不执行。[读码] `P/dist/core/extensions/runner.js:951`；`P/dist/core/agent-session.js:326`；`PA/dist/agent-loop.js:487`。
- `user_bash` 捕获后报告，再抛出，不继续当作默认本地执行。[读码] `P/dist/core/extensions/runner.js:965`。
- 已读 runner 中没有 omp 那样统一的 handler timeout 包装；挂住的 handler 可阻塞该 await 路径。[读码] 同上述 dispatch 实现。

### 事件总线会不会丢

**会错过事件，不是可靠消息队列。**

底层 `EventEmitter`；`emit()` 不等待 async listener 完成，无存储、确认、重放。没有订阅者时事件不会保留，晚订阅者收不到之前的事件。listener 异常被捕获并输出到 console。[读码] `P/dist/core/event-bus.js:1`。

这与 runner 的 `await emit(...)` 是两套语义：前者用于扩展间通知，后者承载宿主钩子。

## 2. omp 的扩展、hooks 和插件接口

### 三层需要分开

| 层 | 职责 |
|---|---|
| Extension | 工厂注册生命周期钩子、工具、命令等，是最接近 pi 的主要运行时接口。`O/src/extensibility/extensions/types.ts:1630` |
| Hook | 单独的 factory/API/runner，能力较窄，有自己加载和错误处理路径。不能把 ExtensionRunner 的全部保证套到 HookRunner。`O/src/extensibility/hooks/loader.ts:72`；`hooks/runner.ts:47` |
| Plugin package | 安装、启用、features、settings，以及 extensions/tools/hooks/commands 的资源集合；不是另一个对话循环。`O/src/extensibility/plugins/types.ts:24` |

### 注册、清单和加载

- 工厂仍是 `(pi: ExtensionAPI) => void | Promise<void>`；接受函数模块或模块的 default 函数。[读码／契约] `O/src/extensibility/extensions/loader.ts:61`；`types.ts:2053`。
- 原生 `.omp/.pi` extension capability、hooks、已安装插件、显式路径共同参与发现；按绝对路径去重，支持 disabled id。[读码] `O/src/extensibility/extensions/loader.ts:565`。
- **模块导入并行，factory 按原路径顺序串行绑定**；不能把并行 import 理解成并行注册。[读码] `O/src/extensibility/extensions/loader.ts:485`。
- extension package root 可额外贡献 `skills/`、`hooks/`、`tools/`、`commands/`、`rules/`、`prompts/`、`.mcp.json`。[契约] `O/src/discovery/omp-extension-roots.ts:1`。
- `package.json` 的 `omp` 或 `pi` 清单有 `extensions[]`、tools/hooks 入口、commands、features、settings schema。feature 可以控制各类入口，具有默认启用值。[契约] `O/src/extensibility/plugins/types.ts:1`。
- 插件运行状态包括 enabled、enabledFeatures、settings；有全局 lock state 和项目 overrides 类型。[契约] `O/src/extensibility/plugins/types.ts:103`。
- 单个导入或绑定失败返回错误，其他扩展继续；factory 出错会恢复其 pending provider registration 检查点。[读码] `O/src/extensibility/extensions/loader.ts:410`。

### 调度、失败、取消与超时

**同样没有通用的数字 priority。** 普通事件按扩展顺序、handler 注册顺序串行执行；shutdown 特例并行。延迟添加的扩展排在后面。[读码] `O/src/extensibility/extensions/runner.ts:1100`、`:1698`。

| 情况 | 行为 |
|---|---|
| 普通 handler 抛错／超时 | 报 extension error，结果视为无返回值，继续。默认预算 30,000 ms。[读码] `runner.ts:133`、`:1610` |
| `tool_call` 抛错／超时 | 返回 block，阻止工具运行。[读码] `runner.ts:1945` |
| 等待 handler 时工具调用取消 | 停止等待，最终返回 block，不能借取消绕过审批。[读码] `runner.ts:1987` |
| context handler 期间取消 | 返回前再 `throwIfAborted()`，避免把未完成处理的上下文交给模型。[读码] `runner.ts:2162` |
| shutdown | 单 handler 默认 2,000 ms，多个 handler 并行；finally 清文件 fallback 和托管 timer。[读码] `runner.ts:150`、`:447`、`:1718` |
| 超时是否能撤销任意副作用 | **不能据此保证**。实现通过 signal、竞争等待和注册 scope 收束；扩展自己的未响应取消的 I/O 仍需要扩展负责。[读码／推断] `runner.ts:1610` |

旧 `HookRunner` 是另一条实现路径，不应声称也有上述统一 timeout 保证。其 API、上下文和 handler 装配单独存在。[读码] `O/src/extensibility/hooks/runner.ts:47`；`hooks/loader.ts:72`。

### 事件总线、补发和丢失

- 普通 `EventBus` 是 `Map<string, Set<listener>>`。同步调用 listener wrapper，但不等待其 async 完成；异常写 logger；不保存历史、不确认、不重放。[读码] `O/src/utils/event-bus.ts:3`。
- `session_start` 晚加载补发是 **ExtensionRunner 专门实现**，不是 EventBus 的通用保证。[读码] `O/src/extensibility/extensions/runner.ts:1100`、`:1698`。
- 初始化前 credential-disabled 最多缓存 **32** 条，MCP notification 最多 **100** 条；超限移除最老项。[读码] `runner.ts:378`、`:923`、`:949`。
- 因此不能声称 omp “事件不丢”；只能说特定事件有有限缓存或特定补发策略。

## 3. 两家的差异表

| 维度 | pi | omp | 差别与适用情况 |
|---|---|---|---|
| 注册核心 | 单一 ExtensionAPI 工厂 | Extension + 旧 hooks + plugin package | pi 更容易保持接口集中；omp 适合已有多种扩展格式的宿主 |
| 包清单 | pi.extensions 等资源入口 | omp/pi manifest、features、settings、启用状态 | omp 更适合插件分发管理；不是最小内核必需 |
| 导入与初始化 | 路径顺序逐个加载 | import 并行，factory 串行 | omp 加速模块导入，同时保留注册顺序 |
| 输入接管 | action 联合类型 | handled/text/images 可选字段 | 都支持首个接管停止；pi 返回类型更明确 |
| 优先级 | 加载／注册顺序 | 加载／注册顺序 | 都缺 Sumika 所需显式优先级和消息批契约 |
| 请求上下文 | context 与 context_with_system 分层 | context + provider context 内部处理链 | pi 明确保护 system/tool 声明；omp 更强调每次请求改写标记 |
| system prompt | string + 结构化构造选项 | string[] | pi 有较细 prompt section 修改面；omp 用段落数组 |
| 最终消息改写 | message_end，可替换同角色消息 | assistant_message，只改既有文本 | pi 灵活但影响面大；omp 约束更适合保持工具／thinking 结构 |
| message_end 观测 | 同时是改写点 | 分离快照通知 | omp 区分“变换”和“通知”更清楚 |
| 工具参数 | 原地改 input | 返回 input，最后一个胜出 | omp 显式返回更易审阅；不能假定每个 handler 都看到前一个返回的 input |
| 工具附加信息 | 可改工具结果 | 另有 additionalContext 聚合 | omp 区分工具数据和可信指令，但 Sumika 仍需自己的信任边界 |
| 普通异常 | 多数报告后继续 | 多数报告后继续 | 两者普通 hook 都不能直接当强制审核门 |
| 工具前异常 | 阻止执行 | 阻止执行，并处理超时 | omp 对挂起审批处理更完整 |
| 收尾 | turn_end / agent_before_settle 边界 entry；agent_settled | session_stop 续行；agent_end 带继续标记 | pi 适合会话历史边界变更；omp 适合停止前补一轮 |
| 压缩 | before_compact 可完整替换 | 同上，另有 session.compacting | omp 多一个摘要 prompt/context 定制层 |
| 生命周期 | stale runtime、订阅跟踪 | 延迟添加、暂停恢复、托管 timer/fallback | omp 更适合长驻且动态启停的宿主 |
| reload | 有扩展缓存清理及上下文失效机制 | ctx.reload 是会话重读 | 同名不能按同一语义移植 |
| 事件可靠性 | 无通用持久化／重放 | 同样无；少数事件有专门补发／缓存 | 两者都不适合作为渠道可靠投递队列 |
| 项目信任 | ctx 提供 trust 状态 | isProjectTrusted 固定 true | omp 明确默认信任项目输入；不应移植为 Sumika 权限默认值 |

出处分别见前两节；最后一项的 omp 明文契约在 `O/src/extensibility/extensions/types.ts:731`。

## 4. 四项已知需求怎么接

以下为 **[推断]**，接点依据前述源码，不代表两家已提供 QQ 或 Sumika 插件。

| 需求 | pi 接法 | omp 接法 | 顺不顺、缺什么 |
|---|---|---|---|
| 记忆：请求前召回 | `context` 给本次请求插参考信息；需要改变结构化 prompt 时用 before_agent_start | `context`；已有可选 ctx.memory，但属于 omp 自己的 memory runtime | 请求临时参考信息接得顺；须区分“一次用户活动”和“每次模型请求”，工具续行也会再次触发 context |
| 记忆：结束后总结 | 每个模型 turn 用 turn_end；整次活动真正结束用 agent_settled；要写会话边界用 agent_before_settle | turn_end；终结判断需要看 agent_end 的 willContinue/awaitingAsyncWork；session_stop 可以续行 | 不能把每次 agent_end 都当一次完整对话最终结束，否则重试／后台续行可能重复总结 |
| 三个记忆工具 | registerTool | registerTool | 两者都直接支持；存储、检索、可见性由 Sumika 提供 |
| 发出前防泄漏 | message_end 能改最终文本，但普通异常继续 | assistant_message 能改最终文本，但普通异常继续 | **均缺强制 outbound gate**；流式内容也可能已经暴露，必须由平台发送路径统一审核 |
| 渠道中间件 | 入口规范化后调用 session；input 可处理文本；输出监听最终消息 | 同样；可用 custom message / source 等桥接 | 缺平台原始事件、统一 Person/Conversation、群内开口决策、批次、发送确认；不能只靠 text/images/source 表达 |
| 复读／戳一戳拦截 | input 返回 action:handled | input 返回 handled:true | 首个接管停止很接近；缺显式 priority、原始事件类型、整批消费／部分消费契约 |
| QQ 平台适配器 | 外部服务或 extension 自管连接 | 外部服务或 extension 自管连接，托管 timer 只解决部分清理 | 两家都没有从这些 API 直接得到平台连接、重连、去重、ack、附件上传、群成员映射协议 |

两点尤其影响 Go 接口选择：

1. **“拦截完成就不调模型”应落在模型请求之前的批处理中间件。** 不宜在 context hook 返回空消息假装完成，也不宜以 abort 代替“已处理”。两家的 input 短路语义可借，数据结构需要另定。依据：`P/dist/core/extensions/runner.js:1196`；`O/src/extensibility/extensions/runner.ts:2073`。
2. **“发出去前检查”必须覆盖所有发送来源。** 模型回答、复读插件、戳一戳回复、主动发送都要经过同一平台发送门；两家的 assistant 改写点只覆盖模型消息，不能覆盖这些来源。依据：pi 的 message_end 接线 `P/dist/core/agent-session.js:935`；omp 的 assistant 限定 `O/src/extensibility/extensions/types.ts:1121`。

这里不改变本地私聊、本地群聊、QQ 私聊、QQ 群的任何默认可见性或工具权限；这些差异需要由 Sumika 自己的调用上下文携带。

## 6. 对接口选择的建议与待核实项

**[推断] 建议借 pi 的内核回调分层，借 omp 的强制门失败策略和生命周期管理，渠道接口由四项已知需求单独约束。**

具体可借：

- `transformContext`、工具前后回调、streamFn、steering/follow-up drain 的内核边界。
- 将“通知”和“允许替换／阻止的处理链”分开；避免一个事件名同时承担观测和修改。
- 对审批、出站审核这类门明确“出错／超时／取消即不放行”；不能沿用普通 context hook 报错后继续的策略。
- 最终文本改写保持工具调用和其他结构不变；平台发送前审核另设接口。
- 扩展注册顺序与业务拦截优先级分别定义。消息批拦截需显式说明“第一个接管消费整个批次”，不能从两家的 text input 钩子暗推出来。

仍待核实的具体范围：

1. 两家未发布的对话循环测试源码：FakeModel、mock provider、fixtures、实际测试案例和断言。
2. omp replay tests 的数据格式、录制和重放机制；两家的对话 E2E harness。
3. omp 扩展源码重新导入的完整热更新入口；当前已确认 `ctx.reload()` 只是会话重读。
4. 插件自行创建的外部连接、原生 timers、总线订阅在暂停／卸载时的完整清理责任；目前不能声称宿主统一接管。
5. 两家现有回归测试是否实际覆盖上面的每条过线项。表中列的是可借的行为契约，未运行任何验证。
