# 蒸馏：Claude Code 团队怎么做验证，对照 Sumika 的验证流程

> 来源：Anthropic 博客《How the Claude Code team thinks about verification》（claude.dev/blog，2026-11-18 读，[读原文]，转述不摘录）。主人 2026-11-18 要求“把核心思想蒸馏出来，并且用于优化我们的验证、测试流程”。
> 挂在：[待办](../待办.md) 第八节“验证流程按蒸馏笔记改”一条。

## 一、核心思想（五句话）

1. **验证是让人敢多派活的前提。** 每样东西都得人看，就只能同时跑一两个代理；验证能自己跑，才能放手并行。人的角色从“读每个改动”变成“定义什么算做完、看证据”。
2. **验证 = 把改动真跑起来。** 端到端（像用户那样操作真程序）比单元测试更难糊弄、失败信息更有用（哪一步、截图、为什么）。把“怎么启动、怎么操作、怎么看结果”写成一个 verify 技能，提交前必跑，并花力气让它快和稳。
3. **三种测试最值得投资**：端到端；性质测试（往返、不变量、幂等、和朴素实现等价，让库生成成千上万输入去撞）；差分测试（新旧两版同一批输入比输出，排掉无关差异，登记有意的改动）。不稳的测试会教代理“重跑”而不是修，慢的测试会减少每批能跑的检查。
4. **检查不能被它要判的改动改到。** 审阅规则从基线分支读，不从 PR 里读；结论绑定到具体提交，推了新提交就作废；便宜的检查先跑。每个提交都盖章写明“怎么验的”，没验也写“没验”。新门槛先“只记录不拦”看误报，再改成拦截；同一会话拦两次就放行，免得卡死。
5. **验证层本身也要被验证、被修剪。** 用真出过事的改动（后来被回滚的、被拒的）加同等大小的干净改动当对照，分别量“找到了几个、核实后剩几个、最终报出几个”；漏掉的变成规则（至少出现在两个改动里、从 diff 能看出来、三个代理试着推翻、人批准）；规则和测试会越堆越多，要定期删。按 diff 触发的可靠性清单（触发条件、检查、出处事故），每次只查命中的三到十条。失败三轮还修不好就停下交给人。

## 二、对照我们现在的做法

| 文章说的 | 我们现在 | 差距 |
|---|---|---|
| verify 技能：真启动、真操作、看结果，提交前必跑 | 有 `ui.NewTester`（组件级）、`cmd/ui-tour`、`cmd/e2e-run`、`-demo`；没有一个“启动 Sumika 走一遍主流程”的统一入口，代理改完界面常只跑单元测试 | **缺统一 verify 入口** |
| 端到端优先 | 产品测试多是包内测试；完整路径测试只在少数地方（密钥设置页、本地聊天） | 主流程端到端少 |
| 性质测试 | LESSONS 已写“清理两遍 = 清一遍”；全仓只有两处 fuzz | **几乎没用**；Go 自带 `testing` 的 fuzz 就能做 |
| 差分测试 | Go 对 Bun 录像对拍（golden）做了很多 | 有；ADR-389 脚本迁 Go 正好用它 |
| 检查不被改动改到 | 提交和推送钩子跑的是工作区里的检查脚本；合并队列跑的是合并后树里的 go-verify。改检查的分支由它改过的检查来判 | **有缺口** |
| 结论绑提交、盖章 | 合并提交带 go-verify 结论行；验证记录按树认 | 基本有；普通提交没写“怎么验的” |
| 便宜检查先跑 | 钩子快检查 + 队列 + 每日整套 | 有 |
| 新门槛先观察再拦截 | 新检查一上线就拦，11 月里几次挡合并 | **缺观察档** |
| 不稳的测试：不重跑、不加 sleep，查不出根因就删掉并写原因 | AGENTS 已有“不重跑碰运气”“不靠放宽超时” | 缺“查不出就删并写原因”这条出口，偶发红挂在待办里很久 |
| 失败三轮就交给人 | 派活说明里没写上限，代理有时反复折腾 | 缺 |
| 按 diff 触发的可靠性清单 | 边界清单是通用的，LESSONS 是规则，没有“触发条件”一栏，靠人记 | **缺** |
| 验证复核本身 | 高风险派独立复核；没量过复核找 bug 的命中率 | 缺 |
| 规则会长，要修剪 | LESSONS 三天升级 AGENTS；没有定期删 | 缺修剪 |

## 三、建议的改动（按收益排）

1. **verify 技能**（`.claude/skills/verify/`）：一条命令编出 exe、用编的数据目录（`cmd/desk-fixture`）以 `-demo` 或 receive 起来，经 `sumika-ctl` 和 `ui-tour` 走主流程（本地私聊发一句、流式、停止、审批一张卡、切会话），失败时给出哪一步、截图、日志尾。改界面、回合、渠道的提交前必跑；派活说明里写上。
2. **检查从基线读**：合并队列和 CI 里，检查脚本（钩子、check-docs、隐私扫描、go-verify 的挑包规则）用 main 上的版本跑；分支改到这些脚本时，额外用分支版本再跑一遍，两版结论都写进合并说明，并标“改了检查本身”走高风险复核。ADR-389 把脚本迁 Go 时一起做。
3. **按 diff 触发的可靠性清单**：把 LESSONS、证据存档、复核记录里的事故整理成“触发条件（看 diff 能判断，例如改了 `internal/store` 的表结构、改了消息类型、改了场合判断）、检查、出处”三栏；合并前由脚本按 diff 挑出命中的几条写进 PR。第一版从证据存档里挑出现过两次以上的。
4. **性质测试**：先挑五处（文本清理幂等、导出改写幂等、配置读写往返、`jsjson` 解析往返、上下文压缩不丢最近两轮），用 Go 自带的 fuzz（`go test -fuzz`）写，`-short` 下只跑种子语料。
5. **新门槛三档**：新加的拦截类检查先“只记录”一周看误报，再“拦截”；拦截时允许提交说明写明为什么跳过，同一分支连拦两次的情况记进报告。
6. **派活说明加两条**：同一个失败修三轮还不过就停下交回、写清卡在哪；偶发红查不出根因时删掉这个测试并写原因（挂待办），不加等待、不重跑。
7. **提交盖章**：提交说明末尾固定一行“验证：……”（跑了哪些、结论行；没验写“没验”），钩子先只检查有没有这一行（观察档）。
8. **量复核的命中率**：拿已回滚或复核抓到过的高风险改动当样本，加同样数量的干净改动当对照，量独立复核代理的“找到 / 核实后 / 报出”三段召回。量完再决定要不要调复核提示词。
9. **定期修剪**：复盘任务每周看一次 LESSONS、AGENTS、check-docs 规则和慢测试，列可删项给主人。

第 1、4、6 条不改规矩，可以直接做；第 2、3、5、7、9 条改的是检查本身或 AGENTS，先给主人看再做。
