# 方案：一个群就是一个项目工作区（探索稿，2026-11-16）

> 状态：方向已定（2026-11-16，[ADR-387](../决策记录.md)）：第 7 节五项主人都照推荐定了，第 2 项另补“主人也可以自己加文件夹”。实现排在工单之后，还没写规格。
>
> 起因：主人 2026-11-16 说，像 Grok bot 那样一个对话从头聊到尾，不适合同时安排几件事：同时派几件不同的任务，它的上下文会被各张工单的进度通知搅乱。主人的想法是：
> - 一个群就是一个项目工作区；
> - 群里有不同分工的角色，同一种分工可以有多个，按需“分裂克隆体”；
> - 一个群可以链接多个本地文件夹，每个文件夹有访问或修改权限，角色实际能做什么取各方权限的交集。
>

- **终点**：主人往一个群里交代几件事，各自推进、互不打扰。群里只出现需要主人看的东西；想看某件事的细节，或者想插话，点进去就行。
- **现在在哪**（2026-11-16 核过代码）：
  - “工作”这一层只有三张空表（`trace/0020_work.sql`），没有任何代码读写；

  - 本地群聊有成员表，没有文件夹；按会话选目录是一个会话一个目录，群聊不能设；

## 1. 主人说的 → 对应 → 边界

| 主人说的 | 对应 | 边界 |
|---|---|---|
| 一个群就是一个项目工作区 | 群是长期的项目容器，管成员、链接的文件夹、权限。补的正是讨论稿 9.3 推后的“项目”那层 | 只限本地群聊。QQ 群照 ADR-206 永远不带文件夹 |
| 同时给它派几件不同的事 | 每件事是群里的一项**工作**，有自己的**工作线**（独立上下文）。T3 Code、Amp 都是“一件事一个线程” | 群的主时间线不再兼当所有工作的父线程（T3 Code 的坑，见第 2 节） |
| 上下文别被进度通知搅乱 | 进度只进工作线和看板。群里和私聊只收几种状态变化（第 2 节） | 这是这份方案的验收线，见第 5 节 |
| 不同分工的角色，同种可以多个、按需克隆 | 两种读法差别很大，见第 3 节。推荐：角色不克隆，分工靠工牌，队员按需多开 | 记忆只写给带人设的角色。队员不以角色的人格说话 |
| 链接多个文件夹，有访问或修改权限 | 群挂 N 个文件夹，每个标“只读”或“读写”。工作默认继承，可以收窄 | 链接文件夹等于扩权：每个文件夹主人点一次头，接 ADR-206 的信任 |
| 权限取交集 | 某个角色或队员对某个文件夹的实际权限 = 群给这个文件夹的 ∩ 工牌上限 ∩ 场合上限 ∩ 提出人上限。就是 ADR-369 第 4 条那串交集再加一项 | 不是“全群取最弱的那个”；不放宽 ADR-369 表里任何一格 |

## 2. 进度到底去哪：解决“上下文被搅乱”的关键

三家参考的共同做法：子任务的过程留在它自己的上下文里，回到上一层的只有结果。

- Claude Code Agent Teams 的队长只收四样：完成（附最终答复）、失败、队员主动发来的消息、等批的权限请求。进度放在任务清单文件里，不进队长的上下文。
- T3 Code 的后台状态走界面通知（侧栏状态、角标、提示），不发进别的线程。但它的子任务做完，会自动“唤醒”父线程并把结果塞进去。所以如果群聊兼当所有工作的父线程，结果和提问照样全堆在群里。

推荐的去向：

| 东西 | 去哪 | 不去哪 |
|---|---|---|
| 队员的每一步、工具调用、中间结果 | 只进它自己的工单上下文。主人点开工作能看到 | 不进工作线，不进群 |
| 工单交回的结果 | 进所属工作的工作线，由负责的角色接着处理 | 不直接进群 |
| 工作的状态：开始、要拍板或审批、完成（一句结论）、失败 | 群里一张**工作卡片**，原地更新，不是一条条往下追加 | 不追加成消息历史 |
| 进行中的工作有哪些 | 给群里角色看的是一份**看板快照**，放在请求末尾，每轮替换。末尾变化不破坏前缀缓存（LESSONS：每轮变化的内容只放末尾） | 不进历史 |
| 私聊里交代的事 | 默认挂在她的日常下面，不进任何群。说明了是哪个项目，就挂进那个群 | — |

## 3. “克隆”的两种读法（要主人定）

- **读法 A：克隆带人设、带记忆的角色。** 群里同时有铃音、铃音 2、铃音 3，各干各的，都以铃音的口吻说话。
  - 问题：记忆写给谁、互相冲突时听谁的；群里同时有好几个“她”说话，没法分辨；和 ADR-354 第 3 条“队员共用、不分角色”、讨论稿“执行者不以另一个人格说话”都冲突。
- **读法 B（推荐）：角色只有一个，她可以同时负责好几项工作，每项各一份上下文；“同一种分工多个”靠工牌，队员按需多开。**
  - 正例：铃音负责“查资料”和“改代码”两项工作，两条工作线各一份上下文，记忆都写回同一个铃音。“改代码”那项一下开了两个干活的队员，群成员栏里显示成“铃音的队员 · 干活 #1、#2”。主人能点进去看过程、插话（Agent Teams 也能直接和某个队员说话），但队员不以铃音的口吻在群里发言。
  - 反例：群里冒出第二个铃音用她的人设回话；队员把东西写进铃音的长期记忆。
- **为什么推荐 B**：主人要的“同时干几件、互不打扰”，靠的是“一件事一份上下文”，不需要复制人格。复制人格带来的记忆、身份问题，A 解决不了，B 根本不会碰到。

## 4. 文件夹和权限的细节

- 群设置里能加、能移除文件夹，每个文件夹标“只读”或“读写”。
  - 第一次加某个文件夹时问一次信不信任（ADR-206）；
  - 加文件夹要主人点头，因为它决定了能在哪执行、能改哪些文件。
- 工作默认继承群的文件夹，可以收窄，不能放宽。工单也只能收窄（ADR-295 第 3 条）。
- 几项工作同时改同一个文件夹时：默认共用，负责的角色判断要并行改时，给这项工作开一个 worktree（只限 git 仓库，照 T3 Code、Cursor 的做法）。
  - 要在卡片上写明：主目录里没提交的改动，不会自动带进 worktree（T3 Code 的已知行为）。
- 审批卡照 ADR-369：写明哪个群、哪项工作、哪张单、哪个队员，因为哪条消息、谁提的。
- 三家参考都没有“每个文件夹单独设只读或读写”，这一块是我们自己定的，规格里要单独做“形状 × 入口”表。

## 5. 验收线（主人的原场景）

- **同一个角色同时接三件事**：每件的上下文里看不到另外两件的进度。群里只有三张卡片，各自原地更新。主人点进任一件能看到过程、能插话。
- **只读文件夹**：在只读文件夹里改文件，四种场合里任何一种都过不了门。
- 群没挂文件夹时，就是普通群聊，体验不变。

## 6. 成本

- 没量过。群聊 token 效率按 ADR-352 第 4、5 条排在前面：没被点到的成员不跑模型；工作线只在有事的时候跑；看板快照放在末尾，不破坏前缀缓存。
- 落地前先在本地群聊用固定剧本，量“三项工作并行”时每轮每个角色的输入 token。

## 7. 主人定了（2026-11-16，都照推荐；见 ADR-387）

1. **克隆的读法**：A 还是 B？推荐 B。
2. **群里显示什么**：推荐开始、要拍板或审批、完成、失败四种，用卡片原地更新；进度不进群。
3. **加文件夹要不要点头**：推荐要，每个文件夹一次。
4. **同一文件夹多项工作同时改**：推荐默认共用，她判断需要时开 worktree；另一种是每项工作都默认开 worktree。
5. **私聊里交代的活**：推荐默认挂在她的日常下面，提到项目才挂进那个群。
