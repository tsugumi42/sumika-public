## 3. 现在怎么跑

### 嵌入服务（Bun 和 Go 共用同一份 Python）

`<MaiBot 目录>\server.py`：FastAPI + onnxruntime，只装一个模型。

- 模型 id 写死 `qwen3-embedding-0.6b-local`。请求里的 `model` 对不上就 404。
- 目录默认 `<模型根目录>/_待分类/Qwen3-Embedding-0.6B`，可用环境变量 `MAIBOT_EMBED_MODEL_DIR` 改。Go 侧**没有**设这个变量。
- 直接跑是 `127.0.0.1:11435`。Sumika 不走这条：`embed/bridge.py` 导入同一个 app，加上 Bearer 令牌，听 `SUMIKA_EMBED_PORT`（随机端口）。
- 只注册了 `CPUExecutionProvider`，intra 线程 2，一把锁同时只算一条。缓存最近 256 条原文。
- 接口：`GET /health`、`GET /v1/models`、`POST /v1/embeddings`（OpenAI 形状，`float` 或 `base64`）。没有重排路由。
- 服务自己不加指令前缀，调用方给什么就算什么。

Go 看管在 `native/internal/embed`：

- `Local` 用配置里的 python 跑 `embed/bridge.py`（`Python`、`ServerDir`、`Model` 三项缺一就不起，ADR-098）。随机端口、随机令牌、180 秒内等 `/health`，之后每 30 秒看一次，挂了按 1/2/4… 秒退避、最长 60 秒再起。Windows 上 `taskkill /T` 杀进程树，不弹黑框。
- 就绪以后 `Embed` 走 `Client`：OpenAI SDK 的 `/v1/embeddings`，30 秒超时，不重试。向量按返回的 `index` 排好。没就绪是 `ErrUnavailable`，调用方退回只用全文，不当成故障。
- `Client` 不关心对面是本机子进程还是别的 OpenAI 兼容地址（`llm.Source` 的 BaseURL + APIKey）。记忆侧没有第二个「重排」插口。

配置示例只写了 `embed.python` / `embed.serverDir` / `embed.model`（`sumika.example.yml`）。`model` 必须等于 `server.py` 的 `MODEL_ID`，否则健康检查能过、真正嵌入会 404。

### 召回里向量用在哪，重排有没有口

`native/internal/memory/recall.go` 的 `Recall`，和规格-记忆-v2 第七节一致，起步参数：

1. 固定要点（约定、边界）先拿出来，不参与排序。
2. 门控。拦住就只留固定要点，后面都不做。
3. 词法：两字、三字两张 FTS，各路按名次做 RRF（k=60），再合成一路。别名命中另记。
4. 向量：查询原文（有上文再加一条「最近几句 + 这句」）交给 `Embedder`。和能看的条目逐条点积，余弦低于 `SimilarityFloor`（0.6）丢掉，取前 50。维度不一致的条目直接跳过。
5. 合并：词法名次和向量名次再各算一次 RRF，乘新近度；别名命中加 1 分，排到前面。候选保留前 40（`Candidates`，考题的「排名」看的是这份）。
6. 再挑进本轮：没过期、这一段没给过；待确认最多 1 条、片段最多 2 条；和已挑的余弦 ≥ 0.92 当重复跳过；按场合限字数。这是考题里「日常真的给了」。

向量存在旁边库 `memory_vectors`：`model`、`prompt_version`、`content_hash`、`dim`、`vec`。现在 `VectorPrompt = "raw-v1"`，注释写明存和查都是原文，没有任务前缀；改前缀要换这个值，旧向量当过期（`index.go`）。嵌入失败或 `ErrUnavailable` 时保留已有向量，不把整次召回打成错误。

插件层另有一道时限：拼参考信息时，向量这一路最多等 `RecallTimeout`（默认 3 秒，内核钩子是 5 秒）。超时退回只用全文，固定要点照给（`native/internal/memplugin/plugin.go`）。

**没有重排调用，也没有 Reranker 接口。** 排序在第 5 步就定了，第 6 步只是按这个顺序往字数预算里装。

## 4. Magpie 能不能代理嵌入和重排

ADR-198 第 1 条：本地模型服务要「像调 API 一样」，本地和在线换着用；动手前先查 Magpie 能不能代理嵌入、重排。

2026-10-28 读到的本机网关 `http://127.0.0.1:3425/`（`name: magpie`，`version: 0.1.1762`）根上的 `apis` **列了** `/v1/embeddings` 和 `/v1/rerank`。对这两个路径发 GET，都是 404。没有发 POST，避免真的调模型。

`GET /v1/models` 读完了（`has_more: false`，最后一项 `opendesign/deepseek-v4.1-flash`）。抽到的 `native_endpoints` 只有 `/v1/chat/completions` 或 `/v1/responses`，没有一项写嵌入或重排。Sumika 仓库里 Magpie 只被当成聊天来源（`native/internal/llm` 的 `Magpie()`，占位 key `magpie-local`）。`docs/notes/拆解-Magpie插件设计-2026-10-25.md` 里搜不到 embed / rerank。Magpie 自己的源码这次没找到，所以：

- 这两条路由是挂了名字，还是 POST 能转发到上游，**没查到**。
- 能不能把本机 ONNX（现在这份 `server.py`，或以后的多模型服务）登记成网关后面的一个来源，**没查到**。

在查清之前，不要假定「记忆改走 3425 就同时有了本地嵌入和重排」。

## 5. Go 记忆接嵌入和重排：几条路

调用形状保持现在这样：记忆只认 `Embedder`（再加一个下面说的 `Reranker`），不认进程和路径。换模型本来就会让 `memory_vectors.model` / `prompt_version` / `dim` 对不上，然后整表重算。这个机制已经有了，不必另造影子表才能做实验；实验用库副本，别在正在写的库上重算。

| 路 | 做什么 | 代价 | 适合 |
|---|---|---|---|
| A. 照现在的子进程 | 一个 `server.py`、一个 ONNX、一个模型 id。重排要再起一个进程，或在桥上加路由 | Go 侧几乎不用动。换模型要改 Python 的池化，不是改目录。仍然是一份 Python 环境；CPU、一把锁、同时只算一条。重排和嵌入抢同一把锁的话，每轮召回会叠上几十次前向 | 维持现状。对比实验可以临时换一份服务，不要改生产 id |
| B. 同一个 `server.py` 装多个模型 | 按请求的 `model` 选会话；每种架构自己的池化（最后一 token / CLS / mean）和前缀写在服务里，不写进记忆。加 `POST /v1/rerank`（query + documents → 分数）。闲置模型按需加载、用完可卸 | 仍是 Python + onnxruntime，但只有一个看管循环，Go 的 `Local` 能接着用。内存按「当前装上的」算，不要八个一起常驻。Qwen 那条带 `past_key_values` 的输入和 pplx 的 int8 输出都得单独接，不能用现在的 `_infer`。重排一次是 N 对，不是 N 条向量 | **和 ADR-198「按需起停、像调 API」最接近的一步。** 表达学习、表情包搜索以后也走这一个地址 |
| C. Go 里直接跑 ONNX | 用 onnxruntime 的 Go 绑定，在进程里算 | 能去掉「最后一小块 Python」（待办里那条）。分词、动态轴、外部数据、Qwen 的空 KV cache、四种池化、重排的 logit，都要在 Go 里重做一遍；现在这些在 `server.py` 里已经写了。绑定和 CPU/GPU 包的版本要自己跟。记忆包不该 import 这些 | 等 B 的接口和考题都稳定再考虑。现在做是把已有的 Python 重写一遍，换不来召回质量 |
| D. 走 Magpie | `Embedder` 的 BaseURL 改成 `127.0.0.1:3425/v1`，重排同样走网关 | 调用处真能和聊天一样换本地/在线。但第 4 节没证实网关会把嵌入/重排转到本机 ONNX，模型目录里也没有这两类。在线嵌入还有密钥、额度和出网，记忆原文会离开本机 | 只在 Magpie 确认能挂本地来源、并且默认仍走本机之后，才把地址换过去。在那之前 D 不是落地路径 |

重排不要塞进 `Embedder`。它吃的是一对文本、吐的是分数，失败时应当退回现在的 RRF 顺序（和嵌入不可用退回全文同一条规矩）。

### 重排放在召回的哪一步

放在 **第 5 步合并出候选之后、第 6 步按字数往里装之前**。

- 重排救不回没进候选的条目（旧调研第 6 节，和模型卡自己的用法一致）。所以它重排的是词法 ∪ 向量 ∪ 别名已经召回的那一池，不是只重排向量前 50，也不是只重排最后塞进字数预算的那几条。只重排已经装进去的几条，换不出「差一点被字数砍掉」的那条。
- 池子先按现在的 RRF 截到一个固定的 M（起步用现在的前 40，和 `Candidates` 一样）。M 要写死在实验里，否则「加重排」和「多看几条」混在一起。
- 重排只改这 M 条的相对顺序，再走现有的门控后挑选：待确认 1 条、片段 2 条、近重复 0.92、字数预算。别名加分和新近度要不要还乘上去，实验里分成两臂，不要和「有没有重排」绑死。
- 门控拦住的轮次不调用重排。
- 重排超时或服务不在：用原来的 RRF 顺序，记一条原因码，不写原文。时限算进现有的 3 秒 `RecallTimeout`，不要另开一条把内核的 5 秒钩子吃满。`bge-reranker-v2-m3` 是 24 层、544MB，CPU 上 40 对可能超过 3 秒；真超过，就只在明确回忆（`ModeExplicit` / 搜索工具）上重排，每轮自动想一下仍只用 RRF。这条等考题的 P95，不要先猜。

## 6. 对比实验（只设计，不跑）

用已经生成的那一份考题，不要重新跑 `scripts/memory-eval/make.ts`。出题会再调后台模型，题目会变，和 2026-10-25 的基线也对不上。

出题和打分现在就是这两处：

- 出题 `scripts/memory-eval/make.ts`：库副本上每条记忆让后台模型写 3 句「以后会怎么提起」，不超过 6 个字的标 `short`，其余 `paraphrase`；另从真实消息里抽去掉标记后 ≤2 字的 60 条当 `chitchat`（正确答案是什么都不给）。题和条目写在 `data/dev/memory-eval/<角色>-v0-<日期>.json`（不进 git）。
- 打分 `native/cmd/memory-eval`：把 `memory.db` 和 `events.db` **拷进临时目录**再打开，嵌入自己起一份子进程。明确回忆（`ModeExplicit`，主人、主窗口）看目标在 `Candidates` 里的名次：前 1 / 5 / 8 / 20。再按日常召回（过门控、限字数）看目标在不在 `Hits` 里（「日常真的给了」）。按条目种类分开：有效事实、待确认、片段、片段（自称闲聊）。寒暄题看给了几条、给了多少字。越权是自检（硬条件 0）。耗时是一次明确回忆的 P50 / P95，含嵌入。`-novec` 是只用全文的对照。

实验只加「哪个嵌入、哪条前缀、重排开还是关」，不改考题、不改门控和字数预算。

### 怎么才算公平

- **同一份题**：一个考题 JSON 路径，所有臂用它。不重新出题。
- **同一份库副本**：开跑前把那份 `memory.db`（连 wal/shm，照 `copyDb`）拷成一份冻住的快照；每一臂再从这份快照拷到自己的临时目录，自己建旁边的 `memory-v2.db`。不要臂与臂共用一个向量表，维度和 `prompt_version` 不同不能混。不要打开正在给 Bun 写的那份。`events.db` 同样只拷一份，给人名和寒暄场合用。
- **同一条代码路径**：只换 `Embedder` 和可选的 `Reranker`。`SimilarityFloor`、RRF 的 k、词法 top、向量 top、字数预算、门控都不改。
- **前缀按模型卡，不按感觉。** 要求查询带指令的，库存侧不加；写明不要前缀的，两侧都不加。`prompt_version` 记进向量表，也写进结果 JSON。另做一张「全部裸原文」只作为附注，不拿来宣布谁赢——那会故意亏待 Qwen 和 Harrier。
- **跑三遍，轮流，不连跑。** 一轮里按臂转一圈，再下一轮；每一轮把臂的先后倒一下，避免总是同一个模型吃冷启动。质量是确定性的：同一臂三遍的前 1/5/8/20 和「日常真的给了」必须一样，不一样先查 bug，不解释成模型波动。耗时用三遍的 P50/P95 分开写；只有三遍同向才说谁更快（上级约定：比两版跑三遍）。服务保持开着，这样第 2、3 遍吃到 `server.py` 那 256 条缓存——所以延迟结论以第 1 遍为准，第 2、3 遍只用来看缓存后的稳定值。开跑前先做一次不计入成绩的补齐向量。
- **补齐耗时单列**：每臂记「N 条库存、批大小 64、墙钟多久」。这是换模型的成本，不要混进单次召回的 P50。规格里写过第一次补齐约 550 条用了 120～130 秒，当时还有别的进程在跑；这次要在嵌入服务只起这一份时重记。
- 结果沿用 `memory-eval` 的 JSON（`exam`、`tag`、`summary`、`p50`、`p95`、逐题 `rows`），`tag` 里带模型名和 `prompt_version`。不要写进 git。

### 量什么、怎样才算更好

沿用打分器已经印的那些，外加补齐耗时：

- 有效事实 × 换说法 / 短的：前 1、前 5、前 8、前 20，和日常真的给了。短的和换说法分开，短句最容易被换嵌入弄坏。
- 待确认、片段、自称闲聊的片段：同样一组。闲聊片段不该因为换了模型就更容易被送进本轮。
- 寒暄：给了东西的比例和字数。这一项只许不升。
- 越权：仍是 0。
- 一次召回 P50 / P95，以及补齐 N 条的墙钟。P95 越过 3 秒的臂，不能当每轮自动召回的候选（会撞上 `RecallTimeout`，向量那一路等于没接上）。

三遍都同向，并且同时满足，才说这臂优于现行 Qwen `raw-v1`：有效事实换说法的前 8 和「日常真的给了」不差于基线，短题不退，寒暄注入不升，越权仍是 0，P95 仍低于 3 秒。只赢前 20、日常给出去的没变，不算更好——前 20 进不了字数预算就碰不到人。重排用同一条线，再加一条：R1 相对 R0 的提升要大于它多出来的延迟所值；中文上重排几乎不赢这件事，旧笔记已经记过（调研-记忆系统设计-研究铃音，Qwen 技术报告 Table 4），所以「没差」是预期中的一种结果，不是实验失败。

公开榜（MTEB、C-MTEB、HAKARI）不作为这次的胜负。那些数对不齐池化、量化和「QQ 里一句短话」，旧调研已经写过。
