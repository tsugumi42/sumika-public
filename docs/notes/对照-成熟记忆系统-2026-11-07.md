# 对照：成熟的单 / 多代理记忆系统（2026-11-07）

> 起因：主人 2026-11-07 问"感觉还是蛮严格的，别的很成熟的单/多Agent共用记忆系统设计是怎么样的？"。

> 挂在：待办"记忆 v2 接下来"一带（建议的放宽项要主人定）。

## 汇总
## 结论先说

业界主流的记忆系统（Mem0、Zep/Graphiti、Letta、LangMem、ChatGPT、Claude）大多不记"这句话是谁说的、在哪说的、能不能让这群人知道"。它们的"共享"基本是过滤器分区，不是权限控制。Sumika 的严格主要在两处：**写入时**（第三方的话不直接当事实）和**说出去之前**（发送守卫）。召回侧已经在 ADR-242 放开，所以你感觉"很严格"，多半来自这两段。

## 三、哪些严格有必要，哪些可以放宽

**有必要（这些是我的判断，依据是你的场景）**
- Sumika 的 QQ 群有陌生人，可以直接写入。业界没有成熟做法可借，但 MINJA、SMSR 等论文（只读摘要，数字未核实）都在讲记忆投毒，风险是真的。第三方候选加多次门槛有道理。
- 召回不分场合后，发送守卫是唯一防止主人私事漏进群里的一道。业界没有替代品，必要。
- 取代保护：Mem0 的 issue #4956、#7535 说明 ADD-only 会留下互相矛盾的记忆，Sumika 反过来保护主人的话，方向是对的。

**可以放宽（以下是我的建议，需要主人定）**
1. 低风险的 fact、preference 从 3 次放宽到 2 次，但仍要求至少 1 次是本人说的；promise、boundary 保持现状。主人在 ADR-228 说过"尽可能少让人去审"，这条和那句话一致。
2. 待确认的确认交给聊天里直接问一句，不做人工审核页。主人 ADR-228 里已经说过这个方向。
3. 后台整理先只在主人私聊开，群聊继续关，等 W6b 验收后再看。
4. 把"无痕也可能进导出"写进导出说明，参考 Claude 团队版的做法。

**不必借**：Character.AI 的 15 条钉住、A-MEM 自动回写旧笔记（一句陌生人的话可能改掉主人的记忆）、Generative Agents 的"越常被问越牢"。Graphiti 的全 group 失效候选有 #1728 的误伤问题，Sumika 已经限定同一主体，保持现状。

**注意**：ChatGPT 和 Character.AI 的官方页面没取到；论文只读了摘要，数字都是作者自报；Mem0 Platform 是闭源的。要定规格前，应先打开这几份原文核对。

## 结论先说（修正后）

1. 两个系统的"共享"都是过滤器分区，不是 ACL。Mem0 用 user_id / agent_id / run_id / app_id 过滤，Graphiti 用 group_id。两边的 OSS 源码里没有鉴权模块。报告这一点仍然成立（本轮没有重做整棵树的检索，只核对了 Graphiti 的 `group_ids` 是唯一过滤手段，见下文）。
2. 更新冲突的处理方向相反：Mem0 v3 OSS 是 ADD-only，矛盾事实并存（[文档] migration 第 16、38 行：`add()` 只返回 ADD；[源码] `ADDITIVE_EXTRACTION_PROMPT` 在 prompts.py 第 468 行起）。Graphiti 用双时态边，旧边标记失效但保留，失效由 LLM 从候选边里挑出来，再由时间规则决定是否真的失效。
3. 报告里有三处需要改正：Graphiti 的失效候选边是全 group 的混合检索结果（报告没写，而这正是 #1728 的根因）；Mem0 的 linked_memory_ids 在检索时会参与实体加分（报告只写了"排序"）；Mem0 论文的 0.200s / 0.657s 是**搜索阶段**的 p95，不是端到端延迟。

### 过滤的陷阱（修正）

- 报告写"AND 同时要求 user_id 和 agent_id 的查询，对 add 默认产生的记录永远返回空"，说过头了。[文档] entity-scoped-memory.mdx 第 45–47 行的原话是：只带 user_id="alice" 的记录，用 `AND [user_id=alice, agent_id=bot]` 查询，结果为空，因为那条记录的 agent_id 是 null，而查询要的是 agent_id="bot"。也就是说，**只带单一归属的记录匹配不到**，而不是所有记录都匹配不到。
- 同一文档第 43 行：只传 `{"user_id": "alice"}` 时，不要求其他字段为 null，带了 agent_id 的记录也会返回。这一条报告没有写。

## 三、对 Sumika 的启发（修正后）

**最值得借的**

1. 溯源：每条事实带来源消息 ID、说话人（ActorKind + ActorID，不靠名字）、场合和可见范围。Graphiti 的 `episodes` 列表和 Mem0 的 `attributed_to` 都是这个方向，但两边都只记到说话人角色，没有记场合。Graphiti 去重时复用旧边并合并 episode 溯源，这一点可以借。
2. 双时态的"失效而不删除"：Sumika 里"住址、工作、关系状态"这类现在的情况适合用 valid / invalid 语义，而不是 ADD-only。Mem0 的 #4956、#5867、#7535 正是 ADD-only 加上无时间排序的代价。
3. 过期隐藏：Mem0 的 `expiration_date` 做法（UTC、含当天、隐藏不删、解析失败视为未过期）可以直接借。

**不适合直接借的**

1. Graphiti 的失效判断是"全 group 混合检索出候选 + LLM 下标判矛盾 + 时间规则落地"。候选面太大，#1728 已经显示会误伤。Sumika 如果借，应该把候选限定在同一主体、同一关系槽位（比如"住址"只能有一个），新事实必须带证据来源，旧事实不由模型直接失效，只能标记为"待确认"。
2. Mem0 的 ADD-only 会留下互相矛盾的记忆，检索又没有时间因子（#7535）。`linked_memory_ids` 只是排序加分，不是状态转换。Sumika 需要显式的 supersede 路径，而不是靠提示词让模型"顺便关联"。
3. 两个系统都没有 per-audience 可见性和 ACL。"主人能看到、群里不能看到"要在查询层按场合强制过滤，不能依赖提示词。Mem0 的 AND 陷阱（只带单一归属的记录匹配不到，见上）说明过滤逻辑本身容易出错，需要按场合组合写测试。
4. 第三方转述（"某人说 X"）两个系统都没有单独的可信度分级，只按说话人角色或名字归属。Sumika 的"第三方断言降级、需要主人确认"规则是两边都没有的，需要自己设计。

## 三、LangGraph / LangMem（0.0.30，commit）

LangMem 建在 LangGraph 的 BaseStore（带命名空间的键值存储）之上，自己不存数据，也不做向量化，向量化由底层 store 的 index 配置提供（`extraction.py` 示例 [源码]）。

## 五、最值得 Sumika 借的 / 不适合 Sumika 的

值得借：Letta V2 的机械护栏。字数和深度上限、只读文件（按 HEAD 比内容、路径、模式）、提交前只拦新增违规、git 历史当撤销记录，都是不靠 LLM 也能守住的边界，并且有测试佐证。LangMem 的 `actions_permitted`（可以只增不删）和 Profile 形态（单文档，适合人设和用户偏好这类"只要最新状态"的数据）也值得参考。V1 的 block description（告诉 agent 这块怎么用）可以搬。

不适合：由 LLM 一锤定音的写入路径，加上没有说话人和来源字段的存储。这两个设计都没法表达"这句话是主人说的还是别人转述的"，也没法按人做可见性，而 Sumika 的多角色、多场合（本地私聊、本地群聊、QQ 私聊、QQ 群）正需要这些。Letta V2 的共享仓库冲突修复（#4832）还没做完，作者自己也承认多人写入时策略要更保守，这和 Sumika 群聊里多人触发写入的情况一样，不能照搬。

### 六、和 Sumika 的对照

Sumika 的结构是：每个角色一个记忆库，另有共享的主人池，聊天渠道分本地和 QQ。

- **项目隔离 ≈ 角色隔离**。Claude 的"项目记忆 + 可选账号记忆"双层开关，对应 Sumika 的"角色自己的库 + 主人池"。Claude 默认读账号记忆，但项目页可以关掉。这个"可以关掉"的开关值得借鉴。
- **敏感话题默认关闭，需要用户自己打开（opt-in），组织开启记忆也不会自动开启敏感话题**。这比"默认全存"保守，和 Sumika "默认收紧"的原则一致。
- **删除记忆不删来源聊天**（ChatGPT、Claude 都是这样）。Sumika 如果做"忘掉某件事"，要说明原始聊天记录还在，只删记忆条目。
- **管理员看不到成员记忆**（Claude 团队版的明确规则）。对应 Sumika 的问题：主人能不能看角色记住的关于群友、QQ 好友的内容。Claude 的答案是"不能"，Sumika 应该先定同样的规则，再做界面。
- **无痕聊天**：不读不写。但 Claude 团队版的无痕聊天仍会进导出并保留 30 天，这是原报告漏掉的点：Sumika 如果做"不留痕"，要写清它在数据导出和备份里怎么处理。
- **Memory tool 的文件式做法**：所有隔离和权限都在应用里，handler 要做路径校验。Sumika 的结构化数据库比它更强，不用照搬文件式。
- **Graphiti 的"失效而不删除"**：对"角色以前说过的事被后来推翻"的情况，比直接覆盖更适合 Sumika，可以保留历史、可以回答"以前是什么"。

**最值得借的**：Claude 的"按项目分、可以关掉账号记忆、敏感话题默认关并需要主动打开、删除记忆不删来源"这几条产品规则；ChatGPT 的"回复下方可展开看用了哪些来源"，可以对应 Sumika 的"这句话是从哪条记忆来的"；Graphiti 的"失效而不删除、保留时间线"。

**不适合的**：Claude API 的"单个文件 + 模型自己整理"，Sumika 已经有结构化库和证据字段，换成文件式会丢掉可查询性和权限控制。Character.AI 的"每角色 400 字符手写框"和"钉 15 条"，对长期陪伴明显不够，不要借。

**缺口**：ChatGPT 和 Character.AI 的官方细节没有取到，自动提取的模型、条数上限、召回算法、组织层面的共享规则本报告都没有依据。要定规格，需要先从官方帮助中心复核（可以用浏览器打开）。MINJA 等论文的数字要读原文结果表后才能引用。

### 6. 2025～2026 年的多 Agent / 多用户协作记忆

**Collaborative Memory（arXiv 2505.18279，2025-05-23）** [论文·摘要]
- 私有记忆（只属于产生它的用户）和共享记忆（用户选择分享）两层 [论文 摘要]。
- 权限用用户、agent、资源三者的二部图表示，不对称，并随时间变化 [论文 摘要]。
- 读策略按当前权限过滤、变换；写策略决定保留、共享或做上下文变换，两者都可依赖系统、agent、用户级信息 [论文 摘要]。
- 每条记忆带不可变的来源属性：贡献的 agent、访问的资源、时间戳，用于事后检查权限 [论文 摘要]。
- 摘要宣称 "provable adherence" 和 "full auditability" [论文 摘要]，但没有给证明过程。
- 摘要页没有实验数字，也没有局限章节 [论文 摘要页]。HTML 或 PDF 版本可能有更多内容，本次未读。

**AIM（arXiv 2609.12320，2026-09-11 提交）** [论文·摘要]
- 信息动态分为私有（只属于一个用户、对他人隐藏）和公开（所有用户可见）[论文 摘要]。
- 权限在检索索引层强制执行，私有记忆只能被主人检索到 [论文 摘要]。
- MUMBench：四个领域的多用户数据集，测检索、新建、更新、删除 [论文 摘要]。
- 三次独立运行的结果：可见性分类准确率 96.0%，严格操作准确率 58.8%，状态感知操作准确率 70.5% [论文 摘要]。
- 摘要没有定义"严格"和"状态感知"操作准确率 [论文 摘要]，需要看正文才能确认计算口径。
- [推断] 分类的 96% 与操作的 59%～71% 形成对比，说明写入和更新的正确率远低于分类，这和 Sumika 担心写入侧出错是同一件事。

**Governed Shared Memory（arXiv 2606.24535，2026-06-23 提交）** [论文·摘要]
- 摘要列出四个原语：范围化检索、时间性取代（temporal supersession）、来源追踪、受策略约束的传播 [论文 摘要]。原报告写的"租户、子租户、到 agent 级"的 scope 层级，摘要没有描述，[未核实]。
- 写入路径：同步的近重复门在写入时运行，异步的矛盾检测器在其后评估矛盾 [论文 摘要]。论文报告了流水线顺序的问题：门可能在检测器看到之前就拒掉矛盾写入 [论文 摘要]。
- 来源结果：100% 的四层派生链被正确还原，并能对应正确的写入者身份 [论文 摘要]。原报告写"四层派生链全部还原"，措辞可以更精确，即"四层深度的派生链"。

### 对 Sumika 的启示

**最值得借的**：
1. Collaborative Memory 和 AIM 的思路：权限按用户、agent、资源（或用户、听众、场合）的关系表示，读策略和写策略分开，并在每条记忆上记录不可变的来源属性（谁说的、在哪说的、何时说的），便于事后检查。这和 Sumika 的 ActorKind、ActorID、场合四格表是同类设计。
2. Governed Shared Memory 的写入先过近重复门、矛盾写入交给异步检测，以及用"时间性取代"代替直接覆盖。这比 A-MEM 的"回头改旧笔记"更适合 Sumika 的改正流程。注意其中的流水线顺序问题：Sumika 不应让确定性的去重门直接吞掉矛盾写入，而应先记下它。
3. CrewAI 的 source、private 标记与 include_private 管理员路径，是工程上最直接的参考，接口形态可以借鉴。

**不适合 Sumika 的**：
1. A-MEM 的自动回写旧笔记：一句陌生人的话可能改写主人的记忆，和"默认收紧、兜底只能收紧"冲突。
2. Generative Agents 的检索即刷新：常被问到的事会越来越牢，和"只有主人重提才强化"相反。
3. 依赖 LLM 判断去重、合并、矛盾的做法（CrewAI 的 consolidation、Governed 的矛盾检测器）：结果不可复现。AIM 的操作准确率 58.8%～70.5% 说明这一点。Sumika 的写入侧应以确定性规则兜底，LLM 只提供候选判断。
