## 一、先说结论（只讲别家）

1. **没有一个成熟项目只靠一层。** 数量上，逻辑 / 组件测试占绝大多数，端到端是零头，视觉回归的基准图数量在"几百张"量级（Element 808 张，egui 约 257 张，Slint 326 张）。
2. **视觉回归的共同做法：固定环境、固定字体、只在一个平台生成基准、更新要走专门入口、更新结果要有人看图。** 做得最严的是 Element（只许 Docker 内生成）、egui（基准只能从 CI 产物接收、不许在 main 上更新）、Flutter（本地更新不影响云端基准，要有权限的人在 Gold 上点通过）。
3. **阈值和渲染路径强相关**：浏览器、GPU 环境都带容差（Playwright 0.2、Zed 99%、Roborazzi 1%、Compose MSSIM 0.98）；进程内软件渲染的（egui 默认 `max_failed_pixels = 0`、Iced 逐字节、Slint 自带字体并强制按 Linux 比、Flutter 本地比较器无容差）基本是零容差。
4. **"过程中的问题"（闪、跳、同步）大多不靠截图，靠虚拟时钟加几何断言**：Flutter 的 `pump(Duration)`、Compose 的 `MainTestClock`、Zed 的 `advance_clock`、Slint 的 `mock_elapsed_time`、egui 的 `step_dt`，再配 Chromium 的布局偏移算法、VS Code 的"三次截图哈希全等"、Telegram Desktop 的"按时间点取帧"和"窗口覆盖判定"。
5. **不稳定的治法也高度一致**：虚拟时间代替睡眠、关动画、固定随机内容（头像颜色、时间戳）、把鼠标停到角落、等到"两次相邻截图相同"再比、失败重试只放在端到端层。

## 三、第二层：单个组件放进真实渲染环境

这一层有两种做法：浏览器里渲染（Storybook、Vitest 浏览器模式、VS Code 的 Component Explorer），和各 UI 框架自带的"无窗口渲染"（Flutter、egui、Slint、Iced、Android 的 Paparazzi / Roborazzi、iOS 的 SnapshotTesting、Zed）。

### 3.1 浏览器里的组件

**Element 的共享组件库**（`packages/shared-components`）：Storybook 加 `@storybook/addon-vitest` 和 `storybook-addon-vis`，浏览器是 Playwright 的 Chromium。
- 112 个 `*.stories.tsx`，基准图 480 张放在 `packages/shared-components/__vis__/linux/`（进 git）。`[读码]` 目录计数。
- `storybookVis({ failureThreshold: 3, snapshotRootDir: ({ci, platform}) => '__vis__/' + (ci ? 'linux' : platform) })`：允许 3 个像素的差；CI 里一律写成 `linux`，因为浏览器跑在 Docker 里。`[读码]` `packages/shared-components/vitest.config.ts:77-82`。
- `parkPointer`：每个故事渲染前把鼠标移到视口右下角，免得某个元素碰巧被悬停。`[读码]` 同文件 `:42-46`。
- 工具类故事要打 `skip-test` 标签，不跑成视觉测试。`[读码]` `packages/shared-components/README.md:330`。
- 更新基准：`pnpm test:storybook:update`，它调用 `playwright-screenshots` 在 Docker 里重跑。`[读码]` `project.json:47-53`。

**VS Code 的 Component Explorer**（`test/componentFixtures/`）：
- 每个"夹具"是一个组件加一种状态，夹具名末尾带主题（`Light`、`Dark`，部分场景还有两种高对比度，见 `screenshotStability.spec.ts:46-49`）。CI 里只渲染以 `/Light$` 结尾的夹具。`[读码]` `.github/workflows/component-fixtures.yml:172`。
- **基准图不进 git。** git 里提交的是 `test/componentFixtures/blocks-ci-screenshots.md`：77 条记录，每条是夹具名加一个按图片 sha256 命名的外链。CI 重新生成这份 md，和提交的版本逐字比较，不一致就失败并给出补丁。图片上传到一个外部服务。`[读码]` `blocks-ci-screenshots.md`（77 个 `####` 标题）；`component-fixtures.yml:211-232、254-300`。
- 本地比对"改动前后"：`component-explorer-diff.json` 声明两个会话，`current` 和 `baseline`，后者从 `HEAD` 开一个 worktree 单独构建。也就是说基准是"同一台机器上同一个环境里的改动前版本"，不是存起来的老图。`[读码]` `component-explorer-diff.json:1-30`。
- PR 里"改动前"的提交点取和目标分支的 merge-base（浅克隆 150 层，找不到就告警并跳过），push 事件取父提交。`[读码]` `component-fixtures.yml:241-260`（只读到确定基准提交这一步，后面怎么用它没读完）。

**Vitest 浏览器模式的视觉回归**（官方文档）：
- 内置 `pixelmatch`；文档建议把视觉测试单独放一个 project，文件名 `*.vrt.test.ts`，更新用 `vitest --project vrt --update`，更新后"提交前要看图"。基准文件名带浏览器和平台（`test-name-firefox-linux.png`）。`[推断]` `docs/guide/browser/visual-regression-testing.md:77、153-174`。
- 阈值：给出的示例是 `threshold: 0.2`、`allowedMismatchedPixelRatio: 0.01`，并写明"Vitest 没有默认容差，取决于你的内容和环境"，建议用比例而不是绝对像素数；同时给了两个上限时取更严的。文字多的区域可以把比例调到 0.1。`[推断]` 同文件 `:239-260、420-426、447-461`。
- 动画：Playwright provider 默认把 `animations` 设成 `disabled`；还建议再用 CSS 把 `animation-duration`、`transition` 清零。`[推断]` 同文件 `:393-410`。
- 字体：用 Web 字体并 `await document.fonts.ready`，或者共享同一套环境（Docker / 自托管 runner / 在 CI 里生成基准）。`[推断]` 同文件 `:434-461、480-481`。基准多了建议用 Git LFS（`:428`）。

**Storybook + Chromatic**（官方文档，Chromatic 本身闭源）：第一次构建建立基准；开发者在 Storybook 里本地"接受"变更，推送后同步到云端，CI 里自动接受，不用评审两次；PR 上有"UI Tests"检查。`[推断]` `docs/writing-tests/visual-testing.mdx:8-10、46、62-78、93`。

- 开发主要在 Linux 上做，靠"Linux 和 Fuchsia 行为几乎一致"（`docs/testing/web_tests.md:91-92`）。`[读码]`

### 3.3 这一层不稳定怎么治
- **用专用测试字体或自带字体**：Flutter 的 `FlutterTest`、Chromium 的 Ahem 与 `test_fonts`、Slint 的 Noto 四文件。`[读码/推断]`

### 4.1 不稳定怎么治（这一层）

## 六、过程和时序问题怎么测

单张静态截图抓不到"闪、跳、飞"。成熟项目的办法大致六类：

### 6.1 虚拟时钟，按点取样（Flutter、Zed、Slint、egui、Compose、Telegram）

- **Flutter**：`pump(Duration)` 推进假时间；`pumpAndSettle(duration = 100ms, timeout = 10 分钟)` 反复推进直到没有待排的帧；`pumpFrames(widget, maxDuration, interval = 16.683ms)` 按 59.94 FPS 一帧帧推。`[读码]` `packages/flutter_test/lib/src/widget_tester.dart:654、695-727、734-738`；时间来自 `FakeAsync.elapse`（`binding.dart:2462`）。
- **Compose `MainTestClock`**：`autoAdvance = false` 后手动推进。注释里写了几个会让人栽跟头的语义：动画先拿到帧时间、再重组，所以**状态改变后的第一帧动画还没开始**（16 ms 步长下，要再推一帧动画才拿到 `t=0`）；`advanceTimeBy(160)` 产生 **10 帧**而不是 1 帧，布局和测量每帧都跑，**绘制不会在帧之间发生**。`[读码]` `compose/ui/ui-test/.../MainTestClock.kt:43-66、100-112`。
- **Telegram `RunClockedFrames`**：在一次同步动作后，按"动作之后过了多少毫秒"这组严格递增的时间点各取一帧；动作之后主线程每 1 ms 睡一次直到该时间点，处理排队的调用，再让动画管理器更新**一次**并渲染；每一帧报告它实际到达的时间区间 `[tick - actionFinished, tick - actionStarted]`；时间点落到动画结束之后就是"不适用"，不算失败；自带的自测用 200 ms 线性动画取 25%、50%、75%、125%，要求像素读出的值落在对应位置的 1.5 设备像素以内、且三个值严格递增。其文档记着它的来历：某次运行里，**十二个 200 ms 的过渡在"下一个 50 ms 的 runner 刻度"取样时已经结束了**。`[读码]` `Telegram/SourceFiles/test/docs/helpers/test_animation_clock.md`（"Clocked frame capture"一节）。
- **Zed**：`TestDispatcher` 按种子确定地调度任务，`run_until_parked()` 跑到没有可运行的任务，`advance_clock(d)` 推进时间；`allow_parking`/`forbid_parking` 控制"没任务了能不能睡眠等外部事件"。`[读码]` `crates/gpui/src/executor.rs:209-263`。
- **egui**：`Harness::step()` 每步用固定的 `step_dt`；`run()` 一直跑到界面稳定，超过 `max_steps` 报 `ExceededMaxStepsError`，并**继续多跑 `diagnostic_max_steps`（默认 100）步，告诉你到底需要多少步才稳定**。`[读码]` `crates/egui_kittest/src/lib.rs:75-100、371-384、457-475`；默认值见 README。
- **Slint**：`mock_elapsed_time(ms)`。`[读码]`

### 6.2 "准备好之后画面不变"（VS Code）

`expectStableScreenshot`：取三张图并比 sha256：① 夹具刚渲染好；② 再等 750 ms（覆盖滚动条的空闲超时，"用这个超时代替随便等一会儿来判断就绪"）；③ 先渲染另一个夹具再渲染回来（卸载、重新挂载）。三张哈希必须全相等，失败时把三张图都作为附件。每个主题、每个场景都跑。这正是"骨架屏闪""切换跳一帧"需要的断言形状，而且**不需要基准图**。`[读码]` `test/componentFixtures/playwright/tests/screenshotStability.spec.ts:122-142`。

同一文件里，滚动锚定的场景（流式输出时标题可见 / 不可见、已完成时可见 / 不可见、思考过程展开）在比图之前先查几何：标题元素的 `getBoundingClientRect` 是否在视口之上（`aboveViewport`）、是否完整可见（`fullyVisible`，要排除吸顶容器的阴影区域）、布局测量与视口一致、"额外折叠留白"为 0 像素。`[读码]` 同文件 `:144-190`。另有 `chatResizeObserver.spec.ts`、`resizeObserverContext.spec.ts`、`sessionsListTwistie.spec.ts` 等专门的布局测试（文件名在目录里，没逐个读）。

### 6.3 把"布局跳动"算成一个分数（Chromium）

`LayoutShiftTracker`：每帧对每个移动过的元素，如果起点或终点的位移超过 `kMovementThreshold = 3.0` CSS 像素才算；分数 = **影响比例 × 距离比例**，影响比例 = 移动区域的并集面积 / 视口面积，距离比例 = 该帧最大位移 / 视口较长边（不超过 1）；用户输入之后 500 ms（`kTimerDelay`）内的移动不计。`[读码]` `third_party/blink/renderer/core/layout/layout_shift_tracker.cc:47-48、549-558、784`。单元测试里有"输入之后忽略""SVG 忽略""子框架加权"等例子（`layout_shift_tracker_test.cc:44-55、133-183`）；WPT 的 `layout-instability/` 有几十个按场景命名的网页测试（只数了文件名）。

### 6.4 "覆盖"而不是"条数"，并以处理时刻为原点（Telegram）

`motion_window.py` 判断一段带时间的运动（静止、按下后移动、松开后滑行）：每个声明的窗口要覆盖到它声明的状态和阶段，每条记录各自的耗时在预算内，声明的运动规律在**处理程序时刻**为原点的数据上成立；**绝不按"最少多少条记录"判定**。它把原因写进了文档开头：一次真实运行里，按"至少 20 条"的门槛判了一段自然结束的 19 条滑行为失败；另一处，因为记录的指针时间戳早于处理程序真正被调用的时间，精确的 x 曲线检查留下 1.812 px 的残差（界限 1.5 px），一个记录的 79 ms 速度跨度只要端点移 1 ms 就变成 80 ms。`[读码]` `.agents/shared/evidence/motion-window.md:1-30`。同一套里还有 `test_paint_stream`：记录一次绘制的全部绘图指令，在优化构建里重放来量真实绘制耗时（因为调试构建里量到的不是绘制成本），要求"一个完整的不透明绘制者"。`[读码]` `test/docs/helpers/test_paint_stream.md`。

**今天在本机量到的三件事**（临时试验程序放在会话草稿目录里，没进仓库）：

1. `[实测]` 同一个场景（一列文字、一个圆角块，125% 缩放）在三个独立进程里 `sha256(Image().Pix)` 完全相同，注册文渊圆体的"小字体"和不注册各自也稳定。→ 本机同一环境下，零容差有希望。
2. 同一行加上中文，用只有 ASCII 的小字体和用系统字体，出图哈希不同 `[实测]`；中文在小字体里没有字形，缺字会回退到系统字体 `[读码]`（`dwrite_windows.go:22-36` 的说明），从出图的字形外观看确实是回退 `[推断]`；`Texts()` 看不出回退。→ 基准里不能混入字体里没有的字。
3. `[实测]` 单用 `Advance(16ms)`，第一步没有帧（第一帧在 16.67 ms），之后采样点与刷新节拍错开；改成 `Advance(time.Second/60)`，**每一步恰好一帧**；`Advance` 之后不需要再调 `Frame()`。→ 现在 `trajectory` 是 `Advance(16ms)` 后紧跟 `Frame()`，采样点上有帧，但那是 `Frame()` 强制出的帧，不在刷新节拍上；去掉 `Frame()` 就会丢第一帧。应改成按刷新周期步进。另外 `Access("标签").Bounds` 能在每一帧读到带 `Label` 的盒子的当前宽度（250 → 逐帧 50、95.9、134.3……，208 ms 到位），**不需要读应用内部状态**。

**还没量的**（方案里要先量）：换一台机器、Windows 更新后、ClearType 开关不同、`Image()` 哈希会不会变（DirectWrite 用系统的 ClearType 和 gamma 设置，见 `dwrite_windows.go:22-36`）；整窗（2048×1030、1.25 倍）一次出图要多久；Tester 的无障碍树是否包含无标签的装饰盒子。

### 9.3 基准图：存放、更新、审

1. **位置**：`native/testdata/ui-golden/<层>/<名字>@<主题>-<缩放>.png`，加一个 `ENV.json` 记录指纹：mygo 版本、Go 版本、Windows 版本号、测试字体文件的 sha256、字体平滑设置（ClearType 开关和类型，从系统读，`[推断]`可从注册表 `FontSmoothing`、`FontSmoothingType` 读）。**指纹对不上时，测试跳过并说明（不是失败）**，理由同 Zed（只在一个平台）、Slint（强制参考系统）。
2. **先不用 Git LFS**：基准图是小图（组件图预计几 KB 到几十 KB，整窗预计几百 KB，`[推断]`未量），先走普通 git；设体积预算（基准总量超过 50 MB 就迁 LFS，写进规格）；提交钩子对单张超 150 KB 的非整窗图报警。egui、Paparazzi、Vitest 都建议 LFS，但它们的基准多到数百上千张，而且有云端 CI。
3. **比较的是解码后的像素，不是 PNG 文件字节**：Go 升级可能改 PNG 编码字节，不改像素（Iced 比的是解码后的 RGBA，Flutter 同理）。
4. **只有三个动作能碰基准**，都在专门入口里，普通 `go test` 永远只读：
   - 比较失败：把 `.new.png`、`.diff.png`、`.old.png` 和一张"前 | 后 | 差"接触表写到**主工作区** `data/dev/test-runs/ui-diff/<运行>/`（AGENTS 规定整套输出存那里；worktree 收掉后证据会消失，LESSONS 第一条），并打印像素数、最大通道差、差异外框。
   - 接受：`bun scripts/ui-golden.ts accept <名字模式>` 才把候选复制进 `testdata`；默认只接受**失败的**，对应 egui 的"只更新失败的"档；没有"全部强制"档，批量刷新要走第 5 条。
   - **缺基准图一律失败**（修 Iced 那个坑），要新增必须显式 `accept --new`。
5. **防止随手批量更新**：①提交钩子统计 `testdata/ui-golden` 里改动的 PNG 数，超过 10 张时要求提交说明里有 `批量基准：原因`；②每次提交说明列出改动基准的名字和原因（沿用提交说明规则：标题短、正文三到八行，所以名字太多时写"见 `ui-golden/CHANGES.md` 对应条目"）；③环境指纹变了（Windows 更新、换字体）才允许"全量重生"，且单独一个提交、附接触表；④合并前审基准变化用接触表看图，不看 PNG 文件列表；⑤每日整套里查**孤儿基准**（磁盘有图、测试没登记），对应 Element 的 `stale-screenshot-reporter`。

### 9.4 字体与 Windows 渲染差异怎么固定

事实：Windows 上 mygo 文字走 DirectWrite，字形随**系统的 ClearType、gamma、对比度设置**变化，缺字时回退**系统字体**（`dwrite_windows.go:22-36`）。所以"软件渲染"不等于"跨机器逐字节相同"。

1. **测试字体**：做一个"测试专用子集"，覆盖夹具里出现的全部字符（ASCII + 夹具里用到的中文，几百字），保留 `fvar` 与布局特性（`pyftsubset --layout-features='*'`），**改掉内部家族名**（SIL OFL：声明了保留字体名的字体，改动后不能再用原名，`docs/决策记录.md:195` 已写）。现有 `WenYuanTiny.ttf` 没改名，也没带许可证文件，这是个独立问题，先记下，不在本笔记里改。注册时仍用现在的家族名 `WY Rounded`，界面代码不用改。
2. **字体覆盖检查**：`uitest` 对 `Texts()` 里每一个字符查测试字体的 cmap（`golang.org/x/image/font/sfnt`，mygo 已依赖），有缺字就让夹具失败。防止系统字体回退悄悄进基准（实测第 2 条）。
3. **字体平滑**：指纹里记录它，不一致就跳过。需要在第二台机器、开关 ClearType 各量一次，看差多少像素，再决定要不要像 egui 那样按环境给阈值。
4. **要两条路并存**：用测试字体画的整图基准（看真实外观），和 Ahem 式"字符都是方块"的**布局基准**（只看盒子位置）。后者对字体渲染差异几乎免疫，是 Chromium、Flutter 的做法；是否需要，等量完第 3 条再定，`[推断]`。
5. **表情**：twemoji 现在也从外部 Bun 仓库路径读（`chatui.EmojiDir`），需要把画廊用到的几张放进 `testdata`，或夹具里不用表情。
6. **外部路径不许再进测试**：画廊只读 `testdata`，读不到就失败，不回退到系统字体（LESSONS：缺失就报错并列出可用项，不拿别的兜底）。

### 9.5 阈值初值

| 项 | 初值 | 依据 |
|---|---|---|
| L2、L3 基准图 | 单像素差 0、允许失败像素 0（零容差） | 软件渲染同环境三进程相同（实测）；egui 默认 0 个失败像素、Iced、Flutter 本地、Chromium 都是零容差；带容差的都是浏览器或 GPU（第五节 5.3） |
| 环境指纹不一致 | 跳过，不比较 | 同 Zed、Slint |
| 若第二台机器 / ClearType 不同导致差异 | 先看实测的差异像素数和最大通道差，再按 egui 的做法分环境配（`OsThreshold`）；**不要**直接抄 Playwright 的 0.2 | 先量再放宽 |
| L1 几何不变量 | 相等类 0.01 DIP；"不应该动"的位移上限 0.5 DIP | mygo 布局是浮点 DIP；Telegram 读像素时用 1.5 设备像素 |
| L4 运动 | 采样一帧一点；"飞走"阈值：相邻帧位移超过该元素运动曲线预期的 2 倍且超过 8 DIP | `[推断]` 初值，上线后按真实数据调 |
| 布局偏移 | 移动阈值 3 DIP；忽略输入后 500 ms；分数上限 0（除声明了动画的元素） | 照 Chromium `kMovementThreshold = 3.0`、`kTimerDelay = 500 ms` |
| 稳定性检查（三哈希） | 零容差 | 同 VS Code |

### 9.6 逐帧稳定性工具：API 草案（`native/internal/uitest/`）

设计原则：**长在现有的 `trajectory` 上，不另起炉灶**；不读应用内部状态，只读 Tester 能看到的东西（`Access().Bounds`、`Find`、`Image`）；元素用稳定的 `Label` 找（对应 Grafana 的 `data-testid`、egui 的无障碍标签），所以族组件要给选中块、悬停块、轨道等装饰盒子设稳定的 `Label`。需要先验证给装饰盒子设 `Label` 是否会让读屏多念（没验证）。

```go
package uitest

// 一帧的时长：按刷新周期，不是 16ms（实测 16ms 的采样点和帧边界错开）。
const Frame60 = time.Second / 60

// Record 在 tt 上推进 d 的虚拟时间，每步恰好一帧，记下关注的元素和（可选）像素。
// 不调用 tt.Frame()：Advance 已经按到期的帧渲染。
func Record(tt *ui.Tester, d time.Duration, opts ...Opt) *Trace

type Opt func(*cfg)
func Watch(labels ...string) Opt          // 每帧读 Access(label).Bounds，缺了记"不存在"
func Pixels(r ui.Rect, every int) Opt     // 每 every 帧取区域哈希；失败时用于接触表
func Phase(name string, from, to time.Duration) Opt // 声明阶段，用于覆盖判定
func Animated(labels ...string) Opt       // 允许这些元素在偏移分数里移动

// 断言（失败信息带帧号、时间、元素、两帧的数值；失败时自动写接触表到 data/dev/test-runs）
func (tr *Trace) Inside(inner, outer string, slack float32)       // 每帧 inner 在 outer 内：抓悬停框溢出、选中块飞出轨道
func (tr *Trace) NoJump(label string, maxStep float32)            // 相邻帧位移上限：抓飞走、跳一帧
func (tr *Trace) Follows(follower, anchor string, tol float32)    // 滚动同步：二者位移差恒定
func (tr *Trace) Settles(label string, by time.Duration)          // by 之后不再动
func (tr *Trace) Bounces(label string, from, to float32)          // 把 motion_test.go 的 checkBounce 搬进来
func (tr *Trace) NoFlicker(label string, minShow time.Duration)   // 出现后不到 minShow 就消失 = 失败：抓骨架屏闪
func (tr *Trace) ShiftScore(viewport ui.Rect) float64             // 照 Chromium：Σ(影响比例×距离比例)，3 DIP 阈值，输入后 500ms 豁免
func (tr *Trace) CoversPhases(names ...string)                    // 覆盖判定：每个阶段至少有一个"在动"的采样；按覆盖，不按条数（Telegram）

// 不依赖基准图的稳定性：首帧、Advance(settle) 之后、重建视图之后，三次区域哈希必须全相等（VS Code）。
func StableWhenReady(build func() *ui.Tester, settle time.Duration, region ui.Rect) error

// 基准图
type Golden struct{ Dir string }                                   // 默认 testdata/ui-golden
func (g Golden) Match(t *testing.T, name string, img *image.RGBA, o ...GoldenOpt) // 只读比较；缺基准=失败；写候选和 diff 到主工作区 data/dev
func RequireGlyphs(t *testing.T, tt *ui.Tester)                    // Texts() 里每个字符都在测试字体里
```

场景举例（对应主人报的毛病，只写用法，不写实现）：
- 滚动时选中框飞走：滚动区里放分段控件，`tt.Wheel(...)`，`Record(tt, 600ms, Watch("选中块", "分段轨道"))` → `Inside("选中块", "分段轨道", 0)`、`NoJump("选中块", 8)`。
- 悬停框溢出：`tt.Move(...)` 到每一行，`Inside("悬停块", "列表", 0)`。
- 骨架屏闪：进入加载态 → 数据到达，`Record(...)` → `NoFlicker("骨架", 400*time.Millisecond)`；并加 `StableWhenReady`。
- 切换时布局跳一帧：切标签页，`Record(...)` → `ShiftScore(窗口) == 0`（除 `Animated` 声明的内容）。

### 9.8 和组件收拢（ADR-322）怎么接

盘点里数出 32 族、31 族有多种实现。建议"一族合一"的验收加三项（这是建议，没改 ADR、规格、待办）：
1. 这一族有画廊（L2）：每种状态一张基准，浅 / 深 / 1.0 / 1.25。
2. 这一族有几何不变量（L1）：悬停框、选中块不出界；同族等距；同心圆角（LESSONS 界面第一条）。
3. 涉及动的族有 `Trace` 断言（L4）：F03 分段（选中块）、F11 悬停框、F19 加载（骨架）、F10 列表行（滚动时）、F25 滚动条、F32 折叠。

顺序：先做 L1 + L4 + `uitest` 包（不依赖基准图，不依赖界面稳定），再做 L2（每族合一后立刻有基准，避免在会变的界面上堆基准）；L3 整窗等 `feat/proto-port` 合入后再做。理由：基准图会随迁移大面积变化，现在建基准等于"批量更新"的反面教材（Flutter 文档里"没分类的图合进来让构建变红"）。

### 9.9 最小可做的第一步（供主会话排）

1. `uitest` 包：`Record`、`Watch`、`Inside`、`NoJump`、`Settles`、`StableWhenReady`，用 `cmd/sumika-proto` 现成的分段和开关当第一批用例，顺手把 `motion_test.go` 的 `trajectory` 改成 `Frame60` 步长并去掉 `Frame()`。
2. 先量三件事：第二台机器 / ClearType 开关的哈希差；整窗出图耗时；无标签装饰盒子在无障碍树里的表现。
3. 测试字体：做改名的子集 + 许可证文件，替换 `WenYuanTiny.ttf`。
4. `Golden.Match` 和 `scripts/ui-golden.ts`（接受、接触表、孤儿检查、批量提交门槛）。

### 9.10 没做、不做、风险

- **不做**：云端基准服务、跨平台基准、感知类比较（SSIM、GMSD）、Playwright 或任何网页端工具。
- **风险 1**：Tester 是软件渲染，不覆盖 GPU 路径和真窗口的合成（毛玻璃、窗口材质、输入法），所以 L5 不能省；Tester 的 `Image()` 过了不等于真窗口里不闪。
- **风险 2**：DirectWrite 随系统设置变化；指纹和跳过规则是保护，不是保证。
- **风险 3**：`Advance` 内部按帧渲染但没有逐帧回调，采样靠自己一步一帧推进；如果将来 mygo 改了刷新节拍（比如 `SetRefreshRate`），`Frame60` 要跟着改。
- **风险 4**：给装饰盒子加 `Label` 可能影响读屏，需要查 `RoleNone` 之类的办法。
