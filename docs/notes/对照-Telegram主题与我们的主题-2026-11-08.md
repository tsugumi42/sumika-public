## 结论

1. **键是一一对上的，格式转换没有阻碍。** Telegram 当前的 `colors.palette` 有 586 个颜色键，MewTypeUI 的 614 个颜色键里恰好有这 586 个（行尾注释写着 Telegram 键名和行号），另外 28 个是 MewTypeUI 自己加的派生角色（`quote.*`、`reaction.*`、`selection.background`、`semantic.*`、`link.text`、`quote.codeDarkBackground`），写成 `@别名`。5 个主题文件里每个键都能落进 MewTypeUI 的主题 JSON；格式差别只有别名写法（`键: 另一键;` ↔ `@点号键`）和每套主题里 17～21 个已从当前 palette 移除的旧键（直接丢掉）。`[读码]`
2. **“能存”和“能画”和“能调”是三件事，现在差得很远。** 按 586 个键数：能存 586；旧界面（MewTypeUI 组件）至少读到 246；新界面聊天列（`chatTheme`）只读 17；外观页能单独调的只有 6。数字的算法和下限性质见第三节。`[读码]` 加 `[推断]`（静态扫描，数的是下限）。
3. **新界面（S8 以后会成为默认）读主题文件的范围最小。** 聊天底色、输入区、气泡内部的引用条、选中底、已读勾、服务消息、头像和名字色全部不读主题，用 `chatui.Derive` 和 `AccentOf` 的公式色。公式的中性色相固定是冷灰 250°，主题再暖（喵喵粉的窗口底 #fff8fc），聊天区仍是冷灰（约 #edf1f5，我用 OKLCH 公式换算，`[推断]`）。
4. **公式推色不是没做，是做了一半没接到界面上。** 引擎有（OKLCH 12 阶、`strongOf` 二分保 4.5:1 对比度、`reach` 保图标和文字对比度），但输入是“角色色”不是“全局主题色”；外观页的“强调色”只是把同一个值平铺写进 5 个 MewTypeUI 键，不进公式。详见第四节。
5. **聊天背景图完全不支持。** 5 个主题都带背景图（3 个近似纯色，2 个整张插画）。MewTypeUI 没有这个令牌，并且明确写了“不复制、不使用”；新界面连程序生成的波点光晕也关着。详见第五节。
6. **每套主题是手调出来的，不是公式出来的**：解析后各有 230～270 种不同颜色。所以复杂档不能做成 614 个并排的色块，要按部位分组。喵喵粉和喵喵蓝倒是几乎单一色相（粉 339°～356°、蓝 225°～252°，只有明度、彩度在变），说明简单档的“一个主色铺开”在真实主题里站得住。`[实测]`
7. **顺带发现一处可能的毛病**：新界面所有 `chatui.Host` 都没设 `SelfChar`（`chatmedia.go:229`、`workbench_composer.go:127`、`:152`），凡是取“我的强调色”的地方（我点的表情回应、引用高亮 35% 底、审批卡按钮）都从全 0 的颜色推，会近乎黑色。没有开真窗口看，`[读码]` 加 `[推断]`。

## 二、Telegram 主题本身

### 2.1 文件格式 `[读码]`

- `colors.tdesktop-theme` 是文本，每行 `键: #rrggbb;` 或 `键: #rrggbbaa;`（透明度在最后），或 `键: 另一个键;`（引用）。`//` 开头是注释。`lib_ui.palette` 里还出现 `#ff000088 | attentionButtonFg` 这种带竖线的写法，当前 5 个主题里没有用到。
- 主题包是 zip 改扩展名：里面 `colors.tdesktop-theme`，外加 `background.jpg|png`（不平铺）或 `tiled.jpg|png`（平铺）。文件头注释原话是这么说的。
- 缺的键用内置默认（`lib_ui.palette` 的浅色默认），引用在合并后的表里解析。MewTypeUI 的做法一样（`exceptions.md:15`）。
- 5 个主题里没有用到 `tiled`，都是 `background.jpg`。

### 2.2 palette 的分节和我用的分组

`lib_ui.palette` 只有 16 个注释分节（行号是节标题所在行）：basic 8、widgets 31、custom title bar 98、tray icon 121、layers 128、boxes 134、intro 166、dialogs 179、history 245、overview 478、profile 485、settings 491、mediaview 510、notification 552、calls 555、spellcheck 617。

分节名不能直接当“部位”用：history 一节有 206 个键（占三分之一强），最后的 spellcheck 一节 70 个键实际是钱包标题栏、会员、星币、统计图等杂项；`340-343` 行有一段注释说下面这些键“marked as (adjusted)，会按壁纸平均色的色相饱和度调整”。所以我按键名前缀把 586 个键分成 17 组（分组规则在 `parse_themes.py` 的 `GROUPS`），下表的“5 套”依次是 momotalk、momotalk-dark、wechat、喵喵粉、喵喵蓝，数字是“和 Telegram 默认配色不同的键数”：

要点：

- **momotalk 不是亮暗两套各算各的**：气泡、已读勾、服务消息底等聊天内容的颜色两套相同，变的只有窗口、会话列表、输入区、标题栏、菜单这些外框。外框里“浅色”是白，“深色”是中灰蓝。
- **窗口底会被主色染色**：喵喵粉 #fff8fc、会话底 #fdf5fa，喵喵蓝 #ebf9ff，都是主色相的近白。我们新界面的底色相是固定冷灰，接不上这种做法。
- **每套都有旧键**：momotalk 和 momotalk-dark 各 21 个、wechat 17 个、喵喵粉和喵喵蓝各 19 个键不在当前 palette 里（例如 `outlineButton*`、`historySystem*`、`historyCaption*`、`introErrorFg`、`dialogsForward*`、`reportSpam*`、`msgFileOutBgOver`），是老版本留下的。导入时丢掉并提示个数即可。

## 四、“只给一个主题色，其余按公式推”到底做到哪

**结论：公式引擎做了，入口没做，而且公式的输入不是用户想要的那个“主题色”。**

### 4.1 已经有的公式 `[读码]`

1. `chatui.Derive(Settings)`（`tokens.go:139`）：从 `Text / Radius / Density / Neutral / Dark` 推出全部尺寸和 `Palette`（约 25 个色，`palette()` 在 `:203`）。中性色是 OKLCH 阶梯，色相由 `Neutral` 的冷 250°、中 250°、暖 70° 三档给（`:133`），彩度固定很小（0.002～0.008）。**色相不能由用户的主题色决定**。
2. `Tokens.AccentOf(char OKLCH)`（`:335`，实际推导在 `:353`）：一个“角色色”推出一组阶梯：`Base / Hover / Press / Soft / SoftHover / Line / Text / On / Strong / OnStrong / OnStrongMuted / Glow`。`strongOf`（`:410`）用二分法找“白字和 90% 白次要字都 ≥ 4.5:1 的最亮一档”；`reach`（`:284`）保图标 ≥ 3、文字 ≥ 4.5；危险、成功色也走它。注释写着“主人 11-06：以后换主题色要能按公式自动更新”（`:128`）。**这就是用户说“之前说过”的那套**：设计语言第三节“每个颜色生成一组 12 阶”，规格-界面令牌的“强调深档”一行（含“默认青色解出 #007A7B”），待办“主题色的‘深浅’手动微调”（`待办.md:318`）。
3. MewTypeUI 主题 JSON 的 `@别名`：28 个派生角色靠它联动（`quote.in.background → quote.in.bar` 之类）。这是“改一处联动一片”的唯一机制，但不是算出来的。

### 4.2 覆盖到哪里 `[读码]`

| 地方 | 用不用 `AccentOf` |
|---|---|
| 新界面：发言人名字色、行内图标、过程气泡图标、引用高亮（`parts.go:149`）、表情回应（`reactions.go:83,146`）、审批卡（`approval.go:112`） | 用，输入是发言人的 `character.yml` 的 `color`（`chatview.go:17` 转成 OKLCH）；“我自己”走 `SelfChar`，**正式程序没设** |
| 新界面：气泡底、气泡文字、时间、链接 | 不用，读主题 JSON（`chattheme.go:83-86`） |
| 新界面：输入区 | 不用，读 `ui.Theme` |
| 新界面：会话列表 | 不用，旧列表组件读主题 JSON |
| 原型 `sumika-proto`：会话选中行（`Strong`）、发送键、气泡 | 用 |

### 4.3 外观页有没有“只调一个颜色”的入口 `[读码]`

没有。`appearance.go:58-83` 有三个颜色框：强调色、收到的气泡、发出的气泡。强调色把同一个值写进 `control.primaryBackground`、`…Hover`、`…Pressed`、`control.focus`、`selection.background` 五个键，悬停和按下都不变深浅；它不动 `message.out.background`、`dialogsBgActive` 对应的 `conversation.backgroundActive`、发送键以外的任何东西，也不进 `AccentOf`。所以在新界面里，同一个“强调色”一部分跟（输入区发送键走 `ui.Theme.Accent`）、一部分不跟（名字、表情回应、高亮走 `AccentOf`）。

设置角色页规格里“主题色”（`character.yml` 的 `color`）也还只能看，不能改（规格-设置角色页 2b，待办）。

### 4.4 历史 `[读码]`

- Bun 版（`_external/sumika-bun-wt/backfill-coverage@99438dc` 的 `web/src/ui/appearance.ts:60-69`）的外观只有冷/中/暖三档底色加每个角色一个颜色，同样没有全局主题色；CSS 里 `--hue / --chroma` 是底色相。
- ADR-024、设计语言第三节定了 12 阶思路；ADR-283 第 3 条把 Bun 配色“搬到 mygo”；`chatui` 的公式是这么搬来的。
- 11-06 主人在聊“主题色的深浅微调”时提到“公式加手动调深浅”（待办 `:318`），11-08 又提简单档、复杂档。所以“之前说过但没做”的准确说法是：**公式做在了角色色上，没有人做过“全局主题色→全部令牌”这条线，也没有入口**。

### 4.5 要接起来大概缺什么 `[推断]`

1. 一个“主题色”的输入（全局，或取主人的角色色）。
2. 把 `Derive` 的中性色相改成跟主题色走（现在是写死的三档）。
3. 一个函数：主题色 → 约 40 个常调键的值（`message.*`、`conversation.*`、`compose.*`、`service.*`……），写成 `Definition` 的覆盖，然后照现有 `changeLook` 编译；亮色夜间各出一套。
4. 新界面把聊天底色、输入区、气泡内部、服务消息改成读主题，否则推出来的键没人画。
5. 对比度检查沿用 `reach`、`strongOf` 的做法，低于线只提示。

## 五、聊天背景图现状

| 位置 | 现状 | 出处 |
|---|---|---|
| 设计语言 | 写了“聊天背景（图案 / 图片）”，实色或图案 | `设计语言.md:49` |
| 风格选择（Bun 时代） | 默认“角色色色晕 + 细点”；纯色、图片可选，图片只放内存不保存，模糊 0/12/24/48（默认 24px），能从图里取角色主题色 | `界面-风格选择.md:25` |
| Go 里的实现 | `chatui.Wallpaper`：20 DIP 格波点加三团角色色光晕，程序生成，整张贴图，**没有图片路径** | `chatui/wallpaper.go:15-57` |
| 原型 | 有“聊天背景图案”开关 | `sumika-proto/view.go:741` |
| 正式程序 | `Wallpaper=false`（`chattheme.go:39`），聊天列只涂纯色 `ChatBg`（`workbench_view.go:139`）；旧界面用 `conversation.background` 纯色 | `[读码]` |
| MewTypeUI | 没有壁纸令牌；`exceptions.md:15` 写明“随主题附带的 background.png 不复制、不使用；不实现壁纸色相调整” | `[读码]` |
| Telegram | palette 里 `340-343` 行注释：标 `(adjusted)` 的键，在用户换壁纸时按壁纸平均色的色相饱和度调整（`historyScroll*`、`msgService*`、`msgDate*`、`historyToDown*` 等这一块） | `lib_ui@2e4fcfb ui/colors.palette:340-343` |

**结论：不支持图片，没有令牌，没有渲染路径，也没有导入路径。** 要做的话至少要定：

- 令牌：模式（无 / 纯色 / 图案 / 图片）、图片路径、铺满方式（cover 或平铺）、遮罩或亮度。
- 渲染：聊天列底下铺图，虚拟列表滚动时背景不动；原型里“壁纸是整张贴的，元素的 Clip 只裁子元素，要自己按圆角裁”的坑（`sumika-proto/view.go:803` 附近的注释）要带上。
- 存储：图放数据目录（不进 git，LESSONS 里的 `git check-ignore` 规矩）；Bun 时代定的“只放内存不保存”重启就丢，要不要改要主人定。
- 取色：Telegram 的 `(adjusted)` 键要不要也随图调，是第二档的事。

## 六、对 Sumika 的启发（唯一写对照的地方）

1. **先做 `.tdesktop-theme` → MewTypeUI JSON 的转换**，哪怕不做编辑页：键一一对应、脚本已跑通，主人导出的任何 Telegram 主题可以直接试穿。旧键丢掉并报数，背景图单独处理。
2. **简单档的公式照真实主题归纳**：喵喵粉里主色相一致，窗口底、会话底是 L≈0.98、C≈0.01 的近白；出站气泡 L≈0.95、C≈0.02；强调 L≈0.76、C≈0.13；选中行深一档 L≈0.61、C≈0.19；链接 L≈0.43；正文是同色相的近黑 L≈0.22。这几档和我们 `AccentOf` 的 a3、a9、a11 能对上，可以回放验证：拿 #f18eb7 当输入，看公式出来和这个主题差多少。
3. **复杂档按部位分组，不按键**：5 套主题各有 230～270 种颜色，614 个并排的色块没人调得动。
4. **新界面补读主题的顺序**：聊天底色 → 气泡内部（引用条、选中、勾）→ 服务消息 → 输入区 → 会话选中行 → 头像名字色。通话、会员、统计、钱包不做。
5. **规格和代码对不上的一处要先定**：规格-新界面主线 S5 的表写 `materials.conversation` 填进 `ChatBg`，代码（`chattheme.go:70`）故意没填，原因在注释里（预设里的窗口、会话材质都是白，气泡会和底融在一起）。做简单档时底色由公式出，这个矛盾自然消失；在那之前别按规格表改。

## 七、要问主人的问题（带推荐答案）

1. 简单档里的“主题色”是**全局一个**，还是**每个角色一个**（现在是后者）？推荐：全局一个，默认取主人自己的角色色；角色色继续管群里别人的名字色和他们的气泡淡色。
2. 窗口底色要不要**跟着主题色染色**（喵喵粉 #fff8fc 那样）？推荐：要，做成一个“染色强度”，默认中等；冷、中、暖三档留着当快捷预设。
3. 复杂档**分多细**？推荐：按部位分约 12 组（聊天背景、入站气泡、出站气泡、会话列表、输入区、窗口……），每组先露最常调的约 3～6 个键，其余折叠；614 个键只在导入导出的 JSON 里露。
4. 复杂档和简单档**什么关系**？推荐：简单档先用公式把所有键填好，复杂档在上面逐键覆盖，记下覆盖了哪些键，每个键能“恢复为公式值”；切回简单档时提示“这些键被手改过，要保留还是重算”。
5. 要不要**直接支持导入 `.tdesktop-theme`**（zip，含背景图）？推荐：支持，作为导入主题的一种格式。
6. **聊天背景**先做到哪？推荐：先做纯色加图片（铺满裁剪）加可选模糊，沿用现有的程序生成图案；图存数据目录、重启还在，不沿用“只放内存”。
7. 亮色和夜间是**一个主题色自动出两套**吗？推荐：是，两套各自可覆盖，和现在“亮色夜间分别保存”一致。
8. 新界面里读不到的键，**先补哪批**？推荐：先聊天底色和气泡内部（第 1、2、4、5 项），再输入区和会话选中行；这批不需要等编辑页。
9. 顺带那处可能的毛病（第 7 条结论：`SelfChar` 没设）**要不要先修**？推荐：先修，小改动，修之前在真窗口里看一眼表情回应和审批卡按钮是不是真的发黑。
