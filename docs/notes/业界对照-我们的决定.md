## 怎么看这张表

- **业界叫什么**：先给中文名，再给英文名，方便以后直接搜。
- **出处**：人名、书、标准、公司的设计指南或论文。标了 ✔ 的链接是这次搜索核对过的；没有标记的是凭记忆写出的，点开前请先确认。拿不准的写"不确定"，没有可靠出处的不写链接。
- **对照**：只写四类之一或几类的组合：一样 / 相近 / 我们多做了什么 / 我们少做了什么。
- **值得补**：业界版本更成熟的地方；没有就写"无"。

## 一、界面与交互

| 我们的决定或规则 | 业界叫什么 | 出处 | 对照 | 值得补 |
|---|---|---|---|---|
| 内容用实色，只有浮在内容上的顶栏、输入框、菜单才用玻璃；不做玻璃叠玻璃（设计语言总原则 1） | 分层材质，液态玻璃（Liquid Glass）只用在控制层 | Apple Human Interface Guidelines：https://developer.apple.com/design/human-interface-guidelines/ （凭记忆） | 相近。我们多做：把六层写成表，每层固定底色和投影；少做：没有逐条对照 Apple 最新的玻璃限制 | 对照 Apple 官方条文，看有没有我们没覆盖的限制 |
| 六层（背景、内容、控制、侧边面板、浮层、提示）分别定底色和投影（设计语言二） | 层级系统（elevation system） | Material Design 2 的 elevation：https://m2.material.io/design/color/dark-theme ✔ 同页也讲层级 | 相近。我们多做：每层都写清"靠什么分层次"；少做：没有把"层级数量上限"写进检查 | 参考 Material 对浮层、对话框、菜单层级的建议，看六层是否够用 |
| 深色模式下，层级越高底色越亮（设计语言总原则 5） | 深色主题的表面叠色（surface overlay） | Material Design 2 深色主题：https://m2.material.io/design/color/dark-theme ✔ | 一样。Material 的做法就是越高越亮，靠半透明白色叠层实现 | 无 |
| 圆角同心：内层圆角 = 外层圆角 − 间距，四边距离相等（总原则 3，ADR-023，LESSONS 2026-10-14） | 同心圆角（concentric corners，nested radius） | Apple SwiftUI 的 ConcentricRectangle 有同样思路（凭记忆，未核对具体页） | 一样。我们多做：用脚本量四边距离，写进 LESSONS；少做：没有官方式的自动计算 | 无 |
| 形状跟内容走：正圆、胶囊、超椭圆三种（设计语言六.1，ADR-024） | 超椭圆角（squircle，连续曲率角，continuous corner） | 维基百科 Squircle（凭记忆）；Apple 的 continuous corner 也是同一概念 | 一样。我们多做：自己画的形状（融球、镂空）也用同一条曲线（|x|⁴+|y|⁴=r⁴），这是很少见的细节 | 无 |
| 同一种状态（悬停、按下、选中、危险）在所有组件里长得一样（总原则 6，设计语言八） | 一致性（consistency and standards） | Nielsen 十条可用性原则第 4 条：https://www.nngroup.com/articles/ten-usability-heuristics/ （凭记忆） | 一样。我们多做：用 lint 脚本拦截自己写的悬停、焦点样式 | 无 |
| 安静，不装饰；不用 emoji 和 ✓✕ 当图标（总原则 7，ADR-024） | 极简美学（aesthetic and minimalist design） | Nielsen 十条第 8 条（同上，凭记忆） | 一样。我们多做：把"装饰动画"列为不做，只留呼吸、眨眼、三个点 | 无 |
| 按下不缩放（设计语言八、九，主人定） | 按压反馈（pressed state feedback）；规范里有的写"可以缩到 0.98" | Apple HIG 的 Buttons 条目（凭记忆） | 我们少做：不用缩放反馈，少了一种常见的手感提示 | 可以在"按下"里加颜色加深，已经有；这条是主人的取舍，不建议改 |
| 组件用无样式组件库（React Aria Components）处理交互和无障碍，外观自己写（ADR-023） | 无样式组件（headless components） | Headless UI：https://headlessui.com/ （凭记忆）；React Aria：https://react-aria.adobe.com/ （凭记忆） | 一样。我们多做：外观全部由设计令牌驱动 | 无 |
| 颜色做成 12 阶，按用途起名（surface、bg、rail、hover……）（设计语言三） | 色阶（color scale，12 步）加语义令牌（semantic tokens） | Radix Colors：https://www.radix-ui.com/colors （凭记忆） | 相近。我们多做：组件只用语义名字，改阶梯不用改组件；少做：角色色还没做到 12 阶自动生成 | 参考 Radix 的做法，用算法生成角色色的 12 阶，而不是手调 |
| 颜色、间距、圆角、字号都从档位里取，组件里不写死数字（总原则 2，ADR-023） | 设计令牌（design tokens） | W3C 设计令牌格式（DTCG 2025.10）：https://www.w3.org/community/reports/design-tokens/CG-FINAL-format-20251028/ ✔ | 一样。我们多做：有 lint 检查（bun run lint:ui）；少做：还没导出成标准格式，别的工具读不了 | 把 tokens.css 的源头改成 DTCG 格式，以后换工具不用重写 |
| 样式检查拦截写死的颜色、尺寸，组件普查拦截新增的尺寸（设计语言十二，设计自查 18） | 样式规则检查（stylelint）；视觉回归前的"设计规范检查" | stylelint：https://stylelint.io/ （凭记忆） | 相近。我们多做：普查新尺寸种数；少做：没有像 stylelint 那样的插件生态 | 无，已经有 |
| 对比度：正文 4.5:1，图标和控件 3:1，脚本自动算（设计语言三.3、十二.3） | 对比度（WCAG 1.4.3、1.4.11） | WCAG 2.2：https://www.w3.org/TR/WCAG22/ （凭记忆） | 一样。我们多做：按 6 个角色色各算一遍，这是个人项目不常做的 | 无 |
| 点击目标至少 24×24，常用按钮 32 以上（设计自查 15） | 最小目标尺寸（target size，WCAG 2.5.8） | WCAG 2.2 2.5.8：https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html （凭记忆） | 相近。我们多做：常用按钮要求 32 以上，比 WCAG 的最低线高；少做：没有按 Apple 的 44 点标准检查触屏 | 手机端做之前，按 44 点再对一次 |
| 焦点环只在键盘操作时出现（设计语言八） | 焦点可见（:focus-visible，WCAG 2.4.7） | MDN :focus-visible：https://developer.mozilla.org/en-US/docs/Web/CSS/:focus-visible （凭记忆） | 一样 | 无 |
| 系统"减少动态效果"时关掉弹簧，循环动画写明停成什么样（设计语言九） | 减少动态效果（prefers-reduced-motion，WCAG 2.3.3） | MDN prefers-reduced-motion：https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion （凭记忆） | 一样。我们多做：循环动画停在什么状态也写清楚（比如转圈放慢到三倍） | 无 |
| 进出场用关键帧动画，不用 transition，因为 React Aria 的入场状态只存在一帧（LESSONS 2026-10-14） | 离场动画（exit animation）与"保持挂载直到动画结束" | 没有统一的中文名；Framer Motion 的 AnimatePresence 做的是同一件事（凭记忆，未核对） | 相近。我们多做：用 getAnimations 和逐帧脚本量动画，并写成 LESSONS；少做：没有自动化的动画回归测试 | 把 check-exit-transition.ts 放进 check:ui，每次改弹层都自动跑 |
| 滑块指示器：选中块从旧位置滑到新位置（设计语言九） | 共享布局动画（shared layout animation） | Framer Motion layout 文档（凭记忆，未核对） | 相近。我们多做：会话列表的悬停块也用同一套 | 无 |
| 融球（goo）：两个形状靠平滑的距离场并在一起，用于"跳到最新"（设计语言七.1） | 元球效果（metaball）；平滑最小值（smooth min） | 维基百科 Metaball（凭记忆）；Inigo Quilez 的 smin 文章（凭记忆） | 相近。我们多做：玻璃上用 SDF 只重算附近一块，放进 Worker 里；少做：没有性能预算的自动测试 | 无 |
| 分拣队列：接受、拒绝、稍后，稍后会自己回来（ADR-057，路线图七） | 分拣（triage）队列 | Linear Triage：https://linear.app/docs/triage ✔ | 相近。Linear 的做法是接受 / 重复 / 拒绝 / 稍后，拒绝要写理由，我们也有理由。我们多做：区分"阅览"和"决定"两种用途；少做：没有撤回窗口 | 补一个撤回窗口和"批量预览后再确认"；拒绝时写理由的做法可以直接照 Linear |
| 决定操作：一次一条、错了撤销、不弹确认框；撤不回的（审批）才要看清再点（设计语言 8、ADR-057） | 撤销优先于确认（undo over confirmation）；防错（error prevention） | Nielsen 十条第 3 条"用户控制与自由"、第 5 条"防错"：https://www.nngroup.com/articles/ten-usability-heuristics/ （凭记忆） | 一样。我们多做：按"能不能撤回 × 影响面"分级（路线图待办）；少做：分级还没有落地 | 把分级做成规则表，写进设计语言 |
| 决定队列用游戏化手感（滑卡片、微交互）降低每次决定的成本（ADR-057） | 游戏化（gamification） | 维基百科 Gamification（凭记忆） | 相近，但有风险。游戏化容易让人快速点、不看清；我们对撤不回的动作用了不同手感，这一点是对的 | 对"影响大"的决定设置"看清再点"，和 Linear 的快捷键分开 |
| 命令面板 Ctrl+K，打字筛选、支持拼音关键词（设计语言八.5） | 命令面板（command palette） | 业界常见，Sublime Text、VS Code 都有（不附链接） | 一样。我们多做：拼音关键词，适合中文用户 | 无 |
| 常用操作放在手边（主人说的"高频操作放在一起"）；目前没有写成规则 | 费茨定律（Fitts's law）：距离越近、目标越大，点得越快 | 维基百科 Fitts's law：https://en.wikipedia.org/wiki/Fitts%27s_law （凭记忆） | 我们少做：还没有用使用频率排序导航和操作的规则 | 把"高频操作靠近常用位置"写成规则，并用使用数据验证 |
| 虚拟列表：只渲染看得见的项，往上翻时补偿高度，防止跳动（LESSONS 2026-10-15） | 虚拟滚动（virtual scrolling / windowing）；滚动锚定（scroll anchoring） | MDN overflow-anchor（滚动锚定）：https://developer.mozilla.org/en-US/docs/Web/CSS/overflow-anchor （凭记忆） | 相近。我们多做：用脚本量"停手后还在动"的次数（59 次），这个指标很好；少做：用的是自己写的补偿，没用浏览器自带的锚定 | 先试浏览器自带的 overflow-anchor，能用就少一份代码 |
| 媒体查询里的覆盖规则要写在被覆盖的规则后面；用计算样式核对（LESSONS 2026-10-15） | CSS 层叠与优先级（cascade） | MDN Cascade：https://developer.mozilla.org/en-US/docs/Web/CSS/Cascade （凭记忆） | 一样，这是 CSS 的基础知识。我们多做：改完用 getComputedStyle 核对 | 无 |
| 先画线框图，评审通过再做组件（界面清单，ADR-024） | 线框图（wireframe）、低保真原型（lo-fi prototype）、设计评审（design critique） | 设计评审是设计团队的常规做法；没有单一出处 | 相近。我们多做：线框图评审十轮，并保留在 Claude 的 artifact 里；少做：没有用户测试，只有主人自己用 | 找 2～3 个真人用一下，看他们第一眼看什么（"一眼先看到什么"） |
| 设计自查表：把 Nielsen 十条和压力测试放在一张表里（设计自查） | 启发式评估（heuristic evaluation） | Nielsen 十条：https://www.nngroup.com/articles/ten-usability-heuristics/ （凭记忆） | 一样。我们多做：每条配脚本；少做：没有其他人独立评审 | 找别人按同一张表打分，比对自己的结果 |

## 二、写作和措辞

| 我们的决定或规则 | 业界叫什么 | 出处 | 对照 | 值得补 |
|---|---|---|---|---|
| 按钮写它会做什么（"批准""删除"），不写"确定""提交"；同一个动作的按钮和提示用同一个词（设计语言十一） | 动词式按钮文案（verb-first button labels）；文案一致（terminology consistency） | Nielsen 十条第 4 条（凭记忆） | 一样 | 无 |
| 说明文字常驻最多一行，细的折叠（设计语言十一，ADR-059） | 微文案（microcopy）；辅助说明文字（helper text） | 维基百科 Microcopy：https://en.wikipedia.org/wiki/Microcopy （凭记忆）；渐进披露：https://www.nngroup.com/articles/progressive-disclosure/ （凭记忆） | 一样。我们多做：规定"要靠一段话才懂的，改选项本身"；这点很少被写出来 | 无 |
| 功能和设置起名用常见 App 的叫法，看名字能猜对它做什么（设计语言十一，ADR-031、ADR-061、睡眠模式） | 最少惊讶原则（principle of least astonishment）；"与现实匹配"（Nielsen 第 2 条） | 维基百科 Principle of least astonishment：https://en.wikipedia.org/wiki/Principle_of_least_astonishment （凭记忆） | 相近。我们多做：起名后问一句"用户会不会以为它多做或少做了什么"，这是个好问题 | 无 |
| 加设置前先想有没有实际场合，说不出理由的不加（设计语言十一） | 不要预先设计（YAGNI，"你不会需要它"） | 维基百科 YAGNI：https://en.wikipedia.org/wiki/You_aren%27t_gonna_need_it （凭记忆） | 相近。我们多做：设置页要和相近设置分清（"暂停"就是例子）；少做：没有规定上限 | 无 |
| 表单字段第一次离开后才检查，之后边改边更新（设计语言 8.3） | 行内校验，失焦后校验（inline validation） | NN/g 表单错误设计指南：https://www.nngroup.com/articles/errors-forms-design-guidelines/ （凭记忆） | 一样 | 无 |
| 出错说清楚原因和下一步（设计语言 8.3、设计自查 9） | 帮助用户识别、诊断、恢复错误（Nielsen 第 9 条） | Nielsen 十条第 9 条（凭记忆） | 一样。我们多做：每个空状态都写下一步（EmptyState） | 无 |
| 空状态要说清楚为什么空、能做什么（设计语言 8.3） | 空状态（empty state） | 业界常见写法，没有单一出处（不附链接） | 一样 | 无 |
| 句末标点换行：句号去掉，感叹号问号留着（ADR-051、ADR-053） | 没有统一的业界名字；属于"标点的语气"设计（不确定） | 不确定 | 我们自己的做法，近似于聊天里按句拆消息的习惯 | 找几个中文聊天样本，看句号是否真的显冷淡，有数据再定 |

## 三、工程流程与验收

| 我们的决定或规则 | 业界叫什么 | 出处 | 对照 | 值得补 |
|---|---|---|---|---|
| 修 bug 时带一个"把旧代码放回去会失败"的测试（AGENTS 验收） | 回归测试（regression test） | 维基百科 Regression testing：https://en.wikipedia.org/wiki/Regression_testing （凭记忆） | 一样 | 无 |
| 故意改坏检查，看测试会不会变红（AGENTS 验收，参考 magpie 的 break check） | 变异测试（mutation testing） | 维基百科 Mutation testing：https://en.wikipedia.org/wiki/Mutation_testing （凭记忆） | 相近。我们多做：每次手工用三种方式改坏，并写进提交说明；少做：没有自动化工具，改坏的数量是人挑的 | 用 Stryker（JS/TS）或同类工具自动生成变异体，每周跑一次看存活率：https://stryker-mutator.io/ （凭记忆） |
| 新页面、新模块验收时"放大十倍"（ADR-056） | 压力测试（stress testing）、可扩展性测试（scalability testing） | 维基百科 Stress testing（software）：https://en.wikipedia.org/wiki/Stress_testing_(software) （凭记忆） | 一样。我们多做：规定用数字（元素数、卡顿时长、跳变次数）验收 | 无 |
| 不稳定的测试要定位根因，不靠重跑碰运气（LESSONS 2026-10-15，三次偶发失败） | 不稳定测试（flaky test）管理；隔离与修复 | 业界常见做法，没有单一出处（不附链接） | 相近。我们多做：只循环跑可疑文件、抓完整调用栈；少做：没有把 flaky 测试自动隔离 | 给 flaky 测试加一个"隔离区"标签，不让它拖垮整轮 |
| 后台被强制结束，3 秒内拉起；一分钟内崩 3 次就停下并通知（桌面壳规格） | 监督者（supervisor）；熔断器（circuit breaker） | 维基百科 Circuit breaker design pattern：https://en.wikipedia.org/wiki/Circuit_breaker_design_pattern （凭记忆）；Michael Nygard《Release It!》是出处 | 一样。我们多做：把"停下来"写成必须弹通知；少做：没有"半开"状态（过一段时间试探性重启） | 加"半开"状态：停下后隔一段时间试一次，成功了才恢复 |
| 验收时直接杀进程看能不能恢复（桌面壳规格第八节） | 故障注入、混沌工程（fault injection，chaos engineering） | 维基百科 Chaos engineering：https://en.wikipedia.org/wiki/Chaos_engineering （凭记忆） | 相近。我们多做：用具体的时间数字验收；少做：没有定期自动注入故障 | 无，等桌面壳做完再加定期演练 |

| 忘掉某人是删除任务，原始聊天记录不删，派生的删（ADR-034 第 6 条） | 软删除（soft delete）；墓碑（tombstone）；原始与派生分离 | 业界常见做法（不附链接）；被遗忘权（right to erasure）：GDPR 第 17 条（凭记忆） | 相近。我们多做：删除要列出每一处（删了什么、哪些索引）；少做：没有写清楚"原始记录不删"在法律上的边界 | 把删除记录写成日志（和 MaiBot 的 delete_operations 一样） |
| 群 A 的事不在群 B 说；私聊只给白名单的人（ADR-041，规格-记忆 3.3） | 情境完整性（contextual integrity） | 维基百科 Contextual integrity：https://en.wikipedia.org/wiki/Contextual_integrity （凭记忆，Helen Nissenbaum，2004） | 一样。这是这个理论最贴的例子：信息在哪个场景流动，要符合那个场景的规范 | 无 |
| 私聊白名单默认是空的，主人和别人一视同仁（ADR-041） | 安全默认值（fail-safe defaults）；最小特权（least privilege） | Saltzer 与 Schroeder，1975：https://web.mit.edu/Saltzer/www/publications/protection/ （凭记忆）；最小特权：https://en.wikipedia.org/wiki/Principle_of_least_privilege （凭记忆） | 一样 | 无 |
| 表达学习的审核只分行、不行，理由每次都写（ADR-054，路线图） | 人在回路审核；理由记录（reason codes） | 人在回路见上 | 相近。我们多做：每条写依据；少做：没有追加式的审核记录表（路线图第五节也写了） | 做追加式审核记录，改动可以查 |

## 最值得补的 5 点（按收益排序）

1. **变异测试自动化**：现在"故意改坏"是人挑的三种方式，换成 Stryker 之类的工具每周自动跑，能发现漏掉的检查（凭记忆的工具名，用前确认）。
2. **记忆加双时态字段**：给记忆加"事实什么时候成立"和"什么时候写进来的"两个时间字段，"以前成立"和"记错了"就能用时间分清，不只靠状态。
3. **熔断器加"半开"状态**：后台连续崩溃后，停下来不是永远不起；隔一段时间试一次，成功了才恢复。
4. **闸门做概率校准**：用 Brier 分数检查"说 0.3 的时候，是不是真有三成会接"，上线前先有基线，不然拟合再多也不知道准不准。
5. **用 DTCG 格式导出设计令牌**：现在的 tokens.css 只能自己用，换工具要重写；W3C 设计令牌格式已经是 2025.10 的稳定版（✔ 已核对）。
