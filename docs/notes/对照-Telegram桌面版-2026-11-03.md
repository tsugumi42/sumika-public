# Telegram Desktop 界面调研：给 Sumika 桌面程序的参考

> 2026-11-03，Sol（omp）读本机 tdesktop 250fc73、lib_ui 1ff7be7 源码和公开资料写成；主会话抽查了窗口宽度（window.style）。用途：ADR-245、ADR-246 的照 Telegram 改聊天界面，组件库 mewtype 的数值也从这里和 mewtype/docs/reference/ 取。

> 背景，不是规则（2026-11-19，P0-5）：这是 Telegram 桌面版的调研和数值；ADR-280 起 Telegram 不再是验收线，ADR-283 只保留分栏和缩放照 Telegram，外观部分已被 ADR-364 暂停；现行规则看[规格-设计令牌](../规格-设计令牌.md)和[开发指导/界面与交互](../开发指导/界面与交互.md)和[设计语言](../设计语言.md)。

## 先说人话

最值得借的五条：**① 把聊天界面的尺寸从全局“疏密”里分出来**，否则改一个间距单位，导航栏、头像、气泡宽度会一起放大；**② 气泡用 16 的大圆角、6 的连接圆角，连发时改变相邻角和间距**，比目前所有角都是 32 更接近 Telegram；**③ 时间属于每条消息，放进气泡右下角，图片上的时间另用浮层**，不再只给一组消息的最后一条写时间；**④ 回复引用、Markdown、图片和消息状态共用一套消息容器**，解决现在 Markdown 引用另外套一个小气泡的问题；**⑤ 优先补“回到最新”、未读分隔和消息右键菜单**，这些对每天翻记录的影响，比贴纸悬停动画更大。

## 取证范围与可信度

- Telegram：官方 [`telegramdesktop/tdesktop`](https://github.com/telegramdesktop/tdesktop)，固定源码提交 ****。该快照的更新日志首项是 **7.3.4 beta，2026-10-29**；最近一项正式版记录是 **7.3.3，2026-10-21**。下文描述的是这个源码快照，不能把所有内容都当成正式版已经发布的行为。[T0]
- Telegram 共用界面库：`desktop-app/lib_ui@1ff7be77d578aaf8ad17d2fa6e51bae1ee567c1b`。
- Sumika：当前工作区源码；依赖是 **mygo v0.7.4、CrychicUI `bf15ddf6600a`**，见 [native/go.mod](/仓库根/native/go.mod:5)。
- 方法：只读源码、官方公告及公开资料；没有启动 Telegram、QQ 或 Sumika，没有访问项目真实数据目录，没有修改文件。
- `[读码]`：实现或样式定义已读；`[文档]`：官方公告明确说明；`[推断]`：根据代码结构推算；`[未核实]`：缺少对应版本的实现或实测证据。**没有任何一项是本次窗口实测结果。**
- 正文先写 Telegram 本身，再写 Sumika 对照；最后的数值都是**我的建议**，不是新增的项目决定。

尺寸统一按基准逻辑像素理解。Telegram 自身的界面缩放、系统缩放，以及 Sumika 的系统文字大小，都可能改变最终物理像素。

## 一、Telegram 的主窗口与顶栏

### 1. 四块区域的宽度

`window/window.style` 给出的基础约束如下。[T1]

| 区域 | 源码数值 | 说明 |
|---|---:|---|
| 文件夹竖栏 | **72** | `windowFiltersWidth` |
| 会话列表 | **260～540** | `columnMinimalWidthLeft`、`columnMaximalWidthLeft` |
| 主聊天栏 | 最小 **380** | `columnMinimalWidthMain` |
| 第三栏／资料栏 | **292～392** | `columnMinimalWidthThird`、`columnMaximalWidthThird` |
| 主窗口 | 最小 **380 × 480** | `windowMinWidth`、`windowMinHeight` |
| 默认窗口 | **800 × 600** | 另有 **1024 × 768** 的较大默认值 |
| 宽聊天布局参考值 | **880** | `adaptiveChatWideWidth`；不能直接当成四栏切换断点 |

文件夹按钮的尺寸也有不同状态：

- 带图标和文字：最小高 **62**，文字 **11 semibold**。
- 只显示图标：最小高 **54**。
- 只显示文字：最小高 **44**。
- 未读徽标：高 **17**，字体 **12 semibold**。[T1]

**窄窗口的处理不是把所有栏按比例压扁。** Telegram 有会话列表压缩、单栏导航和第三栏切换等状态。不过，本次没有把完整自适应状态机及其所有用户设置分支核对完；**头像模式的精确宽度、自动进入头像模式的阈值，以及单栏切换的完整条件标为未核实**。

可以确认的是：不能简单拿 `260 + 380 = 640` 当成整窗断点；文件夹栏、分隔线、用户保存的宽度和当前布局状态也会参与计算。

### 2. 会话列表行

普通会话行的默认样式非常具体。[T2]

| 项目 | 数值 |
|---|---:|
| 普通行高 | **62** |
| 内边距 | 左右 **10**，上下 **8** |
| 头像 | **46 × 46** |
| 名字起点 | 相对行左上角 **(68, 10)** |
| 最后一条消息起点 | **(68, 34)** |
| 时间字号 | **13** |
| 未读徽标高 | **19** |
| 未读徽标水平内边距 | **5** |
| 未读数字字号 | **12 bold** |

不是所有行都固定 62：带标签的行是 **72**，论坛行 **80**，带标签的论坛行 **96**。这些高度是为额外内容留位置，不是随机增加留白。

名字、摘要、时间、未读各有固定职责；选中和悬停通过背景与文字颜色状态变化表达。

### 3. 列表搜索行与聊天顶栏

列表搜索框 `dialogsFilter`：[T2]

- 最小高度 **35**。
- `borderRadius: 18`。
- 文字内边距：左 **12**、上 **8**、右 **30**、下 **5**。
- 不活动背景和活动背景分开。
- 搜索取消按钮 **35 × 35**，交叉图标动画 **150 ms**。

聊天顶栏的实现返回统一的 `st::topBarHeight`，标题和状态文字分别绘制，而不是把两个随意高度的文本控件堆起来。[T8]

**本次没有定位到聊天主顶栏 `topBarHeight` 的最终数值定义，标为未核实。** 已确认的资料顶栏 `infoTopBarHeight` 是 **54**，但不能拿它直接替代聊天主顶栏的取证结果。[T4]

资料顶栏可以作为另一组已核实的排版参考：

- 单行标题：**14 semibold**，位置 **(24, 17)**。
- 双行标题：位置 **(16, 8)**。
- 副标题：位置 **(16, 28)**，弱化文字色。
- 搜索按钮宽 **56**，更多按钮宽 **48**，通话按钮宽 **42**。[T4]

`[推断]` 对齐的关键是让列表搜索区和聊天顶栏共用顶部行的几何边界；搜索框本身比顶栏矮，垂直居中。不能把“搜索框高 35”和“顶栏高多少”混为一个数。

## 二、Telegram 的消息气泡与阅读导航

### 1. 气泡尺寸、圆角和连发

已核实的基础参数：[T3][T5]

| 项目 | 数值 |
|---|---:|
| 普通消息宽度上限 | **430** |
| `msgMinWidth` | **160**，属于消息布局基础参数，不代表每个短气泡都强制宽 160 |
| 正文基础字号 | **13** |
| 时间字号 | **13** |
| 内边距 | 左右 **11**，上下 **8** |
| 大圆角 | **16** |
| 小圆角 | **6**，来自 `roundRadiusLarge` |
| 普通外边距参数 | 左 **16**、上 **6**、右 **56**、下 **2** |
| 连发附着时的顶部额外边距 | **0** |
| 消息头像 | **33** |
| 头像占位步长 | **40** |

Telegram 把消息之间的“附着关系”和气泡绘制联系起来。同一发送者连发时，相邻气泡连接侧使用较小圆角，外露部分保留大圆角。

**每种媒体、方向和首尾状态究竟映射到哪四个角，本次没有完整核实，不能把所有情况概括成一个固定的“小左下角／小右下角”规则。** 实现时应按首条、中间条、末条、单条四种状态分别对照。

连发时间阈值是 **900 秒，也就是 15 分钟**，不是常见印象里的 5 分钟。源码常量是 `kAttachMessageToPreviousSecondsDelta = 900`。[T6]

而且“同一个人、15 分钟内”仍不够，分组还会被这些条件打断：

- 日期分隔、未读分隔、话题栏。
- 服务消息等不允许附着的消息类型。
- 不同话题。
- 不同临时消息接收对象或其他相关状态。
- 特殊转发来源规则。[T6]

### 2. 名字、头像与时间

Telegram 为名字、头像、转发来源和底部信息分别计算显示条件；这些不是正文中的普通文本。

- 群聊名字和头像可随连发分组减少重复。
- 头像并非每条消息都重复占一张图。
- **本次未完整核实头像在所有滚动位置下的贴底／浮动算法。**
- 时间和发送状态由 `BottomInfo` 单独布局，属于消息自身。
- 文本消息为底部信息预留空间；图片等媒体可以使用覆盖在媒体上的时间样式。[T3][T7]

相关参数包括：

- `msgDateSpace: 12`。
- `msgDateDelta: (2, 5)`。
- 媒体时间内边距参数 `msgDateImgPadding: (8, 2)`。
- 发送状态空间 `historySendStateSpace: 24`。[T3]

这些是绘制参数，不能直接翻译成一个通用的 CSS `padding-right`。

**已读勾的含义来自 Telegram 的发送／阅读状态。Sumika 的“自己看到了最新记录”不等于 QQ 对方已读，不能套同一个勾。**

### 3. 日期、未读与回到最新

日期分隔使用服务消息样式；基础服务文字内边距为左右 **12**、上 **3**、下 **4**，日期圆角引用 **6**。浮动日期的隐藏等待是 **1000 ms**，淡入淡出时长参数 **200 ms**。[T3][T5]

未读分隔：

- `historyUnreadBarHeight: 32`。
- `historyUnreadBarMargin: 8`。
- 字体使用 semibold。[T3]

“回到最新”按钮：[T9]

- 控件框 **52 × 62**。
- 圆形波纹区域 **42**。
- 位置参数 **(12, 10)**。
- 徽标尺寸 **22**。
- 显示距离参数 **480**。
- 显示／隐藏动画 **150 ms**。

**52 × 62 是控件框，不是圆圈直径。** 这类区别在照着做时很容易抄错。

## 三、Telegram 的引用、转发、链接和媒体

### 1. 回复引用与正文引用块

Telegram 有两种不同对象：

1. **回复引用**：指向另一条消息，可以包含原作者、摘要、媒体缩略图，并跳到原位置。
2. **正文引用块**：消息正文内部的一种格式，可以有多段，也可以折叠。

回复相关参数：[T3]

- 媒体缩略图 **32**。
- `msgReplyPadding: (6, 6, 11, 6)`。
- 竖线基础尺寸 **2 × 36**。
- 竖线与内容的布局间隔参数 **10**。

正文里的链接预览引用样式另有：

- `historyPagePreview.padding: (10, 5, 7, 7)`。[T3]

**这几套参数不能混用。** 回复摘要卡的竖线，不等于正文 Markdown `>` 的全部样式。

官方在 2023-10-28 明确增加了局部引用：点击引用会定位到原消息的具体位置，并用动画提示。[T10]

### 2. 转发消息

Telegram 把转发来源作为消息头的一部分，和正文、回复引用、媒体、时间共同排在一条消息中。转发来源文字有单独的 `fwdTextStyle`，基础为 semibold。[T3]

需要区分：

- Telegram 的一条转发消息及其来源。
- QQ 的“合并转发聊天记录”，它是可打开的一组记录。

这两者不能只用一个类似 Telegram 的来源标题互相替代。QQ 合并转发需要保留内部多条记录的结构。

### 3. 链接预览

官方公告确认链接预览可以显示标题、描述和媒体；2023-10-28 增加了：[T10]

- 选择预览哪一个链接。
- 调整预览媒体大小。
- 把预览放在正文上方或下方。
- 点击预览区域打开链接。

源码中，链接标题使用 semibold，描述使用普通正文样式；`webPagePhotoDelta` 是 **8**。[T3]

预览内容本身是独立媒体对象，不是把网页标题直接拼进普通文本。

### 4. 多图／相册

样式参数：[T3]

- 相册宽度上限 **430**。
- 最小宽度参考 **100**。
- 图片之间间隔 **4**。

`[推断]` Telegram 的相册外观追求作为一个整体排版，根据图片比例分配布局；本次没有完整核对其拼图算法，因此没有给出“几张必定几列”的结论。

相册的时间、选中状态和外轮廓需要以整体处理；不能给每个内部格子都画完整的大圆角。

### 5. 贴纸、GIF 与表情

基础尺寸上限：[T3]

| 类型 | 数值 |
|---|---:|
| 普通媒体 | **430** |
| 贴纸 | **224** |
| 动态大表情 | **112** |
| GIF | **320** |
| 视频消息 | **240** |
| 大号普通 emoji | **36** |

这些是不同类型的上限，**不能把一切动图都统一改成 320 或 224**。

贴纸和大表情具有独立的显示路径，可使用透明背景。播放、暂停和动效还与窗口活动状态等因素关联；本次没有把完整自动播放策略核对成一张状态表。

### 6. 表情回应

Telegram 的回应有行内胶囊和悬停角标等不同形态。[T3]

行内回应：

- 图标尺寸 **18**。
- 内边距：左 **5**、上 **2**、右 **7**、下 **2**。
- 胶囊之间间距 **4**。
- 图标与后续内容的间隔参数 **3**。
- 回应者小头像 **20**，重叠步长 **7**。

悬停回应角标：

- 控件基础尺寸 **36 × 32**。
- 图标 **22**。

它既是反馈展示，也是交互入口。仅画出“emoji + 数字”还没有覆盖完整交互。

## 四、右键、多选、悬停与动效

### 1. 菜单

Telegram 共用菜单默认参数：[T11]

| 项目 | 数值 |
|---|---:|
| 圆角 | **8** |
| 最小／最大宽度 | **156／300** |
| 条目内边距 | 左右 **17**、上 **8**、下 **7** |
| 菜单上下滚动留白 | 各 **8** |
| `duration` | **150 ms** |
| `showDuration` | **200 ms** |

条目高度由字体和内边距共同决定，不能只拿 13 号字算成固定 28 高。

菜单有悬停、禁用、快捷键文字、分隔线和子菜单状态。消息菜单的项目还会随消息类型、选中文本和权限改变。**本次没有完整核实该快照所有消息类型的菜单项目及顺序**；不能把“回复、复制、转发、删除”等常见集合写成一份固定完整菜单。

### 2. 文本选择与消息多选

正文的文本选择、整条消息选择是不同状态。消息多选有独立勾选视觉；共用圆形勾选动画参数为 **160 ms**，头像选择动画参数 **150 ms**。[T11]

`[建议]` 实现时应分别处理：

- 拖选一段文本后复制。
- 选择一条消息。
- 多选多条消息后批量操作。

把整个消息设为 `Selectable` 只能解决其中一部分。

### 3. 动效时长与曲线

已核实的时长分布：

| 场景／参数 | 时长 |
|---|---:|
| 通用状态变化 `universalDuration` | **120 ms** |
| 页面横向切换 `slideDuration` | **240 ms** |
| `slideWrapDuration` | **150 ms** |
| `fadeWrapDuration` | **200 ms** |
| 会话筛选滑动 | **200 ms** |
| 筛选手势滑动 | **140 ms** |
| 回到最新按钮 | **150 ms** |
| 日期淡入淡出 | **200 ms** |
| 消息显现 `itemRevealDuration` | **150 ms** |

来源：[T2][T3][T5][T9]。

**没有一条“Telegram 全部用某个 cubic-bezier”的统一结论。** 本次没有逐个核实调用点的缓动曲线；具体曲线标为未核实。照着时长做，比臆造一个统一弹簧参数可靠。

另外，7.3.4 beta 的更新日志明确增加了“发送文本飞入气泡”的动画。它是该 beta 的变化，不能倒推成所有历史版本一直如此。[T0]

## 五、深浅主题的颜色组织

`[读码]` Telegram 的基础方式是**按语义和状态定义调色板**，组件样式引用这些名字。[T12]

例如：

- 窗口：`windowBg`、`windowFg`。
- 弱文字：`windowSubTextFg`。
- 悬停：`windowBgOver`、`windowFgOver`。
- 活动状态：`windowBgActive`、`windowFgActive`。
- 菜单：`menuBg`、`menuIconFg`、`menuFgDisabled`。
- 收到／发出的消息：分别有正文、链接、等宽文字、日期和选中颜色。[T3]

基础浅色回退值中可以看到：

| 语义 | 基础值 |
|---|---|
| 窗口背景 | `#ffffff` |
| 普通文字 | `#000000` |
| 悬停背景 | `#f1f1f1` |
| 弱文字 | `#999999` |
| 活动背景 | `#40a7e3` |
| 活动文字色 | `#168acd` |

这些是**基础回退调色板中的值**，不是“用户当前 Telegram 主题必定使用的颜色”。

夜间模式沿用组件的语义引用，替换对应调色板和相关主题资源。**本次没有逐项核对内置夜间主题的最终色值**，所以不提供一张未经核实的“Telegram 暗色十六进制表”。

对 Sumika 最有用的是：保留角色色，同时让收发气泡、时间、引用、链接、选中态都有明确颜色职责；不要靠同一个强调色加不同透明度包办全部状态。

## 六、消息格式近年的更新

Telegram 的格式能力需要分成普通消息实体、Bot API 的 Markdown／HTML 输入，以及新的富文本消息。

| 日期 | 已确认变化 | 出处与边界 |
|---|---|---|
| **2023-10-28** | 局部回复引用；正文引用格式；可调整链接预览 | 官方公告 [T10] |
| **2024-05-31** | 可折叠的正文引用块；媒体说明可放上方 | 官方公告 [T13] |
| **2026-06-09** | Desktop 6.9：Bot 富文本；`.md` 文件查看器 | Desktop 更新日志 [T0] |
| **2026-07-02** | 6.9.4 beta：含媒体、表格、数学公式的富文本编辑器 | Desktop 更新日志 [T0] |
| **2026-07-14** | 官方发布富文本编辑器，支持标题、表格、列表、引用、代码块、正文中间的照片视频 | 官方公告 [T14] |
| **2026-10-20** | Desktop 7.3.2：对富文本消息做引用回复 | Desktop 更新日志 [T0] |

2026-07-14 的公告还明确：

- 富文本消息最多 **32,768 字符**。
- 当时富文本编辑器仅对 Premium 用户提供。[T14]

Bot API 当前明确支持粗体、斜体、下划线、删除线、剧透、普通引用块、折叠引用块、行内链接、行内代码和代码块。[T15]

需要避免三个误读：

1. **Telegram 的 MarkdownV2 不是通用 Markdown。** 转义、实体嵌套和引用规则不同。
2. 普通消息格式与 2026 年富文本消息，不是同一个数据结构层级。
3. “看起来像 Telegram”不要求把 Sumika 的模型输出改成 MarkdownV2；可以保留模型常用 Markdown，借鉴显示和操作。

## 七、Sumika 当前实现对照

### 1. 先纠正尺寸基线

当前主题设置：

- `Spacing = 5`。
- `Radius = 16`。
- 基础字号 `16 × fontScale(base)`。

见 [theme.go](/仓库根/native/theme.go:55)。mygo v0.7.4 的 `Space(n)` 返回 `n × Spacing`。[C1]

因此，源码注释中沿用的“默认间距单位 4”换算已经不能直接当现状：

| 项目 | 当前表达式 | 当前主题下的计算值 |
|---|---|---:|
| 导航栏宽 | `Space(20)` | **100** |
| 三栏顶部内容行高 | `Space(13)` | **65** |
| 气泡上限 | `Space(80)` | **400** |
| 气泡圆角 | `Radius × 2` | **32** |
| 普通气泡内边距 | `Space(2), Space(3)` | 上下 **10**、左右 **15** |
| 消息头像 | `Space(10)` | **50** |
| 普通图片宽上限 | `Space(80) - 2 × Space(3)` | **370** |
| 长图高度上限 | 图片宽上限 × 1.8 | 满宽时 **666** |

这是**读码计算值，不是窗口测量值**。例如 `bubble.go` 注释写“最宽 320、上下 8、左右 12”，实际表达式现在算出来是上表数值。

### 3. Markdown 现在实际支持到哪

`msgFromView` 依据 **`Origin == "character"`** 设置 Markdown 标志；不是所有收到的文字都按 Markdown 解释。[data.go](/仓库根/native/data.go:184)

`chat.MarkdownMessage` 已经：

- 调用 mygo 的 Markdown 渲染器。
- 为代码块显示语言栏和复制按钮。
- 处理标题锚点。
- 通过链接处理函数打开允许的 URL。
- **使用普通面板气泡底色**：组件内部调用 `shell(c, false)`；`Mine` 只改变对齐。[C3]

当前主要差异：

- 消息回复引用和 Markdown 正文不在同一个壳里。
- 正文、图片等块可能分成多个容器。
- 没有接入 Telegram 式可折叠引用的消息展示契约。
- Markdown 路径与普通消息的入场控制不一致。
- 本次没有逐项验证 mygo Markdown 的表格、公式、嵌套引用等兼容范围，不能据组件名字声称“完整支持 Telegram 富文本”。

**建议先统一消息外壳，保留现有代码块复制功能，再定长文和折叠引用的行为。**
