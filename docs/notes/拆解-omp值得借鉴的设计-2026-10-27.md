## 一、评测：if-bench 怎样出题、判分和记录

### 1. 它测的是什么

[读码] if-bench 是**多轮指令遵循和工作记忆评测**，没有执行文件工具、审批、打断或压缩。每个模型维护一条不断增长的对话：模型操作一个字符数组，并在回复中夹入规定的猫叫声。第 N 轮给 N 个操作，第一次答错立即终止。

出处：`pi-coding-agent/src/if-bench/runner.ts:190`、`:220`；`src/if-bench/protocol.ts:91`。

[读码] 默认配置：

| 项目 | 默认值／限制 |
|---|---|
| 最多轮数 | 24 |
| 数组长度 | 24；必须为 8～26 之间的偶数 |
| 单次最大输出 | 32,768 token，还会受模型自己的上限限制 |
| 模型并发数 | 4；同一个模型内部逐轮串行 |
| 猫叫长度 | `nya{1,8}` |
| temperature | 0 |

出处：`pi-coding-agent/src/if-bench/index.ts:24`、`:69`；`src/if-bench/actions.ts:39`；`src/if-bench/protocol.ts:24`；`src/if-bench/runner.ts:305`。

### 2. 题目与正确答案都在本地生成

[读码] 初始数组取 `A..Z` 的前 L 个字符，用固定初始值 `0x9e3779b9` 的 LCG 做洗牌。后续操作由**绝对操作序号**计算，十种操作循环出现：交换、左移、区间反转、移动元素、右移、相邻交换、奇偶重排、分块反转、区间旋转、两半交织。相同长度和轮数得到相同题目。

出处：`pi-coding-agent/src/if-bench/actions.ts:39`、`:62`。

[读码] 宿主用 `applyActions()` 计算期望数组；不请另一个模型判题。只有第一轮提供起始数组，后续轮次要求模型从自己的上一条回复延续状态。正确轮次才把模型回复接入历史，第一次失败后停止，避免把失去正确状态后的结果混入分数。

出处：`pi-coding-agent/src/if-bench/actions.ts:108`；`src/if-bench/protocol.ts:54`；`src/if-bench/runner.ts:190`。

[读码] 猫叫指令按开头、中间、结尾轮换；中间位置会把操作序列分成两半。判分读取回复中的第一个 `<...>`，移除其中匹配的猫叫和空白，再与本地期望值比较；另外检查回复是否出现有效猫叫。失败分为：

- `format`：没有有效结果块。
- `cat`：数组正确，猫叫缺失。
- `result`：猫叫存在，数组错误。
- `result+cat`：两项都错。
- `provider`：请求失败或没有有效文字回复。

出处：`pi-coding-agent/src/if-bench/protocol.ts:54`、`:91`；`src/if-bench/runner.ts:215`、`:320`。

核心判分代码：

```ts
const reported = block[1].replace(cat, "").replace(/\s/g, "");
if (reported === expected) {
    return catPresent ? { passed: true, reported } : { passed: false, failure: "cat", reported };
}
return { passed: false, failure: catPresent ? "result" : "result+cat", reported };
```

出处：`pi-coding-agent/src/if-bench/protocol.ts:96`。

### 3. 记录哪些数，哪些没有

[读码] 每轮保存轮号、本轮／累计操作数、指令位置、耗时、输出 token、费用、通过与否、失败类型、本地期望值、模型回复；模型级报告累计连续通过轮数、正确完成操作数、耗时、输出 token、费用和第一次失败位置。

出处：`pi-coding-agent/src/if-bench/runner.ts:30`、`:220`。

[读码] 该报告没有独立的输入 token、缓存读写 token、TTFT、工具调用次数、RSS 或 CPU 字段。正常情况下轮次接近请求次数，但遇到拒答重试，两者不同。`--json` 将汇总对象输出到 stdout，适合外层批量驱动读取。

出处：`pi-coding-agent/src/if-bench/runner.ts:30`、`:77`；`src/if-bench/index.ts:135`。

### 4. 可重复性有边界

[读码] 题目确定、temperature 为 0，且时钟、stream、session ID、sleep 都可注入。这让评测逻辑容易离线验证；不能据此保证远端模型输出完全确定。

出处：`pi-coding-agent/src/if-bench/runner.ts:77`、`:315`。

[读码] 对前缀匹配 `Refusal (` 的错误最多请求八次，等待序列为 5、15、30、60、90、120、180 秒。函数名叫 `isCyberRefusal`，实际匹配范围比 “cyber” 更宽。每次尝试生成新的 session ID，并重新解析凭据。

出处：`pi-coding-agent/src/if-bench/runner.ts:112`、`:279`。

[读码] **统计只使用最后一次返回的 outcome。** 前面拒答尝试的耗时、费用和退避等待不会累计到这一轮报告中；单次耗时优先取 `message.duration`，否则取注入时钟的差值。因此它的 `durationMs` 不能直接当作用户等候的总墙钟时间。

出处：`pi-coding-agent/src/if-bench/runner.ts:220`、`:279`、`:301`。

[读码] 源码注释说整条线程保持同一 session ID，但执行路径每次请求都生成新 ID，并将其同时用于 `sessionId` 和 `promptCacheKey`：

```ts
const sessionId = options.randomSessionId();
```

```ts
sessionId,
promptCacheKey: sessionId,
```

出处：`pi-coding-agent/src/if-bench/runner.ts:282`、`:308`。

[推断] 历史内容保持相同前缀，有利于内容缓存；但不能按注释认定它具有稳定 cache key，也不能预设网关凭据亲和性和缓存命中一定稳定。做公平比较时应记录实际路由和缓存用量。

## 二、统计：omp-stats 是日志派生的观测库

### 1. 数据模型

[读码] `omp-stats` 从会话日志解析统计，再写 SQLite。它通过自身的结构化类型识别 coding-agent 日志，不直接导入 coding-agent 的实现。模型请求记录以 `(session_file, entry_id)` 去重，工具调用以 `(session_file, tool_call_id)` 去重。

出处：`omp-stats/src/types.ts:1`、`:111`；`src/db.ts:145`、`:229`。

[读码] 模型请求统计包括：

| 分类 | 字段 |
|---|---|
| 身份 | 会话文件、entry、项目目录、model、provider、API、agent 类型 |
| 时序 | timestamp、duration、TTFT |
| 结局 | stop reason、错误文字 |
| 用量 | input、output、cache read、cache write、total、premium requests |
| 费用 | 分项费用、总费用、无缓存输入费用、未能定价标记 |
| 服务差异 | provider 返回的 service tier |

出处：`omp-stats/src/types.ts:9`；`src/db.ts:145`。

[读码] 工具调用另存工具名、调用 ID、所在模型请求、同一步的工具调用数、参数字符数、结果字符数、结果是否报错；工具结果可以在后续增量扫描中再关联回来。

出处：`omp-stats/src/types.ts:211`；`src/db.ts:229`。

[读码] 按工具展示的 token 和费用，是把发起调用的 assistant 请求用量**平均分摊给该步的各个工具**：

```sql
TOTAL(COALESCE(m.total_tokens, 0) * 1.0 / t.calls_in_turn) AS total_tokens_share,
TOTAL(COALESCE(m.cost_total, 0) / t.calls_in_turn) AS cost_share
```

出处：`omp-stats/src/rollup.ts:113`。

[推断] 这能避免按工具求和时重复计算整次请求，但不是工具的真实边际成本。不能拿它认定某个工具“实际花了这些 token”。

### 2. 增量扫描不只记字节偏移

[读码] 每个文件游标包含 offset、设备／文件身份、创建时间、size、mtime、检查点 hash，以及当前位置的 service tier。扫描时检查文件是否被替换、变短、同大小改写或检查点变化；失效就从头重建。正常增量路径只读追加尾部。

出处：`omp-stats/src/parser.ts:494`、`:595`。

[读码] 同步用有界批次控制堆积：512 个文件或 8,192 行派生记录，文件元数据按 128 个一批读取。文件 I/O 不放进数据库事务；解析结果统一送入 `applySessionParseResults()` 的事务。进度回调在提交后触发。

出处：`omp-stats/src/aggregator.ts:61`、`:241`、`:320`；`src/db.ts:698`。

[推断] 这里好的地方是明确区分“已读到”和“已持久化”，既避免大事务包住文件 I/O，也避免界面显示完成后实际游标还没提交。

### 3. 费用不是简单乘当前单价

[读码] 定价区分“日志没有费用”和“日志明确记录了 0”。有按时间变化的价卡时，需要请求时间；无法恢复时间则标记 `cost_unpriced`，不能把那个 0 当免费。非零已记录费用和周期价卡中的明确零费用有保留规则，其他情况可能通过 catalog 补算。

出处：`omp-stats/src/types.ts:51`；`src/db.ts:439`、`:466`。

[读码] 解析器对缺失／畸形用量做规范化，但保留费用缺失语义；未完整结束的 assistant 消息，在没有终止原因时归为 error 或 aborted。

出处：`omp-stats/src/parser.ts:219`、`:266`、`:292`。

[读码] 本次读到的请求／工具统计表没有进程 RSS、私有内存、CPU 或长期增长采样字段；对统计源码搜索 `rss`、`memoryUsage` 也没找到对应实现。不能用这个包完成 B6 的进程资源测量。

出处：`omp-stats/src/types.ts:9`、`:211`；`src/db.ts:145`、`:229`。更广泛的系统资源监控是否存在于其他组件：没查全。

## 三、压缩：先区分文本摘要和 snapcompact

### 1. 常规压缩的触发与切点

[读码] core 默认压缩开启，保留最近 20,000 token，支持回合中途维护和自动续行。默认 reserve 为 16,384 token；有效 reserve 至少为上下文窗口的 15%。小窗口还会调整不合理的默认 reserve，避免预算被默认值吃光。

出处：`pi-agent-core/src/compaction/compaction.ts:200`、`:218`、`:322`、`:338`。

[读码] 阈值判断是 `contextTokens > thresholdTokens`。正的固定 token 阈值优先；固定值到达或超过真实窗口时退回可用 prompt 预算。压缩判断所用上下文取 provider 用量与本地存储会话估算的较大值，防止“线上请求变小了，本地历史却无限长”。

出处：`pi-agent-core/src/compaction/compaction.ts:352`、`:373`、`:388`。

```ts
export function compactionContextTokens(providerContextTokens: number, storedConversationEstimate: number): number {
    return Math.max(Math.max(0, providerContextTokens), Math.max(0, storedConversationEstimate));
}
```

出处：`pi-agent-core/src/compaction/compaction.ts:373`。

[读码] 切点可在 user 或 assistant 消息处，不能落在 toolResult 上。从后向前按合法边界统计完整 assistant／工具组；最新一组即使超预算也保留，不再塞入会导致超预算的更老一组。允许拆开一个长用户回合，因此另记这个回合的起始位置和被压掉的前半段。

出处：`pi-agent-core/src/compaction/compaction.ts:440`、`:525`。

[读码] preparation 根据 provider 实际 prompt 用量与本地估算的比例，必要时缩小保留预算；产物明确分开历史、被拆回合的前缀和最近原文，还携带旧摘要、切点 ID、文件操作等数据。

出处：`pi-agent-core/src/compaction/compaction.ts:1461`、`:1481`、`:1514`。

### 2. 文本摘要怎样拼

[读码] 常规摘要先把消息序列化成对话文本，再生成摘要，避免模型把材料当成待续写对话。输入大于摘要模型预算时按窗口折叠：每一窗更新前一窗得到的摘要，而不是一次塞进超长材料。历史摘要输出预算为 `min(floor(0.8 × reserve), 16384)`。

出处：`pi-agent-core/src/compaction/compaction.ts:894`。

[读码] 拆回合时并行生成“旧历史摘要”和“当前回合前缀摘要”，后者放在 `Turn Context (split turn)` 下；之后生成最多 512 token 的短摘要，并把读取／修改的文件清单由代码附入。

出处：`pi-agent-core/src/compaction/compaction.ts:1217`、`:2190`、`:2230`；`snapcompact/src/snapcompact.ts:753`、`:796`。

[推断] 文件清单由代码生成，比要求模型自己完整记住所有读写路径更可核对；额外短摘要和拆回合摘要也意味着一次压缩可能产生多次模型调用，测费用时必须全部算入。

### 3. snapcompact 的实际机制

[读码] snapcompact 不调用模型写语义摘要。它把被压历史序列化、规范化，再排成 PNG；返回的 summary 是解释这些图像如何阅读的模板文字，图片与归档原文放入 `preserveData.snapcompact`。

出处：`snapcompact/src/snapcompact.ts:2348`；`pi-coding-agent/src/session/compact-modes.ts:51`。

[读码] 再压缩时，把上一份归档保留的源文本接到新历史前面，重新排版；不会把旧图片逐层套进新图片。归档不够大时可全部保留为文本；较大时保留文本首尾，中间用图片。图片仍超预算时，布局会删掉较老的中间内容，并累计 `truncatedChars`。

出处：`snapcompact/src/snapcompact.ts:2122`、`:2348`。

[读码] 它不是无损保留：

- 工具结果默认最多 2,000 字符。
- 每个工具参数值默认最多 500 字符。
- 单个调用参数序列默认最多 2,000 字符。
- 截断默认保留 60% 头部、40% 尾部。
- 归档图片还受布局、数量、字节和模型能力约束。

出处：`snapcompact/src/snapcompact.ts:813`、`:1011`、`:2122`。

[读码] 引擎图片上限默认 80，但宿主会继续按 provider 图片数和字节预算收紧；未知 provider 的图片数预算默认 5，未知部署的归档 base64 字节预算默认 3,000,000。已知 inline-image 字节预算时取其一半。不能把“80 帧”理解成每家模型都实际发送 80 张。

出处：`snapcompact/src/snapcompact.ts:503`、`:528`、`:542`、`:579`。

[读码] 宿主仅在模型确实能在线路上接收图像时考虑 snapcompact；处理字节／payload 超限时会跳过它，避免用图片把请求体进一步放大。维护层还设有 0.8 的恢复带和 0.6 的 snapcompact 压后目标，防止压完仍贴着触发点反复压。

出处：`pi-coding-agent/src/session/session-maintenance.ts:183`、`:323`。

[推断] 它省去当次摘要模型调用，却会让后续请求持续携带图像 token 和图片字节；收益必须按多轮总费用、缓存、识读正确率和网络传输一起量。不能从“无摘要调用”推出“整体更省”。

### 4. 压缩遇到插话、新消息和后台结果

[读码] 手动压缩有独立 AbortController，拒绝重复启动；开始前取消后台预压缩，断开 agent 订阅并停止当前回合。摘要完成后、提交前检查取消状态。

出处：`pi-coding-agent/src/session/session-maintenance.ts:1138`、`:1186`、`:1197`、`:1545`。

[读码] `finally` 恢复订阅、清掉压缩状态，再主动排空滞留的 steer／follow-up。若本次确实打断了正在执行的回合，还根据 generation 和新 prompt 是否已接管，决定是否恢复旧工作。

出处：`pi-coding-agent/src/session/session-maintenance.ts:1604`、`:1994`、`:2028`。

[读码] 后台预压缩在阈值前启动，保存分支快照叶子 ID，生成后只进入 armed 状态，不立即改历史。真正使用前检查：

- 快照叶子仍在当前分支。
- 后面没有新 compaction 或 reset boundary。
- provider 专用保留数据仍能由当前模型重放。
- 新增尾部不会使结果失去必要空间。

存在 `session_before_compact` 处理器时禁用这种预压缩，保留处理器的阻止／替换语义。后台 provider 请求使用独立 session ID，避免与主流式请求共用粘性会话。

出处：`pi-coding-agent/src/session/session-maintenance.ts:2125`、`:2145`、`:2272`、`:2357`。

[推断] 真正值得借的是“计算结果”和“提交历史”分离，并在提交时校验来源仍有效；后台摘要本身则会增加取消、过期结果和无效费用的处理成本。

## 四、记忆：pi-mnemopi 怎样存、召回和接入循环

### 1. 存储与写入

[读码] `pi-mnemopi` 是本地 SQLite 记忆引擎。连接启用 foreign keys、5 秒 busy timeout，文件库启用 WAL。主要数据包括工作记忆、情景记忆、scratchpad、提取事实；工作和情景记忆有 FTS5 索引。

出处：`pi-mnemopi/src/db.ts:79`、`:92`；`src/core/beam/schema.ts:24`、`:131`。

[读码] 工作／情景记忆字段不止 content：还有 session、source、importance、veracity、memory type、有效期、替代关系、scope、作者、channel、trust tier、召回次数及事件时间。情景记忆还带摘要来源、降级 tier、binary vector。

出处：`pi-mnemopi/src/core/beam/schema.ts:24`、`:59`。

[读码] `remember()` 先在同一 session 内按完整 content 查重；重复时更新已有条目，新内容同步写工作记忆，再安排后台 embedding。`extract: true` 时另排事实抽取，抽取 Promise 被跟踪以便退出时等待。存储原文、抽取材料、embedding／FTS 材料可以分别传入。

出处：`pi-mnemopi/src/core/beam/store.ts:153`、`:322`、`:434`、`:500`、`:543`。

### 2. 召回是多信号排序

[读码] 普通召回组合 FTS、向量、关键词、重要度、近期衰减和可信度；工作记忆与情景记忆使用不同计分公式。已过期和已被替代条目被排除，scope 按 session／global／channel 等条件计算。增强召回默认在其内部开启意图调整、同义词与 MMR，并可混入提取事实。

[读码] 另有可选 polyphonic 路径，把混合排序、向量、图、事实、时间等“声音”做倒数排名融合。此次未逐一展开各 voice 的实现，不把它的效果或复杂度收益当作已验证结论。

### 3. 检索缓存处理了范围、写入和时间变化

## 六、另外两个值得借的设计

### 1. 提交边界比异步任务本身更重要

[读码] 三个模块使用相似边界：统计提交后才报告进度；记忆 commit 后才认定首轮召回完成；后台压缩校验分支后才改历史。

出处：`omp-stats/src/aggregator.ts:320`；`pi-coding-agent/src/mnemopi/state.ts:668`；`src/session/session-maintenance.ts:2357`。

[推断] 它们共同解决“事情算完了，但不代表结果还能用或已经交付”。借这条原则，比借一套通用异步任务抽象更直接。

### 2. 区分三种数据：保存的、模型看到的、界面展示的

[读码] snapcompact 保存归档源文本，按 provider 预算选择发送图片；mnemopi 分开原始 transcript、抽取材料和 embedding 材料；UI 可以合并快照而保留语音增量；工具费用明确是分摊数。

出处：`snapcompact/src/snapcompact.ts:2348`；`pi-coding-agent/src/mnemopi/state.ts:721`；`src/modes/controllers/event-controller.ts:875`；`omp-stats/src/rollup.ts:113`。

[推断] 这些做法让优化不必污染证据。评测也应明确记录“原始事件”“实际请求”“展示结果”，避免拿展示预览判工具输出完整性，或拿估算费用当实际扣费。

[推断] 借 omp 的流式原则：累计快照可保留最新值，原始 delta 必须拼接保全，工具完成和回合终结前先 flush；适合在展示边界合帧，不改模型历史或评测原始记录。

[推断] B6 内存比较同时报告“后台主进程”与“所需进程树总量”。omp 的共享 embedding 服务和 Sumika 的 Python 服务都不能被漏算；共享服务是否已热启动也要注明。

[推断] 启动比较分冷进程、热共享服务、完整冷依赖三种条件；分别记首帧和可处理请求。不能拿 omp 的预绘输入框时间对比 Go 后台完成全部初始化的时间。

[推断] 暂不为了追随 omp 增加原生模块边界。Go 已能直接完成不少 CPU 工作，是否需要替换搜索、tokenizer 或向量计算，应由同一回放中的 CPU 和耗时证据决定。

### 5. 和 omp 比：保留 Bun 基线，另列两种公平比较

[读码] 当前过线表明确以 Bun 同模型为基线，B6 另有绝对门槛；omp 是新增参照，不能替换原验收对象。

出处：`docs/规格-Go后台.md:371`。

[推断] 建议结果分开列：

| 比较 | 固定条件 | 解释范围 |
|---|---|---|
| 内核比较 | 相同模型路由、输入历史、提示词、工具声明／实现、采样参数、回放响应 | 请求构造、调度、持久化和本机处理开销 |
