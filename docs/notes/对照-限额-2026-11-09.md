## 先说结论（回答用户那两句）

**一、"回复一般直接跟着模型设置走是不是就行了"：是，而且数据源本来就有。**

- 所有会发单次输出上限的家，默认值都取模型目录里的 `output` 上限，只是在上下文剩余空间不够时往下压：
  - opencode 取 `limit.output`，没有就 32k，封顶 256k（`core/src/session/model-request.ts:54-56,95-103`）。
  - pi 取 `model.maxTokens` 再按上下文余量压（`ai/src/api/simple-options.ts:26-35,59`）。
  - omp 取 `model.maxTokens ?? undefined`，没有就不发（`ai/src/stream.ts:1802`）。
  - Codex 的 Responses 请求体里根本没有这个字段（`codex-api/src/common.rs:287-314`）。
  - Hermes 默认 `None` 不发，只有用户设了、或恢复流程临时抬高才发（`agent/transports/chat_completions.py:376-386`）。
- **没有任何一家有"固定的每请求输出预算"这种旋钮去盖住目录值。** Sumika 有。
- Sumika 的数据源其实够：我只读地请求了本机 Magpie 的 `/v1/models`（没读任何聊天），51 个模型里 **50 个同时报了** `context_length`、`context_window`、`max_input_tokens`、`max_output_tokens`（例：haiku-5-5 是 1000000 / 128000，deepseek-flash 是 1000000 / 232000，beam-free 是 131072 / 32768）【实测】。
- 问题出在上面再叠了一层固定值：`turn/loop.go:337` 先取 `min(模型报的 maxOut, 窗口余量)`，`modelcall/client.go:151` 再 `min(c.RequestOutputTokens, ...)`，`client.go:152-154` 又和请求自带的值取小。所以固定的 4096（main）或 32768（额度分支本地）只要比模型值小就赢。模型值读进来了（`turn/turn.go:340-344` 的 `limits()`），但被盖住。
- **推论**：实跑记录里 b2-11 的 502"空回复（输出在思考里被截断）"、重试 5 次烧 20630 输出令牌，就是这个 4096 盖章造成的，不是缺目录数据。额度分支把它改成 32768 是治标：同一个 DeepSeek 一次请求用了 19592 输出，换个想得更多的模型照样撞。
- 副作用要注意：账本预留按"这次请求要的输出上限"扣 `maxOutputTokens`（`turnbudget/ledger.go` 的 `Reserve`，预留里带 `OutputTokens`）。直接用模型值 232000，一次预留就吃掉 524288 的近一半。所以要么账本预留改成"实际用多少扣多少、预留只防并发"，要么保留一个**上限**（只在模型没报或数值离谱时才生效），不是现在这种下限式的预算。

**二、"models.dev / 请求返回的内容"**：两件事要分开。

1. 请求返回（服务商 `/models`）：Sumika 已经在读，对 Magpie 够用，**不需要新数据源就能让单次输出跟着模型走**。
2. models.dev：opencode、omp、pi 三家都用它做**目录**。
   - opencode 运行时每 5 分钟刷新一次，并带一份打包快照（`models-dev.ts:551,667,691-692`）。
   - omp 在 `catalog/scripts/generate-models.ts` 和 `catalog/src/model-manager.ts` 用。
   - pi 在构建期 `ai/catalog/build.ts` 生成，未报告时默认 4096（`ai/catalog/define.ts:132`）。
   - Hermes 的上下文长度解析顺序里 models.dev 排第 5 位，前面是用户配置、端点 `/models`、本地探测（`agent/model_metadata.py:2215-2220`）。
   - Codex 用自己后端的 `/models`（`protocol/src/openai_models.rs:428` 起的 `ModelInfo`）。
3. **所以 `docs/规格-模型配置.md` 拍板问题 9（"第一版不内置、不联网取 models.dev"，第 21 行）在同行里是少数派选择**。不过对"回复跟着模型走"这个具体问题它无关紧要（上面已证明 Magpie 报全了）。models.dev 的价值在直连其他服务商、且对方 `/models` 不报能力的时候（例如 OpenAI 官方的 `/v1/models` 不带上下文长度，这一点是我的印象，没在本次核实）。要加就按那条规格自己写的"以后作为可选导入，不当默认"，排在"服务商报告"和"手填"之后。价格数据同理：`maxCostMicros` 现在被迫禁用，就是因为没有可证明的价格上界，这是 models.dev 之类数据能补的另一个洞。

## Sumika 哪些默认值"不标准"，哪些有道理保留

按每个旋钮单独判，不按组。"标准"的意思是至少有两家同类做法。

### 不标准，建议改

1. **`requestOutputTokens`（4096 / 32768）及子代理三个定义里写死的 `MaxOutputTokens: 32768`**。所有场合都不标准，没有任何同行有这个旋钮。建议改成：默认跟模型报的 `max_output_tokens`，再按窗口余量压（opencode、pi 的做法）；模型没报时才用兜底（opencode 32k、omp 64k、pi 4096～16384，各家不同，选一个并写进配置说明）；配置项保留，但语义改成**可选的封顶**，不是预算。账本预留要同步改（见上文"副作用"）。实跑里的 502 空回复就是这里造成的。
2. **`limits()` 里"没报按 8000"**（`turn/turn.go:340-344`）。模型没报输出上限时 8000 比所有同行的兜底都低（opencode 32k、omp 64k、pi 默认 16384 或 4096 视来源），对思考型模型尤其容易被思考吃光。Magpie 这边 50/51 报了，所以影响面是没报的那一个和以后的直连服务商，但应该一并改。
3. **纯文字 stop=length 不续写、也不提示（main）**。少数派，不算"非标准"：opencode、Hermes、omp、Claude Code 都续写或有恢复流程，只有 pi 也不续。额度分支加了提示，用户回"继续"，是 pi 那一档；用户已经问过"回复到上限，跟着模型设置走不就行了"，说明他不想手动续。建议：先让单次输出跟着模型走（第 1 条做完，纯文字撞上限的概率会大降），再按 opencode 的做法加最多 2 次自动续写，计预算。
4. **交互式主窗口默认开 `maxRequests`**（main 24、分支 120）。非标准：主智能体没有请求次数上限的是 Codex、opencode（`steps` 默认不设）、omp、pi、Claude Code 交互模式；只有 Hermes 默认开且是 500。120 比 Hermes 低，但比 24 合理得多。如果要留，建议当"软提醒 + 到 1.5 倍停"（omp 子智能体的做法），不要硬拒。
5. **`maxTools` 作为硬上限**：没人这么做；Hermes 是按类型封顶（搜索 50、子智能体 50）。本地私聊建议去掉或放到很大，只保留重复调用提醒和审批。无人值守场合作为兜底可以留。
6. **`maxTokens` 累计令牌上限**：同行里**没有**这个东西，没法说标不标准。实测里缓存命中占 90%，数字含义很怪（"经过模型的总量"，不是花的钱），现在 8000000 这个数是实测凑出来的，换模型、换缓存命中率就变。同行的对应物是"费用上限"（omp 的 `session.maxCost`、Claude Code 的 `--max-budget-usd`），要靠价格数据，而 Sumika 目前没有可证明的价格上界（`maxCostMicros` 被迫禁用），所以要等 models.dev 之类的价格数据，或服务商返回的用量金额。
7. **`maxDurationMs` 默认开**：Hermes 有但默认关，omp、Codex、opencode、pi 都没有。本地私聊 60 分钟比 15 分钟合理，但仍是少数派；建议主窗口默认不设，保留可选。

### 标准，不用动

- **`agent.context.*` 整体**：窗口取自服务商 `/models`（和 Codex、opencode、omp、pi、Hermes 同路），硬线 min(0.85×窗口, 窗口−16384) 落在同行区间内（pi 窗口−16384；opencode 15% 且至少 16k；omp 15%；Codex 90%；Hermes 50%～75%）；软线占位旧工具结果是额外做法，不冲突。"未报告按 128000"也没问题，Claude Code 对未知模型也是警告加兜底 200K（`CHANGELOG.md:207`），界面上标出"未报告"即可（规格-模型配置已写）。
- **重复调用提醒 3/5/8**（`turn/guard.go:15`）：介于 omp 的 5 和 Hermes 的 2/5 之间，只提醒不停也和 Hermes"警告不阻止"一致。
- **带工具调用的 length 不执行、要求重发**：和 pi、Codex、Hermes 一致。
- **读文件 2000 行 / 50KB、命令输出尾 2000 行 / 50KB、命令默认 120 秒上限 600**：和 pi、opencode 基本一致；omp 300/3600、Hermes 180 是不同选择，Codex 10 秒是偏低的另类。不必改。

### 因为 QQ 和群聊有道理，建议保留（顶层 `agent.budget.*`：24 / 60 / 524288 / 15 分钟）

- 不是"标准"，但有同类依据：**无人值守场合默认开硬停**。Hermes 的 `non_interactive_hard_stop_enabled=True`（网关和定时任务默认硬停，交互平台默认关，`tool_guardrails.py:124`），omp 对子智能体默认开 200 次软预算。群里一条消息不该烧掉很多请求，也没有主人逐次看着。
- 自动轮（目标续轮、定期任务）用顶层窄额度、不用本地宽额度：额度分支的 `LimitsForInput` 已经这样分了，合理。
- 这一档**只有"次数、工具数、时限"有道理**；"单次输出 4096"在群里也不该是固定值：群聊回复本来就短，模型报多少都用不到；真正要防的是思考吃光输出，每轮次数加累计输出就够。所以单次输出跟模型走对 QQ、群聊也成立，不用为了群聊保留 4096。
- 群聊并发和预算的关系要再看：单次输出放宽后账本预留变大，同一根下并发请求可能互相挤占，第 1 条落地时单独验。

## 与"标准 harness"的几处结构差异（供后面讨论，不在本任务范围）

- 同行的"防跑飞"几乎都放在**循环侧**（重复检测、用户打断、可选的次数或费用上限，默认关），Sumika 把它做成**账本侧**的四项硬额度默认开。账本的好处是持久化、重启后不重置、能挡子代理；代价是上面几条默认值都得人调。
- 同行的"目录"是**数据**（每个模型有 context、output、输入模态），默认值都从数据派生；Sumika 的额度是**配置**，不从数据派生。这一条是用户那句"写死了不合适"的实质。
- Hermes 的做法最值得借一部分：同一套限额分"交互 / 无人值守"，只在无人值守默认硬停；Sumika 的"本地 / 渠道"分法和它同构，只是分的是额度大小，不是"提醒还是硬停"。
