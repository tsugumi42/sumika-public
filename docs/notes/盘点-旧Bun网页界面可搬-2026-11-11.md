## 2. 外观：好看在哪、和现在的令牌对照

### 2.1 旧版本身（`tokens.css`、`chat.css`，截图）

- **色**：中性色是 `oklch` 阶梯，色相 250、彩度 0.008（`tokens.css:49-50`，“冷”档），浅色 n1 `0.993` 到 n12 `0.25`、深色自成一套不是倒过来；底色三档（`--surface` = n1、`--bg` = n2、`--sunken` = n3），竖栏 `--rail` 比列表再深一档（`:75`）。**角色色** `--char` 一个，往外派生 `--a1…a12`，主按钮 = a9、你的气泡 = a3 + a7 细边（`.su-msg[data-side="me"] { --bub: var(--accent-soft) }`，`chat.css:115`）；群友每人一个色相（`Outside.tsx:18`，`oklch(0.73 0.1 hue)`）。语义色 danger / warn / ok 各带 soft / text 三档。

- **间距圆角**：基础单位 `--g` = 8 × ts；圆角最里层 `--r` = 20 × ts；往外同心：`--r-1 = r + 6`（气泡）、`--r-2 = r-1 + g`（卡片）、`--r-win = r-2 + g`。气泡内边距 `1.6g × 0.9g`；连续相同发言者间距 `--s1`，组间 `--s3`。

## 3. 卡顿的根子

先说证据的分层，免得混：

- **滚动**那一项（11-04 连续滚动 >33 ms 的帧 220～250 对 1）**有 trace 级证据**：`fix/lazy-imports` 的 README 在同一份 17,950 条消息、同一台机器上做了 Chrome trace 分解和逐项样式消融。`[实测]`
- **读旧历史**那一项（P95 120～130 ms）11-04 笔记写“原因没定位”，下面第 3.2 条是我读码推出的最像来源，**没有 trace 验证**，只能标 `[读码]` + 因果 `[推测]`。
- **流式**（10-26 P6 最卡一帧约 87 ms）用到的是本地私聊那条路径（Streamdown），不是 QQ 只读那条，第 3.4 条单列。

### 3.1 滚动：是样式光栅化，不是 React `[实测]`+`[读码]`，写法问题

存档证据（`sumika-bun@ README.md`“时间花在哪里”）：滚动起点后固定 2 秒，主线程共 1939 ms，JS 626（32%）、布局 345（18%）、样式 282（15%）、绘制 223（12%）、合成 149（8%）、GC 27（1%）；`CrGpuMain` 873 ms 另算。**逐项样式消融**（同一 180 步，rAF P95 / GPU 主线程片段）：原样 24.9 ms / 873；**禁用滤镜 20.9 / 744**；**去阴影 16.7 / 602**；去背景 24.9 / 855（没变）；**去“列表内圆角”16.7 / 539**。最终三版本复核后整窗 P95 仍约 25 ms，README 自己的结论是“阴影 / 圆角 / 滤镜栅格化仍是大头”。React 那侧：`ChatFrame` 滚动期重画 375→1 次（修过之后），`VirtualList` 每 180 步 365～371 次 commit，主要是新行挂载。

对应到代码（默认外观下都生效，因为默认 `material: liquid`、`wallpaper: soft`、`corner: squircle`、`elevation: shadow`，`appearance.ts:36-58`）：

### 3.2 读旧历史：每翻一页把整段历史重算一遍 `[读码]`，因果 `[推测]`，写法问题 + 一处结构问题

QQ 页每读一页（`PAGE = 200`，`qq.ts:87`）会整段重做：

1. `qq.ts:201-202`：`[...t.events, ...now.events]` 去重再 `.sort(...)`，复制并排序全部已载入事件（约 2 万条）；91 页读完累计约 91 × 2 万；实时推送一条也一样（`qq.ts:230` 复制 + 排序）。
2. `Outside.tsx:332` `const list = withDays(items(t, …))` **没有 memo**，每次渲染都跑 `items()`（`:219-277`）：
   - `:227` `t.events.flatMap(…)` 扫全部事件，对通知调用 `parseSegs`；`:229` `t.events.filter`；`likesOf`（`:99`）又扫一遍全部事件并对通知 `parseSegs`；
   - **`qq.ts:48` `parseSegs` 每次都 `JSON.parse(e.segments_json)`，不缓存**——约 2,290 条通知 × 两处，每翻一页重解析一遍；
   - `:239` 对每一组 `group.map(<Message …/>)` 建出**全部消息**的 React 元素（约 1.8 万个），虽然虚拟列表只挂十几项，元素对象和闭包全建了；
   - `qq.ts:137` `eventById` 是线性 `find`（`fix/lazy-imports:a5a7ab8` 已改 WeakMap 索引，其微基准 1 万次查询 312～389 → 0.95～3.44 ms，首轮含建索引）。
3. `chat.tsx:291-293` `VirtualList` 每次渲染 `items.filter(it => !seen.has(it.key))` 并在有新增时 `new Set([...seen, ...added])`，O(N)（`152939c` 已改成数组引用没变就复用）。
4. `Outside.tsx:279-297`：`useEffect(() => markRead(conversation), [conversation, count])` 每来一条消息就 POST 一次已读。

11-04 的现象是读历史期间三遍都有超过 100 ms 的帧间隔（`对照-架构A与C-实测` 第 150 行），时间上和“每页一次整段重算”对得上；17,950 条消息 + 2,290 条通知也正是第 1、2 条的规模。**但这一条没有 trace 证明**，而且 `fix/lazy-imports` 修了第 3 条和 `eventById` 之后只量了滚动、没有重量读历史，所以不能说“已知就是它”。

- `parseSegs` 不缓存、`items()` 不 memo、排序全量：**写法问题，能改**。解析在入库时做一次（事件对象上挂已解析的 `meta`）、分组和 `likes` / `recalled` 按事件增量维护，前插一页只处理这 200 条。
- `ChatItem.node` 是**预先建好的 ReactNode**（`chat.tsx:21`、`Outside.tsx:239`）：列表接口让调用方一次建全部元素。这是**结构问题**，旧 `ChatFrame` 不能原样搬；新 `MessageList` 的做法（`items` 是数据，`useVirtualizer` 的 `getItemKey` / 渲染回调只对可见项取）才对。所以搬的时候消息渲染**不搬 `ChatFrame`/`VirtualList`，搬它周围的行为**（第 4 节）。

## 5. 搬法建议（最多 6 条）

1. **先搬令牌映射层 + `@font-face` + 滚动条样式 + 缺的令牌**。一个 `desktop/src/web/ui.css`：旧用途名（`--surface`、`--text-2`、`--accent-soft`……）一对一映射到 `--color-*` / `--dim-*`；补令牌 JSON 里缺的（`focus`、`warn*`、`ok-soft`、`danger-soft`、角色色阶梯、`elevation.*`、`z-*`、代码高亮色）后重新生成；加三个 override 的 `@font-face`。**收益最大、风险最低**：之后每一块搬过来都不用再改颜色。
2. **消息列补全旧版独有的内容，行为用库的选项**：头像（4.1）、系统行、你的气泡强调色、引用块、表情回应小胶囊、媒体卡，滚动补偿换 `anchorTo` / `shouldAdjustScrollPositionOnItemSizeChange` / `userScrolled`，加跨天分隔和日期胶囊。**每加一类视觉就量一次 P1～P4**，不一次全加（3.1 的结论：卡不卡取决于样式，不取决于 React）。
3. **数据层先于视觉：解析在入库时做一次**。事件进仓库时把 `segments_json` 解析成对象、建 `id → 事件` 的 `Map`、增量维护 `likes` / `recalled`；前插一页只处理 200 条，不整段重排（3.2）。这是新仓库（`conv.ts`）的设计要求，不是旧代码的搬运；旧 `Outside.tsx:99-137,219-277` 只当“规则清单”读（5 分钟→15 分钟窗口、撤回、不是她说的合并提示、`origin` 的几种）。
4. **玻璃、阴影、圆角过渡一律先在一个小范围试**：顶栏 + 输入框两条玻璃、不叠；气泡和卡片不要阴影，用 `--color-sunken` 等底色差分层（总则第四节“分界优先留白和底色，其次细边，最后阴影”）；超椭圆只试标题条；各自量 P1（规格第三节）后再进主干。旧的三层渐进模糊和滚动区蒙版**不搬**，要淡出效果用输入框 / 顶栏本身的渐变背景。
5. **第 3 步的组件按“结构用旧的、实现用原生”搬**：输入框胶囊（斜杠、插话 / 排队、计划条）、思考 / 工具 / 审批卡（旧截图最完整）、会话列表滑动选中块、右栏标签。写每个之前先查 `.claude/skills/modern-web-guidance`：弹层和菜单用 `popover` / `dialog` + anchor positioning（旧版是 React Aria Popover，可留库做无障碍）、展开收起用 `grid-template-rows`、选中块滑动用 `view-transition` 或 `anchor-name`、屏幕外长块 `content-visibility: auto`。具体 API 名我没查 skill，`[推测]`，实现时以它为准。
6. **画廊和视觉回归先于功能铺开**：把旧 `web/visual/` 的状态矩阵（平时 / 悬停 / 按下 / 焦点 / 选中 / 不可用 × 亮暗 × 字号圆角疏密）改成 `desktop/` 的页面，几何检查（四边等距、同心圆角）用 Playwright 量 DOM 框（规格 V5）。旧画廊的截图基线整套作废（尺寸圆角都变了），但画廊文件的组织方式能省掉一大块。
