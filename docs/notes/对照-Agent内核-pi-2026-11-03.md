# 1. 回合循环：两边都是循环，区别在运行边界

**pi 怎么做。[读码]**

底层是双层 `while`，并不是持久状态机：

- 内层处理一次模型回复、整批工具调用、插话；有工具或插话便继续。
- 外层在自然停止时检查 follow-up 队列。
- `finishTurn` 可以明确要求继续或结束。
- `prepareRequest` 在每次请求前更新有效上下文、模型、思考档位；`prepareNextTurn` 在步骤之间处理压缩等准备工作。
- `agentLoopContinue` 允许不添加新用户消息地续跑，但要求上下文末尾适合继续请求。

出处：agent-loop.ts:176（私有存档）、agent-loop.ts:249（私有存档）、agent.ts:395（私有存档）。

coding agent 外面还有一层运行管理：底层循环结束后，判断是否重试、压缩恢复、处理结束边界中新来的输入，最后才发 `agent_settled`。因此，pi 的 `turn_end` 是“一次模型回复加工具结果结束”，`agent_end` 是“这次底层循环结束”，两者都不能直接等同于产品上的“整轮完成”。

出处：agent-session.ts:1894（私有存档）、agent-session.ts:2000（私有存档）。

**Sumika 怎么做。[读码]**

`Hub` 按角色和会话排队；`Live` 保存热上下文、当前运行、插话和压缩等状态。`runTurn` 用 `for step := 0; ; step++` 交替请求模型与执行工具，没有工具、也没有送达插话时返回。

`respond` 统一生成回合 ID，记录开始，并通过入口处的 `defer` 发一次 `Settled`，覆盖读卡、建实例等提前失败。这个“整轮定了”的语义比直接暴露底层步骤完成更适合渠道中间件。

出处：[hub.go:31](仓库根/native/internal/turn/hub.go:31)、[hub.go:263](仓库根/native/internal/turn/hub.go:263)、[hub.go:532](仓库根/native/internal/turn/hub.go:532)、[hub.go:1376](仓库根/native/internal/turn/hub.go:1376)、[hub.go:1537](仓库根/native/internal/turn/hub.go:1537)。

**差在思路哪里。**

pi 明确分出“执行一次循环”和“让一次产品运行真正结束”。Sumika 已有后者的核心语义，但实例、请求准备、重试、压缩恢复、历史接纳和渠道交回集中在 Hub 内，边界主要靠字段、条件和调用顺序维持。

**值不值得学、怎么转换。**

值得借**运行边界和请求准备边界**，不需要换状态机框架。继续保留 `Respond → Settled`；以后整理 Hub 时，让下一次请求的有效配置与上下文形成明确结果，减少 `runTurn` 中途读取和修改多处状态。

pi 当前也没有从这套普通循环自动得到整轮预算。不能把“换成 pi 的循环”当作请求数、工具数或累计消耗有界的方案。

# 2. 事件与流式：统一类型有价值，仍需补上宿主身份和恢复语义

**pi 怎么做。[读码]**

`AgentEvent` 是统一的判别联合，覆盖：

- Agent 与步骤开始、结束；
- 消息开始、增量、结束；
- 工具开始、进度、结束。

正文、思考、工具参数增量都通过同一消息更新协议传播。`Agent` 先更新内部状态，再逐个等待订阅者；RPC 还挂了等待 stdout 排空的订阅者，将消费者背压传回执行路径。

出处：types.ts:528（私有存档）、agent-loop.ts:423（私有存档）、agent.ts:602（私有存档）、rpc-mode.ts:353（私有存档）。

但它不是可断点续传的事件日志：

- 通用 `EventStream` 在进程内排队，没有持久游标。
- 普通 Agent 事件本身不带完整的角色、会话、回合身份，订阅对象隐含了归属。
- RPC 可以取 `get_state`、`get_messages` 重建状态；这不等于按增量 offset 重放。

出处：event-stream.ts:25（私有存档）、rpc-mode.ts:448（私有存档）、rpc-mode.ts:672（私有存档）。

**Sumika 怎么做。[读码]**

当前至少有三种通知机制：

1. 回合流式回调：`OnDelta`、`OnTool`、`OnSteer`、`OnCompacting`。
2. 插件通知：`Seen`、`Settled`，每个订阅者独立排队。
3. 桌面已提交数据：store 发失效身份，`desktopread` 重新读库后发布带版本的快照。

审批另有较完整的 `Snapshot/Subscribe`：注册与状态重放原子衔接，按审批 ID 和版本合并，防止旧等待状态覆盖新结局。

出处：[turn.go:68](仓库根/native/internal/turn/turn.go:68)、[plugin.go:177](仓库根/native/internal/turn/plugin.go:177)、[changes.go:7](仓库根/native/internal/store/changes.go:7)、[service.go:218](仓库根/native/internal/desktopread/service.go:218)、[subscribe.go:40](仓库根/native/internal/approval/subscribe.go:40)。

**差在思路哪里。**

pi 的优势是**一次运行内的协议完整**；Sumika 的优势是已有**从已提交状态恢复消费者**的做法。两边都不能直接解决 Sumika 一个 Hub 同时服务多个角色、会话的事件归属。

**值不值得学、怎么转换。**

借 pi 的统一事件类型，借 Sumika 自己审批的“快照加后续变化”语义：

- 所有运行事件带同一份角色、会话、回合身份，工具事件再带调用 ID。
- 区分临时输出、执行结局、已提交聊天。
- 重连先取当前运行快照，再接后续事件；不必为了刷新窗口持久化每个 token。
- 不能把任意慢 UI 放进必须等待的执行订阅链；也不能把不可恢复的正文增量静默丢弃。

这比新增一个全局消息总线更贴近当前问题。

# 3. 会话与状态持久化：最值得借的是投影，不是 JSONL 或树本身

**pi 怎么做。[读码]**

`SessionManager` 的 JSONL 条目带 `id/parentId`，当前 `leafId` 决定活动分支。消息、模型选择、思考档位、压缩、分支摘要、上下文编辑都能成为条目。

分支只移动 leaf，下一次追加形成新路径；旧条目保留。`context_edit` 也是追加一条“替换或省略某个旧条目在模型上下文中的贡献”，不改原始记录。

`buildSessionProjection` 将这些条目投影成模型消息，并保留每份贡献对应的 `sourceEntry`。普通上下文构造和压缩都能利用这个来源关系。

出处：session-manager.ts:57（私有存档）、session-manager.ts:544（私有存档）、session-manager.ts:1370（私有存档）、session-manager.ts:1590（私有存档）。

持久化在消息结束时追加；首次用户消息就会建立文件。加载时逐行解析，跳过坏行。**这只是会话恢复，不是正在执行的工具任务恢复；分支也不撤销文件修改或外部操作。**

出处：agent-session.ts:1157（私有存档）、session-manager.ts:1160（私有存档）、session-manager.ts:617（私有存档）。

**Sumika 怎么做。[读码]**

Go 当前是不同用途的几份记录：

- 平台所属库的顺序聊天事件；
- `context_epochs` 的摘要与原文接续点；
- trace 中的回合、步骤、模型调用；
- 热实例中的参考信息、工具调用和结果、思考等临时材料。

冷启动由 `history.For` 恢复“摘要加后续原文”或最近聊天；热实例通过 `catchUp` 追上已完成回合使用过的事件。渠道回合先产出候选句，裁决写库后再 `Commit`，把这一段实例历史照库重写。

出处：[history.go:155](仓库根/native/internal/history/history.go:155)、[turn.go:344](仓库根/native/internal/turn/turn.go:344)、[hub.go:1108](仓库根/native/internal/turn/hub.go:1108)、[hub.go:783](仓库根/native/internal/turn/hub.go:783)。

崩溃后 `SweepInterrupted` 将未结束回合记为 interrupted，执行中的工具记为结果未知，待审批工具记取消，不自动重放副作用。

出处：[turns.go:55](仓库根/native/internal/store/turns.go:55)。

**差在思路哪里。**

pi 把“模型当前应看到什么”做成会话条目的统一解释结果。Sumika 也有请求副本，但热实例、冷重建、压缩和渠道 Commit 分别承担一部分解释工作，一致性需要多条路径共同维持。

**值不值得学、怎么转换。**

**高收益：统一上下文投影及来源。** 保留 SQLite 和平台事实记录，让模型材料明确引用聊天 seq、步骤、工具结果、摘要和注入来源。

不建议把 QQ 原始记录树化。QQ 的引用关系描述“谁在接谁的话”，pi 的树描述“模型选择走哪条历史”，两者不是同一个概念。本地重新生成、话题探索以后可以有分支，但应建立在聊天事实记录之上。

# 4. 上下文管理：从“裁掉文本”走向“维护可继续的状态”

**pi 怎么做。[读码]**

当前 pi 有三项值得注意。

第一，提示词与工具集合也能沿 transcript 追加变化：`sections` 替换命名段落，`toolsAdded/toolsRemoved` 表达工具变化。支持中途 system 消息的 API 保留其位置，其他 API 折叠成当前有效的头部。

出处：types.ts:550（私有存档）、transcript.ts:59（私有存档）、transcript.ts:110（私有存档）。

第二，压缩维护工作检查点：目标、约束、进度、决定、下一步、关键上下文；允许切到一轮中间，但不把工具结果与调用拆开。摘要材料包括工具调用和截短的结果，省略思考，另保存读过、改过的文件清单。

出处：compaction.ts:389（私有存档）、compaction.ts:507（私有存档）、compaction.ts:952（私有存档）、utils.ts:122（私有存档）。

第三，用户输入和工具结果使用文本、图片内容块；图片在入口按模型限制归一化，换到不支持图片的模型时转换成明确占位。

出处：agent-session.ts:2082（私有存档）、transform-messages.ts:63（私有存档）。

**Sumika 怎么做。[读码]**

固定前缀按 core、角色卡、场合等拼接；参考信息按回合追加，插话送达时再追加。软门槛只替换当前请求中的旧长工具结果，原实例不动；硬门槛、提前压缩和实际溢出恢复各有路径。

出处：[turn.go:307](仓库根/native/internal/turn/turn.go:307)、[hub.go:1290](仓库根/native/internal/turn/hub.go:1290)、[slim.go:10](仓库根/native/internal/turn/slim.go:10)。

当前压缩材料有意滤掉参考信息、工具调用、工具结果和思考，使用 `compact-chat`。这符合可共享聊天摘要的原设计，却不适合保留完整工作进度。Go 的 `Input.Text` 和 `Msg.Text` 仍以文本为核心；渠道将附件排成描述或占位，记忆侧则有独立的图片说明结构。

出处：[compact.go:37](仓库根/native/internal/turn/compact.go:37)、[compact.go:180](仓库根/native/internal/turn/compact.go:180)、[line.go:108](仓库根/native/internal/channel/line.go:108)、[ports.go:17](仓库根/native/internal/memory/ports.go:17)。

**差在思路哪里。**

pi 压缩的是“继续工作的状态”；Sumika 当前主要压缩“已经聊过的话”。陪伴聊天需要保留约定、更正、人物关系和未完话题，不能直接套用文件清单式摘要；本地工作又不能只剩闲聊摘要。

**值不值得学、怎么转换。**

值得让**聊天摘要和工作检查点有不同的材料选择与保留契约**，共用已有压缩机制，不另写第二套循环。工作材料应保留操作结果与引用，聊天摘要继续保留关系和约定。

图片、附件以后宜保留类型与来源引用，渲染成文字或交给视觉模型由请求投影决定；不必把每个历史附件重复内嵌进上下文。

缓存方面，Sumika“每轮只追加”的选择有依据。pi 的动态 system 更新只在对应 API 支持时保住原位置；折叠头部仍可能改变前缀，不能承诺换成它就提高缓存命中。

# 5. 工具系统：共同执行管道值得借，权限与调度不能照搬

**pi 怎么做。[读码]**

工具统一描述 schema、执行函数、进度回调及结果：

- 执行前先整理参数，再按 JSON Schema 校验；校验器按 schema 缓存。
- 参数副本交给执行器，避免修改 transcript 中的原调用。
- 未知工具、校验失败、被拦、执行抛错，都变成模型可见的错误结果。
- `content` 给模型，`details` 给界面，`structuredContent` 给程序调用者；三者职责不同。

出处：validation.ts:6（私有存档）、validation.ts:59（私有存档）、agent-loop.ts:729（私有存档）、types.ts:424（私有存档）。

`runToolCall` 复用同一条参数准备、校验、调用前后钩子路径，供工具内部调用其他工具。Code Mode 也经这条路径执行，不能通过嵌套调用绕过已安装的权限钩子。

出处：agent-loop.ts:813（私有存档）、agent-session.ts:746（私有存档）。

但普通 pi 并未内建 Sumika 这种必经审批政策。没有 `tool_call` handler 就直接进入执行；仓库里的 permission gate 是示例。默认 read/bash 操作直接访问本机文件和子进程，不能称为默认沙箱。

出处：agent-session.ts:674（私有存档）、permission-gate.ts:10（私有存档）、read.ts:58（私有存档）、bash.ts:91（私有存档）。

**Sumika 怎么做。[读码]**

声明、政策、执行分在 `tools.Declaration`、`policy.Specs`、内置执行器或插件工具。执行前有统一审批关、当轮听众核验和逐工具总超时；插件工具必须在集中政策表登记，不能自行声明更宽权限。

参数入口做 JSON 解析、修复和 `Prepare`，当前这条调用路径没有像 pi 那样统一按声明 schema 校验；各工具仍自行处理参数。

出处：[tools.go:17](仓库根/native/internal/tools/tools.go:17)、[policy.go:66](仓库根/native/internal/policy/policy.go:66)、[loop.go:534](仓库根/native/internal/turn/loop.go:534)、[plugin.go:269](仓库根/native/internal/turn/plugin.go:269)、[exec.go:43](仓库根/native/internal/tools/exec.go:43)。

**差在思路哪里。**

pi 把工具接口同时面向模型、UI、程序消费者；Sumika 主要面向模型文本和步骤展示。Sumika 的宿主授权更明确，pi 的接口契约与程序组合能力更统一。

两边当前普通循环的调度其实相近：**任一工具要求串行便整批串行，否则整批并行**。pi 这里也用 `Promise.all`，不是可照搬的有界滚动调度器。

出处：agent-loop.ts:525（私有存档）、agent-loop.ts:660（私有存档）、[loop.go:536](仓库根/native/internal/turn/loop.go:536)。

**值不值得学、怎么转换。**

值得借统一参数校验、结果分层和单一执行入口。保留 `policy.Specs`、审批、Workspace、当轮听众核验。未来确有嵌套工具调用时，要求它再次进入这条入口；现在不用提前造组合框架。

长输出方面，pi 已将完整输出文件创建集中到一处，并用有界内存累计器保留展示尾部、必要时写全文。它仍使用系统临时文件，不是永久审计存储。Sumika 可以借集中所有权，但存放、续读、清理由自己的结果保留策略决定。

出处：output-accumulator.ts:28（私有存档）、output-files.ts:1（私有存档）、[write.go:245](仓库根/native/internal/store/write.go:245)。

# 6. 扩展模型：保留 Go 编译插件，借按需暴露和生命周期契约

**pi 怎么做。[读码]**

扩展是运行时加载的 TS/JS 工厂，通过 API 注册工具、钩子、命令和其他资源。普通事件按注册顺序调用，异常记录后继续；工具调用门的异常向执行路径传播并阻止该调用。会话替换或 reload 后，旧扩展上下文失效，再使用会报错。

出处：loader.ts:1（私有存档）、runner.ts:1087（私有存档）、runner.ts:1249（私有存档）、runner.ts:729（私有存档）。

当前 **MCP 已是内置扩展**，与 llama、codemode、tool-search 一起装配。MCP 支持 direct、deferred、codemode、hidden 等暴露方式；不是把所有远程工具 schema 永久塞进每次请求。技能也只先列名称、描述、位置，正文按需读取。

出处：extensions/index.ts:7（私有存档）、mcp/index.ts:4（私有存档）、skills.ts:357（私有存档）。

MCP 扩展自己管理会话取消、连接代次、后台工作和关闭等待。动态加载不代表安全隔离；普通扩展仍在宿主进程内运行。

出处：mcp/index.ts:310（私有存档）、mcp/index.ts:1252（私有存档）。

**Sumika 怎么做。[读码]**

`Plugin{ID, Setup}` 是编译进来的 Go 接口，注册返回撤销函数；有上下文贡献、Seen、Settled、工具、压缩前钩子。钩子有时限，停用后撤销注册、取消在途执行、丢弃失效结果。

`Contribution.OnAccepted` 还区分“插件算出了材料”和“材料真正进入模型上下文”，避免把超时或被丢弃的贡献记成已经给过。项目上下文插件已有按 `ContextID` 隔离的接纳账本。

出处：[plugin.go:29](仓库根/native/internal/turn/plugin.go:29)、[plugin.go:51](仓库根/native/internal/turn/plugin.go:51)、[plugin.go:344](仓库根/native/internal/turn/plugin.go:344)、[projectcontext/plugin.go:78](仓库根/native/internal/projectcontext/plugin.go:78)。

**差在思路哪里。**

Sumika 对自有 Go 插件的贡献接纳、取消和撤销已经有较清楚的契约。pi 更突出的是**扩展能力多时如何少暴露、按需发现**，不是“运行时加载”本身。

**值不值得学、怎么转换。**

不建议为了类似 pi 改成动态插件宿主。已有 Go 插件继续编译装配。

以后接 MCP，应把服务连接与远程工具映射作为适配层，工具执行仍进宿主政策。工具很多时再采用 deferred discovery；必须区分“模型发现并选中了工具”和“宿主允许执行工具”，不能拿暴露方式代替授权。

# 7. 子代理与多代理：普通 pi 是扩展示例，durable 才有持久任务所有权

**pi 怎么做。[读码]**

普通 coding agent 的 subagent 在 examples 中：

- 启动独立 pi 子进程，参数包含 `--mode json -p --no-session`；
- 给子进程独立任务与追加提示词，可选择模型、工具和 cwd；
- 读取 JSON 事件，汇总正文、错误与 usage；
- 提供单个、并行、链式模式；
- 示例限制最多 8 个并行任务，执行并发 4。

出处：subagent/index.ts:34（私有存档）、subagent/index.ts:298（私有存档）、subagent/index.ts:343（私有存档）、subagent/index.ts:643（私有存档）。

这是独立上下文和结果回收示例，**不是默认启用的持久工单系统**；独立进程也不意味着工作目录、文件权限或凭据已经隔离。

独立的 durable 则把任务归属、子会话、等待和结束条件建模出来。任务可以是 pending、running、waiting、sleeping、completing；后者表示自己的结果已有了，但所属工作尚未排空。子会话本身仍是普通会话，通过所有权绑定到调用任务。

出处：task-graph.ts:26（私有存档）、harness/types.ts:158（私有存档）、harness/types.ts:292（私有存档）。

**Sumika 怎么做。[读码]**

本次核对的 `turn`、`app`、`tools` 生产实现没有对应的子任务管理入口。现有 Hub 管理独立会话，但“多个会话同时运行”不等于“有父子归属、委派权限、取消传播和结果交付的多代理”。

记忆整理已是独立后台工作：按角色、会话合并请求，限并发，保存游标和退避。它有确定输入和写入规则，不必包装成自由行动的子代理。

出处：[hub.go:86](仓库根/native/internal/turn/hub.go:86)、[schedule.go:1](仓库根/native/internal/memplugin/schedule.go:1)、[summary_state.go:9](仓库根/native/internal/memory/summary_state.go:9)。

**差在思路哪里。**

关键不是再起一个模型，而是**谁拥有这份工作、什么算结束、结果交给谁**。普通 pi 示例解释了最小委派，durable 展示了长期持有工作的代价。

**值不值得学、怎么转换。**

Sumika 以后做资料搜索、后台整理任务时，优先借独立上下文、明确父调用、结果归属和取消所有权。不要直接采用“新起进程便继承 cwd、环境和默认工具”的示例行为。

QQ 群里发起任务与本地主窗口操作有不同授权边界；孩子返回资料也不能自动成为另一段公开聊天或长期记忆。已有规格应继续作为入口，本报告不另起一套工单方案。

# 8. 模型提供方：借能力和来源信息，保留网关分工

**pi 怎么做。[读码]**

pi 将 provider、API 协议、模型能力和运行时选择分开：

- 同一 `Models` 接口按 provider 分发，处理凭据与模型目录。
- API 实现统一输出消息、内容块、usage、停止原因。
- assistant 消息保留原 provider、API、model；跨模型投影时据此丢掉不兼容的思考签名、规范化工具 ID、处理图片能力。
- usage 区分缓存读写、思考 token、目录估算费用和提供方实报费用。

出处：models.ts:258（私有存档）、models.ts:929（私有存档）、transform-messages.ts:125（私有存档）、types.ts:464（私有存档）。

请求级重试与会话级重试分层；请求级识别状态码、Retry-After，并可中止退避。费用汇总还覆盖压缩、分支摘要和带 usage 的工具结果。这里的 429 重试不等于统一的多会话限流调度。

出处：provider-retry.ts:21（私有存档）、agent-session.ts:3843（私有存档）、usage-totals.ts:64（私有存档）。

**Sumika 怎么做。[读码]**

`llm.Client` 是 OpenAI 兼容接口的薄包装，每个客户端对应一个 Source；正式装配默认走 Magpie。SDK 自带重试关闭，回合层决定重试。usage、网关实际路由和 reasoning details 已有自己的规范化。

出处：[llm.go:1](仓库根/native/internal/llm/llm.go:1)、[llm.go:26](仓库根/native/internal/llm/llm.go:26)、[llm.go:80](仓库根/native/internal/llm/llm.go:80)、[app.go:268](仓库根/native/internal/app/app.go:268)。

回复和压缩记录调用；后台记忆适配器调用同一个客户端，却只向记忆包返回 `Reply.Text`。`Msg` 也未像 pi assistant 消息那样保留完整提供方身份；当前换模型会重建实例，这减少了跨模型重放复杂性，但也丢掉部分热工作材料。

出处：[guarddeps.go:113](仓库根/native/internal/app/guarddeps.go:113)、[loop.go:31](仓库根/native/internal/turn/loop.go:31)、[hub.go:977](仓库根/native/internal/turn/hub.go:977)。

**差在思路哪里。**

pi 自己承担多协议客户端；Sumika 将很多协议兼容交给网关，内核承担产品回合。这是部署分工，不能仅凭支持的 API 数量判定架构落后。

值得改的是：**一次逻辑调用的身份、有效设置、来源和结果信息，应跨回复、摘要、整理、守卫保持同一契约。**

**值不值得学、怎么转换。**

先统一调用结果和记录口径，保留 usage 是否收到、实际模型与路由、有效思考档位、错误及耗时。记忆包仍可只消费正文，宿主应保留其余信息。

以后直连多协议时再扩 API adapter。账号选择、网关内部重试与路由不要重复搬进 Agent 内核；费用也需区分实报和估算，不能把缺 usage 当成已知的零消耗。

# 9. 取消、并发、错误与可测试性：Sumika 已有基础，应该收拢所有权

**pi 怎么做。[读码]**

每次 Agent 运行持有 `AbortController`，signal 传给模型、工具和钩子。一次运行直到被等待的事件订阅者收尾才解除 active 状态；会话层 `abort()` 同时停止重试、压缩、分支摘要，并等待 idle。替换会话先终止旧运行，再关闭扩展和使旧上下文失效。

出处：agent.ts:529（私有存档）、agent-session.ts:2519（私有存档）、agent-session-runtime.ts:162（私有存档）。

这是协作式取消：普通工具仍需要理会 signal。源码中的普通扩展派发也是直接等待 handler，不能假定任意扩展挂住都会被统一超时打断。

测试通过注入 `StreamFn` 直接产生模型事件；工具有可替换的文件和命令 operations；会话测试夹具组合真实会话管理器与假模型。

出处：agent-loop.test.ts:109（私有存档）、read.ts:46（私有存档）、test-harness.ts:1（私有存档）。

**Sumika 怎么做。[读码]**

同会话排队、不同会话并行；停止定位到正在跑的回合，不取消同角色其他会话。工具总超时与审批等待分开，副作用可能已发生时明确返回未知风险。插件另有时限和失效检查。

装配层按顺序停入口、取消内核、等 Outcome、排空审批、等待压缩、关闭记忆和库。当前 `Hub.Idle()` 只等提前压缩，整个运行寿命的等待仍分散在 app 和组件中。

出处：[hub.go:323](仓库根/native/internal/turn/hub.go:323)、[hub.go:374](仓库根/native/internal/turn/hub.go:374)、[loop.go:733](仓库根/native/internal/turn/loop.go:733)、[app.go:471](仓库根/native/internal/app/app.go:471)、[hub.go:205](仓库根/native/internal/turn/hub.go:205)。

可测试性并不薄弱：有真实 Hub、临时库、可控假 HTTP 网关的夹具，也有严格请求匹配、用尽和剩余交互检查的录像回放。

出处：[turntest.go:1](仓库根/native/internal/turn/turntest/turntest.go:1)、[cassette.go:1](仓库根/native/internal/llm/llmtest/cassette.go:1)、[replay_test.go:1](仓库根/native/internal/llm/replay_test.go:1)。

**差在思路哪里。**

pi 把“这次运行是否还活着”的所有权收在 AgentSession；Sumika 各组件已有清理协议，但新入口接入时仍需要知道多处等待关系。

**值不值得学、怎么转换。**

值得将停止准入、取消、排空活动和后台工作收回内核的明确生命周期入口，装配只负责组件依赖顺序。保留现有 HTTP 录像测试，它能覆盖实际序列化与 SDK 边界；不必为了像 pi 而把测试全部换成直接注入消息。

以后整理边界时，用现有夹具验证取消、冷重建、Commit、压缩交错即可，不需要新增测试框架。

# 10. 另外三项现代设计，以及它们对 Sumika 的限制

## 10.1 上下文修改也有来源，能回放“当时为什么这样看”

**pi。[读码]** `context_edit` 保留原条目，投影层解释替换；工具变化、模型选择也能成为会话历史。  
**Sumika。[读码]** 已有 prompt 段落 hash、epoch、`Msg.Kind/Seq/Scope` 和项目资料接纳账本，但不是一个覆盖所有材料的投影模型。

出处：session-manager.ts:544（私有存档）、[write.go:339](仓库根/native/internal/store/write.go:339)、[loop.go:45](仓库根/native/internal/turn/loop.go:45)。

**判断。[推断 / INFERENCE]** 这是本次最值得借的思路。它既能解释工作上下文，也适合回答“她这次想起了什么、来源是什么”。

尤其应服从已经接受的 [ADR-242:2878](仓库根/docs/决策记录.md:2878)：同角色记忆在本地私聊、本地群聊、QQ 私聊、QQ 群都可召回，并标明来源。**本次读取的 `AllowedScopes` 和召回仍有旧过滤，属于实现与决定尚未对齐**，不能把旧限制重新包装成架构建议。

## 10.2 Code Mode：让程序筛结果，模型只接收必要内容

**pi。[读码]** 模型生成 JavaScript，在 QuickJS sandbox 中组合工具、过滤结果；脚本本身没有 Node、文件系统、网络和计时器。工具能力通过宿主桥接，仍走共同执行管道。脚本有内存与 worker 准入限制。

出处：codemode/tool.ts:1（私有存档）、execute.ts:52（私有存档）、execute.ts:525（私有存档）。

**Sumika。[读码]** 当前主要是模型逐步调用工具，工具结果以文本进入循环。

**判断。[推断 / INFERENCE]** 大量 MCP 数据组合、本地批量处理可能受益；日常陪伴聊天未必受益。先有真实的“多次模型往返只为筛一份大结果”的痛点，再考虑。QuickJS 的脚本隔离也不等于被桥接的本地工具天然无权限风险。

## 10.3 durable：先落执行意图，再决定恢复时能不能重做

**pi durable。[读码]** 工具执行前持久化最终参数和 replay 政策。恢复时，只有记录中的政策和当前工具都为 safe 才重跑；否则返回“可能已部分执行”。正常关闭与崩溃也区分处理。

出处：harness/tool.ts:180（私有存档）、harness/tool.ts:201（私有存档）、scheduler.ts:563（私有存档）。

**Sumika。[读码]** 当前统一采用较保守的恢复：取消待审批，执行中的结果记未知，不自动重跑。

**判断。[推断 / INFERENCE]** 应先借“意图、结果、可否重放分开”的原则。完整 durable 引入了持久任务版本、恢复、所有权、等待和迁移，成本远大于给现有 Hub 多加几个状态；目前不建议整体搬入。

# Sumika 该借的几条

以下按架构收益排序，**不是修改既有排期**。每条都是建议，不是本次已实施的改动。

## 架构上值得改

| 顺序 | 现在的痛点 | 借什么、怎么改 | 主要涉及包 | 主要风险 |
|---|---|---|---|---|
| **1. 统一上下文投影与来源** | 热实例、冷重建、压缩和 Commit 分别解释历史，工具与注入材料又有不同保留寿命 | 借 pi 的 `SessionProjection`：让材料有稳定来源，明确聊天事实、工作材料、摘要和临时注入；逐步共用重建与请求投影规则，继续用 SQLite | `history`、`turn`、`store`，以及 `memplugin`、`projectcontext` 接纳接口 | 容易退化成两份历史；须明确库中事实与可重建缓存，不能新增另一份可独立修改的事实源 |
| **2. 统一运行事件与生命周期** | 流式回调、审批、Settled、桌面快照缺共同运行身份；关闭等待分散 | 借 pi 的完整事件协议，结合现有审批快照与版本；统一回合身份、步骤身份、当前运行快照和排空入口 | `turn`、`approval`、`api`、`desktopread`、`app` | 把步骤结束误作整轮结束；慢消费者阻塞生成；临时草稿被当成已提交聊天 |
| **3. 统一模型调用契约** | 回复、摘要与后台调用保留的信息不对等；部分 adapter 只剩正文 | 借 pi 的统一结果及来源字段；宿主在调用边界保留有效模型设置、usage 是否收到、路由、错误与耗时，业务消费者按需取正文 | `llm`、`app`、`turn`，调整 `memory.Generator` 的宿主适配 | 多层重复记账、隐藏重试；不应将网关账号路由重复实现一遍 |
| **4. 统一工具契约与结果所有权** | 声明 schema 与执行参数处理分开，长结果、界面结果缺统一引用 | 借统一校验管道与 `content/details/structuredContent` 分工；先接现有工具和全文引用，保留宿主审批；未来嵌套调用复用入口 | `tools`、`turn`、`policy`、`approval`、`store` | 强制转换改变现有参数含义；发现或加载工具被误当成授权；全文引用跨会话暴露 |
| **5. 为聊天和工作明确压缩契约** | 聊天摘要过滤工具材料，本地长任务重建后缺少可靠工作进度 | 借 pi 工作检查点的保留项目，按会话用途选择材料；保存目标、约束、已执行结果、未完事项及结果引用，继续复用现有压缩执行机制 | `turn`、`history`、`prompts`、`store` | 工具内部材料进入普通记忆；不同上下文用途混用摘要；不能只换提示词而不补可恢复材料 |

第 1、5 条要保留 Sumika 的产品分工：**长期记忆、当前聊天上下文、工作状态不是同一份东西。** 当前记忆包通过端口读取事件、通过插件接入，整理排程监听 Seen，能处理“群里看到了但没开口”的消息。这是陪伴聊天需要的设计，不应并入 Agent 循环或改成仅在 Settled 后整理。

## 以后再说

| 设计 | 何时值得做 | 转成 Sumika 做法时的边界 |
|---|---|---|
| **工具按需发现** | MCP 工具数量已明显增加提示词和选择负担 | 先按当前角色与场合筛允许集合，再发现；发现不授予执行权限 |
| **会话树与分支摘要** | 本地重新生成、探索不同方案已有明确交互需求 | 树描述模型历史选择；QQ 平台事实和已发生操作不随 leaf 回退 |
| **子代理所有权与任务图** | 后台资料任务需要独立上下文、取消和结果投递 | 沿既有子代理规格做；不默认继承本地工作区和执行权限，不把子过程当公开聊天 |
| **持久任务、跨重启续跑** | 确有等待审批、长任务跨重启继续的需求 | 先保存执行意图和结果，默认不重放未知副作用；不能从“只读”直接推出可安全重放 |
| **Code Mode** | 实际任务经常为了筛选、聚合数据消耗多次模型往返 | 先统一工具执行、结构化结果和取消，再考虑脚本宿主；日常 QQ 聊天不需要默认承担它 |
| **更多原生 provider 与自动路由** | 直连协议或岗位选择出现网关无法满足的需求 | 先统一模型能力和调用结果；不把 Magpie 的账号路由、重试和计费逻辑复制进内核 |

不建议从 pi 照搬的还有两点：普通扩展对任意 handler 的直接等待，以及“运行时能加载代码就有隔离”的假设。Sumika 当前的插件时限、撤销、接纳确认和宿主政策具有独立价值。
