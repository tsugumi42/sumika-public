# 排查：提示词缓存命中率低（2026-11-09）

用处：记录“开启 Work 后每轮第一步缓存命中只有约 36%”的原因、修法和没改的两点（记忆块、历史窗口）。
改 `acquire` 的复用条件、给 Live 加新状态、动记忆插件的去重账本、调 `agent.recentMessages` 之前先读这页。
修复在分支 `fix/cache-reuse`，测试 `native/internal/turn/work_reuse_test.go`；相关规则 ADR-022（只追加不插入）。
来源：下面的“事实”来自任务给定的真实统计和假模型复现，本页没有重新量真实数据；“推断”标明了没量。

## 事实

1. 提交 c459fc62（2026-11-04）在 `acquire` 的复用条件里加了 `(!working || l.in.Identity.RootID == in.Identity.RootID)`。`input.go` 给每个新输入分配新 RootID（等于 RunID），所以开着 Work 时每一轮都新建实例、从库重拼。最近一天主窗口 13 轮全部新建。
2. 重拼时上一轮的记忆参考块（KindContext）不在库里，新块追加在最后。上一轮是 `[系统, 历史, 记忆块, 用户话]`，这一轮是 `[系统, 历史, 用户话, 回答, 新记忆块, 新话]`，从上一轮记忆块的位置起分叉。同一实例里多步请求命中 80% 到 95%，每轮第一步约 36%。
3. 这违背 ADR-022。当时加这个条件的目的是：工作记录（`work_roots`、`work_entries`、`result_refs` 里的预算）按 RootID 存，换了 root 就得开新记录，实例上属于 root 的状态也要换。目的没有要求把整段消息丢掉重拼。

## 修法

换根时复用实例，`l.msgs` 一条不动，只换属于 root 的状态（`hub.go` acquire、`work.go` `switchWorkRoot`）：

- 在库里开出新 root 的工作记录（`Open`，旧计划清单导入也在这一步），读它的状态放进 `l.workState`。
- 前几个 root 留在实例里的工具结果仍可 `result_read`：`Store.Read` 只校验 `ref.Owner == Scope` 和工具权限，不看 RootID；Scope 不同（别的场合、角色、发言人）照旧读不到。没有放宽。
- `cfg.invocation` 每轮在 `runTurn` 开头换成新 root，`recordWork`、`finalizeTool`、预算自然落到新 root。
- 新 root 在库里已经有工作条目（回到一个旧 root）时不追加到末尾，退回整体重建（`rebuildIn`，和重启后从库恢复同一条路）。
- 原有重建条件都在：Scope、Workspace、系统提示、模型、工具清单、压缩快照、闲置超时，以及 `toolPairProblems`（优先于换根）。
- 顺手修了一处：旧计划清单导入的条目没有消息（存成 `null`），`workPort.Load` 把它解成一条空消息放进历史。每个带旧计划的主窗口 root 都会因此被误判成“有条目”。现在 `null` 当作没有消息。

估算：`conversationTokens` 对所有非系统消息求和，含工具结果、参考块和图片；`fitHard`、`slim`、`compactEarly` 都用它，所以保留下来的内容已经算进软、硬门槛（测试 `TestWorkRootSwitchGatesCountRetained` 验证）。

## 没改的两点（只调查）

### 记忆块（约 8757 字符、约占请求 20%）

推断（读了 `memplugin/plugin.go` 的 `context`，没有量真实数据）：

- 记忆插件在实例的插件存储里记“给过哪些”：命中的条目按 `ref` 去重（`s.given`），固定要点只在 `PinnedKey` 变了才重给（`b.Lines(b.PinnedKey != s.pinnedKey)`）。
- 每轮都新建实例时存储是空的，所以每轮把固定要点和命中全部重发一遍，这就是约 8757 字符的来源，而且每轮出现在请求末尾、完全不进缓存前缀。
- 复用实例后账本跟着实例活，已经给过的不再重发：稳定的部分（固定要点、重复命中的条目）只出现一次，留在历史里成为缓存前缀的一部分；每轮追加的只有新命中的条目。所以这条修复本身就是让记忆块稳定部分进缓存的低风险办法，不需要再动记忆插件。
- 风险和要观察的：①`PinnedKey` 一变就整组固定要点重发，频率要看真实数据；②实例被重建（压缩、闲置、换模型）账本清零，下一轮重发一次，属预期；③记忆条目更新后同一 `ref` 内容变了，是否重给取决于 `ref` 是否含版本，本页没查。
- 建议：上线后用 `model_runs` 的 `context_json` 里记忆段的字符数和每轮首步命中率各量一天，再决定要不要排“固定要点按稳定顺序、变了只发差异”。

### `history.For` 的滑动窗口（`agent.recentMessages=30`）

读了 `internal/history/history.go` 的 `For`：

- 没有压缩快照时只取最近 30 条（`MessageWindow`）；有快照时取快照切点之后的全部（`EventsSince`），不受 30 条限制。
- 实例活着时历史只增不减，窗口只在重建那一刻起作用。重建点往前滑一格，窗口的起点就变了，请求从第 1 条消息起分叉，所以任何一次重建都是整段缓存未命中，窗口本身不会再额外多丢一次。
- 对修复后的影响：重建变少（只剩压缩、闲置 45 分钟、换模型、改提示词、重启），窗口造成的损失随之变少。重启后的第一轮必然全未命中，这个修不了（服务商缓存也有存活时间）。
- 有一点要留意：旧代码里每轮重建正好把窗口当成“自动裁剪”，历史超过 30 条时请求不会越来越长；复用之后长度只靠软门槛、硬门槛和提前压缩控制。主窗口的工具结果大时，增长会比以前快，上线后看 `fitHard` 触发和压缩次数。
- 不建议改 30：它决定重建时的上下文量，和这次的命中率问题不在一条线上。
- 2026-11-13 起窗口起点锚定（至少 30、不到 60 条，攒够才跳），重建前后历史接得上：[规格-提示词前缀稳定](../规格-提示词前缀稳定.md)第五节。

## 形状 × 入口（AGENTS 第 7 条额外核验）

入口：A 复用（acquire 里实例可用）、B 重建（acquire 新建）、C `rebuildIn`（硬门槛、工具对不上）、D 重启后从库重建（B 的一种，实例不在了）。

| 形状 | A 复用 | B 重建 | C rebuildIn | D 重启重建 |
|---|---|---|---|---|
| RootID 缺 | 不开 Work（working=假），原路径不变 | 同左 | 同左 | 同左 |
| Scope 无效 | `ValidScope` 假，working=假，原路径 | 同左 | `restoreWork` 直接返回 | 同左 |
| Scope 不同 | 条件里 Scope 不等，走 B | 新建，工作记录按新 Scope | 不会来（C 只对现有实例） | 同 B |
| 新 root 库里已有条目（回到旧 root） | `switchWorkRoot` 发现有消息，转 C | 条目从库里接回 | 整体重建，条目接回；测了 `BackToOldRoot` | `TestWorkProjectionColdHot` 测了 |
| 新 root 库里没有条目 | 只换 `workState`，消息原样；测了 `KeepsPrefix`、`IsolatesWorkState` | 同旧路径 | 同旧路径 | 同旧路径 |
| `loadWork` 报错（读库失败、Scope 对不上） | acquire 返回错误，不复用也不吞；没有专门造故障测试，沿用 `restoreWork` 原有错误路径 | 同左 | 同左 | 同左 |
| 工具调用和结果对不上 | 先 C 后换根（`toolPairProblems` 优先）；测了 `ToolPairGuard` | - | 重建 | 同 B |
| 模型、提示词、工具清单、Workspace 变 | 条件不等，走 B；模型、闲置测了 `IdleAndModelRebuild` | 重建 | - | 同 B |
| 有新压缩快照 | 走 B；测了 `CompactRebuild` | 重建 | 硬门槛压缩后 C；测了 `GatesCountRetained` | 同 B |
| 闲置超时 | 走 B；测了 `IdleAndModelRebuild`、`Images` | 重建 | - | 同 B |
| 软门槛 | 请求里把旧工具结果换成引用占位，实例里不动；测了 `GatesCountRetained` | 同左 | 同左 | 同左 |
| 停止提醒还没说 | 留在实例上带到新 root；测了 `StopReminder` | 带到新实例（原有逻辑） | 同左 | 进程重启后丢，原有行为 |
| 主人发的图 | 留在原消息上，不重复；测了 `Images` | 从事件取回 | 同 B | 同 B |
