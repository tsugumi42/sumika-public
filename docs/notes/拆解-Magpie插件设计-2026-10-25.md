## 1. 插件是什么：接口、结构体与最小实现

### 1.1 先区分三种运行机制

“插件”在这个仓库里不是单一概念：

| 机制 | 插件长什么样 | 在哪里执行 | 证据与可信度 |
|---|---|---|---|
| Go 内置功能插件，即 `plugins/` | 一个 Go 包，在 `init()` 中注册 `pluginrt.Manifest` | magpie 自身进程 | 【读码确认】plugins/middleware/middleware.go:22（私有存档） |
| JS 网关插件 | 导出 `onRequest`、`onProvider`、`onEvent`、`onResponse`、`strategies`、`onUsage` 中至少一种 | 网关进程内的 moejs JavaScript 引擎 | 【读码确认】internal/middleware/middleware.go:167（私有存档） |
| Bun 宿主插件，包括 OpenCode/provider 插件和异步请求钩子 | 动态导入 JS/TS 模块，初始化函数返回 hooks；异步网关钩子使用独立入口 | Bun 子进程；多个插件共用宿主 | 【读码确认】internal/plugin/host.go:890（私有存档）、host.js:1188（私有存档） |

**研究 `plugins/all`、`plugins/groups` 等目录时，主角是第一种；研究拦截请求时，还必须继续追踪第二种。**【读码确认】Go 的 `middleware` 插件实际只是把 JS 链接到核心扩展点上，见 plugins/middleware/middleware.go:28（私有存档）。

### 1.2 Go 插件没有统一的 `Plugin interface`

插件描述是 `Manifest` 结构体，关键字段可概括为：

```go
// 摘录关键字段，省略展示元数据等字段。
type Manifest struct {
    ID                 string
    API                string
    Requires, Provides []string
    Essential          bool
    InUse              func() (int, error)
    Apply              func(*Ctx) error
    Parts              []Part
    Defaults           map[string]any
    Settings           any
    Client             []string
}
```

【读码确认】完整定义：internal/pluginrt/pluginrt.go:35（私有存档）。

- **最少能注册什么：**非空且不重复的 `ID`。`Register` 对空 ID、重复 ID 直接 `panic`；`API` 留空时兼容性检查按 `^1` 解释。`Apply` 可以为 `nil`，因此纯界面贡献插件不必实现启动方法。【读码确认】Register:128（私有存档）、Compatible:391（私有存档）、apply:308（私有存档）。

- **真正有行为的插件怎么写：**在 `Apply` 中调用核心扩展点的注册函数，再把返回的撤销函数交给 `c.OnDispose`。`middleware` 的实现只注册 JS 请求链和用量观察器，业务实现仍放在 `internal/`。【读码确认】plugins/middleware/middleware.go:28（私有存档）。

- **不是所有 `plugins/` 包都处理请求。**例如 `plugins/gateway` 是 Gateway 页面，声明 `Parts`、`Settings`、`Client`，没有 `Apply`；关掉页面并不等于关掉核心网关。【读码确认】plugins/gateway/gateway.go:1（私有存档）。

### 1.3 真正处理请求的是扩展点接口

Go 网关中间件的接口是：

```go
type Agent interface {
    Begin(Info) Run
}

type Run interface {
    Request(body []byte) ([]byte, *Reject)
    Wrap(w http.ResponseWriter) (http.ResponseWriter, func())
    End()
}
```

`Begin` 返回 `nil` 表示本中间件不参与；`Request` 返回修改后的请求，或返回 `Reject` 终止处理；`Wrap` 处理响应；`End` 释放本次请求资源。【读码确认】internal/gwmw/gwmw.go:43（私有存档）。

这体现了两层职责：**`Manifest` 管插件启停，`Agent/Run` 管每次请求。**【读码确认】插件注册桥接（私有存档）、请求执行（私有存档）。

## 2. 怎么注册和装配：编译、运行时启停与依赖顺序

### 2.1 `plugins/all` 是编译时装配入口

装配路径是：

```text
main.go
  └─ 空白导入 plugins/all
       └─ 空白导入各 plugins/<name>
            └─ 各包 init()
                 └─ pluginrt.Register(Manifest)
```

`plugins/all` 不负责执行插件，而是保证各包的 `init()` 运行。注册表是进程级 `map[string]Manifest`，有互斥锁；`Registered()` 按 ID 排序返回。【读码确认】main.go:8（私有存档）、plugins/all/all.go:5（私有存档）、pluginrt.go:121（私有存档）。

因此，**这条 Go 内置插件路径是编译进二进制后运行时启停，不是运行时加载 Go 动态库。**新增这类插件需要加入编译装配；社区 JS/TS 插件才走另一套运行时发现和加载路径。【读码确认】all.go:5（私有存档）、host.js:1234（私有存档）。

### 2.2 启停选择来自 `plugins.yml`

最终是否启用由 `Compose` 决定：

1. 默认所有内置插件开启。
2. `essentials` 预设关闭非 `Essential` 插件。
3. 用户行中的 `enabled` 覆盖前面结果。
4. `InUse() > 0` 再强制开启；`InUse` 报错也按“在用”处理。

`Essential` 表示 Essentials 预设中的默认选择，**不是不可关闭标记**；真正约束关闭的是 `InUse`。GUI 也会拒绝关闭正在使用的插件。【读码确认】internal/pluginrt/config.go:124（私有存档）、internal/gui/builtins.go:141（私有存档）。

### 2.3 依赖决定启用顺序，没有独立优先级字段

`Runtime.Reconcile` 的顺序是：

- 先找出需要停用的插件，并递归包含依赖其服务的插件。
- 按激活顺序逆序卸载。
- 再按 ID 排序扫描想启用的插件。
- 只有 `Requires` 中的服务全部存在才调用 `Apply`。
- 反复扫描，直到没有新的插件被激活。

缺服务的插件保持 `pending`，原因里列出缺失服务；没有看到专门的循环依赖诊断算法，循环依赖也会表现为等待服务。【读码确认】internal/pluginrt/pluginrt.go:211（私有存档）、missing:294（私有存档）。

**依赖相互独立时，ID 排序影响应用顺序；没有看到 `Priority`、`Before`、`After` 这样的排序声明。**【读码确认】Manifest:35（私有存档）、排序与应用:242（私有存档）。

### 2.4 `Provides` 声明不会自动生成服务

运行时判断依赖是否满足时查看的是 `services` 表；真正写入这张表的是 `Ctx.Provide(name, value)`。仅在 `Manifest.Provides` 中列名字，不会自动注册对象。依赖卸载检查也使用实际 `Ctx` 记录的已提供服务。【读码确认】Provide:112（私有存档）、needsGoing:281（私有存档）、missing:294（私有存档）。

### 2.5 社区插件按安装列表装配

社区插件存储在 `plugins.json`，每项有 `spec`、`off`、`options`；`spec` 可以指向 npm 包、Git 仓库、本地文件或目录。JS 中间件按列表顺序加载，关闭的项跳过；Bun 宿主也按传入列表加载相关模块。这条路径没有采用 Go `Requires` 的服务依赖调度。【读码确认】internal/plugin/store.go:46（私有存档）、internal/middleware/middleware.go:124（私有存档）、internal/plugin/host.js:1219（私有存档）。

## 3. 插件之间、插件和核心之间怎么交互

### 3.1 有服务查找，但不是完整的 Cordis 式服务注入

`Ctx` 提供：

- `Provide(name, value)`：登记服务，卸载时删除。
- `Service(name)`：返回 `any`，缺失时返回 `nil`。
- `OnDispose(fn)`：登记清理动作。
- `Contribute(slot, key)`：登记界面贡献。
- `Config`：启用时获得的配置。

【读码确认】internal/pluginrt/pluginrt.go:93（私有存档）。

这里有两个边界：

- `Core` 预置的 `settings/providers/gateway/window` 服务，值都是 `struct{}{}`。它们表示“核心能力已就绪”，不是通过 `ctx.Service("gateway")` 获得可调用网关对象。【读码确认】pluginrt.go:31（私有存档）、New:195（私有存档）。
- 实际内置插件通常直接导入核心包，再调用 `gwmw.Use`、`usage.Observe` 等注册函数。没有看到所有核心能力都必须通过 `Ctx` 注入的约束。【读码确认】plugins/middleware/middleware.go:15（私有存档）、plugins/redact/redact.go:28（私有存档）。

**插件之间禁止互相 import，核心禁止 import 具体插件，靠测试检查；插件调用核心包则被允许。**【读码确认】TestPluginsImportOnlyCore:94（私有存档）。

### 3.2 没查到通用消息事件总线，实际是多个领域扩展点

| 扩展点 | 语义 | 能否拦截 |
|---|---|---|
| `gwmw.Agent/Run` | 修改请求、包装响应 | 可以通过 `Reject` 终止请求 |
| `usage.Observer/Watch` | 请求开始、尝试、结束、用量记录的观察 | 接口不返回处理决策，不能据此消费请求 |
| JS `onEvent` | 处理模型响应的 SSE JSON 事件 | 可丢弃当前 SSE 事件 |
| Bun 异步 `onRequest/onResponse` | 路由前补充上下文、完成后观察回复 | 不能拒绝请求，也不能重写已经输出的回复 |

【读码确认】gwmw.go:43（私有存档）、usage/observe.go:19（私有存档）、middleware/run.go:400（私有存档）、plugin/host.js:1291（私有存档）、gatewayFinish:1357（私有存档）。

**这里的 `onEvent` 是 HTTP 响应流中的协议事件，不是 QQ 的消息、戳一戳、入群等业务事件。**【读码确认】它由响应 writer 切分 SSE 后调用，见 internal/middleware/run.go:400（私有存档）。

在已读的 `pluginrt.Ctx` 和网关扩展点中，通用的 `Emit/On("message")`、事件传播取消协议，**没查到**。【读码确认，限已读范围】Ctx:93（私有存档）、Agent/Run:43（私有存档）。

### 3.3 短路发生在模型请求之前

`serveAgent` 执行链大致是：

```text
会话记录／工具循环检查
  → Bun 异步请求钩子
  → 各 Go Agent.Begin
  → 各 Run.Request
       ├─ 返回 Reject：写协议错误，立即 return
       └─ 继续：安装响应包装
  → 核心 serve：路由、访问上游
```

`Reject` 路径不执行后续中间件，也不进入最后的核心 `serve`。【读码确认】internal/gateway/middleware.go:22（私有存档）。

JS 链内部的规则是：

| `onRequest` 的行为 | 结果 |
|---|---|
| 返回对象 | 成为后续插件和网关看到的请求体 |
| 返回 `undefined` | 保留原始字节；单纯修改参数对象但不返回，不生效 |
| 调用 `ctx.reject(status, message)`，正常返回 | 终止请求链，交由核心写错误 |
| 抛异常、超时、返回非法结果 | 记录失败，保留该插件之前的请求，继续链 |

【读码确认】Request:143（私有存档）、apply:212（私有存档）、请求链测试:67（私有存档）。

需要注意：`ctx.reject` 只接受 `400–599` 状态码，默认 `403`。它表达的是**拒绝 HTTP 请求**，没有“已经发出正常回复，消费成功”的返回值。【读码确认】reject:121（私有存档）。

### 3.4 不同钩子的“拦截”能力不同

- `onProvider` 在具体上游尝试前改请求体；此时 `ctx.reject` 不会拒绝请求，返回 `null` 也不能丢弃请求。每次尝试从 `onRequest` 的结果重新开始，某个 provider 的改动不会污染下次尝试。【读码确认】internal/middleware/run.go:167（私有存档）。

- `onEvent` 返回 `null` 可以丢弃当前 SSE 事件，并停止把这个事件传给后续 JS 插件；它并不取消整个模型生成。【读码确认】internal/middleware/run.go:400（私有存档）。

- `onResponse` 处理完整 JSON 回复；返回 `null` 被视为失败，不能用它丢掉完整回复。【读码确认】internal/middleware/run.go:367（私有存档）。

### 3.5 顺序与错误策略不是全局统一的

**外层 Go 中间件请求正序、响应反向嵌套；内层 JS 链的 `onRequest`、`onResponse`、`onEvent` 都按列表正序遍历。**不能笼统概括为所有钩子都是洋葱模型。【读码确认】gwmw.Use:154（私有存档）、serveAgent:40（私有存档）、JS response:375（私有存档）、JS event:407（私有存档）。

错误策略按用途区分：

- 插件 `Apply` 返回错误或 panic：回滚本次注册，插件进入 `failed`，其他插件继续。
- JS 请求钩子失败：fail open，保留输入继续。
- 隐私脱敏被要求启用，但没有 masker 或 masker panic：fail closed，不发送原文。

【读码确认】pluginrt.apply:308（私有存档）、middleware.Request:143（私有存档）、gwmw.Masking/Safely:268（私有存档）。

## 4. 生命周期：启动、关闭、重载

### 4.1 启动与失败

CLI 启动阶段先迁移设置，再 `pluginrt.Settle()` 初始化/迁移 `plugins.yml`，然后 `Refresh()` 创建进程默认运行时并协调启停；错误打印出来后继续启动。【读码确认】internal/cli/main.go:228（私有存档）。

单个 Go 插件有 `off/pending/active/failed/disposed` 状态。`Apply` 失败时，已经通过 `OnDispose` 登记的动作立即逆序撤销；持续为启用状态的 `failed` 插件不会在每次 `Reconcile` 中自动重试。先关闭使其回到 `off`，再开启，才会重新尝试。【读码确认】状态定义:81（私有存档）、Reconcile:252（私有存档）、apply:308（私有存档）。

### 4.2 关闭依靠撤销函数

- 插件间：依赖者先卸载，被依赖的服务提供者后卸载。
- 插件内：`OnDispose` 按登记的逆序执行。
- 某个 disposer panic 会被记录，其余清理继续执行。
- `Runtime.Stop()` 可以逆序停止全部活动插件。

【读码确认】Reconcile:219（私有存档）、undo:342（私有存档）、Stop:357（私有存档）。

**进程正常退出是否统一调用默认 `pluginrt.Runtime.Stop()`：没查到。**本次针对 `rt.Stop()`、`Running().Stop()`、`def.Stop()` 的检索只找到测试调用。可确认“有停止 API、运行时停用会撤销”，不能据此保证所有进程退出路径都执行插件清理。【读码确认＋检索未发现】Stop 实现（私有存档）、测试中的 Stop（私有存档）。

另外，`Apply` 和 disposer 都在运行时互斥锁持有期间执行；这里没有为插件提供统一超时或生命周期 `context.Context`。插件初始化/清理如果长期阻塞，会阻塞该运行时的协调和状态查询。【读码确认】Reconcile:211（私有存档）、apply 注释与实现:306（私有存档）、Stop:357（私有存档）。

### 4.3 Go 插件支持热启停，但不自动热更新活动实例的配置

网关运行 `KeepFresh`，每两秒检查 `plugins.yml` 及设置、provider、社区插件列表等相关文件的时间/大小变化，变化时执行 `Refresh`。因此不用重启进程就能启停扩展点。【读码确认】internal/gateway/gateway.go:587（私有存档）、internal/pluginrt/config.go:360（私有存档）。

但 `Reconcile` 会直接跳过已经 `active` 的插件，不比较新旧配置，也不替换其 `Ctx.Config`。**保存配置和已激活 Go 插件收到新配置是两件事。**【读码确认】pluginrt.go:252（私有存档）、Ctx 创建:308（私有存档）。

前端另有 `magpie.configure` 和 `ctx.onConfig`：配置变化后更新前端插件配置、通知回调。这个能力属于浏览器 kernel，不能当成 Go `Ctx` 已有相同能力。【读码确认】internal/gui/assets/kernel.js:263（私有存档）。

### 4.4 JS 中间件与 Bun 宿主的重载方式不同

| 路径 | 重载机制 | 边界 |
|---|---|---|
| moejs 中间件 | 下一次请求检查变化，检查间隔约一秒；列表或入口文件变化后重编译、切换当前集合 | `stamp()` 只逐项检查发现的入口文件，没有遍历 import 依赖图；不能保证只改被导入辅助文件就触发重载 |
| Bun 宿主 | `SetOff`、`SetOptions` 等保存后调用 `Restart`；新调用使用新宿主，旧宿主尽量完成已有调用 | 旧宿主最多等待约十分钟退休；不是原地更换单个插件对象 |

【读码确认】middleware/current 与 Reload:90（私有存档）、stamp:138（私有存档）、store.SetOff:599（私有存档）、SetOptions:644（私有存档）、host.Restart/retire:681（私有存档）。

Bun 异步请求钩子的完成通知是 best effort，关闭、宿主退休、容量限制可能丢弃通知，不能当作可靠消息队列。【文档说的；调度方式读码确认】gateway-request-hooks.md:76（私有存档）、GatewayRun.Finish:194（私有存档）。

## 5. 配置：声明、校验与默认值

### 5.1 内置插件使用结构体生成配置 schema

Gateway 页面的实际例子：

```go

// 注册时：
```

## 6. 隔离和安全：插件能碰到什么

### 6.1 Go 内置插件是信任边界内的代码

Go 插件和核心同进程，可以导入核心包、访问进程权限允许的资源。`Ctx` 提供的是组织和清理机制，没有把文件、网络、全局变量等访问限制在 `Ctx` 内；包间 import 规则也是测试约束。【读码确认】插件直接调用核心包（私有存档）、import 边界测试（私有存档）。

`Apply` 的 panic 隔离不等于整个插件安全隔离：源码只在相应调用边界 recover；任意后台 goroutine、无限阻塞、任意文件写入没有因此获得统一保护。【读码确认＋推测】apply:308（私有存档）、undo:342（私有存档）。

### 6.2 moejs 中间件能力受限，但不能据此宣称完整安全沙箱

可确认的限制：

- 模块只允许相对路径 import，拒绝普通 npm/Node 模块名；解析后的路径必须落在插件根目录范围内。
- 宿主显式注入了 `console`；请求钩子得到协议元数据、`options/state/reject`，没有把 Go `http.Request` 直接交进去。
- 加载限时一秒，请求/上游尝试/完整响应钩子限时 250ms，SSE 事件钩子限时 50ms。

【读码确认】internal/jsmod/jsmod.go:20（私有存档）、新建运行时:218（私有存档）、ctx 构造:91（私有存档）、时间限制:34（私有存档）。

**它能看到脱敏前的请求内容。**中间件先运行，随后才进入上游发送/脱敏流程；不能把“最终发送给模型前会脱敏”理解成“插件看不到原文”。【读码确认＋文档说的】serveAgent:31（私有存档）、gateway-middleware.md:32（私有存档）。

独立内存配额、每插件操作系统身份、完整恶意代码隔离保证，**没查到**。源码新建 moejs runtime 时使用空的 `Options{}`；本次没有继续审计该引擎自身的安全边界。【读码确认，限已读范围】internal/middleware/middleware.go:218（私有存档）。

### 6.3 Bun 宿主有进程边界，但插件仍具有用户权限

Bun 加载器交给插件的输入包括 `Bun.$`，模块也是真实动态 import。作者明确写道：工具和 provider 插件以用户权限运行，安装插件就是信任它。多个插件共用一个宿主，没有每插件独立进程的隔离。【读码确认＋文档说的】host.js:1188（私有存档）、宿主加载列表（私有存档）、plugin-tools.md:32（私有存档）。

异步请求钩子的专用 `ctx` 不转发授权头，限制其修改客户端工具、模型和流式开关，并提供取消信号。这是**调用契约上的数据收敛**，不能把有用户权限的整个 Bun 插件降格理解为不可信沙箱代码。【读码确认＋推测】GatewayContext:76（私有存档）、host.js:1317（私有存档）。

### 6.4 社区页面另有更严格的浏览器隔离

社区 HTML 页面/面板使用 sandbox frame；CSP 包含 `sandbox allow-scripts`、`connect-src 'none'`，限制脚本和资源来源。允许读取的能力只有声明后的 `usage:summary`、`providers:list`，后端再次校验声明。【读码确认】internal/gui/pluginpage.go:204（私有存档）、读取授权检查:337（私有存档）、PageReads:75（私有存档）。

**第三方插件已经有实际实现，不能只称为未来设想。**文档 P4/P5 描述了 JS 策略、观察器、工具、页面、面板；但这些路径的权限模型各不相同。【文档说的，部分路径已读码确认】plugin-runtime.md:256（私有存档）。

## 9. 对你们消息事件插件的判断

### 9.1 适合借鉴的做法

| 做法 | 在复读、戳一戳插件中的用法 | 判断与依据 |
|---|---|---|
| 插件生命周期与单次事件执行分开 | 插件启用时注册处理器；每条消息到来再执行处理器。不要每条消息都重新装配插件 | 【推测】借鉴 Manifest.Apply（私有存档） 与 Agent.Begin/Run（私有存档） 的分层 |
| 注册动作返回撤销函数 | `OnMessage`、定时任务、服务注册都返回取消函数，统一交给 `OnDispose` | 【推测】借鉴 middleware 插件登记清理（私有存档） |
| 依赖就绪后启动，逆序卸载 | 插件声明依赖消息发送服务、存储服务；先停插件，再关闭它依赖的服务 | 【推测】借鉴 Reconcile（私有存档） |
| 观察器与可消费处理链分离 | 日志、统计观察消息；复读、戳一戳在有短路能力的链中处理 | 【推测】借鉴 Observer（私有存档） 与 Run.Request（私有存档） 的职责差异 |

### 9.2 需要重新设计的地方

**第一，定义正常消费语义，不能照搬 HTTP `Reject`。**

你们需要至少区分：

- `Pass`：本插件未消费，继续后续处理。
- `Handled`：本条事件已经完成；停止后续可消费处理器，也不调用模型。
- `error`：处理失败；由核心执行明确的失败策略。

复读插件发送成功后返回 `Handled`；戳一戳插件决定静默处理，也可以返回 `Handled`。不应通过抛错、伪造 `403` 或返回空文本表示正常完成。【推测】依据是 magpie 的 `Reject` 只能表达 HTTP 错误，见 run.go:121（私有存档）。

建议的事件路径：

```text
QQ 适配器 → 统一事件
              ├─ 观察器：记录、统计
              └─ 可消费处理链
                   → 复读插件
                   → 戳一戳插件
                   → 其他处理器
                   → 模型兜底
```

**核心不变量：一旦返回 `Handled`，后续处理器和模型兜底都不执行。**这是把 magpie“在核心 `serve` 前 return”的机制迁移成业务成功语义。【推测】参考 serveAgent 短路点（私有存档）。

**第二，明确事件类型与处理顺序。**

magpie 的输入是某种 HTTP API 请求体，`onEvent` 是这次响应里的 SSE 事件。QQ 的消息、戳一戳、撤回等应具有明确事件类型和公共身份字段，不宜直接套进 HTTP `body` 或字符串 hook 名字里。消费链顺序也应由装配列表或明确阶段表达，避免插件 ID 改名就改变行为。【推测】对照 gwmw.Info（私有存档）、SSE event（私有存档）、ID 排序（私有存档）。

**第三，复读状态属于群聊，不能放进请求级实例或实例池全局变量。**

magpie 的 `ctx.state` 每个插件、每次请求新建；moejs runtime 从池里借出再归还，模块全局变量也不代表某个稳定会话。复读所需的“上一句、连续次数、已触发状态”应按群/会话保存，并明确并发保护；同群消息通常需要保持可解释的先后顺序。【读码确认＋推测】请求 state 创建（私有存档）、runtime get/put（私有存档）。

**第四，保留 Cordis 的服务边界，不必照搬字符串 `any` 容器。**

你们可以让插件拿到类型明确的消息发送、存储和事件订阅服务，继续禁止互相 import 具体插件。magpie 的核心服务只是就绪标记，`Service` 返回 `any`，同名 `Provide` 会覆盖原值，撤销时直接删除；这套简单实现没有提供完整的服务冲突和类型保证。【读码确认＋推测】Core 初始化（私有存档）、Provide/Service（私有存档）。

**第五，聊天链需要可取消的 I/O 和明确的发送结果。**

复读、戳一戳实际调用 QQ 发送接口，会等待 I/O。应把可取消的 `context.Context` 传入处理器；发送失败时是否允许模型补答，要按你们的业务明确规定。magpie 的同步 JS 链面向短时间内的 JSON/SSE 变换，其 Bun 异步钩子虽支持 I/O，却明确不能消费请求，因此两者都不能原样充当你们的处理器契约。【推测】参考 同步钩子限时（私有存档）、异步钩子契约（私有存档）。

**第六，配置变更策略应是显式契约。**

对复读概率、触发次数、冷却时间等配置，可以选择“下一事件读取不可变配置快照”，或“配置变化后停旧实例、启动新实例”。不要只保存文件，再假定旧插件对象会自动获得新值；magpie 的 Go 活动实例没有这个保证。也不建议照搬 `InUse` 强制开启：机器人管理员关闭复读插件，通常就应停止处理，历史状态仍存在不应自动把它打开。【推测】依据 活动插件跳过协调（私有存档）、InUse 强制开启（私有存档）。

### 9.3 HTTP 网关与聊天事件流的关键差别

| magpie 的约束 | 你们需要补充的约束 | 判断依据 |
|---|---|---|
| 一次客户端请求有一个响应生命周期；工具循环主要由客户端负责 | 消息可以被静默消费，也可以主动发多条回复；模型调用是可选后续动作 | 【文档说的＋推测】gateway-request-hooks.md:3（私有存档） |
| `onEvent` 修改已经产生的模型流 | 应在调用模型之前决定是否消费消息，否则仅丢输出仍会花模型调用成本 | 【读码确认＋推测】run.go:400（私有存档）、serveAgent:49（私有存档） |
| 请求级 `state` 随请求结束 | 复读、冷却等状态跨事件存在，需要按群保存 | 【读码确认＋推测】run.go:91（私有存档） |
| 异步完成通知允许丢失 | 若某项聊天动作需要可靠执行，必须另定确认、重投及幂等语义，不能当作普通完成观察器 | 【文档说的＋推测】gateway-request-hooks.md:76（私有存档） |

QQ 的消息去重、机器人自身消息回流、每群串行调度、戳一戳事件语义，在本次研究的这些插件扩展点中**没查到**；它们应作为你们事件核心的独立职责，而不是期待从网关中间件直接获得。【推测，限已读范围】对照 网关输入上下文（私有存档）、异步上下文（私有存档）。

### 9.4 最值得继承的行为测试

以下是针对你们场景的建议，**不是 magpie 已实现的机器人能力**。【推测】可沿用 TestReject 的后续不执行断言（私有存档）、TestReconcile 的启停断言（私有存档） 和 HTTP 集成测试方式（私有存档）：

- 未匹配复读/戳一戳条件：继续处理，模型按规则调用。
- 发送成功并返回 `Handled`：只发送预期消息，后续处理器调用次数为零，模型调用次数为零。
- 静默消费：不发送消息，也不调用模型。
- 发送失败：严格按既定策略处理，不能把异常误当成功消费。
- 停用插件：后续事件不再进入其处理器，已登记订阅和任务被清理。
- 配置变更及两个群同时收消息：新配置按约定生效，群状态互不串扰。
