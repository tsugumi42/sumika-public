# 做一件事的标准流程

从接到一句需求到合进 main，每件事都走这六步。具体规矩在 [AGENTS.md](../AGENTS.md)、[LESSONS.md](../LESSONS.md) 和各份规范里，这一页只管顺序和“这一步算做完”的标准。小改动（错字、一行修复）可以合并步骤，但第 5、6 步不能省。

| 步 | 做什么 | 做完的标准 |
|---|---|---|
| 1 接需求 | 把主人的话写成“我理解成……”，有歧义就举例问；登记进[需求登记簿](需求登记.md)，和旧条冲突的把旧条改成“被取代” | 登记簿里有这条，状态是“生效”或“等确认” |
| 2 看现状 | 读要改的模块的[子系统参考](subsystems/README.md)和代码；查登记簿、[决策索引](决策索引.md)有没有相关或冲突的条目；查 `docs/notes/` 有没有同类调研 | 冲突已问主人或已标明；用到的调研写进规格开头的“参考” |
| 3 定做法 | 小改直接做。新模块、新领域、新对外接口：规格开头先填五栏开工卡（我理解成〔带正反例〕、领域正统做法〔带出处〕、最省事的字面做法够不够、不做什么、用户能看能试的验收，ADR-378），再写一页内的短规格：目标、参数、禁止的偷懒写法、已知的坑、验收标准（AGENTS 第 4 条） | 开工卡五栏都填了；规格里每条验收标准都对得上一个测试或一段日志 |
| 4 实现 | 在自己的分支或 worktree 里改；测试照[规范-测试耗时](规范-测试耗时.md)写，跑测试经 `bun ../scripts/slot.ts`；修 bug 留旧代码会红的回归测试 | 相关包和测试绿；没有绕开全机测试名额 |
| 5 验收 | 提交后 `bun scripts/merge-queue.ts add <分支>` 走合并队列；界面改动按[设计自查](设计自查.md)截图、提交说明写量到的数；高风险改动（AGENTS 第 7 条）做改坏检查并派独立复核 | 队列绿；截图、量测或复核记录在 `data/dev/` |
| 6 回填 | 登记簿该条改成“已做完”并写落在哪；规格状态头、待办（做完删条）、参考页、决策索引同步；新 ADR 在索引加一行 | 和代码同一个提交改完（`check:docs` 会查一部分） |

## 文档放哪

- **现行**（`docs/` 顶层、`docs/notes/`、`docs/subsystems/`）：现在成立的规矩和设计，一个主题一份，只写“是什么、为什么”。新建文件前先在 [README](README.md) 里找同主题的，有就改那份。
- **登记**：[需求登记簿](需求登记.md)（主人的要求）、[决策索引](决策索引.md)（ADR 现在算不算数）。
- **历史**（`docs/archive/`）：做完或被取代的规格、调研、拆解。搜索默认跳过（仓库根 `.ignore`），查来由时指名这个目录搜。
- **过程记录**（进度、交接、量测输出、截图）：写 `data/dev/`，不进 `docs/`。

## 派给代理的任务

任务说明照这六步写：背景、要做什么、范围（只改哪些文件、不碰什么）、做完的标准、交回什么格式。代理看不到这边的对话，路径写全，临时文件写会话草稿目录。代理交回的结论要自己核对文件和测试结果再转述。
