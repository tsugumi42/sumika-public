## 一、我理解成

主人 2026-11-08 的话："能不能加上 sumika 对自身数据目录的磁盘空间管理和运行中性能占用管理（内存占用结构，不同部分吃多少内存和 CPU、显存之类的）专门一个页面可视化表格，像任务管理器那样？然后一个页面用来统一管理所有前后台任务日志的 tokens 消耗统计和运行质量评估（各个部分花了多少时间运行，报错失败次数以及各自的原因分类，方便看出来是哪里出问题了之类的）"。

我理解成：左栏加一个"运行"页，里面四个标签。

| 标签 | 回答的问题 | 一句话做法 |
|---|---|---|
| 资源 | 现在谁在吃 CPU、内存、显存 | 按进程列表（主程序、`sumika-models`、命令分析用的常驻 pwsh、各 MCP 服务子进程）；主程序内部列堆、协程数、GC；各后台队列的积压。**不硬拆"每个模块各占多少内存"**：Go 的所有模块共用一个堆，拆出来的数不准，只给"进程总占用 = Go 运行时 + 其他（SQLite、图像缓冲、系统库）"这一层 |
| 存储 | 数据目录里谁占了地方、能清什么 | 按类别统计（各平台聊天库、trace.db、媒体、缩略图、备份、检查点、日志、本地模型、缓存），每类写清清理规则；给手动清理入口，会删东西的先确认，能进回收站的进回收站 |
| 用量 | 钱（token）花在哪 | 按任务类别和模型统计输入、缓存命中、输出、次数、耗时；按天、按周看 |
| 质量 | 哪里在出问题 | 每类任务的成功、失败、超时、重试次数；失败原因按类别分；最慢的环节（p50、p95）；最近的失败列表，点开看详情 |

同时提供 `sumika-ctl stats [resources|storage|usage|quality] [--json]`，界面和命令行走同一个 api（第三节）。运行页只读为主，唯一会改数据的是存储页的清理动作（第五节第 6 条、第十二节第 6 步）。

不在这次范围：金额（模型接口没有价格，`model_runs.cost_micros` 现在全是空，见第二节）；Magpie 订阅额度（已有 `magpie usage` 可查，不进这页）；结束进程；改配置；任何会让模型调用到的统计工具（模型看不到运行页数据，见第三节第 5 条）。

### 3. token 口径

`llm.Usage` 里 `Input` 是**没命中缓存的输入**，总输入 = `Input + CacheRead + CacheWrite`，缓存命中率 = `CacheRead / (Input + CacheRead + CacheWrite)`（`llm/llm.go:176`；LESSONS 里 pi 的口径同理）。用量页的"输入"列显示总输入，旁边小字写缓存命中率，不拿未缓存输入当总输入。Bun 历史行的口径第 1 步抽样核对（拿一条有 `cache_read_tokens` 的行对 Magpie 用量），不一致就在映射里按行的时间段区分。`usage_seen` 为假、`incomplete` 为真的行（供应商没回用量）单独计数并在表脚标"N 次没拿到用量，未计入"。

### 5. 统计怎么写、数据量大了怎么保证快

查询只碰窄列，示意如下（`:from`、`:to` 是毫秒时间戳，`:day_ms` 是一天的毫秒数，都由 Go 按本地时区算好传入；"天"也在 Go 里按本地时区折，避免在 SQL 里写时区）：

```sql
SELECT purpose, stage, model, (started_at - :tzoff) / :day_ms AS day,
       COUNT(*) AS runs, SUM(error IS NOT NULL) AS failed,
       SUM(input_tokens), SUM(cache_read_tokens), SUM(cache_write_tokens), SUM(output_tokens), SUM(reasoning_tokens),
       SUM(total_ms), SUM(usage_seen = 0 OR incomplete = 1) AS no_usage
FROM model_runs
WHERE started_at >= :from AND started_at < :to
GROUP BY purpose, stage, model, day;
```

- 现在 9 千行，直接查，不做汇总表。第 1 步用 `cmd/stress` 把 trace.db 灌到 10 万、50 万行测：10 万行内用量查询要在 150 毫秒内，50 万行内 500 毫秒内。**超了才做汇总表**，新建 `usage_rollup`（天 × purpose × stage × model，带失败数和耗时直方桶），由 `AddRun` 在同一事务里累加；到那一步再写迁移和回填，不提前建。
- 加索引 `ix_runs_started ON model_runs(started_at)`，再加部分索引 `ix_runs_failed ON model_runs(started_at) WHERE error IS NOT NULL`，"最近失败"列表只走它。
- p50、p95 不用 SQL 算（SQLite 没有分位函数）：按类别取出区间内成功行的 `total_ms`（只一列），在 Go 里排序取分位；一个类别超过 20 万行时抽样到 20 万并在界面标"抽样"。耗时只统计成功的请求，失败的单独看次数，不混进分位。
- 回合和工具步骤同理：`turns` 取 `ended_at - started_at`，`steps` 取 `ended_at - started_at`，按 `kind`、`name` 分组。
- 页面和命令行的查询一律走只读连接，不抢写连接。`modernc.org/sqlite` 的只读连接要和现有 `store.Set` 的开法一致，第 1 步核对。

## 三、共用 api 和命令行

1. 新包 `internal/runstats`：`Service` 有四个读方法 `Resources(ctx)`、`Storage(ctx)`、`Usage(ctx, Range)`、`Quality(ctx, Range)`，加一个只给存储页用的 `Rescan(ctx)` 和第 6 步的 `CleanPlan`、`CleanApply`。返回的结构体定义在 `internal/ctlproto`（命令行客户端只依赖协议包，不链接后台，`internal/archcheck` 守着），界面和命令行共用这些结构，不各写一份。
2. `internal/api` 新增小接口 `StatsReader`（同样四个读方法），界面通过它读，和别的页面一样不直接碰库；`runstats.Service` 实现它。
3. 命令行：`ctlproto` 加 `CmdStats = "stats"`，服务端 `ctlserver/server.go` 加一个 case，调的是同一个 `Service`。用法：

```
sumika-ctl stats                          四块各一行摘要
sumika-ctl stats resources                进程表、主程序运行时、队列
sumika-ctl stats storage                  各类别占用、上次统计时间；不触发重扫（要重扫去界面）
sumika-ctl stats usage   [--days N | --year Y | --all] [--by task|model|day] [--full]
sumika-ctl stats quality [--days N | --all] [--task <类别>] [--failures N]
每个都能加 --json
```

   `--days / --year / --all` 互斥（照 opencode）；默认 `--days 7`；不加 `--full` 只给按类别的汇总，加了才列到模型和失败原因。命令行**只读**：不接受路径、SQL、清理动作，清理只在界面做（和本机控制接口"不许任意路径"一致）。退出码沿用该规格。
4. 入口 × 能看到什么：

| 入口 | 看运行页数据 | 清理 |
|---|---|---|
| 主窗口（本地私聊、本地群聊都在这个窗口里） | 能 | 能，要确认 |
| `sumika-ctl`（管道只给当前 Windows 用户） | 能，只读 | 不能 |
| QQ 私聊、QQ 群 | 不能（QQ 不提供通用本地能力，AGENTS 安全边界） | 不能 |
| 模型可调用的工具 | 不开放：用量和失败详情里有别的会话的信息，也避免模型靠它试探 | 不能 |

5. 失败详情里的文字写入时就脱敏（走现有 `app.RedactLog` 那一路），只存类别和最多 500 字节的脱敏摘要，**不存会话名、号码、URL、令牌、模型回复原文**；会话一律显示成"本地私聊 / 本地群聊 / QQ 私聊 / QQ 群"（照[词汇表](词汇表.md)），不显示群名和号码。

|---|---|---|
| CPU | `GetProcessTimes` 取内核态加用户态时间，两次采样之差除以时间差再除以逻辑核数（任务管理器同口径） | 不要，`golang.org/x/sys/windows` 已在依赖里 |
| 内存 | 默认列"内存"取**专用工作集**（任务管理器默认列的口径）：`GetProcessMemoryInfo` 用 `PROCESS_MEMORY_COUNTERS_EX2` 的 `PrivateWorkingSetSize`；x/sys 没封装的字段用 `NewLazyDLL("psapi")` 自己调；取不到（权限或老系统）退回 `WorkingSetSize` 并把列名改成"工作集"，不静默换口径。另给"提交"列（`PrivateUsage`） | 不要 |
| 显存 | **用性能计数器（PDH）**：`\GPU Process Memory(*)\Dedicated Usage`、`\GPU Engine(*)\Utilization Percentage`，实例名形如 `pid_<pid>_luid_…_phys_0`，按 pid 解析后累加。PDH 通过 `pdh.dll` 的 `NewLazyDLL` 调用，不加依赖 | 不要 |

**显存的结论**（我在本机实测过）：这台机器是 NVIDIA 显卡，`nvidia-smi --query-compute-apps` 对每个进程都回 `[N/A]`，因为 Windows 的 WDDM 显示驱动模式下，NVML 不报单进程显存；而 PDH 计数器能按 pid 给出"专用显存"，和任务管理器是同一个数据源（实测前几名进程各自有几百 MB 到一千多 MB）。所以：

| 方案 | 可行性 | 代价 | 结论 |
|---|---|---|---|
| NVML（`nvml.dll`，purego 或 LazyDLL 动态加载） | 能取整卡已用 / 总量；**单进程显存在 WDDM 下是 N/A，不可用**；只支持 NVIDIA | 要处理驱动版本差异 | 不做；整卡总量用下面的方案同样能拿到 |
| DXGI（`IDXGIAdapter3::QueryVideoMemoryInfo`） | 只给调用方自己进程的预算和占用，看不到别的进程 | COM 调用，要写不少封装 | 不做 |
| **PDH 性能计数器** | 单进程专用 / 共享显存和各引擎利用率都有，NVIDIA、AMD、Intel 通用；整卡用 `\GPU Adapter Memory(*)\Dedicated Usage` | 通配符会展开出上百个实例，要在采样时按 pid 过滤；利用率类计数器需要两次采样才有值，所以第一次采样显示"—" | **采用**，不加依赖 |

`sumika-models` 用的 ONNX Runtime 目前只开 CPU 执行提供器（`localmodels/ort/ort.go` 只检查 `CPUExecutionProvider`），所以**本地模型进程的显存预期是 0**，显存列保留，写"当前预期为 0"；主程序因为 mygo 界面绘制会有非零显存。PDH 取不到（计数器被禁用或权限不足）时整列显示"不可用"和原因，不显示 0。

### 2. 进程从哪里来

现在各处起子进程都不暴露 pid（`embed/local.go`、`mcpclient/process.go`、`policy/analyzer.go`），所以：

1. 主路径：新包 `internal/procreg`，上一节 E 项的几个起进程的地方在 `Start` 成功后登记（类别、标签、pid），退出时撤销；几十行，不依赖任何插件。标签不含命令行参数和路径，MCP 只写配置里的服务 id。

3. 登记簿里的 pid 每次采样前核对"进程创建时间"，防 pid 被系统复用后张冠李戴。

### 3. 怎么快速算出大小

1. **单个文件**（各个 `.db`、`-wal`、`-shm`）：直接 `os.Stat`，瞬间。
2. **小目录**（日志、配置、角色卡、备份、检查点、工作结果）：打开存储标签时现遍历，用 `FindFirstFileEx`（`FindExInfoBasic`，大缓冲）的 Go 封装或 `os.ReadDir`，文件数少，十几毫秒量级，第 2 步实测。
3. **大目录**（媒体、缩略图、`dev/`、本地模型）：**不在打开页面时全量遍历**。做法：
   - 后台低优先级扫描协程（线程优先级降到 background，每处理一千项让出一次），结果写进 `maintenance_runs`：`started_at`、`ms`、`total_bytes`、`sizes_json`（各类别的字节数和文件数）、`cleaned_json`（这次清理动作的汇总）。页面显示"上次统计：时间、用时"，旁边一个"重新统计"按钮，扫描中显示进度并可取消；离开页面不取消，窗口关闭取消。
   - 媒体是内容寻址、只增不改，用**增量**：快照之后，`mediastore.Put` 每真正落下一个新文件就把字节数累加到内存计数器（第二节 D 项；同哈希已存在的不加），清理动作删文件时扣减；退出时和每次重扫后把"快照加增量"写回 `maintenance_runs` 新的一行。页面显示"约"，并写明是快照加增量。
   - **不用目录修改时间判断是否要重扫**：Windows 上目录的修改时间不随子孙文件变化，这个捷径是错的。
   - 缩略图、`dev/` 等没有写入钩子的，只靠快照，显示"统计于 N 小时前"。
4. 启动时不扫；第一次打开存储标签若 `maintenance_runs` 没有记录，显示"还没有统计过"和"开始统计"，不自动开扫（13 GB 的目录首次冷扫可能要几十秒，第 2 步量）。

### 6. 清理入口（第十二节第 6 步才做，前面都只读）

只开放这几项，每项都先"预览"再确认：

| 项 | 范围 | 处理 |
|---|---|---|
| 缩略图缓存 | `go/media-thumbs/`、`cache/thumbs/` | 可重建，确认后直接删，确认框写"会自动重新生成" |
| 过期临时文件 | 上面第 2 节里的 `.partial`、视频临时副本、链接展开临时目录 | 直接调现有函数（`CleanTmp`、`CleanVideoTmp`），不另写一份 |
| 旧日志 | `logs/` 里早于 N 天的文件（N 由主人定） | 进回收站 |
| 旧备份 | `Sumika-备份/`、`data/backups/` 里早于 N 天的 | 进回收站 |
| 开发数据 | `dev/` 里早于 N 天的 | 进回收站 |
| trace.db 瘦身（可选，主人定） | 早于 N 天的 `model_runs` 把 `sections_json`、`injected_json`、`context_json` 置空，并清掉不再被引用的 `prompt_sections` | 先备份 trace.db 到 `data/backups/`，再改；用量和质量统计不受影响（它们不读这三列） |

规则：

1. 一个入口函数 `CleanPlan(项, 参数) → 预览（将删几个文件、多少字节、是否进回收站）`，`CleanApply(预览的凭据)` 才真删；预览和执行之间文件变了就重新预览。
2. 路径必须落在固定的白名单根目录里（走 `internal/safepath` 的检查），不接受界面或命令行传来的任意路径；不跟随符号链接和联接。
3. 进回收站用 `SHFileOperationW` 加 `FOF_ALLOWUNDO`（shell32 通过 x/sys 的 `NewLazyDLL` 调，不加依赖）。回收站不可用（网络盘、目录太大回收站容纳不下，系统会提示将永久删除）时**不静默永久删**：再弹一次确认，写明"这次无法进回收站，会永久删除"。
4. 确认框写"删什么、几个文件、多少 MB、能不能找回"，按钮写"移到回收站"或"删除"，不写"确定"（界面模式规范第 5 节）。
5. 执行结果进 `task_runs`（模块 `storage-clean`），失败写类别，不吞；执行完把新的大小写回 `maintenance_runs`。
6. **永不碰**：任何 `.db`（聊天库、记忆库、trace.db 除上表的置空操作外）、`config/`、`characters/` 的卡、`go/media/` 正文。

## 七、质量标签

### 1. 数据

模型调用的成功和失败直接读 `model_runs`；其余任务读新表 `task_runs`：

```sql
CREATE TABLE task_runs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  at INTEGER NOT NULL,            -- 开始时间，毫秒
  module TEXT NOT NULL,           -- 见下表"模块"
  outcome TEXT NOT NULL,          -- ok / failed / timeout / cancelled / degraded / skipped
  class TEXT NOT NULL DEFAULT '', -- 失败或退化的原因类别，ok 时为空
  ms INTEGER,                     -- 耗时
  attempts INTEGER NOT NULL DEFAULT 1,
  root_id TEXT,                   -- 有的话，对上 model_runs 或回合
  detail TEXT                     -- 已脱敏，最多 500 字节
);
CREATE INDEX ix_task_runs_at ON task_runs(at);
CREATE INDEX ix_task_runs_module ON task_runs(module, at);
```

迁移同时给 `model_runs` 加 `error_class TEXT` 和上面第二节的两个索引；**取号前先看 main 和各分支 trace 迁移的最后一号，在 main 占号**（LESSONS）。`task_runs` 每条任务都记（行很小），保留 90 天，由存储页的"过期记录"规则清，不无限涨。

旧行没有 `error_class`：读的时候用同一个分类函数对 `error` 文字现算，**不回写真实库**。真实数据里能看到的原文样子是：连接被重置、请求被中止（有"Request aborted"和"Request was aborted"两种写法，现算时合并）、超过 N 秒没写完、流里出错、模型名 Magpie 不认识、输出不是合法 JSON 或不是合法的识图结果、思考打转、守卫超时。

### 2. 原因类别

沿用 ADR-311 和静默失败盘点的"模块 · 类别"写法；类别用各模块自己的字符串常量，页面不造全局错误树，只把"模块 · 类别"原样显示。起步词表（做的时候以各模块已有的哨兵错误为准，已有的优先，不新造）：

| 模块 | 类别 |
|---|---|
| 模型请求 | cancelled、timeout、network、stream_error、rate_limited、context_overflow、content_filter、bad_request、model_unknown、auth、server_error、parse_failed、loop_detected、budget_exhausted |
| 工具步骤 | denied（审批被拒，不算失败）、error、timeout |
| 发送（QQ） | unsupported、rejected（协议端明确拒绝，不重试）、retry_exhausted、receipt_unknown、send_check、intent_missing |
| 链接取数 | not_found、login_required、rate_limited、network、timeout |
| 链接展开换形式 | form_degrade（直接发 → 直接发转 180° → 合并转发里转 180° → 文字，每一步一行，标签写形式和结果；无回执的核实另记“核实：到了 / 没到 / 查不了”）、rotate_retry（两个转 180° 的形式）；ADR-331、333 |
| 媒体下载与转码 | tools_missing、container_invalid、capability、timeout、blocked |
| 用户钩子 | check_failed、exit_nonzero、spawn_failed、timeout、invalid_output、loop_limit、config_invalid、untrusted（成功也记，详情见[规格-用户钩子](规格-用户钩子.md)第六节） |

| 记忆整理 | write_disabled、no_store、model_failed |

"未分类"（`unknown`）单独成行并显示占比；**这个占比本身就是质量页的一个指标**，大于一成时在页面标红，提醒去补分类，而不是让它悄悄涨。

### 3. 页面

1. 范围选择同用量页。
2. 总表（按任务类别和模块）：次数、成功、失败、超时、取消、重试次数、失败率、p50 耗时、p95 耗时。耗时只统计成功的请求。点行展开到失败原因分布（原因类别、次数、占比、最近一次时间）。
3. "最慢的环节"：同一时间范围内按 p95 降序列前 10 个（任务类别 × 模型，或工具名），写明样本数；样本少于 20 的灰显，避免被个别请求误导。
4. "最近的失败"列表：时间、任务类别、模型或模块、原因类别、场合（本地私聊 / 本地群聊 / QQ 私聊 / QQ 群，悄悄话处理那一轮单列“悄悄话”）、耗时。默认 50 条，翻页，走部分索引。点一行在右侧抽屉里展开详情（界面模式规范 2.2 列表加详情）：脱敏摘要、重试了几次、对应哪个回合、供应商和模型路由、同一回合里前后的步骤（只显示名称和结果，不显示内容）。
5. 回合层：回合结局分布（done、stopped、error、budget_exhausted）和回合耗时 p50、p95；工具步骤成功、失败、未完成和中位耗时（照 opencode 的工具表）。
6. 第 3 步先覆盖**模型调用和工具步骤**（数据现成加 `error_class`）；`task_runs` 接入的模块逐个上，每个模块一个提交，页面上没接入的模块显示"未接入"，不显示 0 次失败。

## 八、界面

照界面模式规范的检查表逐条写。形态：页面外壳是"标签栏加内容区"（照设置页的形态，ADR-283 的"设置类页面照 Codex / Claude 桌面版"），资源和存储以 2.7 表格为主，质量的失败详情用 2.2 的抽屉；信息结构照任务管理器。配色、字号、圆角全部用令牌，几何四边等距、圆角同心（设计语言），不手写色值；数值上色用同一个单色强调色的深浅，不另起色板；错误用红色角标，不弹窗。

## 九、禁止的偷懒写法

- 不许把"每个模块各占多少内存"用估算凑出来；只给进程占用、Go 运行时分项和"其他"。
- 不许为了"看起来有数"给预留行（识图、子代理、/goal、/loop）填 0；没接入就写"未接入"。
- 不许用 `ReadMemStats`（停世界），不许在没有订阅者时保留采样定时器。
- 不许用目录修改时间判断大目录要不要重扫。
- 不许每次打开存储页全量遍历 13 GB 的媒体目录。
- 不许统计查询 select `sections_json`、`injected_json`、`context_json` 这三列大文本。
- 不许把 `error` 原文直接当类别展示（"Request aborted"和"Request was aborted"会变成两类）。
- 不许把失败、超时算进耗时分位，也不许把"没拿到用量"当 0 token 静默计入。
- 不许让 `unknown` 类悄悄变大：占比超过一成要标红。
- 不许在命令行或界面接受任意路径、任意 SQL；清理只走白名单根目录和预览凭据。
- 不许回写真实库来补 `error_class`；旧行读时现算。
- 不许永久删除而不明说；进不了回收站要再确认一次。
- 不许 import 各插件实现来取队列读数；只认 `runmetrics` 注册表。
- 不许把 `goal` 评判、识图等新的模型调用绕过 `modelcall` 另起一条线。

## 十、已知的坑

- 显存：NVML 在 WDDM 下单进程显存回 N/A（本机实测），别走回头路；PDH 的利用率类计数器第一次采样没有值，要两次。
- 进程 pid 会被系统复用，登记簿要核对进程创建时间。
- 本地模型子进程崩了会被重启，pid 会变，登记簿要跟着换；`--exit-on-stdin-eof` 保证主程序没了它也退，运行页不需要管孤儿进程，但"未登记的子进程"兜底行能让异常暴露出来。
- 时区：按天、按周的边界用本地时区，由 Go 算好再传给 SQL；周一起算。
- `model_runs.error` 可能含供应商回显，写入 `task_runs.detail` 和界面前必须脱敏并截断。
- `usage_seen` 为假的请求没有用量，不是 0 token。
- 数据目录可能是联接（`paths.Open` 允许），遍历前先解到真实路径，且不跟随目录内的联接和符号链接。
- 备份目录在数据目录同级（`paths.BackupRoot`），按数据根遍历会漏。
- `gate_decisions` 行数最多，哪天要瘦身是另一件事，运行页只显示它占多少。
- 并行分支加迁移前先看编号（LESSONS）。
- mygo 的图表组件没核对到；规范里已有图表浮层的规则，说明会有这类需求，缺口登记后再决定是否通用化。

- **命令行**：`sumika-ctl stats quality [--days N | --all] [--task 类别] [--failures N] [--json]`，只读；服务端不收 `--year`、`--by`、`--full`，`--task` 只认任务类别和模块键，usage、storage 不收 `--task`、`--failures`；没接入的行写"未接入"，没记录的写"这段时间没有记录"。
- **实测**（真实 `go/trace.db` 的只读副本，拷到草稿目录，用完已删；手动测试 `internal/runstats/real_trace_test.go`，`SUMIKA_REAL_TRACE` 门控）：失败按新分类全部归了类，`unknown` 是 0。最近 7 天：前台回合 284 次、失败 27（`stream_error` 20、`cancelled` 6、`budget_exhausted` 1），守卫 53 次、失败 13（全是 `timeout`）。全部范围：前台 1,247 次失败 62（含 `cancelled` 34、`stream_error` 20、`network` 3、`model_unknown` 2、`timeout`、`server_error`、`budget_exhausted` 各 1）、守卫 13（`timeout`）、记忆整理 64（`network` 29、`loop_detected` 18、`parse_failed` 11、`stream_error` 2、`timeout` 2、`model_unknown`、`server_error` 各 1）、识图 140（`network` 76、`parse_failed` 36、`timeout` 13、`stream_error` 11、`loop_detected` 2、`model_unknown`、`auth`→修正后 `server_error` 各 1）。迁移到最新后的副本上跑 `Quality`（全部范围、9 千行）用时 238 毫秒。

**第 5 步做的时候定下的细节和实测（2026-11-09，feat/run-resources，基于 main；界面一并做了，第 6 步只剩质量失败抽屉、导航角标和存储清理）**：

- **包的划分**：`internal/procreg`（登记簿，叶子包）、`internal/runmetrics`（队列注册表，叶子包）、`internal/resstat`（采样器，Windows 调用在 `*_windows.go`，别的平台是空实现，进程表只剩主程序）。`runstats.Service.Resources` 通过 `Options.Resources` 注入采样器，一行都不碰库；`api.StatsReader` 加了 `Resources`。`internal/archcheck` 加了三个包不 import 插件实现、起进程的地方确实登记了的测试。
- **登记了三处**：`embed/local.go`（sumika-models 或旧 Python 嵌入进程）、`mcpclient/process.go`（标签只写服务 id）、`policy/analyzer.go`（常驻 pwsh）。**没登记**：`tools/shell.go` 起的命令（含整棵树）和 `mediafetch` 的 ffmpeg 这类短命进程，它们是主程序的后代，会以"未登记的子进程（exe 名）"出现在表里，而不是不显示；要登记得改各自的启动路径（命令那边有 Job 对象和 taskkill 兜底，不想顺手动），排后。
- **取法**：CPU 用 `GetProcessTimes` 两次采样之差除以间隔除以逻辑核数（第一次、前值超过 30 秒时写"—"，两次采样距离不到 200 毫秒直接复用上一份）；内存列用专用工作集（`PROCESS_MEMORY_COUNTERS_EX2.PrivateWorkingSetSize`），主程序拿不到时整列退回工作集并把列名改成"工作集"，不混用；显存和 GPU% 用 PDH（`PdhAddEnglishCounterW`，中文系统计数器名被本地化，不用 English 版本会找不到），按实例名里的 pid 汇总，引擎利用率同种引擎相加、种间取最大、限到 100。取不到时整列写"不可用"和原因，行里是 null；**打开性能计数器要 400 多毫秒**，所以页面第一次采样不开它（`GPUStatus.Pending`，两列写"—"），下一次再开，命令行当场开；计数器句柄打开超过 10 分钟重开，打开失败后 60 秒内不重试。
- **进程列表节流**：`CreateToolhelp32Snapshot` 在这台机器（一千二百多个进程）上列一次要 20 到 30 毫秒，每次采样都列会超 1% 预算，所以最多 5 秒重列一次，期间只读已知进程；新登记的进程立刻重列，复用旧列表时已退出的进程（`OpenProcess` 回无效参数）从表里消失。没登记的新子进程最多晚 5 秒出现。
- **主程序内部**用 `runtime/metrics`（规格第三节的名字表，测试钉住每个名字在这个 Go 版本里都认识），不用 `runtime.ReadMemStats`：后者每次读要短暂停住整个程序。"其他"= 主程序专用工作集 − Go 运行时总量，差为负（两个数不是同一时刻读的）写"—"，不编。
- **队列表是固定的七行**（模型请求槽位、补录、识图、记忆整理、媒体下载、链接展开、本地模型池），没注册的写"未接入"。**现在只接了模型请求槽位**：`modelcall.Client` 新增 `Load()`（在跑、容量、排队数、最久等待，排队用只记开始时刻的小表，没有协程），在 `app.WireKernelBudget` 登记，"堵"的时限 30 秒（我定的起步值，没有实测依据，攒几天真实排队时长再改）。积压、最久等待没有计数的队列写"—"，状态按"能确定的"判：没人在跑就是空闲，全不知道是"—"。补录、识图、记忆整理、媒体下载、链接展开、本地模型池都还没有读数方法，各自接的时候往 `runmetrics.Register` 登记一个读数函数即可；`turn/budget.go` 里那个备用的 `modelcall.New` 没登记。
- **采样和订阅**：`resstat.Sampler` 没有协程和定时器，只在有人来要数据时采一次；界面和 `sumika-ctl` 共用桌面外壳里的同一个（`native/resstat_wire.go`）。资源标签在前台才订阅，默认 2 秒一次，可选 1、2、5 秒和暂停（暂停时订阅在、定时器不在，显示最后一次的时间）；离开标签、切走页面、窗口隐藏都取消订阅，并让采样器丢前值、放计数器句柄。命令行 `stats resources` 没有前值时自己隔 250 毫秒采两次。
- **没做的**：① 进程表行尾的 CPU 小折线（规格第四节第 5 条的 120 点环形缓冲）；② 进程表点列头排序，现在是树加 CPU 降序；③ 进程名称筛选框；④ "GPU 列可见才采 GPU"：列一直可见，所以一直采；⑤ 整卡显存用量（`\GPU Adapter Memory`）；⑥ 本地模型进程显存"当前预期为 0"的说明。
- **实测**（只量采样本身，机器上别的东西也在跑，`SUMIKA_RES_COST=1` 手动跑 `internal/resstat` 的 `TestSampleCostReport`）：稳态单次采样中位 1.2 到 1.3 毫秒（含读主程序和已知进程、运行时、显存计数器）；每 5 秒重列进程那一次约 20 到 30 毫秒（一千二百多个进程）；本进程 CPU，间隔 1 秒时 30 秒内用 156 毫秒、占单核 0.52%，间隔 2 秒时用 125 毫秒、占 0.42%，几乎全是重列进程的开销。**预算"一次采样低于 20 毫秒"在重列进程那一次略超，稳态远低于；"页面打开时单核 1%"采样部分 0.4% 到 0.5%。** 界面一帧：演示数据下（四行进程）宽窗 2048、1100、窄窗 480 一帧 p50 约 0、p95 约 1 毫秒、最大 2.1 毫秒，换数据后的第一次 `Tester.Frame`（约 20 帧）6 到 7.6 毫秒。**没量到的**：真窗口里连着开页面跑一分钟的整体 CPU（演示模式不走真采样器，真采样的整页没法用 ui-tour 巡）；上面两个数相加按估算 0.5% 左右。
- **真窗口巡视**：`ui-tour -runpage` 加了资源标签，宽窄深浅四张都过，检查器 Issues 0；窄窗（480）进程表靠横向滚动，和用量、存储页一样。

整体顺序按主人的要求：先 api 和命令行、再界面；先存储和用量，再资源和质量。第 1、2 步之间互不依赖，可以分开合；第 3 步依赖前两步；第 4、5 步互不依赖。

## 十三、需要主人定的事

> 2026-11-08 已定（ADR-321）：第 1 条按推荐（日志 90 天、`dev/` 30 天、进回收站、界面手动清）；第 2 条按推荐（媒体正文只显示大小）；第 3～5 条照推荐执行，主人有异议再改。


1. **没有清理规则的几类要不要定规则、定多少天**：日志（现在每天一个文件、没有删旧）、`dev/` 开发数据（约 1.5 GB）、旧备份、`task_runs` 的 90 天。我的推荐：日志留 90 天、`dev/` 留 30 天、备份留最近 N 份加 30 天内的，都进回收站，先在界面手动清，不自动删。
2. **媒体正文（13 GB）要不要提供清理**。它们被聊天记录引用，直接删会让历史消息里的图变成破图。我的推荐：这次不做批量删，只显示大小；以后真要做，另写规格，先做"找出没有任何聊天记录引用的孤儿文件"再说。
3. **trace.db 瘦身要不要做**：置空老的大文本列能省体积，但它们是排查提示词问题的原始材料。我的推荐：先不做，现在才几十 MB，第 6 步只留这一项为"可选"，等 trace.db 到几百 MB 再说。
4. **导航角标要不要有**：存在堵塞或最近一小时有失败就亮红点。我的推荐：要，只在有问题时出现；但会让主人经常看到红点，主人嫌烦就去掉。
5. **导航位置**：放在设置之上，还是并进设置页里做一个分类。我的推荐：独立入口，因为会经常看，不是设置。
