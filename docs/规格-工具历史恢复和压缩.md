## 一、问题和根因

话在事件库，工具在按 root 分的工作库，每个新输入一个新 root。闲置 45 分钟、换模型、换 exe、实例回收后重建，`buildWith` 只读说过的话，`restoreWork` 只查新 root，查出来是空的。

压缩两处都丢：`compactSource` 明确去掉工具，提示词固定 `compact-chat`（写的是主人的心情，不写改了哪个文件）。

查的时候还撞到两个现网 bug，都在这次修：

- **溢出恢复把本轮接两遍**。`recoverOverflow` 走 `rebuildIn → restoreWork` 把当前 root 这一轮已入库的条目装回来，再 `append(tail)` 接同一批。工具结果和只调工具的回复 `Seq == 0`，`seen` 去不了重。探针：同一次请求里说的话、工具结果、`tool_call_id` 各出现两次。`TestOverflowKeepsToolStep` 能过只是因为它没开工作记录。
- **恢复以后输出上限被压成 1**。`requestFor` 用尾部回复的 `Usage` 估上下文（`piEstimate`），恢复后尾部还带着压之前的用量，`Window - 估算 - 4096` 为负，`max_completion_tokens` 变成 1。

## 二、技术路线和参数

### 2.1 恢复（`turn/workhistory.go`）

入口：`restoreWork`。它被实例新建、`rebuildIn` 走到，所以闲置、换模型、换 exe、回收、压缩后重建都覆盖。

1. 门槛 `workHistoryEnabled`：工作记录开着 + 前台运行 + `ownerConsoleAudience` + `ConsoleScope` + `ActorKind=owner` + 本地私聊 + 不是话题线。
2. `store.WorkRootsOf(owner)` 按开根顺序倒着列这个 owner 的 root（`owner_json` 全等，含 authority），当前 root 跳过，已经比历史窗口最早一条还早就停。最多回看 2000 个 root。只读，不补写。
3. 每个旧 root 读折叠线（`ThroughOrdinal`）之后的条目，和当前 root 用同一个配对函数：缺结果的调用补“结果未知”，文字一样但**不写库**。
4. 编织：调用组挂在它前面最近一条“说过的话”（`Seq`）后面。回复既有字又有调用时把调用合到历史那条上，字以事件库为准。挂靠点不在历史窗口里（压缩切点之前、裁掉的）就不恢复，这正好是摘要已经覆盖的部分。没有任何挂靠点的 root 放不进去，跳过（只有 `/goal` 那种没存事件的输入才可能）。
5. 预算，从最新往回算，全是确定性的：

| 级别 | 条件 | 怎么放 |
|---|---|---|
| 全文 | 累计不超过 `全文预算 = min(keepTokens, 软门槛 - 固定前缀 - 已有历史)`；最新一组总是全文 | 原样 |
| 占位 | 全文之后，累计不超过 `占位预算 = min(4000, 剩余空间)` | 结果换成引用占位（有 `Ref` 给 `result_read` 的 id），不到 200 字的不换；调用参数里超过 200 字的字符串换成“（约 N 字，已省略）” |
| 不放 | 再往前 | 整组不放，历史末尾加一条 `KindWork` 带累计工作记录 |

一组一旦降级，更早的都不再升回去，前缀才稳定。

### 2.2 压缩（`turn/compact.go`）

- **选提示词**：`workHistoryEnabled` 且实例里有工具活动（改文件或跑命令至少一次、或工具调用至少 3 次、或清单有未完成）用 `compact-topic`，否则 `compact-chat`。只读过一两个文件的闲聊还是闲聊。
- **材料**：工作场景保留工具调用和结果，去掉参考信息和思考（ADR-190 第 1 条不变），过一遍 `slim`。估算超硬门槛或服务商报溢出时退到不带工具再试一次。
- **切点**：本地私聊（不论用哪份提示词）把跟在每条话后面的工具 token 算进 `keepTokens`，因为重建时这些步骤会接回来；不算的话压完工具历史还是满的，下一轮又压（`TestWorkRootSwitchGatesCountRetained` 抓到过）。
- **自检**：路径校验的原文加上调用参数和工具结果；工作场景的路径按文件名也算对上（模型写 `./src/a.go`、原文是 `src/a.go` 不该判失败）。
- **累计工作记录**：摘要末尾由宿主追加一块，模型写的同名块先删掉（工具输出可能伪造），JSON 转义 `<` `>` 防止提前闭合：

```
<work-record>
{"modified":["src/a.go"],"read":["src/b.go"],"commands":["跑测试"],"pending":["接上入口"],"unknown":["powershell：结果未知…"]}
</work-record>
```

| 字段 | 来源 | 上限 |
|---|---|---|
| `modified` | `write`、`edit` 的 `path`，加上一份 | 200，留最近的 |
| `read` | `read` 的 `path`，改过的不重复列，加上一份 | 100 |
| `commands` | `powershell` 的 `purpose`（没有用 `command`），加上一份 | 20，每条 120 字节 |
| `pending` | 当前工作状态的清单（整份替换，不累加） | 30 |
| `unknown` | 工作状态的未知项，加上一份 | 10，每条 200 字节 |

`powershell` 改的文件不追踪（只记做了什么），和 pi 一样。

### 2.3 溢出多次（`turn/overflow.go`）

本地私聊一轮最多 6 次（常量 `maxOverflowRecoveries`），其他场合 1 次。

1. 第一次：照旧压前面的轮次（一轮之内前面的轮次不会再长，后面不再压）。
2. 压完估算还超硬门槛，或者压不了、没压成：折叠本轮尾部。第 n 次保留最近 `keepTokens >> (n-1)`（最少 1000）token 的完整调用组，更早的结果换占位、长参数省略。
3. 占位还省不下 10%：更早的整组拿掉（回复的字留着），放一条 `KindWork` 带累计工作记录，同一轮只留最新的一条。
4. 这一次什么都没省下：报服务商原错误，不再请求。
5. 每次恢复后清掉尾部的 `Usage`，修输出上限被压成 1。

`recoverOverflow` 里 `restoreWork` 按 `RunID` 排除当前这一轮（`work_entries.run_id` 已有），修接两遍。tail 是权威版本：它有参考信息、图片、受控正文，库里没有。

### 2.4 其他

- 插话也记进工作记录（只本地私聊）：不记的话，第二组调用会排到插话前面。
- 不加迁移、不加配置键。`WorkRootsOf` 扫 `work_roots`，只在重建时跑；带量测（第六节）。

## 三、禁止的偷懒写法

- 不许把工具历史写进事件库、记忆或 `history.For`。聊天语义不变。
- 不许按名字、正文判断是不是本地私聊；只认宿主给的 `Identity.Scope`。
- 不许放宽 `owner_json` 全等去“找回”撤权前的记录。
- 不许恢复时执行任何工具，不许在旧 root 补写结果。
- 不许让模型写工作记录再原样信任。
- 不许用“每次重建都全带”糊过去：要有预算，估算要算进门槛。
- 溢出恢复不许静默丢用户说的话或工具调用对；不许无进展地循环请求。
- 不许为过测试把 `TestOverflowStopsRecovery`、`TestWorkNeverBecomesSharedChat` 的断言删掉。

## 四、已知的坑

- **重建时第一次请求必然缓存不中**：参考信息和思考不进工作记录，重建后的前缀和重启前不一样。这和现状一样。要保证的是重建之后只追加、两次重建逐字节相同。
- **预算线随总量移动**：下次重建时占位的边界可能往后挪，前缀从那里断。重建本来就稀少（闲置超过缓存时间、换模型），不为它做滞后。
- **去掉思考块**：`Record` 不存思考。DeepSeek（Magpie 两条线路）实测接受没有 `reasoning_content` 的工具历史。走签名思考块的模型（Anthropic 原生）可能拒绝，未测，主人用这类模型干活时要再探一次。
- **工作目录**：相对路径按当时的工作目录。现在没有入口切工作目录（审查 10），切了以后要回来看。
- **摘要请求调工具**：历史里全是工具调用时模型更容易继续调。先按提示词约束，真模型撞到再加催促或 `tool_choice`。
- **估算不等于真实窗口**：折叠按估算算，服务商窗口更小时靠每次减半收敛。
- **结果文件被清**：`result_read` 报取不到，恢复本身不读文件、不失败。

## 七、量测

### 7.1 真实模型：多步编程题，中途重启，再压缩

2026-11-09，`TestRealToolHistory`，经 Magpie 的 `auto/deepseek-flash`，本地私聊、真实 `write` 和 `powershell`。第一轮让模型建 `wordfreq.py`、`test_wordfreq.py` 并跑通；重启（`RestartIn`，丢掉内存实例）后问“刚才改过哪些文件”；再接着加 `top_n` 参数；然后压缩一次，再问。原始记录 `data/dev/tool-history/real-tool-history.json`。

| 步骤 | 请求体字节 | 工具消息 | prompt token | 缓存命中 |
|---|---|---|---|---|
| 第一轮第 1 步 | 13741 | 0 | 3480 | 99.3%（固定前缀） |
| 第一轮第 4 步（做完） | 18742 | 4 | 4757 | 96.8% |
| **重启后第一步** | 17935 | 4 | 4577 | 75.5% |
| 接着干，同实例 | 18723 → 21489 | 4 → 7 | 4719 → 5543 | 94.9% / 86.0% / 94.6% |
| 同实例再问 | 22016 | 7 | 5693 | 96.6% |
| 压缩请求（`compact-topic`，带工具） | 24005 | 7 | 6180 | 72.4% |
| **压缩后第一步** | 17737 | 0 | 4617 | 44.3% |

结果：

- 重启后模型回答“动了两个文件：wordfreq.py、test_wordfreq.py”，各自做了什么说对了；这一轮执行了 0 次工具（不重放）。
- 重启后第一步命中 75.5%：固定前缀命中，历史部分因为参考信息和思考不进工作记录，前缀和重启前不一样，符合第四节“重建第一次必然不中”；之后同实例每步 86%～97%，前缀只追加。
- 压缩：`tokens_before` 5807 → `tokens_after` 4985（估算，含固定前缀约 3400）；压缩后第一步实际 prompt 4617，比压缩前最后一步（5693）少约 19%，工具消息从 7 条变 0 条，由摘要和累计清单承接。压缩后问“改过哪些文件、跑过什么命令”，模型答对了两个文件、`top_n` 的后续改动和跑过的测试命令（5 passed、6 passed 也对）。
- 摘要（`compact-topic`）里目标、决定、验证、下一步、关键上下文都在，路径和函数签名原样，末尾宿主追加 `{"modified":["wordfreq.py","test_wordfreq.py"],...}`。第一次跑时模型把一句临时的“先不要动手”写成了长期偏好，提示词已补一句（只管眼前一步的话写进度，不进偏好）。
- 压缩后第一步命中只有 44.3%：压缩改了前缀，这是已知代价（ADR-190 第 1 条），压缩本来就稀少。

### 7.2 单元量测

见各测试的断言：恢复后调用和结果配对、两次重建逐字节相同、预算内全文条数少于总数、占位带 `result_read` id、溢出恢复后请求里工具结果只出现 1 次、输出上限不是 1。改坏检查：去掉 `Load` 里按 `RunID` 排除、去掉恢复后清 `Usage`，`TestOverflowWithWorkNoDuplicate`、`TestOverflowClearsStaleUsage` 各自变红（工具结果出现 2 次、输出上限为 1）。

重建耗时（`TestToolHistoryRebuildCost`，临时库，机器正忙时）：200 个 root、每个一次工具调用，重建一次 13.6 ms，历史窗口 30 条说过的话加 32 条工具消息。回看会在历史窗口最早一条之前停下，所以 `WorkRootsOf` 的全表扫描在窗口小时只读最近几十个 root；窗口很大（压缩快照之后话很多）时才逼近 2000 个 root 的上限，那时再量。
