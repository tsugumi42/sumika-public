# 规格：QQ 渠道（第二阶段）

> 状态（2026-11-16 整理）：主体已实现并合 main（`native/internal/channel/qq`：收消息、认人、私聊回复、掉线补录和收发自检）；群聊开口、回溯学习见各自规格。
> 2026-10-14 状态：主人定了第十一节（ADR-027），可以动手。相关决定：ADR-006（OneBot v11，只连接不部署）、ADR-007（小号给角色）、ADR-009（掉线先只做系统通知）、ADR-014（私聊和群聊分开上下文）、ADR-015（原始事件只存一份）、ADR-026（数据怎么存）。群聊插件见 [规格-群聊插件.md](规格-群聊插件.md)，它们建在这个渠道上。

## 一、这一阶段做什么、不做什么

**做**：
1. 连上 QQ 协议端（SnowLuma 优先，NapCat 也能接），可以同时连几个号，每个号绑一个角色。
2. 收：私聊、群消息、通知（撤回、戳一戳、禁言、进退群、改名片、表情回应）全部收下来，统一成内部格式存进 `events.db`。
3. 认人：QQ 号 → 主人 / 某个角色 / 群友；解析 @ 和引用。
4. **QQ 私聊**：主人私聊她的号，她像在主窗口一样回复（同一份记忆，不同的上下文）。
5. 掉线提醒、断线补录、收发自检。
6. 主窗口：竖栏加 QQ 图标，QQ 的会话列表和聊天记录（只读，耳语第三阶段）；设置里的"平台账号"。

**不做**（第三阶段或另有规格）：在群里说话（兴趣判断、发言协调、接龙上限）、耳语、群聊插件、陌生人私聊的回复策略细节。群消息这一阶段**只收不说**，但收的格式、认人、存法要一次做对，第三阶段直接用。（已被 ADR-090 改为：群里说不说由规格-群聊闸门 10.1 的档位管，"说话"档的群真发，2026-10-18 先只开主人的群）

## 二、怎么连

- OneBot v11 的**正向 WebSocket**：协议端开一个 WebSocket 服务，Sumika 去连它（ADR-006"只连接"：Sumika 不启动、不配置、不登录协议端）。
- 每个号一条连接，在 `sumika.yml` 里配：

```yaml
qq:
  owner: <主人的号>          # 主人的 QQ 号（认得出主人全靠它）
  accounts:
    - id: <她的号>         # 她的号
      character: a           # 绑给哪个角色
      # url: 不写就自动找（按本机 SnowLuma 的配置，ADR-100）；写了照用
      # token: 一般不写：存在加密的密钥里，设置 · 平台账号里"从 SnowLuma 读取令牌"读一次（ADR-071、ADR-100）；也能写成 ${QQ_TOKEN_A}
  groups: [<群A>]       # 群白名单：只收这些群
  privateAllow: []           # 私聊白名单：除了主人，还有谁私聊她会回；默认空
  # memoryAll 已被 ADR-242 取消（2026-11-04）：不再有"私聊全记忆"白名单
  # qqDir、protocolDir 不用手写：启动时自己找，找到了写回这里（见下面「本机目录」）
```

- 消息格式要求协议端用"数组"格式（`message_post_format: array`），不用 CQ 码字符串；连上以后先调 `get_login_info`、`get_version_info` 核对号对不对、是什么协议端。
- **同一个号不能同时被 MaiBot 和 Sumika 用**（ADR-007）：连上前检查 `get_login_info` 返回的号和配置一致；Sumika 不去碰 MaiBot、NapCat 的配置，切号由主人自己做。

### 本机目录（2026-10-15 主人提：路径不写死）

- **QQ 的目录**（qq.qqDir）：用来取小黄脸的图。先找正在运行的 QQ.exe（协议端在跑的话 QQ 一定开着），再查注册表的卸载信息；认的标准是目录里有 QQ.exe 和 ersions。
- **SnowLuma 的目录**（qq.protocolDir）：没写连接地址（url）的号，或者写了的号的口在 SnowLuma 那边不在听，就看本机所有正在监听的进程（一次查完，不逐个扫端口），顺着它的程序路径（和命令行里的绝对路径）往上找 package.json 名字带 snowluma、有 config 的目录。SnowLuma 没开时找不到。协议端日志默认取它下面的 logs（protocolLogDir 手写了就用手写的）。
- **连接地址（qq.accounts[].url）不写就自动找**（ADR-100）：每次连之前，读协议端目录里的 `config/onebot_<号>.json`（没有 `mode: "snapshot"` 的先叠加全局的 `onebot.json`），取 ws-default（没有就取第一条启用的 Universal），host 为 0.0.0.0 / 空 / :: 时用 127.0.0.1，拼成 `ws://…`。只读地址相关的几项，不写、不改 SnowLuma 的配置。找不到就不连，状态写"连不上协议端：没找到正在运行的 SnowLuma，打开它，或者在配置里写 url"，隔 60 秒再找，SnowLuma 晚开了也能接上。自动找到的地址不写回 sumika.yml，只在运行时用，状态里写"按 SnowLuma 的配置连的"。
- 启动时：配置里的目录还在就用；没配或者不在了（重装、换盘）就自己找，找到了写回 sumika.yml。设置 · 平台账号里可以"自动识别"，或者"选择文件夹"弹系统的文件夹选择窗口手动选（窗口在后台那台电脑上弹出）；选的目录不对会拒绝并说明。
- 全程只读：只看进程、端口、注册表和文件，不启动、不改 QQ 和 SnowLuma。
- **小黄脸的图**：从 <QQ 目录>/versions/<最新版本>/resources/app/resource/default-emojis 复制按 id 命名的 PNG 和 default_config.json（id → 名字、分组）到 data/cache/qq/faces/，版本变了才重新复制。超级表情也只用这里的静态图；emoji 那一组没有图，显示 emoji 字符。本机 QQ 里没有的 id 显示 [名字]。
- 本机 QQ 9.9.36 的安装目录里只有到 417 号左右的表情；更新的超级表情（自检时收到的 478、489）本机没有，显示成 [超级表情478]。
- QQ 还会把一套更全的表情下载到用户数据目录（`<Tencent Files>\nt_qq\global\nt_data\Emoji\emoji-resource`：`face_config.json` 282 个，`sysface_res\apng` 是会动的 APNG，`qlottie` 是超级表情的 Lottie 动画）。以后想让小黄脸会动可以从这里取（还没做；Tencent Files 的位置在 QQ 里可以改，要另外识别）。
- 以后（没装 QQ 的机器）：可以运行时下载 QQ 安装包、解开取同一个目录（主人的想法，还没做）。

## 三、消息的内部格式

收到的每条消息变成一个事件（`events` 表已有）。`segments_json` 是一个对象 `{ segs?: 段[], aborted?: true }`：`segs` 是下面这串"段"，只有纯文字时可以不写（文字在 `text` 列里）；`aborted` 是本地被打断的回复（第一阶段就这么存，不用迁移）。段：

| 段 | 内容 | 存法（ADR-026） |
|---|---|---|
| `text` | 文字 | 原文 |
| `at` | 被 @ 的号（`all` = 全体） | 号 |
| `reply` | 引用的消息 id | 对应到我们的事件 id |
| `image` | 图片；`sticker: true` 表示自定义表情包（NapCat 的 `sub_type=1`，SnowLuma 接上后核对） | 下载算 sha256 存 blob，段里只记哈希、尺寸。Go 2026-10-31 起先在段里存协议端给的 `url`（只留 http(s)）和 `file`（单个文件名，不能当本地路径），下载和哈希还没做；地址会过期，比较只认哈希 |
| `face` | QQ 小黄脸 | 编号 |
| `mface` | 商城表情（2026-10-26 改正：原来误写成"超级表情"；超级表情是 `face` 段带 `super` 标记的） | `emoji_id`、包号、名字 |
| `record` / `video` / `file` | 语音、视频、文件 | 元数据 + 链接，要看再下载。Go 2026-11-02 起：`url`（只留 http(s)）和 `file`（单个名字）三种都存；`file` 段另存 `file_id`（不透明标识）和 `size`（字节数，0 = 不知道），界面显示"文件名 · 大小"。SnowLuma 的 `record`、`video` 段 data 只有 `file`、`url`（`file` 可能是标识不是名字），没有时长和大小，所以这两种界面仍写"[语音]""[视频]"。下载还没做 |
| `forward` | 合并转发 | Go：段存资源 Ref，宿主异步 get_forward_msg（同一个 2 秒间隔只读通道）取树，10 层、合计 200 条，一层一行 qq_forwards；含陌生人照取，图合计最多 60 张，复用 mediafetch。桌面显示前三行预览和条数，可点开、嵌套返回；角色和记忆仍只看到 [合并转发]，不给角色展开等主人定。见规格-链接和合并转发第三节 |
| `card` | 小程序 / 分享卡片（JSON 段） | Go：完整 JSON 最多 256 KiB，Raw 预览 200 字；适配器从完整原文提取标题、简介、来源、http(s) 跳转和封面。桌面卡片点击打开浏览器，封面经 mediafetch 下载入本地媒体库才显示；认不出时 [卡片]。见规格-链接和合并转发 1.4 |
| `poke`、`dice`、`rps`、`location`、`contact` 等 | 少见的 | 类型 + 关键字段 |
| 认不出的 | — | 原样存类型和数据（截短），不丢 |

**文件到底是什么格式，看内容不看扩展名**（QQ 里扩展名经常对不上：表情包以普通图片发、gif 叫 .jpg、apng 叫 .png、还有图种）：

- 下载后读开头的几个字节（文件头）判断真实格式：PNG `89 50 4E 47`、JPEG `FF D8 FF`、GIF `GIF87a/GIF89a`、WebP `RIFF....WEBP`、AVIF / HEIC / MP4 / MOV（`ftyp` 后面的品牌）、WebM / MKV `1A 45 DF A3`、QQ 语音 SILK（`#!SILK_V3`，前面可能多一个 `02`）、AMR `#!AMR`、MP3 / OGG / WAV 等。认不出来的当普通文件。存进 blob 时记的是认出来的类型，不是扩展名。
- **是不是动图**也看内容：GIF 有不止一帧；PNG 里有 `acTL` 块就是 APNG；WebP 的 `VP8X` 头里动画标记位是 1。动图照样用 `<img>` 显示（浏览器原生会播），静态图标"静态"；"减少动态效果"打开时动图只显示第一帧。
- **图种**（图片后面接了一个压缩包）：图片按自己的结束标记（JPEG 的 `FF D9`、PNG 的 `IEND`、GIF 的 `3B`）算出图片到哪结束，后面还有数据、且是 `PK 03 04`（zip）、`Rar!`、`7z` 这类文件头，就标成"图片里藏了一个文件"。**不自动解压、不自动打开**，主窗口的图片下面多一个"里面藏了一个 xx 文件（多大）"，主人点了才另存出来；给她看的描述里也注明。
- **表情包以普通图片发出来的**：协议端标了是表情（`sub_type`）就是表情包；没标的，看这张图的哈希以前有没有被当表情包发过（自己记一张"见过的表情包"表），有就当表情包；都没有就按普通图片处理，不靠尺寸猜。
- 只处理位图和音视频；SVG、HTML 这类能带脚本的格式一律当文件，不在页面里直接渲染。
- 普通图片超过 20 MiB 不下载；QQ 正文视频已被 ADR-255 改为 ≤100 MiB 自动下载，超过等手动、报字节进度并能取消。file 段按 ADR-261 的两档：扩展名与实头一致的常见媒体 / 文档 / 文本同视频门槛，其余默认不下、能手动；直接收到与合并转发同规则，详见[收图规格第十三节](规格-QQ收图下载和断线补录.md#十三视频和文件下载后台adr-255261)。

- 会话 id：`qq:group:<群号>`、`qq:private:<她的号>:<对方号>`（私聊带上她的号：主人同时私聊两个号时是两个会话，2026-10-15 实现时改）。**会话和"哪个号看到的"分开**：同一个群被两个号看到，消息只存一份，每个号各记一条"我看到了"（就是已有的 `observations` 表：一个号绑一个角色）。用 OneBot 的 `message_id` + 会话去重（`qq_msgs` 表）。所有号的事件排进同一个队列处理，两个号同时推同一条时不会因为下载图片的等待存成两份。
- 谁"看到了"：主人、白名单里的人的私聊、白名单群的消息记给收到它的号；陌生人私聊不记（所以不会被总结、也翻不到原话）。群消息这一阶段只记"看到了"，不触发总结。
- 群友的名片簿在 `events.db` 的 `qq_people`（昵称、各群名片、曾用名、最近一次说话）；角色自己对人的印象另在记忆库的 `people` 表。见过的表情包在 `qq_stickers`。
- 她自己发出去的消息由 Sumika 发送时直接记下；从 QQ 客户端手动用小号发的，要协议端打开"上报自己的消息"（SnowLuma 的 `reportSelfMessage`，默认关，主人自己决定开不开）才收得到。
- 通知单独一类事件（`kind: notice`），不当成发言。

**给模型看的格式**（第三阶段群聊才大量用，这里先定）：每条一行，`[时间] 名字(身份)：内容`；图片写成 `[图片：描述]`，表情包 `[表情包：含义]`，引用写 `↪引用 名字：前 20 字`。群友原文里出现的"[系统]"之类框架头要转义，不能伪造（设计文档）。名字（群名片、昵称、转发里的名字、被 @ 和被引用的人）另外把半角括号换全角、冒号换空格、换行并成空格（`util/escape.ts` 的 `escapeName`）：行头里的半角括号和冒号只能是系统写的，群名片改成"主人(主人)：……"也伪造不出主人的行头（2026-10-19 审查查出来的）。

## 四、认人

- 主人：`qq.owner` 配置的号。
- 角色：`qq.accounts` 里的号 → 对应角色。另一个角色的发言认得出是谁，但不自动接她的话（设计文档"角色之间"）。
- 群友：其余的号。`people` 表（已建表，第一阶段空着）按 QQ 号记：昵称、各群名片、曾用名、最近一次说话。名字只当线索，身份认号（信息架构"人物画像"）。
- 每条消息解析出"在对谁说"：@ 了谁、引用了谁、私聊对象。

## 五、QQ 私聊

- **谁的私聊她会回**：`qq.reply` 打开时（默认关），只回白名单——主人，加上 `qq.privateAllow` 里的人。
- **陌生人**（白名单外）私聊：**只存原文，不回、不分析**——不进总结、不提炼记忆、不做任何后台判断，主窗口里能看到记录。
- 上下文：每个私聊一个会话（`qq:private:<号>`），和主窗口私聊是不同的上下文、同一份记忆（ADR-014）。
- 工具：主人 × QQ 私聊只有记忆工具，没有读写文件、跑命令（设计文档"工具与权限"，执行类默认关）。
- 回复：流式生成，**整段生成完再发**（QQ 不能边打边改）；太长的按段落拆成几条，每条之间停一下（像打字）；单条超过 QQ 上限就拆。
- 发送前守卫：发出去之前过一遍可见性检查，私密记忆的内容不能出现在发给别人的消息里（设计文档）。
- 发送失败：重试 2 次，还失败就记一条通知、告诉 `health`，主窗口那条消息标"没发出去"。
- 主人在 QQ 里打断（她还没发出去时又发了一句）：和主窗口一样，打断重新回复（ADR-020）。只中止这个 QQ 会话的那一轮，不取消主人在主窗口上待批的操作。
- 实现（2026-10-15 起）：`qq-chat` 已换成通用的 `plugins/router.ts`，收发走 `message/inbound` / `message/outbound`（见 规格-插件（私有存档） 第六节第 3 步）。下面是 2026-10-15 时的写法，留作历史：`plugins/qq-chat.ts` 听 `qq/message`，调 `agent.respond`（主窗口的 `chat` 也改成走它：会话、渠道、听众、"场合"提示词都是参数）。场合提示词 `prompts/channel-qq-private.md`（不用 Markdown、分段）。白名单里的朋友用 `{ personIds: ['qq:<号>'], privateOk: false }`，守卫是 `memory.leaks`：去掉空白标点后，对方不该看到的记忆里任意连续 10 个字出现在回复里就拦下（短于 6 个字的记忆不查），那条回复标"没发出去"。【已有】

## 六、掉线、补录、自检

- **心跳**：协议端每隔一段时间发心跳（`meta_event.heartbeat`）；超过 3 个心跳间隔没收到，或连接断开，就算掉线。
- **重连**：1 秒起，翻倍到最多 60 秒，一直重试。
- **协议端自己的日志**：SnowLuma、NapCat 都会在命令行和日志文件里写掉线、被踢下线的原因。配了 `protocolLogDir` 的话，掉线时只读地翻一下最近的日志，把相关的几行（打码令牌）附在通知中心那条记录里，方便看是网络断了还是被风控。不写、不删它的日志。
- **提醒**（ADR-009）：掉线超过 30 秒弹 Windows 系统通知"她的 QQ 掉线了"，恢复时再弹一次；主窗口竖栏 QQ 图标的角上显示状态点（正常 / 重连中 / 掉线），通知中心记一条。风控（被踢下线、`kicked_offline`）单独一种提醒。
- 实现（2026-10-15）：`plugins/qq-health.ts`。系统通知用系统自带的 Windows PowerShell 5.1 调 WinRT 通知接口（`util/notify.ts`，不装依赖）；提醒同时记进 `qq_alerts` 表，以后通知中心读。被踢下线认 NapCat 的 `bot_offline` 通知（SnowLuma 接上后按自检核对）；协议端登录的号和配置不一致单独提醒一次。协议端日志：最近改过的 .log / .txt 末尾 256 KB 里和掉线有关的最后 8 行，打码（含令牌原值）。【已有】
- **断线补录**：重连后对白名单里的每个群和最近的私聊，用 `get_group_msg_history` / `get_friend_msg_history` 拉断线期间的消息，按 `message_id` 去重后补进来，标成"补录"（主窗口有小标记）。补录的消息不触发回复。这两个接口不是 OneBot v11 标准里的，是 NapCat 等协议端的扩展；协议端没有的话就不补录，主窗口在那段时间标"这里可能漏了消息"。
- **收发自检**（设置 · 平台账号里的按钮，升级 SnowLuma 或 QQ 后跑）：逐项列出收、发是否正常——文字、图片、表情包、小黄脸、超级表情、引用、@、合并转发（收 / 发）、撤回通知、戳一戳。发的那几项只发给主人的私聊，不往群里发。
  - 实现（2026-10-15，后台部分）：`daemon/qq/selftest.ts`（各项、收到的消息算哪几项、测试用的 PNG）+ `Qq.startSelftest / selftestSend / stopSelftest`，接口 `/api/qq/selftest*`。**自检期间她的号和主人的私聊：照存、标 `selftest`、不记"看到了"、她不回**；她发出去的测试消息也一样。表情包、超级表情、@ 只测收（发超级表情要商城数据；@ 只在群里有，这一阶段不往群里发，收 @ 是主人在白名单群里 @ 她）。私聊的撤回、戳一戳平时不记，自检期间记进结果。界面（设置 · 平台账号里一步步引导）还没做，先由我用接口带着主人过。
- **私聊自动回复的开关**：`sumika.yml` 的 `qq.reply`（默认关，ADR-037；77115dc 把代码默认值也改成了 false）。人设、记忆、学习没做好之前关着：消息照收照存，她不回，也就不会触发记忆整理。

### 消息的状态标签（2026-10-15 主人提）

每条 QQ 消息存的时候带上状态，后面所有"拿消息去用"的流程按这张表过滤，不能只靠"她有没有看到"推断：

| 标签 | 在哪 | 回复 | 当前对话的上下文 | 记忆整理 | 回溯学习（以后） | QQ 页里显示 |
|---|---|---|---|---|---|---|
| 平常 | — | 按规则 | 是 | 是（她看到了的） | 是 | 照常 |
| 补录 `backfill` | segments | 不回 | 是 | 否（已被 ADR-092 改为否：她当时不在场） | 是（按"学到哪了"） | "补录" |
| 自检 `selftest` | segments + 不记看到了 | 不回 | 否 | 否 | **否** | "自检：她不回、不进记忆" |
| 陌生人 | 不记看到了 | 不回 | 否 | 否 | 否 | 照常 |
| 没发出去 `unsent` | segments | — | 是（她知道没发出去） | 是 | 否 | "没发出去" |
| 撤回 | 通知（reply_to 指向原消息） | — | 原消息标已撤回 | 原消息不整理 | 否 | 通知一行 |
| 不是她说的（原来的 `notMine`，规格-插件 第四节已改成 `origin` 的 human / external） | origin | — | 是，但标明"从你的号发出去、不是你说的" | 是，署名"她的号（不是她说的）" | 是（同样标明） | "不是她说的" |

- `notMine`：她的号发出去、但不是 Sumika 让发的——主人登录她的号手动发的，或者以前 MaiBot 之类别的程序用这个号说的（2026-10-15 主人提）。Sumika 自己发的消息，回声按"正在发的文字"认出来跳过，不会被认成 `notMine`。超时记录的认领（2026-10-19 审查 #20）：超时没确定的那一段（记在 `maybeSent`）5 分钟内，她号上对得上的回声也认成它，映射到那条回复、不另存；那段是整条回复的最后一段的，去掉"没发出去"和"发了一半"。过了 5 分钟不认，照常存成"不是她说的"。实时收到这类消息要 SnowLuma 打开 `reportSelfMessage`；没开时靠补录拿到。旧库里 204 条补录进来的她的号的消息已一次性补上这个标记。

- 新加标签时在这张表里加一行，再改各流程的过滤；回溯学习实现时第一件事是按这张表写过滤并加测试。
- 实时的学说法（表达学习）和记忆整理的过滤都在 `daemon/util/material.ts`：记忆整理不算补录、自检、陌生人（ADR-092）；学说法（以后的人物画像也一样）不算自检、陌生人，补录的算（已被 ADR-101 改：补录的是别人当时真说过的话，只是她不在场，不写成她的经历）。

## 六点五、图文混排的消息怎么显示（本地和 QQ 共用，2026-10-15 主人提）

一条消息是一串段（文字、图片、表情包、语音、视频、文件……），主窗口按原来的顺序显示，**一条消息就是一个气泡**：
- 连着的文字合成一段；图片、表情包、文件卡、语音条按位置插在文字之间，都在同一个气泡里。气泡里的图片宽度跟气泡走（不超过 320），圆角 = 气泡圆角 − 气泡内边距（同心）。
- 只有图片 / 表情包、没有文字的消息：不套气泡，用现在的"图片本身就是气泡"的样子（组件库 `ImageMessage`）。
- 只有文件 / 语音 / 视频的：用各自的卡片，不套气泡。
- 本地也一样：主人发截图加一句话、她的回复里带工具产出的图片，都按这个规则显示。
- Go 桌面：中立段由 desktopread 整理后给气泡。JSON 分享卡片显示标题、两行简介、来源和本地封面，整张点击打开原链接；合并转发显示聊天记录卡片、前三行和条数，点开窗口后复用正文、图片、表情、引用、链接和卡片的画法，嵌套有返回；认不出的段仍用说明。Bun 的 PartsMessage 已随网页退役。

## 七、主窗口（这一阶段的部分）

- 竖栏：本地下面加一个 QQ 图标，角上是连接状态点。
- 会话列表：QQ 的私聊和群，头像右下角叠"谁在聊"的角色小头像（组件库已有）；最近活动在上。
- 聊天窗口：群聊用 `MessageGroup`（有头像和名字），私聊和本地一样。只读，下面没有输入框，只放一行"主人在 QQ 里直接说就好"的提示（耳语第三阶段）。
- 设置 · 平台账号：每个号的连接地址、在线状态、绑给谁、收发自检。
- Go 的图片、小黄脸、引用、表情回应、分享卡片和合并转发已接桌面气泡；视频和语音仍是文字占位。卡片、链接和转发的输入表、参数和验收见[规格-链接和合并转发](规格-链接和合并转发.md)。
- 实现（2026-10-15）：竖栏 QQ 图标（角上状态点：都在线 / 有号在重连 / 有号掉线）、QQ 列表（群聊、私聊两组）、只读聊天窗口（`web/src/Outside.tsx`，群聊用 MessageGroup，消息用 PartsMessage，通知是居中的一行，"没发出去"和"补录"有标记）、设置 · 平台账号（状态、绑给谁、协议端）。前端的 QQ 数据在单独的 Zustand 仓库 `web/src/qq.ts`（ADR-120），QQ 来消息本地的聊天窗口不重画。接口在 `daemon/plugins/qq-console.ts`（`/api/qq/*`、按哈希取图片 `/api/blobs/:hash`，只有位图和音视频按原类型给；加 `?w=<档>` 给缩略图，见 ADR-043）。小黄脸先显示成"[表情编号]"，语音 / 合并转发 / 卡片先是一行说明；视频已经有播放器（2026-10-19，行内播放、放大看，见 `docs/设计语言.md` 第九点六）。**收发自检还没做**（要真机）。

## 八、不许偷懒

- 不许把 CQ 码字符串当消息存（用数组格式，存结构化的段）。
- 不许拿 QQ 的临时图片链接当图片身份（会变），用内容哈希。
- 不许把令牌写进日志、提示词、任何会进 git 的文件。令牌一般存在加密的密钥里（`qq.<号>.token`，ADR-071）：设置 · 平台账号里"从 SnowLuma 读取令牌"读一次存进去（ADR-100，只在主人点的时候读，界面和日志都不显示值）；也可以写成 `${环境变量名}`；日志里一律打码。（2026-10-15 主人原来定的是可以直接写在 `sumika.yml`；做了密钥（ADR-071）以后，令牌不再这样写。）
- 不许让补录的消息触发回复。
- 不许在群里发任何东西（这一阶段），自检也只发给主人。（已被 ADR-090 改为：只有档位是"说话"、注入测试全过的群发，带保险丝；自检照旧只发给主人）
- 不许在代码里写死主人或她的 QQ 号（都从配置读）。

## 九、已知的坑

- （2026-10-15 时）SnowLuma 还没装，先用一个**假的协议端**（测试里起一个本地 WebSocket，按 OneBot v11 回包）把收发、认人、补录、断线都测完；真机测试等主人装好 SnowLuma 并指定测试的号和群。不碰 MaiBot 正在用的 NapCat。
- NapCat 和 SnowLuma 在一些字段上不一样（表情包标记、文件字段、合并转发的接口名 `send_forward_msg` / `send_group_forward_msg`），按协议端分别处理，以自检结果为准。
- 小程序卡片的 JSON 结构各家 App 不一样，先收集真实样本。
- 群消息量大：白名单外的群不收，和数据规格的期限一起管住体积。
- 同一条消息可能被两个号各推一次，靠 `message_id` + 群号去重。

## 十二、第三阶段（群聊）要专门做的（2026-10-14 主人提）

- **防提示词注入**：群友很可能会故意测试（"忽略之前的指令"、伪造"[系统]"框架头、在图片文字或合并转发里藏指令、冒充主人）。要专门做一轮：群友原文一律当数据转义、框架头不能伪造（设计文档已有这条）、发送前守卫、冒充主人只认 QQ 号不认名字，再准备一套注入测试题，每次改提示词都跑一遍。
- **认出谁是 AI 群友**：群里现在不少人在玩 AI 群友。可以用的线索：QQ 官方机器人账号标记、回复的速度和时间分布（全天候秒回）、回复长度和格式（Markdown、整齐的列表）、被 @ 必回、自称或群名片里带 bot、和已知 bot 的号对照。结论记在人物画像里（"可能是 AI，依据是……"，主人可以确认或改），她和 AI 群友说话时可以不一样（比如不和它接龙、不被它带节奏）。先观察、再决定怎么用。

- **从没读过的历史里学（回溯学习，2026-10-15 主人提）**：新接的群能往上翻历史、掉线回来补录的消息，她当时都没"在场"。这些消息已经标了"补录"、不触发回复；以后让后台把它们也过一遍学习（表达方式、黑话、群里的人和关系、表情含义），和实时消息走同一套学习，但不当成"她亲身经历的对话"写进记忆（只学群的风格和人物画像，不生成"那天我在群里说了……"这类记忆）。一次补录太多时按时间分批、限速，旧的先压成摘要再学。
  - **记住学到哪了**：每个会话记一个"已学到"的位置（按消息时间，和主窗口的"看到哪了"`qq_read` 分开），学完一批往前推；重启、掉线后接着学，不重复学。往上翻拉回来的更早的消息在这个位置之前，单独记一个"往前学到哪了"。
  - **另一个对话来做**：回溯学习是后台的一个独立任务（自己的上下文、用"学习反思"岗位的模型），只读消息、只写学习结果（表达、黑话、人物画像、表情含义），不碰她和别人聊天的那个上下文，也不能发消息（"后台只读"那条）。她下次说话时，学到的东西从慢变层进来。
- **特别关心 / 关注的人**：QQ 的"特别关心"是客户端的提醒功能，协议端拿不到名单，用不上。同样的意思可以做在 Sumika 里：配置一份她关注的人，这些人说话时回复意愿高一些。MaiBot 除了固定概率还有按群里热闹程度、有没有提到她动态调整的回复意愿，做群聊回复调度时一起调研（ChatGPT），整理进 Notion 再定。
- **表达自然**：MaiBot 放了几天就学会不少黑话和表达习惯，主人觉得它比较自然。做人设时先调研它的表达学习和提示词怎么拼（见[设计](设计.md)"提示词的组织"的按场景拼装）。

- **界面上第三阶段要接的（2026-10-15 记，别漏）**：输入框里的 @ 提及和输入联想（耳语、群聊）；等你批准的浮卡（`askApproval`）接到真的审批上——主人不在那个会话时弹；合并转发展开看；小黄脸、超级表情显示成图（现在是"[表情编号]"）；表情面板（emojibase-data 中文包）。
