# 规格：她写文件时用哪种换行

> 状态：已合 main（PR#1，a72dc251f，2026-11-19；验收第 4 条真机试结果写在 a72dc251f 的提交说明里）。来源：主人 2026-11-19“这个设计本身能不能也融入到sumika里，在某些时候（github仓库内/不同的操作系统等）或者手动设置换行方式？”。起因是仓库自己的 CRLF 问题（同日 `.gitattributes` 改成 `eol=lf`）。

## 开工卡

- **我理解成**：工具“写整个文件”（`write`）落盘前，按一条固定的顺序决定用 LF 还是 CRLF，和“编辑文件”（`edit`）沿用原文件换行的做法合成一套。
  - 正例：在一个 `.gitattributes` 写了 `* text=auto eol=lf` 的仓库里，她在 Windows 上新建 `a.md`，写出来的是 LF。
  - 正例：覆盖一个已有的 CRLF 文件，写回仍是 CRLF，即使她给的正文是 LF。
  - 正例：不在任何仓库里、也没有 `.editorconfig`，在 Windows 上新建 `笔记.txt`，用 CRLF；在 Linux 上用 LF。
  - 反例：把所有文件统一改成一种换行；改动她读文件时看到的内容；碰二进制文件或被标成 `-text` 的文件。
- **领域正统做法**：
  - EditorConfig 的 `end_of_line`（lf / crlf / cr），按路径就近查 `.editorconfig`，`root = true` 停止向上查（editorconfig.org 规范）。VS Code、JetBrains 都认它，并且让它压过编辑器自己的设置。
  - Git 的检出换行规则（git-scm.com/docs/gitattributes “eol”“text”两节）：路径的 `eol` 属性优先；其次 `core.autocrlf=true` 时检出 CRLF；再其次 `core.eol`，默认跟系统。`-text` 的文件不转换。
  - 编辑器对已有文件一律沿用原换行（VS Code 打开文件时检测、保存时照旧）。
  - VS Code 的 `files.eol` 默认 `auto`，即跟系统。
- **最省事的字面做法够不够**：只加一个配置项 `lf / crlf` 不够。仓库和 `.editorconfig` 已经写明的约定会被它覆盖掉；在同一台机器上，不同项目需要的换行也不一样。
- **不做什么**：
  - 不改 `read`、`grep` 等读的结果。
  - 不批量转换已有文件。
  - 不支持单独的 CR 换行（老 Mac 格式）：`.editorconfig` 写 `cr` 的按 LF 处理并记一行日志。
  - 不做按会话单独设置。
  - 不碰 shell 命令写出来的文件，只管 Sumika 自己的写文件工具。
- **用户能看能试的验收**：
  - 在本仓库让她新建一个文件，`git ls-files --eol` 看到 `w/lf`。
  - 在桌面新建文本文件，用记事本的状态栏看到“Windows (CRLF)”。
  - 设置里把 `tools.lineEnding` 改成 `lf` 后，在桌面新建的变成 LF。

## 决定换行的顺序

`write` 落盘前，对目标的绝对路径依次判断，第一个给出答案的算数：

1. **文件已存在**：沿用它现在的换行。判断方法和 `edit` 用同一个函数：看第一个换行，CRLF 就用 CRLF，否则用 LF（现有 `edit-crlf`、`edit-mixed` 用例的语义）。文件是二进制的，或者里面一个换行都没有，就跳到第 2 步。
2. **`.editorconfig`**：取该路径最终生效的 `end_of_line`，写了就照它。
3. **Git 仓库**：路径在某个工作树里，且本机能找到 `git` 时，按 Git 检出这个文件时会用的换行来定：
   - 路径属性是 `-text`：不转换，按她给的原样写；
   - 有 `eol=lf|crlf`：照它；
   - 否则 `core.autocrlf=true` 时用 CRLF；
   - 否则 `core.eol` 是 lf / crlf 时照它；
   - 都没有就跳到第 4 步。
   - 实现上用一次 `git check-attr eol text -- <路径>` 和一次 `git config --get core.autocrlf` / `core.eol`。调用要带超时（1 秒），环境里清掉 `GIT_*`；git 不存在或失败就当不在仓库里。
4. **配置 `tools.lineEnding`**：可以填 `auto`（默认）、`lf`、`crlf`。`auto` 按系统定：Windows 上用 CRLF，其他系统用 LF。

决定之后，先把正文里的 CRLF、单独的 CR 统一成 LF，再换成选定的换行。BOM 照原样保留，规则和 `edit` 一致。

## 已知的坑

- 审批卡上看到的差分，必须就是最终写进文件的字节。决定换行的函数要在算预览时和真写时各调用一次，两次用同一个函数、同一组输入（LESSONS：审批门和执行共用“算出实际位置”的函数），不能各写一份。
- `.gitattributes` 的匹配规则很复杂，交给 `git check-attr`，不要自己解析。
- 在 worktree 里，`.git` 是一个文件而不是目录，找“在不在仓库里”时两种都要认。更简单的做法是直接跑 `git -C <父目录> rev-parse --is-inside-work-tree`。
- 一次写很多文件时，Git 查询会被调用很多次。按“仓库根 + 路径”缓存一轮回合内的结果，回合结束就清掉。
- 选新依赖（例如 `editorconfig-core-go`）时，照 AGENTS 写三行：创建时间和最近提交、维护者人数、许可证。

## 配置键

`tools.lineEnding`，可选 `auto` / `lf` / `crlf`，默认 `auto`。按 AGENTS 文档分层对照表“配置键或默认值”一行，同提交改 `native/internal/config`、`sumika.example.yml`、参考页（`docs/subsystems/tools.md`）和本规格；再加一个测试，证明改了这个值行为会变。

## 验收

1. 四步顺序各有一个 Go 测试，临时目录用 `t.TempDir()`：
   - 已有 CRLF 文件沿用 CRLF；
   - `.editorconfig` 写 `end_of_line = lf` 时压过系统默认；
   - 临时 git 仓库里 `eol=crlf` 的路径写出 CRLF，`-text` 的路径原样写；
   - 都没有时 `auto` 在 Windows 上写出 CRLF，配置成 `lf` 时写出 LF。
2. 审批预览和实际写入的字节逐字节相等，有测试。
3. 工具层对拍（`testdata/cases.json`）里的 edit 用例全部不变。write 用例是在没有仓库、没有 `.editorconfig` 的临时目录里新建文件，按第 4 步，在 Windows 上会从“原样写”变成 CRLF。这属于有意改变，按 AGENTS 技术约束“有意改变就在 Go 重录”处理：改预期，在提交说明里写明原因，每条变了的用例逐条列出。
4. 真机试一次：在本仓库和桌面各让她写一个文件，贴出 `git ls-files --eol` 的结果和记事本状态栏的截图。

## 实现记录（2026-11-19，分支 feat/write-eol）

- 代码：[`lineend`](../native/internal/lineend/lineend.go)；`tools.write` 和 `approval.Gate.Describe` 都调 `lineend.Final`；配置键 `tools.lineEnding` 默认 `auto`，设置页可改、当场生效。参考页见[工具与审批](subsystems/tools.md#go-写文件的换行featwrite-eol未合-main)。
- 新依赖 `github.com/editorconfig/editorconfig-core-go/v2` v2.6.5（间接带 `gopkg.in/ini.v1`）：2016-07 创建、最近提交 2026-11-16；主要维护者约 2 人（greut、10sr，另有 dependabot）；MIT。
- 和上面规格不同或补充的几处：
  - 缓存没做：没有“回合”可挂，实测每次 git 约 85 毫秒（本机 Defender），写一个文件预览加执行最多 4 次 git。出现感觉得到的卡顿再加，缓存键用“仓库根 + 路径”。
  - git 的环境：清掉 `GIT_*`，只留 `GIT_CONFIG_GLOBAL`、`GIT_CONFIG_SYSTEM`、`GIT_CONFIG_NOSYSTEM`（指向用户配置，不会让 git 查别的仓库；测试靠它隔开本机配置）。
  - 正文自带 BOM 照留；没带而原文件带 BOM 时保留原文件的 BOM。
  - 已有文件只看开头 1 MiB；前 8000 字节有 NUL 当二进制。
  - 网络共享和设备路径：不读原文件、不查 `.editorconfig` 和 git，预览和写入一致地落到 `tools.lineEnding`。
- 回合对拍（turn）的夹具固定 `lineend` 为 LF（`turn/main_test.go`），基线仍是 Bun 原样写，不随系统变。
- 对拍有意改变（Windows 上；Linux 上 auto 是 LF）：`tools` 的 `write-new`（`a.txt`：`甲\n乙` → `甲\r\n乙`）；`approval` 的 `write-new` 预览正文 LF → CRLF；Linux 上 `tools` 的 `write-nested`（`b.md`：`# 标题\r\n正文\r\n` → LF）。登记在 `tools/testdata/intended.json` 的 `files`（按 windows / other）和 `approval/gate_test.go` 的 `intendedNewFileEOL`。edit 用例全部不变。
