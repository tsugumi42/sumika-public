# 规格：库版本与升级护栏（P1-4）

> 状态：已做完（2026-11-16），四步都做了：护栏包 `internal/dbguard`；接进聊天库和 trace（只停一个平台、自检 S14、`sumika-ctl db status`）；记忆库；里程碑库升级回归（`store/testdata/milestones/`）和数据目录格式号按区间读。独立复核记录在 `data/dev/review-p1-4/`。**换 exe 前**还要做验收第 7 条（在恢复演练目录上跑一遍新程序的开库），见待办。

## 开工卡

- **我理解成**：每个 SQLite 库自己记“现在是第几版、最低要第几版的程序才能读”；程序开库前先只读看一眼：库比程序认识的新、而且新到程序读不了，就拒绝开这个库并说清楚；有待跑的迁移，先给这个库拍一份快照再迁；迁移中途失败，把库换回快照，只停这一个库对应的功能，别的照常启动。正例：QQ 库的第 18 号迁移在主人机器上失败 → `qq.db` 回到迁移前的样子、QQ 这一块不收不发、自检和状态里写清原因和快照在哪，本地聊天照常能用；换上修好的程序重启，自动再迁一次。反例：迁移失败整个程序起不来（现在）；回退到旧 exe 后，旧代码直接读写新结构的库（现在）；快照只拍不验、换回后只数行数。
- **领域正统做法**：Chromium `sql::MetaTable`（`sql/meta_table.h`）：每个库一张 `meta` 表记 `version` 和 `last_compatible_version`；开库时 `last_compatible_version` 大于代码的版本就判“库太新”，拒绝打开；只改加表加列的迁移不涨兼容版本。SQLite 自己的文件头也是同一个思路（第 18、19 字节分读版本、写版本）。迁移前快照用 SQLite 的 `VACUUM INTO`（已在 `internal/sqlitesnap` 用着）。
- **最省事的字面做法够不够**：只在 `openGo` 里加一句“版本比程序新就报错”不够：平台库有两条迁移轨（坑 2）、整批迁移不原子（坑 4）、失败后仍整个起不来（坑 7）、没有快照，四件事一件没解决。
- **不做什么**：不涨数据目录格式号（`DataFormat` 仍是 1，见“设计”第 7 条）；不改“角色记忆库文件在却打不开就整个不启动”（`TestSend57BrokenMemoryDBStopsOpen`，10-31 定的，保护“没有记忆却当成有”的情况）；不改 Bun 管的只读平台库的“版本必须相等”检查（冻结线，坑 8）；不做存储底座大重构（P5-10）；不做“Go 建出角色记忆库”（块 G 严重第 2 条）——已由[规格-记忆库从零建库](规格-记忆库从零建库.md)做（2026-11-16）。
- **用户能看能试的验收**：见“验收”第 1、2、6 条。

## 名词

- **库**：一个 SQLite 文件。现在有：`go/trace.db`、`go/chat/<平台>.db`（local、qq）、`shared/owner-memory.db`、`go/characters/<id>/memory.db`、记忆旁路索引 `memory-v2.db`。
- **迁移轨**：一组按号排的迁移文件和它的 goose 版本表。平台库上有两条轨：通用的 `chat`（表 `goose_db_version`）和平台自己的 `qq` / `local`（表 `goose_db_version_<平台>`）。trace 一条（`trace`），记忆库一条（`memory`）。旁路索引没有 goose，按一条只有版本号的轨记（`memory-index`）。
- **块**：一个库停了会影响的那部分功能。平台库 = 这个平台；trace = 整个后台（核心块）；主人共用记忆库、角色记忆库 = 记忆。

## 设计

### 1. 版本表

每个库一张 `sumika_schema`，每条迁移轨一行：

| 列 | 含义 |
|---|---|
| `track TEXT PRIMARY KEY` | 迁移轨名：`chat`、`qq`、`local`、`trace`、`memory`、`memory-index` |
| `version INTEGER NOT NULL` | 这个库这条轨现在的版本（等于 goose 表里最大的已应用号） |
| `min_reader INTEGER NOT NULL` | 最低能读这个库的程序版本（程序认识的这条轨最大号 ≥ 它才能开） |
| `migrated_by TEXT NOT NULL` | 最后一次写这行的程序（构建的 `vcs.revision` 前 9 位，取不到写 `dev`） |
| `migrated_at TEXT NOT NULL` | 时间，RFC 3339 |

- **不用 `PRAGMA user_version`**：平台库一个文件两条轨，一个整数装不下；`user_version` 也没有“最低可读”。数据目录与备份规格第三节那句同提交改成指向本规格。
- **不经 goose 建**：`CREATE TABLE IF NOT EXISTS` 和写行在同一个事务里，由护栏自己做，不占迁移号；goose 只当执行器，“现在第几版”以 goose 表为准，`sumika_schema` 补“最低可读”和来历。两者不一致（上次迁完、写版本表之前崩了）时，以 goose 表的版本为准补写这一行。
- **不删、不改名 goose 表**：`OpenFresh` 靠 `goose_db_version` 在不在区分 Bun 库和 Go 库（坑 17）。

### 2. 最低可读版本从哪来

- 每个迁移文件第一行写一个标记：`-- sumika: compatible`（只加表、加可空列、加索引，旧程序照样能读写）或 `-- sumika: breaking`（改列含义、删列、改触发器语义等，旧程序读写会出错）。
- 程序对每条轨算两个数：`latest` = 嵌入的最大号；`minReader` = 最大的 `breaking` 号（没有就是这条轨的第一个号）。迁完后写进 `sumika_schema` 的 `min_reader` 就是这个 `minReader`。
- **存量迁移**（本规格落地时已有的文件）一律按 `breaking` 算，不回头加标记：每条轨在代码里登记一个“护栏起点号”（chat 17、qq 8、local 3、trace 21、memory 3、memory-index 1），起点号及以前的文件不要求标记、都算 `breaking`；之后的新文件必须带标记，没有就测试红（检查放 `internal/archcheck` 或护栏包自己的测试，读嵌入的文件系统）。
- **新迁移不写 Down**：起点号之后的文件出现 `-- +goose Down` 且下面有语句就测试红。回退靠快照（块 G 第 5 条）。存量的 Down 不动。

### 3. 开库顺序（每个库文件一次，包住它所有的轨）

护栏的单位是**文件**：平台库的 `chat` 轨和平台轨一起处理，第二条轨失败时第一条轨已提交的改动也一起换回（坑 2、4）。顺序：

1. **文件不存在**：照现在新建、跑完所有轨，写版本表，结束（新库没有可保护的数据，不拍快照）。新建中途失败：这个文件是这次建的，关掉并删掉它和旁文件，块不可用，原因 `create_failed`。只有版本号、没有迁移文件的轨（`memory-index`）不跑 goose，只写版本表。测试模板那条捷径（`openGo` 里拷模板）拷出来的库也必须已经带版本表（模板在写完版本表之后才存，坑 16）。
2. **只读探查**：用只读连接（`mode=ro`）查 `sqlite_master`：有没有 `sumika_schema`、各 goose 表在不在；在的就读每条轨的已应用最大号和 `min_reader`。**探查不写库、不建表、不用 goose 的 Provider**（坑 3）。
3. **太新**：任一条轨 `min_reader` 大于程序这条轨的 `latest` → 这个库**拒绝打开**，块不可用，原因写“这个库被较新的 Sumika（<migrated_by>）升级过，请用新版本打开”。没有版本表的库不会走到这里（见第 6 条）。
3a. **版本表落后或缺行，又比程序新**：某条轨 goose 的号大于程序的 `latest`，而且版本表里没有这一行（或没有版本表）、或记的 `version` 小于 goose 的号（较新的程序迁完、写版本表之前崩了）→ `min_reader` 无从得知或不可信，按“太新”处理。
3b. **认不出的库**：有用户表、却一张 goose 表都没有 → 拒开，原因 `unknown_schema`（可能是 Bun 建的库或别的程序的库，不能当 0 版去迁）。例外：调用方声明这条轨接受“没有 goose 表的旧库”（记忆库：Bun 建的老库就是这样，由 `memory.Migrate` 自己认）。0 字节或一张表都没有的文件按“文件不存在”走新建。
3c. **探查本身失败**（不是 SQLite、表结构读不懂、`min_reader` 不是整数）→ 块不可用，原因 `probe_failed`；文件不动，错误消息不带库里单元格的值。
4. **较新但能读**：某条轨库的版本大于程序的 `latest`、但 `min_reader` 不大于 → 正常打开，**不迁移、不改版本表**，日志一次“库比程序新，按兼容版本打开”。
5. **没有待跑的迁移**：正常打开；版本表缺行或落后就补写（单个事务，不拍快照）。
6. **有待跑的迁移**：
   1. 先查空间：库目录所在盘剩余空间不到库文件（含 `-wal`）大小的 2 倍 → 不迁移，块不可用，原因“磁盘空间不够拍迁移前快照”。
   2. 拍快照：`sqlitesnap.IntoFile` 拍到快照目录（第 5 条），`.partial` 名字写完再改名；拍完 `sqlitesnap.Inspect` 必须通过，再核对快照里每条轨的 goose 最大号等于第 2 步读到的号。任何一步失败 → 不迁移，块不可用，原因写清是哪一步。
   3. 打开可写连接，按轨依次迁移（平台库先 `chat` 后平台轨），全部成功后写版本表（一个事务）。
   4. **任何一条轨失败**：关掉这个库的所有连接 → 换回（第 4 条）→ 块不可用，原因“第 <号> 号迁移失败：<错误>；库已换回迁移前（快照在 <路径>）”，号从 goose 的错误里取出来。迁移途中 `ctx` 被取消：照样换回（换回和验证不受取消影响），返回取消错误本身，不算 `restore_failed`。
   5. 进程在迁移途中被杀：goose 每个文件一个事务，库停在某个完整的中间版本；下次启动对这个中间状态再拍快照、接着迁（已知限制，不另做恢复）。
7. 同一进程里对同一个文件的两次开库互斥（按绝对路径加锁）；跨进程靠数据目录锁。把句柄交给调用方之前护栏已经走完；护栏期间这个文件没有别的连接（自检、备份、记忆打开方都在开库之后才起，坑 6；第 2 步实现时用测试守住这个顺序）。

### 4. 换回

- 先关这个库的所有连接；把快照复制到同目录的临时文件、落盘，再改名覆盖原库（Windows 上改名被拒照密钥库的做法重试几次）；然后删掉原库旁边的 `-wal`、`-shm`、`-journal`（坑 5，残留的预写日志套在换回的主文件上会把库弄坏），删除和改名用同一套重试；删不掉时原因写明“主文件已换回、旁文件 <路径> 残留”。换回后的主文件头是回滚日志模式（`VACUUM INTO` 的产物），调用方的可写连接每次都要重设 WAL。
- 换回后用只读连接验：`integrity_check` 通过，每条轨的 goose 最大号等于迁移前的号，`sumika_schema` 等于迁移前（迁移前没有就仍然没有）。
- 换回失败（复制、改名、删旁文件、验证任一步）：除了给快照改名加 `-restorefailed`（换回失败的这份是迁移前唯一的好数据，任何保留规则都不碰它），不再动任何文件；块不可用，原因同时写出原库和快照的完整路径，让人手动处理；**绝不删快照**。
- “换回原样”的含义是**逻辑相等**：表结构（`sqlite_master` 的 `sql` 列）相同、每张表的内容哈希相同、两张 goose 表都回到旧版本。`VACUUM INTO` 的产物和原文件字节不同，不拿字节比，也不只比行数。

### 5. 快照放哪、留多久

- 目录：`<数据目录>/go/upgrade-snapshots/`，加进 `internal/paths` 的路径表（`UpgradeSnapshotDir()`）。文件名 `<库相对路径，斜杠换横线>-<轨>-v<旧>-to-v<新>-<YYYYMMDD-HHMMSS>.sqlite`。**扩展名用 `.sqlite` 不用 `.db`**，并在备份的排除名单里登记这个目录：备份兜底会把没登记的 `.db` 都再拍一遍（`backup/service.go:724-737`，坑 15 同类），快照不该进每天的备份。
- 存储统计（`internal/storagestat`）给这个目录一个类别“升级前快照”，说明“迁移前自动拍的，每个库留最近 3 份”。
- 保留：每个库留最近 3 份（按文件名里的库和时间），迁移成功后清掉更旧的。带 `-failed`（迁移失败、换回成功）的不参与这条；同一个库、同一组迁移轨、同一段“从几到几”的 `-failed` 只留最新一份（持续失败时不会每次启动多一份），旧的那份是同版本更早的状态，被新的取代。快照名的前缀用库相对数据目录的路径，调用方必须给（每个角色的库都叫 `memory.db`，只用文件名会互相清）。拍快照前清掉这个库残留的 `.partial`。
- 空间检查同时看库所在盘和快照目录所在盘。
- 一个库一次迁移最多拍一份快照。

### 6. 第一次碰到没有版本表的库

- 本规格之前的程序建的库都没有 `sumika_schema`。探查时按 goose 表推断：`version` = goose 最大号；`min_reader` 按第 2 条从程序的标记算（存量全是 `breaking`，所以等于这条轨在那个号时的值）；然后按第 3 条的 5、6 照常走，写上版本表。
- 这一步会改真实库（加一张表、写几行）。换 exe 前先在 P1-1 的恢复演练目录（真实数据的副本）上跑一遍新程序的开库，确认通过再换（验收第 7 条）。

### 7. 数据目录格式号

- 不涨 `DataFormat`。涨到 2 会让所有本规格之前的 exe 拒绝打开整个真实目录，是单向门；要涨先问主人。
- 读取规则改成区间：`sumika-data.json` 允许多一个可选的 `minReaderFormat`（缺省 = `format`）。程序 `DataFormat` ≥ 目录的 `minReaderFormat` 就能开；`format` 比程序的 `DataFormat` 新但 `minReaderFormat` 不超过时照常开、不改这个文件。现在写这个文件的地方不写 `minReaderFormat`（值和 `format` 一样时不写）。
- **已知限制**：本规格之前的程序不认版本表，回退到它们没有保护；保护从第一个带护栏的构建开始。

### 8. 块不可用之后

- **平台库**：这个平台整个关掉：不收、不发、不补录、它的通道不启动；库没开就读不到它的会话，界面上这个平台显示“这个平台的库没打开：<原因>”。**不能变成“缺着闸门、暂停状态继续跑”**（AGENTS 第 7 条：兜底后可见、可触发的人不能更多）。别的平台、记忆、本地照常。
- **trace（核心块）**：迁移失败照样换回快照，但整个后台不启动（跟现在一样，只是库已经回到原样、错误说清楚）。理由：审批结果、回合留痕都在它上面，缺了它跑不安全。
- **主人共用记忆库**：启动时自动迁移（现在就是），加快照和换回；失败后仍按现在的规则整个不启动（库已换回）。不改成只停一块，理由同“不做什么”里的记忆库那条。
- **角色记忆库**：启动时不迁移（现在就是），只做第 3 条第 2～4 步的探查：太新 → 整个不启动，原因写“记忆库被较新的 Sumika 升级过”（和“文件在却打不开”同一个规则）。迁移只在 `memory-migrate` 里做：每个库先快照、失败换回、**接着做下一个角色**，最后汇总哪几个失败（坑 11）。
- **旁路索引 `memory-v2.db`**：开的时候建 / 读它自己的 `memory-index` 轨（只有版本号，没有迁移文件，现在是 1）；太新 → 这个角色的记忆按“太新”处理；不自动删除重建（重建要重算向量，旧程序删新程序的索引是破坏性的）。
- **解除入口**（ADR-379）：不可用的原因都可以通过“换上能读它的程序或修好问题，再重启 Sumika”解除——每次启动都会重新走第 3 条，自动重试。同提交加：
  - 自检一项 `store.unavailable`（照 `mcp.quarantined` 写）：有块不可用就 bad，例子里放库、轨、原因（固定词：`too_new`、`unknown_schema`、`probe_failed`、`create_failed`、`migrate_failed`、`restore_failed`、`no_space`、`snapshot_failed`）、快照路径；备注写解除办法。
  - `sumika-ctl db status`（只读，进只读名单）：每个库、每条轨的版本、`min_reader`、程序的 `latest`、状态、最近一次快照。
- 版本检查也覆盖只读的归档打开（`OpenGoReadOnlyWith`，坑 9，宿主启动时先进的“只看历史”就是它）：只探查、不写版本表；平台库太新、认不出、探查失败时**和接收模式一样只停这个平台**（不进平台列表、记下原因、`db status` 能看到），trace 不可用才整组失败（2026-11-16 复核后改：原写“太新就拒绝”会让一个平台库太新就把整个后台卡在启动）。
- 所有平台库都不可用时，后台打开失败，错误里逐个写出每个库的原因（不能被盖成“没有能用的库”）。
- 只读或旁路的读者（存储统计等）碰到有待跑迁移的库：只探查，跳过这次，不替主程序迁移。

## 分步（每步可单独撤回、单独入队）

1. **护栏包**（不接线）：新包 `internal/dbguard`。迁移轨的定义（嵌入文件系统 + goose 表名 + 起点号）、读标记算 `latest` / `minReader`、只读探查、判定（第 3 条的 1～6）、快照（复用 `sqlitesnap`）、换回和换回后的验证、写版本表、快照保留、空间检查（可注入）。对外一个函数，形如 `Open(ctx, file, tracks, opts) (*sql.DB, Report, error)`，`Report` 说明走了哪条路、快照在哪；块不可用用一个带固定原因词的错误类型。标记和 Down 的检查。全部单元测试用注入的迁移文件系统（`fstest.MapFS`），**失败注入只靠注入的迁移文件，不加生产能触发的开关**。第一个测试先实证“goose 对比程序新的库静默通过”（盘点标的是推断）。
2. **接进聊天库和 trace**：`openGo` / `openSetOpts` 改走护栏（平台库两条轨一次）；`Set` 记下不可用的平台和原因，`For` / `ForConversation` 等取不可用平台时返回明确的错误而不是空句柄；App 跳过这个平台的通道；归档只读打开加太新检查；快照目录进路径表、备份排除、存储统计；自检 `store.unavailable`；`sumika-ctl db status`。动手前先用 code-finder 列全 `Set.For`、`ForConversation`、`byName` 的所有调用方，做成“形状 × 入口”表（行：可用、不可用、太新、较新能读、换回失败；列：每个调用方），每格记处理了 / 不可能 / 测了。**不可用状态、解除入口、自检项同一个提交**。
3. **记忆库**：主人共用记忆库走护栏（失败仍整个不启动）；角色记忆库开库时的太新检查；`memory-migrate` 每库快照、失败换回、继续下一个；旁路索引的 `memory-index` 轨。
4. **里程碑回归和目录格式**：`sumika-data.json` 的区间读取；`testdata` 放冻结的建库 SQL（不放二进制，坑 20），至少三个里程碑：chat/qq/trace 各取 2026-11-02 切 Go 那天的版本、一个中间版本、最新减一；记忆库取 Bun 时代的结构（现有 `newBunDB` 夹具的建表语句冻结下来）；数据全是编的。测试：从每个里程碑升到最新，行数不变、关键查询通过、版本表正确。生成 SQL 的工具留在测试里（`-update` 才重写）。

## 禁止的偷懒写法

- 版本检查只放在 `migrateWith` 里（测试模板路径和归档只读会漏掉，坑 16、9）。
- 探查时用 goose Provider 或任何会建表的调用。
- 换回只比行数，或拿 `Inspect` 通过就当换回成功。
- 块不可用时把这个平台当“空的”继续跑（缺闸门、缺暂停状态）。
- 失败后自动删快照；或者快照放 `.db` 扩展名进了每天的备份。
- 迁移失败用 goose `Down` 回退。
- 为了让旧测试过，把存量迁移补标 `compatible`。

## 验收

1. 故意让平台库的迁移失败（注入一个会失败的平台轨迁移，在它前面的 `chat` 轨迁移已成功）：库换回原样（表结构、每表内容哈希、两张 goose 表的版本都等于迁移前），App 照常启动，另一个平台能收能发，失败的平台不收不发；自检 `store.unavailable` 为 bad 且写出快照路径；`sumika-ctl db status` 显示这个库不可用和原因。去掉注入、再启动：自动迁移成功，块恢复。
2. 用一个内置版本号较低的程序（测试里注入较少的迁移文件）打开 `min_reader` 更高的库：拒绝并提示“被较新的 Sumika 升级过”；主库文件一个字节都没变（拒绝前后 SHA-256 相同）。只读连接在 WAL 库上会留下空的 `-wal`、`-shm`（第 1 步实测），不算改库。`min_reader` 不高于程序版本、但 `version` 更高的库：正常打开，不迁移，版本表不变。
3. 快照：有待跑迁移时快照落在 `go/upgrade-snapshots/`、扩展名 `.sqlite`、校验通过；每库只留 3 份，失败的那份不被清；备份清单里没有这个目录的文件。
4. 换回的边界：失败时原库旁边有非空的 `-wal`；换回时改名第一次被拒（注入）；换回后的验证不通过（注入）——三种都不留下坏库，最后一种块不可用、原因带两个完整路径、快照还在。
5. 空间不够（注入剩余空间）：不迁移、不拍快照，块不可用，原因 `no_space`。
6. 主人共用记忆库迁移失败：库换回原样，启动报错说清是记忆库、快照在哪。`memory-migrate` 三个角色里第二个失败：第一个、第三个迁完，第二个换回，命令最后列出失败的那个。
7. 换 exe 前演练：用 P1-1 的恢复演练（`sumika-ctl backup` 的恢复到新目录）得到真实数据的副本，用新程序对它开库一次：每个库都补上版本表、没有触发迁移、各表行数不变；输出存 `data/dev/`。这一条由主会话做，不交给代理，**不碰真实数据目录**。
8. 新迁移文件没有标记、或者带 Down 语句：测试红，报出文件名。
