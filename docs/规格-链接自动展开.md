## 一、范围、数据流和前置形状表

技术路线：`实时消息入库 → 插件准入/提链 → 共享 Service 取数和关联 → 内容政策过滤 → 有序消息形状 → 下载/渲染 → 唯一 Outlet → SnowLuma → 逐动作回执`。两个出口仍共用一个 link-reader、一份 Result 和 24 小时缓存；发送端不生成模型回复、不翻译、不让模型判短长或判 R18。取数失败、主体部分可用和发送结果分别记录。

展开范围（`linkexpand.Supports`，2026-11-09）：B 站视频、会员购、动态、专栏、小店商品、番剧、课程、音频、合集和系列（后面这几种见[页面类型和样式第九节](规格-链接页面类型和样式.md)）、X、GitHub 仓库、YouTube、抖音、网易云歌曲、pixiv，加上后接进来的小黑盒游戏页、BOOTH 商品、Steam（app、package、sharedfile、profile）、爱发电（creator、post、album、album_post）、Bluesky（post、profile）、Telegram（公开频道 post）、Misskey（note、user）、Mastodon（status、account）、Spotify（track、album、playlist、artist、episode）、TikTok（video、user）。小红书和小黑盒帖子、用户页匿名取不到，不进范围。每个站点的模板见[链接解析模板](规格-链接解析模板.md)。

具体参数：仅 QQ 私聊、QQ 群自动展开；本地私聊、本地群聊的展开 action 恒为 0。默认每消息 3 个不同干净链接；首次出现顺序不变。同一消息的正文与卡片重复链接只算一次；不同消息重复分享每次都展开，附本会话 previous_count，即“发过 x 次”（之前次数，不含本次）。origin 固定 `automation:link-reader`。自动展开不改变角色的接话档位、`qq.reply`、观察关系或详情工具权限。

## 二、触发、配置及热更新

技术路线：在现有入库提交后提供一次消息级的自动化接点，与角色观察后接点分开。它取得完整 Stored/Inbound、源消息 seq、平台消息号和接收账号；先过滤补录/自发/回声/自检/陌生人/CanTrigger，再判断展开名单。不要把它放进群闸门、拦截链 3 秒等待或 turn.OnContext。沿 `linkplugin` 的同一队列管理同一消息工作；上下文消费者和展开消费者对同一 key 共享任务，不能取两次、关联两次。新接点只需覆盖正常实时可触发 QQ 消息，不为本任务修改陌生人政策。

| `linkReader.expand.privateStatus` | `开始解析链接……`（ADR-194）；1～200 rune，拒绝纯空白、NUL | 文本编辑 |

| `linkReader.expand.bilibiliFormat` | 已删除（2026-11-08）：并入 `linkReader.expand.templates.bilibili-video` / `bilibili-mall`，旧 `card` = `@卡片`，`cover-text` = `@封面文字`，见[链接解析模板](规格-链接解析模板.md)第五节 | 站点模板页 |
| `linkReader.expand.video.enabled` | false；我定的，把 ADR-217 原 B 站默认关延续到统一视频开关（ADR-253） | 开关 |

| `linkReader.expand.imageMaxMB` | 20（ADR-333）；十进制 MB，允许 1～20 整数；QQ、SnowLuma 都没有公开的单图上限，20 是保守值，也是下载端上限；发送前检查，超过的退文字 | 数值行 |
| `linkReader.expand.video.maxMB` | 100（ADR-192、217）；十进制 MB，我定的允许 1～1000 整数；实际阈值 `maxMB × 1_000_000` 字节 | 数值行 |

会话键使用 `types.Conversation` 的现有规范串：QQ 群 `qq:group:90002`，QQ 私聊 `qq:private:90001:90003`（编造号码）。名单按会话而非发送者；私聊键含接收小号。账号路由取此次真实接收账号及其绑定角色，不能从显示名或群内“第一个角色”猜；当前单 QQ 接收号仍是装配边界，不借此支持多号发送。

共享取数 TTL 24h、队列 256、取数 worker 2 沿现有 Service/Plugin。入库回调只提链入队，满队不发状态、不做下载，记一次队列满诊断；重启不补发积压任务。同消息多于上限的余数在第一条结果/失败文字附“还有 N 条没处理”，不为余数额外发一条。45 秒现有 JobTimeout 仅限元数据阶段，不能包住后续 60 秒下载；每个链接在自己的元信息截止后独立进入媒体阶段。

热更新用不可变 LinkRuntime + 版本发布。格式、文案、下载参数在任务开始冻结；enabled、名单和 allowSensitive 作为可撤销许可，每次准备下载和每动作前重读最新值，旧快照不得保留已撤销的许可。关闭取消该出口任务，保留给她看的独立等待者；重新打开只处理此后新消息。仅改展开设置不重建 Hub、WebSocket、Intake 或 Outlet。

禁止的偷懒写法：沿旧草图增加 `expand.groups/privates` 或 `bilibili.downloadVideo` 兼容键；新旧两套并存；名单写真实号码到仓库；开黑名单模式不提示含义；worker 数量乘角色数；关开关后仍用旧许可发图。

已知的坑：群键没有 self，必须把实际接收账号一起带入任务；同一消息两角色通知不能重复展开；短链最终归一后可能与本条另一链接相同，应在最终身份上合并、返还本条名额，不多发。名单里的旧会话暂时不在目录时保留展示“当前目录不可用”，不要悄悄删去黑名单项导致放开。

验收标准：默认配置零发送；空白名单/空黑名单的差异可见。三个角色档位下相同允许消息形成相同展开计划，角色响应各自按原档位；`qq.reply=false` 不妨碍已明确允许的非陌生 QQ 私聊展开。重复投递只有一次，新消息同链接再次发且次数增加；TTL 内平台请求不增加。阻塞下载→删名单/关 R18→放行，旧媒体不外发。

## 三、内容政策和每种消息的完整形状

> 已被[规格-链接发送改版](规格-链接发送改版.md) B4 改为：内置转发模板不再先发一条“…，内容见合并转发。”，整条内容都进合并转发，第一个节点就是头部（链接、作者等）；“发过 N 次”“还有 N 条没处理”“正文未完整取得”接在第一个节点末尾。本节样例里的“动作1 `[Q(-71), T("…，内容见合并转发。")]`”以那一节为准；行间空行、推文、pixiv、视频的排法也已被同一份规格 B1、B2、B7、B8 改过。

技术路线：只消费 `linkreader.Result` 的 Field 状态和 Blocks 原序。主体 available 才可作正常展开；统计 available 的 0 写 0，未返回写“未返回”；时间为 UTC 保存、显示为 `YYYY-MM-DD HH:mm +08:00`（我定的固定展示时区，避免随进程所在时区漂移）。字段不足显示具体缺项或“正文未完整取得”（已被[规格-链接发送改版](规格-链接发送改版.md)改为：取数层的缺项说明不进群，只进运行记录），不把缺失变成零、非 AI、无图或短帖。外部字串走普通 text，不执行 CQ/HTML，不产生 @ 段。

具体参数与通用规则：连续 text 合一个节点，按 rune 超过 2000 拆（切点优先在空行、其次换行、再次句末标点，不落在链接、@用户名、#话题 中间；单条链接自己超过 2000 字就整条放一个节点，ADR-344）；image/video/gif 各在原位置成节点。转发一层、最多 80 节点（ADR-252），第 80 个位置在溢出时留给“后面还有 N 段，看原文\n<干净链接>”；N 为节点化后被省略的块数，包含因 2000 字拆出的块。标题、作者和统计不计入正文但计入节点总数。引用推文先“引用 @账号（外部内容）”，再放该层内容（已被[规格-链接发送改版](规格-链接发送改版.md) B 第 11 条改为一行“引用 名字 @账号：”）；更深引用只写“还有更深引用，看原文”，不递归跟取。Unknown block 保留原位置文字“这一段未能读取”。

成人规则在下载、封面、头像和卡片渲染之前执行：

| 数据标记 | 本会话 allowSensitive=false | allowSensitive=true |
|---|---|---|
| 明确全年龄 | 正常形状 | 正常形状 |
| 非 pixiv 成人/敏感、或无法判定 | 文字、统计和干净原帖链接；不下载/渲染/发封面、头像、图、视频、GIF或外链卡图 | 按正常形状展开媒体（ADR-217第6条），分级未知仍如实标未返回，不冒称全年龄 |
| pixiv R18、R18-G（插画/漫画/动图/小说） | 整条只剩引用 + r18Text；无标题、作者、AI 标记、标签、链接或媒体 | 正常形状，保留 R18/R18-G 标签；登录限制照旧拒绝 |
| pixiv 分级缺失、null、类型错误 | 引用 + `无法判断作品分级，未展开`（我定的）；不给标题/链接/媒体 | 同左，不以开关掩盖解析错误 |
| 登录/付费/无权读取 | 群里不发文字、换失败表情；私聊回“没解析出来”（ADR-344）；不换服务绕过 | 同左 |

pixiv“关着不解析”指本展开消费者取得最小元信息、识别 xRestrict 后立即停止：允许匿名读取资源 ID、种类和分级，不由这个消费者抓页图列表、原图、ugoira ZIP、小说正文。缓存命中也先过同样政策，不能因曾在别处打开而漏出正文；共享 Service 必须支持这个分阶段消费，不能先全量 Fetch 再过滤。本规格不改变“给她看”的独立权限或字段政策，不把展开开关作为上下文授权。其他已有授权消费者确需全文时仍可独立请求，不能把它的请求算成本展开允许。最小元信息与完整结果按完成阶段区分，缓存键仍是同一资源；不以受限消费者的部分结果覆盖已存完整结果，最小元信息也不能冒充完整正文的24小时成功缓存。

以下全部是编造数据，不是实测帖子。记法：Q(-71)=引用本会话原消息；T=文字段；I=图片段；V=视频段；G=GIF 图片段；F=[有序节点]。每行“动作”表示一次 OneBot action，未写省略号的示例即完整正文。媒体槽位是编造资源名，实际字节由假端夹具供给；所有 F 前的引用导语与 F 绑定同一结果计划。QQ 私聊会在这些结果之前先有第二、八节的状态消息，QQ 群先有回应；此处不重复列起始状态。

## 四、唯一出口、消息段、Caps 与协议帧

技术路线：仍只有一个 Outlet。一个 Part 对应一次 action；增加 `PartMessage` + 有序 `Body`（text/image/video/gif），Quote 为该动作的可选原消息号；ForwardNode 从 Name/Text 改为 Name/Body，Body 不允许 reply、node、forward、poke、react。既有 text/image/emoji 的调用者全部迁移到 Message，不保留同义发送通路；poke、react、forward 仍是各自 Part。旧独立 PartQuote 已拒绝，趁迁移删除死常量及死测试，不恢复。所有受影响的复读、回合裁决、本地适配器、假适配器、存储编解码、桌面出站展示、契约测试同提交更新。

具体参数：Body 的媒体字段是宿主签发的资源句柄，含类型/MIME、尺寸、实际字节数、可读资源和寿命，不收外部任意路径或“把 Ref 当 file://”。运行内原图 bytes、卡片 PNG/JPEG 不写计划库；计划和 events 只存资源元信息/不可复用句柄及可展示文字，不存 base64、签名 URL。回读旧已完成计划只用于历史，不发送；旧持久记录格式的读取沿存储迁移统一处理，不能双写两份新旧字段。

资源生命周期接合面也由Outlet提供：拟议的 `SendOwned` 接收同一发送参数和一组资源持有对象，仍进同一条SendHeld/发送队列，不是另一出口；原Send无资源路径也走同一实现。持有对象只暴露受管理的读入口与Release；校验/落库失败立即释放，入队后由Outlet在整计划终态且所有实际Adapter调用退出后恰好释放一次，涵盖unknown、aborted、重启清扫和未Start的Held关闭。逻辑终态先到而Write仍在退出时不得释放。撤回与停用通过计划号调用拟议 `CancelPlan`，只中止未发动作，不抹掉已confirmed；每次发送前仍检查最新许可，取消不是唯一一道保护。插件无需轮询库或猜OnPart是否涵盖unknown。E1同时迁移这一持有契约及假适配器，保留Send给无媒体调用方，不保留旧媒体Ref发送路径。

Caps 在启动时读一次，保留 QuoteGroup/Private、ForwardGroup/Private、ReactGroup；将媒体能力按场合集中为 `MediaGroup` / `MediaPrivate`，成员为 Image、ImageBase64、Video、GIF、ForwardImage、ForwardVideo、ForwardGIF（均 bool，我定的）。现有 Image 消费者一起迁移，不保留新旧两份能力。基础文字不新增 capability。每个 Body 和每个 Node.Body 都检查，不能只看外层 Forward=true。引用只与 Message 组合，Forward.Quote 始终拒绝；两步计划在同一会话队列内不可被别的计划插入。

origin 感知的发送政策是必要改动：`OutletConfig.Mode` 及其入队、排队、重试前的查询都改收 character/origin/conv，装配按注册插件身份分发。只有确认为 link-reader 的调用路径使用展开名单；其他 origin 仍走角色 Mode。调用方不得传强制发送 flag、冒充 origin 解锁。插件候选已通过并不替代出口的最新名单检查。

QQ 硬前置由既有 `qqSendMode` 抽出共用许可判断，保留 GoSend、意图/实际发送锁/protocol、full守卫及Check等启用约束、登录核号和健康、托盘暂停、通道门暂停；不能用 `ModeSpeak` 覆盖这些。消息内容是固定外部数据，但原有发送前守卫仍检查导语、正文、节点和所有要画进卡片的文字，合并检查累计文字，失败不落原文。渲染器接到的必须是检查过的文本。自动展开无“主人在问”例外。

“不经模型”的确定范围是取数、政策判断、内容编排、卡片和下载均不调用模型；既有 CheckOutbound 安全守卫可能调用模型确认，发送上线规格要求保留。本规格不擅自免掉它。若主人要求连既有安全确认也零调用，须先定等强度的无模型守卫方案；列在第十二节，在此之前不把全链零模型调用列为已满足。

禁止的偷懒写法：再造一个 Outlet、给全部 automation 提权、只在入队看名单、跳过节点或卡片文字守卫、序列化图片 bytes 到 SQLite、把 HTTP URL 或任意文件路径直接交协议端、一个未知 action 后轮试其他名字。

已知的坑：当前 `guardActions` 仅查带引用文字和文字节点，必须迁移到 Message/Node.Body 与卡片语义文字；当前回声认领按纯文字/转发类型，不足以安全认领纯图/视频。新媒体动作只靠有效 action 回包确认，除非真帧证明可核对稳定媒体身份；禁止仅按“同时间来了一张图”认领。带文字媒体组合也须比媒体，不能仅凭链接相同把另一张图认走。

验收标准：假 WebSocket 接上实际 Outlet/Adapter，逐帧断言四种媒体场合能力，缺能力在写出前拒绝。节点夹带 reply/forward、伪造 uin、失锁、暂停、名单撤销均零不合法 action；相同文字不同图片回声不能串认，迟到回包不覆写终态。真机清单见十二节。

## 五、卡片图的离屏渲染

技术路线：使用 MewTypeUI theme/文字与布局组件构建静态卡片 view；用当前 mygo v0.7.4 的 `ui.Render(view,width,height,scale)` 软件渲染得到 `image.Image`。HTTP 下载、解码、排版准备和编码都在后台单一渲染 worker，独立 Context，不借真实窗口的 Context/Element；不触发 WebView、浏览器、GPU窗口或文件截图。卡片只画已过滤、已过守卫的结构化内容，封面/头像提前解码为 Bitmap，绘制回调不 I/O。

具体参数（ADR-252只定字段、MewTypeUI离屏与内存编码，没有定像素和字体名；以下均“我定的”，字阶参考 A）：固定720物理像素宽、scale=1，不受桌面125%缩放或文字放大影响。内边距24，内容宽672；封面672×378，保比例居中留底色，不裁掉文字；区块间16。标题30px/行高40、最多2行，作者28px/行高36最多1行，日期/时长/数据24px/行高32。先度量后分配，高度随可用字段变化、上限960；圆角16，固定浅色 MewTypeUI 主题，字体取该主题已加载的中文字体栈和 fallback，不硬编码某个用户字体路径。标题溢出省略号，字段文字保留在语义计划，干净链接始终图外可复制。

标准720×720样例排版：顶部24→封面378→间隔16→标题80→间隔16→作者36→间隔16→日期与时长32→数据三行96→底26。数据按“播放/收藏/转发/评论”和额外弹幕/点赞/投币排，不能为凑齐布局漏字段；每行按实际测宽换行，最多960高度，超限只截长标题/作者、不可截关键数据。图中不嵌分享链接、二维码、无关按钮或桌面设置说明。

内存 `bytes.Buffer` 编码，PNG 为默认；PNG 超过2,000,000字节时以同图 JPEG quality=90 编码，仍超则作为渲染失败返回，不静默降分辨率。两种编码均在内存，base64只在适配器写帧时生成，不预先复制到结果缓存。PNG/JPEG含透明背景时先画不透明底色再编码，禁止黑底。编码错误返回媒体阶段原因；回固定 cover-text 格式并标“卡片未生成”，不把缺图当成功卡片。

禁止的偷懒写法：调用窗口截图、用 HTML/Playwright 作日常卡片、PNG正常路径落盘、测宽靠字符数估计、用系统缩放把720变900、持久化 UI Element、卡片漏字段但测试只断言文件非空。

已知的坑：emoji/CJK fallback、超长无空格英文、换行标题、封面旋转/坏图、空作者、0与缺统计、绘图首帧主题未应用、字体首次加载与热渲染开销不同。输入图片先查 DecodeConfig，单张解码≤40,000,000像素（我定的工程上限）；超限不解码，注明封面不可用。像素量上限不是 pixiv原图缩小下载的理由，原件发送可不解码。

验收标准：实际调用 ui.Render，解码生成 PNG/JPEG 核对宽高、字段布局界、缺字段/长标题/中文emoji可读；绘图和编码错误可见。正常路径创建文件0个、0字节；fallback文件模式只在适配器阶段出现。报告冷/热耗时、CPU、分配与进程峰值，不把截图像素相等当唯一行为测试。性能门槛见十一节。

## 六、媒体下载、GIF与文件寿命

技术路线：在 linkreader 的既有安全传输基础上加流式媒体读取，复用相同的平台分路、逐跳URL/IP校验、TLS与地址绑定、限速和冷却；不能调用当前 `request` 把100MB视频整段读进内存，也不能沿用其10秒 Client.Timeout截断60秒视频。元信息仍用10秒请求/30秒整体/4MiB；媒体客户端复用安全 Transport 和连接池，但独立流式读取、独立总截止。X走既有proxy，B站直连，其他平台按取数实现的同路由，不为下载新增随意的fake-ip域名后缀例外。

具体参数：统一 video.enabled 默认关，关闭时不请求播放信息或视频/GIF来源MP4；缩略图仍按内容政策发送。开启时单个视频从播放信息取得、下载到必要封装/转码合计60秒、100,000,000字节（可配）；多个视频串行各自预算，不能每个分片重新计时。下载前准备缩略图，结束时立即使用成功视频或缩略图，不让一个失败视频抹去主体和其他媒体。文件上限用 min(声明长度,实际限额)早拒绝，但最终以实际字节判；未知长度允许流式读到上限+1并拒绝，不先发HEAD估大小。

B站开启后按选中P补匿名播放地址，优先可直接发的MP4；DASH音轨/视频轨必须共用100MB与60秒预算，合并后再查输出大小。当前Result尚无播放地址是实现前置；匿名无直链、需登录、付费只回封面和原因。YouTube等若取数层使用yt-dlp获得元信息，不把外部工具的未校验直连下载当安全下载器；只消费其候选，通过同一受限HTTP读取。HLS/DASH清单和每个分片也必须逐跳校验，不能把外部清单URL直接交ffmpeg联网绕过。

图片优先在内存流式取并base64；单张上限20,000,000字节、20秒（我定的，沿QQ收图的数量级）。pixiv带 `Referer: https://www.pixiv.net/`，明确用原图URL；只有原图实际超此单张上限才允许一次regular候选，节点注明“原图超过20 MB，使用regular”，regular也受同上限。不因一般403/登录/网络错偷偷换小图。其他图片下载失败只在原槽位标失败。

GIF：原生GIF保留原字节；X的gif型MP4在video.enabled打开时下载并转GIF，关闭时缩略图。pixiv ugoira 是图片作品，按ADR-254无论video.enabled如何都可取帧转GIF，但必须先过分级。ugoira ZIP输入上限100MB、解包累计上限100MB、≤300帧，最长边720、输出≤15fps、单次转换60秒、最终GIF≤20MB（我定的工程初值）；保留总时长，不截掉第301帧冒充完整动图，无法满足时静态缩略图+明确原因。`frames[].delay`转换为GIF百分之一秒，累计舍入避免时长漂移。ZIP只按元数据指定帧读取，不信任路径、绝对路径、`..`、符号链接、重复帧名或膨胀尺寸；超预算立即失败，不全帧一次展开进内存。

X视频转GIF使用现有ffmpeg可执行文件，`exec.CommandContext`参数数组、不经shell；低优先级、`-threads 1`、不联网，只读已下文件，stdout/stderr封顶64KiB、诊断脱敏。ugoira可用现有Go图像库和image/gif逐帧处理；没有成熟流式编码能力时先用隔离smoke证明峰值内存，不为本任务引入未定新库。APNG/动态WebP暂只做真机能力探测，未证实会动时转换为GIF或明确静态，不伪称动态。

视频与必要转换中间件存 `<数据目录>/go/tmp/link-expand/<本进程实例>/<jobID>/`（我定的）；只写宿主管理目录，不进永久QQ收件媒体库，最终扩展名按真实内容。文件持有权由任务转给Outlet，只有所有实际写操作已经退出、资源不再被适配器读取才清理；Send返回“已入队”不是发完。明确失败的有限重试之间保留文件；确认/最终失败/未知/中止后释放，未知也不保留为自动续发材料。协议端回包后是否已读完本地文件必须真机确认；无法证明时先不启用文件模式。

正常结束删除所有本任务文件，内存资源同步释放。崩溃后在持有后台独占运行锁时清理上次实例超过1小时的无主残留，当前实例活跃文件绝不按年龄删除。删除失败记本机诊断，不称已清理；下次启动清理。持久Result/关联仍保留24小时缓存与历史快照，媒体需用再下；不另加总媒体磁盘配额（ADR-217），峰值仍须量测。

禁止的偷懒写法：只查Content-Length、音视频各放100MB、无限yt-dlp/ffmpeg后台进程、转GIF不计资源、把文件存在当完整成功、文件模式提交后立即删、未知换base64再发、视频超限改发文件段。

已知的坑：60秒下载与10秒action上传是两段时钟，不能把下载放进Adapter.Send后把发送超时放宽；协议端上传大文件可能超10秒，现有回执上限不自动增加，先记未知并列真机风险。图片和base64扩容会叠加，必须限制同时在内存的图组；一个渲染worker、最多两个媒体任务，节点图片可依次准备，但转发action最终载荷仍可能大，按实际峰值验收，失败不靠放宽资源预算。

验收标准：假HTTP端覆盖无/假长度、上限-1/正好/+1字节、DASH合计、重定向内网、取消、超时、坏容器/ZIP与regular回退；观察实际写出字节及临时目录。假协议端回包前文件可读，回包并退出读操作后文件消失。视频关闭不请求视频来源；R18关连缩略图/原图/ZIP请求都为0。测实际60秒边界可用可拨钟或可取消屏障，不靠真实睡一分钟。

## 八、开始状态与表情回应

> 2026-11-08 主会话定：不再“不擅选默认”。`startEmoji` 默认 `289`，新增 `doneEmoji`（默认 `124`）和 `failEmoji`（默认 `9`），完成时撤掉开始表情再换上完成/失败表情；私聊仍不调表情接口（真帧 failed/100）。下面的候选表和“空时不能验收”是 2026-11-04 的状态，以[链接解析模板](规格-链接解析模板.md)第六节为准。

技术路线：通过插件准入且成功入队、具备可用发送硬许可后，真正开始处理时给原消息一次开始反馈；缓存命中也反馈。群只React，QQ私聊只状态文字，不另发群“正在解析”。状态与结果均经Outlet，均为automation来源。一个源消息至多一个开始反馈，不按3个链接发三次；开始状态与结果使用源消息jobID关联，不能从成功状态推断结果已经发出。

具体参数：群 `PartReact` 指向本会话原消息号；私聊 Message `[reply原消息,text privateStatus]`（引用状态句为我定的），默认“开始解析链接……”。反馈计划提交后再启动元信息请求，不等群回应的完整回包来占住入库回调。私聊状态若明确失败/未知，保留其终态；结果是独立计划，按最新许可决定是否发，不把状态计划重放。开始回应失败只在本机诊断，不能临时改群发状态句。完成/失败不再贴第二种表情。

## 九、发送失败、未知、部分成功与关闭

技术路线：保留发送上线三态，不新增模糊的“partial=成功”终态。（下面关于“引用导语”的句子和表里三行已被[规格-链接发送改版](规格-链接发送改版.md) B4、A5 改为（ADR-360）：合并转发前不再另发导语，结果计划从转发本身开始。）结果计划中引用导语→转发逐动作推进；一段最终failed/unknown，余下未发段aborted；已confirmed的消息号与Via永久保留，不撤销、不重放。元信息失败可以预先形成一条引用+failureText，发送失败不得再发送“发送失败”递归报错。

具体参数：沿已有MaxAttempts=3（首次+最多两次）、明确失败重试间隔1秒；未知不重发。所谓“不重发”针对已确认、未知、整组重放和重启补发，不取消原规格对明确未发出的有限重试。适配器一次action10秒、Outlet兜底30秒、CloseWait5秒、既有文字/转发回声窗口5分钟；不为了大媒体悄悄加时。

| 场景 | 计划/回执、后续动作 | 保留与用户可见结果 |
|---|---|---|
| 取数整体失败，尚未结果发送 | 群里不发文字，把开始表情换成失败表情；私聊协议端不能贴表情，回写死的一句“没解析出来”引用原消息（ADR-344）；没有细节塞入群消息 | 本机诊断含jobID、固定错误类别 |
| 主体成功、部分媒体失败/超限/关闭 | 先编排缩略图或原位置原因，再正常提交结果 | 不丢好正文，不把超限叫“解析失败” |
| 导语confirmed，forward最终failed | 导语保留，forward failed，后续aborted | 原成功消息号不清除，失败提醒沿OnPart |
| 导语confirmed，forward写出无回包 | forward unknown，只一次action；后续aborted | 不换普通消息补发，不重放导语 |
| 导语本身failed/unknown | 不发forward | 已发开始反馈保留；不另发错误句 |
| 回包retcode整数0且非failed，有合法非0正/负message_id | Message/Forward confirmed并映射 | 回包迟到不覆盖先到确认 |
| retcode缺/null/字符串0/非0且非failed，缺消息号，写后断线/超时 | unknown，不重试 | 媒体不按类型/时间瞎认回声；已证明的文字/转发沿既有规则 |
| 明确status:failed，或能证明未Write的失败 | failed；按次数重试或Unsupported直接停 | 第一次最终失败提醒、连续3次暂停沿原OnPart；每段只计一次 |
| 撤回、关展开、名单撤权、托盘暂停、关闭宿主 | 未发aborted；在途等待/取消后按真实三态收尾 | 不删除真实QQ已发内容；释放资源，迟到任务不再新发 |
| 重启遇到待发/发送中 | 既有Sweep：待发aborted，发送中unknown | 不恢复几分钟前的展开，不重新下载继续发 |

消息正文、封面和媒体政策是在发送之前决定；一旦有action可能已发，不允许以“降级”名义改变Body重试。只有明确未发出的base64格式拒绝允许第四节的传输方式改变，语义内容仍相同；错误类型证据不足按unknown。通道门通知、失败提醒与暂停全复用原出口，插件不另造计数器。

禁止的偷懒写法：超时当failed、成功节点重发、Send返回计划ID就显示发送完成、失败后清空已成功回执、重启补发、媒体unknown附加一次同内容“仅文字版”、结束清理前关闭数据库。

已知的坑：action回包与回声竞争、回声先于回包、失锁时还有上传在途、关闭超时后适配器仍读文件。关闭顺序必须先停新触发和未发任务→等下载/转换取消→Outlet结束在途→清媒体持有→Service关闭→关库；不同合法上下文等待者仍要按宿主已有顺序收掉，不让共享任务越过关库。

验收标准：用屏障控制假端成功/failed/不回包/断线与关闭；精确核对action次数、三种回执、余段aborted、成功号仍存在、OnPart一次。重建进程读临时库不出新action，文件最终可删除；日志只含脱敏身份、jobID/planID、阶段、耗时、实际字节和错误类别，无base64/签名查询/令牌/正文。
