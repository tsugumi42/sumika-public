## 一、本地分两种会话

主人 2026-10-16：平时吹水不用分，干正事要隔离。

| | 闲聊（默认） | 话题（干正事时开） |
|---|---|---|
| 是什么 | 和她一直聊的那一条线 | 一件具体的事一个话题：查报错、写东西、整理文件 |
| 怎么开 | 打开就是 | 输入框上的"新话题"按钮、`/新话题`；或者她看出来"这是件正事"时问一句要不要开，主人点了就开一个新话题，把要做的事**预先填进输入框、不发送**，主人改过再发（ADR-062：闲聊和干活用的模型不同） |
| 上下文 | 只有这条线自己的 | 只有这个话题自己的，和闲聊、别的话题互不影响 |
| 记忆 | 照常写，来源标"本地闲聊" | 照常写，来源标"话题：标题"；话题结束时写一条"这件事做完了，结果是……" |
| 满了怎么办 | 每次整理完记忆，那一批就压掉；快满了还没到整理时间，先整理记忆再压（ADR-062） | 和通用的编程 / 干活代理一样（像 pi 带界面），满了按 pi 的方式压 |
| 列表里 | 角色下面第一条 | 列在闲聊下面，标题由她起（可改），做完可以"归档"；归档的能翻到、能搜到，搜索结果里排后面、带"已归档"标记 |

- 话题之间可以引用：在话题里说"刚才闲聊里提到的那个"，她可以从记忆里找，不直接读闲聊的上下文。
- 这就是信息架构里"本地私聊分话题"的设计稿落地；测试用的"从这里开始新话题"改成"开一个新话题"。

## 二、压缩

### 2.1 什么时候压

- **可用预算 = min(模型自己报的长度, 封顶) − 预留**（已经按模型长度算了）。
- 快到软门槛：先把旧的工具结果换成占位（现在就是这样）。
- 快到硬门槛：**在后台提前压好**（规格-插件第七节），她说下一句时直接用压好的，不让主人等。来不及时才现场压，现场压时输入框上显示"正在整理前面的聊天"。
- 模型报"上下文超了"：压一次再重试，只试一次，不循环（pi 的做法）。（本地私聊已被[规格-工具历史恢复和压缩](规格-工具历史恢复和压缩.md)改为最多 6 次、没进展就停，其他场合不变；已被 ADR-339 改为这样。）

### 2.2 怎么压（尽量复用 pi）

pi 的压缩代码（`pi-coding-agent` 的 `compaction`）能直接用的就用：

| 用 pi 的 | 我们改的 |
|---|---|
| 切点规则：不切在工具结果上、工具调用和结果成对；一段太长时在段内切、分两份摘要再合 | — |
| 摘要的固定格式：目标、约束和偏好、进度（做完 / 在做 / 卡住）、关键决定和理由、下一步、关键上下文；要求原样保留文件路径、函数名、报错 | 闲聊会话换一套格式：谁说了什么、她答应了什么、主人的状态和心情、还没聊完的事；加"不写'我是 AI、没有记忆'这类套话"（LESSONS 2026-10-13） |
| 第二次压缩时把上一份摘要放进去、只更新（防滚雪球） | — |
| 工具结果截到 2000 字后再交给摘要 | — |
| 用上一次请求的真实用量算大小，之后新加的才估算 | 中文按每字约 1 个 token 估（pi 按 4 个字符 1 个 token，对中文偏低，要实测确认） |

- **先写记忆，再压缩**：压掉的那段里值得长期记的，先交给记忆（带来源和消息编号）；摘要本身不写进长期记忆。
- **摘要请求和正常对话同前缀**：同一个模型时，摘要请求用一样的系统提示、工具和历史，末尾加一句"请整理前面的内容"，这样大部分 token 走缓存，又快又省。主人设了"用便宜模型压"时，界面上写明"换模型压，没有缓存"。
- **聊天区留一条分割线**（ADR-063）：压缩生效的位置画一条带说明的横线，比如"以上的聊天已经整理压缩过（压掉 120 条，留了最近 30 条）"，悬停看详情（谁触发的、压前压后多少 token）。主人看到右边缓存率突然下降时，往上一看就知道为什么。
- **压完验证**：最近几轮一条不少、工具调用都成对、摘要里提到的文件路径在原文里找得到；验证不过就不用这份摘要，退回到"只带最近的话"（现在的紧急纪元）。

### 2.3 主人能调的、不能调的

| 能调（设置 · 模型） | 默认 | 说明（界面上一行） |
|---|---|---|
| 上下文封顶 | 跟随模型（ADR-062） | 不写就用模型自己的长度；写了就最多用这么多 |
| 给回复留的余量 | 16K | 太小时长回复会被截断 |
| 压缩后保留最近原文 | 20K | 越大越不容易忘刚才的细节 |
| 闲聊自动压缩 | 开 | 关掉的话满了只带最近的话 |
| 压缩用的模型 | 和聊天同一个 | 换成便宜的会慢一点（没有缓存），但省钱 |

不开放：摘要格式、切点规则、"先写记忆再压"、原文保留（原文永远在库里，压缩只改"给模型看的"）。乱调会把压缩弄坏，或者打断缓存。

闲聊因为每次整理记忆后就压掉，上下文平时不会长到几十万；跟随模型只是上限，不代表每句话都背着那么多。

## 三、token 流程监控（参考 Magpie 的思路）

"运行"里加一页"模型调用"，看最近的调用质量好不好：

- **每次调用一行**：时间、角色、场合（本地 / 群 / 私聊 / 后台岗位）、模型和实际落到的渠道、首字多久、每秒多少字、输入 / 缓存命中 / 输出 / 思考的 token、前缀复用率、花费、成功还是失败（失败写原因）。
- **趋势**：最近一天、一周的首字时间、速度、缓存命中率，按模型分开画。
- **自动标出不对劲的**：
  - 缓存命中率突然掉下来，而且不是压缩引起的（压缩引起的标"预期的重建"，参考 Claude Code）；
  - 首字时间比这个模型平时慢一倍以上；
  - 同一个渠道连续失败；
  - 一次调用的输入特别大（快到上限了）。
- **压缩也是一行**：谁触发的（规则 / 主人手动 / 超限恢复）、压前压后多少 token、压掉几条、留几条、摘要用了什么模型、花了多久（ADR-058）。
- 数据大部分已经有（`model_runs` 表、用量页的速度），缺的是逐条列表、趋势和标记。

## 四、不许偷懒

- 不许压缩时删原文：只改给模型看的那份。
- 不许每轮都改前缀（摘要只在纪元切换时换）。
- 不许摘要失败了也写进去：失败就退回"只带最近的话"，并记一条。
- 不许把压缩引起的缓存重建算成"缓存断了"的告警。

## 五、要主人定的

都定了（ADR-062）。

## 六、验收

- 闲聊连续压缩 5 / 10 / 20 次后，回放样本里压缩前答得上的问题照样答得上（规格-插件第七节的回放集）；验证时用 `recentMessages: 0` 排除对话历史（LESSONS）。
- 后台提前压好的情况下，主人说下一句不需要等压缩。
- 压缩那一轮缓存断开标"预期的重建"，下一轮起前缀复用率回到 90% 以上。
- 话题之间互不串：在话题 A 里说的事，话题 B 的上下文里没有（记忆里可以有）。
- 模型调用页每次调用都有一行，故意让一个渠道失败、让一次缓存断掉，都被标出来。

## 七、第②步"本地分话题"的做法（2026-10-17，ADR-073）

照线框 Topics 做。这一步只做手动开话题、切换、改名、置顶、归档；分叉和 `/压缩` 放到第③步，删除和"她主动问"见 ADR-073。

- **会话 id**：闲聊还是 `console:<角色>`（永远排第一、不能归档）；话题是 `console:<角色>:topic:<编号>`。每个会话各有自己的对话实例和上下文，互不串；记忆照常按会话整理（`turn/end` 已经按会话记）。
- **表**：events.db 的 `local_topics`：编号、角色、标题、标题是谁起的（她 / 主人）、置顶时间、归档时间、建的时间、最后一条的时间。
- **接口**：列出某个角色的话题；开新话题；改名、置顶、归档 / 拿回来；原来按角色取消息、步骤、模型调用的三个接口加一个可选的 `conversation`（只认这个角色自己的会话）；WebSocket 发消息带上会话。
- **模型**：（已被 ADR-084 改为：放在配置 `characters.<角色>.topic`，不在角色卡里）话题用这个角色 `character.yml` 里的 `models.topic`（实现时和 `models.background` 放在一起，ADR-073 写的是 `topicModel`），没写就用 `model`（ADR-073 第 1 条）。设置 · 模型单独一组"话题里干活用的"，每个角色一行，第一项"跟着闲聊"；在话题里点输入框上的模型按钮换的也是这一项。
- **标题**：话题第一轮她回完以后，用后台模型（低档思考）起一个 12 个字以内的标题；失败或还没起好时显示"新话题 时:分"。主人改过的不再自动改。
- **归档**：归档时顺带整理一次这个话题的记忆（现成的总结），话题从"最近"挪到"已归档"；能拿回来。
- **界面**：本地会话栏先列角色；点进一个角色，这一栏变成"她的话题"：顶上"回到本地"和"新话题"，下面分"置顶""最近""已归档（N）"三段，闲聊排最前；每行标题、时间、一行副标题（最后一句或"等你批准"）。右键：置顶、重命名、归档。聊天顶栏写"角色名 · 话题 · N 轮"，点标题能改名。输入框里 `/新话题`。"从这里开始新话题"（测试用的分隔）改成"开一个新话题"。（已被 ADR-086 改为：点"新话题"只打开空白的，发出第一句才建出来、不说话切走什么都不留；聊天窗口顶栏不放"新话题"按钮。会话栏已被规格-本地会话栏（私有存档）改为一层：私聊 / 群聊分段、日常置顶、话题按角色折叠）
- **做成的样子**（2026-10-17）：点角色那一行进她的话题，方向键只换选中、不进去；闲聊不能归档、不能改名；归档正在看的话题会回到闲聊；她在别的话题里回复时，这个会话不显示"正在回复"；窄到只剩头像时话题行显示标题的第一个字、顶上只留"回到本地"（两层的做法已被规格-本地会话栏改掉，见那份）。`scripts/check-topics.ts`（进了 `check:ui`）在临时数据目录里查这些。
- **验收**：在话题 A 里说的事，话题 B 和闲聊的上下文里都没有（看模型实际收到的消息）；切换会话时各自的历史、注入面板、草稿互不串；归档后能拿回来；话题用的模型生效；十个角色、每个几十个话题时会话栏不卡（ADR-056 放大十倍）。

## 八、第③步"压缩"的做法（2026-10-17，ADR-074）

分四小步，每步做完能用再做下一步：

| | 做什么 | 先做的理由 |
|---|---|---|
| ③a | 纪元快照、手动 `/压缩`、聊天区分割线、压完自检、失败退回 | 话题照 pi 做，规则最明确；后面几步都靠快照 |
| ③b | 闲聊按记忆批次压（ADR-062 第 2 条） | 要先有 ③a 的快照 |
| ③c | 后台提前压好（软门槛）、模型报"上下文超了"时压一次再试 | 体验优化，③a 时先现场压 |
| ③d | 分叉 | 看第 5 条问题二 |

1. **纪元快照存哪、怎么重建**：events.db 加表 `context_epochs`：编号、会话、`from_seq`（快照之后从哪条原文接着带）、摘要、场合（闲聊 / 话题）、谁触发的（规则 / 主人手动 / 超限 / 记忆批次）、压前压后多少 token、压掉几条、留几条、用的模型、状态（成了 / 失败退回）、时间。重建实例 = 固定前缀 + 最新一份成了的快照（作为历史最前面的一条参考信息）+ `seq ≥ from_seq` 的原文。有快照的会话不再"读最近 30 条"（规格-插件第七节"重建"）；以前插过的"从这里开始新话题"分隔比快照新时照旧按分隔截。原文一条不删。
2. **切点**：自己写（pi 的 `findCutPoint` 要它的会话格式，用不上）。从最新往前数，留到约 20K token 为止（用我们按中文算的 `estimateTokens`，不用 pi 的"4 个字符 1 个 token"），切在主人说话的那一条前面；工具调用和结果不拆开；最近一轮不压。
3. **摘要怎么写**：
   - 同前缀：摘要请求用这个会话正在用的系统提示、工具定义和历史，末尾追加一句"请按下面的格式整理前面的内容"，走同一个模型；这样前面几乎全部命中缓存。pi 的 `generateSummary` 会把聊天另外拼成一段文字，前缀不一样、没有缓存，所以只借它的提示词思路，不直接调它。
   - 格式：话题用 pi 那套（目标、约束和偏好、进度、关键决定、下一步、关键上下文，原样保留路径、函数名、报错）；闲聊用第二节那套（谁说了什么、她答应了什么、主人的状态和心情、还没聊完的事）。都不写"我是 AI、没有记忆"这类套话。第二次压时把上一份摘要放进去、只更新。提示词放 `prompts/compact-topic.md`、`prompts/compact-chat.md`。
   - 先写记忆再压：压掉的那段先交给记忆整理（`memory.summarize` 整理到切点），摘要本身不进长期记忆。
4. **压完自检**：最近几轮一条不少、工具调用都成对、压完降到门槛的 80% 以下、摘要里提到的文件路径在原文里找得到。不过就不用这份，退回现在的"只带最近的话"（紧急纪元），记一条失败。
5. **主人定的**（ADR-074）：话题到 200K 就压（开始压缩的线 = min(按模型长度算的硬门槛, 200K)，设置里能改）；分叉 = 把原话题现在"给她看的那份"（最新快照 + 之后的原文）复制成新话题的记录，复制的不进记忆整理；回放验收 ③a 后先跑 5 次那档，10 / 20 次等 ③b 做完。
6. **界面**：
   - 分割线画在切点（`from_seq` 那一条前面），不是另插一条事件："以上的聊天已经整理压缩过（压掉 120 条，留了最近 30 条）"，悬停看谁触发的、压前压后多少 token、用的模型。插在列表中间，做完跑一遍 `measure-scroll-jump`。
   - `/压缩` 斜杠命令；现场压时输入框上写"正在整理前面的聊天"。
   - 右侧栏用量条上标出"到这里会自动压缩"的竖线（线框 Topics 已画）。
7. **给第④步留的**：`model_runs` 加纪元编号和"预期的重建"标记（开新纪元后的第一次请求），压缩本身记一行 `stage = 'compact'`。
8. **配置的默认值**（按第二节 2.3 改）：`agent.context.reserve` 10000 → 16384；新加 `agent.context.keepTokens` 20000（压完保留最近原文）、`agent.context.topicCompactAt` 200000（话题开始压的线，ADR-074），代替按比例留的 `keepRatio`（1M 的模型留 40% 太多）；`agent.context.autoCompactChat` 默认开；压缩用的模型默认和聊天同一个。改了照 AGENTS 的表同步 `sumika.example.yml`、参考页。
9. **不许偷懒**（在第四节之外）：不许用 pi 的 `generateSummary` 另起前缀还说"走缓存"——验收看摘要请求的前缀复用 ≥ 90%；不许用"4 个字符 1 个 token"估中文；不许在纪元中间换快照（只在建实例、一轮开始前换）；后台压缩的活在插件关掉后不碰库（LESSONS"异步和收尾"）。
10. **验收（③a）**：5～10 段真实会话（主人的闲聊为主，号码打码）压一次：压前压后 token、自检通过几段、摘要请求的前缀复用；挑 2～3 份摘要给主人看。话题里 `/压缩` 后接着干活，她还记得目标和做到哪一步。
## 九、第④步"模型调用页"的做法（2026-10-17，做完）

照第三节做，放在"运行"里，和"用量""性能"并排的第三页"模型调用"。线框里没画这一页，照"运行 · 用量"的样子做（卡片、图表、表格，ADR-062 第 5 条）。

1. **范围**：最近一天 / 最近一周（切换），所有角色、所有用途（回复、压缩、后台岗位）。
2. **要留意的**（顶上一排卡片，点一张只看那一类）。都是规则算的，不调模型：
   - **缓存突然掉了**：回复的前缀复用（这次命中 ÷ 上一次回复的输入总量）低于 50%，上一次在 10 分钟以内，而且这次不是开新纪元（`rebuild` 为空）。开新纪元的写"预期的重建"，隔了 10 分钟以上的写"隔得久，缓存过期"，都不算。
   - **首字变慢**：首字时间超过这个模型最近 7 天中位数的两倍，并且超过 2 秒（样本少于 5 次不判）。
   - **渠道连续失败**：同一个实际渠道连着 3 次以上出错，从第 3 次起标。我们自己拦下的（思考打转、输出格式不对、压缩自检没过）和**被新消息打断的那一轮（pi 报 "Request aborted"）**不算，也不打断连续（2026-10-22：私聊一秒内连发 7 张图，前 6 轮被后一条打断，被误标成渠道失败）。
   - **输入快满了**：这次的输入（或估算）超过硬门槛的九成。
   - **出错**：没成功的都列出来，写原因（压缩自检没过的也算，写"压缩没用上"）。
3. **趋势**：首字（中位数）、出字速度（中位数）、缓存命中三张图，调用最多的前 4 个模型各一条线；一天按小时、一周按天。
4. **每次调用一行**：时间、角色、用途（本地 / 话题 / QQ 私聊 / 群、后台岗位名、压缩）、模型（实际渠道在悬停里）、首字、速度、输入 / 命中 / 输出、前缀复用、花费（有价格缓存时）、结果（成功 / 原因，加上面的标记）。新的在前，一次 500 行，"再往前看"接着读。用虚拟列表只画看得见的那些（第一版用 React Aria 的表格，400 行点一下"再往前看"卡 668 毫秒，换成虚拟列表后 1000 行 0 次卡顿）；趋势是一张图、切换看首字 / 速度 / 命中。
5. **接口**：`GET /api/runs?days=&before=&flag=`，后台一次读出范围内的调用（只读轻的列，不读提示词原文），算好标记、计数、趋势、花费再分页返回。标记的规则写在 `util/runs.ts`（纯函数，单测）。
6. **不做的**：思考 token 单列（pi 只报输出总数，分不出思考）；点一行看完整请求（存的只有出错和调试时的原文，以后再说）。
7. **验收**：故意让一个渠道连续失败、让一次缓存断掉（不是压缩引起的），都被标出来；压缩那一轮标"预期的重建"、不算缓存断了；一周上万条调用时页面不卡（放大十倍，量出来）。
