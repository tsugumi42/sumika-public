# 规格：组件画廊

> 状态：2026-11-15 草稿；第一版 2026-11-18 随设计硬化合 main。
> 参考了：[规格-设计令牌](规格-设计令牌.md) 第二节（包的层次）、第六节 6.2（组件 API 约定）、第八节（组件目录和画廊的原计划，采用它的包位置和“例子用真实感数据”“每条例子亮暗各打开一遍”）；CrychicUI 的画廊（只借“组件目录 + 登记表”，**不照它的交互**，主人说它“交互不是特别好，不太方便”）；`cmd/sumika-proto`（起窗口和构造主题的写法）。

## 开工卡

| 栏 | 内容 |
|---|---|
| 我理解成 | 一个开发时用的独立小程序，把正式界面的组件一个个摆出来，能真的去按、去拖。正例：打开后按下方向键换到“按钮”，一眼看到主、次、禁用，伸手按两下看到悬停和按下的反馈，再按一下方向键就到“审批卡”。反例：一个组件一页、要点进去再点返回；或者只有截图不能点；或者另画一套长得像的假组件。 |
| 领域正统做法 | 组件库通常配一个展示站（Storybook 那类）：左边目录、右边例子、顶上切主题。出处：规格-设计令牌第八节的原计划、lobe-mygo 和 CrychicUI 的画廊。 |
| 最省事的字面做法够不够 | 照 Storybook 做“一条例子一页”不够：主人要的是 3 秒看完一个、立刻换下一个，所以状态要一次全摆出来、切换不能有跳转。 |
| 不做什么 | 不进 `sumika.exe`；不改组件本身和它们的取值；不做网页版展示站、不做自动截图比对；第一版不求覆盖所有组件族。 |
| 用户能看能试的验收 | 主人原话：“能够做到在 3 秒钟之内把一个组件大部分的东西手动点完，一下子能看出来它是个怎么样的风格和反馈，然后立刻可以切换到下一个组件去看”。 |

## 交互

1. 一个窗口、不翻页。左边窄列是组件族，上下方向键（或 J / K）直接切，顶上的框打字就筛，切换没有转场。
2. 右边是舞台：上面一排把固定状态并排摆出来；下面是能动手的大实例，点了有看得见的结果。
3. 能点的都在一屏内，不用滚动。
4. 顶上常驻开关：亮色 / 夜间、底色冷暖、字号、圆角、疏密，改了舞台立刻变。
5. “显示层”开关：给每层嵌套的容器描边，写出最深几层。来由：主人指出审批卡“一直往里面缩进，缩得有点太多了”。

## 技术路线

- `native/internal/catalog`：每条例子 `Entry{ID, Family, Name, Blurb, Demo}`，`catalog.Add` 登记。层次在 `winshell` 之上、`cmd/*` 之下。
- `native/cmd/sumika-gallery`：画廊程序。
- 例子只调用正式组件（`winshell.Kit`、`chatui` 的渲染函数）。

## 禁止的偷懒

- 另画一个“长得像”的组件放进画廊。
- 例子用“按钮 1”“Item”这类占位数据。
- 为了把某个组件接进画廊去改组件本身。
- “显示层”做不到通用就画一个假的层数。

## 已知的坑

- 聊天区组件要一堆宿主状态（`chatui.Host`），接的时候照 `chatui/shot_states_test.go` 的假数据写法。
- Tester 的软件渲染不能当外观证据，只用来确认不崩和出粗图；手感要在真窗口里由主人判断。

## 验收

| 编号 | 标准 | 证据 |
|---|---|---|
| G1 | 两个包能构建、能过 vet | 命令输出 |
| G2 | 每条例子亮、暗各打开一遍不崩 | 测试 |
| G3 | 至少四个组件族能看能点 | 出图加主人试用 |
| G4 | 3 秒内点完一个组件并切到下一个 | 只有主人能验 |
