## 零、先说人话

QQ 发来的视频不超过 100 MiB 就自动保存到本地，超过的等手动请求；大小未知先下载，流式超限后丢弃半文件。后台提供字节进度和取消，界面接入另由 MewTypeUI 第 4 步完成。有 ffmpeg/ffprobe 时生成封面和时长，下载完成后仍用系统播放器打开。

## 一、范围

第一步：QQ 私聊、白名单 QQ 群收到的视频（包括陌生人、自检、她自己的号发来的）自动下载；非白名单群仍整条不存。本地私聊、本地群聊不接 QQ 下载，不改变准入、观察者和工具权限。图片仍用原来的 20 MiB 上限。

本规格不做：下载按钮和进度界面、窗口内播放、补扫以前的视频、视频理解、voice 段下载、出站媒体、转码。file 段下载已另按 ADR-261 扩展现有后台，契约见[收图规格第十三节](规格-QQ收图下载和断线补录.md#十三视频和文件下载后台adr-255261)。原有图片补扫不批量扩展到旧视频，混合消息也不顺带补以前的视频。

## 四、技术路线

1. 适配器在 video 分支用 onlyStr、mediaURL、mediaFile、fileID、fileSize 保存协议端可提供字段；文件名和标识都不作路径。
2. 复用 Fetcher 工人，video 独立上限。已声明大小超过上限不发 HTTP；Content-Length 超限不读正文；无长度或谎报长度由 mediastore.Put 实际字节限额拦截。文件头识别放 mediastore，下载与播放扩展名复用同一实现。支持 ISO BMFF 的 mp4/mov（ftyp 且品牌属于视频）、EBML 的 webm/matroska（核对 DocType），拒绝 HTML、SVG、压缩包及 AVIF/HEIC 冒充视频。
3. 下载文件按 sha256 放媒体库。成功后后台顺序执行 ffprobe（时长、视频流宽高）和 ffmpeg（第一帧 JPEG，长边最多 640）；封面也经 Put 入媒体库。工具失败只失去相应元数据，视频仍完成，不重复下载已完成的视频。
4. chat/0008 在 media_fetch 加 `cover_hash`、`duration_ms`、`size`；沿用 width/height。hash、元数据同一个 FinishSegHash 事务提交，原 URL、File 和其余 JSON 字节不改。状态新增 not_video；失败行的大小也保存。
5. DisplaySegment 增加 Cover（带来源的 MediaRef）、DurationMS、FetchState；视频本地 hash 用已有 Media。整页查询一次读媒体状态，投影核对父视频 hash 后给封面凭据；消息列表、单事件、订阅重读不打开文件。
6. 封面通过已有 ReadMedia 异步图像管线读取；凭据只允许可见事件自身或其合法引用的段 hash，以及该视频对应已完成行的 cover_hash。不能凭另一个视频的封面 hash 越过事件范围。
7. 可选 VideoReader 接口提供 PrepareVideo：核对可见事件中视频 hash 后，后台打开可信媒体文件、认真实容器，复制到 `.tmp/video-open/<随机名>.<真实扩展名>`，返回绝对路径。使用副本，避免播放器修改硬链接时污染内容寻址原件【我定的】。不通过 ReadMedia 把整段视频拷进界面内存。
8. UI 用现有 ButtonBase、pictureFill 和图片缓存画视频气泡：封面或 16:9 深色块、中心播放图标、右下角时长；点下载好的视频才后台准备副本并通过可替换包级 openVideoFile 打开。失败显示一行可重试原因；不启动假播放器。Windows 用 ShellExecute，参数不经 shell。
   合并转发节点同样调用 `videoBubble`，已有视频 hash 由 `PrepareVideo` 核对完整 `MediaRef.Forward` 链和终点的 video 段；封面、图片及卡片 hash 不能冒充视频。文件扩展按 ADR-261 增加逐层路径、节点下标及 video/file 下载动作；`OfferForward` 自动下载图片和 file 段，转发 video 段自动策略仍另定，file 形式的视频同常见文件策略。文件的已验证 video hash 也可 PrepareVideo。
9. 启动（包括只读归档模式）清播放临时目录中超过一天的普通文件，不动媒体原件；ffmpeg 子进程受宿主取消和超时约束，关闭等待现有工人退出。

## 六、禁止的偷懒写法

- 不在读消息、投影或 UI 构建路径里打开媒体、ffprobe、复制视频、联网；封面异步到达不改变气泡尺寸。
- 不凭后缀、Content-Type、平台字段判断真实容器，不把 AVIF 的 ftyp 当 MP4，不把任意 EBML 当视频。
- 不因 probe/封面失败丢掉已下载视频；不伪造时长、尺寸或图片。
- 不用协议端文件名、本地路径或 URL 打开播放器；不让 shell 拼接文件名；不记录含临时密钥的 URL 或完整外部工具错误。
- 不新增 recover、无消费方字段、重复内部校验、无限子进程/输出；不让图片元数据补扫对视频逐条刷错。
- 不改准入、观察、默认工具权限；不扫描真实 data，不改协议端配置与数据。

## 八、已知的坑

- 平台通常不给大小，因此只能下载响应头或实际流判断大视频；无 Content-Length 超限时不知道完整大小，显示“视频较大，尚未下载”，不把已读字节当完整文件大小。
- get_msg 依赖协议端本地媒体元数据，失败后仍可能返回旧地址；重新请求一次后按原有状态处理，不能声称 QQ 上已经删除。
- 没 ffmpeg 时缺尺寸；有封面但后续读取失败时也保持框尺寸，不在 UI 临时探测视频。
- ftyp 只证明可识别容器，不证明全部码流可播放；ffmpeg 失败不妨碍交给系统播放器，播放器解码能力由系统决定。
- 点击准备文件和系统打开是后台动作；新窗口/宿主关闭后旧任务不能再开播放器。
- 内容寻址文件无后缀；只复制到专用临时目录，启动清旧文件，不立即删正在播放的副本。
- 0008 可能和 feat/rich-msg 撞号，合并时由主会话顺延迁移，不在本分支改其他分支。
- 沿用 500 项有界队列，满时入库不等待；补扫恢复本轮 Offer 见过的 video seq 范围，补录的旧时间戳不套图片 7 天窗口。没有收到的旧视频不批量下载。
- 同一条消息可能重复发送同一视频，UI 状态按段序号区分，不能只用内容 hash 作同级元素的 key。
