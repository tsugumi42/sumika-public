# 规格：每日整套放回仓库（P1-5）

> 状态：已做完（2026-11-16）：脚本和队列显示（独立复核两轮，记录在 `data/dev/review-p1-5/`）；主人同日同意登记任务计划 `SumikaNightly`（每天 04:30，已登记）、巡检改成读整套结论（Claude 应用的巡检说明已改）。验收第 1 条（真跑一次）由 11-17 04:30 第一次自动运行完成，看 `merge-queue status` 第一行。

## 开工卡

- **我理解成**：每天的整套测试（不带 `-short` 的 `go-verify --full`）由仓库里的一个脚本跑，由 Windows 任务计划按时起；结果单独记一份（绿还是红、哪份代码、多久以前）；合并队列每次打印状态时写一行“上次整套：多久以前、绿 / 红”，超过 36 小时没有绿的整套就提醒。正例：主人睡觉时整套在专用 worktree 里跑完，早上 `merge-queue status` 第一行是“上次整套：6 小时前，绿”。反例：现在这样，整套只在 Claude 应用的定时任务里跑，仓库里什么都没有，验证记录里 200 条全是短跑；哪天定时任务悄悄没了也没人知道。
- **领域正统做法**：CI 的 nightly 构建：定时触发、在干净检出上跑、结果和提交号挂钩、看板显示“上次 nightly 是否绿、多久以前”，过期就告警（GitHub Actions `schedule`、Buildkite scheduled builds）。本机没有 CI 机器，所以用系统任务计划代替调度器。
- **最省事的字面做法够不够**：只登记一个任务计划去跑 `go-verify --full` 不够：验证记录分不出绿红、200 条滚动会把整套挤掉（坑 1、2），主工作区常年有半成品会让整套直接退出（坑 5），队列也读不到它（坑 3）。
- **不做什么**：不做 `doctor --fix` 自动登记（`sumika-ctl doctor` 的 `env.nightly` 仍是“不适用：只在开发机上有”）；不加 `-race`（X-38 另一条路线）；不改队列只跑 `-short` 的规矩；不碰产品代码。
- **用户能看能试的验收**：见“验收”第 1、3 条。

## 设计

1. **脚本 `scripts/nightly.ts`**：
   - 在专用 worktree（`<git 公共目录>/../.claude/worktrees/nightly`，或照 `merge-queue.ts` 的 `prepWorktree` 放在它管的位置）里 `checkout --detach` 到本地 `main` 的最新提交，拷 `vendor/bin`（坑 5）。
   - 在那里跑 `bun scripts/go-verify.ts --full --by nightly`（`go-verify` 加 `--by` 参数，坑 9），名额档 `verify`（go-verify 本来就是）。
   - 输出边跑边写主工作区 `data/dev/test-runs/nightly-<本地日期时间>.txt`（坑 15）。
   - 跑之前看合并队列：队列有条目在跑就等它跑完再开（读 `sumika-merge-queue.json`，最多等 30 分钟，等不到就照跑，名额锁会排队）（坑 6）。
2. **整套结论单独一份**：`<git 公共目录>/sumika-nightly.json`，只存最近 30 次：`{at（UTC ISO）, commit, tree, ok, seconds, exit, output（文件路径）, failed（红的包，最多 20 个）}`。临时文件写完再改名（照 `addVerified` 的重试），不和验证记录共用文件（坑 1、2、3）。`ok` = `go-verify --full` 退出码 0。
3. **队列显示**：`merge-queue.ts` 读 `sumika-nightly.json`（用 `ctx.common` 拼路径，坑 3 的末尾）：
   - `status` 第一行：“上次整套：<多久以前>，绿（<短提交号>）”或“红（<短提交号>，<几个包>，输出 <路径>）”；没有记录写“还没有整套记录（bun scripts/nightly.ts 跑一次）”。
   - 36 小时内没有绿的整套：`status`、`add`、`run` 的每一轮（**包括队列空的那一支**，坑 13）都打一行提醒：“超过 36 小时没有绿的整套（上次绿：…）”。“没有记录”和“有记录但过期”文案分开（坑 11）。计时用 `Date.now() - Date.parse(at)`（坑 12）。
4. **登记任务计划**：`bun scripts/nightly.ts --register [--at HH:MM]`、`--unregister`、`--status`（只读，显示任务在不在、下次几点、上次结果）。登记用 PowerShell `Register-ScheduledTask`：
   - **仅在用户登录时运行**（名额锁是 `Local\` 的，SYSTEM 账户起的会和队列叠着跑，坑 4）；
   - `StartWhenAvailable`（睡眠错过了醒来补跑，坑 7）；
   - 低优先级（照 `run-low.ps1`）；任务名 `SumikaNightly`；
   - 时间默认 04:30，登记时由主人定。
   - **`--register` 会改系统的持久配置：主会话运行前先问主人**（时间、要不要登记）。
5. **跑法指纹**：`scripts/nightly.ts` 加进 `go-verify.ts` 的 `RUNNERS` 和 `go-affected.ts` 的 `FULL`（坑 10）。
6. **巡检**：Claude 应用里 12:00 的巡检现在自己跑整套 `go test ./...`。登记好任务计划、整套记录跑起来以后，巡检改成读 `sumika-nightly.json` 和最新的整套输出，不再自己跑（省一次重活）。这是改 Claude 应用的定时任务，**也要先问主人**。

## 验收

1. `bun scripts/nightly.ts`（主会话手动跑一次，在主人同意的时段）：专用 worktree 在 main 最新提交上、输出存 `data/dev/test-runs/nightly-*.txt`、`sumika-nightly.json` 多一条 `ok`；验证记录里多一条 `by: nightly`、不带 `short` 的记录。
2. 脚本单元测试（`scripts/` 现有的测试写法，临时目录、假的 go-verify）：绿 / 红 / go-verify 起不来三种都写对 `sumika-nightly.json`；只留 30 条；写的时候文件被占（注入）重试。
3. 队列：`status` 第一行显示上次整套；注入“上次绿在 40 小时前”→ `status`、`add`、空队列的 `run` 都打提醒；没有记录时文案不同；绿在 2 小时前 → 不提醒。
4. `--register`、`--unregister`、`--status` 生成的 PowerShell 命令（测试里只检查生成的命令文本，不真登记）：仅在登录时运行、`StartWhenAvailable`、时间参数对。
5. 改 `scripts/nightly.ts` 让 `go-affected` 判整套、让旧验证记录失效（指纹测试）。

## 禁止的偷懒写法

- 整套结论塞进验证记录的 200 条滚动数组。
- 在主工作区里跑整套。
- 任务计划用 SYSTEM 或“不管用户是否登录”。
- 测试里真的登记任务计划。
