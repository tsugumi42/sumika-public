# 规格：提示词前缀稳定（缓存命中）

> 状态：2026-11-13 写完直接做（ADR-083，决定记在 ADR-366），已合 main（指纹， 批次逐条、用途头、锚定和思考， 批次比对退回）。需求 R-226、R-368；第七节（ADR-368）参考信息块按档存库，已合 main（2026-11-13；做法的偏离、实测数和残余写在第 7.9 节）。依据：缓存盘点报告 `data/dev/cache-audit-.md`（只在主工作区，不进 git），[排查-提示词缓存命中-2026-11-09](notes/排查-提示词缓存命中-2026-11-09.md)。采用报告第 3 节改法 0、2、8 和改法 1 里不涉及“谁能看什么”的两项（窗口锚定、思考字段）；参考信息块按档落库（改法 1b）、复用条件不比说话人（改法 6）、会话头（改法 7）不在这里做。
> 目标（主人 2026-11-13）：前缀稳定时命中率不低于 95%，逐步往 97～99% 提。

## 一、为什么

服务商按字节前缀缓存。相邻两次请求只要中间一条消息差一个字节，后面全部重算。盘点时 QQ 群前台只有 43%：重建实例以后历史一条都对不上，复用实例时多条批次的下一轮在那一批的位置断开。

## 二、记录（改法 0）

`model_runs.prompt_hashes_json`（trace 迁移 0021）：每次真正发出去的 messages 逐条的角色、字节数和哈希链，tools 的字节数和哈希。不存正文。格式和比法见 `llm.PromptHashes`、`llm.PromptPrefix`，子系统参考 [runtime](subsystems/runtime.md)。

## 三、渠道批次逐条（改法 2）

- 渠道回合的这一批在回合里就照库里的写法逐条追加：每个 seq 一条 user 消息，写法是 `history.Of`，和交回以后照库重写（`Live.settle`）、从库里重建的一样。参考信息块照旧排在这一批前面。
- 插件、闸门、`kernel_inbox` 看到的 `Input.Text` 照旧是拼好的多行。
- 照旧拼成一条的几种：本地回合（主人那句由内核存，Bun 录像对的是它）、子运行、带图的批次、识图兜底改过文字的、有分块的；库里读出来的条数和 seq 对不上的，或者逐条拼起来和 `Input.Text` 不是逐字节相同的（入库时排的那一行可能比开口时少东西，比如被引那条的链接摘要后来才有，不能让她这一轮少看到）。后两种各记一行日志。
- 插话（回合中途来的那几条）照旧拼成一条、带“你回话的中途……”前缀：前缀只在回合里有意义，交回以后照库重写时去掉，这一处照旧断一次。
- 禁止：把 `FormatLine` 拼好的多行按换行拆开当逐条用。拼的时候和库里的 `segments.line` 可能不一样（报告里 36 个批次连拼好的文字都不同）。

## 四、用途头（改法 8）

- 发往 Magpie 的请求按调用种类带 `x-openai-subagent`：`modelcall.PurposeOf` 定，前台回复（foreground）不带，其余是 `sumika_` 加种类名（链接翻译是 `sumika_translate`），最长 40 个字。Magpie 用量记录里显示成 `kind:<值>`。
- 不用 Magpie 有专门处理的名字（memory、memgen、memory_consolidation、thread_title、title、thread_description、collab_spawn、guardian、compact、vision、web_search、routing、luna_reserve），加了前缀就撞不上。
- 本机实测（2026-11-13，Magpie 127.0.0.1:3425）：带 `x-openai-subagent: sumika_probe` 发一次最短请求（`auto/deepseek-flash`），`GET /v1/magpie/usage/requests?agent=sumika` 的 purposes 里出现了 `kind:sumika_probe`，那一行的 kind 也是它。
- 不走 `modelcall` 的模型请求（如报告 2.8 说的 trace 里对不上的后台记忆请求）带不上，照旧是 unmarked。
- 会话头（`x-session-affinity`）和 ADR-033 冲突，不在这里做，等主人定。

## 五、重建的历史和接着用的实例对得上（改法 1a、1d）

- **窗口锚定**（2026-11-14 ADR-377：本地私聊和主人的 QQ 私聊已被 ADR-377 改为从“上下文起点”重建，先留痕一周再动手（2026-11-16 ADR-385 改为不等一周、P2-6 之后直接做），后续路线 P1-6、P2-9；QQ 群和其他场合照下面）：没有压缩快照时，重建带的原文从“算数的消息”（通知、没说出口的、这一批不算）里按 seq 编号，起点取 `agent.recentMessages`（n，默认 30）的整数倍里还能留下至少 n 条的最大那个（`history.AnchoredStart`）。带的条数在 [n, 2n) 里，新消息进来起点不动，攒够 n 条整体往后跳 n 条。只由库里的状态算，不加表，重启前后一样。有快照的照旧从快照切点起。超了硬门槛的裁剪（从新往旧留 keepTokens）不动：只在快满时才走。
- **思考字段**：渠道回合交回以后照库重写时，她每一步的思考不再带回来（重建出来的本来就没有）。最后一步的思考本来就没当输入发过，所以不多断一次；中途被插话接着的那一步，交回以后那一截本来就因为插话、工具步骤重排而断开。本地回合的实例照旧留着思考（DeepSeek 的模板本来就丢掉以前轮次的思考，按 token 算没差别；动它会改 Bun 录像），重建以后没有，这一处仍不一致。
- 代价：重建时多带的历史最多到 2n−1 条（QQ 群约 30 条多 2500 token 左右）。锚点要数一遍这个会话算数的消息（`count(*)`，现有索引只有 `(conversation, seq)`，要回表看 kind、origin）：临时库里一个会话 20 万行时每次重建约 0.35 秒，取起点那一下从最新往回数，不另扫。真实大群慢的话加 `(conversation, kind, origin, seq)` 覆盖索引（要迁移真实库，另做）。
- 已知的额外跳点：定期任务那一轮的话从“待分类”改回可见来源、或者补录插进旧消息时，后面的编号整体挪位，下一次重建会多断一次。
- **还差的**：参考信息块（时间、对面是谁、记忆召回、审批说法、停止提醒）不进库，重建以后没有。重建和接着用的实例在第一块参考信息处仍会断开，公共前缀只到“系统提示 + 起始那段历史”，不能说重建等于活实例。把它按（角色、会话、档、排在哪条前）存库是“谁能看什么”的改动（报告改法 1b），要走 AGENTS 第 7 条，未做，见第七节（ADR-368）。catchUp（别的档说的追在末尾）和重建按 seq 排的差别（改法 1e）也没做。

### 7.2 设计：参考块按档存库，重建时插回原位

**存什么。** 每个渠道回合交回（Commit）时，把这一回合发给模型的参考块原字节写进会话事件库：迁移 `events/0006_ref_blocks.sql`，和会话事件同库（不放 trace，trace 不存正文）。**生产的平台库跑的是 `migrations/chat`，这张表同时加在 `chat/0017_ref_blocks.sql`（见 7.9）**。**只存 7.3 节允许的那几类块**，一块一行，字段：

- `character_id`、`conversation`；
- `scope_key`：档，即 `memory.ScopeKey(aud)`（可见范围排序后拼接）。**用 `ScopeKey(aud)`，不用 `Input.Scope`**：本地主窗口的 `Input.Scope` 是 `turn.ConsoleScope`（`"owner"`），对应的档是 `"all"`（`memplugin/plugin.go` 的 `scopeMatches` 就是这样比的）；
- `before_seq`：块后面第一条事件的 seq（这一批第一条的 seq，或本回合她第一句的 seq）；
- `ordinal`：同一 `before_seq` 内的序号；
- `card_hash`：角色卡加系统段的哈希；
- `memory_refs_json`：块引用的记忆，形如 `[{"id":"…","hash":"…"}]`，没有就是 `[]`。`hash` 是这条记忆这一行给模型看的全部内容的哈希：文字、来源、类型、待确认、固定、取代的旧版本，加上本档的 OwnerOnly 标记、过期和隔离状态。召回不按范围过滤（`memory.AllowedScopes` 恒为 nil，ADR-242），可见范围只体现在 OwnerOnly 标记上，所以它要进哈希。
  - 实现前提：`turn.RecallItem` 现在没有 ID，`Contribution` 也不带结构化引用。要在 `Contribution` 上加 `Refs`（ID 和哈希），由 `memplugin` 从同一次召回里给出；哈希在渲染那一刻算，不另查一遍。
- `text`：块原文，不重写。空文字不写行（和 `buildContext` 返回 "" 一致），不报错；
- `created_at`。

写块和交回的事件在同一个事务里。事务失败则整次交回失败，活实例按库重写（与现在 Commit 的失败路径一致），不会出现库里没有、活实例里却有的块。写块的校验不过（缺档，或记忆引用不是 `[{id,hash}]` 数组）是代码错误，不是用户输入，同样让交回失败，并记一行日志。

**重建时插回。** acquire 的冷路径和 `rebuildIn`（`hub.go:1391`）只取锚定窗口内、同 `(character_id, conversation, scope_key)` 的块，按 `(before_seq, ordinal)` 插回 `before_seq` 之前的位置。不同档的块不插；`card_hash` 不等于当前值的块不插；记忆核对不过的块整块不插（见 7.3）。

**活实例与重建的关系。** Commit 之后活实例里的块，是库里该档窗口内的块，加上本回合里因 7.3 不存而没进库的块。后者重建时没有，这一处断一次前缀（7.5）。窗口锚点跳变那一跳（ADR-366 已有）另算。

**不变量（写进测试）：** 对任一 `(角色, 会话, 档)`，重建出的参考块序列是库里同档、窗口内、核对通过的块的子集；对存了的块，与活实例逐字节相同。

### 7.3 失效

- **记忆删改、改范围、过期、隔离。** 重建时逐条核对块引用的记忆：用当前时间和本档，按 7.2 的算法重算哈希。记忆已删、哈希不等，或读记忆库失败，整块不插。过期是随时间变的，所以这一步必须在重建时做，只在写入时做不够。不改写文字，免得拼出新内容。同时在记忆删除、改写、改范围、隔离的写入路径上删掉引用它的块行：块文字是记忆的派生副本，不能比记忆活得久。两道都做：删行是清理，核对是兜底。删行与记忆写入不在同一事务时，删失败只记日志，由核对兜底。写入路径在实现时逐个列全（`memory/tools.go` 的 `Forget` 是其中一个入口）。
- **角色卡热更新。** `card_hash` 变了，块不插。系统段变了本来就要重建（acquire 里的 `l.system == system`），两者一致。
- **可见档变了。** 档不同，就是另一组行，互不插入。档内 OwnerOnly 的变化由哈希覆盖（上面第一条）。
- **闲置、重启、换 exe。** 行在库里，重建照常插回。
- **审批规则、计划提醒、停止提醒、被打断提醒、“现在是……”。** 按当时的原字节保存，不改写。过时的审批规则由后面新写的那句覆盖，与活实例现在的做法一样。“现在是……”保留当时的时间，那是历史。
- **权限、工作区信任、插件开关、会话工作区（第一版不存）。** 块里只要有一行来自下面这些插件，整块不存：客户端能力（`clientinfo`，“本会话可用”）、技能目录（`skills`，按 `ContextAccess(in)` 取）、工作区说明（`projectcontext`，受信任状态控制）、链接摘要（`linkplugin`，受开关和会话工作区控制）。这些内容随授权、信任、开关变：撤销信任、收窄技能来源、关掉链接上下文、或切了会话工作区，旧行若存在库里，重建时会插回比当前权限更宽的内容。改前这些变化会让实例重建、旧行随之消失，改后就不一定了。第一版没有有效性令牌挡它，所以不存这一类块，代价是这些回合每次重建断一次（7.5）。将来要存，先给每块加令牌（授权版本、工作区、插件启停与工具清单的指纹），不带令牌的行不入库，单开一步。
- **窗口裁剪。** 窗口是按会话锚定的（`AnchoredStart`），起点后跳后，`before_seq` 小于起点的块不再插。清理谁、何时：每次交回在同一事务里调用 `PruneRefBlocksTx`，删同（角色、会话）下 `before_seq` 小于窗口起点的块，所有档一起删。不另开定时任务。

### 7.4 说话人比较（改法 6）：这次不删

- 盘点 2.3 认为复用条件比说话人是 QQ 群重建的主要来源。做完 7.2 之后，换说话人的重建字节和活实例一样，服务商缓存照样命中。所以比较保留，代价接近零，**本节不动比较，权限边界不动**（AGENTS 第 7 条）。
- 比较防的是什么：实例里的工具结果预览（`r.Text`）和历史消息，会让下一个说话人看到上一个人的工具输出。`history.Of` 只读 `message` 事件。渠道回合交回后，实例里那一段照库重写，所以重建读到的和复用时看到的一致。**本地回合没有这一步**：它的工具结果只留在实例里，重建时 `history.Of` 读不到，这一段只有 `Identity.Scope` 比较在挡。所以“比较不是唯一的挡板”只对渠道回合成立。这一点要靠 7.6 的形状表验证：B 在复用实例里看到的 A 的工具结果，要和 B 从库重建看到的一样。如果 history 按说话人过滤工具结果，这个结论不成立，那就保留比较（现状）。
- 将来要删比较，必须先完成三件事，才开单独的改法 6 提交：
  - (a) 说话人私有行（关系行、本地私聊的审批规则）不进共享历史，只作为本次请求的尾部临时行；
  - (b) 授权读取全部按本轮 `in.Identity` 取，不从实例里取：`InvocationWorkspace`（`lifecycle.go:220`）、compact 的 `src.work`（`compact.go:65`）、workhistory 的 handoff Scope（`workhistory.go:613`）、compact job 的 identity（`hub.go:966`）；
  - (c) 本地回合的工具结果不经库：要么让它进库（同一事务写），要么证明重建读不到的内容不影响结果。
  - AuthorityID、AuthorityRevision、ActorKind（主人或他人）仍然比较。

### 7.5 残余（本节不做，写明）

- **本地私聊不写块，重建照现状。** 本地回合没有交回（`channel/settle.go` 的 Commit 只在渠道回合调用），它的审批规则、关系行等都不进库，重建时仍然丢。本节不另设本地私聊的写入点。
- **本地群聊待核对。** 它是否经过交回（`channel/settle.go` 的 Commit 调用条件），实现第一步先查清；经过就同 QQ 群处理，不经过就同本地私聊。（2026-11-13 查清：不经过。全仓调 `Hub.Commit` 的只有 `channel/settle.go` 和测试夹具，本地群聊是 `in.local()` 的回合，同本地私聊，不存块。）
- **含非记忆插件行的块整块不存（7.3）。** 这类回合每次重建断一次。实现前先量：离线剧本里，这类块占 QQ 群回合的比例。占比高到第一版没有意义，就停下，先做有效性令牌，不硬上。量出的数写进这一条。（2026-11-13 量：离线剧本没装客户端能力、技能目录、工作区说明、链接摘要，占比是 0，不代表线上；线上占比要看新 exe 跑一天后有多少回合的块没存，见 7.9。）

### 7.9 实现记录与实测（2026-11-13，已合 main：，分支 feat/ref-block-cache-2）

按 7.8 的顺序做完 (1)–(5)：存库层和清理（`store/ref_blocks.go`）、`Contribution` 带引用（`Storable`、`Refs`）、重建时插回（`turn/refblock.go`、`buildWith`）、记忆核对（`memory.VerifyRefs`，`Registry.OnRefCheck`）、失效删行（`memory.Options.OnChanged` → `Hub.PurgeRefBlocks`）、离线剧本加断言（`TestPrefixRebuildEqualsReuse`）。(6) 线上一天后哈希链核对没做，要新 exe 跑过才有。

**和 7.2–7.8 写的不一样的地方：**

1. **迁移放在哪。** 规格写 `events/0006`。生产的平台库（`local`、`qq`）跑的是 `migrations/chat`，`events/` 只给 `OpenFresh` 的单库和测试，所以只加 `events/0006` 的话，真实回合写块会报 no such table（跑 `turntest` 夹具的测试第一次就红了）。补了 `chat/0017_ref_blocks.sql`，两处建表语句逐字相同，`TestRefBlocksInPlatformDBs` 比对。
2. **“同一个事务”。** 渠道回合里她说的话是中间件先写好的，Commit 只收到已经在库里的行，所以和事件同一个事务做不到。实际是：Commit 里写块加清理窗口起点之前的块在一个事务里（`SaveRefBlocks`），写不进去 Commit 报错、实例什么都不改、库里不留半截（`TestBlockCommitAtomic`、`TestSaveRefBlocksAtomic`），中间件照约定 `RestartIn`。**没有“失败时回撤已写的块”**：Commit 在块写成之后别处失败（挂步骤记录、照库重写读库出错）时块留着，因为活实例里本来就有这块，留着和实例一致；删了反而造出“实例有、库里没有”。
3. **她没说话的回合也存。** 规格只写“交回时”，群里她多半不开口、不会有 Commit，这样的回合占大多数，漏了等于没做。回合结束时存（`respond` 里 `len(res.Said) == 0` 的那一支，出错只记日志；`TestBlockStoredWhenSilent`）。
4. **存什么：白名单，不是黑名单。** 规格 7.3 是“块里有这四个插件之一的行就不存”。实现是：只有声明了 `Contribution.Storable` 的贡献才存（目前只有记忆召回），没声明的（含用户扩展、示例插件、将来新加的）整块不存。比规格更严，不会漏掉没列出名字的插件。另外带悄悄话处理记录（`Config.Notes` 并进关系行）的块也不存：它不随档、卡、记忆变，也没法核对。
5. **记忆指纹。** `memory.HitDigest` 只取不随时间变的字段：文字、来源、类型、待确认、范围、被取代的旧版本（文字和时间）、这一档的“主人私下说的”标记；不含渲染出的“N 天前”（含了的话隔一天所有块都对不上）。过期、隔离不是字段，由 `VerifyRefs` 重建时用当时的钟、当前的条目表重算。规格写的“固定”没进指纹：固定要点由类型和状态决定，已经在里面。
6. **窗口清理的下限**（`history.WindowFloor`）：和 `MessageWindow` 共用同一份起点算法，再留一个跳点的余量（下一轮重建会把它那一批排除在计数之外，总数少几条，起点可能比现在落在上一个跳点），有压缩快照时取快照起点和窗口起点里更早的。`TestWindowFloor` 钉着“不比任何一次重建的实际起点更晚”。
7. **插回的位置**：排在第一条 seq 不小于锚点的消息前面（和插话那块参考信息照库重写时一样的规则）；下限是重建后真正留下的第一条消息（快照、新话题分隔、裁剪之后），更早的块不要；锚点超出历史的块不插。
8. **重建后恢复“给过什么”（规格没写）。** 重建出来的实例以前当自己什么都没给过，下一轮又报一次时、又说一遍对面是谁（每次重建在尾巴上多约 165 字节）。现在从插回的块里恢复：最近一块报时块的时刻、整段出现在块里的关系行（`Built.ClockAt`、`Built.Relation`；没插回的块不算给过）。
9. **测试名。** 7.7 列的 `TestBlockMemory{Deleted,Rewrite,ScopeChanged,Expired,Quarantined}Skipped` 做成了一个表驱动的真记忆端到端测试 `memplugin.TestBlockMemoryChangesSkipOnRebuild` 的子用例，核对器出错、插件停了、没有记忆库的在 `turn.TestBlockMemoryRefsFailClosed`、`TestBlockMemoryChangesSkipOnRebuild/这个角色没有记忆库`；`TestBlockMemoryReadFailSkipped` = `TestBlockMemoryRefsFailClosed/读记忆库失败`；`TestBlockRefsInvalidFailsCommit` = store 的 `TestRefBlocksRejectsBadMemoryRefs`（写块的校验）。其余同名。
10. **重建后恢复插件存储（规格没写，实测出来的）。** 内核把插回去的块引用的记忆交给插件（`Registry.OnRestore`、`RestoreIn.Blocks`，引用带 `Pinned` 标记），记忆插件据此恢复“已经给过哪几条”和固定要点的指纹（`life.restore`）：已经在插回的块里的记忆不再给第二遍；没插回的块（核对没过）里的记忆照旧可以再给。不恢复就会越重建越多（见 7.4 那一段）。`TestBlockMemoryNotDuplicatedAcrossRebuilds`（真记忆，重建 5 次后每条只在一条消息里）、`TestBlockRestoreHookGetsInsertedRefs`。
11. **`Input.Scope` 必须等于听众算出的档。** 实例按 `Input.Scope` 分，块按 `memory.ScopeKey(听众)` 分；两个对不上说明装配处算错了档，这一轮不存不插（和记忆插件对 Scope 的做法一样）。生产里渠道的 Scope 就是 `ScopeKey(听众)`，不受影响（`TestBlockScopeMismatchNotStored`）。

**7.4 说话人比较：保留，代价如实写在这里。** 离线剧本里 23 次请求有 15 次是重建，其中 12 次是说话人变了触发的。现在重建出来的请求和接着用的实例逐字节相同，缓存照样命中，所以比较本身不再耗缓存；留着的代价是插件在实例里的存储（`ContextIn.State`，记忆插件记“这个实例里给过哪几条”）每次换人就重置。这在存块以前没事（旧块重建时全丢，重新给一遍就是一份），存块以后不处理会越重建越多：实测说话人轮换重建 5 次后，固定要点和命中各在历史里出现 6 份。所以加了恢复（第 10 条）。要不要为这个去动权限边界，仍按 7.4 的三个条件，这里不动。

|---|---|---|---|---|---|---|

目标是 QQ 群全部 ≥ 95%、重建与复用差 ≤ 2 个百分点、本地私聊不退步。结果：**本地私聊不退步（达到）；重建与复用差：去掉窗口跳变是 0.8 个百分点（达到）、带上窗口跳变是 10.9（没到）；QQ 群全部 88.4%（没到）。** 卡在两处：

- **窗口跳变 3 次**（23 次请求里的 #05、#13、#22）。重建恰好落在“历史窗口起点往后跳一格”的那一刻，历史第一条就和上一次对不上，每次丢掉约 1763/4500 字节的前缀。其余 12 次重建和接着用的实例逐字节相同（`TestPrefixRebuildEqualsReuse` 断言）。这是锚定窗口的算法（ADR-366，规格第五节“窗口锚点跳变另算”），这一轮没动。

**残余和下一步（记进待办）：**

- **说话人换了的重建沿用旧实例的窗口起点**，不在这时候往后跳：离线剧本上预计 QQ 群 88.4% → 94.6%。要同时让窗口清理的下限取“这个会话里活实例中最早的起点”，不然会清掉它还要用的块，所以单开一步。
- **重建时核对的耗时没量**：每个带引用的块逐块同步问一次记忆（回查来源要读事件库），窗口里几十块时一次重建要问几十次，每块钩子上限 5 秒。记忆库一慢重建会拖慢整轮。要的话给整次重建一个总时限，超了把剩下带引用的块不插。
- **含非记忆插件行的块不存**：离线占比 0（剧本没装那几个插件）不代表线上。线上有链接摘要、技能目录、工作区说明的群回合，这样的回合每次重建断一次。新 exe 跑一天后数“没存的块占回合的比例”，高了就做有效性令牌（授权版本、工作区、插件启停与工具清单指纹），不带令牌的行不入库。
- **独立复核没做**：形状表和改坏清单（`data/dev/test-runs/ref-block-shape-entry-20261113.md`，126 格：测了 52、处理了 8、不可能 66；改坏检查 23 种全部变红）按 AGENTS 第 7 条要交独立复核（Sonnet high），这一轮执行环境没有派子代理的工具，没做，不由写的人自己判定。

### 8.1 存哪

`model_runs.context_json` 里加一个键 `rebuild`，只在重建后的第一步写（和现有 `reset` 同一个条件；不是第一步时整个省掉、不写 null，不然 `AddRun` 冲突时 `json_patch` 会把已记的删掉）。不改表结构、不用迁移号。`rebuild` 列（`fresh`、`reset`、`compact`）和 `reset_reason` 列不动，现有 `cmd/soak`、`cmd/stress` 照旧按 `fresh` 查。

```json
"rebuild": {"reason":"idle","also":["model"],"kept":30,"dropped":12,"covered":0,"count":"exact","snapshot":false}
```

| 字段 | 含义 |
|---|---|
| `reason` | 为什么重建，见 8.2。按固定优先级取第一个，其余进 `also`。 |
| `kept` | 带上的原文条数（不含快照那一条）。 |
| `dropped` | 算数的消息里，seq 小于带上的第一条的条数（窗口外、新话题分隔之前、快照切点之前、超硬门槛裁掉的都在里面）。这一批、排队没轮到的更新消息不算。没带上任何原文时数到这一批之前。 |
| `covered` | `dropped` 里被压缩快照覆盖的条数（seq 小于快照切点的）。快照之后又被硬门槛裁掉的不算覆盖。`covered > 0` 才叫“有摘要覆盖”。 |
| `count` | `exact`（数了）或 `failed`（这次数条数出错，`dropped`、`covered` 记 0 且不进平均；照常重建）。 |
| `snapshot` | 这次重建用没用上压缩快照。 |

不记正文、会话名、号码、角色名。场合由查询时按会话串算（`runstats` 的 `placeOf`），不写进记录。

### 8.2 原因表（按优先级，同时满足时第一个当 `reason`，其余进 `also`）

| 标识 | 触发点（代码） | 显示 |
|---|---|---|
| `stale` | `Hub.MarkStale`：主动联系、提醒往会话写了话（`acquire` 里 `staleGen` 不等） | 会话被标记要重读 |
| `speaker` | `l.in.Identity.Scope.ActorID` 变了（说话人换了） | 说话人变了 |
| `scope` | `Identity.Scope` 别的字段变了（授权版本等） | 身份范围变了 |
| `workspace` | `l.in.Workspace != in.Workspace` | 工作目录变了 |
| `model` | `l.model != m.ID` | 换了模型 |
| `persona` | 固定前缀里 `persona*` 段变了（改卡；或私下段随听众里有没有外人变） | 角色设定段变了 |
| `scene` | `scene-*`、`platform-*` 段变了 | 场合提示词变了 |
| `prompt` | 其余段（通用规则、命令说明）变了 | 通用提示词变了 |
| `tools` | 工具清单变了（插件启停、权限） | 工具清单变了 |
| `compacted` | 有了新的压缩快照（`EpochSeen != latest`） | 有了新摘要 |
| `idle` | 实例闲了 `idleAfter` 以上（在 `acquire` 里认，或被 `recycleLocked` 放掉） | 闲置超时 |
| `evicted` | `recycleLocked` 因超过 `MaxLive` 放掉 | 实例数超限被挤掉 |
| `restart_in` | `RestartIn`：新话题、检查点回退、渠道交回要求 | 主动丢掉实例 |
| `restart` | 本进程第一次见这个会话，库里已有旧消息（程序重启后第一次） | 程序重启后第一次 |
| `first` | 本进程第一次见，库里没有旧消息 | 这个会话第一次 |
| `new_audience` | 本进程见过这个会话，没见过这一档（`liveKey` 里的听众档） | 同会话换了听众档 |
| `over_limit_compacted` | `fitHard`：回复前过了硬门槛，压缩成了、换新快照 | 超硬门槛，压缩后重建 |
| `over_limit_trimmed` | `fitHard`：压缩没成、关了自动压缩、渠道，只带最近的 | 超硬门槛，只留最近的 |
| `provider_overflow` | `recoverOverflow` 里 `swapHistory`：服务商报上下文超长后压缩重建 | 服务商报超长后重建 |
| `tool_pair` | `acquire` 复用时发现工具调用和结果对不上，原地重建 | 工具调用配对错乱 |
| `work_root` | `switchWorkRoot`、`work.go` 里退回整个重建 | 工作记录对不上 |
| `unknown` | 以上都不是（没有登记的放掉方式）。**不许**归到别的原因里凑数 | 不明 |

没带 `rebuild` 键的旧记录（本节上线前的）在查询里单列“没记原因”，不并进 `unknown`。

同一轮里先 `acquire` 重建、还没记到记录就又 `rebuildIn` 的，两次原因都留：先到的当 `reason`，后到的进 `also`。重建后这一轮没发出请求（出错、被停）的，不产生记录，下一个发出的请求带上。
