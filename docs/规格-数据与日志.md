# 规格：数据与日志（存什么、存多久、怎么不越存越大）

> 2026-10-14 状态：主人 2026-10-14 同意（ADR-026）。已实现：截断、blob、SQLite 设置、日志落盘、步骤落库、模型调用瘦身、每天的维护和数据健康度接口。等 QQ 渠道一起做：群消息 90 天归档、普通图片 60 天清理、媒体下载、运行页界面。接 QQ（第二阶段）之前定下来，因为群消息、图片、她的后台分析一接上就会涨得很快。

## 一、现在的情况（2026-10-14 量的）

| 来源 | 多久 | 多大 | 主要是什么 |
|---|---|---|---|
| Sumika 挂机测试 | 约 2 天，只有主窗口私聊 | 26.6 MB | 一半以上是 SQLite 的预写日志（`.db-wal`，每个库约 4 MB，合并回库以后文件不缩小） |
| MaiBot（主人在用） | 3 天多（10-11 起） | 日志 1.6 GB + 数据 1.1 GB | 日志里 1.5 GB 是**每次调用模型都把整份提示词另存一个文件**（2937 个，出错的单个 30 MB）；数据里图片 410 MB（1013 张）、表情包 207 MB（442 个）、记忆库 360 MB |
| Codex（本机） | — | 会话 25 MB + 日志库 29 MB + 插件缓存 530 MB | 会话记录里 70% 是工具输出；有人报告涨到 42 GB（每次压缩上下文都把完整历史重写一遍，归档从不清理） |

结论：**最容易失控的不是聊天文字，是"每次调用都存一份完整请求"和"媒体文件"**。聊天文字本身很小。

Sumika 现在的问题：
- `trace.db` 每次模型调用都存 `request_json` / `response_json` 和提示词各段的全文。人设、规则这些段每轮都一样，存了 N 遍；接上 QQ 以后每条群消息都可能触发一次"要不要接话"的判断，就是 MaiBot 那 1.5 GB 的翻版。现在只按 7 天删，没有大小上限。
- 工具调用和思考过程完全没存（刷新页面就没了），所以现在不大，但要存的话得先定规矩。
- 预写日志没设上限；库从来不整理，删了数据文件也不会变小。
- 程序日志只打到终端，没落盘（落盘以后也要管）。**已被 ADR-367 改为**：程序日志已落盘（`logs/`），带级别和模块，见 [规格-日志分级](规格-日志分级.md)；运行时自检的每日结果在 `selfcheck/`，见 [规格-运行时自检](规格-运行时自检.md)。

## 二、目录

```
data/
  shared/
    events.db        原始事件：本地的私聊、QQ 私聊和群消息、通知（ADR-015，全局一份）
    trace.db         模型调用记录、工具调用、后台判断
    blobs/ab/cdef…   媒体和大段内容，按内容哈希（sha256）存，一份内容只存一份
  <角色>/memory.db   她的记忆（不变）
  logs/              程序日志，一天一个文件（格式见 规格-日志分级）
  selfcheck/         运行时自检的每日结果，一天一个 JSON（见 规格-运行时自检，ADR-367）
  archive/           冷归档：按月压缩的旧群消息、旧日志
```

## 三、存什么、怎么存

**原则**：记录里只放"发生了什么"和引用；大块内容放 blob，同样的内容只存一份；**从不重写已经写下的历史**（Codex 的 42 GB 就是重写出来的）。

| 东西 | 怎么存 | 上限 |
|---|---|---|
| 消息文字 | `events` 表原文 | — |
| 图片、自定义表情包 | 下载后算 sha256 存进 blobs，消息里只记哈希（复读、表情学习也靠这个哈希）。QQ 的临时链接不当身份用 | 单个 20 MB |
| 视频、文件、语音 | Go 视频及 file 段按内容 hash 保存；voice 段仍只记元数据。文件扩展按 ADR-261 复用媒体下载和媒体库，正文与合并转发同策略，从不自动打开或执行 | 视频及类型匹配的常见文件 ≤100 MiB 自动下；超限和其余文件手动，带进度与取消；无半文件保留 |
| 合并转发 | 收到就取，展开后的整棵树（JSON）存进 `qq_forwards` 表，消息上只记条数和前几行预览；陌生人发的不取（主窗口点开时才现取）。里面的媒体照样走 blobs，图照样识图（结果进 `media_descriptions`）。给她看的展开几行和写进占位的图（`line`、`forwardImgs`）跟着那条消息存进 `segments_json`，不另存；识图补上的描述和"图上的字"随那一行存进 `seen`（ADR-093，[规格-合并转发](规格-合并转发.md)） | 取树 10 层 / 200 条（预算用完不再往里取、不存空树，没取下来的条数记在树上 `truncated`）；给她看的展开 30 行 / 1500 字 / 16 张图 / 3 层 |
| 工具调用（新增） | `steps` 表（写这份时叫 `tool_calls`，实现时和思考记录合成一张）：工具名、参数、状态、用时、审批结果、输出预览；完整输出超过上限就存 blob | 参数 4 KB；预览保留开头和结尾共 16 KB；完整输出 blob 1 MB |
| Go 工作结果（K2） | `go/work/results/<随机ID>` 保存规范正文，trace 的 `result_refs` 保存精确 owner 与 SHA256；`steps.full_hash/result_ref` 关联详情，文件成功关闭和改名后才发布数据库引用 | 预览含包装 16 KiB；单结果 16 MiB（上限 64 MiB）、根 64 MiB（上限 256 MiB）；超限不删除旧证据 |
| 思考过程（新增） | 跟着那一轮存 | 32 KB |
| 模型调用记录 | 每次：模型、用时、token（input 和 cacheRead 分开，LESSONS 第一条）、各段的哈希 + 字数。**段的全文按哈希存一次**，人设没改就不会多存 | — |
| 完整请求 / 回复 | **默认不存**。只在出错时存一份（图片换成哈希，不存 base64），或者主人在主窗口打开"调试记录"时存 | 单份 2 MB |
| 后台判断（要不要接话、兴趣、她在想什么） | 每次一行：看了哪几条、结论、一句话理由、用了多少 token；提示词全文不存（同上，出错或调试才存） | 理由 300 字 |
| 程序日志 | **已被 ADR-367 改为**：纯文本一行一条（`时间 级别 模块 消息`），一天一个文件，不按大小切（见 [规格-日志分级](规格-日志分级.md) 第三、七节） | 见第四节 |

刷新页面以后工具卡片和思考还在，就是靠新增的 `tool_calls` 和思考记录（顺便修掉主窗口现在的这个问题）。

## 四、存多久

**不悄悄删**：所有清理都在后台维护里做，每次写一行日志"删了什么、多少、为什么"；运行页能看到每类占多大、下次会清什么，也能手动清。期限都能在设置里改。

| 东西 | 热（直接查） | 之后 |
|---|---|---|
| 本地的私聊、QQ 私聊 | 一直留 | 不删（是记忆的出处） |
| QQ 群消息 | 90 天 | 按月压成 zstd 归档（约小 6 倍）；记忆里引用到的那几条照样能翻原话 |
| 表情包 | 一直留（复读、表情学习要用） | 很久没人发、也没被记住的，主人可以在运行页手动清 |
| 群里的普通图片 | 60 天没被看过、也没被记忆引用（ADR-029：暂不执行，先都留着，以后做成设置项） | 删 blob，消息里留"图片已清理"和描述 |
| 工具完整输出 blob | 30 天 | 删，`tool_calls` 里的预览还在 |
| Go 工作结果（K2） | 活跃工作及仍被交接引用的证据一直留 | 显式解除引用且没有工作状态的结果 30 天后可回收；未发布孤儿超过一天才回收；不改变真实数据清理策略，归档删除仍等 Q6 |
| 模型调用记录 | 明细 14 天 | 之后只留按天、按模型、按角色的汇总（用量面板要用） |
| 出错 / 调试时存的完整请求 | 7 天 | 删 |
| 后台判断 | 30 天 | 删（"她在想什么"面板只看最近的） |
| 记忆召回日志（`trace.db` 的 `recall_log`，规格-记忆-v2 第七节） | 30 天 | 删（里面有查询原文；考题从这里取样，要留的先抄进 `data/dev/memory-eval/`） |
| 出站记数（她发到平台上的话里客服腔这类，真发的和试运行"她会说"的，`trace.db` 的 `outbound_hits`，ADR-110） | 一直留（命中一类才一行，很小；要量一段时间再定拦不拦） | 不删，维护不碰 |
| 程序日志 | **已被 ADR-367 改为**：14 天后删，不压缩（[规格-日志分级](规格-日志分级.md) 第七节；删除在第 8 步才实现） | 14 天 |

**总量上限**：数据目录设一个提醒线（默认 5 GB），超过就在通知中心提醒并列出最大的几类，不自动删。

## 五、SQLite 的设置

- 建库时：`journal_mode = WAL`、`journal_size_limit = 4 MB`（预写日志合并以后截短，不再一直占着）、`auto_vacuum = INCREMENTAL`（删了数据以后能原地变小）。已经存在的库要先整理一次才能切过去。
- 后台维护（每天一次，挑没在聊天的时候）：`wal_checkpoint(TRUNCATE)`、`incremental_vacuum`、`PRAGMA optimize`，然后做第四节的清理。
- 备份用 `VACUUM INTO` 出一份干净副本，不停服务。
- 不对正在用的库直接 `VACUUM`（要锁库，还要两倍空间）。

## 六、不许偷懒

- 不许每次调用都存完整请求"以后排查用"（MaiBot 的 1.5 GB、我们现在的 `request_json`）。
- 不许把 base64 图片写进任何记录或日志。
- 不许重写已经写下的历史（压缩上下文时只追加一条摘要）。
- 不许静默删除：每次清理都要能在日志和运行页看到。
- 不许只在一处做截断：所有写入路径（工具输出、日志、调试记录）共用同一个截断函数，并有测试。
- 截断要保证不切坏 UTF-8、留下"后面省略了多少"的标记，开头结尾都保留（错误信息常在最后）。

## 七、已知的坑

- SQLite 在一直有读者的时候合并不了预写日志，WAL 会越来越大；维护时先等空闲。
- `auto_vacuum` 只能在建表前设，老库要整理一次。
- blob 被删之前要确认没有消息、记忆、合并转发还引用它（记引用计数或删前查）。
- QQ 的图片 `file` 字段在 NapCat / SnowLuma 里不一定相同，哈希以下载下来的内容为准。
- Codex 那边 64 KiB 的截断在本机实测并没有完全生效（单条最大约 1 MiB）：我们自己的截断要用测试盯住。

## 八、验收

- 单元测试：截断函数（UTF-8、头尾、标记）；blob 同一内容只存一份、引用计数；清理只删到期且没被引用的。
- 用临时数据目录模拟一天的群聊（比如 5000 条消息、500 张图其中 300 张是重复表情包、2000 次后台判断、50 轮带工具的私聊），量出各部分大小，写进这份规格的第一节；目标：除媒体外每天 < 20 MB。
- 挂机测试加一列"数据目录大小"，看每天涨多少；预写日志文件不超过 4 MB。
- 清理跑一次以后，日志里能看到删了什么，运行页的数字对得上。

## 九、数据健康度（放在"运行 · 性能"）

和运行时的性能（内存、运行时长、挂机记录）放在同一页，数据来自每天的后台维护和挂机测试：

- 每类数据占多大（群消息、私聊、媒体、表情包、模型调用记录、工具输出、日志、归档），每天涨多少，按天画线。
- 每个库的预写日志文件大小（应 ≤ 4 MB），超了标黄。
- 上次维护的时间、用时，清了什么、多少（点开看清理日志）。
- 离总量提醒线（5 GB）还有多远；超过时通知中心提醒并列出最大的几类。
- 媒体去重省了多少（同一张表情包被发了几次）。
