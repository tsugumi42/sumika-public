## 二、先说人话

群里每个角色是一个独立的“实例”，各自装着系统提示词、工具声明、人设和群历史，各自调模型。一句主人的话最多让两位角色开口，没开口的角色不花钱。花钱的地方在三处：
1. **同一个角色在“主人叫她”和“接别人的话”之间切换时，工具声明变了**，实例重建、整段历史按全价重发。
2. **第二位自动接话**占了全部输入的三分之一。
3. **QQ 群的实例闲置太久被放掉**（再加上供应商缓存过期），回来时整段重发。这块 Go 在管，Bun 还没接 QQ。

## 四、改法候选

“预计省多少”都从上面的数推算，写明基准；有两个以上一起做的，不能把百分比直接相加（后一个的基数变小了）。**加权成本**是假设缓存读按 0.1 倍价算（比较用，不是账单）。

### A. 本地群聊的工具声明在“主人发起 / 接话”之间别翻转（新增，测量发现）

- **做什么**：`server/src/app.ts` 里 `tools()` 现在对 `g && !g.direct`（接话那一轮）只返回 `memory_search`。改成本地群聊的每一轮都声明同一组工具，接话那一轮靠 `server/src/local/gate.ts` 第 25 行已有的拦截（“这一轮不是主人发起的，群里不能用这个工具”）拒绝调用。
- **真实代码里翻转得更多**：`app.ts` 第 233 行附近，联网工具和记忆写入也是只给主人发起的那一轮（剧本没带）；别的代理刚合进的本地工具补齐（edit、grep、find、todo_write 等）也让“全套”变得更大，所以翻转时被冲掉的缓存更多，剧本的 −47% 在这一点上偏保守。剧本把工具集写死成补齐之前的五个，数字可重复。
- **预计省多少**：剧本里加权成本 108,088 → 57,436（**−47%**），换种子 −44%；整体可缓存前缀 61% → 90%，估算未命中 42% → 14%。代价是总输入多 10.7%（接话那一轮多带 4 个工具声明，但都被缓存）。真实群里的降幅取决于“主人点名”和“接话”交替的频率，剧本里 33 个非首次请求有 23 个翻转（70%），偏高。
- **代价与风险**：接话那一轮的模型看得到它不能用的工具，可能试着调用、被拦、多一次请求（频率未知，上线后看拦截次数）；拦截要给明确的原因，不让模型以为是故障。
- **和现有设计的冲突**：这是 ADR-269（“只有主人发起的那一轮才给执行工具”）的实现方式变化：从“不给”变成“给但拦”。声明不等于能用，但属于权限默认值的变化，**按 AGENTS 动手前第 4、7 条，要先问主人，并走独立复核**：核对表“形状 × 入口”——行：读 / 写 / 命令 / 记忆写入 / 联网 / 派活；列：主人点名、第一位无点名、接话、悄悄话、空工具名单；四种场合里只有本地群聊受影响，其余三种写“不可能”并各有测试。
- **要动哪些文件**：`server/src/app.ts`（tools 构造）、`server/src/local/gate.ts`（拦截文案和测试）、`server/test/local-group.test.ts`、`server/test/` 里 ADR-269 的审批测试；`chat.ts` 的 `acquire` 不用动。Go 的本地群聊是否同样翻转没核对（Go 只修 bug，不动）。
- **验收**：重跑 `server/scripts/group-playout.ts`，翻转请求为 0、整体可缓存 ≥ 85%；接话那一轮调用 `write` / `powershell` 被拦且原因出现在工具结果里。
- **不能靠中途 system 消息绕开**：pi 支持 `toolsAdded` / `toolsRemoved` 的中途 system 消息，但发给 Magpie 的 OpenAI 兼容接口会折叠成开头一条，等于还是在最前面变（见 pi-ai `transcript.d.ts` 的注释）。

### B. 第二位自动接话改成可选（ADR-352 候选 1 的剩余部分）

- **现状**：“只让点到的角色跑模型”在本地群聊里**已经是现状**，没点到的不跑。能再省的是第二位：没点名时轮转往后补一位，或第一位回复里点了另一位的名。
- **做什么**：把“自动接话”做成群的一个选项（默认 / 不默认待主人定）。关闭时，没点名只有轮转到的那一位回；第一位回复里点到的人仍可以回（那算被叫到）。或更温和：只在第一位回复里点名时才接，不再无点名补一位（B2）。
- **预计省多少**：剧本里接话请求占全部输入的 31.7%；关闭后总输入 −32%，加权成本在 A 之前约 −28%（接话请求更小、命中更低）；**先做 A 再做 B**时，B 能省的约是剩下的 1/3（每个主人发言 1.8 → 1.2 个请求，估算）。B2 省得少，只拿掉无点名补一位那几次（剧本 6 回合里的 6 个请求，约 3.2 万，占 14%）。
- **代价与风险**：群里“热闹感”下降，角色之间不再自己接话；规格-本地群聊的原话是“后一位看到前一位已经说完的话”，这是产品选择，不是技术问题。
- **和现有设计的冲突**：[规格-本地群聊](规格-本地群聊.md)第 43～46 行（最多两位、自动接话每位最多 1 次、冷却 5 秒）与 ADR-035 要改，需要先写 ADR。
- **要动哪些文件**：`server/src/local/localgroup.ts`（`round` 里的 `candidates` / `eligible`）、表 `local_groups`（加选项列要在 `native/internal/store/migrations/` 占号，ADR-345；或先只做配置键 `localGroup.autoRelay`，不动表）、`server/test/local-group.test.ts`（对拍 Go 的 `service_test.go` 那几组要同步改基线，Go 一侧不改，在 Bun 这边登记“有意改变”）。
- **验收**：剧本里 `autoRelay = off` 时每回合请求数 ≤ 点名人数 + 1（无点名时 1）；点名的两位都仍回。

### C. 实例重建：查清、再决定要不要调闲置回收（新增，测量发现）

- **现状**：Go 时代 QQ 群回合 67% 是重建，占未命中输入 81%。其中 30 分钟以上的间隔全是重建（命中 18%），这是闲置 45 分钟回收 + 供应商缓存过期叠在一起，本地基本不可避免；但**同群 2 分钟内也有 22 个重建**，系统提示词、工具、快照、模型都没变，原因没查到（报告 2.5）。
- **做什么**：1) 查那 22 个的原因（嫌疑：`Identity.Scope` 里的 `ActorID` 随触发者变；`staleGen` 被提前推进）；2) 实测各供应商缓存的实际有效时长（deepseek / agnes / claude 不同），再决定 `agent.idleMinutes` 要不要和它对齐；3) Bun 第 4 批移植 QQ 时，`acquire` 的复用条件逐条核对，不照抄“范围变了就重建”。
- **预计省多少**：只修 2 分钟内的重建：22 个 × 平均约 6.3k × 未命中约 80%，约占 Go 时代 QQ 群未命中输入的 **11%**。闲置回收对齐供应商过期不会省钱（过期了本来就要全价）。
- **代价与风险**：没有功能代价。如果原因在 Go 的 `turn/hub.go` `acquire`，是 bug 修复，Go 可以改；如果在设计上，转 Bun 的第 4 批规格。
- **冲突**：无。**要动哪些文件**：先只读排查；可能涉及 `native/internal/turn/hub.go`、`server/src/local/chat.ts` 的 `acquire`。
- **验收**：Go 时代同口径统计里，间隔 < 2 分钟的请求重建率 < 5%。

### D. 群历史做成共享可缓存前缀，人设和记忆放末尾（ADR-352 候选 2）——**测量支持不做**

- **假设**：把通用规则、场合、工具、群历史放前面，所有角色共用一串字节，只有人设和这一轮新话放在末尾，第二位角色就能吃第一位的缓存。
- **量到的**：把剧本的请求按这个排法重算（上限估算，报告 3.5），估算未命中从 42% 涨到 56%，加权成本 108k → 144k；和候选 A 一起做时也是 14% → 42%，57k → 118k。原因：人设约 2.2k 估算 token（占 29%）一挪到末尾就永远不被缓存；而每个角色自己的实例已经有 90% 的前缀命中，共享只多省“别人刚说的几句”。
- **还会冲突的设计**：pi 的 `systemPrompt` 是单独字段，Go 的 `prefixOf` 顺序是 通用规则 → 人设 → 场合，改顺序两边都要动；`toMessage(e, character)` 把自己的话写成 assistant、别人的写成 user，要改成中立写法；参考信息块（对面是谁、几点）每个实例各自一份，要统一；通用规则开头带角色名，也要挪走；人设放到历史后面对角色稳定性的影响**没量过**，要主人定，不是技术问题。
- **什么时候值得再看**：人设短到约 600 token 以下，或同群角色 ≥ 5 个且共享历史很长（每个请求“别人刚说的话”超过人设那么大）。现在的 3 个角色、30 条上限不满足。
- **预计省多少**：负数（上面）。**要动的文件**：不做，不列。

### E. 长历史按段压成共享摘要（ADR-352 候选 3）

- **现状**：历史是最近 30 条原文（`recentMessages`），重建时只给这 30 条。Go 有压缩快照（epoch），Bun 的 `history.ts` 能读快照但**还没有写快照的一步**（`chat.ts` 里没有压缩）。
- **做什么**：群里每攒够一段（比如 30 条之外的内容），由便宜模型压成一份**中立的**摘要（事实、结论、谁答应了什么，不带各自视角），存成会话的快照，所有成员的实例重建时都用同一份；最近 N 条仍给原文。
- **预计省多少**：历史约占请求的 33%（2.5k 估算）；摘要代替超过 N 条的部分，N 取 12 时历史 2.5k → 约 1.2k；只在重建时有效（接着用的实例前缀不变），所以按“重建占未命中 81%、历史占重建请求约 40%、摘要砍掉一半”估：QQ 群未命中输入 **−15% 左右**；本地群聊重建少得多（剧本里 3 次 / 36），收益更小，**本地群聊先不做**。摘要本身要花一次模型调用（输入约 3～4k，每攒一段一次），要从省下来的里扣。
- **代价与风险**：摘要更新时所有成员的缓存断一次；摘要质量（把“她说过不喜欢”写成“她是 AI 没有记忆”这类套话，LESSONS“总结提示词排除套话”）；摘要写进库是改“她看到的历史”，要有撤回、要留原文。
- **冲突**：和记忆系统的证据来源不能混（摘要不是证据）；Go 的压缩快照格式要共用（读同一张表，Bun 不自己建表，ADR-345）。
- **要动哪些文件**：`server/src/prompt/history.ts`（拼快照）、`server/src/local/chat.ts`（压缩触发）、`native/internal/store/migrations/`（如果要加列先占号）。
- **验收**：重跑统计，同口径下重建请求平均总输入降 ≥ 15%，抽检摘要 20 份，事实错误率为 0。

### F. 用便宜模型先定“谁接话”（ADR-352 候选 4）

- **现状**：谁接话是程序决定的（点名 / 轮转 / 回复里点名），不调模型，**不花钱**。加一个路由模型只有在它能比规则更准地“拦住不该有的接话”或“选对首位”时才合算。
- **做什么**：每个主人发言前先问一个小模型：“这句话该谁回？要不要有人接？”，输出角色 id 列表（0～2 个）；失败退回现在的规则。
- **预计省多少**：一次路由请求约 1k 估算 token（守卫类请求的平均）；一个接话请求约 5.5k（剧本里 71.7k / 13）。只要路由拦住约 1/6 的接话就不亏。按“接话占输入 32%、路由准确率 70%”：净省约 32% × 0.7 − 路由费 9% ≈ **13%**（路由费 = 20 回合 × 1k ÷ 22.6 万）。比 B 的 −32% 小，但保留了热闹。
- **代价与风险**：多一次串行请求，每个主人发言晚 1～2 秒才有第一个字；路由出错（漏掉该回的人）比多回一句难受；路由模型要有自己的评测。
- **冲突**：规格-两段式说话（私有存档）已经设想“先定动作再写话”，路由步可以并进它，别做成两套；ADR-352 里的 Work / Run 模型也有“谁负责”的概念，路由不应该自己存一份负责人。
- **要动哪些文件**：`server/src/local/localgroup.ts`（`round` 开头）、新增路由调用（走 `src/local/model.ts` 的便宜模型）、评测样本放 `data/dev/`。
- **验收**：拿真实群聊样本（用打码后的）比规则：该回的人 100% 在候选里；每个主人发言的路由耗时 p95 < 1.5 秒。

### G. 群里交代的事直接变成工作、指定负责角色（ADR-352 候选 5）

- **做什么**：主人在群里说“XX 你去做 …”，消息上给一个“转成工作”的入口（ADR-352 第 2 条已经定了），生成一个 Work，负责角色是那一位，之后的跟进走 Run（只带目标和进度），不再把整段群历史读一遍。
- **预计省多少**：**现有数据量不出来**。机制上，Run 的上下文是系统提示词 + 工具（约 2.7k 估算）+ 目标，对比群回合的 6～9k 估算，长任务的每次跟进可能省一半，要等 `server/src/work/` 的 Run 有真实用量再量。
- **代价与风险**：转工作是主人的显式动作还是模型自己判断，是权限问题（“主动活动可以观察、分析、私下提醒，对外动作另授权”，ADR-352 第 3 条）；群里谁能指派谁，要按 `ActorKind` / `ActorID` 认，不按名字认（LESSONS）。
- **冲突**：和 ADR-352 第 1、3 条一致，不冲突；它依赖 Work 的界面入口，排在会话结构界面里。
- **要动哪些文件**：`server/src/work/`（建工作时记来源群和负责角色）、协议里加一个方法（`protocol/sumika-rpc.json`，`scripts/gen-rpc.ts` 生成）。

### A′. 主人发起 / 接话各留一个实例（已做，代替 A）

- **做什么**：`server/src/local/chat.ts` 的实例按“槽”存：本地群聊里接话那一轮用 `<会话>` 加接话后缀的槽，主人发起的（点名、第一位）和别的场合照旧一个会话一个槽。两种轮的工具声明各自不变，来回切时两边的前缀（系统提示词 + 工具声明 + 历史）都接得上。**工具一个不多给**，ADR-269 的“接话那一轮只给 memory_search”照旧，不用问主人。
- **补消息**：`groupCatchUp` 原来只补别人说的（她自己的话默认已在实例里）。两个槽以后，她在另一个槽里说的话按她说的（assistant）补进来；这个槽上一轮自己说的（`ownSeqs`，收尾时记）跳过，不重复。
- **测量**（`server/scripts/group-playout.ts` 新加“按提供方缓存算”：和同一角色之前任一次请求比最长公共前缀。原来的“和自己上一次请求比”看不到两份前缀同时在缓存里，A′ 在那一栏不会变好）。缓存读按 0.1 倍价的加权成本：

  | 种子 | 一个实例（改前） | 两个槽（A′） | A（接话也给全套） |
  |---|--:|--:|--:|
  | 20261111 | 91,035 | 72,760（−20%） | 72,599 |
  | 7 | 86,993 | 70,224（−19%） | 70,473 |

  A′ 和 A 省得一样多，代价是每个角色多一个冷启动的实例（剧本里多 1～2 次重建）。输出在 `data/dev/bun-round6/group-playout/`。
- **和第二节的数对不上**：第二节、测量笔记里 A 是 108,088 → 57,436（−47%，按“和自己上一次请求比”）；在今天的代码上同一个口径 A 是约 10.2 万，复现不出 57k，原因没查（可能是之后合进的改动让 50 分钟重建后的请求前缀也变了，`#28` 之后几条在旧口径下都断）。以本节的数为准。
- **假设 [推断]**：提供方的缓存按内容前缀存，一个角色的两份前缀可以同时留着（DeepSeek、Anthropic、OpenAI 的提示缓存都是这样说的，这次没有联网核实）；Magpie 把同一模型的请求路由到不同上游时缓存本来就接不上，和 A′ 无关。
- **验收**：`server/test/local-group.test.ts`“主人点名和接话来回切”：第 5 次请求的开头逐字等于第 2 次整段请求，她在另一个槽里说的话只出现一次且是 assistant，丢实例时两个槽一起丢。改坏检查 6 项全红（`data/dev/bun-round6/改坏检查-群聊双实例.txt`）。

## 五、推荐顺序

1. **A 固定工具声明**。最大的一块（剧本 −44%～−47% 加权成本）、改动小、能立刻量出来；代价是动了权限默认值的“实现方式”，要主人点头并独立复核，所以放第一件，让主人先定这一条。
2. **C 查清实例重建**。零功能代价，纯排查，可以和 A 并行；QQ 群 11% 的未命中输入在这里，也决定 Bun 第 4 批怎么写 `acquire`。
3. **B 第二位自动接话改可选**（先做 B2：无点名不再补一位，再看要不要全关）。产品取舍，要主人拍板；放在 A 之后，因为 A 做完接话请求本身就便宜了，B 的收益降到约三分之一，值不值得牺牲热闹感看那时的数。
4. **E 共享摘要**，只先给 QQ 群（Bun 第 4 批一起），本地群聊重建少，不急。
5. **F 便宜路由**，只在主人选了 B 的“保留热闹”方向、又想要更准的接话时做；可以并进两段式说话。
6. **G 转成工作**，跟着会话结构界面和 Work 模块走，不单独排期。
7. **D 共享前缀：不建议做**（测量为负），除非主人想看人设放末尾对角色稳定性的影响——那是另一个实验，不是 token 问题。

依据：先做能量出数的、改动小的、不伤体验的（A、C），再做要主人取舍的（B、F），最后做依赖别的模块的（E、G）。D 的结论来自这次的估算，且估算偏保守，方向不会变。
